## 1. 业务侧方案设计

### 1.0 方案概览

基于 《调研文档》5.6 选型结论，OpenViking 作为主选型。本章按「概览 → 蓝图 → 架构 → 风险」四段展开：1.0 方案概览与核心概念速查，1.1 产品蓝图（一/二期业务需求与开发功能），1.2 业务架构（知识分层 L1/L2），1.3 系统架构（三层架构图 + 分期规划），1.4 方案级风险。接入与记忆模型见第 2 章。

**方案价值主张**：以「知识库」为中心抽象，OpenViking 为底座，叠加 ② 层知识库授权中心与 account 级隔离，实现跨 Agent 记忆复用、部门/个人/会话三级隔离与企业级合规治理——让 Agent 记得住用户、管得住知识、审得清访问。

**关键数字速览**：2 期演进（L1 基础 RAG + L2 记忆基础链路 → L1/L2 产品化 + 多 Agent 治理）· 3 层架构（①应用层 / ②授权中心 / ③单实例）· 1 个 OV 实例（account 级隔离）· 3 接入通道（Hooks / MCP / SDK）· 4 关键数据流路径 · 6 类知识库 · 7 类记忆类型 · 4 类企业侧扩展需求。

#### 1.0.1 核心概念速查

阅读本章架构图与目录表前，先掌握以下 6 个核心概念（架构图中 `(官方)` / `(企业侧扩展)` 标注依据此划分）：

- **官方原生**：OpenViking 开源产品自带的能力（4 命名空间 / 7 Hook / 9 MCP / L0-L2 分层 / RAGFS 存储引擎 / 多租户 account-user 模型等），开箱即用
- **企业侧扩展**：OpenViking 官方不提供、由本方案自建补齐的能力（② 层知识库授权中心 / account 级隔离 / 跨知识库联邦查询 / 180 天冷存 / KMS 审计等），用于满足企业级多 Agent 治理需求
- **② 层知识库授权中心**：本方案核心扩展组件，做 Agent×知识库 授权矩阵（哪个 Agent 能访问哪个知识库）+ 身份鉴权 + 路由 + 审计，Agent 不直连知识库、所有请求经此层
- **account 级隔离**：部门/公司等高敏知识库用独立 OpenViking account 部署（account 级逻辑隔离），复用官方 account/user 模型，单实例内实现部门/公司/个人三级隔离
- **跨知识库联邦查询**：② 层并行 fan-out 多个 account 检索再合并排序（单实例内跨 account），让一次请求触达多个库
- **知识库（KB）**：独立于 Agent 存在的记忆载体，按归属/用途分类（个人偏好/技能/项目上下文/部门SOP/公司政策/会话归档），Agent 被授权访问、不拥有

#### 1.1.2 一期蓝图：L1 基础 RAG + L2 记忆基础链路跑通

**一期目标**：用最简形态跑通 Agent↔L1+L2 双向闭环——**L1 侧**：从 Agent 获取信息（项目上下文 B1、Agent 生成文档 B3 写入 L1）+ 给 Agent 用（MCP search 检索召回返回 Agent）+ L1 向量知识库基础 RAG 可用 + RAG 可视化文件列表 + 支持选择企业传统知识库文档；**L2 侧**：从 Agent 获取信息（B4 偏好/事件/案例/技能经 Hooks auto-capture + Memory Extraction 写入 L2）+ 给 Agent 用（自动召回路径 3 + MCP search 路径 4）+ 会话归档冷存（commit→archive→180 天迁 TOS），均用默认配置。验证 OpenViking RAG + 记忆能力在企业场景下的可行性，同时为二期②层网关入口预埋。

#### 1.1.3 二期蓝图：L1/L2 产品化 + 多 Agent 治理

**二期目标**：L1 向量知识库产品化（各环节支持用户配置）+ L2 记忆产品化（提取规则/时机/画像更新策略可配置，基础链路一期已跑通）+ 多 Agent 多库统一治理。②层补全授权矩阵与跨 account 联邦，Agent 侧接入契约不变、零改造演进。

**业务背景**：2000 人规模互联网公司统一部署多类 AI Agent，知识库类型多（个人偏好/技能、项目上下文、部门 SOP、公司政策、会话归档等 6 类，见 1.3.3），且知识库天然需要被分享与复用。一期跑通了 Agent↔L1+L2 双向闭环（L1 基础 RAG + L2 记忆基础链路·默认配置），但 L1/L2 各环节不可配置、无法支撑多 Agent 协作，二期承接这些产品化与治理需求的落地（二期技术形态见 1.3.0 分期规划）。

**二期需求 → 开发功能 → 验收清单**：

| 业务需求                    | 开发功能                                   | 技术归属  | 依赖              | 验收标准                                              |
| ----------------------- | -------------------------------------- | ----- | --------------- | ------------------------------------------------- |
| L1 各环节可配置                | 切片策略 / Embedding 模型 / 检索参数 / Rerank 用户可配置 | 官方 + 企业侧 | 管理控制台           | 用户可在控制台配置切片策略、选择 Embedding 模型等                   |
| L2 记忆系统产品                | 提取规则（LLM 5 类分类）+ 时机（capture 门禁/commit 阈值）可配置 | 官方 + 企业侧 | 管理控制台           | 用户可配置记忆提取规则与 capture 时机                          |
| 需求一 · 一个 Agent 需要多个知识库源 | ②层跨 account 联邦 fan-out（单实例内多 account 并行检索 + 合并排序） | 企业侧扩展 | 授权矩阵            | 一次请求并行检索个人库+部门库+公司库，结果按相关度+知识库优先级合并去重             |
| 需求二 · 多个 Agent 共用一个知识库源 | 知识库独立化（独立创建/归属/授权登记）+ 同一库被多 Agent 授权访问 | 企业侧扩展 | 授权矩阵            | 公司政策库只存一份、全公司所有 Agent 只读共享，一处更新所有授权 Agent 即时生效    |
| 需求三 · 知识库类型多需统一治理与隔离    | ②层 RBAC + ACL 授权矩阵 + account 级路由 + 审计 + 成本归因 | 企业侧扩展 | KMS / audit log | 部门管理者可管控本部门库的 Agent 访问范围；token 成本可精确分摊到 Agent×知识库 |
| 需求四 · 新增 Agent 零改造接入    | ②层授权矩阵配置即可接入（解耦 Agent 与知识库）            | 企业侧扩展 | 授权矩阵            | 新增 Agent 仅在矩阵配置一行授权，不动任何知识库数据，零改造上线               |

> 综上：一期跑通 Agent↔L1+L2 双向闭环（L1 基础 RAG + L2 记忆基础链路·默认配置），二期面向 2000 人多 Agent 公司的真实场景——L1/L2 产品化（各环节/规则/时机可配置）+ 多 Agent 多库统一治理与分享，是知识库独立化、跨 Agent 协作记忆复用的二期目标。

#### 1.2.3 向量知识库 vs 记忆系统

| 对比点  | L1 向量知识库                       | L2 记忆系统                       |
| ---- | ------------------------------ | ----------------------------- |
| 核心问题 | AI 懂不懂企业资料                     | AI 认不认得用户                     |
| 数据来源 | 企业传统知识库(A) + Agent 中(B1/B2/B3) | Agent(B4)                     |
| 数据性质 | 静态文档型                          | 动态事件/画像型                      |
| 抽取方式 | 切片(按文档结构)                      | LLM 5类分类 + WM v2 压缩           |
| 检索单位 | 文档切片                           | 事件/画像/偏好                      |
| 命名空间 | `viking://resources/`          | `viking://user/` + `session/` |
| 召回方式 | 仅 MCP 显式检索(路径4)，不参与自动召回        | 自动召回(路径3) + MCP 显式检索(路径4)     |

> **L2 与 L1 的关系**：① L2 不读 L1 的业务文档（自动召回只搜 `user/memories` + `user/skills`，不搜 `resources/`，防跨命名空间泄露）；② L2 复用 L1 的 RAG 检索基础设施（记忆内容同样经 Embedding 向量化 + flat_hybrid + rerank 两阶段检索召回）。一句话：**L2 不读 L1 内容，但复用 L1 的 RAG 能力**。

#### 1.2.4 会话归档（archive）的双重角色

archive 在本架构中具有双重角色，需单独说明：

- **作为 L2 记忆系统的归档层**：会话结束/PreCompact 时触发 archive，落到 `viking://session/{sid}/archive/`，是记忆系统的冷数据层（对应 《调研文档》4.1 归档记忆）。
- **作为 L1 向量知识库的数据源**：archive 经沉淀/转存后，可提取有价值的项目上下文、决策案例等入库 `viking://resources/`，服务于向量知识库检索。
- **边界**：archive 原始归属 L2（记忆系统），转存后的衍生内容归属 L1（向量知识库）。180 天后迁 TOS 冷存（企业侧策略，1.1.2）。

#### 1.2.5 OpenViking 统一引擎

- 如 §1.2.1 底座层所示，OpenViking 官方定位 "Context Database for AI Agents"，L1 与 L2 由同一实例统一承载（喂文档=知识库、喂对话=记忆）。
- 产品概念上分层（L1 管"懂不懂资料"、L2 管"认不认得你"），实现上共用同一套 RAGFS + VectorDB 底座，靠 `viking://` 命名空间区分（`resources/` vs `user/`+`session/`）。
- 这也解释了为什么记忆系统能"复用 RAG 能力"——同一引擎、同一套向量检索链路（flat\_hybrid + rerank 两阶段检索，2.5）。

> 系统架构（Agent→授权中心→单实例）见 1.3.1；记忆类型与命名空间映射见 2.2；批量导入入口见 《调研文档》4.4.2；知识库归属类型见 1.3.3。


#### 1.2.6 L1 向量知识库能力规格

本节补充 L1 向量知识库在切片、检索、向量化、重排、多模态方面的能力维度，作为 §1.2.3 对比表与 §3.2 二期产品化的细化支撑。能力维度参考 VikingDB 向量知识库调研，具体数值以 OpenViking 实际能力为准。

**切片（Chunking）规格与管理**：

| 维度 | 说明 |
| --- | --- |
| 切片管理 | 支持查阅 / 编辑 / 删除切片（维度参考 VikingDB，OpenViking 切片规格以实测为准） |
| 元数据（meta） | 导入时可配置 doc_id 等元数据，便于按 ID 精准召回 |

**检索能力**：

| 检索能力 | 说明 |
| --- | --- |
| 语义检索 | 基于向量相似度的语义匹配（稠密） |
| 关键词检索 | 稀疏向量检索，适合专有名词、术语 |
| 混合检索（推荐） | 稠密 + 稀疏向量混合检索（OpenViking 为 flat_hybrid：dense + sparse + int8 量化） |
| 标量过滤 | 按元数据（doc_id、文档类型等）过滤检索 |
| 标签检索 | 支持按标签过滤检索（标签数量上限以 OpenViking 为准） |

**Embedding 模型**（OpenViking 支持，见附件3 §3.2）：

**Rerank 模型**：

OpenViking 采用两阶段检索（flat_hybrid 向量召回 → rerank 精排），rerank 模型通过 `ov.conf` 配置，具体模型以 OpenViking 实际支持为准。

**多模态文档支持**：L1 向量知识库支持多模态文档——图片（JPEG/PNG 等，OCR 解析）+ 视频（mp4）+ 图文 Embedding 模型（vision-text / vision-image），从文档解析到向量化全链路支持图文多模态。

### 1.3 系统架构

无论一期、二期，均为**单 OpenViking 实例**——通过 account 级隔离实现部门/公司/个人三级知识库隔离，不采用多实例物理隔离。本节承接 §1.2 业务架构的知识分层，给出系统如何部署实现（Agent→授权中心→单实例）。业务架构回答「知识是什么、怎么分层」，系统架构回答「用什么组件实现、怎么部署接入」。

#### 1.3.0 设计理念：单实例 + account 级隔离

OpenViking 官方提供通用记忆能力，业务上有 4 类需求（account 级隔离 / Agent×知识库 授权矩阵 / 跨 account 联邦查询 / 归档冷存 180 天迁 TOS）官方不解决或解决不足，需企业侧扩展（4 类需求与官方能力边界的详细对照见文末附录 A）。

> 以下架构图中，`(官方)` 标注为 OpenViking 原生能力，`(企业侧扩展)` 标注为本报告设计的企业侧治理逻辑。

**分期规划**

本方案按两期演进，②层网关入口一期即埋好，二期补全授权矩阵与联邦，Agent 侧接入契约不变、二期零改造：

| 维度   | 一期（公司云 Agent 平台现状）                         | 二期（目标态）                               |
| ---- | ------------------------------------------ | ------------------------------------- |
| 实例   | 单 OpenViking 实例（多 Agent 共用）              | 单 OpenViking 实例（不迁移，仅扩展 account）           |
| 授权矩阵 | 无（单 account 天然隔离）                         | 完整 Agent×库 矩阵（RBAC+ACL）               |
| account | 单 account（部门级）                              | 多 account（部门/公司/个人）+ 路由 + 跨 account 联邦 fan-out |
| ②层   | 简化：协议适配 + 身份鉴权 + 路由 + 审计 + 观测（矩阵/联邦缺席）     | 完整：协议适配 + 矩阵 + 鉴权 + 路由 + 联邦 + 审计 + 观测 |

> 二期的业务价值（一个 Agent 用多库 / 多个 Agent 用一库 / 多类型库治理 / 零改造接入）见 1.1.3。

**演进原则**：②层网关入口一期即部署（简化版），二期补全授权矩阵 + 联邦 + account 级路由；Agent 侧接入契约不变，二期零改造演进。

#### 1.3.3 知识库归属与授权模型

**知识库独立于 Agent 存在**：知识库独立于 Agent 存在，**支持单独创建**（如法务部门单独创建并维护法务知识库），也支持**在创建 Agent 时选择/创建知识库**（为 Agent 绑定其可访问的库）。Agent 不拥有知识库，只通过 ② 层授权矩阵被授权访问；同一知识库可被多个 Agent 访问，同一 Agent 可访问多个知识库。知识库的创建、归属、授权均经 ② 层知识库授权中心登记与治理。

**知识库类型与授权关系**：知识库按归属分为个人/项目组/部门/公司四类，类型多样、归属与敏感度各异（个人偏好低敏、部门 SOP 中敏、公司政策高敏只读）。② 层按 Agent × 知识库 做授权矩阵（RBAC + ACL），同一知识库可被多个 Agent 授权访问、同一 Agent 可访问多个知识库。具体的归属类型、命名空间、典型承载内容示例与授权矩阵样例见下。接入通道与 4 条数据流的端到端实证见第 2 章。

### 1.4 方案级风险（4 条）

以下 4 条为本方案（选 OpenViking + 单实例 account 级隔离架构）的方案级风险；记忆系统通用风险见 5.1。

1. **单产品绑定** — 若 OpenViking 项目停滞或不满足新需求，迁移成本高
   - **缓解**：接受单栈绑定风险。PoC 阶段充分验证 8 项核心能力 + 3 维 RAG 底座 + 5 道业务题覆盖度，确保上线前识别能力缺口。不预留 Adapter 抽象层（避免过度设计）。若未来确需迁移，按当时实际需求评估迁移成本（重评估触发条件见 5.2 第3条）。
2. **企业合规责任由部署侧承担** — OpenViking 不提供第三方 SaaS 合规证书；由于是自托管部署，数据不出企业，合规能力由公司内部审计 / 等保 / 数据驻留策略保证（**这是私有化部署的常规做法，不构成产品缺陷**）
3. **被动抽取质量需持续调优** — OpenViking 官方抽取管线（`compression.ov_wm_v2` + Memory Extraction，附件3 第 297-308 行）依赖 LLM 与 prompt
   - **缓解**：建立 golden set 抽取效果基线，定期回归；PoC 阶段用真实数据校准；利用 web-studio 检索轨迹可视化定位抽取偏差
4. **多知识库联邦查询延迟** — 本方案单实例 account 级隔离下，Agent 跨知识库召回需 ② 层 fan-out 多个 account 并行检索再合并排序，增加召回 P95 延迟
   - **缓解**：并行 fan-out（最多 5 个 account，`KB_FEDERATION_MAX_KB`）+ 8000ms 超时（`KB_FEDERATION_TIMEOUT_MS`）；高频知识库结果本地缓存（授权矩阵缓存 `KB_AUTH_MATRIX_CACHE_TTL=300s`）；Hooks 自动召回（路径 3）只查个人 account（单 account 无联邦），仅 MCP search（路径 4）才触发跨知识库联邦

### 2.1 接入通道

接入方式是 Agent 出站时用什么协议与本系统通信的选择，和数据流主干（①→②→③）是两件事：同一请求按 Agent 框架能力择一走 Hooks / MCP / SDK 通道，而非依次经过。接入方式不是数据流的"第二层"，而是 ① Agent 出站时的协议选择维度（官方 · 附件3 第 60-110 行）。

**三通道职责**

| 通道            | 驱动方式        | 覆盖能力                                                              | 适用 Agent                                                           |
| ------------- | ----------- | ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| Plugins·Hooks | 生命周期驱动·自动触发 | 7 Hook 覆盖读/写/归档/隔离四类                                              | Claude Code 等生命周期型 Agent                                           |
| MCP           | 模型意图驱动·按需调用 | 9 工具：search/read/list/store/add\_resource/grep/glob/forget/health | MCP 兼容 Agent（Cursor/Trae/OpenClaw 等）                               |
| SDK/HTTP      | 通用编程接入      | Python/Go/TS SDK + HTTP                                           | 无 MCP/Hook 能力的框架（LangChain/二期自建/特殊集成）；已有 Agent（CC/OpenClaw 等）走左两通道 |

**7 Hook 生命周期时间轴**（官方 · 附件3 第 75-83 行 · Plugins 通道自动触发）：

```
SessionStart ─► UserPromptSubmit(读) ─► Stop(写)
     │            │                       │
     │            └─► [模型可选调 MCP 9 工具]
     ▼                                    ▼
PreCompact(强制归档) ─► SessionEnd(收尾)  SubagentStart(隔离)
                                          └─► SubagentStop
                                               (子 Agent 归档)
```

> Hooks 与 MCP 互补：Hooks 保证记忆能力不依赖 LLM 意愿（自动 capture/recall），MCP 提供精细化操作能力（模型按需 store/search）。两者均经 ② 层协议适配归一为 OV HTTP 语义后鉴权路由。

**Agent 接入决策树**：

- **Claude Code / 同类生命周期型 Agent** → Plugins(Hooks) + MCP 双通道（自动召回 + 模型按需检索）
- **OpenClaw / Hermes** → 按其框架能力选择 MCP 通道或 SDK 通道（待 PoC 确认）
- **Cursor / Trae / 其他 MCP 兼容 Agent** → MCP 通道（9 工具）
- **LangChain / LangGraph / 二期自建 Agent** → Python/Go SDK + HTTP（无 MCP/Hook 能力时的通用接入；二期自建 Agent 上线后零改造复用已建的授权矩阵与单实例多 account）
- **新增 Agent 零改造接入**：只需在知识库授权中心配置 Agent×知识库授权矩阵，不动任何知识库数据（本方案解耦优势）

**② 层观测埋点独特价值**：② 层是所有 Agent 请求的唯一全量拦截点，在此埋点可捕获 100% 的 Agent×知识库访问（若埋点放各知识库实例内部，只能看到单实例视角，无法聚合）。具体价值：① 跨知识库归因——一次 Agent 请求可能触达多个知识库（联邦查询），只有 ② 层能记录"这次请求触达了哪些库"；② token 成本分摊——② 层知道 Agent 身份 + 目标知识库，能把 LLM/Embedding token 成本精确归因到"哪个 Agent 访问哪个知识库花了多少"，支撑按部门/Agent 的成本分摊。

### 2.2 记忆类型与分类

**分期说明**：本节及 §2.3-2.5 描述的记忆类型、记入、存储、召回模型**一期即适用**（基础链路·默认配置），二期为产品化（提取规则/时机可配置）。

记忆系统的本体是 OpenViking 官方定义的记忆分类，记入/存储/召回都围绕这些类型展开（官方 · 附件3 第 323-333 行）：

| 记忆类型   | 语义   | 承载内容                  | 落地命名空间                                  |
| -------- | ---- | --------------------- | ---------------------------------------- |
| preferences | 用户偏好  | 稳定偏好（编码习惯、语言、风格）        | `viking://user/{uid}/memories/preferences/` |
| events      | 事件    | 稳定事实、决策案例、关键事件          | `viking://user/{uid}/memories/events/`      |
| cases       | 案例    | 决策案例、问题解决经验             | `viking://user/{uid}/memories/cases/`       |
| memories    | 通用记忆  | 其他值得沉淀的稳定信息             | `viking://user/{uid}/memories/memories/`    |
| skills      | 技能    | 用户习得的操作方式、任务经验          | `viking://user/{uid}/skills/`               |
| archive     | 会话归档  | 单次对话上下文（20000 token 切分） | `viking://session/{sid}/archive/`           |
| resources   | 多模态资源 | 项目结构、部门 SOP、公司政策、知识规则 | `viking://resources/{project、team、public}/` |

> 记忆类型与知识库归属的映射见 1.3.3 知识库归属与授权模型——个人库承载 preferences/events/cases/memories/skills，部门库/公司库承载 resources，会话归档库承载 archive。

### 2.3 记忆记入模型

本节回答"什么场景、什么时机、用什么方式把记忆**记入**系统"。通道机制（Hooks/MCP 触发时机）引用 2.1，本节聚焦记入业务逻辑（门禁规则、抽取算法、落地命名空间）。

**场景 × 时机 × 记入方式框架表**：

| 通道（引用 2.1） | 场景         | 时机           | 记入方式                                                                               | LLM 介入                          | 落地命名空间                                      |
| ----------- | ---------- | ------------ | ---------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------- |
| Hooks（自动）   | 每轮对话结束     | Stop Hook 触发 | auto-capture.mjs 解析 transcript → shouldCapture 门禁 → buildParts → Memory Extraction | LLM 5 类分类 + WM v2 7 sections 压缩 | `viking://user/{uid}/memories/` 或 `skills/` |
| MCP（显式）     | 模型判断"值得沉淀" | MCP store 调用 | SDK 补 ID/元数据 → 服务端 LLM extraction + Embedding → 生成 L0/L1                           | LLM extraction + Embedding 向量化  | 指定知识库（含 resources）                          |

**自动记入流程**（Hooks 通道 · 对应 2.0 路径 1）：

```
Stop Hook 触发（每轮对话结束）
   │
   ▼
auto-capture.mjs 读 transcript_path → 解析 turn → 增量过滤（capturedTurnCount，避免重复 capture）
   │
   ▼
sanitize：剥离 <openviking-context> / <system-reminder> 等注入块（防污染回环）
   │
   ▼
shouldCapture 门禁（核心过滤规则）：
   - 长度门禁：低于阈值的不记入
   - 命令/问句模式：纯命令或纯问句不记入
   - 符号/关键词模式：无实质内容的不记入
   │
   ▼
buildParts：text→text part，tool_use/tool_result→tool part（output ≤2000 字截断）
   │
   ▼
★ ②层鉴权路由：Agent 身份鉴权（mTLS/JWT）→ 确认写入权限 → 路由到目标知识库实例
   │
   ▼
addMessage → POST 到目标实例的 OV Session（cc-<sha256(cc_session_id)>）→ 服务端处理（见 2.4 存储模型）
   │
   ▼
落地到 viking://user/{uid}/memories/{preferences|events|cases|...}/ 或 viking://user/{uid}/skills/
```

**显式记入流程**（MCP 通道 · 对应 2.0 路径 2）：

```
模型判断"这一条值得沉淀" → 调 MCP store 工具
   │
   ▼
★ 知识库选择 + 授权校验：Agent 指定目标知识库 → ②层校验写入权限（RBAC + ACL）
   │  ─ 无写入权限 → 拒绝 + 审计日志
   ▼
SDK 层补 ID + 元数据拼路径（企业侧扩展）
   │
   ▼
②层路由 → 目标知识库实例的 OpenViking HTTP/SDK → 服务端处理（见 2.4 存储模型）
```

> Hooks 自动记入覆盖绝大多数场景（无需 LLM 意愿判断），MCP 显式记入用于模型主动沉淀的精细化场景。两者均经 ② 层鉴权后进入服务端存储流程。

### 2.4 记忆存储模型

本节回答"记入后如何分层、压缩、归档存储"。对应 2.0 路径 1/2 中"服务端处理"段的内部逻辑。

**L0/L1/L2 三层结构**（官方 · 附件3 第 337-343 行）：

| 层级 | 文件形态           | 内容              | 加载策略                       |
| -- | -------------- | --------------- | -------------------------- |
| L0 | `.abstract.md` | LLM 生成的摘要（最精炼）  | 召回时优先加载，省 token            |
| L1 | `.overview.md` | LLM 生成的概览（中等粒度） | L0 空时 fallback L1          |
| L2 | 原文             | 完整原始内容          | 相关度高 + 预算充足时才加载（单条截 500 字） |

**Working Memory v2 Compression**（官方 · 附件3 第 297-308 行）：

- 触发：pending token ≥ 20000（COMMIT\_TOKEN\_THRESHOLD）时触发 commit
- 压缩方式：LLM Function Calling，按 WM 7 sections 结构化压缩
- 配合 Memory Extraction：LLM 按 MemoryTypeRegistry 5 类分类（preferences/events/cases/memories/skills）
- 输出：生成 L0 abstract + L1 overview + Embedding 向量化 → 落地到对应命名空间

**commit / archive 阈值与冷存**：

| 阶段      | 触发条件                   | 动作                                                          | 归属    |
| ------- | ---------------------- | ----------------------------------------------------------- | ----- |
| commit  | pending token ≥ 20000  | 触发 WM v2 压缩 + Memory Extraction + Embedding → 生成 L0/L1 → 落地 | 官方    |
| archive | 会话结束 / PreCompact Hook | session 内容打包归档到 `viking://session/{sid}/archive/`           | 官方    |
| 冷存      | 180 天未访问               | 迁移到 TOS 对象存储（按 URI 检索可恢复）                                   | 企业侧策略 |

> 官方 session archive 是会话级归档，企业侧 180 天迁 TOS 是冷存策略——两者不冲突，archive 是"会话结束归档"，180 天规则是"长期未访问冷存"。

### 2.5 记忆召回模型

本节回答"需要时怎么把记忆召回注入 Agent 上下文"。通道机制（Hooks/MCP 触发时机）引用 2.1，本节聚焦召回算法（排序、过滤、预算、降级）。

**自动召回 + 显式召回对比表**：

| 通道（引用 2.1） | 触发                       | 召回范围                                                                 | 排序与过滤                                                                                                               | 预算与降级                                                                                |
| ----------- | ------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Hooks（自动）   | UserPromptSubmit Hook    | 仅 `viking://user/memories` + `skills`（官方安全边界，resources 不参与，防跨命名空间泄露） | base score + leafBoost + eventBoost + prefBoost + lexicalOverlap → score≥0.35（SCORE\_THRESHOLD）→ 去重 → recallLimit=6 | 2000 token 内（RECALL\_TOKEN\_BUDGET）注完整内容，超出降级为「URI + 相关度%」；注入 `<openviking-context>` |
| MCP（显式）     | 模型判断"6 条不够" → MCP search | 可覆盖 `viking://resources`（自动召回不搜的范围），跨 account 联邦 fan-out 多 account 并行检索（单实例内）             | 各实例两阶段检索（flat\_hybrid dense+sparse+int8 量化 → doubao-seed-rerank 精排）→ 多库结果按相关度+知识库优先级合并 → 去重 → Top-K                 | 返回 L0/L1 摘要 + 按需 MCP read 加载 L2 详情                                                   |

**自动召回流程**（Hooks 通道 · 对应 2.0 路径 3）：

```
UserPromptSubmit Hook 触发（用户每次提交 prompt）
   │
   ▼
auto-recall.mjs 通过 stdin 拿到 prompt / session_id / cwd
   │
   ├─ 命中 bypass / query<3 字符 / server offline → 直接 approve（跳过）
   ▼
★ ②层鉴权路由：Agent 身份鉴权 → 获取授权知识库列表 → 路由到目标实例
   │
   ▼
多路检索：POST /api/v1/search/find（发往授权的个人知识库 account）
   │
   ▼
★ 自动召回边界（官方安全边界，附件3 第 345-350 行）：
   只搜 viking://user/memories + viking://user/skills
   viking://resources 不参与自动召回（防跨命名空间泄露）
   │
   ▼
排序：base score + leafBoost + eventBoost + prefBoost + lexicalOverlap
   │
   ▼
score ≥ 0.35 过滤（SCORE_THRESHOLD）+ 去重 + 取前 recallLimit=6
   │
   ▼
内容解析：优先 L0 abstract，abstract 空时 fallback L1 overview，
        相关度高 + 预算充足时才拉 L2 全文（单条截 500 字 RECALL_MAX_CONTENT_CHARS）
   │
   ▼
预算：2000 token 内（RECALL_TOKEN_BUDGET）注入完整内容，
     超出降级为「URI + 相关度%」
   │
   ▼
输出 <openviking-context> 注入块 → 追加到用户 Prompt 前
   │
   ▼
SDK 层按授权矩阵过滤（企业侧扩展 · 知识库授权中心已校验）
   │
   ▼
SDK 发 OTel Trace + Prometheus 指标（命中率 / 延迟 / llm_token_usage / embedding_token_usage）
```

**显式召回流程**（MCP 通道 · 对应 2.0 路径 4）：

```
模型判断"自动注入的 6 条不够" → 调 MCP search 工具（可指定 scope + 知识库）
   │
   ▼
★ ②层鉴权：Agent 身份鉴权 → 获取授权知识库列表 → 确认目标知识库读权限
   │
   ▼
★ 跨知识库联邦查询：②层 fan-out 到多个授权 account 并行检索（单实例内）
   │  ├ 个人偏好知识库 account（viking://user/）
   │  ├ 部门 SOP 知识库独立 account（viking://resources/team/{dept}/）
   │  └ 公司政策知识库只读 account（viking://resources/public/）
   ▼
各知识库实例执行两阶段检索
   │
   ├─ 阶段 1：flat_hybrid（dense + sparse + int8 量化）向量召回
   └─ 阶段 2：doubao-seed-rerank 精排 + 阈值过滤
   │
   ▼
★ 可覆盖 viking://resources（自动召回不搜的范围），由模型显式指定 scope
   │
   ▼
合并排序：多知识库结果按相关度 + 知识库优先级合并 → 去重 → 取 Top-K
   │
   ▼
返回 L0/L1 摘要 + 必要时按 URI 调 MCP read 加载 L2 详情
```

> **自动召回 vs 显式召回的边界**：自动召回（Hooks）保证每轮对话都有基础记忆注入（6 条内、2000 token 预算），不依赖 LLM 意愿；显式召回（MCP）让模型按需深挖（跨 account 联邦、可覆盖 resources）。两者互补，共同构成完整的记忆召回能力。

## 附录 A：企业侧扩展需求详述

**为什么需要"企业侧扩展"？** OpenViking 是面向个人开发者 / 小团队的通用开源产品，官方只提供必要且通用的能力（4 个顶级命名空间、7 Hook、9 MCP 工具、LLM+Embedding+VLM 三分工）。业务上有 4 类需求官方不解决或解决不足，需企业侧扩展。下表对照官方能力缺口与企业侧方案：

| # | 企业需求 | OpenViking 官方能力 | 官方缺口 | 企业侧方案 | 依赖 |
| --- | --- | --- | --- | --- | --- |
| 1 | 部门级隔离（设计部/研发部 SOP 不串数据） | account 级逻辑隔离（Concepts 11） | account 级隔离可用；缺口在跨 account Agent 授权 | ② 层授权矩阵 + account 级隔离（复用官方 account 模型） | ② 层 + account 模型 |
| 2 | Agent×知识库 授权矩阵（哪个 Agent 能访问哪个库） | account/user 模型 | 表达不了跨租户 Agent 授权关系 | ② 层授权中心 RBAC + ACL | KMS / audit log |
| 3 | 跨知识库联邦查询（一次请求触达多库） | 单实例多 account 视角（account 间不互通） | 无跨 account 联邦能力 | ② 层 fan-out 多 account 并行检索 + 合并排序（单实例内） | 授权矩阵 |
| 4 | 归档冷存 180 天迁 TOS | resources 挂 S3 | 无"180 天规则"企业侧策略 | 180 天未访问迁移 TOS 对象存储 | TOS |

> 以上 4 类企业需求对应的核心概念（官方原生 / 企业侧扩展 / ②层知识库授权中心 / account 级隔离 / 跨知识库联邦查询 / 知识库 KB）定义见 1.0.1 核心概念速查。

## 附录 B：设计理念：分界与承接

- **官方能力**：解决"记忆怎么读、怎么写、怎么召回、怎么分层、怎么被 LLM 结构化压缩"+ account/user/peer 多租户隔离 + ROOT/ADMIN/USER 角色权限——**覆盖记忆读写/召回/分层/压缩/多租户隔离**。
- **企业侧扩展**：解决"哪个 Agent 能访问哪个知识库、跨 account 联邦查询、account 级隔离、审计怎么落"——**覆盖 Agent×知识库 授权/联邦查询/account 级隔离/审计**（官方 account/user 模型表达不了这种跨租户 Agent 授权关系）。
- **两者接口**：企业侧扩展**不改 OpenViking 源码**，通过 ② 层知识库授权中心（网关模式）实现——
  0\. **协议适配**（入站首步）：多 Agent 消息格式异构（Hooks transcript JSON / MCP 工具调用 / SDK 编程对象），② 层入站时先归一为 OpenViking 的 `viking://` + REST 语义（addMessage/search/find + commit/archive），再进入鉴权；
  1. **身份鉴权 + 授权决策**：归一后验 mTLS/JWT 令牌 → 查 Agent×知识库 授权矩阵（允许/不允许）→ 放行或拒绝；
  2. **路由转发 + 联邦查询**：放行后路由到目标知识库实例；跨库召回时 ② 层 fan-out 多实例并行检索再合并排序。
- **好处**：OpenViking 升级 → ② 层授权中心无需重写（仅靠 HTTP 网关转发对接）；合规责任边界清晰（与 1.4 风险 2 一致）。
