## 1. 业务背景

**术语约定**（按主题分组）：

**① Agent 名称**（公司统一部署的外部 AI Agent）
- **Hermes**：外部第三方 AI Agent，公司部署使用，与 Claude Code 同类。
- **OpenClaw**：外部第三方 AI Agent 平台，公司部署使用。

**② 核心概念**
- **云端 Agent 记忆系统**：正式术语；正文尽量避免"云 Agent / 记忆中间件"混用。
- **知识库（Knowledge Base）**：本方案的核心抽象，指组织/部门/个人拥有的一组结构化记忆集合（含偏好/技能/会话/项目上下文/SOP/政策等），物理上对应一个或多个 OpenViking 实例的区域（namespace 或整实例）。Agent 不拥有知识库，只被授权访问；一个 Agent 可同时访问多个知识库，多个 Agent 可访问同一知识库。全文"知识库"即此义，不再用缩写 KB。

**③ 基础设施与服务**
- **KMS（Key Management Service）**：密钥管理服务，管理知识库实例的静态加密密钥与租户密钥，由企业侧部署（火山引擎 KMS 或同类产品），被 ②③ 层调用。
- **TOS**：火山引擎对象存储（Tinder Object Storage），用于知识库 180 天冷存归档与原始附件存储。

**公司规模与场景**：互联网公司 **2000 人规模**，希望在云端搭建**云端 Agent 平台**，为员工统一部署 **Claude Code / OpenClaw / Hermes** 等多类 AI 智能体，未来仍会持续接入新 Agent。

**当前痛点**：

> 根因：当前部署的 Agent **既无独立记忆系统，也无 RAG 知识库**，上下文只存在于单次会话的临时窗口，导致执行质量与成本双重问题。

- **原生记忆弱 → 执行质量差**：Claude Code / OpenClaw 等仅有基础会话上下文，原生记忆能力弱、跨会话即失忆，无用户偏好/项目结构/部门 SOP 的持久承载，每次都从零开始，输出频繁偏离规范、重复试错
- **无 RAG 知识库 → 知识无法沉淀复用**：部门规范、项目文档、历史决策没有统一入库与语义检索入口，Agent 无法按需调取权威资料，只能靠用户手工粘贴。**RAG 知识库的价值**（参考 OpenViking 官方定位"Context Database for AI Agents"）：把文档/SOP/代码统一入库 + 语义索引 + 按需检索，Agent 像查文件系统一样调取权威知识，告别手工粘贴、避免凭空臆造
- **使用成本高**：跨会话记忆缺失（同一用户明天再来还要"重讲一遍"）+ 跨 Agent 上下文不复用（Claude Code 写入的偏好，OpenClaw/Hermes 读不到）→ 重复输入、重复 token、重复人工校对
- **数据边界模糊**：部门 / 个人间无统一治理入口，安全、审计、合规无处落地

**目标形态**：为云端 Agent 挂载**以「知识库」为中心的记忆系统**——知识库按归属与用途分类（个人偏好库 / 个人技能库 / 项目上下文库 / 部门 SOP 库 / 公司政策库 / 会话归档库，详见 §6.2.3），Agent 不拥有知识库、只被授权访问。具体具备：

- **按库分类承载**：短期（会话内）+ 跨会话工作 + 长期稳定 + 归档冷存，分别落在对应类型的知识库
- **隔离分两层**：
  - **规范库（逻辑隔离）**：个人偏好/技能/会话归档等，共享实例内以 namespace 隔离
  - **实例库（物理隔离）**：部门 SOP、公司政策等高敏/只读库，用独立 OpenViking 实例隔离（多实例物理隔离，见 §6.2.0）
- **迁移与授权**：一个 Agent 可访问多个知识库（跨库联邦查询，见 §6.2.0）；**一期按 1 实例↔1 Agent↔1 库的最简映射（多 Agent 并存、各自 1-to-1）先跑通**，二期扩展为 1 Agent↔N 库 + 多实例池 + 跨库联邦（见 §6.2.0 分期规划）
- **企业级治理**：Agent×知识库 授权矩阵 + ACL + 审计 + 合规 + 可观测（见 §6.2.1 ②层）

> 具体的落地模式与产品选型延后到 §5 候选调研与 §6 业务侧方案设计，本章不预设结论。

## 2. 典型用户

本报告涉及三类用户，按「使用—治理—建设」分层：

**A · Agent 使用方**（通过 Agent 消费记忆系统）

- **个人用户**（研发/产品/设计等员工）：使用 Claude Code / OpenClaw / Hermes 完成日常任务，需要记住个人偏好、项目状态、常用规范
- **团队 / 业务知识库维护方**（如法务部门）：负责维护本业务领域的知识库（法务知识库、研发 SOP 库等），既是使用方也是该库的内容治理方

**B · 公司 / 部门**（管理视角 · 监察与统一治理）

- **部门管理者**：关注本部门知识库的内容合规、访问审计、敏感数据不外泄
- **公司治理层**（安全/合规/审计）：关注 2000 人规模下的统一治理入口、数据驻留、GDPR/个保法、跨部门数据边界、成本与可观测大盘

**C · 云端 Agent 团队**（平台建设与运营方）

- **平台工程**：负责知识库实例池部署、Agent 接入、②层授权中心、隔离与生命周期治理
- **安全 / 合规工程**：落地 ACL、审计日志、KMS 密钥、数据驻留策略
- **可观测工程**：负责命中率、污染率、P95 延迟、LLM/Embedding token 成本等运行指标

## 3. 要解决的问题

> 由 §1 痛点与 §5 候选调研提炼。聚焦两类核心问题，对应 §6 选型与方案设计要回答的设计目标：

**问题一 · Agent 原生记忆弱且无 RAG**（使用侧）

- Claude Code/OpenClaw 等原生记忆弱、跨会话失忆、跨 Agent 不复用，且无 RAG 知识库、部门文档/SOP 无入库入口 → 执行质量差、使用成本高
- 要回答：记忆怎么分层承载（短期/工作/长期/归档）、怎么自动沉淀与按需召回、怎么把部门文档/SOP 入库做语义检索供 Agent 按需调取（RAG 价值）

**问题二 · 企业级多 Agent 记忆系统建设**（治理与建设侧）

- 2000 人多 Agent 共存下，如何做部门/个人/会话三级隔离、Agent×知识库 授权、跨库联邦、审计与成本治理
- 要回答：库怎么分类与隔离（规范库/实例库）、Agent 怎么被授权访问多个库、新增 Agent 如何零改造接入、合规与可观测怎么落

> 以上两类问题在 §6 选型与方案设计中进一步拆解为 5 道业务题（Q1 跨 Agent 共享 / Q2 短期+长期闭环 / Q3 三级隔离 / Q4 企业级治理 / Q5 可观测）。

## 4. Agent 记忆系统：定义、边界与能力框架

**定义**：Agent 记忆系统是位于 **Agent Runtime（Agent 运行时，即 Agent 执行对话/工具调用的运行环境）与知识/存储底座之间**的**上下文管理层**，由「记忆分层 + 写入判断 + 召回 + 生命周期治理 + 跨 Agent 共享 + 治理审计」几个部分组成，把会话中产生的事实、偏好、任务状态与可共享知识，沉淀为可写入、可检索、可治理、可审计的记忆，按用户/部门/Agent/会话边界安全召回。

**组成部分简介**：
- **记忆分层**：短期上下文 / 工作记忆 / 长期记忆 / 归档记忆四层（见 §4.1）
- **写入判断**：决定什么该被记住、由谁写入、记到哪一层
- **召回**：按任务按需检索并注入上下文
- **生命周期治理**：何时更新、合并、归档或删除
- **跨 Agent 共享**：多 Agent 安全复用同一份记忆/知识
- **治理与审计**：ACL、来源追溯、审计日志

**与 RAG / 向量数据库的边界**：RAG / 向量数据库主要解决"从资料中找相关内容"；Agent 记忆系统还要解决**什么应该被记住、由谁写入、谁可以使用、何时更新或删除、如何跨 Agent 共享、如何避免记忆污染**。本方案的 RAG/向量底座能力见 §4.5。

### 4.1 记忆系统的组成层次

| 层次        | 生命周期    | 典型内容                 |
| --------- | ------- | -------------------- |
| **短期上下文** | 单次会话内   | 当前对话轮次、临时变量、工具调用中间结果 |
| **工作记忆**  | 跨会话、任务级 | 未完成任务状态、过程草稿、暂存偏好    |
| **长期记忆**  | 跨用户生命周期 | 稳定事实、偏好、部门 SOP、项目知识  |
| **归档记忆**  | 冷数据     | 时效过期但需保留的历史条目        |

### 4.2 参考实践

| 参考对象               | 一手事实                                                                                                                                                                                          | 可迁移原则                                                                                   |

### 4.3 记忆系统的产品形态

| 形态            | 代表                     | 边界                                                 |
| ------------- | ---------------------- | -------------------------------------------------- |
| Agent 内置长期记忆  | Claude Code、Coze LTM   | 平台内部闭环；Coze LTM 是 Coze 记忆资源之一（Coze 完整记忆分层见附件2 B.1） |
| 平台型知识库 / 应用记忆 | Dify、Coze              | 应用内可用，不天然跨 Agent                                   |

### 4.4 Agent 记忆系统核心能力

本节给出 Agent 记忆系统的 8 类核心能力框架（4.4.1 作用域与隔离 / 4.4.2 记忆写入 / 4.4.3 记忆类型 / 4.4.4 记忆召回 / 4.4.5 生命周期 / 4.4.6 跨 Agent 共享 / 4.4.7 治理与安全 / 4.4.8 可观测性），按「能力类 → 必要能力 → 能力说明」三层展开。这 8 类能力对应完整记忆闭环：写入前先判断作用域和权限，写入时记录来源和类型，运行时按任务召回，长期通过生命周期治理保持准确，并通过可观测指标发现污染、延迟和成本问题。此框架同时作为 §5 候选调研的评估维度。

#### 4.4.1 作用域与隔离

| 功能   | 子能力         | 能力说明                                                                                                            |
| ---- | ----------- | --------------------------------------------------------------------------------------------------------------- |
| 隔离层级 | 用户级隔离       | 每个自然人独立命名空间，防止跨人污染                                                                                              |
| 隔离层级 | 部门/团队级隔离    | 按组织层级隔离记忆域，支持部门间共享或独占                                                                                           |
| 隔离层级 | 项目/资源级隔离    | 以项目、知识库或资源为边界，跨用户共享同一份项目记忆                                                                                      |
| 隔离层级 | Agent 级隔离   | 不同 Agent（Claude Code / Hermes / OpenClaw 等）可持有独立或共享记忆                                                           |
| 隔离层级 | 会话级隔离       | 单次会话/任务的短期上下文与长期记忆解耦                                                                                            |
| 权限模型 | 命名空间与 ID 体系 | user\_id / agent\_id / run\_id / app\_id / workspace 等多级 ID 组合                                                  |
| 权限模型 | 访问控制 ACL    | Read / Write / Delete / Share 细粒度权限（能力上限，如 Cognee dataset 粒度 4 类 ACL）；本方案据 Agent 意图驱动特性降为布尔粒度（允许/不允许），详见 §6.2.3 |
| 权限模型 | 多租户与数据驻留    | 租户级密钥、region 隔离、私有化部署可控                                                                                         |

#### 4.4.2 记忆写入

| 功能   | 子能力     | 能力说明                            |
| ---- | ------- | ------------------------------- |
| 写入方式 | 显式写入    | Agent 或用户主动通过 API/工具调用把事实写入长期记忆 |
| 写入方式 | 自动抽取    | LLM 从对话/文档中被动抽取事实、偏好、关系并入库      |
| 写入方式 | 批量导入    | 从文件、外部知识库、历史会话批量导入              |
| 写入治理 | 来源记录    | 每条记忆保留来源 URL / 会话 ID / 用户 / 时间戳 |
| 写入治理 | 写入确认与撤回 | 支持写入前确认、写入后撤回，避免误写污染            |
| 写入治理 | 幂等与去重   | 同一事实多次写入不产生重复条目                 |

#### 4.4.3 记忆类型

| 功能     | 子能力    | 能力说明                 |
| ------ | ------ | -------------------- |
| 结构化记忆  | 事实型    | 人名、时间、数值、状态等原子事实     |
| 结构化记忆  | 偏好型    | 用户偏好、风格、口味、习惯        |
| 结构化记忆  | 实体-关系型 | 人-项目-文档等图状关联，支持图检索   |
| 半结构化记忆 | 过程型    | 任务步骤、流程状态、Agent 执行轨迹 |
| 半结构化记忆 | 任务状态   | 待办、进行中、已完成的任务上下文     |
| 非结构化记忆 | 文档型    | 长文档、笔记、纪要、代码片段       |
| 非结构化记忆 | 多模态    | 图像、音频、视频及其描述文本       |

#### 4.4.4 记忆召回

| 功能   | 子能力       | 能力说明                          |
| ---- | --------- | ----------------------------- |
| 召回维度 | 按任务/查询召回  | 基于当前对话或工具调用意图检索相关记忆           |
| 召回维度 | 按用户/主体召回  | 按 user\_id / agent\_id 限定召回范围 |
| 召回维度 | 按时间召回     | 支持时间窗、最近 N 条、时间衰减加权           |
| 召回维度 | 按来源/重要性召回 | 按来源可信度、访问频次、置信度加权             |
| 召回控制 | Top-K 与阈值 | 控制返回条数与最低相关度门槛                |
| 召回控制 | 多信号融合     | 语义 + 关键词 + 元数据 + 图 多路合并排序     |
| 召回控制 | 上下文注入策略   | 决定召回结果如何拼接进 Agent Prompt      |

#### 4.4.5 生命周期

| 功能    | 子能力    | 能力说明                                       |
| ----- | ------ | ------------------------------------------ |
| 去重与合并 | 语义去重   | 同义/近似事实归并成单条记忆                             |
| 去重与合并 | 冲突解决   | 新旧事实冲突时按时间/来源/置信度裁决                        |
| 更新与版本 | 记忆更新   | 支持字段级或整条更新，保留历史版本                          |
| 更新与版本 | 版本化与回溯 | 记忆变更可审计、可回滚                                |
| 遗忘与归档 | 时间衰减   | 长期未使用记忆分数衰减、退出热召回                          |
| 遗忘与归档 | 自动归档   | 冷记忆迁移到归档层或对象存储                             |
| 遗忘与归档 | 删除与遗忘  | 显式删除、级联删除（连同引用与摘要一并清理，即"被引用清理"）、GDPR 遗忘权支持 |

#### 4.4.6 跨 Agent 共享

| 功能   | 子能力           | 能力说明                                     |
| ---- | ------------- | ---------------------------------------- |
| 接入形态 | API / HTTP 接口 | 语言无关，任何 Agent 可通过 HTTP 接入                |
| 接入形态 | 多语言 SDK       | Python / TypeScript / Go 等主流语言 SDK       |
| 接入形态 | MCP 协议        | 通过 Model Context Protocol 让新 Agent 零改造接入 |
| 共享语义 | 统一 schema     | 事实/偏好/文档等类型有跨 Agent 一致定义                 |
| 共享语义 | 共享/私有边界       | 明确哪些记忆全 Agent 可读、哪些仅本 Agent 可读           |
| 共享语义 | 冲突协调          | 多 Agent 同时写入时的锁/合并/顺序策略                  |

#### 4.4.7 治理与安全

| 功能    | 子能力        | 能力说明                                                      |
| ----- | ---------- | --------------------------------------------------------- |

### 5.1 OpenViking（详尽）

- **定位**：火山引擎开源记忆中间件；文件系统式抽象；AGPL-3.0

- **独特短板**：部门级 ACL / 合规资质需自建；SDK 覆盖 Python/Go/TS（TS 为社区/实验性支持）；实体-关系记忆弱

### 5.2 Mem0（重点）

- **定位**：开源个人化记忆中间件；LLM 自动抽取事实/偏好；4 级 ID 隔离

### 5.3 Letta（原 MemGPT）（重点）

### 5.4 Cognee（概览）

### 5.6 业务侧选型结论

#### 5.6.1 业务约束与选型范围

**业务约束**：

- 2000 人并发
- 多 Agent 共存：Claude Code / OpenClaw / Hermes + 未来
- 隔离：部门 → 个人 → 会话 三级（对齐 Q3 三级隔离）

- 使用成本高（重复输入、重复 token、重复人工校对）
- 数据边界模糊（部门/个人间无统一治理入口）

**对齐 §3 五道业务题**（选型与方案须逐一回答）：

| ② 知识库（文档型+混合型承载）           | ✅ 文件系统范式匹配文档结构；L0/L1/L2 下钻定位；Memory+Resources 统一承载记忆与文档                                      | ⚠️ 文档型承载弱；无资源范式                 | ⚠️ archival ≤300 tokens 限制大文档                            | ⚠️ 文档→图谱丢失原文档结构；记忆与文档非统一范式      |

| ④ 一体化（记忆+知识库统一引擎）          | ✅ Context Database，喂对话=记忆、喂文档=知识库，统一 viking://（附件4 第 11 行）                                   | ❌ 仅记忆中间件                        | ❌ 仅记忆+工具                                                 | ⚠️ 以图谱为核心，非"记忆+知识库"双范式          |
| ⑤ 落地约束（许可/运维/生态）           | ⚠️ AGPL-3.0 传染性 + 自建向量库 + 生态约 6 个月                                                           | ✅ Apache-2.0 友好 + 20+ 后端可插拔     | ⚠️ Enterprise 需付费 + 显式调用成本                               | ✅ Apache-2.0 友好 + 图后端运维成本高      |

> **能力维度是记忆系统命脉**：本方案为**多知识库架构**（个人/部门/公司多库分担负载，见 §6.2.1 ③层（多知识库实例池）），2000 人高频场景下各实例按隔离粒度承载相应负载；能否把长对话自动压缩为按需加载的分层摘要，决定 token 成本与召回质量。OpenViking 是 4 款中唯一具备"transcript→commit→archive→L0/L1/L2 完整会话压缩管线 + 三层信息结构 + Memory/Resources/Skills 三类上下文统一"三合一能力的产品；Cognee 以知识图谱为核心（remember→图谱），无分层压缩归档管线，更适合作为关系推理增强层而非独立承担会话记忆。
>
> **一体化维度是本场景刚需**：本报告要建"记忆+知识库"混合系统（部门 SOP + 项目上下文 + 个人偏好），OpenViking 官方定位即"Context Database for AI Agents"（附件4 第 11 行），以统一 viking:// 文件系统同时承载会话记忆与文档资源，是 4 款中范式统一性最完整的方案；Cognee 的对话与文档均归一为知识图谱，非"记忆+知识库"双范式。
>
> **落地约束决定适用场景**：OpenViking 的 AGPL-3.0 传染性许可证对闭源商用产品有法律风险，且需自建向量库、生态仅约 6 个月（2026-01 开源）。本报告场景为**公司内部云端 Agent 平台、自托管内网部署**，AGPL-3.0 自托管不构成阻断风险，故选型成立；若未来出现闭源商用外发需求，需重估 AGPL-3.0 许可合规。

**落选理由（对齐五维度）**：

- **Mem0**：能力维度——无 transcript 压缩归档、三层结构缺、三类上下文以记忆为主；知识库维度——文档型承载弱；范式维度——条目式无路径可视化。以"个人化偏好"为核心叙事，与本报告"部门 SOP / 项目上下文"侧重错位。
- **Letta**：能力维度——会话压缩强但显式 LLM 调用模式在 2000 人高频场景成本高；archival passage ≤300 tokens 限制大文档承载；三类上下文统一弱（无资源/技能抽象）。
- **Cognee**：能力维度——无分层压缩归档、扁平图谱无 L0/L1/L2；知识库维度——文档→图谱丢失原文档结构；一体化维度——以图谱为核心，非"记忆+知识库"双范式。实体-关系图能力可作为"能力借鉴"而非主栈（图后端 Ladybug/Neo4j 运维成本高）。

**综上**：OpenViking 在**能力、知识库、范式与体验、一体化**四维度综合最优，胜出为主选型，是 4 款中唯一具备"会话压缩管线 + 三层信息结构 + 三类上下文统一 + 记忆与知识库一体化"的方案；Mem0 / Letta / Cognee 综合判断落选，保留作能力参考。落地约束（AGPL-3.0 / 自建向量库 / 生态早期）决定 OpenViking 适用于内网 / POC / 非闭源商用场景，与本报告公司内部自托管场景匹配，故选型成立。

> **选型结论**：本报告选定 OpenViking 作为云端 Agent 记忆系统的主选型。下文 §6 起围绕此选型展开业务场景覆盖与方案架构设计。

> 竞品功能参考的三款商业产品仅用于借鉴功能设计，不进入选型池，原因：

> 2. **平台边界定位不同**：Coze 是 Bot 平台，Dify 是应用开发平台，VikingDB 是向量底座，均与本报告的"Agent 记忆系统"目标不在同一抽象层。

## 6. 业务侧方案设计

### 6.0 方案概览

基于 §5.6 选型结论，OpenViking 作为主选型。本章按"概览 → 蓝图 → 架构 → 风险"四段展开：§6.0 给出核心概念速查，§6.1 给出一/二期业务需求与开发功能蓝图，§6.2 给出完整架构设计（三层架构图见 §6.2.1、分期规划见 §6.2.0），§6.3 给出方案级风险。

#### 6.0.1 核心概念速查

阅读本章架构图与目录表前，先掌握以下 6 个核心概念（架构图中 `(官方)` / `(企业侧扩展)` 标注依据此划分）：

- **官方原生**：OpenViking 开源产品自带的能力（4 命名空间 / 7 Hook / 9 MCP / L0-L2 分层 / RAGFS 存储引擎 / 多租户 account-user 模型等），开箱即用
- **企业侧扩展**：OpenViking 官方不提供、由本方案自建补齐的能力（② 层知识库授权中心 / 多实例物理隔离 / 跨知识库联邦查询 / 180 天冷存 / KMS 审计等），用于满足企业级多 Agent 治理需求
- **② 层知识库授权中心**：本方案核心扩展组件，做 Agent×知识库 授权矩阵（哪个 Agent 能访问哪个知识库）+ 身份鉴权 + 路由 + 审计，Agent 不直连知识库、所有请求经此层
- **多实例物理隔离**：部门/公司等高敏知识库用独立 OpenViking 实例部署（物理分隔），比官方 account 级逻辑隔离更强
- **跨知识库联邦查询**：② 层并行 fan-out 多个知识库实例检索再合并排序，让一次请求触达多个库
- **知识库（KB）**：本方案一等公民，按归属/用途分类（个人偏好/技能/项目上下文/部门SOP/公司政策/会话归档），Agent 被授权访问、不拥有

#### 6.1.2 一期蓝图：单 Agent 记忆链路跑通

**一期目标**：用最简形态（1 实例 ↔ 1 Agent ↔ 1 库，多 Agent 并存各 1-to-1）跑通单 Agent 的 capture / recall / 归档全链路，验证 OpenViking 核心能力在公司场景下的可行性，同时为二期②层网关入口预埋。

**一期需求 → 开发功能 → 验收清单**：

| 业务需求（对应 §6.1.1 场景） | 开发功能 | 技术归属 | 优先级 | 验收标准 |
|---|---|---|---|---|
| 单 Agent 跨会话记忆 | ②层简化版网关：协议适配 + mTLS/JWT 身份鉴权 + 1-to-1 路由 + 审计 + 观测埋点 | 企业侧扩展 | P0 | 同一用户隔天再发起会话，能自动 recall 上次偏好/决策案例 |

- ✗ 授权矩阵（1-to-1 天然隔离，无需求）
- ✗ 跨库联邦查询（单实例无此需求）
- ✗ 多实例路由（每 Agent 直连自己的实例）
- ✗ 知识库独立产品化（一期知识库与 Agent 1-to-1 绑定）

> 一期技术形态详见 §6.2.0 分期规划表、§6.2.1 一期架构图。

#### 6.1.3 二期蓝图：多 Agent 多库统一治理

**二期目标**：面向 2000 人多 Agent 公司的真实场景，把知识库做成独立产品，实现"一个 Agent 用多库、多个 Agent 用一库、多类型知识库统一治理与分享、新增 Agent 零改造接入"。二期②层网关补全授权矩阵与跨库联邦，Agent 侧接入契约不变、零改造演进。

**业务背景**：2000 人规模互联网公司统一部署多类 AI Agent，知识库类型多（个人偏好/技能、项目上下文、部门 SOP、公司政策、会话归档等 6 类，见 §6.2.3），且知识库天然需要被分享与复用。一期"1 实例↔1 Agent↔1 库"解决了单 Agent 记忆链路跑通的基础问题，但无法支撑以下真实业务需求，二期是这些需求落地的必要演进（二期技术形态见 §6.2.0 分期规划）。

**二期需求 → 开发功能 → 验收清单**：

| 业务需求 | 开发功能 | 技术归属 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 需求一 · 一个 Agent 需要多个知识库源 | ②层跨库联邦 fan-out（多实例并行检索 + 合并排序） | 企业侧扩展 | 授权矩阵 | 一次请求并行检索个人库+部门库+公司库，结果按相关度+知识库优先级合并去重 |
| 需求二 · 多个 Agent 共用一个知识库源 | 知识库独立产品化（独立创建/归属/授权登记）+ 同一库被多 Agent 授权访问 | 企业侧扩展 | 授权矩阵 | 公司政策库只存一份、全公司所有 Agent 只读共享，一处更新所有授权 Agent 即时生效 |
| 需求三 · 知识库类型多需统一治理与隔离 | ②层 RBAC + ACL 授权矩阵 + 多实例路由 + 审计 + 成本归因 | 企业侧扩展 | KMS / audit log | 部门管理者可管控本部门库的 Agent 访问范围；token 成本可精确分摊到 Agent×知识库 |
| 需求四 · 新增 Agent 零改造接入 | ②层授权矩阵配置即可接入（解耦 Agent 与知识库） | 企业侧扩展 | 授权矩阵 | 新增 Agent 仅在矩阵配置一行授权，不动任何知识库数据，零改造上线 |

**需求详解**（业务价值展开）：

**需求一 · 一个 Agent 需要多个知识库源**

Agent 完成一次任务往往需要同时调取多类知识：张三用 Claude Code 做研发，既要他的个人偏好库（编码习惯）、也要研发部 SOP 库（规范流程）、还要公司政策库（HR/合规底线）。一期一个 Agent 只绑一个库，只能看到个人记忆，部门 SOP 和公司政策无处调取，Agent 输出频繁偏离规范。

二期价值：②层授权矩阵让一个 Agent 被授权访问 N 个库，②层跨库联邦 fan-out 让一次请求并行检索个人库+部门库+公司库并合并排序——Agent 像查一个文件系统一样调取多源知识，告别手工粘贴，输出对齐规范（对应 Q1 跨 Agent 共享、Q2 长期闭环）。

**需求二 · 多个 Agent 共用一个知识库源（方便复制分享）**

公司政策库（HR 制度/合规规范/通用知识）是全公司共享的，Claude Code、OpenClaw、Hermes、未来自建 Agent 都要读同一份；研发部 SOP 库要被部门内所有 Agent 共享。一期各 Agent 独占实例、知识库无法跨 Agent 复用——同一份公司政策要在每个 Agent 实例里各存一份，更新一次同步 N 次，且无法保证一致性。

二期价值：知识库作为独立产品（见 §6.2.3），同一知识库可被多个 Agent 授权访问——公司政策库只存一份、全公司所有 Agent 只读共享；部门 SOP 库部门内 Agent 共享。一处更新、所有授权 Agent 即时生效，知识沉淀可复制可分享，跨 Agent 协作记忆复用（对应 Q1 跨 Agent 共享）。

**需求三 · 知识库类型多，需统一治理与隔离**

2000 人公司知识库类型多、归属杂：个人库（N 个，按用户数）、部门库（N 个，按部门数）、公司库（全公司唯一）、项目库（按项目数）、会话归档库（按活跃会话）。这些库敏感度不同（个人偏好低敏、部门 SOP 中敏、公司政策高敏只读），需要分级隔离与统一授权治理。一期靠实例物理分隔硬做，无策略层——部门管理者无法管控"本部门知识库被哪些 Agent 访问"，合规审计无统一入口。

二期价值：②层 RBAC+ACL 授权矩阵统一表达"哪个 Agent 能访问哪个库"，按敏感度分级（个人 namespace 逻辑隔离 / 部门独立实例物理隔离 / 公司只读实例）；②层全量拦截点做审计与成本归因——部门管理者可管控本部门库的 Agent 访问范围，安全/合规有统一治理入口，token 成本可精确分摊到 Agent×知识库（对应 Q3 三级隔离、Q4 治理、Q5 可观测）。

**需求四 · 新增 Agent 零改造接入**

公司未来持续接入新 Agent（Cursor/Trae/自建等），一期每接一个新 Agent 要独立部署实例+配置接入，改造量大、上线慢。

二期价值：②层授权矩阵解耦 Agent 与知识库——新增 Agent 只需在矩阵配置一行授权，不动任何知识库数据，零改造接入（对应 Q4 治理）。

> 综上：一期验证记忆链路可行性（单 Agent 跑通 capture/recall/归档），二期面向 2000 人多 Agent 公司的真实场景——一个 Agent 用多库、多个 Agent 用一库、多类型知识库统一治理与分享，是知识库作为独立产品、跨 Agent 协作记忆复用的必要演进。

### 6.2 方案架构

#### 6.2.0 设计理念：以知识库为中心 + 企业侧扩展

**为什么需要"企业侧扩展"？** OpenViking 是面向个人开发者 / 小团队的通用开源产品，官方只提供必要且通用的能力（4 个顶级命名空间、7 Hook、9 MCP 工具、LLM+Embedding+VLM 三分工）。业务上有 OpenViking 官方不解决的 4 类需求：

| 企业需求                              | OpenViking 官方是否原生支持                                   | 是否需企业侧扩展补齐           |
| --------------------------------- | ----------------------------------------------------- | -------------------- |
| 部门级隔离（设计部/研发部 SOP 不串数据）           | ⚠️ 有 account 级逻辑隔离（Concepts 11），但本方案用独立实例做多实例物理隔离（更强） | ✅ 企业侧扩展（多实例物理隔离）     |
| Agent×知识库 授权矩阵（哪个 Agent 能访问哪个知识库） | ❌ 官方 account/user 模型表达不了跨租户 Agent 授权关系                | ✅ 企业侧扩展（② 层授权中心）     |
| 跨知识库联邦查询（一次请求触达多个知识库）             | ❌ 官方单实例单 account 视角，无联邦                               | ✅ 企业侧扩展（② 层 fan-out） |
| 归档冷存 180 天迁 TOS                   | ⚠️ 官方支持 resources 挂 S3，但无"180 天规则"                    | ✅ 企业侧策略              |

> 以上 4 类企业需求对应的核心概念（官方原生 / 企业侧扩展 / ②层知识库授权中心 / 多实例物理隔离 / 跨知识库联邦查询 / 知识库 KB）定义见 §6.0.1 核心概念速查。

**设计理念：分界与承接**

- **官方能力**：解决"记忆怎么读、怎么写、怎么召回、怎么分层、怎么被 LLM 结构化压缩"+ account/user/peer 多租户隔离 + ROOT/ADMIN/USER 角色权限——**技术与租户隔离闭环**。
- **企业侧扩展**：解决"哪个 Agent 能访问哪个知识库、跨知识库联邦查询、部门级物理隔离、审计怎么落"——**Agent×知识库 授权与多实例治理闭环**（官方 account/user 模型表达不了这种跨租户 Agent 授权关系）。
- **两者接口**：企业侧扩展**不改 OpenViking 源码**，核心是 ② 层知识库授权中心（网关模式）——
  0\. **协议适配**（入站首步）：多 Agent 消息格式异构（Hooks transcript JSON / MCP 工具调用 / SDK 编程对象），② 层入站时先归一为 OpenViking 的 `viking://` + REST 语义（addMessage/search/find + commit/archive），再进入鉴权；
  1. **身份鉴权 + 授权决策**：归一后验 mTLS/JWT 令牌 → 查 Agent×知识库 授权矩阵（允许/不允许）→ 放行或拒绝；
  2. **路由转发 + 联邦查询**：放行后路由到目标知识库实例；跨库召回时 ② 层 fan-out 多实例并行检索再合并排序。
- **好处**：OpenViking 升级 → ② 层授权中心无需重写（仅靠 HTTP 网关转发对接）；合规责任边界清晰（与 §6.3 风险 2 一致）。

> 以下架构图中，`(官方)` 标注为 OpenViking 原生能力，`(企业侧扩展)` 标注为本报告设计的企业侧治理逻辑。

**分期规划**

本方案按两期演进，②层网关入口一期即埋好，二期补全授权矩阵与联邦，Agent 侧接入契约不变、二期零改造：

| 维度   | 一期（公司云 Agent 平台现状）                         | 二期（目标态）                               |
| ---- | ------------------------------------------ | ------------------------------------- |
| 形态   | 1 实例 ↔ 1 Agent ↔ 1 库（多 Agent 并存，各自 1-to-1） | 1 Agent ↔ N 库（跨库联邦）                   |
| 实例   | 每 Agent 独占 1 个 OV 实例                       | 多实例池（个人共享 + 部门独立 + 公司只读）              |
| 授权矩阵 | 无（1-to-1 天然隔离）                             | 完整 Agent×库 矩阵（RBAC+ACL）               |
| 实例池  | 无（各 Agent 直连自己的实例）                         | 多实例池 + 路由 + 跨库联邦 fan-out              |
| ②层   | 简化：协议适配 + 身份鉴权 + 路由 + 审计 + 观测（矩阵/联邦缺席）     | 完整：协议适配 + 矩阵 + 鉴权 + 路由 + 联邦 + 审计 + 观测 |
| 目标   | 各 Agent 跑通自身记忆链路，天然隔离                      | 跨 Agent 共享、跨库联邦、统一治理、成本分摊             |

> 二期的业务价值（一个 Agent 用多库 / 多个 Agent 用一库 / 多类型库治理 / 零改造接入）见 §6.1.3。

**演进原则**：②层网关入口一期即部署（简化版），二期补全授权矩阵 + 联邦 + 多实例路由；Agent 侧接入契约不变，二期零改造演进。

#### 6.2.2 层职责说明

数据流主干为 ①→②→③。接入方式（Hooks/MCP/SDK）是 Agent 出站时的协议选择，Agent 按能力择一、非依次经过，不单独成层（详见 §6.3.1 接入通道）。横切支撑层为旁路依赖，不参与层级编号。

#### 6.2.3 知识库归属 × 授权矩阵

**知识库作为独立产品**：知识库是本方案的一等公民（独立产品），**支持单独创建**（如法务部门单独创建并维护法务知识库），也支持**在创建 Agent 时选择/创建知识库**（为 Agent 绑定其可访问的库）。Agent 不拥有知识库，只通过 ② 层授权矩阵被授权访问；同一知识库可被多个 Agent 访问，同一 Agent 可访问多个知识库。知识库的创建、归属、授权均经 ② 层知识库授权中心登记与治理。

| 知识库类型      | 归属方    | OpenViking 命名空间                   | 记忆类型（官方分类）                              | 承载内容                    | 实例形态（多实例物理隔离）      | 数量级（N 人公司） |

| 项目上下文知识库   | 个人/项目组 | `viking://resources/{project}/`   | 多模态资源 / 知识规则                            | 项目结构、代码风格、协作规范          | 按项目独立或共享           | 按项目数         |

#### 6.2.4 关键数据流（4 条路径）

> 4 条路径对应接入方式的两条通道（Plugins/Hooks + MCP）× 两个方向（写入 + 召回），召回路径（3/4）落地 §4.4.4 记忆召回能力。Hooks 通道自动触发，MCP 通道模型按需触发。
> **协议适配前置**：4 条路径入②层时均先经协议适配子模块归一消息格式（Hooks JSON / MCP 调用 → OV HTTP 语义），再进入身份鉴权；以下 ★ 标注聚焦鉴权+授权+路由环节。

**4 条路径总览**（接入通道 × 方向）：

| <br />          | 写入                          | 召回                                     |
| --------------- | --------------------------- | -------------------------------------- |
| **Hooks（自动触发）** | 路径 1 · Stop Hook 自动 Capture | 路径 3 · UserPromptSubmit Hook 自动 Recall |
| **MCP（模型按需）**   | 路径 2 · MCP store 显式写入       | 路径 4 · MCP search 跨库联邦检索               |

**路径 1 · Hooks 自动 Capture（写入 · 生命周期驱动）**

```
Stop Hook 触发（模型每轮回答结束）
   │
   ▼
auto-capture.mjs 读 transcript_path → 解析 turn → 增量过滤（capturedTurnCount）
   │
   ▼
sanitize：剥离 <openviking-context> / <system-reminder> 等注入块（防污染回环）
   │
   ▼
shouldCapture 门禁：长度 / 命令 / 问句 / 符号 / 关键词模式
   │
   ▼
buildParts：text→text part，tool_use/tool_result→tool part（output ≤2000 字）
   │
   ▼
★ 知识库授权中心校验：Agent 身份鉴权（mTLS/JWT）→ 确认写入权限 → 路由到目标知识库实例
   │
   ▼
addMessage → POST 到目标知识库实例的 OV Session（cc-<sha256(cc_session_id)>）
   │
   ▼
OV 服务端 pending token ≥ 20000（COMMIT_TOKEN_THRESHOLD）→ commit
   │
   ▼
Memory Extraction（LLM，按 MemoryTypeRegistry 5 类分类）
   + Working Memory v2 Compression（LLM Function Calling，按 WM 7 sections）
   + Embedding 向量化
   │
   ▼
落地到目标知识库实例的 viking://user/{uid}/memories/{preferences|events|cases|...}/ 或 viking://user/{uid}/skills/
```

**路径 2 · MCP store 显式写入（写入 · 模型意图驱动）**

```
模型判断"这一条值得沉淀" → 调 MCP store 工具
   │
   ▼
★ 知识库选择 + 授权校验：Agent 指定目标知识库 → 知识库授权中心校验写入权限（RBAC + ACL）
   │  ─ 无写入权限 → 拒绝 + 审计日志
   ▼
SDK 层补 ID + 元数据拼路径（企业侧扩展）
   │
   ▼
知识库授权中心路由 → 目标知识库实例的 OpenViking HTTP/SDK
   │
   ▼
显式写入：服务端 LLM extraction + Embedding 向量化 → 生成 L0/L1 → 落地
```

**路径 3 · Hooks 自动 Recall（召回 · 生命周期驱动）**

```
UserPromptSubmit Hook 触发（用户每次提交 prompt）
   │
   ▼
auto-recall.mjs 通过 stdin 拿到 prompt / session_id / cwd
   │
   ├─ 命中 bypass / query<3 字符 / server offline → 直接 approve（跳过）
   ▼
★ 知识库授权中心校验：Agent 身份鉴权 → 获取授权知识库列表 → 路由到目标知识库实例
   │
   ▼
多路检索：POST /api/v1/search/find（发往授权的个人知识库共享实例）
   │
   ▼
★ 自动召回边界（官方安全边界，附件4 第 345-350 行）：
   只搜 viking://user/memories + viking://user/skills
   viking://resources 不参与自动召回（防跨命名空间泄露）
   │
   ▼
排序：base score + leafBoost + eventBoost + prefBoost + lexicalOverlap
   │
   ▼
score ≥ 0.35 过滤（SCORE_THRESHOLD）+ 去重 + 取前 recallLimit=6
   │
   ▼
内容解析：优先 L0 abstract，abstract 空时 fallback L1 overview，
        相关度高 + 预算充足时才拉 L2 全文（单条截 500 字 RECALL_MAX_CONTENT_CHARS）
   │
   ▼
预算：2000 token 内（RECALL_TOKEN_BUDGET）注入完整内容，
     超出降级为「URI + 相关度%」
   │
   ▼
输出 <openviking-context> 注入块 → 追加到用户 Prompt 前
   │
   ▼
SDK 层按授权矩阵过滤（企业侧扩展 · 知识库授权中心已校验）
   │
   ▼
SDK 发 OTel Trace + Prometheus 指标（命中率 / 延迟 / llm_token_usage / embedding_token_usage）
```

**路径 4 · MCP search 模型主动检索（召回 · 模型意图驱动 · 跨知识库联邦）**

```
模型判断"自动注入的 6 条不够" → 调 MCP search 工具（可指定 scope + 知识库）
   │
   ▼
★ 知识库授权中心校验：Agent 身份鉴权 → 获取授权知识库列表 → 确认目标知识库读权限
   │
   ▼
★ 跨知识库联邦查询：平台层 fan-out 到多个授权知识库实例并行检索
   │  ├ 个人偏好知识库共享实例（viking://user/）
   │  ├ 部门 SOP 知识库独立实例（viking://resources/team/{dept}/）
   │  └ 公司政策知识库只读实例（viking://resources/public/）
   ▼
各知识库实例执行两阶段检索
   │
   ├─ 阶段 1：flat_hybrid（dense + sparse + int8 量化）向量召回
   └─ 阶段 2：doubao-seed-rerank 精排 + 阈值过滤
   │
   ▼
★ 可覆盖 viking://resources（路径 3 不搜的范围），由模型显式指定 scope
   │
   ▼
合并排序：多知识库结果按相关度 + 知识库优先级合并 → 去重 → 取 Top-K
   │
   ▼
返回 L0/L1 摘要 + 必要时按 URI 调 MCP read 加载 L2 详情
```

> **4 条路径对应关系**：路径 1/3 走 Hooks 通道（自动），路径 2/4 走 MCP 通道（按需）；写入走路径 1/2，召回走路径 3/4。Hooks 与 MCP 互补：Hooks 保证记忆能力不依赖 LLM 意愿，MCP 提供精细化操作能力。
>
> **本方案授权贯穿**：4 条路径均经过 ② 层知识库授权中心校验——写入路径（1/2）校验写权限后路由到目标知识库实例；召回路径（3/4）校验读权限后路由/联邦查询授权知识库实例。Agent 无法越界访问未授权知识库。

> 详细 SDK/MCP 定位、多 Agent 对接方式、写入/遗忘规则见 [附件3-一期OpenViking落地方案.md](附件3-与openvking对接问题.md)；Claude Code × OpenViking 端到端接入实证（hooks 生命周期/写入抽取/召回注入/观测埋点全链路）见 [附件4-智能体集成OpenViking实证.md](附件4-智能体集成OpenViking实证.md)。

### 6.3 接入与记忆模型

本节回答两个核心问题：**Agent 用什么协议与记忆系统通信**（§6.3.1 接入通道），**记忆如何记入、存储、召回**（§6.3.2-6.3.5 记忆模型）。接入通道是通信管道，记忆模型是管道里跑的业务逻辑，通道机制只在 §6.3.1 定义一次，§6.3.3/6.3.5 直接引用。数据流端到端实证见图 §6.2.4。

#### 6.3.1 接入通道

接入方式是 Agent 出站时用什么协议与本系统通信的选择，和数据流主干（①→②→③）是两件事：同一请求按 Agent 框架能力择一走 Hooks / MCP / SDK 通道，而非依次经过。接入方式不是数据流的"第二层"，而是 ① Agent 出站时的协议选择维度（官方 · 附件4 第 60-110 行）。

**三通道职责**

| 通道            | 驱动方式        | 覆盖能力                                                              | 适用 Agent                                                           |
| ------------- | ----------- | ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| Plugins·Hooks | 生命周期驱动·自动触发 | 7 Hook 覆盖读/写/归档/隔离四类                                              | Claude Code 等生命周期型 Agent                                           |
| MCP           | 模型意图驱动·按需调用 | 9 工具：search/read/list/store/add\_resource/grep/glob/forget/health | MCP 兼容 Agent（Cursor/Trae/OpenClaw 等）                               |
| SDK/HTTP      | 通用编程接入      | Python/Go/TS SDK + HTTP                                           | 无 MCP/Hook 能力的框架（LangChain/二期自建/特殊集成）；已有 Agent（CC/OpenClaw 等）走左两通道 |

**7 Hook 生命周期时间轴**（官方 · 附件4 第 75-83 行 · Plugins 通道自动触发）：

```
SessionStart ─► UserPromptSubmit(读) ─► Stop(写)
     │            │                       │
     │            └─► [模型可选调 MCP 9 工具]
     ▼                                    ▼
PreCompact(强制归档) ─► SessionEnd(收尾)  SubagentStart(隔离)
                                          └─► SubagentStop
                                               (子 Agent 归档)
```

> Hooks 与 MCP 互补：Hooks 保证记忆能力不依赖 LLM 意愿（自动 capture/recall），MCP 提供精细化操作能力（模型按需 store/search）。两者均经 ② 层协议适配归一为 OV HTTP 语义后鉴权路由。

**Agent 接入决策树**：

- **Claude Code / 同类生命周期型 Agent** → Plugins(Hooks) + MCP 双通道（自动召回 + 模型按需检索）
- **OpenClaw / Hermes** → 按其框架能力选择 MCP 通道或 SDK 通道（待 PoC 确认）
- **Cursor / Trae / 其他 MCP 兼容 Agent** → MCP 通道（9 工具）
- **LangChain / LangGraph / 二期自建 Agent** → Python/Go SDK + HTTP（无 MCP/Hook 能力时的通用接入；二期自建 Agent 上线后零改造复用已建的授权矩阵与多实例池）
- **新增 Agent 零改造接入**：只需在知识库授权中心配置 Agent×知识库授权矩阵，不动任何知识库数据（本方案解耦优势）

**② 层观测埋点独特价值**：② 层是所有 Agent 请求的唯一全量拦截点，在此埋点可捕获 100% 的 Agent×知识库访问（若埋点放各知识库实例内部，只能看到单实例视角，无法聚合）。具体价值：① 跨知识库归因——一次 Agent 请求可能触达多个知识库（联邦查询），只有 ② 层能记录"这次请求触达了哪些库"；② token 成本分摊——② 层知道 Agent 身份 + 目标知识库，能把 LLM/Embedding token 成本精确归因到"哪个 Agent 访问哪个知识库花了多少"，支撑按部门/Agent 的成本分摊。

#### 6.3.2 记忆类型与分类

记忆系统的本体是 OpenViking 官方定义的记忆分类，记入/存储/召回都围绕这些类型展开（官方 · 附件4 第 323-333 行）：

| 记忆类型 | 语义 | 承载内容 | 落地命名空间 |
|---|---|---|---|
| preferences | 用户偏好 | 稳定偏好（编码习惯、语言、风格） | `viking://user/{uid}/memories/preferences/` |
| events | 事件 | 稳定事实、决策案例、关键事件 | `viking://user/{uid}/memories/events/` |
| cases | 案例 | 决策案例、问题解决经验 | `viking://user/{uid}/memories/cases/` |
| memories | 通用记忆 | 其他值得沉淀的稳定信息 | `viking://user/{uid}/memories/memories/` |
| skills | 技能 | 用户习得的操作方式、任务经验 | `viking://user/{uid}/skills/` |
| archive | 会话归档 | 单次对话上下文（20000 token 切分） | `viking://session/{sid}/archive/` |
| resources | 多模态资源 | 项目结构、部门 SOP、公司政策、知识规则 | `viking://resources/{project|team|public}/` |

> 记忆类型与知识库归属的映射见 §6.2.3 知识库归属表——个人库承载 preferences/events/cases/memories/skills，部门库/公司库承载 resources，会话归档库承载 archive。

#### 6.3.3 记忆记入模型

本节回答"什么场景、什么时机、用什么方式把记忆**记入**系统"。通道机制（Hooks/MCP 触发时机）引用 §6.3.1，本节聚焦记入业务逻辑（门禁规则、抽取算法、落地命名空间）。

**场景 × 时机 × 记入方式框架表**：

| 通道（引用 §6.3.1） | 场景 | 时机 | 记入方式 | LLM 介入 | 落地命名空间 |
|---|---|---|---|---|---|
| Hooks（自动） | 每轮对话结束 | Stop Hook 触发 | auto-capture.mjs 解析 transcript → shouldCapture 门禁 → buildParts → Memory Extraction | LLM 5 类分类 + WM v2 7 sections 压缩 | `viking://user/{uid}/memories/` 或 `skills/` |
| MCP（显式） | 模型判断"值得沉淀" | MCP store 调用 | SDK 补 ID/元数据 → 服务端 LLM extraction + Embedding → 生成 L0/L1 | LLM extraction + Embedding 向量化 | 指定知识库（含 resources） |

**自动记入流程**（Hooks 通道 · 对应 §6.2.4 路径 1）：

```
Stop Hook 触发（每轮对话结束）
   │
   ▼
auto-capture.mjs 读 transcript_path → 解析 turn → 增量过滤（capturedTurnCount，避免重复 capture）
   │
   ▼
sanitize：剥离 <openviking-context> / <system-reminder> 等注入块（防污染回环）
   │
   ▼
shouldCapture 门禁（核心过滤规则）：
   - 长度门禁：低于阈值的不记入
   - 命令/问句模式：纯命令或纯问句不记入
   - 符号/关键词模式：无实质内容的不记入
   │
   ▼
buildParts：text→text part，tool_use/tool_result→tool part（output ≤2000 字截断）
   │
   ▼
★ ②层鉴权路由：Agent 身份鉴权（mTLS/JWT）→ 确认写入权限 → 路由到目标知识库实例
   │
   ▼
addMessage → POST 到目标实例的 OV Session → 服务端处理（见 §6.3.4 存储模型）
```

**显式记入流程**（MCP 通道 · 对应 §6.2.4 路径 2）：

```
模型判断"这一条值得沉淀" → 调 MCP store 工具
   │
   ▼
★ 知识库选择 + 授权校验：Agent 指定目标知识库 → ②层校验写入权限（RBAC + ACL）
   │  ─ 无写入权限 → 拒绝 + 审计日志
   ▼
SDK 层补 ID + 元数据拼路径（企业侧扩展）
   │
   ▼
②层路由 → 目标知识库实例的 OpenViking HTTP/SDK → 服务端处理（见 §6.3.4 存储模型）
```

> Hooks 自动记入覆盖绝大多数场景（无需 LLM 意愿判断），MCP 显式记入用于模型主动沉淀的精细化场景。两者均经 ② 层鉴权后进入服务端存储流程。

#### 6.3.4 记忆存储模型

本节回答"记入后如何分层、压缩、归档存储"。对应 §6.2.4 路径 1/2 中"服务端处理"段的内部逻辑。

**L0/L1/L2 三层结构**（官方 · 附件4 第 337-343 行）：

| 层级 | 文件形态 | 内容 | 加载策略 |
|---|---|---|---|
| L0 | `.abstract.md` | LLM 生成的摘要（最精炼） | 召回时优先加载，省 token |
| L1 | `.overview.md` | LLM 生成的概览（中等粒度） | L0 空时 fallback L1 |
| L2 | 原文 | 完整原始内容 | 相关度高 + 预算充足时才加载（单条截 500 字） |

**Working Memory v2 Compression**（官方 · 附件4 第 297-308 行）：

- 触发：pending token ≥ 20000（COMMIT_TOKEN_THRESHOLD）时触发 commit
- 压缩方式：LLM Function Calling，按 WM 7 sections 结构化压缩
- 配合 Memory Extraction：LLM 按 MemoryTypeRegistry 5 类分类（preferences/events/cases/memories/skills）
- 输出：生成 L0 abstract + L1 overview + Embedding 向量化 → 落地到对应命名空间

**commit / archive 阈值与冷存**：

| 阶段 | 触发条件 | 动作 | 归属 |
|---|---|---|---|
| commit | pending token ≥ 20000 | 触发 WM v2 压缩 + Memory Extraction + Embedding → 生成 L0/L1 → 落地 | 官方 |
| archive | 会话结束 / PreCompact Hook | session 内容打包归档到 `viking://session/{sid}/archive/` | 官方 |
| 冷存 | 180 天未访问 | 迁移到 TOS 对象存储（按 URI 检索可恢复） | 企业侧策略 |

> 官方 session archive 是会话级归档，企业侧 180 天迁 TOS 是冷存策略——两者不冲突，archive 是"会话结束归档"，180 天规则是"长期未访问冷存"。

#### 6.3.5 记忆召回模型

本节回答"需要时怎么把记忆召回注入 Agent 上下文"。通道机制（Hooks/MCP 触发时机）引用 §6.3.1，本节聚焦召回算法（排序、过滤、预算、降级）。

**自动召回 + 显式召回对比表**：

| 通道（引用 §6.3.1） | 触发 | 召回范围 | 排序与过滤 | 预算与降级 |
|---|---|---|---|---|
| Hooks（自动） | UserPromptSubmit Hook | 仅 `viking://user/memories` + `skills`（官方安全边界，resources 不参与，防跨命名空间泄露） | base score + leafBoost + eventBoost + prefBoost + lexicalOverlap → score≥0.35（SCORE_THRESHOLD）→ 去重 → recallLimit=6 | 2000 token 内（RECALL_TOKEN_BUDGET）注完整内容，超出降级为「URI + 相关度%」；注入 `<openviking-context>` |
| MCP（显式） | 模型判断"6 条不够" → MCP search | 可覆盖 `viking://resources`（自动召回不搜的范围），跨库联邦 fan-out 多实例并行检索 | 各实例两阶段检索（flat_hybrid dense+sparse+int8 量化 → doubao-seed-rerank 精排）→ 多库结果按相关度+知识库优先级合并 → 去重 → Top-K | 返回 L0/L1 摘要 + 按需 MCP read 加载 L2 详情 |

**自动召回流程**（Hooks 通道 · 对应 §6.2.4 路径 3）：

```
UserPromptSubmit Hook 触发（用户每次提交 prompt）
   │
   ▼
auto-recall.mjs 通过 stdin 拿到 prompt / session_id / cwd
   │
   ├─ 命中 bypass / query<3 字符 / server offline → 直接 approve（跳过）
   ▼
★ ②层鉴权路由：Agent 身份鉴权 → 获取授权知识库列表 → 路由到目标实例
   │
   ▼
多路检索：POST /api/v1/search/find（发往授权的个人知识库共享实例）
   │
   ▼
★ 自动召回边界（官方安全边界，附件4 第 345-350 行）：
   只搜 viking://user/memories + viking://user/skills
   viking://resources 不参与自动召回（防跨命名空间泄露）
   │
   ▼
排序：base score + leafBoost + eventBoost + prefBoost + lexicalOverlap
   │
   ▼
score ≥ 0.35 过滤（SCORE_THRESHOLD）+ 去重 + 取前 recallLimit=6
   │
   ▼
内容解析：优先 L0 abstract，abstract 空时 fallback L1 overview，
        相关度高 + 预算充足时才拉 L2 全文（单条截 500 字 RECALL_MAX_CONTENT_CHARS）
   │
   ▼
预算：2000 token 内（RECALL_TOKEN_BUDGET）注入完整内容，
     超出降级为「URI + 相关度%」
   │
   ▼
输出 <openviking-context> 注入块 → 追加到用户 Prompt 前
   │
   ▼
SDK 发 OTel Trace + Prometheus 指标（命中率 / 延迟 / llm_token_usage / embedding_token_usage）
```

**显式召回流程**（MCP 通道 · 对应 §6.2.4 路径 4）：

```
模型判断"自动注入的 6 条不够" → 调 MCP search 工具（可指定 scope + 知识库）
   │
   ▼
★ ②层鉴权：Agent 身份鉴权 → 获取授权知识库列表 → 确认目标知识库读权限
   │
   ▼
★ 跨知识库联邦查询：②层 fan-out 到多个授权知识库实例并行检索
   │  ├ 个人偏好知识库共享实例（viking://user/）
   │  ├ 部门 SOP 知识库独立实例（viking://resources/team/{dept}/）
   │  └ 公司政策知识库只读实例（viking://resources/public/）
   ▼
各知识库实例执行两阶段检索
   │
   ├─ 阶段 1：flat_hybrid（dense + sparse + int8 量化）向量召回
   └─ 阶段 2：doubao-seed-rerank 精排 + 阈值过滤
   │
   ▼
★ 可覆盖 viking://resources（自动召回不搜的范围），由模型显式指定 scope
   │
   ▼
合并排序：多知识库结果按相关度 + 知识库优先级合并 → 去重 → 取 Top-K
   │
   ▼
返回 L0/L1 摘要 + 必要时按 URI 调 MCP read 加载 L2 详情
```

> **自动召回 vs 显式召回的边界**：自动召回（Hooks）保证每轮对话都有基础记忆注入（6 条内、2000 token 预算），不依赖 LLM 意愿；显式召回（MCP）让模型按需深挖（跨库联邦、可覆盖 resources）。两者互补，共同构成完整的记忆召回能力。

### 6.4 方案级风险（4 条）

以下 4 条为本方案（选 OpenViking + 多实例架构）的方案级风险；记忆系统通用风险见 §7.1。

1. **单产品绑定** — 若 OpenViking 项目停滞或不满足新需求，迁移成本高
   - **缓解**：接受单栈绑定风险。PoC 阶段充分验证 8 项核心能力 + 3 维 RAG 底座 + 5 道业务题覆盖度，确保上线前识别能力缺口。不预留 Adapter 抽象层（避免过度设计）。若未来确需迁移，按当时实际需求评估迁移成本（重评估触发条件见 §7.2 第3条）。
2. **企业合规责任由部署侧承担** — OpenViking 不提供第三方 SaaS 合规证书；由于是自托管部署，数据不出企业，合规能力由公司内部审计 / 等保 / 数据驻留策略保证（**这是私有化部署的常规做法，不构成产品缺陷**）
3. **被动抽取质量需持续调优** — OpenViking 官方抽取管线（`compression.ov_wm_v2` + Memory Extraction，附件4 第 297-308 行）依赖 LLM 与 prompt
   - **缓解**：建立 golden set 抽取效果基线，定期回归；PoC 阶段用真实数据校准；利用 web-studio 检索轨迹可视化定位抽取偏差
4. **多知识库联邦查询延迟** — 本方案多实例物理隔离部署下，Agent 跨知识库召回需平台层 fan-out 多个知识库实例并行检索再合并排序，增加召回 P95 延迟
   - **缓解**：并行 fan-out（最多 5 个知识库实例，`KB_FEDERATION_MAX_KB`）+ 8000ms 超时（`KB_FEDERATION_TIMEOUT_MS`）；高频知识库结果本地缓存（授权矩阵缓存 `KB_AUTH_MATRIX_CACHE_TTL=300s`）；Hooks 自动召回（路径 3）只查个人知识库共享实例（单实例无联邦），仅 MCP search（路径 4）才触发跨知识库联邦

| -- | -------------- | ------------- | ----------------------------------------------------------------------------------------------------------------- |
| R1 | 记忆污染（错误偏好被强化）  | AI 行为偏离       | 借鉴 Letta 的召回-证据引用做法（archival passage + sleep-time 整合，每次召回要求 LLM 显式引用来源），做记忆污染防护                                   |
