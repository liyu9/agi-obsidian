## 4. 产品方案设计

本章把第 3 章「功能架构」翻译为可落地的产品策划案--从核心业务流程切入，梳理各类用户操作流程，再确定过程中用到的产品、功能、页面与规则。第 1-3 章为方案与架构设计（做什么、为什么），第 4 章为产品落地设计（怎么做、做成什么样），第 5 章为风险与建议。

**设计方法论**：核心流程切入 -> 用户操作流程 -> 产品/功能/页面（对齐 B 端产品方案设计 SOP）。

**与前章关系**：本章引用 §1.1.1 三类用户与 S0-S8 场景、§1.3.1 三层架构、§1.3.3 知识库类型、§1.3.4 权限模型、§2.0-2.5 数据流与记忆模型、§3.1-3.2 功能架构，不重复定义，仅做产品视角的翻译与细化。

### 4.1 业务核心流程

基于 §1.1.1 的 9 个业务场景（S0-S8）与 §2.0 的 4 条数据流，梳理 7 条端到端核心业务流程。每条流程标注涉及的场景、角色、系统与数据流转。

#### F1 知识入库流程（对应 S0）

把企业传统知识库文档与 Agent 沉淀的信息写入 L1 向量知识库，使其可被检索。

```
数据源 A（企业文档）         数据源 B1/B3（Agent 沉淀）
  │ 前端上传/TOS导入/URL/API   │ MCP store / Hooks
  ▼                            ▼
②层鉴权路由（身份鉴权 -> 写入权限校验）
  │
  ▼
切片 Chunking（默认配置 / 二期可配置）
  │
  ▼
Embedding 向量化
  │
  ▼
向量索引入库（viking://resources/）
  │
  ▼
可检索状态（MCP search / web-studio 文件列表可见）
```

- **涉及角色**：A 类（知识库维护方）、C 类（建设方）
- **涉及系统**：①Agent 应用层、②知识库授权中心、③OpenViking 实例
- **关键规则**：数据源 A 入库需选择目标知识库；B1/B3 入库经 ②层鉴权后写入；一期切片/Embedding 用默认配置，二期可配置

#### F2 Agent 接入流程（对应 S5/S8）

新 Agent 从注册到可访问知识库的端到端接入流程。

```
C 类用户在管理控制台注册 Agent
  │ 填写 Agent 名称、描述、归属部门
  ▼
选择接入通道（Hooks / MCP / SDK）
  │ 根据 Agent 框架能力择一（决策树见 §2.1）
  ▼
配置身份凭证（mTLS 证书 / JWT Token）
  │ ②层颁发凭证，绑定 Agent 身份
  ▼
配置授权矩阵（Agent × 知识库 允许/不允许）
  │ 一期：1-to-1 绑定 account；二期：完整 RBAC+ACL 矩阵
  ▼
②层协议适配（归一为 OV HTTP 语义）
  │
  ▼
接入验证（health check + 检索测试）
  │
  ▼
上线（Agent 可经 ②层访问授权知识库）
```

- **涉及角色**：C 类（建设方）
- **涉及系统**：②知识库授权中心、管理控制台
- **关键规则**：一期 1 Agent 绑 1 account（天然隔离）；二期矩阵配置一行即接入（零改造）；新增 Agent 不动任何知识库数据

#### F3 记忆记入流程（对应 S1/S2，§2.3 路径 1/2）

Agent 对话中的偏好/事件/案例/技能自动或显式记入 L2 记忆系统。

```
Stop Hook 触发（每轮对话结束）         MCP store 调用（模型显式写入）
  │                                      │
  ▼                                      ▼
auto-capture.mjs 解析 transcript         Agent 指定目标知识库
  │ 增量过滤（避免重复 capture）            │
  ▼                                      ▼
sanitize（剥离注入块）                  ②层校验写入权限（RBAC+ACL）
  │                                      │ 无权限 -> 拒绝+审计
  ▼                                      ▼
shouldCapture 门禁                     SDK 补 ID/元数据
  │ 长度/命令/符号过滤                     │
  ▼                                      ▼
buildParts（text/tool part）           ②层路由
  │                                      │
  ▼                                      ▼
②层鉴权路由 ──────────────────────- ──- ──- ──→ 目标实例
  │
  ▼
服务端 Memory Extraction（LLM 5 类分类）
  │ preferences/events/cases/memories/skills
  ▼
WM v2 Compression（≥20000 token 触发）
  │
  ▼
Embedding 向量化 -> 生成 L0/L1/L2 三层
  │
  ▼
落地 viking://user/{uid}/memories/ 或 skills/
```

- **涉及角色**：A 类（Agent 使用方，被动受益）
- **涉及系统**：①Agent 应用层（Hooks/MCP）、②知识库授权中心、③OpenViking 实例
- **关键规则**：Hooks 自动记入覆盖绝大多数场景（不依赖 LLM 意愿）；shouldCapture 门禁过滤无实质内容；LLM 5 类分类决定落地命名空间；一期用默认规则，二期规则可配置

#### F4 记忆召回流程（对应 S0/S1，§2.5 路径 3/4）

需要时把记忆召回注入 Agent 上下文，分自动召回与显式召回两条路径。

```
路径 3 · 自动召回（Hooks）              路径 4 · 显式召回（MCP）
UserPromptSubmit Hook 触发             模型判断"6 条不够" -> MCP search
  │                                      │
  ▼                                      ▼
auto-recall.mjs 拿到 prompt/sid       ②层鉴权 -> 获取授权知识库列表
  │                                      │
  ▼                                      ▼
②层鉴权 -> 路由到个人 account          跨 account 联邦 fan-out（多库并行）
  │                                      │ ├ 个人库 account
  ▼                                      │ ├ 部门 SOP account
多路检索（仅 user/memories + skills）   │ └ 公司政策 account
  │ ★ resources 不参与自动召回            │
  ▼                                      ▼
排序（base+leafBoost+eventBoost...）  各库两阶段检索
  │                                      │ flat_hybrid -> rerank
  ▼                                      ▼
score≥0.35 过滤 + 去重 + 取前 6 条     多库结果合并排序 + 去重 + Top-K
  │                                      │
  ▼                                      ▼
预算控制（2000 token 内）              返回 L0/L1 摘要
  │ 超出降级为 URI+相关度%                │ 按需 MCP read 加载 L2
  ▼                                      ▼
注入 <openviking-context> 到 Prompt    返回 Agent 上下文
```

- **涉及角色**：A 类（Agent 使用方，被动受益）
- **涉及系统**：①Agent 应用层、②知识库授权中心、③OpenViking 实例
- **关键规则**：自动召回只搜 user/memories+skills（防跨命名空间泄露）；显式召回可覆盖 resources；自动召回 6 条/2000 token 预算，超出降级；显式召回支持跨 account 联邦

#### F5 会话归档与冷存流程（对应 S3，§2.4）

会话从产生到归档到冷存的全生命周期。

```
会话进行中（pending token 累积）
  │
  ▼ pending token ≥ 20000（COMMIT_TOKEN_THRESHOLD）
  │
commit 触发
  │ WM v2 压缩（LLM Function Calling，7 sections 结构化）
  │ + Memory Extraction（5 类分类）
  │ + Embedding 向量化
  ▼
生成 L0 abstract + L1 overview -> 落地命名空间
  │
  ▼ 会话结束 / PreCompact Hook 触发
  │
archive（打包归档到 viking://session/{sid}/archive/）
  │
  ▼ 180 天未访问
  │
冷存迁移 TOS 对象存储（按 URI 检索可恢复）
```

- **涉及角色**：A 类（Agent 使用方）、C 类（建设方运维）
- **涉及系统**：③OpenViking 实例、TOS 对象存储
- **关键规则**：commit 阈值 20000 token（一期默认，二期可配置）；archive 是会话级归档；180 天迁 TOS 是企业侧冷存策略；冷存后按 URI 可恢复

#### F6 授权管理流程（对应 S4/S6/S7，§1.3.3-1.3.4）

知识库从创建到被 Agent 授权访问的全流程。

```
B 类用户创建知识库
  │ 填写名称、归属（个人/部门/公司）、敏感度
  ▼
②层登记知识库归属与命名空间
  │ 分配 account / namespace
  ▼
B 类用户配置授权矩阵
  │ Agent × 知识库 -> 允许/不允许
  │ 一期：1-to-1 绑定；二期：完整 RBAC+ACL
  ▼
②层授权决策生效
  │ Agent 请求时查矩阵 -> 放行/拒绝
  ▼
Agent 访问知识库
  │ ②层按授权路由到目标 account
  ▼
变更管理（新增/撤销授权）
  │ 矩阵配置一行即生效，不动知识库数据
```

- **涉及角色**：B 类（管理视角）
- **涉及系统**：②知识库授权中心、管理控制台
- **关键规则**：知识库独立于 Agent 存在；同一库可被多 Agent 访问，同一 Agent 可访问多库；授权变更仅改矩阵配置，零改造；公司政策库为只读属性

#### F7 审计治理流程（对应 S4，§1.3.2 ②层职责）

②层作为所有 Agent 请求的唯一全量拦截点，做审计与成本归因。

```
Agent 请求入站
  │
  ▼
②层全量拦截（协议适配 -> 鉴权 -> 授权决策 -> 路由）
  │
  ▼ 记录审计日志
  │ Agent 身份 + 时间戳 + 目标 account + 操作类型
  │
  ▼ token 成本归因
  │ LLM/Embedding token -> Agent × 知识库
  ▼
审计日志存储
  │
  ▼ 可观测大盘展示
  │ 访问量/命中率/延迟/成本/异常
  ▼
B 类用户审计查询（按 Agent/知识库/时间范围筛选）
```

- **涉及角色**：B 类（管理视角）、C 类（建设方）
- **涉及系统**：②知识库授权中心、审计日志、可观测大盘
- **关键规则**：②层是唯一全量拦截点（100% 覆盖 Agent×知识库访问）；联邦查询记录"一次请求触达哪些库"；token 成本精确归因到 Agent×知识库；审计日志支持按维度筛选

### 4.2 各类用户操作流程

基于 §1.1.1 三类用户，梳理各自的核心操作流程。每条流程标注前置条件、操作步骤与后置状态。

#### A 类 · Agent 使用方（个人 / 知识库维护方）

**A1 查看个人偏好记忆**
- 前置条件：用户已有 Agent 对话记录，Stop Hook 已 capture 偏好
- 操作步骤：登录管理控制台 -> 进入「画像记忆查看页」-> 按 user_id 筛选 -> 查看偏好字段（编码习惯/语言/风格）与最近更新时间
- 后置状态：用户了解已沉淀的偏好，可判断是否需修正

**A2 查看个人技能记忆**
- 前置条件：用户已有 Agent 对话记录，技能已被 Extraction 分类
- 操作步骤：登录管理控制台 -> 进入「画像记忆查看页」切换技能 tab -> 查看技能列表与习得来源
- 后置状态：用户了解已沉淀的技能

**A3 查看会话归档**
- 前置条件：用户有已结束的会话且触发过 archive
- 操作步骤：登录管理控制台 -> 进入会话归档列表 -> 按 session_id 查看归档内容 -> 如超 180 天需从 TOS 恢复
- 后置状态：用户可回溯历史会话上下文

**A4 导入企业文档到 L1**
- 前置条件：用户有知识库维护权限（ADMIN 或被授权）
- 操作步骤：进入「知识库基础管理页」-> 选择目标知识库 -> 点击导入 -> 选择上传方式（前端上传/TOS/URL/API）-> 等待切片+向量化完成 -> 在文件列表确认
- 后置状态：文档可被 MCP search 检索召回

**A5 检索调试（web-studio）**
- 前置条件：L1 知识库已有文档
- 操作步骤：进入 web-studio -> 选择知识库 -> 输入检索 query -> 调整参数（Top-k/Dense Weight/阈值）-> 查看召回结果与检索轨迹
- 后置状态：用户验证检索效果，定位召回偏差

#### B 类 · 公司 / 部门（管理视角）

**B1 创建 / 管理知识库**
- 前置条件：用户有 ADMIN 权限
- 操作步骤：进入「知识库基础管理页」-> 点击新建 -> 填写名称/归属（个人/部门/公司）/敏感度 -> ②层登记归属与命名空间 -> 可上传文档或配置 Agent 授权
- 后置状态：知识库已创建，可被授权 Agent 访问

**B2 配置 Agent × 知识库授权矩阵**
- 前置条件：知识库已创建、Agent 已注册（二期）
- 操作步骤：进入「授权矩阵配置页」-> 选择 Agent -> 勾选可访问的知识库 -> 设置操作权限（读/写/管理）-> 保存生效
- 后置状态：②层按矩阵做授权决策，Agent 请求被放行或拒绝

**B3 查看审计日志**
- 前置条件：②层已运行并有访问记录
- 操作步骤：进入「审计查询页」-> 按 Agent/知识库/时间范围/操作类型筛选 -> 查看访问明细（身份+时间+目标+操作）-> 可导出
- 后置状态：管理者掌握访问合规情况

**B4 查看成本分摊**
- 前置条件：②层已记录 token 成本归因数据
- 操作步骤：进入「成本分摊大盘」-> 按部门/Agent/知识库维度查看 token 消耗与费用 -> 可下钻明细
- 后置状态：管理者掌握成本分布，可做预算管控

**B5 管理用户与角色**
- 前置条件：用户有 ROOT 权限
- 操作步骤：进入「account 管理页」-> 查看/新增/编辑 account 成员 -> 分配角色（ROOT/ADMIN/USER）-> 处理离职/变动（§1.3.4(5)）
- 后置状态：成员角色生效，权限按角色控制

#### C 类 · 云端 Agent 团队（建设方）

**C1 注册新 Agent**
- 前置条件：管理控制台可用
- 操作步骤：进入「Agent 注册与接入配置页」-> 点击新建 Agent -> 填写名称/描述/归属部门 -> 选择接入通道（Hooks/MCP/SDK）-> 生成身份凭证（mTLS/JWT）
- 后置状态：Agent 已注册，待配置授权与接入

**C2 配置 Agent 接入通道**
- 前置条件：Agent 已注册
- 操作步骤：在 Agent 配置页 -> 根据决策树（§2.1）确认通道 -> 下载 Hooks 脚本/MCP 配置/SDK 包 -> Agent 侧集成 -> health check 验证
- 后置状态：Agent 可经 ②层通信

**C3 L1 各环节配置（二期）**
- 前置条件：二期管理控制台已上线
- 操作步骤：进入「L1 各环节配置页」-> 选择知识库 -> 配置切片策略/Embedding 模型/检索参数/Rerank -> 保存生效
- 后置状态：L1 检索按自定义参数运行

**C4 L2 记忆规则配置（二期）**
- 前置条件：二期管理控制台已上线
- 操作步骤：进入「L2 记忆配置页」-> 配置事件记忆规则模板（规则名/抽取方法/字段定义/权重）-> 配置画像记忆规则模板 -> 配置 capture 门禁/commit 阈值 -> 配置画像更新时机与方式
- 后置状态：L2 记忆按自定义规则提取与更新

**C5 系统监控与运维**
- 前置条件：系统已部署运行
- 操作步骤：进入「可观测大盘」-> 查看访问量/命中率/延迟/异常 -> 进入「生命周期管理页」-> 管理冷存/归档策略 -> 必要时进入 ov CLI 做运维操作
- 后置状态：系统运行状态可视，异常可及时发现

### 4.3 产品列表

基于 §1.3.1 三层架构与 §3.1-3.2 功能架构，将系统划分为 4 个产品/子系统，每个产品有明确的定位、职责与用户群体。

#### P1 · 管理控制台（企业侧 Web 管理平台）

- **定位**：面向 B 类（管理者）与 C 类（建设方）的统一 Web 管理入口，承载所有需开发页面（一期 2 个自研 + 二期 12 个自研）
- **核心职责**：Agent 注册与接入配置、知识库管理、授权矩阵配置、L1/L2 参数配置、审计查询、成本查看、系统监控
- **包含模块**：§3.1 模块⑥管理控制台（一期）+ §3.2 模块⑥管理控制台完整版（二期）
- **用户群体**：B 类（管理者）、C 类（建设方）
- **对应架构层**：②层（部署在知识库授权中心侧）
- **与官方 web-studio 的关系**：web-studio 是 OpenViking 官方按实例提供的 Playground + 检索轨迹可视化工具，P1 管理控制台是平台级管理页面，两者互补不重叠（§3.0）

#### P2 · 知识库授权中心（网关服务）

- **定位**：所有 Agent 请求的唯一入口，做协议适配、鉴权、授权、路由、联邦、审计与观测
- **核心职责**：多 Agent 消息归一（Hooks/MCP/SDK -> OV HTTP）、mTLS/JWT 身份鉴权、Agent×知识库 授权矩阵（RBAC+ACL）、按授权路由到目标 account、跨 account 联邦 fan-out、审计日志写入、token 成本归因、观测埋点
- **包含模块**：§3.1 模块①接入网关（一期简化版）+ §3.2 模块④②层知识库授权中心（二期完整版）+ §3.2 模块⑤知识库独立化
- **用户群体**：无直接用户（后端服务），被 P1 管理控制台配置、被 P3 Agent 接入套件调用
- **对应架构层**：②层
- **分期差异**：一期简化版（协议适配+鉴权+1-to-1路由+审计+观测，无矩阵/联邦）；二期完整版（补全 RBAC+ACL 矩阵+联邦+account 级路由）

#### P3 · Agent 接入套件（Agent 侧集成代码包）

- **定位**：跑在 Agent 端的 Hooks/MCP/SDK 代码，让 Agent 具备记忆读写与检索能力
- **核心职责**：Stop Hook 自动 capture（auto-capture.mjs）、UserPromptSubmit Hook 自动 recall（auto-recall.mjs）、MCP 9 工具（search/read/list/store/add_resource/grep/glob/forget/health）、SDK 编程接入
- **包含模块**：§3.1 模块⑤ L2 记忆基础链路中的 Agent 侧集成部分 + §3.2 模块①数据源接入中的 Agent 侧集成部分
- **用户群体**：C 类（建设方，负责集成部署）
- **对应架构层**：①Agent 应用层
- **通道选择**：Claude Code -> Hooks+MCP 双通道；Cursor/Trae/OpenClaw -> MCP 通道；LangChain/自建 -> SDK 通道（决策树见 §2.1）

#### P4 · OpenViking 实例（记忆与知识库底座）

- **定位**：OpenViking 官方产品，作为 L1 向量知识库与 L2 记忆系统的统一底座引擎
- **核心职责**：文档切片+Embedding+向量索引+两阶段检索（flat_hybrid+rerank）、Memory Extraction（LLM 5 类分类）、WM v2 Compression、L0/L1/L2 三层存储、session archive、web-studio 控制台、ov CLI 运维
- **包含模块**：§3.1 模块②L1 基础 RAG + 模块③RAG 可视化 + 模块④account 级隔离 + 模块⑤ L2 记忆基础链路（后端部分）+ §3.2 模块②L1 产品化 + 模块③L2 记忆产品化
- **用户群体**：无直接用户（后端服务），被 P2 知识库授权中心调用、被 P1 管理控制台管理
- **对应架构层**：③层
- **形态**：单实例多 account（account 级隔离），含 openviking-server + web-studio + ov CLI

**产品间关系**：

```
P1 管理控制台 ──配置──> P2 知识库授权中心 ──路由──> P4 OpenViking 实例
                          ↑
                   P3 Agent 接入套件 ──请求──> P2（经 ②层鉴权）
                          ↑
                    ① Agent 应用层（CC/OpenClaw/Hermes...）
```

> P1 管理 P2 的配置（Agent 注册/授权矩阵/L1-L2 参数），P2 拦截 P3 的请求并路由到 P4，P4 执行实际的记忆读写与检索。P1 的 web-studio 部分直接由 P4 官方提供。
