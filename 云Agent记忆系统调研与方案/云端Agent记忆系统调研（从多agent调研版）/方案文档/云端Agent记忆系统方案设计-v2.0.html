云端 Agent 记忆系统方案设计#

0. 阅读说明#

1. 业务侧方案设计#

1.0 方案概览#

基于 《调研文档》5.6 选型结论，OpenViking 作为主选型。本章按「概览 → 蓝图 → 架构 → 风险」四段展开：1.0 方案概览与核心概念速查，1.1 产品蓝图（一/二期业务需求与开发功能），1.2 业务架构（知识分层 L1/L2），1.3 系统架构（三层架构图 + 分期规划），1.4 方案级风险。接入与记忆模型见第 2 章。

方案价值主张：以「知识库」为中心抽象，OpenViking 为底座，叠加 ② 层知识库授权中心与 account 级隔离，实现跨 Agent 记忆复用、部门/个人/会话三级隔离与企业级合规治理——让 Agent 记得住用户、管得住知识、审得清访问。

关键数字速览：2 期演进（L1 基础 RAG + L2 记忆基础链路 → L1/L2 产品化 + 多 Agent 治理）· 3 层架构（①应用层 / ②授权中心 / ③单实例）· 1 个 OV 实例（account 级隔离）· 3 接入通道（Hooks / MCP / SDK）· 4 关键数据流路径 · 6 类知识库 · 7 类记忆类型 · 4 类企业侧扩展需求。

1.0.1 核心概念速查#

阅读本章架构图与目录表前，先掌握以下 6 个核心概念（架构图中 (官方) / (企业侧扩展) 标注依据此划分）：

  • 官方原生：OpenViking 开源产品自带的能力（4 命名空间 / 7 Hook / 9 MCP / L0-L2 分层 / RAGFS 存储引擎 / 多租户 account-user 模型等），开箱即用
  • 企业侧扩展：OpenViking 官方不提供、由本方案自建补齐的能力（② 层知识库授权中心 / account 级隔离 / 跨知识库联邦查询 / 180 天冷存 / KMS 审计等），用于满足企业级多 Agent 治理需求
  • ② 层知识库授权中心：本方案核心扩展组件，做 Agent×知识库 授权矩阵（哪个 Agent 能访问哪个知识库）+ 身份鉴权 + 路由 + 审计，Agent 不直连知识库、所有请求经此层
  • account 级隔离：部门/公司等高敏知识库用独立 OpenViking account 部署（account 级逻辑隔离），复用官方 account/user 模型，单实例内实现部门/公司/个人三级隔离
  • 跨知识库联邦查询：② 层并行 fan-out 多个 account 检索再合并排序（单实例内跨 account），让一次请求触达多个库
  • 知识库（KB）：独立于 Agent 存在的记忆载体，按归属/用途分类（个人偏好/技能/项目上下文/部门SOP/公司政策/会话归档），Agent 被授权访问、不拥有

1.1.2 一期蓝图：L1 基础 RAG + L2 记忆基础链路跑通#

一期目标：用最简形态跑通 Agent↔L1+L2 双向闭环——L1 侧：从 Agent 获取信息（项目上下文 B1、Agent 生成文档 B3 写入 L1）+ 给 Agent 用（MCP search 检索召回返回 Agent）+ L1 向量知识库基础 RAG 可用 + RAG 可视化文件列表 + 支持选择企业传统知识库文档；L2 侧：从 Agent 获取信息（B4 偏好/事件/案例/技能经 Hooks auto-capture + Memory Extraction 写入 L2）+ 给 Agent 用（自动召回路径 3 + MCP search 路径 4）+ 会话归档冷存（commit→archive→180 天迁 TOS），均用默认配置。验证 OpenViking RAG + 记忆能力在企业场景下的可行性，同时为二期②层网关入口预埋。

1.1.3 二期蓝图：L1/L2 产品化 + 多 Agent 治理#

二期目标：L1 向量知识库产品化（各环节支持用户配置）+ L2 记忆产品化（提取规则/时机/画像更新策略可配置，基础链路一期已跑通）+ 多 Agent 多库统一治理。②层补全授权矩阵与跨 account 联邦，Agent 侧接入契约不变、零改造演进。

业务背景：2000 人规模互联网公司统一部署多类 AI Agent，知识库类型多（个人偏好/技能、项目上下文、部门 SOP、公司政策、会话归档等 6 类，见 1.3.3），且知识库天然需要被分享与复用。一期跑通了 Agent↔L1+L2 双向闭环（L1 基础 RAG + L2 记忆基础链路·默认配置），但 L1/L2 各环节不可配置、无法支撑多 Agent 协作，二期承接这些产品化与治理需求的落地（二期技术形态见 1.3.0 分期规划）。

二期需求 → 开发功能 → 验收清单：

业务需求 开发功能 技术归属 依赖 验收标准
L1 各环节可配置 切片策略 / Embedding 模型 / 检索参数 / Rerank 用户可配置 官方 + 企业侧 管理控制台 用户可在控制台配置切片策略、选择 Embedding 模型等
L2 记忆系统产品 提取规则（LLM 5 类分类）+ 时机（capture 门禁/commit 阈值）可配置 官方 + 企业侧 管理控制台 用户可配置记忆提取规则与 capture 时机
需求一 · 一个 Agent 需要多个知识库源 ②层跨 account 联邦 fan-out（单实例内多 account 并行检索 + 合并排序） 企业侧扩展 授权矩阵 一次请求并行检索个人库+部门库+公司库，结果按相关度+知识库优先级合并去重
需求二 · 多个 Agent 共用一个知识库源 知识库独立化（独立创建/归属/授权登记）+ 同一库被多 Agent 授权访问 企业侧扩展 授权矩阵 公司政策库只存一份、全公司所有 Agent 只读共享，一处更新所有授权 Agent 即时生效
需求三 · 知识库类型多需统一治理与隔离 ②层 RBAC + ACL 授权矩阵 + account 级路由 + 审计 + 成本归因 企业侧扩展 KMS / audit log 部门管理者可管控本部门库的 Agent 访问范围；token 成本可精确分摊到 Agent×知识库
需求四 · 新增 Agent 零改造接入 ②层授权矩阵配置即可接入（解耦 Agent 与知识库） 企业侧扩展 授权矩阵 新增 Agent 仅在矩阵配置一行授权，不动任何知识库数据，零改造上线

综上：一期跑通 Agent↔L1+L2 双向闭环（L1 基础 RAG + L2 记忆基础链路·默认配置），二期面向 2000 人多 Agent 公司的真实场景——L1/L2 产品化（各环节/规则/时机可配置）+ 多 Agent 多库统一治理与分享，是知识库独立化、跨 Agent 协作记忆复用的二期目标。

1.2.4 会话归档（archive）的双重角色#

archive 在本架构中具有双重角色，需单独说明：

  • 作为 L2 记忆系统的归档层：会话结束/PreCompact 时触发 archive，落到 viking://session/{sid}/archive/，是记忆系统的冷数据层（对应 《调研文档》4.1 归档记忆）。
  • 作为 L1 向量知识库的数据源：archive 经沉淀/转存后，可提取有价值的项目上下文、决策案例等入库 viking://resources/，服务于向量知识库检索。
  • 边界：archive 原始归属 L2（记忆系统），转存后的衍生内容归属 L1（向量知识库）。180 天后迁 TOS 冷存（企业侧策略，1.1.2）。

1.2.5 OpenViking 统一引擎#

  • 如 §1.2.1 底座层所示，OpenViking 官方定位 "Context Database for AI Agents"，L1 与 L2 由同一实例统一承载（喂文档=知识库、喂对话=记忆）。
  • 产品概念上分层（L1 管"懂不懂资料"、L2 管"认不认得你"），实现上共用同一套 RAGFS + VectorDB 底座，靠 viking:// 命名空间区分（resources/ vs user/+session/）。
  • 这也解释了为什么记忆系统能"复用 RAG 能力"——同一引擎、同一套向量检索链路（flat_hybrid + rerank 两阶段检索，2.5）。

系统架构（Agent→授权中心→单实例）见 1.3.1；记忆类型与命名空间映射见 2.2；批量导入入口见 《调研文档》4.4.2；知识库归属类型见 1.3.3。

1.3.0 设计理念：单实例 + account 级隔离#

OpenViking 官方提供通用记忆能力，业务上有 4 类需求（account 级隔离 / Agent×知识库 授权矩阵 / 跨 account 联邦查询 / 归档冷存 180 天迁 TOS）官方不解决或解决不足，需企业侧扩展（4 类需求与官方能力边界的详细对照见文末附录 A）。

以下架构图中，(官方) 标注为 OpenViking 原生能力，(企业侧扩展) 标注为本报告设计的企业侧治理逻辑。

1.4 方案级风险（4 条）#

  1. 单产品绑定 — 若 OpenViking 项目停滞或不满足新需求，迁移成本高
    - 缓解：接受单栈绑定风险。PoC 阶段充分验证 8 项核心能力 + 3 维 RAG 底座 + 5 道业务题覆盖度，确保上线前识别能力缺口。不预留 Adapter 抽象层（避免过度设计）。若未来确需迁移，按当时实际需求评估迁移成本（重评估触发条件见 5.2 第3条）。
  2. 企业合规责任由部署侧承担 — OpenViking 不提供第三方 SaaS 合规证书；由于是自托管部署，数据不出企业，合规能力由公司内部审计 / 等保 / 数据驻留策略保证（这是私有化部署的常规做法，不构成产品缺陷）
  3. 被动抽取质量需持续调优 — OpenViking 官方抽取管线（compression.ov_wm_v2 + Memory Extraction，附件3 第 297-308 行）依赖 LLM 与 prompt
    - 缓解：建立 golden set 抽取效果基线，定期回归；PoC 阶段用真实数据校准；利用 web-studio 检索轨迹可视化定位抽取偏差
  4. 多知识库联邦查询延迟 — 本方案单实例 account 级隔离下，Agent 跨知识库召回需 ② 层 fan-out 多个 account 并行检索再合并排序，增加召回 P95 延迟
    - 缓解：并行 fan-out（最多 5 个 account，KB_FEDERATION_MAX_KB）+ 8000ms 超时（KB_FEDERATION_TIMEOUT_MS）；高频知识库结果本地缓存（授权矩阵缓存 KB_AUTH_MATRIX_CACHE_TTL=300s）；Hooks 自动召回（路径 3）只查个人 account（单 account 无联邦），仅 MCP search（路径 4）才触发跨知识库联邦

2.1 接入通道#

接入方式是 Agent 出站时用什么协议与本系统通信的选择，和数据流主干（①→②→③）是两件事：同一请求按 Agent 框架能力择一走 Hooks / MCP / SDK 通道，而非依次经过。接入方式不是数据流的"第二层"，而是 ① Agent 出站时的协议选择维度（官方 · 附件3 第 60-110 行）。

② 层观测埋点独特价值：② 层是所有 Agent 请求的唯一全量拦截点，在此埋点可捕获 100% 的 Agent×知识库访问（若埋点放各知识库实例内部，只能看到单实例视角，无法聚合）。具体价值：① 跨知识库归因——一次 Agent 请求可能触达多个知识库（联邦查询），只有 ② 层能记录"这次请求触达了哪些库"；② token 成本分摊——② 层知道 Agent 身份 + 目标知识库，能把 LLM/Embedding token 成本精确归因到"哪个 Agent 访问哪个知识库花了多少"，支撑按部门/Agent 的成本分摊。

2.4 记忆存储模型#

本节回答"记入后如何分层、压缩、归档存储"。对应 2.0 路径 1/2 中"服务端处理"段的内部逻辑。

L0/L1/L2 三层结构（官方 · 附件3 第 337-343 行）：

Working Memory v2 Compression（官方 · 附件3 第 297-308 行）：

  • 触发：pending token ≥ 20000（COMMIT_TOKEN_THRESHOLD）时触发 commit
  • 压缩方式：LLM Function Calling，按 WM 7 sections 结构化压缩
  • 配合 Memory Extraction：LLM 按 MemoryTypeRegistry 5 类分类（preferences/events/cases/memories/skills）

commit / archive 阈值与冷存：

阶段 触发条件 动作 归属

附录 A：企业侧扩展需求详述#

为什么需要"企业侧扩展"？ OpenViking 是面向个人开发者 / 小团队的通用开源产品，官方只提供必要且通用的能力（4 个顶级命名空间、7 Hook、9 MCP 工具、LLM+Embedding+VLM 三分工）。业务上有 4 类需求官方不解决或解决不足，需企业侧扩展。下表对照官方能力缺口与企业侧方案：

# 企业需求 OpenViking 官方能力 官方缺口 企业侧方案 依赖
1 部门级隔离（设计部/研发部 SOP 不串数据） account 级逻辑隔离（Concepts 11） account 级隔离可用；缺口在跨 account Agent 授权 ② 层授权矩阵 + account 级隔离（复用官方 account 模型） ② 层 + account 模型
2 Agent×知识库 授权矩阵（哪个 Agent 能访问哪个库） account/user 模型 表达不了跨租户 Agent 授权关系 ② 层授权中心 RBAC + ACL KMS / audit log
3 跨知识库联邦查询（一次请求触达多库） 单实例多 account 视角（account 间不互通） 无跨 account 联邦能力 ② 层 fan-out 多 account 并行检索 + 合并排序（单实例内） 授权矩阵
4 归档冷存 180 天迁 TOS resources 挂 S3 无"180 天规则"企业侧策略 180 天未访问迁移 TOS 对象存储 TOS

以上 4 类企业需求对应的核心概念（官方原生 / 企业侧扩展 / ②层知识库授权中心 / account 级隔离 / 跨知识库联邦查询 / 知识库 KB）定义见 1.0.1 核心概念速查。

附录 B：设计理念：分界与承接#

  • 官方能力：解决"记忆怎么读、怎么写、怎么召回、怎么分层、怎么被 LLM 结构化压缩"+ account/user/peer 多租户隔离 + ROOT/ADMIN/USER 角色权限——覆盖记忆读写/召回/分层/压缩/多租户隔离。
  • 企业侧扩展：解决"哪个 Agent 能访问哪个知识库、跨 account 联邦查询、account 级隔离、审计怎么落"——覆盖 Agent×知识库 授权/联邦查询/account 级隔离/审计（官方 account/user 模型表达不了这种跨租户 Agent 授权关系）。
  • 两者接口：企业侧扩展不改 OpenViking 源码，通过 ② 层知识库授权中心（网关模式）实现——
    0. 协议适配（入站首步）：多 Agent 消息格式异构（Hooks transcript JSON / MCP 工具调用 / SDK 编程对象），② 层入站时先归一为 OpenViking 的 viking:// + REST 语义（addMessage/search/find + commit/archive），再进入鉴权；
    1. 身份鉴权 + 授权决策：归一后验 mTLS/JWT 令牌 → 查 Agent×知识库 授权矩阵（允许/不允许）→ 放行或拒绝；
    2. 路由转发 + 联邦查询：放行后路由到目标知识库实例；跨库召回时 ② 层 fan-out 多实例并行检索再合并排序。
  • 好处：OpenViking 升级 → ② 层授权中心无需重写（仅靠 HTTP 网关转发对接）；合规责任边界清晰（与 1.4 风险 2 一致）。
