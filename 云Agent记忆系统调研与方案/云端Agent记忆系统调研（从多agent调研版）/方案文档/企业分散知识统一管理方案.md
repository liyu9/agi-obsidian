# 企业分散知识统一管理方案

> **定位**：本文档是《云端Agent记忆系统方案设计-v2.1》的知识管理视角补强。v2.1 回答"数据源怎么接入 OpenViking"，本文档回答"接入后分散知识怎么合理管理"--明确哪些知识入 RAG、哪些不入、怎么分层、怎么治理、怎么演进。
>
> **与 v2.1 的关系**：不推翻 v2.1，而是补全 v2.1 未覆盖的"log 系统处理决策"和"知识分层治理方法论"。

## 1. 知识分类决策：哪些入 RAG，哪些不入

### 1.1 核心原则

**不是所有知识都该入 RAG。** 企业分散知识按"数据形态 + 查询模式 + 数据量级"做分类决策：

| 知识源 | 数据形态 | 决策 | 入哪里 | 理由 |
|---|---|---|---|---|
| **WIKI / 在线文档** | 非结构化文档 | ✅ 入 RAG | L1 向量知识库 | 语义检索强项，RAG 主战场 |
| **智能表格** | 半结构化 | ✅ 入 RAG | L1 向量知识库 | 转文档/CSV 入库，支持语义 + 结构化检索 |
| **静态文档(md/pdf/ppt)** | 非结构化 | ✅ 入 RAG | L1 向量知识库 | RAG 主战场 |
| **Agent 沉淀(B1-B4)** | 动态事件型 | ✅ 入 RAG/记忆 | B1/B3->L1, B4->L2 | v2.1 §1.2.3 已覆盖 |
| **log 系统** | 时序型、海量 | ❌ 不入 RAG | Agent 直连查询 | 量太大、时序型、实时性高，入 RAG 成本爆炸且失真 |
| **HRIS/OA/CRM** | 关系型表 | ❌ 不入 RAG | Agent 直连查询 | 精确查询为主，RAG 不擅长 |

### 1.2 决策判据（可复用）

- **入 RAG 的判据**：非结构化/半结构化 + 语义检索需求 + 数据量可控（GB-TB 级）
- **不入 RAG 的判据**：海量时序/关系型 + 精确查询为主 + 实时性要求高

### 1.3 log 的特殊处理（关键洞察）

> **log 本身不入 RAG，但 log 的"元数据"要入 RAG 作为"资产目录知识"。**

具体做法：
- **log 原始数据**留在 ELK / ClickHouse / 数仓，Agent 经授权后直连查询（不入向量库）
- **log 的元数据**（有哪些 log 流、每个 log 流什么结构、在哪个系统、怎么查）作为文档入 L1 的资产目录命名空间，让 Agent 先通过 RAG 检索"发现"log 在哪，再直连查询

**背书**：火山引擎 LAS + ByteHouse 构建 PDF 知识库的实践中，结构化数据与文档型 RAG 分离处理；腾讯 WeKnora 的"多源同步"也是元数据同步而非原始数据全量入库。

**这样做的好处**：
- 避免了 log 全量向量化的成本爆炸（log 每天 TB 级，全量向量化成本不可接受）
- 避免了 log 入 RAG 后的"时序失真"（向量检索是语义相似，不是时序查询）
- Agent 仍能"发现"log（通过 RAG 检索资产目录），再直连查询

## 2. 知识分层组织：6 类形态 × RAG 分层映射

### 2.1 知识的 6 类形态

企业知识不是一锅粥，归纳成 6 类形态，每类特征不同、归属不同：

| # | 知识形态 | 例子 | 回答的问题 | 特征 |
|---|---|---|---|---|
| 1 | **领域知识** | 业务说明/产品定位/规则手册 | "业务是什么" | 半静态，业务变了才更新 |
| 2 | **方法论知识** | 分析方法/SOP/最佳实践/图表规范 | "怎么做" | 较稳定，最佳实践沉淀 |
| 3 | **资产目录知识** | log 索引/表文档/数据源清单 | "有哪些数据" | 动态增长，随数据源增加 |
| 4 | **映射标准知识** | ID字典/字段枚举/指标口径/别名 | "怎么对齐" | 高频复用，每次查询都要用 |
| 5 | **流程规则知识** | 防编造规则/自检规则/角色约束 | "按什么纪律走" | 约束性，管 Agent 行为 |
| 6 | **经验复用知识** | 分析计划/历史决策案例/解析器模板 | "上次怎么做的" | 可重放，省重复劳动 |

### 2.2 6 类形态 × L1/L2 分层映射

| 知识形态 | 入哪里 | 怎么存（命名空间） | 作用 |
|---|---|---|---|
| 1. 领域知识 | L1 向量知识库 | `viking://resources/domain/` | Agent RAG 检索业务知识 |
| 2. 方法论知识 | L1 向量知识库 | `viking://resources/methodology/` | Agent RAG 检索方法论 |
| 3. 资产目录知识 | L1 向量知识库 | `viking://resources/catalog/` | Agent 检索"有哪些 log/表/数据源" |
| 4. 映射标准知识 | L1 + 元数据配置 | `viking://resources/mapping/` + 字段映射配置 | ID 翻译/字段对齐 |
| 5. 流程规则知识 | **不入 RAG，作为 Agent 规则** | CLAUDE.md / rules / 提示词 | 约束 Agent 行为（防编造/必自检/必确认） |
| 6. 经验复用知识 | L1 + L2 | `viking://resources/experience/` + `viking://user/{uid}/` | 跨次复用 + 个性化记忆 |

### 2.3 两个关键设计决策

**决策 1：流程规则知识（第 5 类）不入 RAG**

流程规则知识是约束 Agent 行为的纪律（防编造、必自检、必确认），应该作为 Agent 的规则配置（CLAUDE.md / rules / 提示词），而不是检索知识。

理由：如果把规则当文档入 RAG，Agent 可能检索不到或忽略，纪律就失效了。规则必须是"强制注入"，不是"按需检索"。

**背书**：数据分析工具的 `.claude/rules/analyze-pipeline.md` + `CLAUDE.md` 就是把流程纪律作为 Agent 规则配置，而非入库检索。

**决策 2：经验复用知识（第 6 类）横跨 L1+L2**

- **通用经验**（如分析计划模板、标准 SOP）入 L1 `resources/experience/`，供所有人复用
- **个人偏好**（如某用户习惯的分析方式）入 L2 `user/{uid}/`，个性化召回

**背书**：腾讯 WeKnora 的"Wiki Mode + ReAct Agent"组合，就是通用知识（Wiki）+ 个性化推理（Agent）的双层结构。

## 3. 知识治理机制：5 个机制落地到 RAG+记忆

### 3.1 五个治理机制

| 机制 | 落地到 RAG+记忆 | 具体实现 |
|---|---|---|
| **1. 分层组织** | RAG 命名空间分层 | `viking://resources/{domain/methodology/catalog/mapping/experience}/` 五个子命名空间 |
| **2. 索引发现** | RAG 检索 + 目录索引 | L1 向量检索 + `resources/catalog/INDEX.md` 资产总目录 |
| **3. 随流程注入** | RAG 按需检索 + 记忆自动召回 | 需求阶段检索领域知识；取数阶段检索资产目录；加工阶段检索映射标准；交付阶段检索方法论 |
| **4. 可复用可重放** | L1 经验复用 + L2 个性化记忆 | 分析计划入 L1 可重跑；用户偏好入 L2 自动召回 |
| **5. 可演进可扩展** | 增量入库 + 目录自动更新 | 新文档增量入 L1；新 log 流自动更新资产目录 |

### 3.2 "随流程注入"机制详解（最关键）

这是知识管理的核心--知识不是一次性全灌给 Agent，而是**按流程节点按需注入**：

```
Agent 执行流程          注入的知识              从哪来
─────────────────────────────────────────────────────────
需求理解阶段     <- 领域知识 + 方法论        <- RAG 检索 resources/domain + methodology
数据源发现阶段   <- 资产目录知识             <- RAG 检索 resources/catalog
取数查询阶段     <- 映射标准知识             <- RAG 检索 resources/mapping
加工分析阶段     <- 经验复用知识             <- RAG 检索 resources/experience + L2 召回偏好
交付输出阶段     <- 方法论 + 图表规范        <- RAG 检索 resources/methodology
贯穿全程         <- 流程规则知识             <- Agent 规则配置（非 RAG，强制注入）
```

**设计依据**：
- Agent 窗口有限，精准注入 > 全量灌入（避免上下文爆炸）
- 每个阶段只加载需要的知识，调用更精准
- 流程规则知识强制注入（不靠检索），确保纪律生效

**背书**：
- 微软 GraphRAG 的"社区层次结构"也是分层按需检索，不是全量灌入
- 腾讯 WeKnora 的"ReAct Agent + MCP 工具"按需调用知识，而非一次性加载
- 火山引擎 RAG 解决方案的"检索增强"也是按需检索注入

## 4. 分散知识集成架构图

```
┌──────────────────────────────────────────────────────────────────┐
│  企业分散知识源                                                    │
│  WIKI / 在线文档 / 智能表格 / 静态文档 / log系统 / HRIS·OA·CRM    │
└────────────┬─────────────────────────────────────┬───────────────┘
             │ 知识库型（入RAG）                    │ 结构化/时序（不入RAG）
             ▼                                     │
┌──────────────────────────────────────┐          │
│  知识分类决策层                        │          │
│  · 非结构化/半结构化 -> 入 L1           │          │
│  · 时序/关系型 -> 不入，只登记目录      │          │
└────────────┬─────────────────────────┘          │
             │ 入库                                │ 元数据登记
             ▼                                     │
┌─────────────────────────────────────────────────┐│
│  RAG 知识库 + 记忆系统（OpenViking）              ││
│  L1 向量知识库（6类知识分层，其中5类入库）         ││
│  ├ resources/domain/      领域知识                ││
│  ├ resources/methodology/ 方法论知识              ││
│  ├ resources/catalog/     资产目录知识 <──────────┼┘
│  ├ resources/mapping/     映射标准知识            │  log/HRIS 元数据登记为资产目录
│  └ resources/experience/  经验复用知识            │
│  L2 记忆系统（用户级）                             │
│  └ user/{uid}/  偏好/事件/案例/技能               │
└────────────┬────────────────────────────────────┘
             │ RAG检索 + 记忆召回
             ▼
┌─────────────────────────────────────────────────┐
│  Agent（随流程注入知识）                           │
│  · 知识注入：RAG 按流程节点检索                   │
│  · 规则约束：CLAUDE.md/rules（非RAG，强制注入）   │
│  · 直连查询：log/HRIS 经授权直连                  │
└─────────────────────────────────────────────────┘
```

### 4.1 架构要点

1. **分类决策层**：先判断知识源是"知识库型"还是"结构化/时序型"，决定入 RAG 还是只登记目录
2. **L1 五子命名空间**：领域/方法论/资产目录/映射标准/经验复用 分层存储
3. **资产目录桥接**：log/HRIS 不入 RAG，但元数据登记到 `resources/catalog/`，让 Agent 能"发现"它们
4. **Agent 三通道**：RAG 检索（知识库型）+ 直连查询（log/结构化）+ 规则约束（强制注入）

### 4.2 与 v2.1 架构的衔接

| v2.1 现有 | 本方案补强 |
|---|---|
| 数据源 A 批量导入 L1（§1.2.3 L244） | 补：A 入库时按 5 子命名空间分类 |
| 数据源 B1-B4 写入 L1/L2（§1.2.3 L245-248） | 不变，B1-B4 仍按 v2.1 路径 |
| L0/L1/L2 三层摘要管线（§2.5） | 不变，本方案的 5 子命名空间在 L1 内部 |
| account 级隔离（§1.3.4） | 不变，5 子命名空间在 account 内 |
| log 系统未覆盖 | **新增**：log 不入 RAG，元数据登记为资产目录 |

## 5. 落地演进路径（三期）

### 5.1 三期分期

| 期次 | 目标 | 具体动作 | 对应 v2.1 |
|---|---|---|---|
| **一期：知识库型入库** | wiki/文档/智能表格入 RAG | 数据源 A 批量导入 L1；建资产目录 `resources/catalog/`；建领域知识库 `resources/domain/` | 对齐 v2.1 一期 §3.1 |
| **二期：知识分层治理** | 6 类知识分层 + 治理机制 | 方法论/映射标准/经验复用分类入库；建索引；随流程注入；L2 记忆跑通 | 对齐 v2.1 二期 §3.2 |
| **三期：log/结构化集成** | log 不入 RAG 但可发现可直连 | log 元数据登记为资产目录；Agent 直连查询通道；跨源统一治理 | v2.1 未覆盖，新增 |

### 5.2 一期优先做的三件事

1. **建资产目录**：把"有哪些知识源"先登记成 `resources/catalog/INDEX.md`（哪怕只是清单）
2. **领域知识入库**：把 wiki/文档里最核心的业务知识批量导入 `resources/domain/`
3. **跑通 RAG 基础闭环**：Agent 能检索 L1 + 写入 L2（v2.1 一期已规划）

### 5.3 二期治理机制建设

- **索引建设**：每个子命名空间建 INDEX.md，支持快速发现
- **随流程注入设计**：梳理 Agent 执行流程，明确每个节点的知识注入点
- **L2 记忆跑通**：偏好/事件/案例/技能的 capture + recall（v2.1 二期已规划）

### 5.4 三期 log/结构化集成

- **log 元数据登记**：把 log 流的元信息（名称/结构/所在系统/查询方式）文档化入 `resources/catalog/`
- **Agent 直连查询通道**：Agent 经授权后直连 ELK/ClickHouse 查询 log
- **跨源统一治理**：RAG 检索 + 直连查询的统一授权与审计

## 6. 大厂实践背书

本方案的关键设计均有大厂实践背书：

| 设计点 | 大厂背书 | 背书内容 |
|---|---|---|
| **知识分层（5 子命名空间）** | 微软 GraphRAG | "分层检索增强生成，构建社区层次结构"，分层按需检索而非全量灌入 |
| **log 不入 RAG，元数据登记** | 火山引擎 LAS+ByteHouse | 结构化数据与文档型 RAG 分离处理；腾讯 WeKnora 多源同步是元数据同步 |
| **RAG + Agent + 规则三层** | 腾讯 WeKnora | RAG Quick Q&A + ReAct Agent + Wiki Mode + RBAC 权限 + Langfuse 可观测性 |
| **双知识库（结构型+向量）** | 玄晶引擎 | "RAG 结构型知识库 + 向量知识库"双轮驱动，结构化与语义检索并存 |
| **知识随流程注入** | Agent-native Knowledge Context Layer | 从 RAG 到"知识上下文层"，按 Agent 流程节点注入 |
| **经验复用 + 个性化记忆** | 腾讯 WeKnora | Wiki（通用）+ Agent 推理（个性化）双层结构 |
| **规则强制注入而非检索** | 数据分析工具实践 | `.claude/rules/` + `CLAUDE.md` 把纪律作为 Agent 规则配置 |

### 6.1 不做的事（避免构想无法落地的方案）

- ❌ **不引入独立图数据库**（Neo4j/Ladybug）：v2.0 调研已评估，运维成本高，当前阶段不引入
- ❌ **不做全量 log 向量化**：成本爆炸且时序失真，大厂实践也未这么做
- ❌ **不做"知识图谱自动构建"**：微软 GraphRAG 虽支持，但企业级落地需大量调优，当前阶段不做
- ❌ **不推翻 v2.1 架构**：本方案是 v2.1 的知识管理视角补强，不改变 v2.1 的三层架构/接入通道/权限模型
