云端 Agent 记忆系统调研报告#

0. 阅读说明#

本报告面向 2000 人规模互联网公司统一部署多类 AI Agent（Claude Code / OpenClaw / Hermes 等）的记忆共享与治理需求。核心结论：以「知识库」为中心抽象、OpenViking 为底座，叠加② 层知识库授权中心与 account 级隔离，实现跨 Agent 记忆复用、部门/个人/会话三级隔离与企业级合规治理。

各章节安排：

  • 第 1-3 章：业务背景、问题、用户
  • 第 4 章：Agent 记忆系统的定义、边界与能力框架（先定义记忆系统，再区分组成层次、产品形态、核心能力与 RAG / 向量数据库底座能力）
  • 第 5 章：候选产品调研（OpenViking 详尽、Mem0/Letta 重点、Cognee 概览）+ 业务侧选型结论
  • 附件2（附件2-引用来源与竞品参考.md）：引用来源 + 竞品功能参考（Coze / 火山 VikingDB / Dify，仅用于借鉴功能设计，不参与选型）

方案设计：基于本报告 §5.6 选型结论（OpenViking），详细的业务侧方案设计、接入与记忆模型、产品框架、关键风险与建议见《云端Agent记忆系统方案设计-v2.0》。

1. 业务背景#

术语约定（按主题分组）：

① Agent 名称（公司统一部署的外部 AI Agent）

  • Hermes：外部第三方 AI Agent，公司部署使用，与 Claude Code 同类。
  • OpenClaw：外部第三方 AI Agent 平台，公司部署使用。

② 核心概念

  • 云端 Agent 记忆系统：正式术语；正文尽量避免"云 Agent / 记忆中间件"混用。
  • 知识库（Knowledge Base）：本方案的核心抽象，指组织/部门/个人拥有的一组结构化记忆集合（含偏好/技能/会话/项目上下文/SOP/政策等），物理上对应一个或多个 OpenViking 实例的区域（namespace 或整实例）。Agent 不拥有知识库，只被授权访问；一个 Agent 可同时访问多个知识库，多个 Agent 可访问同一知识库。全文"知识库"即此义，不再用缩写 KB。

③ 基础设施与服务

  • KMS（Key Management Service）：密钥管理服务，管理知识库实例的静态加密密钥与租户密钥，由企业侧部署（火山引擎 KMS 或同类产品），被 ②③ 层调用。
  • TOS：火山引擎对象存储（Tinder Object Storage），用于知识库 180 天冷存归档与原始附件存储。

公司规模与场景：互联网公司 2000 人规模，希望在云端搭建云端 Agent 平台，为员工统一部署 Claude Code / OpenClaw / Hermes 等多类 AI 智能体，未来仍会持续接入新 Agent。

当前痛点：

根因：当前部署的 Agent 既无独立记忆系统，也无 RAG 知识库，上下文只存在于单次会话的临时窗口，导致执行质量与成本双重问题。

  • 原生记忆弱 → 执行质量差：Claude Code / OpenClaw 等仅有基础会话上下文，原生记忆能力弱、跨会话即失忆，无用户偏好/项目结构/部门 SOP 的持久承载，每次都从零开始，输出频繁偏离规范、重复试错
  • 无 RAG 知识库 → 知识无法沉淀复用：部门规范、项目文档、历史决策没有统一入库与语义检索入口，Agent 无法按需调取权威资料，只能靠用户手工粘贴。RAG 知识库的价值（参考 OpenViking 官方定位"Context Database for AI Agents"）：把文档/SOP/代码统一入库 + 语义索引 + 按需检索，Agent 像查文件系统一样调取权威知识，告别手工粘贴、避免凭空臆造
  • 使用成本高：跨会话记忆缺失（同一用户明天再来还要"重讲一遍"）+ 跨 Agent 上下文不复用（Claude Code 写入的偏好，OpenClaw/Hermes 读不到）→ 重复输入、重复 token、重复人工校对
  • 数据边界模糊：部门 / 个人间无统一治理入口，安全、审计、合规无处落地

目标形态：为云端 Agent 挂载以「知识库」为中心的记忆系统——知识库按归属与用途分类（个人偏好库 / 个人技能库 / 项目上下文库 / 部门 SOP 库 / 公司政策库 / 会话归档库，详见 《方案文档》§1.3.3），Agent 不拥有知识库、只被授权访问。具体具备：

  • 按库分类承载：短期（会话内）+ 跨会话工作 + 长期稳定 + 归档冷存，分别落在对应类型的知识库
  • 隔离分两级（单实例内）：
  • account 级隔离：部门 SOP、公司政策等高敏/只读库，用独立 OpenViking account 隔离（单实例 + account 级隔离，见 《方案文档》§1.3.0）
  • namespace 级隔离：个人偏好/技能/会话归档等，account 内以 namespace 隔离
  • 迁移与授权：一个 Agent 可访问多个知识库（跨 account 联邦查询，见 《方案文档》§1.3.0）；一期跑通 L1 基础 RAG + L2 记忆基础链路（单实例 + account 级隔离·默认配置），二期补全 L1/L2 产品化 + 多 Agent 多库治理 + 跨 account 联邦（见 《方案文档》§1.3.0 分期规划）
  • 企业级治理：Agent×知识库 授权矩阵 + ACL + 审计 + 合规 + 可观测（见 《方案文档》§1.3.1 ②层）

具体的落地模式与产品选型延后到 §5 候选调研与 《方案文档》§1 业务侧方案设计，本章不预设结论。

2. 典型用户#

本报告涉及三类用户，按「使用—治理—建设」分层：

A · Agent 使用方（通过 Agent 消费记忆系统）

  • 个人用户（研发/产品/设计等员工）：使用 Claude Code / OpenClaw / Hermes 完成日常任务，需要记住个人偏好、项目状态、常用规范
  • 团队 / 业务知识库维护方（如法务部门）：负责维护本业务领域的知识库（法务知识库、研发 SOP 库等），既是使用方也是该库的内容治理方

B · 公司 / 部门（管理视角 · 监察与统一治理）

  • 部门管理者：关注本部门知识库的内容合规、访问审计、敏感数据不外泄
  • 公司治理层（安全/合规/审计）：关注 2000 人规模下的统一治理入口、数据驻留、GDPR/个保法、跨部门数据边界、成本与可观测大盘

C · 云端 Agent 团队（平台建设与运营方）

  • 平台工程：负责知识库实例池部署、Agent 接入、②层授权中心、隔离与生命周期治理
  • 安全 / 合规工程：落地 ACL、审计日志、KMS 密钥、数据驻留策略
  • 可观测工程：负责命中率、污染率、P95 延迟、LLM/Embedding token 成本等运行指标

3. 要解决的问题#

由 §1 痛点与 §5 候选调研提炼。聚焦两类核心问题，对应 《方案文档》§1 选型与方案设计要回答的设计目标：

问题一 · Agent 原生记忆弱且无 RAG（使用侧）

  • Claude Code/OpenClaw 等原生记忆弱、跨会话失忆、跨 Agent 不复用，且无 RAG 知识库、部门文档/SOP 无入库入口 → 执行质量差、使用成本高
  • 要回答：记忆怎么分层承载（短期/工作/长期/归档）、怎么自动沉淀与按需召回、怎么把部门文档/SOP 入库做语义检索供 Agent 按需调取（RAG 价值）

问题二 · 企业级多 Agent 记忆系统建设（治理与建设侧）

  • 2000 人多 Agent 共存下，如何做部门/个人/会话三级隔离、Agent×知识库 授权、跨库联邦、审计与成本治理
  • 要回答：库怎么分类与隔离（规范库/实例库）、Agent 怎么被授权访问多个库、新增 Agent 如何零改造接入、合规与可观测怎么落

以上两类问题在 《方案文档》§1 选型与方案设计中进一步拆解为 5 道业务题（Q1 跨 Agent 共享 / Q2 短期+长期闭环 / Q3 三级隔离 / Q4 企业级治理 / Q5 可观测）。

4. Agent 记忆系统：定义、边界与能力框架#

定义：Agent 记忆系统是位于 Agent Runtime（Agent 运行时，即 Agent 执行对话/工具调用的运行环境）与知识/存储底座之间的上下文管理层，由「记忆分层 + 写入判断 + 召回 + 生命周期治理 + 跨 Agent 共享 + 治理审计」几个部分组成，把会话中产生的事实、偏好、任务状态与可共享知识，沉淀为可写入、可检索、可治理、可审计的记忆，按用户/部门/Agent/会话边界安全召回。

组成部分简介：

  • 记忆分层：短期上下文 / 工作记忆 / 长期记忆 / 归档记忆四层（见 §4.1）
  • 写入判断：决定什么该被记住、由谁写入、记到哪一层
  • 召回：按任务按需检索并注入上下文
  • 生命周期治理：何时更新、合并、归档或删除
  • 跨 Agent 共享：多 Agent 安全复用同一份记忆/知识
  • 治理与审计：ACL、来源追溯、审计日志

与 RAG / 向量数据库的边界：RAG / 向量数据库主要解决"从资料中找相关内容"；Agent 记忆系统还要解决什么应该被记住、由谁写入、谁可以使用、何时更新或删除、如何跨 Agent 共享、如何避免记忆污染。本方案的 RAG/向量底座能力见 §4.5。

4.1 记忆系统的组成层次#

层次 生命周期 典型内容
短期上下文 单次会话内 当前对话轮次、临时变量、工具调用中间结果
工作记忆 跨会话、任务级 未完成任务状态、过程草稿、暂存偏好
长期记忆 跨用户生命周期 稳定事实、偏好、部门 SOP、项目知识
归档记忆 冷数据 时效过期但需保留的历史条目

4.2 参考实践#

参考对象 一手事实 可迁移原则
Claude Code Memory 官方 4 层：Enterprise policy（组织级只读）+ Project memory（./CLAUDE.md）+ User memory（~/.claude/CLAUDE.md）+ Project memory local（./CLAUDE.local.md，已 Deprecated 建议改用 imports）；提供 /memory 编辑入口 企业场景需要组织级只读 + 项目级 + 用户级分层承载（本方案对应 《方案文档》§1.3.3 六类知识库：公司政策库=组织级只读、部门SOP库=项目级、个人偏好/技能库=用户级）
Codex / AGENTS.md 将项目规则、测试命令、代码风格、安全注意事项写成 Agent 可读文档，并支持目录级覆盖 需要项目级、目录级、团队级记忆类型
MemGPT / Letta 强调 Core / Archival / Conversation 层次与外部工具集，跨会话记忆持续复用 需要短期、工作、长期记忆的组成层次

4.3 记忆系统的产品形态#

形态 代表 边界
Agent 内置长期记忆 Claude Code、Coze LTM 平台内部闭环；Coze LTM 是 Coze 记忆资源之一（Coze 完整记忆分层见附件2 B.1）
平台型知识库 / 应用记忆 Dify、Coze 应用内可用，不天然跨 Agent
记忆中间件 Mem0、Letta、OpenViking 独立治理 schema/权限/生命周期
RAG / 向量数据库底座 VikingDB、Qdrant、Milvus 靠切片、向量索引、语义召回解决检索，不直接解决记忆写入判断和治理

4.4 Agent 记忆系统核心能力#

本节给出 Agent 记忆系统的 8 类核心能力框架（4.4.1 作用域与隔离 / 4.4.2 记忆写入 / 4.4.3 记忆类型 / 4.4.4 记忆召回 / 4.4.5 生命周期 / 4.4.6 跨 Agent 共享 / 4.4.7 治理与安全 / 4.4.8 可观测性），按「能力类 → 必要能力 → 能力说明」三层展开。这 8 类能力对应完整记忆闭环：写入前先判断作用域和权限，写入时记录来源和类型，运行时按任务召回，长期通过生命周期治理保持准确，并通过可观测指标发现污染、延迟和成本问题。此框架同时作为 §5 候选调研的评估维度。

4.4.1 作用域与隔离#

功能 子能力 能力说明
隔离层级 用户级隔离 每个自然人独立命名空间，防止跨人污染
隔离层级 部门/团队级隔离 按组织层级隔离记忆域，支持部门间共享或独占
隔离层级 项目/资源级隔离 以项目、知识库或资源为边界，跨用户共享同一份项目记忆
隔离层级 Agent 级隔离 不同 Agent（Claude Code / Hermes / OpenClaw 等）可持有独立或共享记忆
隔离层级 会话级隔离 单次会话/任务的短期上下文与长期记忆解耦
权限模型 命名空间与 ID 体系 user_id / agent_id / run_id / app_id / workspace 等多级 ID 组合
权限模型 访问控制 ACL Read / Write / Delete / Share 细粒度权限（能力上限，如 Cognee dataset 粒度 4 类 ACL）；本方案据 Agent 意图驱动特性降为布尔粒度（允许/不允许），详见 《方案文档》§1.3.3
权限模型 多租户与数据驻留 租户级密钥、region 隔离、私有化部署可控

4.4.2 记忆写入#

功能 子能力 能力说明
写入方式 显式写入 Agent 或用户主动通过 API/工具调用把事实写入长期记忆
写入方式 自动抽取 LLM 从对话/文档中被动抽取事实、偏好、关系并入库
写入方式 批量导入 从文件、外部知识库、历史会话批量导入
写入治理 来源记录 每条记忆保留来源 URL / 会话 ID / 用户 / 时间戳
写入治理 写入确认与撤回 支持写入前确认、写入后撤回，避免误写污染
写入治理 幂等与去重 同一事实多次写入不产生重复条目

4.4.3 记忆类型#

功能 子能力 能力说明
结构化记忆 事实型 人名、时间、数值、状态等原子事实
结构化记忆 偏好型 用户偏好、风格、口味、习惯
结构化记忆 实体-关系型 人-项目-文档等图状关联，支持图检索
半结构化记忆 过程型 任务步骤、流程状态、Agent 执行轨迹
半结构化记忆 任务状态 待办、进行中、已完成的任务上下文
非结构化记忆 文档型 长文档、笔记、纪要、代码片段
非结构化记忆 多模态 图像、音频、视频及其描述文本

4.4.4 记忆召回#

功能 子能力 能力说明
召回维度 按任务/查询召回 基于当前对话或工具调用意图检索相关记忆
召回维度 按用户/主体召回 按 user_id / agent_id 限定召回范围
召回维度 按时间召回 支持时间窗、最近 N 条、时间衰减加权
召回维度 按来源/重要性召回 按来源可信度、访问频次、置信度加权
召回控制 Top-K 与阈值 控制返回条数与最低相关度门槛
召回控制 多信号融合 语义 + 关键词 + 元数据 + 图 多路合并排序
召回控制 上下文注入策略 决定召回结果如何拼接进 Agent Prompt

4.4.5 生命周期#

功能 子能力 能力说明
去重与合并 语义去重 同义/近似事实归并成单条记忆
去重与合并 冲突解决 新旧事实冲突时按时间/来源/置信度裁决
更新与版本 记忆更新 支持字段级或整条更新，保留历史版本
更新与版本 版本化与回溯 记忆变更可审计、可回滚
遗忘与归档 时间衰减 长期未使用记忆分数衰减、退出热召回
遗忘与归档 自动归档 冷记忆迁移到归档层或对象存储
遗忘与归档 删除与遗忘 显式删除、级联删除（连同引用与摘要一并清理，即"被引用清理"）、GDPR 遗忘权支持

4.4.6 跨 Agent 共享#

功能 子能力 能力说明
接入形态 API / HTTP 接口 语言无关，任何 Agent 可通过 HTTP 接入
接入形态 多语言 SDK Python / TypeScript / Go 等主流语言 SDK
接入形态 MCP 协议 通过 Model Context Protocol 让新 Agent 零改造接入
共享语义 统一 schema 事实/偏好/文档等类型有跨 Agent 一致定义
共享语义 共享/私有边界 明确哪些记忆全 Agent 可读、哪些仅本 Agent 可读
共享语义 冲突协调 多 Agent 同时写入时的锁/合并/顺序策略

5.1 OpenViking（详尽）#

  • 定位：火山引擎开源记忆中间件；文件系统式抽象；AGPL-3.0
  • 独特优势：4 款中唯一"文件系统式抽象 + 内置 doubao-seed-rerank + 原生 Prometheus + 火山生态亲和"；分级目录直接映射公司/部门/个人四级
  • 独特短板：部门级 ACL / 合规资质需自建；SDK 覆盖 Python/Go/TS（TS 为社区/实验性支持）；实体-关系记忆弱

详细能力映射（§4.4 × §4.5）、§3 5 道业务题作答、行内证据 URL 见 候选调研详情 §1

5.2 Mem0（重点）#

  • 定位：开源个人化记忆中间件；LLM 自动抽取事实/偏好；4 级 ID 隔离
  • 独特优势：4 款中唯一同时公开 SOC 2 + HIPAA + BYOK + Air-gapped；2026-04 v3 新算法给出 LoCoMo 91.6（+20）、LongMemEval 94.8（+27）、BEAM 1M 64.1、BEAM 10M 48.6（单次调用，非 agentic 循环）；引入 entity linking + 多信号（semantic + BM25 + entity）并行融合 + 时序推理
  • 独特短板：文档型记忆仍弱；开源版无内置观测面板；部门级隔离靠元数据过滤自建

详情见 候选调研详情 §2；基准来源见 GitHub mem0ai/mem0 README "New Memory Algorithm (April 2026)" 与 mem0.ai/research

5.3 Letta（原 MemGPT）（重点）#

  • 定位：分层记忆 Agent 框架；Memory Blocks（Core）+ Archival + Conversation 三层 + 外部工具集；唯一原生多 Agent 共享 memory blocks
  • 独特优势：4 款中唯一原生"多 Agent 共享 memory blocks + read-only 权限"；分层记忆最完整；OTel + ClickHouse 观测栈最完整
  • 独特短板：显式 LLM 调用模式，2000 人高频场景成本高；无独立神经 Rerank；archival passage ≤300 tokens

详情见 候选调研详情 §3

5.4 Cognee（概览）#

  • 定位：认知图 + 向量融合；实体-关系图为核心；Apache-2.0
  • 独特优势：4 款中唯一内置"实体-关系图 + 向量混合"；唯一 Read/Write/Delete/Share 4 类 ACL（dataset 粒度）；数据处理管线最丰富（Docling / OCR / Parser）
  • 独特短板：多 Agent 成熟度弱；图数据库运维成本高；分层记忆抽象弱
  • 重要变更（2026-05）：v1.0.4 主图后端由 Kuzu 迁移到 Ladybug（Kuzu 目录保留兼容）；主 API 已改为 remember / recall / forget / improve（原 add / cognify / search 语义收敛）

详情见 候选调研详情 §4

判断方法：4 款开源候选（OpenViking / Mem0 / Letta / Cognee）平等参与主选型，从能力、知识库、范式与体验、一体化、落地约束五个维度综合对比（含与 Cognee 的逐项对比），不局限于单一维度或单一产品视角。

能力维度决定记忆系统是否可用：本方案为多知识库架构（个人/部门/公司多库分担负载，见 《方案文档》§1.3.1 ③层（单实例多 account）），2000 人高频场景下各实例按隔离粒度承载相应负载；能否把长对话自动压缩为按需加载的分层摘要，决定 token 成本与召回质量。OpenViking 是 4 款中唯一具备"transcript→commit→archive→L0/L1/L2 完整会话压缩管线 + 三层信息结构 + Memory/Resources/Skills 三类上下文统一"三合一能力的产品；Cognee 以知识图谱为核心（remember→图谱），无分层压缩归档管线，更适合作为关系推理增强层而非独立承担会话记忆。

一体化维度是本场景刚需：本报告要建"记忆+知识库"混合系统（部门 SOP + 项目上下文 + 个人偏好），OpenViking 官方定位即"Context Database for AI Agents"（附件3 第 11 行），以统一 viking:// 文件系统同时承载会话记忆与文档资源，是 4 款中范式统一性最完整的方案；Cognee 的对话与文档均归一为知识图谱，非"记忆+知识库"双范式。

落地约束决定适用场景：OpenViking 的 AGPL-3.0 传染性许可证对闭源商用产品有法律风险，且需自建向量库、生态仅约 6 个月（2026-01 开源）。本报告场景为公司内部云端 Agent 平台、自托管内网部署，AGPL-3.0 自托管不构成阻断风险，故选型成立；若未来出现闭源商用外发需求，需重估 AGPL-3.0 许可合规。

落选理由（对齐五维度）：

  • Mem0：能力维度——无 transcript 压缩归档、三层结构缺、三类上下文以记忆为主；知识库维度——文档型承载弱；范式维度——条目式无路径可视化。以"个人化偏好"为核心叙事，与本报告"部门 SOP / 项目上下文"侧重错位。
  • Letta：能力维度——会话压缩强但显式 LLM 调用模式在 2000 人高频场景成本高；archival passage ≤300 tokens 限制大文档承载；三类上下文统一弱（无资源/技能抽象）。
  • Cognee：能力维度——无分层压缩归档、扁平图谱无 L0/L1/L2；知识库维度——文档→图谱丢失原文档结构；一体化维度——以图谱为核心，非"记忆+知识库"双范式。实体-关系图能力可作为"能力借鉴"而非主栈（图后端 Ladybug/Neo4j 运维成本高）。

综上：OpenViking 在能力、知识库、范式与体验、一体化四维度综合最优，胜出为主选型，是 4 款中唯一具备"会话压缩管线 + 三层信息结构 + 三类上下文统一 + 记忆与知识库一体化"的方案；Mem0 / Letta / Cognee 综合判断落选，保留作能力参考。落地约束（AGPL-3.0 / 自建向量库 / 生态早期）决定 OpenViking 适用于内网 / POC / 非闭源商用场景，与本报告公司内部自托管场景匹配，故选型成立。

5.6.3 选型结论与竞品不入选说明#

选型结论：本报告选定 OpenViking 作为云端 Agent 记忆系统的主选型。下文 《方案文档》§1 起围绕此选型展开业务场景覆盖与方案架构设计。

竞品功能参考的三款商业产品仅用于借鉴功能设计，不进入选型池，原因：

  1. 不是开源候选：本轮候选池的定位是"未来可能落地的开源框架"，商业闭源平台与本目标不匹配。
  2. 平台边界定位不同：Coze 是 Bot 平台，Dify 是应用开发平台，VikingDB 是向量底座，均与本报告的"Agent 记忆系统"目标不在同一抽象层。
  3. 能力覆盖 ≤ 开源候选：三者在 §4.4 的 作用域与隔离（部门/ACL） / 生命周期 / 跨 Agent 共享 等能力上比开源候选弱。详细一手事实见附件2。
