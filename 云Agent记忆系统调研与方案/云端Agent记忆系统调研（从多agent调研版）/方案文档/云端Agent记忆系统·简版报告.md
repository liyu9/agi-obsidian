## 1. 业务背景与问题

> 来源：[调研报告 §1-3](云端Agent记忆系统调研报告-v2.0.md)

**公司场景**：互联网公司 2000 人规模，云端统一部署 Claude Code / OpenClaw / Hermes 等多类 AI Agent，未来持续接入新 Agent。

**四大痛点**（根因：当前部署的 Agent 既无独立记忆系统，也无 RAG 知识库）：

1. **原生记忆弱 → 执行质量差**：跨会话即失忆，无偏好/SOP 持久承载，每次从零开始
2. **无 RAG 知识库 → 知识无法沉淀复用**：部门文档/SOP 无入库入口，Agent 只能靠手工粘贴
3. **使用成本高**：跨会话重复输入、跨 Agent 上下文不复用 → 重复 token + 重复人工校对
4. **数据边界模糊**：部门/个人间无统一治理入口，安全审计合规无处落地

**两类核心问题**：

- **问题一（使用侧）**：Agent 原生记忆弱且无 RAG → 记忆怎么分层承载、怎么自动沉淀与按需召回、怎么把文档/SOP 入库做语义检索
- **问题二（治理侧）**：2000 人多 Agent 共存 → 怎么做三级隔离、Agent×知识库授权、跨库联邦、审计与成本治理

**五道业务题**（方案须逐一回答）：Q1 跨 Agent 共享 · Q2 短期+长期闭环 · Q3 三级隔离 · Q4 企业级治理 · Q5 可观测

**目标形态**：为云端 Agent 挂载以「知识库」为中心的记忆系统——知识库按归属分类（个人偏好/技能、项目上下文、部门 SOP、公司政策、会话归档），Agent 不拥有知识库、只被授权访问。

## 2. 选型结论

> 来源：[调研报告 §5.6](云端Agent记忆系统调研报告-v2.0.md)

**候选池**：4 款开源候选（OpenViking / Mem0 / Letta / Cognee）平等参与主选型；Coze、VikingDB、Dify 为商业闭源，仅作功能参考不入选。

**选定：OpenViking**

> OpenViking 在能力、知识库、范式与体验、一体化四维度综合最优，是 4 款中唯一具备"会话压缩管线 + 三层信息结构 + 三类上下文统一 + 记忆与知识库一体化"的方案。落地约束（AGPL-3.0 / 自建向量库 / 生态早期）适用于公司内部自托管内网部署场景，选型成立。

> **额外注意**：OpenViking 当前的开源许可为 **AGPL-3.0，没有完全开源**（部分配套能力依赖官方私有实现）。作为公司内部自托管内网部署使用、不对外提供服务，AGPL-3.0 不构成阻断风险；若未来出现闭源商用外发或衍生作品交付第三方等场景，需重评许可合规性，详见调研报告 §5.6.1 与方案设计 §1.4 风险第 5 条。

**落选理由（一句话）**：

- **Mem0**：无 transcript 压缩归档、文档型承载弱、条目式无路径可视化，与"部门 SOP / 项目上下文"侧重错位
- **Letta**：显式 LLM 调用模式 2000 人高频场景成本高，archival ≤300 tokens 限制大文档
- **Cognee**：以知识图谱为核心，无分层压缩归档，非"记忆+知识库"双范式，更适合关系推理增强层

## 3. 方案概览

> 来源：[方案设计 §1.0](云端Agent记忆系统方案设计-v2.0.md)

**方案价值主张**：以「知识库」为中心抽象，OpenViking 为底座，叠加 ② 层知识库授权中心与 account 级隔离，实现跨 Agent 记忆复用、部门/个人/会话三级隔离与企业级合规治理。

**关键数字速览**：2 期演进（L1 基础 RAG + L2 记忆基础链路 → L1/L2 产品化 + 多 Agent 治理）· 3 层架构 · 1 个 OV 实例 · 3 接入通道 · 4 数据流路径 · 6 类知识库 · 7 类记忆类型 · 4 类企业侧扩展需求。

**6 个核心概念**：

| 概念 | 含义 |
|---|---|
| 官方原生 | OpenViking 开源产品自带能力（4 命名空间 / 7 Hook / 9 MCP / L0-L2 分层 / RAGFS / 多租户 account-user 模型），开箱即用 |
| 企业侧扩展 | 官方不提供、本方案自建补齐的能力（②层授权中心 / account 级隔离 / 跨库联邦 / 180 天冷存 / KMS 审计）|
| ② 层知识库授权中心 | 核心扩展组件，做 Agent×知识库 授权矩阵 + 身份鉴权 + 路由 + 审计，Agent 不直连知识库 |
| account 级隔离 | 部门/公司等高敏库用独立 OV account 部署，单实例内实现部门/公司/个人三级隔离 |
| 跨知识库联邦查询 | ② 层并行 fan-out 多 account 检索再合并排序，让一次请求触达多个库 |
| 知识库（KB） | 独立于 Agent 存在的记忆载体，按归属/用途分类，Agent 被授权访问、不拥有 |

| # | 业务场景（对应业务题） | 一期 | 二期 | 分期价值说明 |
|---|---|---|---|---|
| **基础能力** | | | | |
| S0 | L1 基础 RAG 双向闭环——Agent 写入/检索 L1（Q2） | ✅ | ✅ | 一期跑通 Agent↔L1 双向（写入+检索），RAG 可视化文件列表 |

| S2 | 个人偏好/技能持久化——记住用户习惯、习得操作（Q2） | ✅ | ✅ | 一期 Hooks 自动 capture + Extraction 落地；二期产品化（可配置） |
| S3 | 会话归档与冷存——长对话压缩归档、180 天迁 TOS（Q2） | ✅ | ✅ | 一期 commit→archive→TOS 链路完整；二期产品化（阈值/策略可配置） |
| **治理能力** | | | | |
| S4 | 接入鉴权与审计——谁访问了什么（Q4 治理） | ⚠️ 部分 | ✅ | 一期②层简化版有鉴权+审计，**无授权矩阵**；二期补全 RBAC+ACL |
| S5 | 多 Agent 并存各自隔离——CC/OpenClaw 互不串数据（Q3） | ✅ 天然 | ✅ | 一期靠 account 级隔离**硬分隔**；二期升级为策略层隔离 |
| **多 Agent 协作（二期专属）** | | | | |
| S6 | 一 Agent 访问多库——一次任务同时调取个人库+部门库+公司库（Q1/Q2） | ✗ | ✅ | 一期 1 Agent 只绑 1 account；二期补跨 account 联邦 fan-out |

> **一期边界**：S0（L1 基础 RAG）+ S1-S3（L2 记忆基础链路·默认配置）+ S4 部分 + S5（天然）共 6 个场景跑通，验证 Agent↔L1+L2 双向闭环可行性。

> **二期补全**：L1/L2 产品化（各环节/规则/时机可配置）+ S6-S8 多 Agent 协作 + S4 授权矩阵 + S5 策略层升级，面向 2000 人多 Agent 公司真实治理需求。

## 5. 业务架构：知识分层

> 来源：[方案设计 §1.2.1 + §1.2.3](云端Agent记忆系统方案设计-v2.0.md)

本方案将知识分为两层：**L1 向量知识库**（让 AI 懂企业资料）与 **L2 记忆系统**（让 AI 认得用户），共用同一 OpenViking 引擎，靠 `viking://` 命名空间区分。

**L1 vs L2 对比**：

| 对比点 | L1 向量知识库 | L2 记忆系统 |
|---|---|---|
| 核心问题 | AI 懂不懂企业资料 | AI 认不认得用户 |
| 数据来源 | 企业传统知识库(A) + Agent 中(B1/B2/B3) | Agent(B4) |
| 数据性质 | 静态文档型 | 动态事件/画像型 |
| 抽取方式 | 切片(按文档结构) | LLM 5类分类 + WM v2 压缩 |
| 命名空间 | `viking://resources/` | `viking://user/` + `session/` |
| 召回方式 | 仅 MCP 显式检索(路径4) | 自动召回(路径3) + MCP 显式检索(路径4) |

> **L2 与 L1 的关系**：L2 不读 L1 的业务文档（防跨命名空间泄露），但复用 L1 的 RAG 检索基础设施（Embedding + flat_hybrid + rerank）。一句话：**L2 不读 L1 内容，但复用 L1 的 RAG 能力**。

## 6. 系统架构

> 来源：[方案设计 §1.3](云端Agent记忆系统方案设计-v2.0.md)

**设计理念：单实例 + account 级隔离 + 一期先联通、二期再补网关**

无论一期、二期，均为**单 OpenViking 实例**——通过 account 级隔离实现部门/公司/个人三级知识库隔离，不采用多实例物理隔离。**一期优先满足 Agent 与知识库的联通性**（Hooks/MCP/SDK 三通道任选一条直连 OpenViking 实例，先打通业务联通链路），②层知识库授权中心（协议适配 + 鉴权 + 路由 + 审计 + 观测）的网关能力在**后续迭代中按需补齐**，二期补完整版（RBAC+ACL + 联邦 + account 路由）。Agent 侧接入契约不变、二期零改造。

**分期规划**：

| 维度 | 一期（公司云 Agent 平台现状） | 二期（目标态） |
|---|---|---|
| 实例 | 单 OpenViking 实例（多 Agent 共用） | 单 OpenViking 实例（不迁移，仅扩展 account） |
| 接入方式 | **先联通后补网关**（Agent 经 Hooks/MCP/SDK 直连 OV）→ 按需补简化网关 | Agent → ②层完整网关 → OV（零改造） |
| 授权矩阵 | 无（直连 + 单 account 天然隔离） | 完整 Agent×库 矩阵（RBAC+ACL） |
| account | 单 account（部门级） | 多 account（部门/公司/个人）+ 路由 + 跨 account 联邦 fan-out |
| ②层 | 一期初版：直连（无网关）；按需补简化版网关（协议适配 + 鉴权 + 1-to-1 路由 + 审计 + 观测） | 完整：协议适配 + 矩阵 + 鉴权 + 路由 + 联邦 + 审计 + 观测 |

```
│  │ 协议适配    │ Agent 身份   │ 路由         │ 观测埋点     │    │

│  │ 消息归一    │ mTLS / JWT   │ 本 Agent 绑  │ +token 成本  │    │
│  │ → OV HTTP   │              │ 定的实例     │              │    │
│  └─────────────┴──────────────┴─────────────┴──────────────┘    │
│  + 审计日志                                                      │
│  ✗ 授权矩阵（account 级天然隔离，无需求）                       │
│  ✗ 联邦查询 / account 级路由（单 account 无此需求）             │
└─────────────────────────────┬───────────────────────────────────┘
                              │ 路由到本 Agent 绑定的 account
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  ③ 单 OpenViking 实例（account 级隔离 · L1 基础 RAG + L2 记忆）  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ viking://user/{uid}/memories/ + skills/                 │   │
│  │ viking://session/{sid}/archive/（会话归档）               │   │
│  │ viking://resources/（L1 向量知识库）                      │   │
│  ├──────────────────────────────────────────────────────────┤   │
│  │ 实例内部：openviking-server + web-studio + ov CLI        │   │
│  └──────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  横切支撑层（非数据流下游 · 不参与层级编号）                     │
│   观测：Prometheus + Grafana    密钥：KMS                       │
│   存储：TOS（冷存）             审计：audit log                  │
│   模型：LLM + Embedding + VLM + rerank                          │
└─────────────────────────────────────────────────────────────────┘
```

> **设计意图补充（一期先联通、二期再补网关）**：上述一期架构图描绘的是"②层 + ③层"的**目标态**（简化版网关 + 单实例）。实际落地时，一期优先满足"先联通"——即 **Agent 经 Hooks/MCP/SDK 三通道任选一条直连 OpenViking 实例**，安全性靠 OpenViking 原生 mTLS/JWT、ROOT/ADMIN/USER 三角色、命名空间隔离保证；②层知识库授权中心（协议适配 + 鉴权 + 路由 + 审计 + 观测）的网关能力在**后续迭代中按需补齐**。
>
> **演进路径**（3 步）：
> 1. **一期初版**（联通态）：Agent 直连 OV 实例；
> 2. **一期补强**（按需）：多 Agent/跨 account/统一审计需求出现时，补 ②层简化版网关；
> 3. **二期**（目标态）：②层升级为完整版（RBAC+ACL + 联邦 + account 路由）。
>
> **好处**：优先验证业务 · 降低初期成本 · 平滑迁移（Agent 侧协议不变）。**代价**：一期直连阶段缺乏统一审计与 token 成本归因，需人工/单实例审计补位。

### 6.2 二期系统架构图（单实例 · 多 account · 完整治理态）

二期②层补全：知识库授权矩阵（RBAC+ACL）+ account 级路由 + 跨 account 联邦 fan-out；③层扩展为多 account（个人/部门/公司/只读政策库）。Agent 侧接入契约不变，零改造演进。

> 完整二期系统架构图（含授权矩阵示例、多 account 命名空间、实例内部六层架构）见 [方案设计 §1.3.1](云端Agent记忆系统方案设计-v2.0.md)。

**三层职责**：

| 层 | 承担职责 | 归属 |
|---|---|---|
| ① Agent 应用层 | 消费记忆能力，产生对话/任务/事实；Agent 无库归属，被授权访问 | 官方接入对象 |
| ② 知识库授权中心 | 协议适配 + 身份鉴权 + 知识库授权矩阵 + 按授权路由 + 跨 account 联邦 + 审计 + 观测 | 企业侧扩展 |
| ③ 单 OpenViking 实例 | 个人/部门/公司多 account 隔离 + openviking-server + web-studio + ov CLI | 官方 |
| 横切支撑层 | 观测/密钥/存储/审计/模型（旁路依赖，非数据流下游） | 官方 + 企业侧 |

## 7. 接入与记忆模型（精简）

> 来源：[方案设计 §2](云端Agent记忆系统方案设计-v2.0.md)

**4 条关键数据流路径**（接入通道 × 方向）：

| | 写入 | 召回 |
|---|---|---|
| **Hooks（自动触发）** | 路径 1 · Stop Hook 自动 Capture | 路径 3 · UserPromptSubmit Hook 自动 Recall |
| **MCP（模型按需）** | 路径 2 · MCP store 显式写入 | 路径 4 · MCP search 跨 account 联邦检索 |

**3 接入通道**：

| 通道 | 驱动方式 | 适用 Agent |
|---|---|---|
| Hooks | 生命周期自动触发 | Claude Code（支持 Hooks 的框架） |
| MCP | 模型按需调用 | OpenClaw / Hermes / Cursor / Trae（MCP 兼容） |
| SDK/HTTP | 通用编程接入 | LangChain / 二期自建 Agent（无 MCP/Hook 能力时） |

**记忆模型一句话概括**：

- **记忆类型**：7 类（preferences 偏好 / events 事件 / cases 案例 / memories 事实 / skills 技能 / archive 归档 / resources 资源），由 LLM 按 5 类分类规则抽取
- **记入**：Hooks auto-capture（Stop Hook）+ Memory Extraction（LLM 5 类分类）+ Embedding 向量化 → 写入对应命名空间；会话经 commit（≥阈值）→ archive → 180 天迁 TOS
- **召回**：自动召回（路径 3，Hooks 触发，只查个人 account）+ MCP 显式检索（路径 4，可跨 account 联邦）；两阶段检索 flat_hybrid（dense+sparse+元数据）+ rerank

> 记入/存储/召回模型的字段级细节见 [方案设计 §2.2-2.5](云端Agent记忆系统方案设计-v2.0.md)。

## 9. 关键风险与路线图

> 来源：[方案设计 §1.4 + §5](云端Agent记忆系统方案设计-v2.0.md)

**方案级风险（5 条）**：

1. **单产品绑定** — 若 OpenViking 项目停滞或不满足新需求，迁移成本高。**缓解**：PoC 阶段充分验证核心能力 + 5 道业务题覆盖度；不预留 Adapter 抽象层（避免过度设计）
2. **企业合规责任由部署侧承担** — OV 不提供第三方 SaaS 合规证书；自托管部署数据不出企业，合规由公司内部审计/等保/数据驻留策略保证（私有化部署常规做法，非产品缺陷）
3. **被动抽取质量需持续调优** — 官方抽取管线依赖 LLM 与 prompt。**缓解**：建立 golden set 基线定期回归；利用 web-studio 检索轨迹可视化定位偏差
4. **多知识库联邦查询延迟** — 跨库召回需 fan-out 多 account 并行检索再合并。**缓解**：并行 fan-out（最多 5 account）+ 8000ms 超时 + 高频库本地缓存 + 自动召回只查单 account
5. **OpenViking AGPL-3.0 未完全开源** — OpenViking 主项目以 AGPL-3.0 协议发布，**并非完全开源**（部分配套能力依赖官方私有实现），且 AGPL-3.0 具有传染性。**缓解**：作为公司内部自托管内网部署、不对外提供服务、不向外部分发衍生作品，AGPL-3.0 不构成阻断风险。**重评触发条件**：出现闭源商用外发需求 / 二次开发后向外部交付 / 部分核心能力长期停留在私有实现（任一发生即重开选型）。**关联**：调研报告 §5.6.1、方案设计 §1.4 风险第 5 条

**落地路线图**：

| 阶段 | 周期 | 交付物 | 验收 | 依赖 |
|---|---|---|---|---|
| PoC | 2 周 | 个人偏好命中率 + 部门 SOP 召回质量验证 | 偏好 7 天命中、SOP 召回相关 | OV 实例 + CC Hooks |
| 一期 | L1基础RAG+L2记忆基础链路 | ②层简化网关 + L1基础RAG + L2记忆基础链路 + 文件列表可视化 + 企业文档导入 | 1.1.2 验收清单 8 项 | PoC 通过 |
| 二期 | L1/L2产品化+多Agent治理 | 授权矩阵 + account级联邦 + L1产品化 + L2记忆产品化 + 管理控制台 | 1.1.3 验收清单 5 项 | 一期上线 + 2000 人场景 |
