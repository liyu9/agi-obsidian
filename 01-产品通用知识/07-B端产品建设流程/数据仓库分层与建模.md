## 一、数据仓库概述

### 1.1 什么是数据仓库

**定义**：数据仓库（Data Warehouse）是一个面向主题的、集成的、非易失的、随时间变化的数据集合，用于支持管理决策过程。

**核心特征**：
| 特征 | 说明 |
|------|------|
| 面向主题 | 按业务主题组织数据（如用户、商品、订单） |
| 集成 | 整合多个数据源，统一数据标准 |
| 非易失 | 数据一旦进入仓库，一般不更新 |
| 随时间变化 | 记录历史数据，支持趋势分析 |

### 1.2 数据仓库 vs 业务数据库

| 维度 | 业务数据库（OLTP） | 数据仓库（OLAP） |
|------|-------------------|-----------------|
| 目的 | 处理日常业务操作 | 支持决策分析 |
| 设计 | 面向业务过程 | 面向分析主题 |
| 数据 | 当前最新数据 | 历史数据 |
| 更新 | 频繁增删改 | 批量导入，一般不更新 |
| 查询 | 简单、高并发 | 复杂、深度分析 |

## 二、数据分层模型

### 2.1 分层原则

以 **"数据加工深度"** 和 **"服务目标"** 为核心轴，每层承担单一明确职责：

- **上游层（ODS/DWD）**：聚焦"数据整合与清洗"，服务下游分析
- **下游层（DWS/ADS）**：聚焦"数据聚合与应用"，直接支撑业务

### 2.2 四层架构

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        数据仓库分层架构                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ADS层（应用数据层）    │ 直接支撑业务应用                       │   │
│  │  Application Data Store│ 报表、BI、数据服务                      │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                    ▲                                    │
│                                    │                                    │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  DWS层（汇总数据层）    │ 主题化数据聚合                         │   │
│  │  Data Warehouse Summary│ 用户汇总、商品汇总、时间汇总            │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                    ▲                                    │
│                                    │                                    │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  DWD层（明细数据层）    │ 原子级数据清洗                         │   │
│  │  Data Warehouse Detail │ 业务宽表、维度退化、去重去噪            │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                    ▲                                    │
│                                    │                                    │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ODS层（操作数据层）    │ 原始数据保留                           │   │
│  │  Operational Data Store│ 与源系统一致、保留历史                  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  ▲ 向上游数据溯源    ▼ 向下游提供数据服务                              │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.3 各层详细定义

#### ODS层：原始数据保留区

**核心职责**：
- 保持与源系统数据完全一致（结构+内容）
- 提供历史数据存储能力
- 作为数据故障恢复的基准点

**边界红线**：
- ❌ 不删除源数据字段
- ❌ 不做业务逻辑计算（如用户等级判定）

**处理方式**：
- 仅做必要技术处理（编码转换、字段类型调整）
- 不进行业务逻辑加工
- 增加数据抽取时间、来源系统等元数据

**命名规范**：`ods_源系统_表名`

#### DWD层：明细数据层

**核心职责**：
- 业务清洗（补全空值、修正异常值）
- 维度退化（如将"商品分类ID"转为"分类名称"）
- 表结构重构（宽表化）

**边界红线**：
- ❌ 不做汇总计算（如"每日下单总量"）
- ❌ 不冗余非关联字段

**命名规范**：`dwd_主题_业务过程_表名`

#### DWS层：汇总数据层

**核心职责**：
- 按业务主题汇总（如按"用户""商品""时间"聚合）
- 计算通用指标（如"用户月消费额""商品周销量"）

**边界红线**：
- ❌ 不做业务场景化计算（如"双11活动转化率"）
- ❌ 汇总粒度不低于"日级"

**命名规范**：`dws_主题_时间粒度_表名`

#### ADS层：应用数据层

**核心职责**：
- 场景化计算（活动指标、报表指标）
- 数据格式化（适配BI工具、API接口）

**边界红线**：
- ❌ 不存储原始/明细数据
- ❌ 计算逻辑不重复（复用DWS层指标）

**命名规范**：`ads_应用场景_表名`

### 2.4 边界判断示例

| 需求 | 归属层级 | 判断依据 |
|------|----------|----------|
| 获取用户每次下单的商品名称 | DWD | 原子明细 + 维度退化，非汇总/场景化 |
| 统计每个商品每月的销售总量 | DWS | 主题汇总 + 通用指标，非场景化 |
| 计算618活动期间每个商品的优惠券核销率 | ADS | 场景化计算 + 特定时间范围 |

## 三、维度建模

### 3.1 核心概念

**事实表**：记录业务行为明细，如订单事实表、用户行为事实表

**维度表**：记录描述性信息，如用户维度表、商品维度表、时间维度表

### 3.2 星型模型

**结构**：一个中心事实表，直接连接多个维度表

```
        ┌─────────┐
        │ 时间维度 │
        └────┬────┘
             │
    ┌────────┼────────┐
    │        │        │
┌───┴───┐┌──┴──┐┌───┴───┐
│用户维度││商品维度││渠道维度│
└───────┘└─────┘└───────┘
    │        │        │
    └────────┼────────┘
             │
       ┌─────┴─────┐
       │  事实表   │
       │ (订单/交易)│
       └───────────┘
```

**特点**：
- 非规范化设计
- 查询性能高（少关联）
- 结构简单易理解

**适用场景**：互联网公司、敏捷交付、快速分析

### 3.3 雪花模型

**结构**：对星型模型的维度表进一步层次化

```
           ┌─────────┐
           │ 时间维度 │
           └────┬────┘
                │
    ┌───────────┼───────────┐
    │           │           │
┌───┴───┐   ┌───┴───┐   ┌───┴───┐
│地区维度│   │商品维度│   │渠道维度│
└───┬───┘   └───┬───┘   └───────┘
    │       ┌────┴────┐
    │   ┌───┴───┐┌───┴───┐
    │   │品类维度││品牌维度│
    │   └───────┘└───────┘
    │       │       │
    └───────┼───────┘
            │
      ┌─────┴─────┐
      │  事实表   │
      └───────────┘
```

**特点**：
- 规范化设计，减少数据冗余
- 存储效率高
- 查询需要更多关联

**适用场景**：数据量大、存储成本敏感、查询性能要求不高

### 3.4 星型 vs 雪花对比

| 维度 | 星型模型 | 雪花模型 |
|------|----------|----------|
| 结构 | 非规范化 | 规范化 |
| 存储 | 冗余较多 | 节省存储 |
| 查询 | 少关联，性能高 | 多关联，性能较低 |
| 维护 | 数据更新复杂 | 数据更新简单 |
| 复杂度 | 简单 | 复杂 |

**建议**：优先使用星型模型，只在维度表极大、存储成为瓶颈时才考虑雪花模型

## 四、数据仓库架构

### 4.1 Kimball架构（维度数据仓库）

**提出者**：Ralph Kimball

**核心思想**：
- 自底向上开发
- 维度建模（星型/雪花模型）
- 总线架构（一致性维度）

**特点**：
- 数据集市是维度数据仓库的子集
- 分析系统可直接访问数据仓库
- 面向业务流程

**优点**：
- 开发周期短
- 快速交付
- 易于理解和使��

**缺点**：
- 数据冗余较多
- 维护相对困难

### 4.2 Inmon架构（企业级数据仓库）

**提出者**：Bill Inmon（"数据仓库之父"）

**核心思想**：
- 自上而下规划
- 范式建模（3NF）
- 企业信息化工厂（CIF）

**特点**：
- 先建立企业级数据仓库
- 数据集市从数据仓库派生
- 分析系统通过数据集市访问数据

**优点**：
- 数据一致性高
- 规范化设计，维护简单
- 适合长期规划

**缺点**：
- 建设周期长
- 初始成本高

### 4.3 两种架构对比

| 维度 | Kimball | Inmon |
|------|---------|-------|
| 建模方式 | 维度模型（星型/雪花） | 范式模型（3NF） |
| 开发方式 | 自底向上 | 自上而下 |
| 数据集市 | 数据仓库的子集 | 从数据仓库派生 |
| 访问方式 | 可直接访问数据仓库 | 通过数据集市访问 |
| 建设周期 | 短 | 长 |
| 初始成本 | 低 | 高 |
| 数据冗余 | 多 | 少 |
| 维护难度 | 较难 | 较易 |
| 适用场景 | 敏捷交付、快速迭代 | 大型企业、长期规划 |

### 4.4 混合架构实践

**互联网公司常用方案**：
1. **基础层（Inmon思想）**：按主题域建模，构建企业级数据仓库
2. **集市层（Kimball思想）**：面向分析主题，采用星型模型

**优势**：
- 兼顾数据一致性和分析效率
- 业务分析人员易于理解使用
- 技术部门可快速开展

## 五、数据分层实施方法

### 5.1 建模流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          数据仓库建模流程                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐│
│  │  1.业务调研 │───▶│  2.主题域划分│───▶│  3.总线设计 │───▶│  4.维度建模 ││
│  └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘│
│         │                                                         │     │
│         │         ┌─────────────┐    ┌─────────────┐              │     │
│         └────────▶│  5.事实表设计│◀───│  6.汇总层设计│◀─────────┘     │
│                   └─────────────┘    └─────────────┘                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.2 步骤详解

#### 步骤1：业务调研
- 梳理核心业务流程
- 识别关键业务过程
- 收集业务需求和数据需求

#### 步骤2：主题域划分
- 按业务主题组织数据
- 常见主题域：用户、商品、订单、流量、库存、财务

#### 步骤3：一致性维度设计
- 设计跨主题复用的维度
- 如：时间维度、地区维度、用户维度
- 确保口径一致

#### 步骤4：维度建模
- 选择建模方式（星型/雪花）
- 设计维度表（主键、属性、层级）
- 确定维度类型（退化维度、缓慢变化维）

#### 步骤5：事实表设计
- 确定度量（可加/半可加/不可加）
- 设计事实表类型（事务型、周期快照型、累积快照型）
- 定义事实表粒度

#### 步骤6：汇总层设计
- 按分析主题设计汇总表
- 预计算常用指标
- 平衡查询性能和存储成本

### 5.3 实施要点

| 要点 | 说明 |
|------|------|
| 逐层净化 | 从ODS到ADS，数据质量逐步提升 |
| 避免跨层 | 上游层不服务下游，上下游职责清晰 |
| 口径统一 | 同一指标在所有层保持一致 |
| 可复用 | DWS层设计通用汇总，ADS层直接复用 |
| 适度冗余 | 为了查询性能，允许适当数据冗余 |
