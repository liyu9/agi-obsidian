## 一、立项背景

### 1.1 业务痛点

| 痛点 | 现状 | 影响 |
|------|------|------|
| SQL门槛高 | 查询是核心数据工具，需掌握SQL语法 | 会用的人少，业务响应慢 |
| 需求积压 | 会SQL的分析师、开发人员有限 | 数据团队负荷重，业务等待长 |
| 项目众多 | 游戏项目多，数据需求量大 | 人力瓶颈明显 |
| 口径不一 | 各方对指标定义理解不同 | 数据可信度低 |

### 1.2 解决方案

依托大模型技术，打造**对话式数据分析Agent**，实现：
- 自然语言直接查询，降低使用门槛
- 业务人员自主取数，减少对数据团队的依赖
- 口径标准化统一，确保数据一致性

### 1.3 行业趋势

- **2025年**：智能BI元年，大模型赋能数据分析
- **2026年**：Agent从"助手"到"协作者"，数据分析智能化加速

### 4.2 各阶段详细说明

#### 阶段1：提问（自然语言输入）

**输入**：
- 口语化表述："昨天的安卓新用户首日付费金额为什么下降这么多？"
- 支持模糊表达："收入怎么样"

**处理**：
- 语音转文本（可选）
- 口语化预处理（纠错、补全）

#### 阶段2：解析（语义理解）

**核心任务**：
- 分词与词性标注
- 句法分析
- 实体识别（指标、时间、维度、人群）
- 意图初步判断

**案例解析**：

```
输入："昨天的安卓新用户第一天的付费金额为什么这么低？上周就不是这样"

实体抽取：
┌────────────────────────────────────────────────────────────┐
│  指标      │ 首日付费金额                                    │
│  时间      │ 昨天                                            │
│  对比时间  │ 上周同周期                                       │
│  维度      │ 安卓渠道                                        │
│  人群      │ 新用户                                          │
│  任务目标  │ 找出下降原因                                     │
└────────────────────────────────────────────────────────────┘
```

#### 阶段3：业务术语标准化

**核心任务**：
- 检索知识库，匹配业务术语
- 消除歧义，映射到标准口径
- 生成标准化查询需求

**术语映射表**：

| 业务口语 | 标准化定义 | 数据库字段 |
|----------|------------|------------|
| 新用户 | 注册日期 = 分析日期 | dim_user.is_new = 1 |
| 首日付费金额 | 用户首日累计付费 | dws_user_pay_1d.first_day_amt |
| 安卓渠道 | Android/HarmonyOS | dim_channel.os_type IN ('android','HarmonyOS') |
| 上周同期 | 7天前同周期 | dt = DATE_SUB(当前日期, INTERVAL 7 DAY) |

#### 阶段4：意图识别与改写

**意图类型**：

| 意图类型 | 特征 | 后续流程 |
|----------|------|----------|
| 简单查数 | 单指标、单时间点 | 直连SQL生成 |
| 趋势分析 | 多时间点对比 | SQL生成+趋势图 |
| 归因分析 | 含"为什么"等词 | 任务规划+多维下钻 |
| 异常检测 | 含"异常/波动"等词 | 波动归因分析 |

**智能追问机制**：
- 信息缺失时自动追问
- 模糊表达时确认澄清
- 多义理解时提供选项

**案例**：
```
用户："收入怎么样"
Agent："您想了解哪个指标的收入？[总收入/付费收入/广告收入]以及什么时间范围？"
```

#### 阶段5：智能体任务规划与拆解

**触发条件**：
- 意图为"归因分析"、"复杂分析"
- 用户明确要求多维分析

**任务拆解树**：

```
┌─────────────────────────────────────────────────────────────┐
│                    任务：安卓新用户首日付费下降原因分析          │
├─────────────────────────────────────────────────────────────┤
│  1. 计算基准差异                                              │
│     └─ 本期 vs 上期：下降幅度、下降金额                        │
│  2. 公式拆解贡献度                                            │
│     └─ 拆解：人数 × 付费率 × ARPU                            │
│     └─ 贡献度：各因子对下降的贡献比例                          │
│  3. 下钻维度分析                                              │
│     └─ 渠道维度：各安卓渠道表现                               │
│     └─ 时间维度：近7天每日趋势                               │
│     └─ 群体维度：新用户来源、注册方式                          │
└─────────────────────────────────────────────────────────────┘
```

#### 阶段6：SQL生成

**技术方案**：
- NL2SQL大模型生成SQL
- 模式关联（Schema Linking）对齐表字段
- DSL中间层实现可解释、可干预

**生成示例**：

```sql
-- 逻辑SQL（基于DSL生成）
SELECT 
    dt,
    os_type,
    COUNT(DISTINCT user_id) AS new_users,
    SUM(first_day_amt) AS total_amt,
    SUM(first_day_amt) / COUNT(DISTINCT user_id) AS arpu
FROM dws_user_pay_1d
WHERE dt BETWEEN '2026-05-19' AND '2026-05-26'
  AND is_new = 1
  AND os_type IN ('android', 'HarmonyOS')
GROUP BY dt, os_type
ORDER BY dt;
```

#### 阶段7：校验

**校验项**：

| 校验项 | 检查内容 | 处理方式 |
|--------|----------|----------|
| 语法检查 | 符合PrestoSQL语法 | 语法错误时重新生成 |
| 权限校验 | 用户具备表权限 | 无权限时提示申请 |
| 结果验证 | 数据合理性检查 | 异常值时提示确认 |
| 口径验证 | 与标准定义一致 | 偏差时提供修正建议 |

**SQL透明化**：
- 显示逻辑SQL（业务可理解）
- 支持查看物理SQL（技术可验证）
- 执行过程可追溯

#### 阶段8：执行

**执行策略**：
- 支持并发查询
- 结果缓存加速
- 超时自动中断

**异常处理**：
```
执行异常 → 捕获错误日志 → 返回阶段6 → 大模型修复SQL → 重新校验执行
```

### 5.2 核心功能说明

#### 5.2.1 多轮对话与智能追问

**功能描述**：
- 支持上下文记忆，多轮追问
- 意图模糊时自动追问澄清
- 异常结果时智能提示确认

**交互示例**：

```
用户：昨天的收入多少？
Agent：昨天总收入 128.5 万元，较前日上涨 5.2%。

用户：那安卓渠道呢？
Agent：安卓渠道收入 45.2 万元，占比 35.2%。

用户：为什么比上周低？
Agent：【归因分析】
     安卓渠道上周同期收入 52.1 万元，下降 13.2%。
     主要原因：
     1. 新用户数下降贡献 60%（新用户减少 15%）
     2. ARPU下降贡献 30%（付费率下降 2.3%）
     3. 其他因素贡献 10%
```

#### 5.2.2 波动归因分析

**功能描述**：
- 自动检测数据波动
- 智能拆解波动原因
- 量化各因子贡献度

**归因模型**：

```
下降 = Σ(因子贡献度 × 因子变化)

示例：
付费金额下降 = 人数变化贡献 + 付费率变化贡献 + ARPU变化贡献

计算方式：
人数贡献 = (本期人数 - 上期人数) × 上期付费率 × 上期ARPU
付费率贡献 = 本期人数 × (本期付费率 - 上期付费率) × 上期ARPU
ARPU贡献 = 本期人数 × 本期付费率 × (本期ARPU - 上期ARPU)
```

#### 5.2.3 数据解读与洞察

**功能描述**：
- 自然语言解读数据
- 趋势、对比、异常自动识别
- 业务建议智能生成

**解读模板**：

```
【数据概览】
- 指标：总收入
- 本期：128.5 万元
- 环比：+5.2%（↑）
- 同比：+12.8%（↑）

【趋势分析】
近7天呈上升趋势，周三达到峰值后小幅回落

【异常识别】
无明显异常

【优化建议】
建议关注周末转化率，可考虑活动刺激
```

**功能描述**：
- 显示业务可理解的逻辑SQL

### 6.2 多轮会话实现方案

#### 6.2.1 记忆层设计

**短期记忆（会话级）**：
```json
{
  "session_id": "xxx",
  "messages": [
    {"role": "user", "content": "昨天的收入多少？"},
    {"role": "assistant", "content": "昨天总收入 128.5 万元"},
    {"role": "user", "content": "那安卓渠道呢？"}
  ],
  "context": {
    "last_query": {"指标": "收入", "时间": "昨天"},
    "referent": "那安卓渠道" → "安卓渠道收入"
  }
}
```

**长期记忆（用户/全局级）**：
```json
{
  "facts": [
    {"fact": "华东区是核心业务区", "source": "业务知识库"},
    {"fact": "新用户定义：注册日期=分析日期", "source": "指标口径"}
  ],
  "relationships": [
    {"from": "产品A", "relation": "属于", "to": "安卓渠道"}
  ]
}
```

#### 6.2.2 指代消解

```
上下文：昨天的总收入 128.5 万元
用户问：那安卓渠道呢？

指代解析：
- "那" → 承接上文
- "安卓渠道" → 维度限定
- 完整理解：安卓渠道昨天的收入

DSL生成：
{
  "指标": "收入",
  "时间": "昨天",
  "维度": "安卓渠道"
}
```

## 七、落地难点与解决方案

### 7.1 准确率问题

| 难点 | 解决方案 |
|------|----------|
| SQL生成错误 | 自研NL2SQL模型，SQL标注规范，badcase持续优化 |
| 幻觉问题 | DSL中间层校验，过程可验证，结果可干预 |
| 歧义理解 | 智能追问澄清，术语标准化映射 |

### 7.2 性能问题

| 难点 | 解决方案 |
|------|----------|
| 查询延迟高 | 结果缓存，预计算加速 |
| 并发压力大 | 限流降级，异步处理 |
| 复杂分析慢 | 任务拆解，并行执行 |

### 7.3 落地运营

| 难点 | 解决方案 |
|------|----------|
| 场景碎片化 | 模板化分析场景，知识库沉淀 |
| 口径不统一 | 指标体系管理，标准化口径 |
| 持续优化 | badcase反馈机制，定期模型优化 |
