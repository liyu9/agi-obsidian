# 多轮深度思考与反思

## 核心能力

本 Skill 赋予 Agent 类似豆包 APP 的"深度思考"能力，支持：
- **任务分解**：将复杂问题拆解为可执行的子任务
- **多轮推理**：通过多轮迭代逐步逼近最优解
- **自我反思**：在每一步执行后进行反思和修正
- **动态调整**：根据执行反馈调整后续策略

## 思考模式层级

```
┌─────────────────────────────────────────────────────────────────┐
│  思考深度层级（类似豆包的四层思考模式）                          │
├─────────────────────────────────────────────────────────────────┤
│  Level 1 - 快速响应    │ 简单查询，直接回答，无需深度思考       │
│  Level 2 - 标准思考    │ 常规任务，单轮推理，直接执行           │
│  Level 3 - 深度思考    │ 复杂问题，多轮推理，逐步拆解           │
│  Level 4 - 研究模式    │ 深度研究，边想边搜，迭代优化           │
└─────────────────────────────────────────────────────────────────┘
```

## 执行流程

### Step 1: 意图识别与复杂度评估

分析用户请求，判断所需思考深度：

| 特征 | Level 1 | Level 2 | Level 3 | Level 4 |
|------|---------|---------|---------|---------|
| 问题类型 | 事实查询 | 操作任务 | 分析决策 | 研究探索 |
| 步骤数量 | 1步 | 2-3步 | 4-8步 | 8步以上 |
| 信息需求 | 已知知识 | 本地文件 | 多源整合 | 实时搜索 |
| 示例 | "今天星期几" | "优化这段代码" | "设计系统架构" | "调研竞品方案" |

### Step 2: 任务分解（Level 3+）

对于复杂任务，自动拆解为子任务：

```
用户请求："帮我设计一个电商系统的订单模块"

任务分解：
├── 子任务1：需求分析
│   └── 明确订单模块的功能边界
├── 子任务2：数据建模
│   └── 设计订单相关的数据表结构
├── 子任务3：API设计
│   └── 定义订单相关的接口规范
├── 子任务4：流程设计
│   └── 绘制订单状态流转图
└── 子任务5：实现建议
    └── 提供技术选型和实现方案
```

### Step 3: 多轮推理执行

采用"思考→执行→反思→调整"的循环模式：

```
第1轮：
  思考：理解问题核心
  执行：完成初步分析
  反思：是否遗漏关键信息？
  
第2轮：
  思考：基于反馈深化理解
  执行：补充分析维度
  反思：是否需要更多信息？
  
第3轮：
  思考：整合所有信息
  执行：生成完整方案
  反思：方案是否全面可行？
```

### Step 4: 自我反思与修正

每轮执行后必须进行反思：

**反思清单**：
- [ ] 是否完全理解用户意图？
- [ ] 当前结果是否准确？
- [ ] 是否有遗漏的关键点？
- [ ] 是否需要调用工具获取更多信息？
- [ ] 下一步应该如何优化？

### Step 5: 结果整合与输出

将多轮思考的结果整合为最终输出：

```markdown
## 思考过程
1. 第一轮分析：...
2. 第二轮深化：...
3. 第三轮验证：...

## 最终结论
...

## 执行建议
- 短期行动：...
- 中期规划：...
- 长期考虑：...
```

```
✓ 确定约束条件

Step 2: 收集相关信息
✓ 检索本地知识库
✓ 分析现有代码
↓ 进入下一步

Step 3: 生成解决方案
✓ 提出3个候选方案
✓ 评估各方案优劣
↓ 进入下一步

Step 4: 优化与验证
✓ 细化最优方案
✓ 检查潜在风险
→ 输出最终结果
```

## 工具协同策略

在多轮思考中合理使用工具：

| 思考阶段 | 可用工具 | 使用时机 |
|---------|---------|---------|
| 信息收集 | search, read, browse | 需要外部信息时 |
| 代码分析 | grep, glob, codebase | 分析项目代码时 |
| 方案验证 | bash, test | 验证方案可行性时 |
| 文档生成 | write, edit | 输出最终结果时 |

## 反思触发条件

以下情况必须触发反思机制：

1. **信息不足**：发现缺少关键信息时
2. **结果异常**：执行结果与预期不符时
3. **用户反馈**：用户指出问题或补充需求时
4. **多方案选择**：需要在多个方案中选择时
5. **风险评估**：识别到潜在风险时

## 示例场景

### 场景1：代码重构建议

```
用户：帮我优化这段代码的性能

思考过程：
Step 1: 分析代码现状
  - 读取代码文件
  - 识别性能瓶颈
  - 反思：是否遗漏了算法复杂度问题？

Step 2: 研究优化方案
  - 检索最佳实践
  - 对比多种优化策略
  - 反思：这个方案是否适用于当前场景？

Step 3: 生成优化建议
  - 提供具体优化代码
  - 说明优化原理
  - 反思：建议是否全面？

Step 4: 补充测试建议
  - 添加性能测试方案
  - 提供验证方法
  - 反思：是否遗漏边界情况？
```

### 场景2：技术选型决策

```
用户：我们应该用React还是Vue？

思考过程：
Step 1: 分析项目需求
  - 团队技术栈现状
  - 项目复杂度评估
  - 反思：是否考虑了长期维护成本？

Step 2: 对比框架特性
  - React vs Vue 核心差异
  - 生态系统对比
  - 反思：是否考虑了学习成本？

Step 3: 结合实际情况
  - 团队熟悉度分析
  - 项目特定需求匹配
  - 反思：是否有遗漏的约束条件？

Step 4: 给出决策建议
  - 明确推荐方案
  - 说明决策依据
  - 提供迁移/实施建议
```

## 配置参数

在 Agent 中使用本 Skill 时，可通过以下参数调整行为：

```yaml
thinking_config:
  max_rounds: 5          # 最大思考轮数
  reflection_threshold: 0.8  # 反思触发阈值
  auto_tool_call: true   # 是否自动调用工具
  show_process: true     # 是否展示思考过程
  depth: "adaptive"      # 思考深度：fast/standard/deep/adaptive
```
