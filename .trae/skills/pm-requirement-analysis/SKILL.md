# B端需求分析与优先级管理

基于《决胜B端》第06/12章方法论，完成从原始需求到产品需求的分析转换，并进行优先级判定和需求验证。

## 触发条件

用户提到以下意图时激活：
- "分析这个需求"
- "评估这几个需求的优先级"
- "管理需求池"
- "做需求挖掘"
- "区分原始需求和产品需求"
- "这个需求怎么评估价值"

## 执行流程

### Phase A: 需求分析

#### Step 1: 区分原始需求与产品需求

**目标**：将用户提报的一句话需求，转化为颗粒度清晰的产品需求。

**方法**：原始需求是未分析加工的用户诉求，充满了不确定性；产品需求是分析后的解决方案，具备确定性。两者是多对多关系。

**操作**：
1. 收集原始需求（用户提报、业务观察、监管要求）
2. 识别原始需求中的混合诉求（可能包含痛点描述 + 用户提出的解决方案）
3. 拆散或合并原始需求，形成产品需求
4. 验证：产品需求颗粒度是否清晰、逻辑是否完整、是否能直接提给研发

**输出**：原始需求清单 + 产品需求清单（含对应关系）

#### Step 2: 十三要素五步法深度分析

**目标**：对原始需求进行深度分析，找到痛点，明确业务本质。

**方法**（第06章核心方法论）：

**Step 2.1 角色-场景-路径分析**
- 角色：谁在什么岗位发起了这个需求？
- 场景：这个需求发生在什么业务场景下？
- 路径：当前的操作路径是什么？痛点在哪一步？

**Step 2.2 数据建模**
- 梳理业务背后的数据对象（人/事/物）
- 确定对象之间的关系（一对一/一对多/多对多）
- 提炼关键属性

**Step 2.3 业务规则挖掘**
- 显性规则：用户明确表达的规则
- 隐性规则：业务运作中不言自明的规则
- 边界条件：什么情况下会触发异常？

**输出**：十三要素分析结果（角色+场景+路径+数据模型+规则）

#### Step 2.4: 逆向分析法（补充）

**目标**：挖掘用户真实需求，避免被表层诉求带偏。

**方法**（社区方法论补充）：

**核心思路**：用户说要X，但真正需要的可能是Y。

**五步法**：
1. 用户说：记录用户原话（"我需要一个XX功能"）
2. 追问为什么：为什么要XX？（可能是因为遇到了某个问题）
3. 再追问为什么：为什么这个问题会造成困扰？（可能影响了他的什么KPI）
4. 挖掘本质：找到用户真正想解决的问题（不是XX功能，而是解决某业务痛点）
5. 反向验证：如果不解决这个本质问题，用户还能接受吗？

**适用场景**：
- 用户明确提出解决方案的需求（"加个按钮"、"做个导出"）
- 需求模糊、无法直接分析的场景

**输出**：逆向分析表

| 用户原话 | 本质问题 | 真正需求 |
|---------|---------|---------|
|         |         |          |

#### Step 3: 需求分类与价值评估

**目标**：确定需求属于哪个层次，体现什么价值。

**方法**（第12章 + 社区方法论）：

**需求层次分类**（四层，由浅入深）：
- **表层需求**：用户直接提出的功能诉求（如"需要报表导出"）
- **业务需求**：对应部门的核心痛点（如财务需要的是"多维度成本分析"）
- **战略需求**：企业数字化转型目标（如"流程在线化，效能提升30%"）
- **技术需求**：功能复用、架构设计，体现技术价值

**三来源分类**：
- 业务需求：来自中高层管理人员，自顶向下
- 用户需求：来自一线用户，自下向上
- 技术需求：来自研发团队，架构驱动

**四类价值**：
- 商业价值：是否符合产品定位和商业战略
- 业务价值：提升规模/降低成本/提高效率/保证品质/控制风险
- 用户价值：提升操作效率和满意度
- 技术价值：降低研发成本/提升产品化能力

**输出**：需求分类标签 + 价值评估结论

---

### Phase B: 需求管理与优先级

#### Step 4: 需求池管理

**目标**：建立和维护两个需求池。

**方法**：

**原始需求池字段**：
- 原始需求ID / 主题 / 内容 / 来源 / 提出日期 / 关联产品需求ID

**产品需求池字段**：
- 产品需求ID / 原始需求ID / 产品线 / 需求类型 / 主题 / 内容
- 优先级 / 迭代版本 / 产品经理 / 研发负责人 / 状态 / 计划上线日期

**状态流转**：待跟进 → 需求调研中 → PRD编写中 → 待评审 → 待排期 → 开发中 → 测试中 → 待上线 → 已上线

**输出**：需求池表格（原始需求池 + 产品需求池）

#### Step 5: 优先级判定

**目标**：确定需求的执行顺序，决定做什么和不做什么。

**方法**（按需选择）：

**成本价值模型**（最通用）：
| 象限 | 价值 | 成本 | 策略 | 优先级 |
|------|------|------|------|--------|
| Ⅰ | 高 | 高 | 规划并持续关注 | P2 |
| Ⅱ | 高 | 低 | 快速投入执行 | P0 |
| Ⅲ | 低 | 低 | 关注并抽空实现 | P3 |
| Ⅳ | 低 | 高 | 放弃 | P4 |

**RICE模型**（SaaS产品适用）：
```
RICE Score = Reach × Impact × Confidence / Effort
```
- Reach：触达的客户数量
- Impact：价值评分（1-10分）
- Confidence：信心指数（百分比）
- Effort：研发人天

**价值范围模型**（企业内部产品适用）：
- 纵轴：规模/效率/成本/风险/品质/体验
- 横轴：涉及的的利益方
- 单元格定义优先级

**KANO模型**（单一功能评估，注意：不完全适用于B端多角色场景）：
优先级顺序：必备属性(M) > 期望属性(O) > 魅力属性(A) > 无差异属性(I) > 反向属性(R)

**输出**：优先级排序表（含判定依据和模型选择理由）

#### Step 6: 需求验证与评估

**目标**：上线后验证需求是否达成预期价值。

**方法**：

**业务需求收益评估**：
- 拆解业务指标（规模→访问量→转化率→支付成功率）
- 跟踪量化子指标变化

**用户需求收益评估**：
- 操作效率提升（操作步骤减少/时间缩短）
- NPS净推荐值跟踪

**技术需求收益评估**：
- 基础功能：考核交付质量与时间
- 中台建设：考核接入量与人力的节省
- 纯技术优化：考核稳定性/安全性/性能指标

**终极指标**：产品使用人数跟踪

**输出**：需求验证方案（上线后如何度量价值）

## 验证检查项

- [ ] 原始需求和产品需求是否做了区分？多对多关系是否梳理？
- [ ] 十三要素分析是否覆盖角色/场景/路径/数据/规则？
- [ ] 逆向分析法是否使用？（当用户提出明确解决方案时）
- [ ] 需求层次分类是否完整？（表层/业务/战略/技术）
- [ ] 需求池两个池是否都建立？
- [ ] 优先级判定是否选择了合适的模型并说明了理由？

## 使用示例

**示例1: 业务方提了一个模糊需求**
> 用户: "业务说想要一个智能推荐功能"
> → Step1: 识别这是原始需求，包含"智能推荐"这个用户提出的解决方案
> → Step2: 十三要素分析：谁用？在什么场景推荐？当前如何做？痛点是什么？
> → Step3: 分类为用户需求+业务需求（如果涉及转化率）
> → Step5: 用RICE模型评估

**示例2: 需求优先级判定**
> 用户: "有三个需求，产品说重要，研发说技术复杂，怎么排优先级"
> → Step5: 成本价值模型定位象限 + RICE打分量化
> → 输出优先级排序表和判定依据

**示例3: 需求池梳理**
> 用户: "整理一下我们团队的需求池"
> → Step4: 建立原始需求池+产品需求池模板
> → 导入现有需求，按字段分类整理
