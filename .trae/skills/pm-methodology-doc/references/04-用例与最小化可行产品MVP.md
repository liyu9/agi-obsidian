# 用例与最小化可行产品（MVP）

> 来源课程：硅谷产品实战36讲（第09/10讲）、PM需求方法论、三节课-产品经理高阶课

---

## 一、用例（Use Case）

### 核心定义

用例就是描述在什么场景下用户用产品来做什么事。用例的目的是清晰沟通产品要解决哪几个问题、具体怎么解决、用户需要做哪些操作。

> 用例可以用文字、图表或流程图来表示，能让设计师和工程师清楚、准确地理解才是最重要的，而不是遵循某个固定格式。

### 方法论：用例三要素

| 要素 | 说明 |
|------|------|
| **触发条件** | 什么情况下能开启这个功能？ |
| **预期结果** | 执行完操作后，用户得到了什么？ |
| **复用架构** | 如何利用已有产品架构？哪些部分可共用、哪些需要新增 |

### 用例具体化

**成熟产品**（已有框架）：逐步骤详细描述工作流
> 用户点击"+" → "添加好友" → 文本框输入用户名 → 开启搜索 → 完全吻合才显示 → 点击进入用户页面 → 点击"添加到通讯录"

**新产品**（无框架）：先描述功能组成部分，再逐一细化
> 用户进入添加好友页面 → 有搜索用户名的地方 → 显示搜索结果（需预防加错人机制）→ 添加目标用户

### 注意事项

- 不要过于追求复杂图表，把时间花在做图上
- 重点是表述方式是否最准确、最清晰
- 流程图可以用"第1步、第2步"等简单方式表达

### 案例：微信加好友功能的用例

#### 第1步：列出所有用例

**一个用户想添加另一个用户：**
1. 通过用户名添加
2. 通过朋友分享的名片添加
3. 通过扫描二维码添加
4. 在群成员中找到用户添加

**一个用户想同时添加一群人：**
5. 找到距离很近的用户同时添加（面对面群场景）
6. 输入相同密码自动加入群再添加

#### 第2步：分析触发条件

- 1-4：任何情况下都可以开启，但1和3更适合面对面
- 5-6：适用于一群人在一起面对面添加好友

#### 第3步：复用已有架构

**可以共用：**
- 入口点一样：点击"+" → "添加好友" → 选择具体添加方式
- 找到用户后的介绍页面（头像、用户名、一句话介绍、"添加到通讯录"）完全共用

**需要新增：**
- 菜单里新增两个选项
- 5和6需要能让用户快速添加（区别于前4种的搜索匹配）
- 第5种利用地理位置（假设相同位置的用户多半在一起聚会）

> **Facebook实战：** 搜索、添加好友的功能涉及用户信息显示、隐私设置等，看似简单的添加好友功能会影响几十个不同的产品、上百个工程师，以及非常多的场景。把用例写得足够清楚非常重要。

## 二、最小化可行产品（MVP）

### 核心定义

来源：埃里克·莱斯《精益创业》

> 提倡"验证性学习"，先推出极简原型，以最小成本验证产品是否符合用户需求。如果不符合，"快速地失败、廉价地失败"。

**MVP = 最小化 + 可行性**

| 要素 | 含义 | 误区 |
|------|------|------|
| **最小化** | 没有任何一个功能是"加上去也挺好的"，少了任何功能都无法解决基本需求 | ≠ 只做最简单的功能，而是只做最必要的功能 |
| **可行性** | 至少要很好地满足一个需求 | 不能为了追求速度发布只能解决50%需求的产品 |

> MVP好比"凤凰男"：刚相处时除了对你好一无所有，但后来奋发图强逐步进化。最关键的是"对你好"这个基本需求必须满足好。

**优先级：** 如果连最基本需求都解决不好，先提升体验，不要着急加新功能。

### 方法论：MVP设计流程（三节课-产品经理高阶课）

#### 阶段一：0 → 0.5（验证产品价值）

目标：验证产品是否有价值，不需要大规模研发。

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| **仿真Demo** | 用Sketch/Mockplus等原型工具做出以假乱真的demo，观察用户点击和期待 | 纯在线产品 |
| **产品介绍视频** | 做一个视频发给种子用户，看他愿不愿意扫码关注 | 内容型产品 |
| **文档** | 写一篇有价值的文档（如旅游攻略），看用户下载量和加微意愿 | 知识/内容类 |
| **预售** | 只有图文介绍就开始卖，用户花钱投票 | 商品/课程类 |
| **着陆页** | 先介绍产品收集用户信息，让他加微信或群 | 收集种子用户 |

**案例：Dropbox** — 上线前做了一个3分钟演示视频，附带邮箱注册。一夜之间从5000人飙升至75000人等待邀请，零代码就验证了需求。

#### 阶段二：0.5 → 1（让用户真实能用）

目标：用户能正常完成一次完整使用过程。

**三个关键因素：**

1. **最小** — 突出核心功能，注册登录可用第三方授权解决
2. **可用** — 基本流程能正常使用，不能有明显断档
3. **用第三方工具** — 减小开发量、提升速度，大量调整时不用返工

> **三节课自身教训：** 早期花了3-4个月开发MVP，上线效果不明显。后来直接用第三方工具嫁接上课工具、上传视频让用户做作业，反而更快验证了产品价值。基于此重新设计的学习体验一直用到现在。

> **Uber案例：** 早期通过类似电话方式派单，招了第一个程序员后才做信用卡注册流程。上线后1-2年一直在调算法，前端界面不需要大改——因为MVP阶段已完成了用户体验验证。

## 三、案例

### Instagram — 没有滤镜不算MVP

- 初版只有发图片功能，用户体验不好
- CEO女朋友一句话点醒：能不能把照片弄得好看一点？
- 用户需求不是"分享照片"，而是"分享拿得出手的照片"
- 没有滤镜的Instagram不能算MVP，因为连基本需求都没解决好

### Facebook 2004 — MVP成功

只有：个人介绍、联系方式、政治观点、个人兴趣、朋友列表、小组、发消息。没有朋友圈，但满足了和朋友交流、窥探朋友的基本需求。

### Google 1997 — MVP成功

只有文本搜索功能，域名还在Stanford下面，但满足了搜索信息的核心需求。

### Amazon 1994 — MVP成功

只是一个书单，连物流系统都没有，但能帮你找到书店找不到的书。

### Jelly — 忽视可行性的失败案例

Twitter联合创始人做的朋友互动搜索引擎：
1. 只解决提问者需求，回答者毫无意义 → 回答量逐渐减少
2. 等朋友回答需要时间，用户没耐心等

### Chorus — 忽视可行性的失败案例

帮助朋友互相监督健身的APP。社交压力过大 → 被提醒者羞愧 → 不再使用。8个月后下架。

> 两个失败案例的共同教训：忽视了"可行性"，没有真正解决用户最基本的需求，或没有以好的方式解决。

## 四、要点速查

| 概念 | 一句话定义 |
|------|-----------|
| 用例 | 描述在什么场景下用户用产品来做什么事 |
| 用例三要素 | 触发条件 + 预期结果 + 复用已有架构 |
| 用例具体化（成熟产品） | 逐步骤描述工作流，细节到每一步操作 |
| 用例具体化（新产品） | 先列功能模块，再逐个思考设计 |
| MVP | 最小化可行产品 = 降低试错成本 + 确保解决核心需求 |
| 最小化 | 没有任何一个功能是"加上去也挺好的"，少了任何一个都无法解决基本需求 |
| 可行性 | 必须能比较好地满足至少一个核心需求 |
| MVP 0→0.5 | 验证产品价值：仿真Demo/视频/文档/预售/着陆页 |
| MVP 0.5→1 | 让用户真实能用：最小+可用+第三方工具 |
