## 四、新章节内容简介（供对话输出）

### §6.3 接入方式

**定位**：回答"Agent 用什么协议与记忆系统通信"。与数据流主干（①→②→③）正交，是 Agent 出站时的协议选择维度。

- **6.3.1 三通道职责**：Hooks（生命周期驱动·自动）/ MCP（模型意图驱动·按需）/ SDK（通用编程接入）三表对比
- **6.3.2 7 Hook 生命周期时间轴**：SessionStart → UserPromptSubmit(读) → Stop(写) → PreCompact(归档) → SessionEnd → SubagentStart/Stop
- **6.3.3 Agent 接入决策树**：CC/OpenClaw/Hermes/Cursor/Trae/LangChain/自建 各走哪条通道
- **6.3.4 ②层观测埋点独特价值**：为什么埋点必须在②层而非各实例内部（跨库归因 + token 成本分摊）

### §6.4 记忆模型

**定位**：回答"什么场景下、什么时机、用什么方式**记入**记忆、记入后**怎么存储**、需要时**怎么召回**"。完整覆盖"记入 → 存储 → 召回"三个环节，对应数据流路径 1/2（记入）+ 服务端处理（存储）+ 路径 3/4（召回）。

- **6.4.1 记忆类型与分类**：官方 5 类（preferences/events/cases/memories/skills）+ archive + resources，每类的语义与承载内容
- **6.4.2 记忆记入模型**（场景 × 时机 × 记入方式三表）：
  - **自动记入**（Hooks 通道）：场景=每轮对话结束；时机=Stop Hook 触发；方式=auto-capture.mjs 解析 transcript → shouldCapture 门禁（长度/命令/问句/符号/关键词）→ buildParts → Memory Extraction（LLM 按 MemoryTypeRegistry 5 类分类）
  - **显式记入**（MCP 通道）：场景=模型判断"这一条值得沉淀"；时机=模型主动调用；方式=MCP store → 服务端 LLM extraction + Embedding
- **6.4.3 记忆存储模型**（分层 × 压缩 × 归档）：
  - **L0/L1/L2 三层结构**：.abstract.md / .overview.md / 原文，按需加载省 token
  - **Working Memory v2 Compression**：LLM Function Calling 按 WM 7 sections 压缩
  - **commit/archive 阈值**：pending token ≥20000 触发 commit；180 天未访问迁 TOS 冷存
- **6.4.4 记忆召回模型**（自动 + 显式）：
  - **自动召回**（Hooks）：UserPromptSubmit Hook 触发 → 多路检索 → score≥0.35 过滤 → recallLimit=6 → 2000 token 预算 → 注入 `<openviking-context>`
  - **显式召回**（MCP）：模型判断"6 条不够" → MCP search → 跨库联邦 fan-out → 合并排序 Top-K

## 六、假设与决策

- **假设 1**：§6.2.4 关键数据流（4 条路径）保留在 §6.2，作为"数据如何流动"的实证图，不抽到 §6.4。理由：数据流图是架构层的端到端验证，与记忆模型（讲提取/存储/召回的逻辑）是两个视角。
- **假设 2**：§6.4 记忆模型需要**新增**"场景×时机×方式"框架表，因为现有内容只有流程图（auto-capture/auto-recall），没有从"模型视角"讲清楚提取/存储/召回的逻辑分层。
- **决策 1**：推荐方案 A（新增 §6.3/§6.4，原 §6.3 风险顺移），理由是接入方式与记忆模型都是独立完整的知识域，值得独立章节，不应继续塞在 §6.2 架构里。
- **决策 2**：§6.4 记忆模型以"提取/存储/召回"三段式组织（对应 6.4.2/6.4.3/6.4.4），而非按"自动/显式"组织，因为提取/存储/召回是记忆系统的本体逻辑分层。
