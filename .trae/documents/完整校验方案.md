# 17 篇文档完整校验与质量保障方案

## 0. 根因分析：为什么"反复校验，反复有新问题"

| 根因 | 表现 | 后果 |
|------|------|------|
| **源不对齐** | 之前用 `doc_content.xml`（旧导出），现在用飞书 v2 实时拉取 | 两次基准不同，每次切换基准都"发现新问题" |
| **检测器片面** | 每次只查一类问题（格式 / 内容 / 图片） | 修一类时往往破坏另一类 |
| **修复脚本引入新 bug** | 用正则批量替换 HTML 标签时，误把代码块内合法的 `<tag>` 也替换了 | 修了 1 个问题，产生 1 个新问题 |
| **无单一事实源（SSOT）** | `.bak` 是旧版，`.md` 是新版，校验器各算各的 | "已修"与"未修"判断标准不一致 |
| **检测器与生成器耦合** | 检测器自己也有 bug（如 `<u>` 行内代码误判） | 报告"问题"实际是误报 |
| **人工 vs 机器校验脱节** | 机器只查语法，Obsidian 渲染时才发现图片错位、列表断裂 | 校验"通过"但实际有显示问题 |

## 1. 总体策略：分层校验 + 单一事实源

        │              │                  │
        │              ▼                  │
        │       修复脚本（保守）           │
        │              │                  │

                       │

## 2. 完整校验矩阵（10 个维度）

每个维度都有：检测器 → 报告 → 自动修复（保守）→ 抽样人工核验。

| # | 维度 | 检测器 | 报告项 | 自动修复 | 人工核验 |
|---|------|--------|--------|----------|----------|
| 1 | **源对齐** | `step2_parse_source_v2.py` | 17 章源数据 JSON | 不可自动修 | 抽查 03、06、17 |
| 2 | **段落完整性** | `step4_compare.py` LCS | 源/本地段数比 | 不自动修（防误改） | 抽查 04 RAG、06 实操 |
| 3 | **图片数量** | `step7_final.py` | 源图/本地图比 | 重新从源生成 | 抽查 04、05、06 |
| 4 | **图片位置** | 前后 50 字符锚点 | 偏离 >200 字符 | 重新生成 | 抽查 04 RAG 图片 |
| 5 | **代码块平衡** | 栈式追踪 fence | 未闭合 fence | 重新生成 + 栈修复 | 抽查 03、04、05 |
| 6 | **代码块内容** | 行级 LCS | 内容差异 | 重新生成 | 抽查 03 Prompt |
| 7 | **Heading 层级** | `# ~ ######` 序列 | 跳级、空 H1 | 重新生成 | 抽查 04 子节 |
| 8 | **列表/嵌套** | `-/*/+/1.` 缩进 | 不规范列表 | 重新生成 | 抽查 04、06 |
| 9 | **格式细节** | `format_check.py` | 9 类问题 | 自动修（白名单） | 抽查修复后 |
| 10 | **Obsidian 渲染** | 人工 | 图片/链接/表格渲染 | 重新生成 | **必查** 1-2 篇 |

## 3. 单一事实源（SSOT）策略

### 3.1 源文档 SSOT
- **主源**：飞书云文档 `https://my.feishu.cn/docx/YQVcdz0mgoqNWtxy9msc58uwnje`
- **离线快照**：`feishu_source.xml`（每次抓取时备份到 `feishu_source_YYYYMMDD_HHMMSS.xml`）
- **结构化数据**：`chapter_standards.json`（从源 lxml 解析生成，17 章）
- 每次修复前，先重新拉源 + 重新生成 `chapter_standards.json`

### 3.2 本地 SSOT
- **当前**：`亚慧AI产品经理知识星球/*.md`
- **回滚**：每篇保留一个 `.bak`（**最多一个**，旧的 bak 删除，避免混乱）
- **修复流程**：新方案 → 验证 → 替换 `.bak` 为上一版 → 保存新版本

### 3.3 检测器 SSOT
- **生成器**：`step5_one.py`（按章节，单一入口）
- **校验器**：`format_check.py` + `step7_final.py`（两个工具互不耦合）
- **报告**：`validation_report.md`、`final_report.md`、`.trae/documents/`

## 4. 校验脚本架构（去耦合）

```
工作流：
   抓源 → 解析源 → 生成新文件 → 校验 → 报告 → 修复

关键：每一步都是独立可重入的脚本，不互相依赖中间文件状态。
```

### 4.1 关键脚本
| 脚本 | 职责 | 入口 |
|------|------|------|
| `step1_extract.py` | 抓取飞书 → feishu_source.xml | `python step1_extract.py` |
| `step2_parse_source_v2.py` | 源 XML → chapter_standards.json | `python step2_parse_source_v2.py` |
| `step5_one.py N` | 生成第 N 章 | `python step5_one.py 1` |
| `step6_full_doc.py` | 生成完整文档 | `python step6_full_doc.py` |
| `format_check.py [N]` | 格式校验 | `python format_check.py` |
| `format_fix.py [N]` | 格式修复 | `python format_fix.py` |
| `step7_final.py` | 源-本地对比 | `python step7_final.py` |

### 4.2 检测器必须"干净"
- **format_check.py**：跳过代码块、行内代码、表格内代码
- **step7_final.py**：基于 lxml 真实解析，不用本地 buggy parser
- 检测器自身需要被校验（自举测试）

## 5. 修复策略（保守优先）

### 5.1 三类修复方式

| 修复方式 | 风险 | 适用范围 |
|----------|------|----------|
| **保守正则** | 低 | trailing 空格、列表缺空格、HTML 标签转行内代码 |
| **基于上下文的脚本** | 中 | 图片位置调整、代码块配对 |
| **整章重生成** | 高（但最稳） | 内容大面积缺失、错乱 |

### 5.2 修复原则
1. **优先整章重生成**（高风险但最稳）
2. 修复前必须备份（`.bak` 滚动）
3. 修复后必须**重新跑全部校验**（不只是修的那一项）
4. 引入新问题的修复必须回滚

## 6. 完整执行流程（一次性闭环）

```
第 1 步：抓飞书源（备份快照）
   python step1_extract.py
   → feishu_source_YYYYMMDD.xml

第 2 步：解析源（生成结构化标准）
   python step2_parse_source_v2.py
   → chapter_standards.json

第 3 步：删除所有 .bak 和旧 .md，保留上一版 .md
   （或保留 .bak 供回滚）

第 4 步：逐章重生成（17 次）
   for i in 1..17: python step5_one.py $i
   → 每章都重新从源生成

第 5 步：生成完整文档
   python step6_full_doc.py

第 6 步：跑全部校验
   python format_check.py       # 格式
   python step7_final.py         # 源-本地
   → final_report.md

第 7 步：自动修复（仅修复检测器已知的）
   python format_fix.py
   → format_report.md

第 8 步：再跑一次校验
   python format_check.py
   python step7_final.py

第 9 步：人工抽样（关键章节）
   01、04 RAG、05 Agent、06 实操、12 行业报告
   在 Obsidian 中打开，肉眼检查：
   - 标题层级
   - 图片是否显示
   - 代码块是否正常高亮
   - 列表是否缩进
   - 表格是否对齐

第 10 步：报告
   校验 + 修复 + 抽样结果 → 完整报告
```

## 7. 长期保障机制

### 7.1 飞书变更检测
- 每月运行 `step1_extract.py`
- 对比新源与旧源
- 若有差异，列出新增/删除/修改段落

### 7.2 检测器自检
- 每个检测器附带一段 mock 数据，验证自身无 bug
- 修复检测器 bug 时必须先重跑历史样本

### 7.3 文档版本管理
- `.md` 是当前版本
- `.md.bak` 是上一版
- `.md.YYYYMMDD` 是历史版本（可选，按需启用）

## 10. "新问题不再产生"的预防

1. **修复前先备份**，且只保留**一个** `.bak`（避免连锁修复）
2. **任何修复脚本必须附带回滚**（git diff 风格）
3. **检测器与修复器解耦**（避免误判 → 误修）
4. **每章独立处理**（一章失败不影响其他）
5. **整章重生成优于局部修复**（除非有明确证据局部够用）
6. **关键章节必须人工核验**（Obsidian 中真实打开）

## 11. 推荐工具

- **优先**：`lxml` 树形解析（已用）
- **次选**：BeautifulSoup
- **避免**：复杂正则 alternation（之前的 bug 根源）
