## Proposed Changes（下一轮对话的 5 个改写块）

### 改写块 A · 术语速查表（放在回复最前）

- 目的：一次性解决用户诉求 1，让后文所有术语都有可回查的定义位。
- 形式：一张 8-10 行 Markdown 表，列 3 列（术语 / 一句话含义 / 在架构中位置）。
- 收录术语（最小必要集）：
  - `Adapter`：产品适配器，把 SDK 的通用调用翻译成具体产品 API 的转换层
  - `dept_id`：部门 ID，隔离维度之一，用于映射 `team/{dept}/` 目录
  - `visibility`：可见范围标签（public / shared_within_dept / shared_within_user / private / session），决定记忆能被谁读取
  - `SDK`：软件开发工具包，Agent 侧的本地调用库（Python / Go / TS）
  - `MCP`：Model Context Protocol，Anthropic 提出的标准协议，让外部 Agent 零改造接入工具/记忆
  - `L0/L1/L2`：OpenViking 的三级信息精度（一句话摘要 / 段落摘要 / 原文详情）
  - `dense`：稠密向量索引，负责语义召回
  - `sparse`：稀疏索引（BM25/关键词），负责精确匹配
  - `flat_hybrid`：OpenViking 内置的稠密+稀疏融合索引结构（cosine + int8 量化）
  - `TOS`：火山引擎对象存储，用于 L2 原文冷存与归档
  - `KMS`：企业密钥管理服务，负责静态加密密钥
  - `OTel`：OpenTelemetry，可观测标准协议（Trace + Metric + Log）

### 改写块 B · 4 层架构分层原理（保留但精修）

- 目的：保持 4 层结构不变，把术语按"块 A 表"消费，避免二次定义。
- 每层输出统一 4 小节：
  1. 层职责（1 句话）
  2. 为什么必须单独一层（对应哪对矛盾）
  3. 内部组件的技术设计原理（引用块 A 术语，不再解释）
  4. 与相邻层的连接协议
- 特别标注：② 层第 3 小节要专门回答"MCP 通道是否绕过治理钩子"（对接改写块 D）。

### 改写块 C · "业务动词收敛"专题段（解决诉求 2）

- 目的：把上一轮一句话"收敛成 4 个业务动词"拆成 3 个子问题的完整答复。
- 结构：
  1. **业务动词是什么** — 明确 4 个动词的定义与语义边界：
     - `remember(subject, type, content, visibility, ttl)`：把一段内容作为记忆写入
     - `recall(subject, query, top_k, threshold)`：按查询召回相关记忆
     - `update(memory_id, patch)`：更新已有记忆的字段
     - `forget(memory_id | subject_filter)`：删除或标记遗忘
  2. **为什么要收敛（3 条理由）**：
     - 语义层稳定：业务只表达"记 / 找 / 改 / 忘"，OpenViking 后续升级 API 时业务代码不动
     - 治理可植入：4 个动词是 4 个天然拦截点，ID 注入 / 可见性拼路径 / 埋点全部挂在这 4 个入口
     - 跨产品可对齐：Mem0 / Letta 等候选产品都能落到这 4 个动词，未来切换后端时接口层不变
  3. **"换产品时只改 Adapter"具体含义**：
     - Adapter 是唯一知道产品 API 细节的类（例如 `OpenVikingAdapter.remember()` 内部会调 OpenViking 的 `POST /v1/memories/add`）
     - 换成 Mem0 时，写一个 `Mem0Adapter.remember()` 内部调 `mem.add(...)`，SDK 上层的 `remember(...)` 调用签名和业务代码完全不变
     - 用一段 5 行伪代码示意（SDK 调 Adapter、Adapter 分别对接 OpenViking / Mem0）

### 改写块 D · MCP 与"SDK 唯一入口"的一致性澄清（解决诉求 3）

- 目的：把冲突表述转成"三通道 → 统一治理内核"的清晰模型。
- 核心澄清点（用 1 张 4 行表 + 1 段文字）：
  - **SDK 内核（Python/Go/TS 库）**：治理钩子在这里
  - **HTTP Server**：REST 封装，内部调 SDK 内核 → 走同一套治理钩子
  - **MCP Server**：MCP 协议壳，内部调 SDK 内核 → 走同一套治理钩子
  - **结论**：三条通道在物理上不同，但在治理层收敛到同一份 SDK 内核代码；"SDK 是唯一入口"应表述为"**SDK 内核是唯一治理入口**"，MCP / HTTP 都是它的协议外壳
- 加一句关键约束：MCP Server 与 HTTP Server 都禁用直连 OpenViking 的能力，物理隔离上通过网络策略实现。

### 改写块 E · "底座" 与 OpenViking 的关系澄清（解决诉求 4）

- 目的：明确底座是 OpenViking **内置**能力，不是外部第三方组件。
- 事实依据：报告 §5.0 表 B-2 一手事实——OpenViking 的存储后端为"**内置** dense + sparse + flat_hybrid"，索引为"flat_hybrid（cosine + int8 量化）"。
- 表达要点（1 段话，3 个子点）：
  - `dense` 与 `sparse` 索引：OpenViking Server 自带的向量与关键词索引，由 flat_hybrid 融合，属于产品内部
  - `TOS`：火山引擎对象存储，是 OpenViking 的"外部冷存插件"，用于 L2 原文与归档；属于外围支撑层（④ 层），通过 S3 兼容协议对接
  - 结论修正："底座（dense/sparse/TOS）"不严谨，应分开表达为：**"OpenViking 内置底座（dense + sparse + flat_hybrid）+ 外挂冷存（TOS，S3 协议）"**

### 改写块 F · 与企业 MD 知识库（语雀式）的协作方案（新增诉求 5）

- 目的：回答场景层与技术层两个维度，给出可执行的接入形态。
- 结构分两小节：

#### F.1 场景层：MD 知识库与记忆系统的定位区分
- 一张 5 行对比表：
  - **MD 知识库（语雀）**：人写、人读为主；结构化知识；文档粒度；权限由平台管理；生命周期靠人维护
  - **记忆系统（OpenViking）**：Agent 写、Agent 读为主；对话/事实/偏好；条目粒度；权限由目录树管理；生命周期靠 SDK 自动化
- 结论：**不是替代，是互补** — MD 知识库承载"部门 SOP / 项目文档 / 静态知识"，记忆系统承载"用户偏好 / 会话上下文 / Agent 沉淀"
- 场景举例 2 条：
  - 研发工程师问"我们的代码规范是什么"→ Agent 从 MD 知识库检索
  - 研发工程师说"以后代码注释用中文"→ Agent 写入个人偏好到记忆系统

#### F.2 技术层：两种主流集成模式与推荐路径
- **模式 A · 单向同步（推荐主路径）**：
  - 通过语雀 Open API（`GET /repos/:namespace/docs` + `body` 字段 + `updated_at` 增量）拉取 Markdown
  - Webhook（`doc_update / doc_delete / toc_update`）触发实时增量
  - 归一化后落到 OpenViking 目录树 `resource/kb/{space}/{path}.md`，走 OpenViking 官方抽取管线（Parser → TreeBuilder → L0/L1/L2 → flat_hybrid 索引）
  - 优点：召回统一在 OpenViking 内，检索质量可控
- **模式 B · 双源检索（推荐兜底路径）**：
  - Agent 先按 query 命中记忆系统 → 拿到 doc_id → 命中后按 doc_id 回源语雀 API 拉最新正文用于生成
  - 优点：正文实时性最新、深链可审计
  - 用于：HR / 财务等权限敏感、内容频繁变更的知识库
- **推荐组合**：默认走模式 A（单向同步 + OpenViking 承载检索），敏感空间叠加模式 B（命中后回源鉴权 + 取最新正文）
- **权限映射的关键动作**：
  - Ingest 时抓取语雀文档 `permissions`，展开为 `principal_ids: [user_id[], group_id[]]` 快照写入 OpenViking 元数据
  - 检索时把 Agent 调用者身份下推为 filter，命中的 chunk 必须与调用者 `principal_id` 有交集才返回
  - 订阅语雀 `permission_updated` 事件 → 命中"立即失效队列"更新 ACL
- **单独一张"MD 同步管线数据流图"**（4 步）：
  ```
  语雀 Open API / Webhook  →  Ingest 网关（幂等 + 签名校验）
                                    │
                                    ▼
                          归一化 Markdown + front-matter + ACL 快照
                                    │
                                    ▼
                    通过 SDK.remember() 写入 resource/kb/{space}/{path}.md
                                    │
                                    ▼
                     OpenViking 抽取管线 → L0/L1/L2 → flat_hybrid 索引
  ```
- **风险与缓解 3 条**：
  - 语雀 API 限流（个人 100 QPH，企业需申请）→ 队列 + 优先级 + 退避
  - 语雀 `lake` 格式（画板/公式）转 Markdown 有损耗 → 保留原始正文用于展示，向量层只索引可转 md 部分
  - 权限撤销延迟 → 敏感空间强制走模式 B 命中后回源鉴权
