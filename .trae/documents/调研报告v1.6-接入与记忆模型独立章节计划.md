# §6 新增 §6.3 接入与记忆模型章节计划（方案 1 合并版）

## 一、需求理解

用户反馈：当前 §6.2.1-6.2.4 把"接入方式"和"记忆模型（记入/存储/召回）"内容嵌在架构图后面，读起来像架构图的附属说明，缺乏独立章节的详细阐述。

**关键决策**：接入通道（Hooks/MCP/SDK）本就是为记忆记入/召回服务的，硬拆两章会反复交叉引用（如 7 Hook 生命周期既属接入也属记入触发）。**合并为一章 §6.3 接入与记忆模型**，按"通道 → 类型 → 记入 → 存储 → 召回"线性组织，符合读者认知顺序。

## 三、§6.3 各节内容简介

### 6.3.1 接入通道

**定位**：回答"Agent 用什么协议与记忆系统通信"。与数据流主干（①→②→③）正交，是 Agent 出站协议选择维度。

- **三通道职责表**：Hooks（生命周期·自动）/ MCP（模型意图·按需）/ SDK（通用编程接入）
- **7 Hook 生命周期时间轴**：SessionStart → UserPromptSubmit(读) → Stop(写) → PreCompact(归档) → SessionEnd → SubagentStart/Stop
- **Agent 接入决策树**：CC/OpenClaw/Hermes/Cursor/Trae/LangChain/自建 各走哪条通道
- **②层观测埋点独特价值**：为什么埋点必须在②层（跨库归因 + token 成本分摊）

**来源**：从 §6.2.1 L745-771（接入方式详细说明）+ §6.2.2 L786-792（接入范式决策树）抽出整合。

### 6.3.2 记忆类型与分类

**定位**：记忆本体的语义分类。

- **官方 5 类**：preferences / events / cases / memories / skills，每类语义与承载内容
- **archive + resources**：会话归档 + 多模态资源/知识规则
- **与知识库归属的映射**：6 类知识库如何承载这些记忆类型（引用 §6.2.3 表格）

**来源**：从 §6.2.3 知识库归属表的"记忆类型"列抽出 + §6.2.1 二期架构图 L723 Memory Extraction。

### 6.3.3 记忆记入模型 ⭐（核心新增）

**定位**：回答"什么场景下、什么时机、用什么方式把记忆记入系统"。通道机制引用 §6.3.1，本节聚焦"记入逻辑"。

**场景 × 时机 × 记入方式框架表**：

| 通道（引用 6.3.1） | 场景 | 时机 | 记入方式 | LLM 介入 | 落地命名空间 |
|---|---|---|---|---|---|
| Hooks（自动） | 每轮对话结束 | Stop Hook 触发 | auto-capture.mjs 解析 transcript → shouldCapture 门禁 → buildParts → Memory Extraction | LLM 5 类分类 + WM v2 7 sections 压缩 | `viking://user/{uid}/memories/` 或 `skills/` |
| MCP（显式） | 模型判断"值得沉淀" | MCP store 调用 | SDK 补 ID/元数据 → 服务端 LLM extraction + Embedding → 生成 L0/L1 | LLM extraction + Embedding | 指定知识库（含 resources） |

**记入流程详解**：
- **自动记入流程**：transcript 解析 → 增量过滤 → sanitize（剥离注入块）→ shouldCapture 门禁（长度/命令/问句/符号/关键词）→ buildParts（text/tool part）→ ②层鉴权路由 → addMessage → 服务端 commit + Memory Extraction + Embedding
- **显式记入流程**：模型判断 → MCP store → ②层授权校验 → SDK 补元数据 → 路由 → 服务端 LLM extraction + Embedding

**来源**：从 §6.2.4 路径 1（Hooks Capture）+ 路径 2（MCP store）抽出记入逻辑 + 新增框架表。

### 6.3.4 记忆存储模型

**定位**：回答"记入的记忆如何分层、压缩、归档存储"。

- **L0/L1/L2 三层结构**：`.abstract.md` / `.overview.md` / 原文，按需加载省 token
- **Working Memory v2 Compression**：LLM Function Calling 按 WM 7 sections 压缩
- **commit/archive 阈值**：
  - commit：pending token ≥20000（COMMIT_TOKEN_THRESHOLD）触发 commit
  - archive：180 天未访问迁 TOS 对象存储（企业侧策略）
  - 官方 session archive 归档 vs 企业侧 180 天规则的差异

**来源**：从 §6.2.1 L723-724（Memory Extraction/WM Compression）+ §6.2.4 路径 1 服务端处理段 + §6.1.2 commit/archive + §6.3 风险表 R2 抽出整合。

### 6.3.5 记忆召回模型

**定位**：回答"需要时怎么把记忆召回注入 Agent 上下文"。通道机制引用 §6.3.1，本节聚焦"召回算法"。

**自动召回 + 显式召回**：

| 通道（引用 6.3.1） | 触发 | 召回范围 | 排序与过滤 | 预算与降级 |
|---|---|---|---|---|
| Hooks（自动） | UserPromptSubmit Hook | 仅 `viking://user/memories` + `skills`（官方安全边界，resources 不参与） | base score + leafBoost + eventBoost + prefBoost + lexicalOverlap → score≥0.35 → 去重 → recallLimit=6 | 2000 token 内注完整内容，超出降级为「URI + 相关度%」；注入 `<openviking-context>` |
| MCP（显式） | 模型判断"6 条不够" → MCP search | 可覆盖 `viking://resources`（路径 3 不搜的范围），跨库联邦 fan-out | 多库结果按相关度+知识库优先级合并 → 去重 → Top-K | 返回 L0/L1 摘要 + 按需 MCP read 加载 L2 |

**召回流程详解**：
- **自动召回流程**：UserPromptSubmit Hook → auto-recall.mjs 拿 prompt → bypass/query<3/offline 跳过 → ②层授权 → 多路检索 → 自动召回边界（仅 user/memories + skills）→ 排序 → score≥0.35 过滤 → recallLimit=6 → 内容解析（L0 优先，fallback L1，必要 L2 截 500 字）→ 2000 token 预算 → 注入 `<openviking-context>` → SDK 发 OTel + Prometheus
- **显式召回流程**：模型调 MCP search → ②层授权 + 读权限校验 → 跨库联邦 fan-out 多实例并行检索 → 各实例两阶段检索（flat_hybrid + doubao-seed-rerank）→ 可覆盖 resources → 合并排序 Top-K → 返回 L0/L1 + 按需 read L2

**来源**：从 §6.2.4 路径 3（Hooks Recall）+ 路径 4（MCP search）抽出召回逻辑 + 新增对比表。

## 五、假设与决策
