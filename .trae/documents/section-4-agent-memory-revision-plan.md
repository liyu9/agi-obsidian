# 第四部分改写计划：Agent 记忆系统定义、能力与 RAG 向量底座

## Summary

本计划仅针对 `cloud-agent-memory-research-report.md` 的第四部分进行结构与叙述视角改写。目标是把当前“能力清单解释/标签辩护”式内容，改为“先定义 Agent 记忆系统，再说明产品形态与能力边界，最后单列 RAG / 向量数据库能力”的章节。

成功标准：第四部分开头能清楚回答“Agent 记忆系统是什么、不是什​​么”；正文能分别回答“记忆系统需要哪些能力、有哪些产品形态、RAG 向量底座需要哪些能力”；叙述不再冗长解释维度来源，而是用产品与社区实践支撑能力框架。

## Current State Analysis

目标文件：`.trae/documents/cloud-agent-memory-research-report.md`

当前第四部分的主要问题：

1. **叙述视角偏向自我解释**  
   当前从“能力清单如何推导”“标签如何判定”切入，读起来像在解释报告为什么这样写，而不是帮助读者理解 Agent 记忆系统应该如何设计。

2. **定义缺位**  
   第四部分直接进入“9 大类、44 项”，但没有先定义 Agent 记忆系统的边界：它与上下文窗口、RAG、向量数据库、知识库、用户偏好存储之间是什么关系。

3. **记忆系统能力与 RAG 底座能力混杂**  
   向量检索、全文检索、混合检索、元数据过滤、Rerank 是 RAG / 向量数据库底座能力；它们支撑记忆召回，但不等同于完整的 Agent 记忆系统能力。

4. **产品形态没有单列**  
   Claude Code / Codex AGENTS.md / Coze / Dify / VikingDB 分别代表不同产品形态：指令文件、Agent 运行时记忆、平台型知识库、向量数据库底座。当前第四部分没有把这些形态先区分开。

5. **标签说明过重**  
   当前 4.0.1-4.0.3 解释维度与标签来源，占比偏高。用户要求的是“梳理第四部分内容”，不是进一步扩写标签论证。

## Assumptions & Decisions

1. **只改第四部分及必要的交叉引用**  
   本次不重写第 5 部分产品调研内容，只复用其研究事实支撑第四部分。

2. **Dify“内置向量库”按 Dify 知识库内置 RAG 流程处理**  
   Dify 官方配置中 `VECTOR_STORE` 可选择 Weaviate、Qdrant、Milvus、Zilliz、MyScale、AnalyticDB、Couchbase、OceanBase、TableStore、Lindorm 等后端。因此这里不把 Dify描述为单一自研向量数据库，而是描述为“内置知识库 / RAG 流程 + 可配置向量存储后端”。

   Claude Code 官方记忆文档、AGENTS.md 官网可作为第四部分“长期上下文、作用域、项目规则文件”的主要依据。

4. **Hermes / OpenClaw 作为社区实践参考，不作为硬证据主轴**  
   若实施时无法找到同等权威的一手资料，第四部分只提炼原则，并标注为社区实践参考，避免过度断言。

5. **RAG / 向量库能力必须从记忆系统能力中拆出**
