## 一、规划设计模式 (Planning Workflows)

### 核心思想

类比复杂软件系统中的设计模式（如工厂模式、单例模式），**规划模式**使Agent能够自主决策复杂任务的执行流程，无需预先硬编码工具调用顺序。

### 真实案例：客服助理Agent

**目标**：构建能处理广泛、复杂查询的智能体（如回答"库存中售价低于100美元的圆形太阳眼镜"）

**方法**：
1. **提供工具集**：

| 工具名 | 功能说明 |
|--------|----------|
| `get_item_descriptions` | 获取商品描述/元数据 |
| `get_item_price` | 查询商品价格 |
| `check_inventory` | 检查库存状态 |
| `check_past_transactions` | 查看用户历史交易记录 |
| `process_item_sale` | 执行购买交易 |
| `process_item_return` | 处理退货操作 |

2. **LLM生成计划**：根据用户请求，LLM制定逐步执行计划
3. **逐步执行**：按计划依次调用工具
4. **最终输出**：整合所有步骤结果

![客服助理Agent](../images/5.1.1.png)

### 优势与风险

**优势**：
- 扩展性强：Agent能处理更广泛的任务
- 灵活性高：无需预先固定工具调用顺序

**风险**：
- 不可预测性：LLM生成的计划可能不稳定或越权
- 适用场景局限：目前在AI Coding领域较成功，其他领域仍处于探索阶段

## 二、创建与执行LLM计划 (Creating and Executing LLM Plans)

### 结构化输出的重要性

在规划模式中，如何利用**结构化输出**来保证 LLM 生成的计划能够被下游代码可靠地执行，是非常重要的。

自然语言不够清晰和明确，难以被下游代码稳定地解析和执行。所以需要LLM以**结构化格式（如 JSON 或 XML）**输出计划。

### 结构化格式的优势

- 清楚界定计划的步骤、所需工具及其参数
- 允许下游代码更可靠地解析 (parse) 计划的每个步骤
- 系统性地、一步一步地执行

### JSON 计划格式示例

LLM 返回一个 JSON 列表，每个对象代表一个步骤：

```json
{
  "description": "步骤描述",
  "tool": "要调用的工具名称",
  "arguments": {"参数": "值"}
}
```

## 三、结合代码执行的规划 (Planning with Code Execution)

### 为什么用代码代替JSON？

与其让 LLM 输出 JSON 等结构化数据来表示计划，不如直接让 LLM 直接编写软件代码来的效果更好。LLM可以直接用代码来表达计划的多个步骤和工具调用。

> 许多论文也表示，同样的工具与参数，让LLM直接编写代码的任务评估分数通常明显大于编写JSON而后解析。

### 代码执行的优势

- **利用大型库**：LLM得以利用像 Pandas 这样的数据处理库中数百甚至数千个内置函数
- **高表达能力**：LLM能够编写简洁的代码来表达复杂逻辑的计划
- **性能更优**：研究表明，在许多任务中，让 LLM 编写代码来采取行动的性能**优于**让它编写 JSON 或纯文本计划

![结合代码执行的规划](../images/5.3.1.png)

### 安全问题

直接运行 LLM 生成的代码存在安全风险，需要考虑使用**沙箱 (Sandbox)** 等安全执行环境。

## 四、多智能体工作流 (Multi-agentic Workflows)

### 为什么需要多智能体？

将复杂任务**分解**成多个**独立的角色**或**进程**是一种更有效的开发方法，就像团队协作或计算机的多线程/多进程一样。

把一个Agent拆成很多次级Agent，并构成一个多Agent系统，就十分有必要了。多个承担不同任务的Agent可以靠互相协作来解决复杂的任务。

### 多智能体系统的优势

- **任务分解**：像人类团队一样，将复杂任务分解为拥有不同角色和技能的子任务
- **专注性**：单个Agent的任务越简单，任务完成的效果就越好
- **模块化与复用**：有机会创建可复用于其他应用的通用智能体

### 突破限制

- **上下文限制**：每个Agent只负责自己的部分，最终只返回结果，就能规避上下文限制
- **节约成本**：每个Agent上下文都比较短，更节约Tokens费用；多个Agent还能并行处理任务

## 五、多智能体系统的通信模式 (Communication Patterns)

当一个团队一起工作时，沟通模式可能会非常复杂。类似地，设计多智能体系统的通信模式也同样复杂。

### 四种协作模式

#### 1. 线性模式 (Linear)
- 每个人只和下一个环节沟通
- **优点**：结构简单、易于理解
- **缺点**：不灵活，出错时难以反馈或修正

#### 2. 双层模式 (Hierarchical)
- 有一个"管理员（Manager Agent）"负责协调所有下属Agent
- **优点**：清晰、易于控制、任务协调性强
- **缺点**：可能成为瓶颈（manager负担重）

![双层模式](../images/5.7.1.png)

#### 3. 多层模式 (Deep Hierarchy)
- 子Agent自己也拥有下属Agent
- **优点**：可扩展、模块化、可分层调度
- **缺点**：通信复杂、难以调试

![多层模式](../images/5.7.2.png)

#### 4. 去中心模式 (All-to-all)
- 每个Agent都能随时与其他Agent交流，没有中心
- **优点**：高度去中心化、非常灵活、创意性强
- **缺点**：难以预测结果

![去中心模式](../images/5.7.3.png)

### 模式总结

| 模式类型 | 结构特征 | 优点 | 缺点 | 适用场景 |
|----------|----------|------|------|----------|
| 线性 | 顺序执行，单向通信 | 简单 | 不灵活 | 固定流程任务 |
| 双层 | 中心协调 | 易控制 | 管理负担 | 多任务协调 |
| 多层 | 子Agent层次化 | 模块化 | 复杂 | 大型系统 |
| 去中心 | 自由对话 | 创造性强 | 不可预测 | 探索型任务 |

### 实际应用

- **langchain**：忠实的线性结构
- **smolagents**：更青睐于双层/多层结构
- **metagpt、camelai**：致力于去中心结构

## 六、课程总结

课程回顾：
- **Agentic AI 能实现**以往无法做到的应用场景
- **关键设计模式**：反思（Reflection）与工具调用（Tool Use）

- **更高级模式**：规划（Planning）与多智能体系统

**核心目标**：掌握构建创新的 Agentic AI 应用，提升职业竞争力，并负责任地运用这些知识。

## 七、学习建议

如果某项技术能低成本而平滑地提高生产力，就一定能大行其道。

**在学习大模型时，应该学习的是大模型技术背后那些有迁移性的思想**：
- 对复杂系统的编排拆分
- 项目中的工程与科研思维
- 从平滑迁移到打碎繁琐旧系统，用新技术的特点重建新系统的经验
- 对各类业务系统的底层逻辑总结

同时，在大模型领域深耕与发散的过程中，也要时刻留意新兴技术的萌芽——**技术不是常青树，但持续掌握新技术的人可以是**。
