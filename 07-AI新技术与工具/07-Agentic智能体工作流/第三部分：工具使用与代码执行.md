## 一、什么是工具使用

**核心思想**：模型拥有自主决策权，不再被动根据内部知识库生成答案，而是主动判断是否需要调用工具来完成任务。

**关键比喻**：
- 人类借助锤子、扳手等工具能完成徒手无法做到的事情
- 语言模型通过调用"函数工具"，能突破自身训练数据和能力的限制

## 二、简单工具执行流程

### 案例："现在几点？"

1. **用户提问**："What time is it?"
2. **模型决策**：LLM意识到无法提供实时时间，决定调用 `get_current_time()` 工具
3. **工具执行**：系统执行函数，返回 `15:20:45`
4. **结果反馈**：时间值作为新上下文回传给LLM
5. **最终输出**："It's 3:20pm."

![简单工具执行流程](../images/3.1.1.png)

### 何时调用，何时不调用？

| 调用工具 | 不调用工具 |
|----------|------------|
| "现在几点？" → 需要实时数据 | "绿茶含多少咖啡因？" → 可基于内部知识回答 |

## 三、多工具协作

### 案例：日历助理

**用户请求**："请在周四我的日历中找一个空闲时段，并与Alice预约。"

**工具集**：
- `check_calendar()`：查询日历，返回空闲时段
- `make_appointment()`：创建预约
- `delete_appointment()`：取消预约

**执行流程**：
1. 调用 `check_calendar()` → "Thursday, 3pm; Thursday, 4pm; Thursday, 6pm"
2. 决定选择"3pm"
3. 调用 `make_appointment(time="3pm", with="Alice")`
4. 返回确认："Meeting created successfully!"
5. 回复用户："Your appointment is set up with Alice at 3 PM Thursday."

## 四、工具使用的标准流程

### 两种实现方法对比

| 特性 | 早期方法（手动提示工程） | 现代方法 |
|------|--------------------------|----------|
| **原理** | 通过系统提示词硬性规定精确文本格式 | LLM已接受训练，能原生理解工具描述 |
| **提示词要求** | 需精确编写触发语法 | 只需提供工具的功能描述 |
| **开发者工作** | 需编写复杂的解析代码 | 流程更自动化 |

### 四步循环流程

1. **提供工具**：开发者编写功能函数
2. **告知模型**：通过系统提示词告知LLM有哪些工具可用
3. **解析并执行**：代码监听LLM输出，解析请求并执行函数
4. **反馈结果**：将执行结果作为新上下文回传给LLM

### 关键比喻

> "就像你不能直接命令一个只会说话的人去帮你买咖啡，但你可以告诉他：'如果你想去买咖啡，请说我要买一杯美式。'然后你听到这句话后，自己去帮他买。"

## 五、工具语法与实现

### AI Suite 库

Andrew Ng团队开发的库，提供统一语法调用多LLM提供商，自动处理工具描述。

```python
import aisuite as ai

client = ai.Client()
response = client.chat.completions.create(
    model="openai:gpt-4o",
    messages=messages,
    tools=[get_current_time],
    max_turns=5  # 最大调用轮次，防无限循环
)
```

### 自动化工具描述

AI Suite自动将Python函数转换为JSON Schema：

```json
{
  "type": "function",
  "function": {
    "name": "get_current_time",
    "description": "Returns the current time as a string",
    "parameters": {}
  }
}
```

## 六、代码执行

### 核心概念

代码执行是让LLM编写并运行代码来解决任务。

**核心优势**：
- **强大能力**：LLM生成的代码方案通常聪明且有效
- **灵活性**：相比为每个功能手动创建工具，让模型自行编写代码更具扩展性
- **性能优化**：许多LLM训练者会专门优化模型的代码执行能力

### 示例：简单计算器

#### 传统方法：预定义工具集
- 预定义工具（如 `add`、`subtract`）
- 局限性：无法灵活应对新需求（如计算平方根）

#### 替代方案：让模型自己写代码

1. **系统提示词**：要求模型用Python代码解决问题，用 `<execute_python>` 标签包裹代码
2. **模型输出**：如 `import math; print(math.sqrt(2))`
3. **提取与执行**：使用正则表达式提取代码，在沙盒中执行
4. **结果反馈**：LLM将执行结果格式化为自然语言答案

### 进阶：带外部反馈的反思

1. 模型生成代码
2. 若执行失败（如语法错误），将错误信息反馈给模型
3. 模型根据错误反思并生成改进版代码

### 安全考量

**风险**：直接执行模型生成的代码可能导致数据丢失

**最佳实践**：
- 必须使用沙盒环境（如Docker、E2B）
- 隔离代码以防止系统损坏
- 避免在非沙盒环境中运行任意代码

## 七、MCP（模型上下文协议）

### 定义

MCP（Model Context Protocol）由Entropy提出，旨在为LLM提供标准化的方式访问外部工具和数据源。

### 问题与解决方案

**传统开发模式的问题**：
- 开发者A构建App1，需要集成Slack、Google Drive、GitHub
- 开发者B构建App2，同样需要集成这些工具
- 每个应用都必须独立编写封装代码
- 工作量：`m × n`（m个应用 × n个工具）

**MCP的解决方案**：
- 引入共享服务器
- 只需开发n个MCP服务器
- 工作量降低到 `m + n`

![MCP问题与解决](../images/3.7.1.png)

### MCP核心组件

| 组件 | 角色 | 示例 |
|------|------|------|
| **客户端** | 应用程序 | Cursor, Claude Desktop, Windsurf |
| **服务器** | 提供工具和数据源 | Slack, Google Drive, GitHub, PostgreSQL |

![MCP核心组件](../images/3.7.2.png)

### 实际演示：Claude Desktop使用GitHub MCP服务器

1. 用户输入："总结该GitHub仓库的README文件内容"
2. Claude Desktop向GitHub MCP服务器发送请求
3. 服务器执行请求，从仓库下载文件内容
4. 服务器将内容返回给Claude Desktop
5. LLM生成简洁格式的摘要

## 八、核心价值总结

| 价值 | 说明 |
|------|------|
| **超越知识边界** | 获取实时数据、访问数据库、执行计算 |
| **实现复杂逻辑** | 支持多步推理和工具链协作 |
| **提升应用价值** | 餐厅推荐、零售分析、日程管理等变得更实用 |
| **代码执行** | 智能体应用的核心能力，扩展模型的问题解决范围 |
| **行业趋势** | 推广MCP标准以简化工具集成 |
