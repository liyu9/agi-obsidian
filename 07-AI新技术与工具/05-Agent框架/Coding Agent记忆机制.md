# Coding Agent 记忆机制

记忆机制允许 Coding Agent 在多个任务和会话之间保存上下文信息，从而减少重复输入并提升任务执行效率。通过合理的记忆设计，Agent 可以持续理解项目结构、开发规范和用户偏好，并在后续任务中自动复用这些信息。在 Coding Agent 系统中，记忆通常分为自动记忆、项目记忆和会话记忆等不同层级。

## 为什么 Coding Agent 需要记忆机制？

传统的大模型在每次调用时不会保留之前的状态，因此存在无法跨会话记住项目背景、无法积累解决问题的经验、无法持续学习用户偏好等问题。Agent 系统通过**外部记忆（External Memory）**解决这一问题。典型架构如下：

```
User input
   ↓
Memory retrieval
   ↓
Context assembly
   ↓
LLM reasoning
   ↓
Action / tool call
   ↓
Memory update
```

也就是说：Agent 在执行任务前会检索记忆，在任务结束后更新记忆。这种架构是现代 Agent 系统（LangGraph、AutoGPT、Devin 等）的常见设计。

## 现代 Coding Agent 的完整记忆架构

在架构上，一个完整的 Agent Memory Architecture 通常如下：

```
Short-term memory
    ↓
Session context

Long-term memory
    ├ semantic memory
    ├ episodic memory
    └ procedural memory
```

## Coding Agent 的主要记忆类型

### Session Memory（会话记忆）

- 当前任务中的上下文信息，包括当前对话历史、最近工具调用结果、当前执行计划、当前文件内容。
- 特点：生命周期仅为单个会话、容量受上下文限制、不会长期保存。
- 示例：
  ```
  User: 修复这个 Python bug
  Agent: 分析错误
  Agent: 修改代码
  Agent: 运行测试
  ```

### Project Memory（项目记忆）

- 保存整个代码仓库的长期信息，例如项目架构、编码规范、构建流程、常用命令等。
- 这类信息通常写入 `.md` 文件并在会话开始时加载。
- 示例目录结构：
  ```
  your-project/
  ├── .claude/
  │   ├── CLAUDE.md           # 主项目指令
  │   └── rules/
  │       ├── code-style.md   # 代码样式指南
  │       ├── testing.md      # 测试约定
  │       └── security.md     # 安全要求
  ```

### Semantic Memory（语义记忆）

- 保存知识和事实信息，例如：API 文档、编程语言规则、项目知识库。
- 通常通过 **RAG（检索增强生成）** 实现，流程如下：
  ```
  query
  ↓
  embedding
  ↓
  vector search
  ↓
  retrieve documents
  ↓
  LLM reasoning
  ```

### Episodic Memory（情景记忆）

- 记录 Agent 的历史经验，例如：上次 bug 修复步骤、上次构建失败原因、成功的调试策略。
- 帮助 Agent 从过去经验中学习。
- 示例：
  ```
  Episode:
  CI failure caused by missing dependency
  Solution: upgrade pip package
  ```

### Procedural Memory（程序记忆）

- 记录如何完成任务的策略或流程。
- 示例：
  ```
  Debug_Workflow.md
  1. read error log
  2. locate file
  3. write patch
  4. run tests
  ```
- 通常用于系统提示词工程，工作流模版，agent策略。

## Coding Agent 使用记忆机制的固定范式

在实际工程中，Agent 使用记忆通常遵循固定流程：

1. **记忆检索**：在任务开始前，Agent 会检索项目记忆，知识库，历史经验并注入到上下文中。
2. **上下文构建**：检索到的记忆会被拼接成完整上下文，然后输入到模型。
3. **记忆更新**：任务完成后，Agent 会决定是否写入新记忆，例如：新的项目规则、新的调试经验、用户偏好……

## 如何正确使用 Coding Agent 的记忆机制

主流 Agent 系统中的记忆机制通常具有**分层、可控、可检索、可更新**等特点。一般而言，系统会将记忆划分为**短期记忆**与**长期记忆**两类：短期记忆主要用于保存当前线程或会话中的状态信息，而长期记忆则需要通过显式文件、规则配置、向量检索或其他持久化存储机制进行维护。

有效的方式是建立清晰的记忆管理范式，例如：哪些信息应写入项目级记忆文件，哪些信息适合通过知识库或向量检索获取，哪些信息只需保留在当前会话中，以及在任务结束后哪些内容值得沉淀为长期记忆。

### 区分指令型记忆与学习型记忆

- **指令型记忆**: 由人来写，目的是告诉 Agent "应该如何做事"。内容包括编码规范、目录约定、构建命令、测试流程、命名风格、提交要求、团队安全规则等。（例如 Claude Code 的 `CLAUDE.md`）
- **学习型记忆**: 由 Agent 在执行过程中，从用户的纠正、偏好、失败经验、常见命令和项目习惯中逐步积累。（例如 Claude Code 的"自动记忆"）

**合理做法：**
- 将**规范、制度与行为约束**写入**指令型记忆**，用于稳定约束 Agent 的行为。
- 将**经验、用户偏好、临时发现以及复盘结论**写入**学习型记忆**，用于在后续任务中持续改进决策。

### 分层管理

#### 组织级记忆
- 团队或公司统一下发的规则，适用于所有开发者和所有相关项目。
- 内容：安全与合规要求、代码审查底线、敏感目录不可读写规则、依赖和许可证约束、公司级工程规范。
- 应被视为最高优先级、不可随意绕过的治理层。

#### 项目级记忆
- 团队共享的项目上下文，是 Coding Agent 最核心的记忆层。由版本控制管理。
- 内容：项目架构说明、目录结构约定、构建和测试命令、API 放置路径、命名约定、常见开发流程。
- 必须是项目共享、版本控制、稳定长期存在的。

#### 用户级记忆
- 个人在所有项目中通用的偏好。适用于所有项目，但项目规则优先级更高。
- 内容：偏好的代码风格、常用的调试顺序、喜欢的输出格式、个人的工作流快捷方式。
- 不应覆盖项目共识，只应补充个人习惯。

#### 本地级记忆
- 只对当前项目副本有效，但不该进 Git 的内容。
- 内容：个人测试账号、本地开发端口、临时 mock 服务地址、当前机器上的运行注意事项、尚未准备共享的实验性流程。
- 允许个人高效工作，同时不污染团队共享记忆。

#### 子代理 / 角色级记忆
- 不同 subagent（如测试代理、代码审查代理）可以有自己的独立记忆目录。
- 好处：记忆更短、更准、更稳定，避免上下文互相污染。

### 按路径加载 .md 文件

对于大型项目，建议将规则拆分到 `.claude/rules/` 目录下的多个 Markdown 文件中，每个文件只关注一个主题。规则可以根据**文件路径或子目录进行范围限定**，只有在处理匹配路径的文件时，对应规则才会被加载。

**建议的目录结构：**
```
agent-memory/
├── project.md            # 项目总说明
├── rules/
│   ├── code-style.md     # 代码风格
│   ├── testing.md        # 测试约定
│   ├── api-design.md     # API 设计规范
│   ├── security.md       # 安全要求
│   └── frontend/
│       └── react.md      # 前端专项规范
└── local/
    └── developer.local.md
```

**好处：**
1. 便于维护（每个规则文件覆盖一个主题）。
2. 便于按需加载（减少上下文噪音）。
3. 便于团队协作（不同小组可维护自己的规则）。

### 记忆写法要具体

编写 Agent 记忆时，应尽量使用**具体、可验证的规则**，而不是抽象的原则。

- **不推荐**：保持代码整洁、做好测试、注意 API 设计、适当拆分模块。
- **推荐**：
  - 所有新增 TypeScript 文件使用 2 空格缩进。
  - 修改业务逻辑后必须运行 `pnpm test`。
  - API handler 统一放在 `src/api/handlers/`。
  - React 页面组件不超过 300 行，超过则拆分为 hooks 或子组件。

**一般建议：**
- 指令表达简洁、明确。
- 规则之间保持一致性。
- 主记忆文件最好控制在 200 行以内。
- 使用 Markdown 标题与列表结构提升可读性。
- 尽量将要求写成可检查、可执行的规则。

### 将共享规则与个人偏好分开

按作用域进行分层：
- **项目级（Project）**：所有团队成员共享，版本控制维护。
- **组织级（Organization）**：由 IT 或 DevOps 统一制定。
- **用户级（User）**：仅对个人生效。
- **本地级（Local）**：只适用于当前机器或当前工作环境。
- **角色级（Role / Agent-specific）**：仅供某类专用 Agent 使用。

**核心原则：** 谁负责、谁共享、谁生效。

### 通过导入机制与规则包实现复用

可以在记忆文件中使用导入机制（如 `@path/to/import`）或符号链接来共享规则，构建**可复用的规则包**（如 `company-security-rules`, `frontend-react-rules`）。

**好处：**
1. 规则可以集中维护与统一更新。
2. 不同项目共享相同的工程语言，使 Agent 行为更加一致。

## 记忆故障排除

### Coding Agent 没有遵循我的 `.md` 记忆文件

- `.md` 文件是上下文提示，非强制配置。
- **排查步骤：**
  1. 运行 `/memory`（或等效命令）确认文件是否被加载。
  2. 检查文件是否位于允许加载的路径。
  3. 检查是否存在多个文件间的规则冲突。

### 我不知道自动记忆保存了什么

- 大多数 Coding Agent 会在后台维护自动记忆。
- **查看方式：**
  - 运行 `/memory`（或类似命令）查看当前自动记忆目录。
  - 自动记忆通常以 Markdown 文件形式存储，可直接阅读、修改或删除。

### 我的记忆文件太大

- 过大的文件会占用上下文窗口、降低规则遵循度。
- **解决方案：**
  - 将详细说明拆分为多个 Markdown 文件。
  - 使用文件引用或导入机制。
  - 将规则拆分到专门的规则目录中。

### 指令在上下文压缩后消失

- 长对话中会执行上下文压缩或摘要。
- **解决方法：**
  - 将长期需要的指令**写入 `.md` 记忆文件**。
  - 不要只在对话中说明规则。
