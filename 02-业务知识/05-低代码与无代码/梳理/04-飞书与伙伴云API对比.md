# 飞书多维表格与伙伴云 API 筛选逻辑对比

> 来源：飞书与伙伴云API筛选逻辑对比研究报告.md

---

## 一、两大平台设计哲学

| 维度 | 飞书多维表格 | 伙伴云 |
|------|------------|--------|
| 设计理念 | 简洁优先 | 功能完备 |
| 范式 | 声明式：开发者描述"想要什么数据" | 独立对象：筛选器作为独立对象可复用 |
| 抽象 | filter 内嵌于请求参数 | 筛选器对象独立，可嵌套 |
| 目标用户 | 业务人员+轻量级开发者 | 技术团队+企业级应用 |
| 学习曲线 | 平缓 | 较陡 |

---

## 二、筛选参数结构

### 2.1 飞书多维表格

采用 JSON 格式的 filter 对象，三层架构：

| 字段 | 说明 |
|------|------|
| **conjunction** | 顶层逻辑连接词（"and" / "or"） |
| **conditions** | 条件列表（field_name + operator + value） |
| **children** | 嵌套条件组（仅支持一层） |

> 优点：将筛选逻辑从客户端下沉到服务端，"计算向数据靠拢"，利用服务端数据库优化能力

### 2.2 伙伴云

采用"筛选器（Filter）对象"独立设计：

| 层级 | 元素 | 说明 |
|------|------|------|
| 最小单位 | 筛选项 | field（字段ID/系统字段）+ query（条件） |
| 中间层 | 筛选逻辑 | and / or 组合多个筛选项或嵌套 |
| 顶层 | 筛选器 | 二叉树结构，任意深度嵌套 |

> 优点：可在多个API接口之间复用，理论上可表达任意复杂布尔逻辑

## 三、运算符对比

### 3.1 飞书运算符（完整单词）

| 类别 | 运算符 |
|------|--------|
| 等值比较 | is, isNot |
| 大小比较 | isGreater, isGreaterEqual, isLess, isLessEqual |
| 文本 | contains, doesNotContain |
| 空值 | isEmpty, isNotEmpty |
| 预留未支持 | like, in |

### 3.2 伙伴云运算符（缩写形式）

| 类别 | 运算符 |
|------|--------|
| 基础比较 | eq, ne |
| 大小比较 | gt, gte, lt, lte |
| 集合 | in, nin |
| 空值 | em |
| 用户字段特殊 | myself 变量（"我的数据"） |
| 时间变量 | today, yesterday, tomorrow, last_week, last_month, this_whole_month 等 |

> 缩写优点：减少请求数据量，JSON结构更紧凑
> 缩写缺点：可读性不如完整单词，初次接触需查文档

## 四、动态时间能力对比

| 平台 | 方式 | 典型语法 |
|------|------|---------|
| 飞书 | TODAY() 等日期函数 | 通过TODATE()转换字符串日期 |
| 伙伴云 | 预定义动态时间变量 | `"gte": "last_month"` 筛"上个月至今" |

**伙伴云案例：** `"gte": "last_month"` 即可筛选"创建时间在上个月至今"，无需客户端计算具体时间范围。

## 五、分页机制对比

| 维度 | 飞书多维表格 | 伙伴云 |
|------|------------|--------|
| 方式 | 游标分页（Cursor-based） | 偏移分页（Offset/Limit） |
| 参数 | page_token + page_size | offset + limit |
| 优势 | 深层翻页性能稳定（基于游标） | 支持跳页访问 |
| 劣势 | 不支持跳页 | offset大时性能衰减 |
| 单次上限 | 500条 | — |

**性能数据：**
- 飞书 1万条全量拉取：1.2秒、8.4MB
- 飞书 10万条全量拉取：8.7秒、92MB、内存1.1GB
- 飞书 50万条 → 超时风险

## 六、视图（view_id）优化

两个平台都提供视图，本质是预过滤和预排序的配置。

| 优势 | 说明 |
|------|------|
| 预计算+缓存 | 创建视图时建立索引/缓存 |
| 性能提升 | 百万级数据查询比全表扫描快 **3-5倍** |
| API 简化 | 无需每次构造复杂filter参数 |

> 建议：将高频访问的数据筛选需求抽象为视图。

## 七、批量与特色能力

### 7.1 伙伴云

- **批量检查接口**：`/item/table/:table_id/check` —— 执行批量操作前预检权限
- **批量删除**：直接支持筛选条件，无需先查询再删除
- **myself 变量**：用户字段筛"我的数据"无需拼接用户ID

### 7.2 飞书

- **筛选率优势**：10万条数据、10%筛选率，服务端筛选性能约为全量拉取的 **1/10**

## 八、大规模数据集处理策略

### 8.1 全量拉取的局限

1万→10万→50万条数据，耗时、流量、内存呈指数级恶化。**核心问题：超过90%的网络带宽和计算资源被浪费在无效数据上。**

### 8.2 三大优化策略

| 策略 | 原理 | 收益 |
|------|------|------|
| **服务端筛选** | 在数据库层完成数据过滤 | 性能提升约10倍 |
| **视图优化** | 预计算+缓存 | 性能提升3-5倍 |
| **增量同步** | 时间戳/版本号/变更日志 | O(N) → O(ΔN) |

### 8.3 增量同步组件

- 状态存储（记录上次同步的时间点/版本号）
- 变更检测（根据状态过滤变更数据）
- 数据处理（处理变更数据并更新目标系统）
- 状态更新（更新同步状态为本次同步完成）

### 8.4 飞书 API 限制

| 限制 | 数值 |
|------|------|
| 单应用请求频率 | 20次/秒 |
| 认证 token 有效期 | 2小时 |
| 单次 page_size 上限 | 500条 |

## 九、技术考量

### 9.1 系统架构差异

| 平台 | 可能架构 | 设计影响 |
|------|---------|---------|
| 飞书 | 分布式表格系统（类Google Spanner） | 强调高可用性+全球一致性，简洁语法降低客户端解析复杂度 |
| 伙伴云 | 偏向传统云数据库架构 | 强表达能力，动态时间变量等高级功能需要数据库函数支持 |

### 9.2 性能优化层次

- **查询计划层**：条件重排、索引利用、提前计算
- **索引策略**：按时间/状态/人员建索引，权衡索引数量与写入性能
- **缓存策略**：飞书视图机制本身提供缓存，伙伴云需开发者自行实现客户端缓存

## 十、选型建议

### 10.1 选型决策树

| 业务场景 | 推荐平台 | 理由 |
|---------|---------|------|
| 中小规模（<5万条）+ 简单筛选 + 协同办公 | **飞书多维表格** | 简洁API，开发维护成本低 |
| 大规模（5万+）+ 复杂筛选 + 企业级 | **伙伴云** | 强大筛选能力，灵活逻辑组合 |
| 高频查询固定数据子集 | **两者皆可+视图** | 视图都能提供显著性能优化 |
| 超大规模数据定期同步 | **两者皆可+增量同步** | 高效完成百万级数据同步 |

### 10.2 最佳实践

**筛选条件构造：**
- 优先将高选择性条件放在前面
- 使用 AND 逻辑减少候选集
- 避免在筛选条件中进行复杂计算
- 使用视图替代重复的筛选条件组合

**分页处理：**
- 使用服务端筛选减少单次查询数据量
- 飞书建议单次不超过 500 条
- 实现断点续传机制

**错误处理：**
- 实现重试机制处理网络异常和限流
- 实现 token 自动刷新（飞书 2 小时有效期）
- 详细日志记录便于问题排查

**性能监控：**
- 监控 API 调用的响应时间和错误率
- 关注服务端筛选的命中率（返回记录数/查询记录数）
- 跟踪网络流量和内存使用情况
