# 核心方法论与产品设计

> 来源：低代码平台产品认知总览.md、PM书籍/决胜B端

## 一、平台三阶段发展模型

| 阶段 | 周期 | 核心目标 | 关键动作 |
|------|------|---------|---------|
| **MVP阶段** | 3-6个月 | 快速试错、快速闭环 | 最小可用版本上线，获取天使用户反馈 |
| **成熟期** | 12-18个月 | 发展通用能力 | 任何需求按最通用情形考虑，资源集中通用能力 |
| **超越期** | 长期 | 场景化超越Pro Code | 各场景针对性优化，全面超越传统编码模式 |

### 1.1 成熟期核心原则

1. **对任何业务需求，按最通用情形来考虑** —— 即使对方只要一棵树，仍按一座森林考量，但不一定实际交付整座森林
2. **充分考虑已知场景的共同特征**，暂时忽略个性化特征
3. **能用已有功能实现的，决不新增功能**；稍微扩展就能实现的，也决不新增功能
4. **放低姿态**，注重培育与应用团队的关系，主动协助解决问题

### 1.2 兜底策略

当业务需求超出平台能力边界时，允许回退到 Pro Code 模式继续开发：
- 回退过程需自然、内聚
- 通用场景在超越期可华丽转职为兜底策略的一部分
- 前提：编译器（代码生成器）与编辑器保持松耦合

## 二、基础设施

### 2.1 Web 组件集（最重要的基础设施）

组件集贯穿三大环节：构筑编辑器自身、构筑编辑器的开发能力、构筑业务应用。

**选型三要素（按优先级）：**

| 优先级 | 要素 | 要求 |
|--------|------|------|
| 1 | 自主可控 | 自研或可改源码，不能将研发进度绑在不可控的开源社区上 |
| 2 | 封装程度高 | 数据驱动模式，彻底封装HTML/CSS，只暴露属性API |
| 3 | 功能强大 | 50+组件、气泡化能力、表单友好、性能承载200+活动组件 |

**组件封装模式对比：**

| 封装方式 | 适合场景 | 对编辑器友好度 |
|---------|---------|--------------|
| 数据驱动 | 低代码编辑器 | 极高——所有配置通过属性API，代码生成器只需生成变量 |
| 模板驱动 | Pro Code模式 | 低——HTML模板暴露过多细节 |
| CSS样式模板 | 轻量规范 | 极低——仅提供样式，不封装行为 |

### 2.2 UX 设计规范

- 有了一定规模的应用后，必然已有自己的UX规范
- 若从零开始，可采纳成熟规范：Ant Design、Material Design、ArcoDesign
- UX 规范影响组件集、编辑器、业务应用的全局外观

## 三、核心编辑器能力

### 3.1 布局编辑器

- 支持网格布局、自由布局等多种模式
- 不同场景下效率差异大：网格布局在精细化UI中效率高，表单布局中效率低
- 通用型平台需同时兼顾多种布局需求

### 3.2 属性编辑器

- 解决 Web 组件属性与编辑器的耦合
- 采用松耦合架构，组件通过声明式方式提供属性元数据
- 编辑器根据元数据动态生成配置界面

### 3.3 可视化编程

- 编排前后端交互逻辑
- 可视化编程是可视化开发中最难的一个环节
- 业务技术人员对可视化编排依赖度更高

### 3.4 所见即所得

- 每次操作后即时显示最终效果
- 快速迭代，降低试错成本
- 对业务技术人员至关重要——无需等待构建预览

## 四、代码生成器

### 4.1 编译器与编辑器的关系

- 必须保持松耦合，否则长期演进和插件扩展严重受限
- 编译器是编辑器的下游，编辑器产出结构化数据，编译器将其转为代码

### 4.2 代码生成质量

- 100% 框架性代码自动生成（与业务无直接关系，最难开发的部分）
- 开发者只需填写表达式或少量复杂业务逻辑代码
- 生成代码需人类可读、可改、可维护

---

## 五、数据能力

### 5.1 业务数据获取

- 内置多种数据获取通道：服务端API、本地数据、WebSocket等
- 获取组件个性化数据时需与平台松耦合

### 5.2 存量系统对接

- 低代码平台不是企业第一个系统，必然需要对接存量
- 通过插件机制对接已有系统，处理好数据模型差异
- **优先发展"被集成"能力** —— 低代码平台一般作为子系统被集成

---

## 六、协同与版本管理

- **多人协同编辑**：业务复杂度上升后改造代价极大
- **编辑历史**：提供可回溯的编辑历史，支持分支管理
- **降低非技术人员使用Git的门槛**

## 七、全生命周期覆盖

### 7.1 水平研发线（按优先级排序）

| 环节 | 能力 | 说明 |
|------|------|------|
| 需求端-D2C | UX设计稿转代码 | 识别组件类型+位置+尺寸，喂给编译器自动生成代码 |
| 需求端-模板 | 可视化脚手架 | 丰富的所见即所得模板和业务组件，降低"空白画布恐惧" |
| 开发端 | 可视化+代码双模式 | Low Code与Pro Code混合开发 |
| 交付端-测试 | 自动化测试生成 | 利用平台对App结构和交互的了解，自动生成和维护测试用例 |
| 交付端-埋点 | 数据采集分析 | 自动化植入埋点，自动收集用户行为数据 |

### 7.2 垂直管理线（优先级较低）

| 环节 | 能力 |
|------|------|
| 运维 | 自动部署、灰度发布、紧急回退 |
| 资产 | 代码托管、版本管理 |

### 7.3 面向业务技术人员的策略

- **D2C 优先级低于模板** —— 模板是可视化脚手架，对业务技术人员破冰效果更好
- **自动化测试** —— 业务技术人员最缺的就是测试能力，自动生成测试用例价值巨大
- **代码托管** —— 屏蔽Git专业操作，降低非技术人员的使用门槛

## 八、插件系统与生态

### 8.1 插件系统的价值

- **插件极其廉价**：开发成本低、数量可以庞大、试错成本低
- **解决通用型弊端**：弥补通用平台在特定场景的效率损耗
- **应用团队可参与**：自己为自己量身定做插件，大幅提升效率

### 8.2 核心扩展点

| 扩展点 | 应用场景 | 对业务技术人员的价值 |
|--------|---------|-------------------|
| 数据与数据模型 | 对接存量系统、异构数据源 | 无需理解底层数据协议，插件封装好直接使用 |
| 自定义组件 | 业务特色UI、领域专用展示 | 在那一亩三分地里效率极高 |
| 自定义交互动作 | 封装复杂逻辑、场景化归纳 | 将复杂API归纳为预设场景，只填几个参数即可 |

### 8.3 SDK 设计要素

- 接口和类型定义 —— 勾勒插件系统的轮廓和概貌
- 基类定义 —— 只留尽可能少的抽象方法给二次开发者
- 调试工具和构建部署脚本 —— 没有这些二次开发无法继续
- 辅助性工具类 —— 降本增效

### 8.4 插件生命周期

上传 → 静态校验 → 安装 → 激活 → 使用 → 去激活 → 更新 → 卸载

### 8.5 生态圈

- 依托插件系统连通存量系统，打通数据
- 数据与数据、人与数据、人与人之间形成增强回路
- 低代码平台实际上起到中台的作用
- **生态圈不是刻意打造的，而是插件系统务实运作的自然产物**

## 九、AI 与大模型融合

### 9.1 不可能三角

```
        开发效率
        /     \
   易用性 ——————— 可定制化
```

三者最多只能得其二。功能越强大→编辑器越复杂→易用性越差→效率下降。

### 9.2 传统低代码的优弱势

| 任务类型 | 表现 | 说明 |
|---------|------|------|
| 描述性任务（界面、布局、数据展示） | 优秀 | 可视化+所见即所得天然契合 |
| 逻辑性任务（业务逻辑、数据处理、流程编排） | 差 | 可视化手段灵活性不足，要么简单无用，要么复杂反人类 |

### 9.3 大模型带来的变革

**自然语言作为新的输入手段：**
- 人人生而具备的技能，无需学习成本
- 弥补可视化手段处理逻辑性任务的不足
- 可替代 60-70% 的表单类配置界面，显著降低开发工作量

**自然语言的短板：**
- 逻辑不严谨，容易前后矛盾
- 效率低于可视化（尤其在特定场景下）
- 非结构化，缺乏统一标准

### 9.4 Copilot 模式（指令式助手）

| 特征 | 说明 |
|------|------|
| 核心能力 | 意图分类 + 实体提取 |
| 任务分解 | 由人类主导，逐步下指令 |
| 适用场景 | 重复性任务、探索低代码平台功能 |
| 对业务技术人员的价值 | 用自然语言下指令，无需阅读手册，极大幅度降低试错成本 |

### 9.5 Agent 模式（目标驱动智能体）

| 特征 | 说明 |
|------|------|
| 核心能力 | 自行规划 + 自主执行 |
| 人类角色 | 描述目标 → 观察 → 授权 |
| 关键组件 | 思考框架、任务规划器、执行引擎、错误处理与自我修正 |
| 成熟度 | 尚在探索期，大模型推理能力需继续成长 |

### 9.6 可视化与自然语言的融合策略

| 场景 | 推荐方式 | 理由 |
|------|---------|------|
| 业务流程全局设计 | 可视化 | 形象、有全局观，快速把握脉络 |
| 局部逻辑落地 | 自然语言 | 自由表达复杂逻辑，不拘泥于图形控件 |
| 数据展示编排 | 自然语言 | 定制复杂数据展示逻辑 |
| UI布局微调 | 可视化 | 直观控制组件位置、样式 |

> 已有成熟平台：保持可视化为主，自然语言为辅。从零开始：围绕自然语言为中心设计交互。

## 十、用户体验设计

### 10.1 面向业务技术人员的体验设计

| 原则 | 具体做法 |
|------|---------|
| 说人话 | 少用编程术语，不得不用的就地给出言简意赅说明 |
| 傻瓜化操作 | 简洁的操作流程设计，减少选择负担 |
| 渐进式引导 | 管控各功能对知识的要求和传递，渐进式设计开发流程 |
| 可以抄作业 | 提供大量典型应用范例，模板天然就是教材 |
| 自动化兜底 | 出错时给出准确说明，不能惜字如金 |

### 10.2 学习曲线管理

- 功能越多学习曲线越陡峭 —— 利用自然语言降低复杂度
- 视频教材优于纯文字 —— 采用无音频外挂字幕，方便剪辑和搜索
- **首问责任制** —— 出问题时第一时间获得帮助

### 10.3 职业危机感管理

专业开发人员往往担心在低代码的绑架下失去职业竞争优势：
- 强调低代码是**赋能工具**而非替代工具
- 低代码减少的是无业务价值的框架性代码，开发者聚焦业务逻辑
- 专业技能人员在平台上有更高的掌控力（Pro Code模式兜底）

## 十一、部署与兼容

### 11.1 部署方式

- 公有云：开箱即用，适合中小企业
- 私有化部署：应对数据信息安全担忧，适合大型企业或政企客户
- 通用型平台需同时支持两种方式

### 11.2 与已有系统的关系

- **优先发展"被集成"能力** —— 低代码平台一般不带直接业务价值，作为子系统被集成
- 支持单点登录，对接权限系统
- 区分开发态和运行态权限，建议物理隔离

### 11.3 兼容性管理

- 系统化发现兼容性问题的机制
- 建设兼容性测试体系
- 自动化兼容性问题解决

## 十二、产品经理重点关注清单

### MVP 期（0-6 个月）

- [ ] 明确产品定位（通用型 vs 专用型）
- [ ] 确定目标用户群（业务技术人员占比目标）
- [ ] 核心编辑器能力：布局编辑器 + 属性编辑器
- [ ] 输出首批模板和范例（至少覆盖 2-3 个典型场景）
- [ ] 建立基础组件集（自主可控是底线）

### 成熟期（6-24 个月）

- [ ] 持续拓展通用能力，拒绝与具体业务耦合
- [ ] 建立插件系统的 SDK 和核心扩展点
- [ ] 数据能力建设：对接存量系统
- [ ] 多人协同编辑（避免后期改造）
- [ ] 兜底策略：Low Code / Pro Code 混合开发
- [ ] 培育和改善与应用团队的关系

### 超越期（24 个月+）

- [ ] 各场景针对性优化：表单、Dashboard、图表等
- [ ] 全生命周期覆盖：D2C、自动化测试、埋点、部署
- [ ] AI 融合：Chatbot → Copilot → Agent 逐级演进
- [ ] 插件生态建设，推动应用团队自主开发插件
- [ ] 模板体系丰富化，分门别类
- [ ] 视频教材和知识库建设
