# 4.5 工具与能力：让 AI 操作外部世界的"手和脚"

> **核心结论**：工具 = AI 的"手和脚"——决定 AI 能做什么、不能做什么。
> **判断铁律**：工具调用必须"必要 + 最小 + 可控"——不必要不调、不全开、可回滚。
> **底线思维**：工具越多 ≠ AI 越强；工具越多出错面越大。

## 一、为什么工具调用是 Agent 的"分水岭"

Prompt Engineering（对话型）只能让 AI 在黑盒里"想"，无法操作外部世界。Agent（自主型）的核心是**工具调用**——让 AI 真正"做事"：

- 调用 API 查数据
- 操作数据库增删改
- 发邮件、提交工单
- 执行代码、写文件

反面案例：某 AI 客服"只能查知识库回答问题"，但用户问"我订单的状态"时无能为力——根因是没接订单查询 API，AI 不会查订单系统。

## 二、工具调用的 4 个核心机制

### 2.1 Function Calling（函数调用）

Function Calling 是当前主流的工具调用方式——AI 模型输出"调哪个函数 + 参数"，系统执行后把结果返回给 AI。

**反例（无 Function Calling）**：
> AI 尝试"调"天气 API → 实际只是在文本里写"我帮你查了天气是晴天"

**正例（有 Function Calling）**：
> AI 输出：{"function": "get_weather", "args": {"city": "北京"}}
> 系统执行：调用天气 API，返回"晴天，25℃"
> AI 收到结果：基于真实数据回答

### 2.2 工具描述：让 AI 知道有什么工具可用

每个工具的描述必须包含：

| 字段 | 含义 | 示例 |
|------|------|------|
| 工具名 | 工具的标识 | get_weather |
| 描述 | 工具的功能说明 | "查询指定城市的天气" |
| 参数 | 输入参数定义 | {"city": "string"} |
| 返回值 | 输出的结构 | {"temp": "number", "desc": "string"} |

反面案例：某工具只给了名字没给描述，AI 不知道何时调用，工具"形同虚设"。

### 2.3 工具选择：AI 怎么决定调用哪个工具

模型会根据"用户输入 + 工具描述"自动选择工具。PM 设计时需考虑：

| 设计要点 | 含义 |
|---------|------|
| **工具命名规范** | 一致、易懂（get_xxx / query_xxx） |
| **描述具体** | 说明何时调用、何时不调用 |
| **避免重叠** | 多个工具功能重叠会导致 AI 选错 |
| **示例补充** | 关键工具配示例，提升调用准确率 |

### 2.4 工具执行：调用结果的处理

| 步骤 | 内容 |
|------|------|
| 1. AI 推理出"调什么、参数是什么" |
| 2. 系统执行工具调用 |
| 3. 工具返回结果（成功 / 失败 / 异常） |
| 4. AI 解读结果 |
| 5. AI 决定下一步（继续调用 / 完成任务 / 转人工） |

## 三、工具的 3 个关键设计原则

### 3.1 必要性原则

**不必要不调**。每个工具调用都有成本（Token + 延迟 + 错误风险）。能 Prompt 解决的不调工具。

反面案例：某 AI 助手"先调 API 查今天是几月几日，再回答用户问题"——查日期不需要调 API，浪费时间 + 资源。

### 3.2 最小权限原则

**工具权限按"最小可用"分配**。不要一次性给 AI "所有工具"。

| 权限 | 适用 |
|------|------|
| 只读 | 查询类操作（get_xxx） |
| 写入 | 需人审（create_xxx） |
| 删除 | 必须二次确认（delete_xxx） |
| 付费 | 必须审批（pay_xxx） |

反面案例：某 AI 助手一上线就拥有"删除数据库表"权限，一次误操作导致生产事故。根因是"权限给太大"。

### 3.3 可控性原则

每个工具调用必须**可监控、可回滚、可审计**：

| 维度 | 内容 |
|------|------|
| 监控 | 每次调用的参数、结果、耗时 |
| 回滚 | 写入类操作支持事务回滚 |
| 审计 | 关键工具调用记录到审计日志 |

## 四、工具编排：多个工具协同工作

复杂任务需要多个工具按顺序或并行调用：

**反例（手动编排）**：
> 写死 5 个工具的调用顺序 → 业务变 → 修改 10 处代码

**正例（工具编排引擎）**：
> 用工具编排引擎（DAG / 工作流）配置工具链 → 业务变 → 改配置

**反面案例**：某项目把工具调用逻辑写在 Python 脚本里，业务变化时改脚本，3 个月后变成"无法维护的屎山"。

## 五、工具安全的 4 道防线

| 防线 | 作用 |
|------|------|
| **白名单** | AI 只能调用白名单内的工具 |
| **参数校验** | 工具参数必须符合 schema |
| **执行限制** | 单次调用的资源 / 时间 / 影响范围 |
| **操作审计** | 关键操作必须记录、可追溯 |

反面案例：某 AI 被诱导调用"删除文件"工具，导致关键数据丢失。根因是无白名单 + 无操作审计。

## 六、工具调用的 4 个反模式

| 反模式 | 表现 | 应对 |
|-------|------|------|
| **工具泛滥** | 一次给 AI 50 个工具 | 按场景分组，每次只给 5-10 个 |
| **工具描述模糊** | 只给名字不给描述 | 描述具体 + 加示例 |
| **工具重叠** | 多个工具功能重叠 | 合并 / 命名区分 |
| **无审计** | 工具调用没记录 | 关键工具必审计 |

## 七、PM 行动清单

看完本节后：

1. **每个 AI 功能必问"要不要工具"**：能 Prompt 解决的不上工具
2. **工具描述必具体**：命名 + 描述 + 参数 + 返回值 + 示例
3. **工具权限按最小原则**：先给只读，按需扩展
4. **关键工具调用必审计**：可监控、可回滚、可追溯
5. **复杂任务用工具编排引擎**：避免写死脚本
