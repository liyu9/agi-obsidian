# 4.2 边界与护栏：AI 产品的"不可越界"设计

> **核心结论**：边界 + 护栏 = AI 产品的"两道安全门"——决定 AI 能做什么、不能做什么、出错怎么办。
> **判断铁律**：边界定义"能力范围"，护栏定义"安全约束"——两者缺一不可。
> **底线思维**：没有护栏的 AI 产品，业务方不敢用。

## 一、为什么边界与护栏是企业级 AI 的"生命线"

企业级 AI 项目出问题时，90% 不是"AI 不会做"，而是"AI 做了不该做的事"。

反面案例：某银行 AI 客服误把"投诉"识别为"咨询"，自动回复了"您的咨询已受理"，客户愤怒投诉，3 天后 CEO 亲自道歉。

根因不是"模型不够准"，是**没有边界 + 没有护栏**：
- **没有边界**：AI 不知道"哪些话可以自动回、哪些必须转人工"
- **没有护栏**：AI 识别错误时没有兜底

## 二、边界设计：什么该做、什么不该做

边界定义 AI 产品的**能力范围**。设计边界的 3 个核心问题：

| 问题 | 示例 |
|------|------|
| **能力范围** | AI 能回答什么？不能回答什么？ |
| **数据范围** | AI 能访问什么数据？不能访问什么数据？ |
| **操作范围** | AI 能执行什么操作？不能执行什么操作？ |

### 2.1 能力边界

| 类型 | 该做 | 不该做 |
|------|------|--------|
| 业务咨询 | 标准 FAQ 回答 | 个性化投资建议 |
| 流程处理 | 标准化工单处理 | 异常流程的特殊处理 |
| 数据查询 | 公开数据查询 | 敏感数据查询 |
| 操作执行 | 低风险操作（如发邮件） | 高风险操作（如扣款） |

### 2.2 数据边界

| 类型 | 可访问 | 不可访问 |
|------|--------|----------|
| 用户数据 | 本用户的数据 | 其他用户的数据 |
| 业务数据 | 业务范围内的数据 | 财务、人力等敏感数据 |
| 历史数据 | 业务需要的近 N 个月 | 全量历史数据 |
| 实时数据 | 公开 API 数据 | 内部专网数据 |

### 2.3 操作边界

| 风险等级 | 可执行 | 必须人审 |
|---------|--------|---------|
| 低风险 | 自动发送、自动归档 | - |
| 中风险 | 自动提醒、自动生成 | - |
| 高风险 | - | 扣款、转账、签约 |
| 极高风险 | - | 任何法律相关操作 |

## 三、护栏设计：AI 出错的 3 道安全门

护栏定义 AI 的**安全约束**。当 AI 试图越界或出错时，护栏立即介入。

### 3.1 第一道：输入护栏（用户输入侧）

**作用**：在 AI 接收用户输入前，先做合规检查。

| 触发条件 | 护栏动作 |
|---------|---------|
| 输入包含敏感信息（身份证、银行卡） | 自动打码 |
| 输入超出能力范围 | 提示"我无法回答" |
| 输入包含攻击性语言 | 拒绝回答 |
| 输入触发合规关键词 | 转人工 |

### 3.2 第二道：过程护栏（AI 推理侧）

**作用**：在 AI 推理过程中，监控其行为是否合规。

| 触发条件 | 护栏动作 |
|---------|---------|
| AI 试图访问越界数据 | 立即阻断 |
| AI 调用未授权工具 | 立即阻断 |
| AI 输出包含敏感信息 | 立即过滤 |
| AI 推理超时 | 中断并降级 |

### 3.3 第三道：输出护栏（用户输出侧）

**作用**：在 AI 输出到达用户前，最后一次合规检查。

| 触发条件 | 护栏动作 |
|---------|---------|
| 输出包含违法内容 | 替换为标准回复 |
| 输出存在事实错误 | 加"请核实"标签 |
| 输出涉及高风险建议 | 提示"建议咨询专业人士" |
| 输出包含竞品信息 | 过滤 |

## 四、容错设计：出错时如何优雅降级

| 错误类型 | 容错策略 |
|---------|---------|
| **模型调用失败** | 重试 3 次 → 切换备用模型 → 转人工 |
| **工具调用失败** | 跳过该步骤 → 标注"未完成" → 继续后续 |
| **用户输入理解错误** | 反问澄清 → 给出最可能的解释 |
| **AI 输出错误** | 标注"AI 生成" → 提示用户核实 |
| **整体超时** | 返回部分结果 + "处理中"提示 |

反面案例：某 AI 客服因模型服务故障，输出空白。用户体验为"AI 没响应"，客诉率激增。引入"降级回复"（如"系统繁忙，请稍后再试"）后客诉率下降 80%。

## 五、权限设计：谁能用什么

| 角色 | 权限 |
|------|------|
| 业务用户 | 调用 AI 完成任务 |
| 业务管理员 | 配置 AI 流程、查看统计 |
| IT 管理员 | 管理模型、监控系统 |
| 数据管理员 | 管理知识库、配置数据源 |
| 审计员 | 查看所有 AI 决策日志 |

**关键原则**：**最小权限原则**——每个角色只给必需的权限。

## 六、审计设计：如何追溯 AI 决策

企业级 AI 必须在 3 个层面可追溯：

| 层面 | 追溯内容 | 保留期 |
|------|---------|--------|
| **输入日志** | 用户输入、上下文 | 90 天 |
| **推理日志** | 模型推理过程、工具调用 | 180 天 |
| **输出日志** | AI 输出、用户反馈 | 365 天 |

追溯能力是**合规审计的硬要求**——监管问"为什么这个用户被拒贷"，必须能在 5 分钟内调出完整推理日志。

## 七、PM 行动清单

看完本节后：

1. **每个 AI 功能必过边界三问**：能力 / 数据 / 操作
2. **每条 AI 调用链路必过三道护栏**：输入 / 过程 / 输出
3. **每个 AI 功能必设计容错路径**：失败、超时、出错的降级方案
4. **权限设计按"最小权限原则"**：先给最少权限，按需扩展
5. **审计日志必保留 90+ 天**：满足合规追溯
