# 4.1 需求建模：把业务需求翻译成 Agent 可执行的任务

> **核心结论**：需求建模是 PM 把"业务话"翻译成"Agent 任务"的过程——5 步法可复用。
> **判断铁律**：每个 Agent 任务必须有"输入 / 输出 / 工具 / 状态 / 终止条件"5 个明确要素。
> **底线思维**：没有需求建模的 Agent 项目，100% 跑偏。

## 一、为什么 Agent 需求建模比传统需求更复杂

传统软件需求是"输入 → 输出"的确定性函数。Agent 需求是"输入 + 状态 + 工具调用 → 输出"的非确定性过程。

**传统软件需求**：
- 输入是结构化的（用户填表）
- 流程是确定的（if-else 逻辑）
- 输出是标准的（固定的字段）

**Agent 需求**：
- 输入是开放的（自然语言、文档、图片）
- 流程是动态的（模型决定下一步）
- 输出是非标准的（可能跑偏、可能漏掉）

**反面案例**：某金融企业用传统需求文档（PRD）描述 Agent 项目，写"AI 帮用户分析财务报表"。3 个月后发现团队无法落地——"分析"是开放任务，团队不知道 AI 怎么"分析"，开发无从下手。

## 二、需求建模的 5 个核心要素

PM 在建模 Agent 任务时，每个任务必须明确 5 个要素：

| 要素 | 含义 | 示例 |
|------|------|------|
| **输入** | 任务接收的输入是什么 | 用户上传的 PDF 财务报表 |
| **输出** | 任务产出的输出是什么 | 结构化的财务分析报告 |
| **工具** | 任务可以调用哪些工具 | 数据查询 API、报表生成 API |
| **状态** | 任务执行过程中的状态 | "等待用户确认"、"正在查询数据" |
| **终止条件** | 任务在什么条件下结束 | 用户确认 / 错误次数 > 3 / 超时 |

5 个要素中任一不明确，团队就无法开始开发。

## 三、需求建模的 5 步法

### Step 1：识别业务目标

**问题**：这个业务问题真正想达成什么？
**示例**：财务部门希望"5 分钟内完成一份标准财务分析报告"，而不是"用 AI 写报告"。

### Step 2：拆解为 Agent 任务链

**问题**：从输入到输出，需要哪些 Agent 任务？任务之间如何衔接？
**示例**：
- 任务 1：解析 PDF 财务报表
- 任务 2：抽取关键财务指标
- 任务 3：同比/环比分析
- 任务 4：生成文字分析报告
- 任务 5：用户确认 / 修改

### Step 3：为每个任务明确 5 要素

**问题**：每个任务的输入/输出/工具/状态/终止条件是什么？
**示例**（任务 3 "同比/环比分析"）：
- 输入：抽取后的财务指标
- 输出：同比/环比变化数据
- 工具：内置计算函数
- 状态：计算中 / 计算完成
- 终止条件：计算完成

### Step 4：定义任务之间的衔接协议

**问题**：任务 A 的输出怎么传给任务 B？数据格式是什么？失败时怎么回退？
**示例**：任务 2 抽取的指标统一为 JSON 格式，传递给任务 3；任务 3 失败时回到任务 2 重新抽取。

### Step 5：画 Agent 任务流图

把 5 步结果画成图，让开发一眼看清整个任务链。

反面案例：某项目只做了 Step 1-2，缺少 Step 3-5。开发拿到需求后发现"任务之间的数据格式没定义"，被迫重新设计，整个项目延期 2 个月。

## 四、需求文档的关键要素

| 段落 | 包含内容 |
|------|---------|
| 业务背景 | 业务方是谁、痛点是什么、价值如何衡量 |
| 任务清单 | 拆解后的所有 Agent 任务（带 5 要素） |
| 任务流图 | 任务之间的衔接关系和数据格式 |
| 异常处理 | 工具调用失败 / 任务失败 / 用户取消的兜底 |
| 评估标准 | 怎么判定"做得好"和"做得差" |
| 上线标准 | MVP 的最小可用范围是什么 |

## 五、需求建模的 3 个反模式

| 反模式 | 表现 | 应对 |
|-------|------|------|
| **需求太抽象** | "用 AI 提升财务效率" | 拆到 Step 1-3 的颗粒度 |
| **需求 100% 复制传统 PRD** | 用 if-else 写 Agent 任务 | 用 5 要素重写 |
| **跳过任务流图** | 任务清单列了但没画图 | Step 5 必画 |

## 六、PM 行动清单

看完本节后：

1. **每个 Agent 项目必过 5 步法**：从业务目标到任务流图
2. **每个 Agent 任务必过 5 要素**：输入/输出/工具/状态/终止条件
3. **任务流图作为评审必过项**：没有图的需求文档 = 不完整的 PRD
4. **异常处理写在 PRD 显眼位置**：不藏附录
5. **评估标准必量化**：避免"质量高"这种主观描述
