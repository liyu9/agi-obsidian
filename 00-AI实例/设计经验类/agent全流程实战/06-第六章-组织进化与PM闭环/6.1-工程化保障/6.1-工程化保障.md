# 6.1 工程化保障：让 Agent 在生产环境里"不崩、可查、可控"

> **核心结论**：Agent 的故障谱和传统应用完全不同——需要可观测性 + 可靠性 + 安全性三道护栏。
> **判断铁律**：上线前必须具备 Trace、Hook、循环控制、成本围栏、沙箱、权限网关六件套。
> **底线思维**：可观测性是一切工程化的底座——看不见的 Agent 上不了生产。

## 一、为什么 Agent 需要专门的工程化保障

传统软件工程的"上线即稳定"假设在 Agent 时代被打破。Agent 系统的故障谱有 4 类完全不同的形态：

| 故障类型 | 表现 | 传统应用里 |
|---------|------|-----------|
| 随机性故障 | 同 prompt、同模型，今天和昨天输出差异大 | 不会出现 |
| 连锁性故障 | 工具失败 → LLM 幻觉重试 → 工具再失败 → Token 暴涨 | 极少 |
| 不可见性故障 | Agent "正常运行"但 prompt 拼接错误、上下文污染已埋雷 | 偶发 |
| 成本性故障 | 长尾任务拖垮整个预算 | 不会发生 |

**这 4 类故障的共同点是"上线后才发现"**——传统 QA 流程根本覆盖不到。

工程化保障就是为这 4 类故障建立的护栏。PM 必须在 Agent 项目立项时就把"工程化预算"算进去（建议占总投入 20-30%），否则上线即翻车。

## 二、可观测性三件套：Trace / Metric / Log

### 2.1 Trace 是一切可观测性的底座

Agent 系统的关键状态是分布式的——Prompt 模板、上下文窗口、工具调用栈、模型版本、Token 消耗、规划步骤……这些信息分散在多个调用之间。**单条日志无法还原一次完整决策**。

**Trace（链路追踪）是 Agent 可观测性的第一公民**。一次用户请求对应一条 Trace，由多个 Span 组成：

- **Root Span**：用户原始请求
- **LLM Span**：每次模型调用的入参（prompt、temperature、tools）、出参（content、tool_calls）、耗时、Token 用量
- **Tool Span**：每次工具调用的入参、出参、耗时、错误信息
- **Retriever Span**：RAG 检索的 query、命中数、相似度分布
- **Agent Step Span**：规划器决策、子 Agent 派发等

通过 Trace 可以实现"任意一次用户对话的回放"——这是 Agent 时代 debug 的最基本单位。

### 2.2 Metric 解决"看趋势"的问题

单次 Trace 只反映个案，Metric 才是看趋势的窗口。Agent 场景需要关注的核心 Metric：

| 类别 | 核心指标 |
|------|---------|
| 质量类 | 任务完成率（task success rate）、一次解决率（FCR）、人工接管率（handoff rate） |
| 成本类 | 单次会话 Token、平均每任务成本、P95 成本、Tool 调用成本 |
| 性能类 | 端到端 P50/P95 延迟、LLM 推理耗时、Tool 等待耗时 |
| 可靠性类 | 重试率、循环次数（max steps reached 占比）、超时率、幻觉率 |

Metric 必须以看板形式呈现，且需要按"用户分群 × Agent 名称 × 工具类型"做多维下钻。

### 2.3 Log 是最后一道防线

Log 负责记录 Trace 之外的"边角信息"——业务侧埋点、合规审计所需的完整 prompt/response 快照、异常堆栈、网络抖动等。建议采用结构化 JSON 日志，并按"会话 ID + Trace ID"双重索引，方便排查时把 Log 和 Trace 关联起来。

### 2.4 Hook 骨架：让可观测性"无需业务改造"

可观测性最大的阻力来自"业务侧要改代码"。Hook 骨架通过"在 Agent 框架的固定生命周期点插入回调"的方式，让工程团队无需修改业务代码即可完成埋点。Hook 的常见事件点：

- `on_agent_start` / `on_agent_end`：Agent 启动/结束
- `on_llm_start` / `on_llm_end`：模型调用前后
- `on_tool_start` / `on_tool_end`：工具调用前后
- `on_error`：任意异常
- `on_step`：Agent 单步推进

**Hooks 真正的威力在于"事件驱动自动化"——它不只是埋点，更是策略执行的入口**：

- `on_tool_end` 时自动检查返回内容是否包含敏感词
- `on_llm_end` 时自动核算本次调用成本并写入 Metric
- `on_step` 累计达到阈值时强制中断

这种"可观测性 + 策略"的耦合是 Agent 时代特有的工程实践。

### 2.5 Langfuse：开源可观测性平台的标准选型

Langfuse 是当前 Agent 可观测性领域最成熟的开源平台，核心能力：

- **Trace 持久化与查询**：支持按 session_id、user_id、tags 多维检索
- **Prompt 版本管理**：把 Prompt 模板作为一等公民纳入版本控制，支持 A/B 实验
- **Evaluation 集成**：可在线/离线对 Trace 跑评测，输出质量分
- **成本核算**：自动按模型 × 用量统计成本
- **自托管友好**：可本地部署，避免敏感数据外泄

**落地建议**：把 Langfuse 的接入做成"Agent 框架的标准中间件"，所有新 Agent 默认开启 Trace；老 Agent 按业务重要程度分批接入。

## 三、可靠性护栏：重试、循环控制与成本围栏

### 3.1 重试策略：分层的退避算法

Agent 调用链路的失败模式多样：网络抖动、模型限流、工具 5xx、解析失败、上下文超长……**重试策略必须按失败类型分层**：

| 错误类型 | 处理 | 具体策略 |
|---------|------|---------|
| 可重试错误 | 指数退避 | 网络 5xx、限流 429、临时性解析错误 → 1s/2s/4s/8s，最多 3 次 |
| 不可重试错误 | 直接失败 | 参数校验失败、鉴权 401/403、内容违规 400 |
| 可降级错误 | 降级到备用 | 主模型不可用 → 备用模型；主工具失败 → 兜底工具 |

### 3.2 循环控制：给 Agent 一道"刹车"

Agent 最大的可靠性风险是"循环"——LLM 反复选择同一个工具、反复生成相似的内容，Token 在无声无息中消耗完。**循环控制的三道防线**：

1. **最大步数限制（max_steps）**：硬性中断。建议默认值 10-15，可按任务复杂度分级
2. **重复检测**：对最近 N 步的"工具名 + 入参哈希"做去重，连续重复 N 次自动终止
3. **Token 预算**：单次会话 Token 上限（如 100K），达到上限时强制收尾并返回部分结果

**反面教训**：XiaoPaw 加固前单步循环可达 50 步以上，单次会话成本超过预算 5 倍。

### 3.3 成本围栏：把"美元/人民币"指标化

成本围栏的本质是"用业务指标约束技术指标"。常见做法：

- **单次会话成本上限**：超过阈值时切到更便宜的模型或简化 prompt
- **单用户日成本上限**：超过时降级或转人工
- **业务 ROI 校准**：每次调用前预估"完成该任务能带来多少业务价值"，低于成本时拒绝执行

把成本围栏做成 Hook（`on_llm_start` 触发预估，`on_llm_end` 触发累计），可以让成本控制成为 Agent 框架的标准能力，而不是每个业务方各自实现。

## 四、安全护栏：沙箱、权限网关与身份认证

### 4.1 沙箱：让 Agent 在"受控空间"内操作

Agent 调用工具本质上是在操作企业的真实系统，**工具越权是 Agent 安全的头号风险**。沙箱机制要求：

- **执行环境隔离**：Agent 代码执行、Shell 命令、文件操作必须在隔离容器中，禁止直接访问生产环境
- **文件系统白名单**：Agent 只能读写指定目录，越权访问直接拒绝
- **网络出口白名单**：只允许访问预先审批的外部 API
- **资源限制**：CPU、内存、执行时长必须设上限

### 4.2 权限网关：把"工具调用"变成"权限校验"

工具调用是 Agent 的"特权操作"，必须在工具执行前插入权限网关：

- **基于 RBAC 的工具授权**：不同角色的 Agent 可调用的工具集不同
- **基于 ABAC 的细粒度校验**：例如"只允许查询客户本人数据"这类带数据维度的策略
- **敏感操作二次确认**：删除、支付、对外发送等高风险操作必须人工复核
- **调用审计**：所有工具调用必须留痕，包括调用人、参数、返回、决策依据

### 4.3 身份认证：Agent 本身也是"主体"

传统系统里"用户"是主体，Agent 只是工具。但在企业场景里，**Agent 自身需要被认证和授权**：

- **Agent 身份（Agent ID）**：每个 Agent 拥有独立身份，便于审计与责任归属
- **Agent 委托（Delegation）**：用户把权限委托给 Agent 时，必须显式声明委托范围
- **Prompt 注入防御**：所有外部输入（用户消息、检索结果、工具返回）必须标记来源，注入检测 Hook 实时拦截可疑片段
- **数据脱敏**：模型返回中的身份证、银行卡、手机号等敏感字段必须在出口侧脱敏

## 五、系统加固实战：XiaoPaw 本地工作助手

### 5.1 加固前的"裸奔"状态

XiaoPaw 初始版本存在以下典型问题：

| 问题 | 风险 |
|------|------|
| 无 Trace | 每次对话都是"黑盒"，出问题无法定位 |
| 无重试机制 | 工具调用失败时直接报错，用户体验差 |
| 单步循环可达 50+ 步 | Token 失控，账单爆表 |
| 本地文件无沙箱 | Agent 可任意读写磁盘，数据泄露风险 |
| API Key 明文存放 | 安全合规问题 |

### 5.2 加固路线图（3 步走）

1. **可观测性层**：接入 Langfuse，统一所有 LLM/工具调用的 Trace；在 Hook 骨架中埋入 Token 计量、延迟埋点、错误埋点
2. **可靠性层**：为每个工具调用加上指数退避重试；设置全局 max_steps=12；增加重复检测；接入成本围栏 Hook
3. **安全性层**：将所有本地操作迁移到沙箱容器；引入权限网关控制"删除文件"等高危工具；外部输入统一加 prompt 注入检测；API Key 改用密钥管理服务

### 5.3 加固后的"业务可观测"

加固后的 XiaoPaw 上线第一天就捕获了 3 类典型问题：

| 事件 | 触发 Hook | 自动应对 |
|------|-----------|---------|
| 某工具 14:00-15:00 连续 5xx | `on_tool_end` 错误检测 | 自动触发 3 次重试并降级到备用工具 |
| 某用户高频触发"清空回收站" | `on_tool_start` 权限网关 | 拦截并要求人工确认 |
| 某 Trace 单次会话 Token 飙到 80K | `on_step` 循环检测 | 第 8 步强制中断并给出原因 |

**核心教训**：这些事件在没有可观测性和护栏的情况下，要么静默失败，要么把账单打到爆。

## 六、PM 的工程化语言翻译

PM 在 6.1 节里需要掌握的"工程语言"主要包括：

- **Trace ID / Span / Session ID**：能用这三个 ID 在可观测性平台里查到一次完整对话
- **FCR / handoff rate / P95 latency**：四个核心业务指标的口径和计算方法
- **Hook 事件点**：知道哪些工程节点可以"插入业务策略"
- **沙箱 / 权限网关 / 二次确认**：能用这三层护栏与研发讨论"高风险操作"的边界

**PM 并不需要写代码，但必须能用这套语言与工程团队对齐设计**。

## 七、PM 行动清单

看完本节后：

1. **把工程化预算算进立项**：占总投入 20-30%，不能省
2. **可观测性先行**：新 Agent 默认接入 Langfuse，老 Agent 按重要程度分批接入
3. **三道护栏必建**：可观测性（Trace + Hook）+ 可靠性（重试 + 循环控制）+ 安全性（沙箱 + 权限网关）
4. **用 4 类故障做风险自查**：随机性 / 连锁性 / 不可见性 / 成本性
5. **学 4 个工程语言**：Trace ID / FCR / Hook 事件点 / 沙箱，与研发对话时不卡壳
