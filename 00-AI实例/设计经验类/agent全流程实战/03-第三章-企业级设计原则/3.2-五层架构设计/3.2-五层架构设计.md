# 3.2 五层架构设计：企业级 AI 应用的分层思维

> **核心结论**：企业级 AI 应用必须分层架构——5 层各司其职，避免"一个大模型包打天下"。
> **判断铁律**：每层只做一件事，跨层调用通过标准化接口，层与层之间解耦。
> **底线思维**：不分层的"单层架构"在企业场景活不过 3 个月。

## 一、为什么企业级 AI 必须分层

消费级 AI 应用可以"一个 Prompt 解决所有问题"——因为用户输入可枚举、输出标准、容错率高。但企业级场景中：
- 业务规则多变（每月变 2-3 次）
- 数据源分散（ERP、CRM、日志、数据库）
- 合规审计要求全程可追溯
- SLA 要求毫秒级响应 + 99.9% 可用

不分层的后果：**一个改动引发全局崩溃**。某个数据源接口变化 → Prompt 输出异常 → 业务方不敢用 → AI 沦为 demo。

反面案例：某零售企业把 AI 客服所有逻辑写在一个 Prompt 里，业务规则调整一次需要重写 Prompt 上千字，3 个月后团队无法维护，被迫重构。

## 二、五层架构总览

```
┌─────────────────────────────────────┐
│  L1  表现层（UI / API / 集成端）     │ ← 业务方/员工/C 端用户触点
├─────────────────────────────────────┤
│  L2  编排层（Orchestration）        │ ← 工作流 / 智能体调度
├─────────────────────────────────────┤
│  L3  智能层（Intelligence）          │ ← Prompt / 模型 / 知识库
├─────────────────────────────────────┤
│  L4  数据层（Data）                  │ ← 向量库 / 业务库 / 缓存
├─────────────────────────────────────┤
│  L5  基础设施层（Infra）             │ ← GPU / 监控 / 部署 / 安全
└─────────────────────────────────────┘
```

**核心设计原则**：每层独立部署、独立扩缩容、独立升级。

## 三、5 层职责详解

### 3.1 L1 表现层（UI / API / 集成端）

**职责**：承接所有用户触点。

**典型形态**：
- Web 端：仪表盘、操作界面、对话窗口
- API：RESTful / GraphQL，对接企业内系统
- 嵌入式：嵌入到 ERP / CRM / 客服工作台

**关键设计**：
- 与编排层（L2）通过标准化 API 通信
- 权限控制在前端就做好（操作日志、用户身份）
- 错误兜底（AI 出错时降级为人工入口）

### 3.2 L2 编排层（Orchestration）

**职责**：业务逻辑编排 + 智能体调度。

**典型形态**：
- 工作流引擎（DAG 编排）
- 智能体调度（Multi-Agent 协作）
- 状态机（多轮对话的上下文管理）

**关键设计**：
- 与表现层（L1）解耦：编排层不依赖具体 UI
- 与智能层（L3）解耦：编排层不知道模型细节
- 可观测：每一步执行都打日志，便于调试和审计

反面案例：某企业把工作流逻辑写在 L1 表现层，业务规则调整一次要前端发版。重构时被迫引入编排层，但回溯改造耗资 200 万。

### 3.3 L3 智能层（Intelligence）

**职责**：模型 + Prompt + 知识库。

**典型形态**：
- 模型：通用大模型 / 行业大模型 / 私有化部署
- Prompt：业务规则、Few-shot 示例、CoT
- 知识库：RAG、向量检索、文档索引

**关键设计**：
- 模型可替换：同一套接口支持多模型切换
- Prompt 版本管理：每次 Prompt 变更要可回滚
- 知识库可热更新：业务知识变化时无需重启

### 3.4 L4 数据层（Data）

**职责**：存储 + 检索。

**典型形态**：
- 向量库（Milvus / Qdrant / Weaviate）
- 业务数据库（MySQL / PostgreSQL）
- 缓存（Redis / 本地缓存）
- 日志库（ES / ClickHouse）

**关键设计**：
- 数据隔离：多租户场景下数据物理隔离
- 检索优化：RAG 的召回率/准确率是关键指标
- 数据治理：明确数据来源、保留期、销毁规则

### 3.5 L5 基础设施层（Infra）

**职责**：算力 + 部署 + 监控 + 安全。

**典型形态**：
- 算力：GPU 集群 / 模型推理服务（vLLM / TGI）
- 部署：K8s / Docker / 蓝绿发布
- 监控：Prometheus / Grafana / 链路追踪
- 安全：网络隔离、密钥管理、审计日志

**关键设计**：
- 弹性扩缩容：高峰期 GPU 不足时要能扩
- 灾备：核心服务多 AZ 部署
- 安全合规：满足等保三级 / SOC2 等

## 四、5 层架构的 3 个关键约束

| 约束 | 含义 | 反例 |
|------|------|------|
| **层间解耦** | 一层变更不波及其他层 | L1 表现层写死 L3 模型名 |
| **接口标准化** | 层间通信用稳定 API | L2 直接调 L4 数据库表结构 |
| **独立可观测** | 每层都有自己的监控和日志 | 只在 L1 加监控，故障难定位 |

## 五、五层架构的常见误区

| 误区 | 表现 | 应对 |
|------|------|------|
| **过度分层** | 5 层拆得过细，团队规模撑不起 | 初期 3 层（L1+L3+L4），规模扩大再拆 L2/L5 |
| **省略编排层** | 把工作流逻辑写在 L1 表现层 | 工作流必须独立成 L2 |
| **模型写死在 L1** | L1 直接调具体模型 API | L1 只调用 L2 接口，模型可替换 |
| **数据未隔离** | 多客户共享向量库 | L4 必做多租户隔离 |

## 六、PM 行动清单

看完本节后：

1. **画出本项目的 5 层架构图**：每层列出当前的实现方案和负责人
2. **识别层间耦合点**：找出现有项目中"改动一层要动其他层"的地方
3. **优先解决最严重的耦合**：通常是 L1 与 L3 耦合（写死模型名 / Prompt 写在前端）
4. **为编排层（L2）独立团队**：避免工作流逻辑分散在多个层
5. **建立每层的可观测标准**：日志 / 指标 / 告警三层标准
