# 31｜从Copilot升级到Agent：观察-规划-执行

你好，我是陈旭。

在过去的几讲中，我们一同踏上了一段激动人心的旅程，推动着我们的低代码平台 Awade 向着智能化不断迈进。在第 29 讲，我们打通了从自然语言到 UI 变更的“最后一公里”，让 AI 的“想法”能够直接呈现在画布之上。紧接着在第 30 讲，我们又通过引入“意图模板”和“对话状态”，让我们的助手学会了多轮对话，从一个机械的指令员，进化成了一个懂得沟通的协作者。

我们的 AI 助手现在已经相当能干了。它能听懂你的指令，能在信息不足时主动追问，最终还能将一个完整的意图，比如“创建一个带有关闭按钮的模态框”，转化为画布上实实在在的 UI 组件。这已经是一个非常了不起的成就。

但是，一个更深层次的问题，一个阻碍它从一个优秀的 “Copilot”（助手）进化为真正 “Agent”（智能体）的根本性障碍，也随之浮现。那就是，我们的助手至今为止，依然是在“闭着眼睛”开车。它是一个“盲人摸象”的执行者。

让我用几个你可能很快就会遇到的失败场景，来揭示这个问题所在。

场景一，也是最直接的，它无法回答任何关于当前状态的问题。如果你问它：“我现在页面上有几个按钮？”它会瞬间语塞。因为它从来没有“看过”画布，它的世界里只有指令和实体，没有“状态”这个概念。

场景二，它会尝试执行无效的指令。假设你对它说：“把那个‘登录’按钮的颜色改成红色。”但实际上，页面上根本就没有这个按钮。我们的助手会怎么做？它可能会忠实地走完整个流程，生成一个针对不存在的组件 ID 的 JSON Patch，然后前端在应用时报错。或者，它只能在无法提取到组件 ID 时，机械地回复“无法执行”。这两种结果，体验都非常糟糕。

场景三，它在执行创建类指令时，缺乏对上下文的理解。当你说：“在那个用户注册表单里，帮我加一个‘确认密码’的输入框。”我们的助手会再次陷入困惑。它不知道页面上有几个表单，更不知道哪一个才是你口中的“用户注册表单”。

这些痛点都指向了同一个根源：我们的 AI 助手缺乏“观察”的能力。它就像一个只听从命令但从不观察战场的士兵，无法根据实际情况做出调整。

因此，本讲的使命，就是为我们的 Agent 安装一双“眼睛”，建立一个强大的“观察层”（Observation Layer）。我们要彻底改变它的工作模式，让它在接收到用户指令后，第一反应不再是“我应该做什么？”，而是“为了更好地完成任务，我需要先了解什么情况？”。

这，就是从 Copilot 升级到 Agent，最关键，也是最核心的一步：建立“观察 - 规划 - 执行”的初步闭环。

## 第一步：设计 Agent 的“视觉系统”——定义一个多维度的观察工具集

要让 Agent“看见”，我们不能只是简单地把整个页面的 JSON“蓝图”一股脑地丢给它。那就像是让一个人去看显微镜下的细胞切片来理解一整头大象，信息量巨大，但效率低下且抓不住重点。

一个好的“视觉系统”，应该能提供不同粒度、不同维度、并且是结构化的信息。我们需要设计一套观察工具，让 Agent 可以像人类一样，既能“一览众山小”地看全局，又能“明察秋毫”地看细节，还能“按图索骥”地去寻找目标。

经过思考和提炼，我为你定义了三个核心的“只读”观察工具。它们将构成我们 Agent“视觉系统”的基石，并作为 AI 与我们的低代码平台进行交互的标准接口。

### **工具一：全局扫描 (**`get_page_outline`**)**

这个工具就像是 Agent 的“广角镜”。它的作用是快速获取整个页面的组件树状结构，但不包含每个组件详细的属性信息。这使得 Agent 可以迅速建立起对页面整体布局和组件层级关系的认知。

比如，当用户问“我页面上都有什么？”时，这个工具就能派上大用场。它的返回结果可能像这样：

```
{
  "id": "root", 
  "type": "Page", 
  "children": [
    {
      "id": "header_123",
      "type": "Header",
      "children": [...]
    },
    {
      "id": "form_abc", 
      "type": "Form", 
      "children": [
        {"id": "input_456", "type": "Input"},
        {"id": "btn_789", "type": "Button"}
      ]
    }
  ]
}
```

### **工具二：焦点详查 (**`get_component_details`**)**

如果说 `get_page_outline` 是广角镜，那么 `get_component_details` 就是 Agent 的“放大镜”。当 Agent 需要深入了解某一个特定组件的详细情况时，就会调用这个工具。

它的输入参数很简单，就是一个组件的 ID (`component_id`)。

它的返回结果，则是这个组件所有属性的完整清单：

```
{
  "id": "btn_789", 
  "type": "Button", 
  "properties": {
    "text": "登录", 
    "color": "blue",
    "size": "medium",
    "disabled": false
  }
}
```

这个工具对于回答“那个登录按钮现在是什么颜色？”或者在修改前核对组件当前状态等场景，至关重要。

### **工具三：智能筛选 (**`find_components`**)**

这是我们“视觉系统”里最强大的一个工具，它扮演着“搜索引擎”的角色。它允许 Agent 根据一个或多个条件，来查找所有符合条件的组件列表。

这正是解决我们前面提到的“页面上所有蓝色的按钮”这类指令的基础。它的输入参数相对灵活，可以包含父组件 ID（用于在特定容器内查找）、以及一个过滤器数组。

```
// 伪代码
find_components(
  parent_id: "form_abc", // 可选，限定在某个容器内查找
  filters: [ // 过滤器数组
    {"property": "type", "value": "Button"}, 
    {"property": "color", "value": "blue"}
  ]
)
```

它的返回结果，是一个包含所有匹配组件信息的数组：

```
[
  {"id": "btn_1", "type": "Button", "properties": {"text": "确认", "color": "blue"}}, 
  {"id": "btn_2", "type": "Button", "properties": {"text": "提交", "color": "blue"}}
]
```

有了这套由“广角镜”、“放大镜”和“搜索引擎”构成的观察工具集，我们的 Agent 就拥有了初步的“视觉感知”能力。

## 第二步：实现“视觉”——后端工具的编码实现

设计好了工具集，下一步就是要在我们的 Python 后端，将这些设想变为现实。我们需要为上面定义的三个工具，编写具体的函数实现。

这个过程并不复杂，其核心任务，就是安全地读取和查询我们存储在内存（或 Redis 中）的、代表当前页面状态的那个 JSON“蓝图”。

例如，`get_component_details` 函数的伪代码可能长这样：

```
# 伪代码
def get_component_details(component_id: str):
    # page_schema 是我们存储在服务端的页面状态JSON对象
    page_schema = get_current_page_schema() 
    # 递归遍历 page_schema，找到ID匹配的组件
    component = find_component_by_id(page_schema, component_id)
    if component:
        return {
            "id": component.get("id"),
            "type": component.get("type"),
            "properties": component.get("props", {})
        }
    else:
        return {"error": "Component not found"}
```

在实现这些工具时，有一个极其重要的原则必须被严格遵守：**这些观察工具，必须是“只读”的（Read-only）**。

它们的职责有且仅有“观察”，绝对不能以任何方式意外地修改到页面状态。这是一种安全保障，确保我们的“眼睛”不会错误地变成“手”，造成意料之外的副作用。清晰地划分“读”和“写”的工具，是构建一个稳定可靠 Agent 系统的前提。

## 第三步：打通“感官”与“大脑”——建立“观察 - 推理 - 响应”循环

现在，我们的 Agent 既有了“眼睛”（观察工具集），也有了“手”（上一讲实现的修改工具，如 `createComponent`）。但它还缺少一个关键部分——连接感官与行动的“大脑皮层”。它需要一个机制来决定：什么时候该用眼睛，什么时候该动手？

为此，我们需要对后端的 `/chat` 主处理流程进行一次核心架构升级。我们引入一个全新的模块，我称之为“指令分诊模块”（Triage Module）。

这个模块，是在我们调用真正的“规划器”（我们将在第 32 讲深入探讨）之前，进行的一次智能预处理。它的职责，就是对用户的指令进行初步分析，判断其根本性质。

这个分诊逻辑，我们可以巧妙地通过一次对大语言模型（LLM）的内部提问（我称之为 Meta-Prompt）来实现。

当接收到用户的指令后，系统不再是直接去分析意图，而是先在内部向 LLM 提出第一个问题：

> “请分析以下用户指令：‘[用户的原始指令]’。然后判断，这个指令的主要意图，究竟是‘查询状态’，还是‘修改状态’？”

根据 LLM 的回答，我们的处理流程将进入两个截然不同的分支。

### **分支一：如果意图是“查询状态”**

当用户问“页眉里面现在有什么？”时，分诊模块会将其归类为“查询状态”。

接下来的流程是：

**选择工具**：LLM 会进一步判断，为了回答这个问题，最适合调用哪个“观察”工具。对于这个问题，`find_components` 显然是最佳选择。LLM 会生成调用该工具所需的参数，如 ` {parent_id: 'header'}`。**执行观察**：系统执行 `find_components(parent_id='header')`，并得到一个结构化的组件列表 JSON 数据。**生成回答**：最后，系统会将用户的原始指令和刚刚查询到的数据，一并再次交给 LLM，并给出这样的指令：“请根据以下上下文信息，为用户生成一个自然、流畅的回答。”**最终输出**：LLM 会综合信息，生成一句通俗易懂的话，比如：“好的，我看了一下，页眉里现在有一个 Logo 图片和一个标题文本。”

你看，通过这个流程，Agent 完美地回答了一个它之前完全无法处理的状态查询问题。

### **分支二：如果意图是“修改状态”**

当用户说“把登录按钮变红”时，分诊模块会将其归类为“修改状态”。

此时，流程的关键，在于引入了一个至关重要的步骤——**行动前的“事实核查”（Fact-Checking）**。

**核查事实**：在真正准备执行修改动作之前，系统会先调用“观察”工具进行预检查。它会先用 `find_components` 工具，去确认页面上是否真的存在一个“登录按钮”。**决策判断**：基于核查的结果，系统会做出更智能的决策：

- **如果找到了唯一一个登录按钮**：太好了，事实无误。系统将继续执行后续的 `updateProperty` 等写操作工具。
- **如果找到了多个登录按钮**：系统不会贸然行动，而是会向用户发起一次澄清式的多轮对话：“我找到了两个登录按钮，一个在页眉，一个在弹窗里，请问您想修改哪一个呢？”
- **如果没有找到任何登录按钮**：系统会给出一个友好且明确的报错：“抱歉，我在页面上没有找到‘登录按钮’，请您确认一下。”

通过引入这个基于“观察”的“事实核查”环节，我们极大地提升了 Agent 行为的可靠性。它不再是一个盲目的执行者，而是一个会在行动前三思的、更负责任的智能体。这也为我们将在第 34 讲中探讨的“自我修正”能力，提供了最基础的错误预判机制。

## 典型的场景梳理

让我们在脑海中，完整地过一遍两个典型的场景，来感受一下我们今天构建的这个新系统的威力。

**查询演示：**

- **用户**：“我的页面上有多少个输入框？”
- **分诊模块 (LLM)**：判断为“查询状态”。
- **大脑 (LLM)**：决定使用 `find_components` 工具，其参数为：

```
{
  "filters": [
    {
      "property": "type", 
      "value": "Input"
    }
  ]
}
```

- **眼睛 (系统)**：执行工具，返回一个包含 3 个组件对象的数组。
- **大脑 (LLM)**：接收到包含 3 个对象的数组，并生成回答。
- **嘴巴 (系统)**：向用户回复：“我帮您数了一下，页面上总共有 3 个输入框。”

**带有前置观察的修改演示：**

- **用户**：“把页脚里那个版权信息的文字改大一点。”
- **分诊模块 (LLM)**：判断为“修改状态”。
- **大脑 (LLM)**：启动“事实核查”。决定使用 `find_components`，其参数为：

```
{
  "parent_id": "footer",
  "filters": [
    {
      "property": "text", 
      "value": "版权信息"
    }
  ]
}
```

- **眼睛 (系统)**：执行工具，成功定位到组件，返回（示例）：

```
{
  "id": "text_copyright",
  "type": "Text",
  "properties": {
    "text": "版权信息",
    "fontSize": "small" 
  }
}
```

- **大脑 (LLM)**：核查成功。继续规划下一步，调用 `updateProperty` 工具，其参数为：

```
{
  "componentId": "text_copyright",
  "propertyName": "fontSize",
  "propertyValue": "large"
}
```

- **手 (系统)**：执行 `updateProperty`，生成 JSON Patch 并返回给前端。
- **用户**：看到页脚的版权文字应声变大。

## 小结

今天这一讲，我们完成了从 Copilot 到 Agent 的决定性一跃。我们为 Agent 成功地安装了“眼睛”（多维度观察工具集）和“视觉皮层”（指令分诊模块）。

通过这套系统，我们的 Agent 不再是一个盲目的执行者。它现在能够：

**理解并回答**关于画布当前状态的问题。在执行修改任务前，进行**事实核查**，避免无效操作和错误。在信息不明确时，基于观察结果，做出更智能的**澄清或反馈**。

这使得 Agent 的行为变得更加智能、可靠，也更符合我们对一个真正“智能体”的期待。

当然，我们今天的“观察 - 推理 - 响应”循环还相对简单，通常是一次观察，对应一次响应。但如果一个复杂的任务，比如“帮我把注册表单里的所有输入框都加上非空校验”，需要“多次观察、多次行动”才能完成，那该怎么办呢？

这就引出了我们下一讲的核心主题——智能体的思考核心：**任务规划器（Planner）**。它将消费我们今天构建的强大的观察能力，来制定出复杂的、多步骤的行动计划。
