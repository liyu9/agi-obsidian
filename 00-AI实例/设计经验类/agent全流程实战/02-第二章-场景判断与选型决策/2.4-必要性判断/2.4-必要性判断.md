# 2.4 必要性判断：什么时候该用 Agent，什么时候不必

> **核心结论**：大多数企业场景不需要 Agent。
> **判断铁律**：满足"多步骤 + 工具调用 + 价值>代价"三条件才能上 Agent。
> **底线思维**：架构选择应从简单到复杂——能用 Prompt / Workflow 解决，就不 Agent 化。

## 一、反常识前提：大多数企业场景不需要 Agent

PM 选型时的核心困惑："从过去的'怎么做'，变成了现在的'选哪个'。这就好比面对一个工程需求，你究竟是用一把精美的美工刀去建大楼，还是雇佣一支专业的施工队去修一扇小窗户？"

这个比喻背后的反常识判断：**大多数企业场景，根本不需要 Agent**。反面案例几乎都是"过度 Agent 化"的典型：

| 反面案例 | 教训 |
|---------|------|
| Klarna 用 AI 替代 700 名客服，最终不得不重新招聘 | 场景错选比技术错选代价更大（忽略情感劳动） |
| 多家公司做"对话式数据分析"，前提条件不满足就上 AI | 数据前提不满足时，再先进架构也救不回来 |
| 一个团队因 prompt caching miss 收到 38,000 美元 AWS Bedrock 账单 | 价值/代价比不达标的项目，不应启动 |

共同特征不是"技术不够好"，而是"必要性没判断好"。

PM 启动 Agent 项目前的最后一道关卡：**这个场景，真的需要 Agent 吗？**

## 二、Agent 必要性的三条件

三条件必须**同时满足，缺一不可**。

### 2.1 条件一：业务包含"多步骤"

如果一个业务只用一个单步 Prompt 就能完成，根本不需要 Agent。所有处理逻辑在一个大模型的黑盒里一次性完成，就是 Prompt Engineering 范式。

**判断方法**：画出该业务从输入到输出的流程图。如果只需要 1 个 LLM 调用就完成（情感分析、文本翻译、单段摘要），就是单步。如果需要 2 个或更多 LLM 调用串联（先抽取实体 → 再生成结构化摘要 → 再做事实核查），才是多步。

**多步骤的边界不是步骤数量，而是"步骤之间是否有状态依赖"**：
- 步骤 A 的输出是步骤 B 的输入，且步骤 B 的 prompt 写法因步骤 A 的输出而不同 → 真多步
- 把 3 个独立任务串起来执行（生成标题 + 生成正文 + 生成标签）→ 仍属单步

### 2.2 条件二：业务需要"工具调用"

如果业务完全靠模型自身知识就能完成（常识问答、风格改写），用 Prompt Engineering。只有当业务需要 AI 操作外部世界（查数据库、调 API、写文件、发邮件），才需要 Agent 形态。

**判断方法**：列出该业务执行过程中需要的所有外部数据源和系统。
- ≤ 3 个数据源、≤ 5 个动作 → Prompt Engineering 或轻量 Workflow
- 5+ 个工具协同、工具间有依赖关系 → 真 Agent 形态

**陷阱提醒**：工具数量的"虚假膨胀"。把"调用一个 LLM"也算"工具"，5 个 LLM 调用堆叠不是 Multi-Agent——真正的 Multi-Agent 必须是"具备自主决策能力的 Single Agent"之间的协作。

### 2.3 条件三：业务价值 > 业务代价

最容易被忽视的一个条件。

**价值侧要算清楚**：
1. AI 介入后能为业务节省多少时间/人力/错误成本？
2. 这个节省在企业战略上是否重要？
3. 面向用户的功能是否能带来留存、转化、口碑上的可量化收益？

**代价侧要算清楚**：
1. 模型的 Token 成本（高频调用场景下成本可观）
2. 工程投入（Prompt 调优、工具开发、Guardrails、监控）
3. 维护成本（Prompt 漂移、模型升级、边界情况处理）
4. 风险成本（错误输出的业务代价、合规成本）

**硬约束**：P 维度（Performance Constraints）拥有一票否决权——业务是否要求响应时间必须 < 1 秒？如果是，哪怕场景再复杂，也不能使用需要长时间循环思考的 Agent。

**判断算式**：
- 价值/代价比 > 3 → 建议立项
- 1-3 → 慎重评估
- < 1 → 放弃 Agent 化，用更简单方案替代

## 三、简单优先原则：能用 Prompt / Workflow 解决，就不 Agent 化

架构选择应从简单到复杂，优先级：

1. **Prompt Engineering**（情感分析、文本翻译、单段摘要、风格改写）
2. **Workflow / Chain**（固定流程的报告生成、批量数据处理、多步骤的标准化任务）
3. **Single Agent**（开放式客服、未知 Bug 排查、个性化助手）
4. **Multi-Agent**（复杂研究任务、多模态内容生产、企业级数字员工）

Workflow 范式"能解决 80%-90% 的工程落地问题"。绝大多数企业场景应停在 Workflow 这一层，不应上 Agent 或 Multi-Agent。

**美工刀比喻的工程含义**：多花 10 倍工程投入，得到可能是 5% 边际效果提升——这不叫 ROI，叫浪费。

## 四、快速场景扫描五步法

配合 C.U.P. 评估表，可在 1 小时内完成多个候选场景的必要性判断。

**Step 1：列出候选场景（10 分钟）**
业务方提供 5-10 个"想用 AI 解决"的场景清单，每场景一句话：谁在什么场景下要完成什么任务。

**Step 2：知识类 vs 执行类粗筛（10 分钟）**
把每个场景归到知识类（知识获取/理解/生产）或执行类（流程自动化/工具调用/决策辅助）。
- 文档摘要（知识类）→ Prompt Engineering
- 工单自动分配（执行类）→ Workflow
- 未知 Bug 排查（执行类）→ 真正需要 Agent

**Step 3：C.U.P. 三维细评（20 分钟）**
- **C 复杂度**：交互是单轮还是多轮？是否需要多模态？任务完成仅靠模型知识还是需要外部工具数据？流程是单步还是多步？
- **U 不确定性**：输入边界是否清晰？执行路径是否固定？输出是否有客观评价标准？
- **P 性能约束**：业务是否要求 < 1 秒响应？是否高吞吐低价值场景？

**Step 4：三条件必要性判断（10 分钟）**
- 包含"多步骤"？（多步骤 ≠ 多个独立任务）
- 需要"工具调用"？（不是调用 LLM，是调用外部系统）
- 价值/代价比 > 3？

三个问题都答"是"的场景，进入立项流程。

**Step 5：产品小样最终验证（5-10 天）**
对通过评估的场景，用 1 周时间构建产品小样（Prototype），向业务方直观展示 AI 的能力边界和实际效果。**Demo 容易、产品难**——PM 不能只看 Demo 觉得可行就立项，必须在 MVP 阶段就用真实业务数据验证。

## 五、5 类必要性判断反模式

| 反模式 | 表现 | 应对 |
|-------|------|------|
| **因为技术火就立项** | "Multi-Agent 是趋势"作为立项依据 | 选型基于业务熵分布，不是技术热度 |
| **把"AI 替代人"当立项前提** | 直接做"AI vs 人"二选一 | 严格判断情感劳动、复杂案例处理、合规要求 |
| **把"创意性场景"当万能理由** | "让 AI 帮我们做营销创意" | 结果熵模糊场景改用"对赌式小样"验证 |
| **把"试用一下"当立项** | 立项不严格，试用才发现价值/代价比<1 | 立项前必过三条件 |
| **把"数据基础"当默认前提** | 不验证数据是否存在/质量如何 | 先确认数据前提 |

## 六、PM 行动清单

看完本节后：

1. **建立"必要性是 PM 第一关卡"的意识**：大多数场景停在 Prompt / Workflow，不要被"上 Agent"诱惑
2. **对每个候选场景套用三条件**：多步骤 + 工具调用 + 价值>代价，缺一不可
3. **用五步法做 1 小时场景扫描**：粗筛→细评→必要性判断→小样验证
4. **避开 5 类反模式**：技术火 / 替代人 / 创意性 / 试用一下 / 数据默认
5. **遇 25 分制评估表（2.1 节）分数 < 12 分的场景，直接放弃 Agent 化**：用 Prompt / Workflow 解决
