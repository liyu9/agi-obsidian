# 2.2 业务熵值评估：用阿什比定律判断业务的不确定性格局

> **核心结论**：业务的不确定性（熵）必须由系统的不确定能力（熵）来匹配——熵-架构匹配。
> **判断铁律**：用"输入熵 / 过程熵 / 结果熵"三维评估业务，C.U.P. 中 P 拥有一票否决权。
> **底线思维**：避免 Over Design（低熵业务用了复杂架构）和 Under Design（高熵业务用了简单架构）两个坑。

## 一、为什么要先评估业务的"熵"

PM 启动 Agent 项目时最易犯的错是**先选型再评估**——看到 Multi-Agent 火就想上 Multi-Agent，看到 Workflow 简单就用 Workflow 套所有场景。这种"工具先行"思路会导致两个极端：要么在确定性场景里过度设计（Over Design），要么在高度不确定性场景里简化失败（Under Design）。

L01 把根因讲清楚：AI 圈概念满天飞、极度混乱，同一个词在不同人嘴里意思可能完全不一样。解药是**阿什比定律（Ashby's Law）——"只有多样性才能对抗多样性"（Only variety can destroy variety）**。控制论含义是：一个系统要能控制另一个系统，控制方的状态多样性必须大于等于被控方的状态多样性。

映射到 AI 选型：**业务的不确定性（熵）必须由系统的不确定能力（熵）来匹配**。一个确定性极低的业务流程，不应该用一个确定性极强的 Workflow 去套；反之，一个完全可枚举的流程，也不应该用 Multi-Agent 去做无谓消耗。

L04 进一步给出工程化判断方法——**C.U.P. 三维评估模型**（Complexity、Uncertainty、Performance Constraints）。U（Uncertainty）是核心维度，P 拥有一票否决权。

## 二、业务熵的三维度

业务熵不是一个单维度的"难不难"问题，而是三个独立维度的组合。

### 2.1 输入熵：边界清晰 vs 边界模糊

**输入熵衡量的是：业务任务的输入是否能被预先枚举？**

- **低输入熵**：输入边界清晰，例如"读取标准化的发票 OCR 结果"——输入字段是固定的几种
- **高输入熵**：输入边界模糊，例如"开放式客服助手"——你永远猜不到用户下一句会问什么

**PM 评估方法**：列出该业务过去 3 个月的真实输入样本（来自工单系统、用户日志、表单记录），看类型分布。如果 80% 以上的输入可以归到 5-10 个固定类别，输入熵低；如果类型分散到几十种以上且新类别不断出现，输入熵高。

**极端陷阱**：L34 提到的 ChatBI 失败案例——想做"对话式数据分析"，但企业里"想要分析的那个数据根本不存在"或"质量很差的噪声数据"或"同样语义存了无数份"。这是输入熵的极端形态：输入端连基本数据前提都不满足，任何上层 AI 架构都救不回来。

### 2.2 过程熵：固定路径 vs 未知路径

**过程熵衡量的是：从输入到输出的执行路径是否能被预先编排？**

- **低过程熵**：执行路径固定，例如"OCR 识别 → 验真 → 计算金额 → 写入系统"。每一步都有明确输入输出，可被硬编码成 Workflow
- **高过程熵**：执行路径未知，例如"搜索信息后发现此路不通，需要动态换策略、修改大纲"。每一步走哪、怎么走、走到哪里停，都不能预先确定，必须由模型在运行时自主决定

**PM 评估方法**：画出该业务过去 3 个真实案例的执行流程图，看流程分支数。如果 80% 案例可以用同一条主干路径走完，过程熵低；如果不同案例的流程几乎都不一样，过程熵高。

L02 的 ReAct 范式（Reasoning + Acting 循环）就是为高过程熵场景设计的：模型每一步先推理（决定下一步做什么），再行动（调用工具），再观察（评估结果），循环到目标完成。ReAct 的存在意义，就是为了应对过程熵。

### 2.3 结果熵：标准明确 vs 标准模糊

**结果熵衡量的是：输出的好坏是否有客观评价标准？**

- **低结果熵**：标准明确，例如"判断一个风控指标是否合规"——通过/不通过有明确规则
- **高结果熵**：标准模糊，例如"产出一篇具有深度的行业分析报告"——连用户自己都很难量化其好坏

**PM 评估方法**：问业务方一个问题——"请用 5 个具体指标告诉我输出合格的标准是什么"。如果业务方能在 10 分钟内给出 5 个具体指标（字数、必含数据点、引用来源数等），结果熵低；如果业务方说"看起来专业就行"或"凭感觉"，结果熵高。

**Demo 陷阱**：L34 提到——"有一大类问题，很容易想象、也很容易建 Demo，但极难变成产品。自动驾驶就是典型：绕着街区 Demo 很容易，做成产品需要十年。"Demo 阶段标准是模糊的（"看起来能跑"），产品阶段标准是具体的（"100 种边界情况都要处理"）。PM 必须意识到自己面对的是哪种结果熵。

## 三、熵-架构匹配矩阵

把"业务熵"和"架构范式"放在一起，得到 4×3 矩阵：

| 业务熵类型 | Prompt Engineering | Workflow | Single Agent | Multi-Agent |
|------------|--------------------|----------|--------------|-------------|
| 低输入 + 低过程 + 低结果 | ✓（最佳匹配） | ✓ | 不必要 | 过度设计 |
| 任意 1 维高熵 | 不足 | ✓（最佳匹配） | ✓ | 可选 |
| 任意 2 维高熵 | 不足 | 不足 | ✓（最佳匹配） | ✓ |
| 3 维都高 | 完全不可用 | 严重不足 | 不足 | ✓（最佳匹配） |

四种匹配结果的命名：

1. **Order（秩序）**：低熵业务 + 简单架构。ROI 最高的"甜点"状态
2. **Sweet Spot（甜蜜点）**：熵分布与架构能力刚好匹配。这是"应该"状态
3. **Over Design（过度设计）**：低熵业务 + 复杂架构。"浪费"状态——用 Multi-Agent 跑 5 步确定流程
4. **Under Design（设计不足）**：高熵业务 + 简单架构。"灾难"状态——用 Workflow 套 1000 种分支的客服场景

PM 选型的第一目标不是"用上最先进的技术"，而是"避免掉进 Over Design 和 Under Design 这两个坑"。L01 的比喻：**面对一个工程需求，究竟是用一把精美的美工刀去建大楼，还是雇佣一支专业的施工队去修一扇小窗户？**——选型错位的代价远高于选型保守。

## 四、C.U.P. 三维评估模型

熵评估只是 C.U.P. 三维之一，三个维度必须综合考虑：

- **C（Complexity 复杂度）**：交互复杂性（单轮 vs 多轮多模态）+ 依赖复杂性（仅模型 vs 调用工具数据）+ 过程复杂性（单步 vs 多步）
- **U（Uncertainty 不确定性）**：即本节三维度（输入/过程/结果）
- **P（Performance Constraints 性能约束）**：响应时间约束（是否要求 < 1 秒）+ 成本约束（高吞吐低价值场景的 Token 消耗）

**P 拥有一票否决权**——哪怕场景再复杂，< 1 秒的响应时间要求就直接否掉所有需要循环思考的 Agent。

L04 末尾的金句："**不要靠直觉去猜，要去精准度量（Don't Guess, Measure）**"。把"难不难"的主观感受，拆解成"输入熵/过程熵/结果熵"三个可观察的客观维度，再去和架构能力做匹配——这正是熵评估的精髓。

## 五、熵评估的 3 个反模式

| 反模式 | 表现 | 应对 |
|-------|------|------|
| **凭直觉判断** | "这个需求看起来挺难的" | 用三维评估 + C.U.P. 取代主观感受 |
| **不验证数据前提** | 直接上 Agent 才发现数据不存在 | 立项前先确认数据是否可获得 |
| **忽略 P 维度** | 没问响应时间要求 | P 维有一票否决权，先问业务方 |

## 六、PM 行动清单

看完本节后：

1. **每个候选场景必过熵评估**：用输入熵/过程熵/结果熵三维打分，输出到场景表
2. **画熵-架构匹配矩阵**：把每个候选场景的熵分布与四种范式做对应，识别 Over Design / Under Design
3. **联合 C.U.P. 三维评估**：U 是核心，P 有一票否决权
4. **问业务方 3 个问题验证数据前提**：数据是否存在？质量如何？是否可结构化访问？
5. **遇 25 分制评估表（2.1 节）分数 < 12 分的场景直接放弃**：熵评估再准也救不了低 ROI 场景
