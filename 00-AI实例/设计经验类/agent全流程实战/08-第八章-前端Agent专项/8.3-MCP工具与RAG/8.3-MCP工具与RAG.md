# 8.3 MCP 工具与 RAG：让前端 Agent 真正"能办事"

> **核心结论**：工具调用解决"办事能力"，RAG 解决"知识更新"——两者一起让 Agent 从"聊天"走向"做事"。
> **判断铁律**：不要无脑上 RAG——先搜索引擎，再全文嵌入，最后才经典 RAG。
> **底线思维**：MCP 工具的"USB-C 协议"思维 + RAG 的"先简后繁"原则，是前端 Agent 工程化的两大基石。

## 一、本节定位

8.1-8.2 解决了"前端如何调 LLM API + 如何编排工作流"，但智能体真正"能办事"还需要两块能力：

1. **工具调用（Tool Use）**：让大模型能查数据库、读文件、调 API、执行命令
2. **检索增强（RAG）**：让大模型能基于"它训练时不知道的知识"回答问题

本节聚焦这两块能力在**前端/BFF 架构下的特殊实现**——重点不是协议本身（那是 OpenAI/Anthropic 的事），而是**前端工程如何把它们集成进现有应用**。MCP（Model Context Protocol）是 2025 年才出现的新标准，本节会重点展开它对前端 Agent 工具开发范式的影响。

## 二、前端多轮对话的基础设施

### 2.1 四大核心概念

实现多轮对话之前必须先定义 4 个核心概念（这套术语在 MCP 工具调用、RAG 检索增强中都会复用）：

| 概念 | 定义 | 技术实现 |
|------|------|---------|
| **会话（Session）** | 标记一轮连续对话；相同 session 的 Agent 之间才能共享数据 | UUID |
| **记忆（Memory）** | 记录之前的内容 | 企业级用 Redis/数据库；前端 demo 用内存对象 |
| **时间线（Timeline）** | 规定每个时间段（0-3min 自我介绍 / 3-10min 项目讨论……）内 AI 应聚焦的目标 | 配置 + prompt 切换 |
| **目的表（Purpose Table）** | "目的 → 行动方针"映射；AI 根据当前时间线筛选目的，生成具体 actions | 静态配置 |

### 2.2 异步协同：思考与对话并行

**23 讲最关键的设计洞见：AI 思考必须与用户回答并行执行**。在面试官项目中：

```
T0: AI 提问 "请描述 JS 事件循环"
T0+1s: 用户开始打字
T0+1s: AI 同时启动 "思考 Agent"，准备下一轮策略
T1: 用户提交回答
T1+ε: 思考 Agent 输出 "行动方针"（与用户实际回答无关，针对"所有可能回答"做预案）
T1+δ: 对话 Agent 根据用户实际回答 + 行动方针 → 下一轮提问
```

**前端特殊性**：传统 Web 业务是"同步阻塞"，前端工程师的思维惯性是"等响应再处理"。**AI 应用必须主动设计成异步并行**——这就是为什么 24 讲要专门讲"读写分离"。

### 2.3 时间线（Timeline）配置

典型"前端面试时间线"配置：

| 时间段 | 焦点 | 关键能力考察 |
|--------|------|--------------|
| 0-3 min | 自我介绍 | 信息收集 |
| 3-10 min | 项目讨论 | 技术深度 |
| 10-17 min | 技术讨论 | 知识面 |
| 17-25 min | 代码/算法 | 编码能力 |
| 25-30 min | 非技术问题 | 软素质 |
| 30-32 min | 反问 | 候选人主动性 |
| >32 min | 结束 | 给出评价 |

**时间线的价值：让 AI 拥有"节奏感"**——避免一上来就问算法、避免在算法阶段问软素质。这是"Prompt Engineering"中"动态上下文"的标准实践。

## 三、API 读写分离设计

### 3.1 为什么需要读写分离

SSE 协议只支持 GET 请求（HTTP 规范决定），但很多场景需要 POST 提交长文本/文件。这就需要"读写分离"：

- **POST（写）**：提交用户输入（可能很大、可能是文件），返回 session_id 或 task_id
- **GET（读）**：用 session_id/task_id 建立 SSE 通道，接收流式结果

**读写分离的工程好处**：
1. **GET 连接可以长挂**：用户提交完即可离开页面，SSE 在后台持续推数据
2. **POST 不阻塞**：用户提交后立即释放请求，可以并行提交多个任务
3. **可观测性更强**：读写是两条独立的 HTTP 通道，可以分别埋点、限流

### 3.2 读写分离的实现模式（EventChannel）

```
// 写：POST
const { taskId } = await fetch('/api/submit', {
  method: 'POST',
  body: JSON.stringify({ message: '...' })
});

// 读：SSE
const es = new EventSource(`/api/stream?taskId=${taskId}`);
es.onmessage = (e) => {
  const { uri, delta } = JSON.parse(e.data);
  applyDelta(uri, delta); // 用 jsonuri 应用增量
};
es.onerror = () => es.close();
```

**前端特殊性**：浏览器对 EventSource 有自动重连机制，但**重连时会丢失 session 上下文**。生产实现里通常会在重连时用 lastEventId 让 Server 续传。

## 四、人设、上下文与记忆

### 4.1 人设（Role）

人设 = 角色定义 + 任务定义 + 技能清单 + 行为约束。一个典型的"AI 前端面试官"人设提示词：

```
## 角色
你是月影，字节跳动的前端面试官

## 任务
根据职位需求和候选人背景，提出有针对性的前端技术面试问题，并评估其专业能力、工程实践经验及团队协作潜力。

## 技能
- HTML / CSS / JavaScript
- React / Vue 等主流框架
- 浏览器原理与性能优化
- 前端工程化（Webpack / Vite）
- 跨端开发（小程序 / Flutter）
- 计算机基础（数据结构与算法）

## 约束
- 不要连续追问同一知识点
- 根据候选人级别调整问题深度（初级/中级/高级）
- 候选人答错时给一次提示机会
```

### 4.2 上下文（Context）

上下文包括 3 类：
- **会话上下文**：当前 session 的所有历史消息
- **业务上下文**：候选人简历、岗位描述（JD）、公司信息
- **环境上下文**：当前时间、面试进度（时间线位置）、候选人已展示的能力

**关键设计**：把"岗位描述（JD）"作为独立 prompt 文件注入，**JD 是高频变化的业务变量**，把它从人设中拆出来，可以做到"换岗位不换人设"。

### 4.3 记忆（Memory）三层结构

| 层级 | 存储位置 | 内容 | 生命周期 |
|------|----------|------|---------|
| **短期记忆** | 内存 / sessionStorage | 当前 session 的对话历史 | session 内 |
| **中期记忆** | Redis / SQLite | 最近 N 天的对话摘要、用户偏好 | 天/周 |
| **长期记忆** | 数据库 + 向量库 | 用户画像、知识库 | 永久 |

8.3 节的 RAG 部分会专门讲"长期记忆"中的"知识库"是怎么存的。

## 五、Tool Use：大模型使用工具

### 5.1 OpenAI 工具调用协议

OpenAI 在 2023 年推出 tool use 能力（也称 function calling），后续几乎所有兼容 OpenAI 协议的大模型都支持。基本流程：

1. 客户端在请求中传 `tools` 数组，每个 tool 描述其名称、用途、参数 schema
2. 模型推理时如果决定调用工具，会在响应中返回 `tool_calls` 字段（包含 tool 名 + 参数 JSON）
3. 客户端执行工具，拿到结果后再发一次请求（把 tool 结果作为 `tool` role 的消息传入）
4. 模型基于工具结果继续推理

### 5.2 前端 Tool Use 的特殊性

| 特殊性 | 工程含义 |
|--------|---------|
| **工具执行在 BFF** | 浏览器侧不适合执行命令、读本地文件，所有 tool call 都应通过 BFF 转发到能执行的运行时 |
| **工具注册在 Server** | tools 配置通常在 BFF 集中管理，前端只负责发起请求和展示结果 |
| **工具结果可视化** | UI 上要让用户清楚"AI 调用了哪个工具、参数是什么、结果是什么"——LLM 应用可观测性的基本要求 |

## 六、MCP：Model Context Protocol

### 6.1 什么是 MCP

MCP（Model Context Protocol）是 **Anthropic 在 2025 年推出的开放标准**，目标是**统一 LLM 与外部工具、系统和数据源的交互方式**。

**类比**：
- OpenAI 的 tool use 是"每个模型自己一套调用规范"
- MCP 是"USB-C 协议"——只要遵守 MCP 协议，工具可以被任何支持 MCP 的 LLM 调用

**协议三要素**：
- **MCP Server**：暴露工具的服务端，定义工具列表 + 每个工具的输入 schema
- **MCP Client**：嵌入在 LLM 应用（Claude Desktop、Cursor、自研 Agent）中的客户端，负责发现和调用 Server 上的工具
- **传输方式**：支持 stdio（本地进程间通信）、SSE（HTTP 长连接）、WebSocket 等

### 6.2 用 @modelcontextprotocol/sdk 自建 MCP Server

```
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';

const server = new McpServer({ name: 'Demo', version: '1.0.0' });

server.tool('listFiles', '列出指定目录下的文件',
  { path: z.string() },
  async ({ path }) => {
    const { stdout } = await exec(`ls -la ${path}`);
    return {
      content: [{ type: 'text', text: `已获取到目录 ${path} 文件列表:\n\`\`\`\n${stdout}\`\`\`\n` }]
    };
  }
);

const transport = new StdioServerTransport();
await server.connect(transport);
```

**关键点**：用 zod 定义参数 schema，SDK 自动生成 JSON Schema 给 LLM。

### 6.3 MCP 对前端 Agent 的影响

1. **工具生态**：第三方厂商提供 MCP Server，前端 Agent 可以"开箱即用"——GitHub MCP、Notion MCP、Slack MCP、文件 MCP 等
2. **前端工具开发新角色**：前端工程师可以**专门为某个内部系统写 MCP Server**，让所有 LLM 应用都能调用
3. **协议可移植**：今天用 Claude Desktop 调试的 tool，明天可以零成本迁移到自研 Agent、Cursor、Trae

**前端特殊性**：MCP Server 通常运行在本地进程（stdio 模式）或局域网服务（SSE 模式），前端工程师最熟悉的"启动 Node 进程 + 提供 HTTP 接口"心智模型完全适用——这是 MCP 在前端社区能快速流行的根本原因。

## 七、RAG：检索增强生成

### 7.1 为什么需要 RAG

大模型的知识截止于训练数据，对于以下场景**必须有外部知识源**：
- 最新事件（如 2026 年 6 月的产品发布会）
- 企业内部知识（产品文档、代码库、Wiki）
- 长尾知识（特定领域、特定客户、特定项目）

**RAG 的本质：在模型推理前，把相关知识"喂"进 prompt**。

### 7.2 RAG 的三种替代方案（决策树）

| 方案 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **搜索引擎** | 公开资料 / 已有内部搜索服务 | 零成本接入 | 仅匹配关键词，不理解语义 |
| **超长上下文全文嵌入** | 单轮问答、内容可控（员工手册） | 实现最简 | 成本高、多轮对话浪费 token |
| **结构化目录+文件读取** | AI Coding、项目文档 | 实时性强 | 多轮执行耗 token |
| **经典 RAG（向量库）** | 长尾知识、跨文档语义检索 | 真正语义匹配 | 需建库、需维护 |

**关键洞见**：**不要无脑上 RAG**。很多企业花几个月搭向量库，结果发现把员工手册直接喂 prompt 就能解决 80% 的问题。先用最简单的方案，不够再加 RAG。

### 7.3 经典 RAG 的 5 个核心组件

1. **Embedding 模型**：把文本压缩成语义向量（如 `text-embedding-3-small`、bge-m3、bce-embedding）。模型质量直接决定检索质量
2. **向量数据库**：存储向量 + 原始文本片段（Milvus / Qdrant / Chroma / vectra）。支持相似度检索（cosine / euclidean / dot product）
3. **切块策略（Chunking）**：把长文档切成合适大小的片段（通常 200-1000 token），保留 overlap
4. **Retriever**：给定 query，返回 top-k 最相似的片段
5. **Reranker**（可选）：用更强的模型对 top-k 重排序，进一步提升精度

### 7.4 语义检索 vs 关键词检索

经典例子：
- 用户问："上海有哪些适合小孩的亲子餐厅？"
- 知识库文章标题："儿童友好的家庭用餐场所推荐"

关键词检索（Elasticsearch 之类）几乎不可能匹配。**向量检索通过语义相似度可以完美匹配**——这就是 RAG 的核心价值。

### 7.5 通过 MCP Server 把项目向量化

38 讲演示了一个非常前沿的用法：**用 MCP Server 把任意项目的代码/文档向量化**：

```
server.tool('vectorizeProject', '把指定项目向量化存储到 vectra',
  { path: z.string() },
  async ({ path }) => {
    // 1. 遍历 path 下的代码/文档文件
    // 2. 用 embedding 模型生成向量
    // 3. 存入 vectra
    return { content: [{ type: 'text', text: `已向量化 ${count} 个文件` }] };
  }
);
```

**范式意义**：AI Coding 工具（Trae、Cursor）可以自动维护项目的语义索引，让"我昨天写的代码今天 AI 也能查到"成为现实。

### 7.6 端到端 RAG 流程

```
[离线] 文档 → 切块 → embedding → 向量库
                                ↓
[在线] 用户问题 → embedding → 相似度检索 top-k → 拼接 prompt → LLM → 答案
                                  ↑
                          原始文本片段
```

**前端 Agent 在这条链路里承担的角色**：
- **配置层**：提供"知识库管理"UI（上传文档、查看检索日志、调整参数）
- **查询层**：把用户问题发给 BFF，BFF 完成 embedding + 检索 + prompt 拼接
- **展示层**：在 UI 上展示"AI 回答 + 引用的原文片段 + 相似度分数"，让用户能验证答案来源

## 八、PM 行动清单

看完本节后：

1. **多轮对话的 4 大概念先固化**：Session / Memory / Timeline / Purpose Table
2. **异步并行是 AI 应用的思维范式**：思考与对话并行，不等响应再处理
3. **读写分离是流式应用的工程标配**：POST 提交 + SSE 读流
4. **MCP 是工具调用的"USB-C 协议"**：能写 MCP Server 就不要写单模型适配
5. **RAG 的"先简后繁"原则**：搜索引擎 → 全文嵌入 → 文件系统 → 经典 RAG
