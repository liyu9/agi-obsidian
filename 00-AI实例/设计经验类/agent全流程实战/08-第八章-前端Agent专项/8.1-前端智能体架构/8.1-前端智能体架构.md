# 8.1 前端智能体架构：浏览器里的 Agent 长什么样

> **核心结论**：前端不是推理宿主，是 LLM 的呈现层——必须用"前端薄壳 + BFF 中转 + LLM API 集群"三层架构。
> **判断铁律**：API Key 永远不进浏览器，工具调用永远走 BFF 代理，JSON 流式永远在服务端解析。
> **底线思维**：前端特殊性（网络边界 / CORS / 流式 / JSON 封闭）四条铁律决定架构形态。

## 一、前端 Agent 的四个不可回避的现实

第二至六章的 Agent 方法论是"语言无关、平台无关"的通用框架。但当 Agent 必须运行在浏览器里时，会撞上 4 条硬约束：

| 约束 | 来源 | 工程含义 |
|------|------|---------|
| **网络边界** | 浏览器只能主动发请求 | 前端不是推理宿主，所有 LLM 调用走 HTTP API 或 WebSocket |
| **CORS 与 Key 暴露** | API Key 放在前端 = 公开 | 必须有 BFF（Backend For Frontend）层做代理 |
| **流式优先** | 推理时间以秒计 | 必须 SSE / Fetch Stream，不能等齐再渲染 |
| **JSON 封闭性** | 模型输出是封闭结构 | 解析必须"等齐"，与流式渲染天然矛盾 |

**这 4 条共同决定了前端 Agent 的整体架构：前端薄壳 + BFF 中转 + LLM API 集群**。

## 二、整体架构：三层视图

把"调文本模型、调图像模型、调语音模型"三类典型调用串起来，得到前端 Agent 的稳定三层架构：

```
┌──────────────────────────────────────────┐
│  第一层：浏览器（View 层）                  │
│  - UI 渲染 / 用户输入 / 富文本展示          │
│  - 维护 session / memory / timeline       │
│  - 处理 SSE / Fetch ReadableStream       │
│  - 用 jsonuri + JSONParser 还原 JSON      │
└──────────────────────────────────────────┘
              ▲          ▲
              │ SSE/POST │ SSE/POST
              ▼          ▼
┌──────────────────────────────────────────┐
│  第二层：BFF / Edge 函数（Server 层）       │
│  - 代理大模型 API，隐藏 API Key            │
│  - 合并多模型调用（文本+图像+语音）         │
│  - 读写分离、EventChannel 异步通知         │
│  - 工作流节点的"汇聚与再分发"               │
└──────────────────────────────────────────┘
              ▲          ▲
              │ HTTPS    │ HTTPS
              ▼          ▼
┌──────────────────────────────────────────┐
│  第三层：模型 API 集群（Model 层）          │
│  - 文本：Deepseek / Moonshot / GPT        │
│  - 图像：FLUX / SD / 火山视觉             │
│  - 语音：火山 TTS / CosyVoice             │
│  - 工具/嵌入：bge-m3 / text2vec           │
└──────────────────────────────────────────┘
```

**三层的职责边界**：
- **View 层** 只关心两件事：拿数据、画界面；绝不直接放 API Key
- **BFF 层** 是前端的"智能体运行时"，把多模型输出按 JSON 协议汇聚成单一 SSE 流推回浏览器
- **Model 层** 完全是黑盒，前端只关心协议（OpenAI 兼容、Coze、火山私有协议）

## 三、文本大模型的浏览器调用范式

### 3.1 最小可运行闭环（5 步）

1. 注册大模型平台（Deepseek / Moonshot / 通义 / 智谱），拿到 API Key（**Key 在浏览器侧仅用于开发演示，生产必须迁到 BFF**）
2. 创建前端项目（Vue / React + Vite + TypeScript）
3. 配置 `.env.local`，把 Key 放在 `VITE_XXX_API_KEY`
4. `fetch('https://api.xxx.com/chat/completions', { ... })`，body 严格遵循 OpenAI 兼容协议
5. 拿到 `data.choices[0].message.content` 渲染即可

**关键认知**：Deepseek / Moonshot / 通义千问 / GPT-4 / 智谱 GLM / Ollama（本地）几乎都遵循 **OpenAI Chat Completion 协议**。前端工程师只要学会一套，就能切换到任意一家——这是前端 Agent 在协议层的最大红利。

### 3.2 为什么必须流式

大模型的标准模式是"提交数据 → 服务端推理 → JSON 整体返回"。**问题在于推理耗时和 token 数线性相关**——写一篇千字作文可能要 30 秒以上，等齐再返回前端体验不可用。

主流大模型平台默认采用 SSE（Server-Sent Events）流式响应，**逐 token 实时返回**。前端处理路径：

1. `fetch` 的 `response.body` 是一个 `ReadableStream<Uint8Array>`
2. 用 `TextDecoder` 解码成字符串
3. 按 SSE 协议按行解析（每行以 `data: ` 开头，`data: [DONE]` 结束）
4. 每解析出一段 `delta.content` 就触发一次 UI 更新

**本质上是把"HTTP 响应"当成"事件流"来消费**——这是后续 Ling 框架、MCP 工具调用、Agent 多步推理统一的传输底座。

## 四、多模态在前端的实现

### 4.1 图像生成：FLUX + 轮询

图像生成和文本生成的关键差异：

| 维度 | 文本 | 图像 |
|------|------|------|
| 输出格式 | 增量 token | 整张图 URL |
| 耗时 | 1-30 秒 | 5-60 秒 |
| 协议 | SSE 流式 | 提交任务 → 轮询状态 |
| 失败重试 | 增量无意义 | 必须可重试 |

**典型调用模式**：
1. POST 提交 prompt → 拿到 `task_id`
2. 轮询 GET 任务状态（`Pending` / `Ready` / `Failed`）
3. Ready 时从响应中取 `sample`（图片 URL）
4. 前端 `<img src="...">` 渲染 + 展示进度条

**前端特殊性**：图像生成的"等待感"比文本更强，**必须设计显式的进度反馈**（进度条、占位骨架屏、已耗时提示），否则用户会误以为页面卡死。

### 4.2 语音合成：火山 TTS 私有协议

**语音合成的特殊性在于音频流是二进制**。火山 TTS 的典型做法：
1. 前端发起 POST，body 含文本 + 音色 ID + APP ID + AccessToken
2. 服务端返回二进制音频流（PCM/MP3）
3. 前端用 `AudioContext.decodeAudioData` 解码 → `AudioBufferSourceNode` 播放

**前端特殊性**：浏览器对音频自动播放有严格限制，**必须在用户首次交互后才能播放音频**；移动端还要处理 iOS Safari 的 AudioContext 唤醒问题。

### 4.3 视觉理解（图片理解）

视觉理解模型（多模态）通常接收 **base64 图片 + 文本 prompt**，返回文本结果。技术上仍是 OpenAI 兼容的 chat 接口，区别只是 `messages.content` 数组允许混合 `image_url` 和 `text` 类型：

```
messages: [
  {
    role: "user",
    content: [
      { type: "text", text: "这张图片里有什么？" },
      { type: "image_url", image_url: { url: "data:image/png;base64,xxx" } }
    ]
  }
]
```

**这是前端 Agent 做"拍照记单词"、"AI 面试官"等场景的基础协议**。

## 五、流式与 JSON 的结构性矛盾

### 5.1 矛盾的来源

**前端 Agent 最经典的工程难题**：
- **流式**：用户体验要求"逐 token 渲染"
- **JSON**：前端数据结构要求"封闭、完整、可解析"
- **矛盾**：JSON 在 `}` 到达前是非法数据，传统 `JSON.parse` 必失败

### 5.2 解决思路：动态 JSON 解析

业内三派做法：

| 方案 | 优点 | 缺点 |
|------|------|------|
| NDJSON（每行一个 JSON） | 简单 | 限制模型输出，影响推理 |
| JSONStream 库 | 通用 | 仅 Server 端可用 |
| **动态 JSON Parser**（Ling 方案） | 真正流式、前端可用 | 需要自研或依赖 Ling |

**Ling 框架的 `JSONParser` 思路**：
1. 把 JSON 当成**树形结构**，每个节点用一个 URI（如 `/outline/0/title`）定位
2. 流式到达的每段 token，按"当前是否在某个 key / value 内"更新对应 URI 的状态
3. 通过 `data` 事件 emit `{ uri, delta }`，前端订阅即可
4. 前端用 `jsonuri` 库把 URI 解析回 JS 对象，**不需要等齐**

### 5.3 落到代码：移除 Node 依赖

Ling 的 parser 原生依赖 `node:events`，要在浏览器使用需要替换为自定义 `EventEmitter`——替换后，**整套 JSON 流式解析逻辑可以在浏览器侧运行**。这正是 Ling 后续能直接在 Vue 项目里"边推边渲"的前提。

## 六、流式 JSON 的设计模式

09 讲把上面这套范式总结成一个可复用的设计模式：

1. **服务端**：模型输出流式 JSON → 用 JSONParser 切成 `{uri, delta}` 事件 → 用 SSE 推到浏览器
2. **浏览器**：订阅 SSE → 用 jsonuri 把增量应用到本地对象 → 响应式框架触发 UI 更新

**这个模式在 Ling 框架、多轮对话、RAG 中反复出现，是前端 Agent 工程化的"母模式"**。

## 七、与方法论总纲的对应

| 总纲方法论 | 本节前端特殊化 |
|------------|---------------|
| Agent = LLM + Planning + Memory + Tool | View（前端壳） + BFF（智能体运行时） + Model（LLM API） |
| Tool Use | Tool 全部走 BFF 代理，浏览器只发业务请求 |
| Memory | 前端维护 session / timeline / localStorage，BFF 维护 Redis |
| 流式输出 | SSE / Fetch ReadableStream，前端用 jsonuri 还原 JSON |
| 多模态 | 文本/图像/语音各自一套协议，但都过 BFF 统一出口 |

## 八、PM 行动清单

看完本节后：

1. **认准三层架构**：View（前端壳）+ BFF（智能体运行时）+ Model（LLM API 集群）
2. **API Key 永远不进浏览器**：生产环境必须走 BFF 代理
3. **流式优先**：大模型调用默认开 stream，不要等齐再渲染
4. **多模态分协议**：文本用 SSE 流式、图像用任务轮询、语音用二进制流
5. **前端进度反馈必做**：图像生成等待时间长，必须有进度条 / 骨架屏 / 已耗时提示
