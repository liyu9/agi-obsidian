# 5.2 协作模式：Multi-Agent 的 3 种核心架构

> **核心结论**：Multi-Agent 协作 = 3 种模式（监督 / 分布式 / 混合）——选错模式 = 协作失败。
> **判断铁律**：用任务复杂度 + 协作频率 + 容错要求 3 维度选模式。
> **底线思维**：简单任务用监督式，复杂任务用分布式，跨场景用混合式。

## 一、3 种核心协作模式

### 1.1 监督式（Supervisor Pattern）

**架构**：一个 Supervisor Agent + N 个 Worker Agent。

**运作方式**：
- Supervisor 接收用户任务
- Supervisor 拆解任务，分发给 Worker
- Worker 执行各自子任务
- Supervisor 汇总结果，统一输出

**适用场景**：
- 任务可被 Supervisor 清晰拆解
- Worker 之间不需要直接通信
- 需要中央决策

**优点**：
- 结构清晰、容易实现
- Supervisor 可统一监控 + 错误处理
- 调试相对简单

**缺点**：
- Supervisor 成为瓶颈
- Worker 之间无法直接协作

反面案例：某项目 Supervisor 处理 10 个 Worker，Supervisor 自己 Token 消耗占 60%，性能瓶颈。

### 1.2 分布式（Decentralized Pattern）

**架构**：N 个对等 Agent，无中央 Supervisor。

**运作方式**：
- Agent 之间通过消息队列 / 共享状态通信
- 任务可被任意 Agent 接收
- Agent 自主决定下一步给谁

**适用场景**：
- 任务路径不确定
- Agent 之间需要频繁协作
- 高容错要求

**优点**：
- 无单点瓶颈
- Agent 自主协作更灵活
- 单点失败不影响整体

**缺点**：
- 实现复杂
- 调试困难
- 容易陷入"循环协作"

反面案例：某项目用分布式架构，2 个 Agent 互相踢皮球，循环 20 次仍无结果。

### 1.3 混合式（Hybrid Pattern）

**架构**：监督 + 分布式的组合。

**运作方式**：
- 顶层有 Supervisor
- 底层有 N 个 Worker Group
- Group 内是分布式，Group 间是监督式

**适用场景**：
- 大型复杂任务
- 多业务领域
- 需要分层管理

**优点**：
- 兼具两种模式优点
- 适合复杂场景

**缺点**：
- 架构最复杂
- 维护成本最高

## 二、3 维度选型

| 维度 | 监督式 | 分布式 | 混合式 |
|------|--------|--------|--------|
| 任务复杂度 | 中 | 高 | 高 |
| 协作频率 | 低 | 高 | 中 |
| 容错要求 | 中 | 高 | 高 |
| 实施难度 | 低 | 高 | 中高 |

| 任务场景 | 推荐模式 |
|---------|---------|
| 5 步以内的清晰任务 | 监督式 |
| 10 步以上的高频协作 | 分布式 |
| 多业务领域的复杂任务 | 混合式 |
| 不可中断的关键任务 | 分布式 + 容错 |

## 三、通信协议：Agent 之间怎么"说话"

### 3.1 消息队列（Message Queue）

**适用**：监督式、混合式
**优点**：解耦、可监控、可重试
**缺点**：引入中间件依赖

**典型实现**：Kafka、RabbitMQ、Pulsar

### 3.2 共享状态（Shared State）

**适用**：分布式
**优点**：实现简单、Agent 自主读取
**缺点**：并发冲突需要解决

**典型实现**：Redis、共用数据库

### 3.3 协议选型

| 场景 | 推荐协议 |
|------|---------|
| Agent 数量 ≤ 5，结构稳定 | 共享状态 |
| Agent 数量 5-20，结构动态 | 消息队列 |
| Agent 数量 20+，多层架构 | 混合（消息队列 + 共享状态） |

## 四、协作的 5 个反模式

| 反模式 | 表现 | 应对 |
|-------|------|------|
| **Supervisor 瓶颈** | Supervisor Token 占 50%+ | 分层 + 减任务 |
| **死循环** | Agent 间循环引用 | 加最大跳数 |
| **踢皮球** | Agent 互相推诿 | 明确"谁负责什么" |
| **状态不一致** | Agent 看到不同状态 | 用单一状态源 |
| **通信开销过大** | Agent 通信消息过多 | 减少消息 + 合并通信 |

## 五、PM 行动清单

看完本节后：

1. **每个 Multi-Agent 项目必过 3 维度选型**：复杂度 / 协作频率 / 容错
2. **Supervisor 必加监控**：Token 占比、响应时间
3. **必设计最大跳数**：避免死循环
4. **必明确"谁负责什么"**：避免踢皮球
5. **通信协议按规模选**：≤5 共享状态 / 5-20 消息队列 / 20+ 混合
