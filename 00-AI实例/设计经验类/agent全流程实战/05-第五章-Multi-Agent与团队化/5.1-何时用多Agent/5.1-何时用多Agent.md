# 5.1 何时用 Multi-Agent：单 Agent 的局限与多 Agent 的必然

> **核心结论**：Multi-Agent 不是"更高级的 Workflow"——是处理"高过程熵 + 多角色协作"的必要架构。
> **判断铁律**：用 3 个标准判断——任务可拆解度 / 上下文隔离需求 / 角色专业差异度。
> **底线思维**：Multi-Agent 的复杂度是 Single Agent 的 3-5 倍——能用 Single 解决就不上 Multi。

## 一、为什么会有 Single Agent 的局限

Single Agent 的核心是"一个大脑包打天下"——一个 LLM 接收所有任务，自主决定下一步。这种架构在简单任务下表现良好，但在复杂任务下会出问题：

| 局限 | 原因 | 表现 |
|------|------|------|
| **上下文爆炸** | 长任务中历史信息堆积 | Token 超限、模型"忘记"早期信息 |
| **工具困惑** | 工具太多时选错 | AI 调用了不相关的工具 |
| **角色单一** | 同一大脑处理所有事 | 输出风格混乱、缺乏专业深度 |
| **失败传导** | 一个环节错全盘崩 | 单点失败导致任务整体失败 |

反面案例：某 AI 助手用 Single Agent 处理"研究 → 写作 → 审校"全流程，结果 3 个任务风格不统一，审校环节因上下文过满漏掉错误。

## 二、什么时候该用 Multi-Agent：3 个判断标准

### 标准 1：任务可拆解度

**问题**：这个任务能否拆成多个相对独立的子任务？
- **可拆解** → Multi-Agent
- **强耦合** → Single Agent

| 任务 | 可拆解度 | 适用 |
|------|---------|------|
| 研究 + 写作 + 审校 | 高 | Multi-Agent |
| 单步推理 | 低 | Single Agent |
| 多轮对话 | 低 | Single Agent |
| 多源信息整合 | 高 | Multi-Agent |

### 标准 2：上下文隔离需求

**问题**：子任务之间是否需要"互不干扰"？
- **需要隔离** → Multi-Agent
- **需要共享** → Single Agent

每个 Agent 只看自己需要的上下文，不被其他子任务干扰。好处：
- 单 Agent 上下文更短（更快、更准）
- 不同 Agent 可用不同模型（按需选型）
- 单点失败不影响整体

### 标准 3：角色专业差异度

**问题**：子任务是否需要"专业不同的大脑"？
- **差异大** → Multi-Agent
- **差异小** → Single Agent

反面案例：把"研究员 + 律师 + 医生"塞进一个 Single Agent，结果输出"四不像"——没有专业深度。

## 三、Multi-Agent 的 4 个核心收益

| 收益 | 含义 |
|------|------|
| **上下文隔离** | 每个 Agent 上下文独立，避免爆炸 |
| **工具专注** | 每个 Agent 拥有自己的工具集，不混乱 |
| **角色专业** | 每个 Agent 可用专用模型 + Prompt |
| **失败隔离** | 单 Agent 失败不影响其他 Agent |

## 四、Multi-Agent 的 3 个核心代价

| 代价 | 含义 |
|------|------|
| **复杂度 ×3-5** | 通信协议、状态管理、错误处理都翻倍 |
| **Token ×1.5-2** | 多 Agent 间传话有额外开销 |
| **延迟 ×1.5-3** | 多 Agent 串行/并行都增加耗时 |

反面案例：某团队为了"赶时髦"上 Multi-Agent，结果 6 个 Agent 通信混乱，Token 消耗翻 3 倍，延迟从 2 秒变 8 秒，最终回退到 Single Agent。

## 五、Multi-Agent 的 4 个反模式

| 反模式 | 表现 | 应对 |
|-------|------|------|
| **3 个 Prompt 节点当 Multi-Agent** | 写死的 Workflow，节点无自主决策 | 真 Multi-Agent 必须是 Single Agent 之间的协作 |
| **Single Agent 能解决上 Multi** | 小问题大做 | 先用 Single，撑不住再上 Multi |
| **无通信协议** | Agent 之间靠全局变量通信 | 必设计标准通信协议 |
| **无失败处理** | 单 Agent 失败导致全盘崩 | 必设计"局部失败"降级方案 |

## 六、PM 行动清单

看完本节后：

1. **每个项目必过 3 个判断标准**：可拆解度 / 上下文隔离 / 角色差异
2. **Single 优先**：能用 Single Agent 解决就不上 Multi
3. **上 Multi 前必算 3 个代价**：复杂度 / Token / 延迟
4. **必设计通信协议**：避免 Agent 间靠全局变量通信
5. **必设计失败隔离**：单 Agent 失败不连累其他
