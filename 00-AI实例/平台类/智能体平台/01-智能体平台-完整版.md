## 1. 项目概览

### 1.1 一句话使命与边界

**使命**：让企业在同一套平台上完成从"业务人员零代码搭建简单 AI 应用"到"复杂企业级有状态智能体"的全覆盖，避免企业在 Dify、Coze、LangGraph 之间反复切换。

**边界**：
- ✅ 做：企业内部 AI 应用底座、复杂风控/诊断/自动化任务承载、合规审计闭环
- ❌ 不做：C 端通用 AI 助手、纯算法研发平台、对外商业化 SaaS

### 1.2 当前阶段与规模

| 维度 | 当前值 | 说明 |
| --- | --- | --- |
| 平台阶段 | 孵化期约 1 年 | 已上线，内部价值仍在被持续质疑 |
| 支撑业务团队 | **20+** | 含主 Agent + 多角色子 Agent 模式 |
| Agent 落地周期 | **3 个月 → 2 周** | 标准化模板沉淀后大幅缩短 |
| 多智能体协作步骤 | **5+ 步**复杂业务任务 | 顺序、层级委派、共享记忆 |
| 复杂任务处理质量 | 提升 **60%** | vs 单 Agent 基线 |

### 1.3 关键成果数据速览

平台已用主 Agent（任务拆解与调度）+ 多个角色化子 Agent（专项执行）的模式，支持顺序执行、层级委派、共享记忆/上下文、工具调用、人机协作五大能力，可灵活组装处理复杂业务任务。

## 2. 背景与多角色痛点

### 2.1 企业层痛点

- **现有方案三个缺口**：Dify 仅 DAG 静态工作流，承载不了动态循环、长周期审批、故障排查、代码迭代；Coze 闭源、数据不上私有部署，过不了企业合规；自研需同时覆盖"轻量 AI 应用"+"复杂风控/诊断/自动化"两类需求，缺乏统一底座。
- **采购预算分散**：各部门各自试用 Dify/Coze/Coze 火山版/LangChain，烟囱式采购、数据不互通。

### 2.2 业务层痛点

- **业务人员上手门槛高**：平台为追求强大灵活，把"功能丰富度"做满，但执行层非技术用户反馈"太复杂、上手难"，最终还是技术团队投入成本协助搭建。
- **场景碎片化**：每个业务部门的 AI 需求都是个性化的，但 90% 都是"知识问答 + 流程自动化"的变体，重复造轮子。

### 2.3 技术层痛点

- **DAG 单向限制**：法务审核发现资料不全无法退回初审；动态循环（直到任务达标才停止）做不了。
- **状态丢失**：长周期任务（3-7 天审批）超 24 小时自动终止；只有全局快照、无步骤级历史，监管要求"每步可追溯"无法满足。
- **人工介入薄弱**：仅支持简单同意/拒绝，会签、或签、逐级审批做不了。

### 2.4 管理层痛点

- **平台价值被持续质疑**：管理层用成熟业务 ROI 标准考核孵化平台，焦虑产生。立项时只定功能、没定"培育规则"，没对齐培育周期、阶段性目标、考核口径、容错范围。
- **AI 冲击下的定位焦虑**：低代码平台是否会被 AI 直接生成代码替代？

### 2.5 行业数据交叉验证

| 痛点 | 行业数据佐证 | 来源 |
| --- | --- | --- |
| Dify 生态活跃但企业级不足 | Dify GitHub 145K⭐ / 22.8K forks / 750 open issues（截至 2026-06）| GitHub API（联网验证） |
| Coze 开源后增速明显 | Coze Studio 21K⭐ / 3K forks（2026-04 最后推送，迭代节奏慢于 Dify） | GitHub API（联网验证） |
| LangGraph 成主流复杂编排选项 | 34.7K⭐ / 5.8K forks，每日活跃推送 | GitHub API（联网验证） |
| CrewAI 角色化协作快速崛起 | 53.5K⭐ / 7.5K forks | GitHub API（联网验证） |
| 90%+ 企业 AI 场景仍是知识问答+轻流程 | 行业普遍观察（IDC 2025 中国 AI Agent 市场报告） | 训练知识·建议人工核对 |

## 3. 需求验证（三步法）

### 3.1 目标用户群体确认

| 阶段 | 目标群体 | 拓展逻辑 |
| --- | --- | --- |
| 拓展期 | 全公司所有部门 | 先广撒网识别真实场景 |
| **专注期（P0）** | **AI 运营团队 + 业务团队中的"中间人"角色（懂业务+懂工具）** | 这一群体最可能成为平台第一批深度用户 |
| 拓展期 | 后端工程师、IT 管理员、合规官 | 必须先过的非典型用户 |

### 3.2 痛点假设

| 假设 | 验证依据 |
| --- | --- |
| 业务人员有需求但写不出 AI 应用 | 已上线 1 年，技术团队仍需协助搭建，验证假设成立 |
| 复杂场景（3-7 天审批）无现有方案 | Dify v0.10+ 内置 LangGraph 即为佐证，社区共识 |
| 合规和审计是金融/政务核心阻塞 | 监管要求每步可追溯，Dify 全局快照无法满足 |

### 3.3 假设验证方式与结论

- ✅ 已通过内部访谈和金融风控审批案例验证"长周期+合规"是真痛点
- ⚠️ "业务人员零代码"假设部分证伪——实际仍需技术协助，需要 AI 赋能搭建（解法已在原资料中提出）
- ⏸️ "20+ 业务团队真实使用频率"——待补充活跃用户/团队数据

### 4.3 P0 角色画像

- **小张（AI 运营）**：28 岁，AI 运营 1 年经验，懂业务、会写 prompt、不写代码。痛点：每次新需求都要等开发排期 2-3 周。关键需求：可视化拖拽、模板复用、调试友好。
- **小李（业务中间人）**：32 岁，业务部门数字化负责人，懂业务流程、会用低代码工具。痛点：审批流跨 3-7 天，现有工具中途状态丢失。关键需求：长周期任务支持、人工介入节点、状态可视化。
- **老王（终端业务用户）**：40 岁，业务执行层，只通过 IM 用智能体。痛点：响应慢、答非所问、找不到人工。关键需求：响应快、答案准、能转人工。

### 4.4 用户问题说明

- **作为** AI 运营，**我想做** 用拖拽的方式 30 分钟搭出一个跨系统的智能体，**从而** 不用排期等开发，业务需求当天响应。
- **作为** 业务中间人，**我想做** 配置一个 7 天审批流程并随时查看每步状态，**从而** 复杂业务流程不再依赖人盯人。
- **作为** 终端业务用户，**我想做** 在企微里直接问问题并 3 秒拿到答案，**从而** 不用切换系统、不用等人工。

## 5. 底层需求洞察

### 5.1 表面需求 vs 底层需求对照

| 角色 | 表面需求 | 底层需求 |
| --- | --- | --- |
| 小张 | "给我一个拖拽工具" | 不被开发资源卡住，业务响应零等待 |
| 小李 | "支持 7 天审批流" | 复杂业务流程的可控性和可追溯性 |
| 老王 | "响应快一点" | 把"找信息+找人"这两件麻烦事变成一件 |
| 后端 | "API 要稳定" | 平台不要变成新的运维负担 |
| IT 管理员 | "权限要细" | 出事时有据可查、范围可控 |
| 合规官 | "审计日志完整" | 监管检查时能在 1 小时内调出任意一步证据 |

### 5.2 一句话统一所有 P0 角色诉求

> **企业内每一类人都希望"AI 应用搭建-运营-使用-治理"这一链路上自己负责的那一段，能像水电一样开箱即用且可控。**

### 5.3 心理学维度

- **记忆碎片论（小张）**：每次被开发拖延的痛是反复触发的"碎片"，平台一旦让他自助闭环一次，碎片消失，黏性极强。
- **爱现心理（小张/小李）**：搭好的 Agent 能在团队群里被同事 @ 用，是社交资本，会主动推广。
- **成就感（小李）**：把跨 3 个系统的审批流配通，是数字化转型的"军功章"。
- **安全感（IT/合规）**：审计日志完整=出事不背锅，这是底线需求，权重高于一切。

## 6. 产品定义与方案

### 6.1 使命宣言

让企业 AI 应用从"试点工程"走向"水电基建"——简单场景零代码、复杂场景高可控、全链路可审计。

### 6.2 产品原则

1. **分层兼容**：简单场景零代码、复杂场景高级编排，不强制用户用复杂能力
2. **架构解耦**：展示层与用户层沿用 Dify，复杂引擎层替换/叠加 LangGraph，不重构底座
3. **数据绝对隔离**：会话、文件、知识库、权限严格隔离，杜绝跨用户/跨部门污染
4. **合规优先**：所有操作可追溯、所有数据可审计、所有能力可管控
5. **用户体验对齐 Coze**：简化操作、可视化思考、引导式配置、低学习成本
6. **能力兜底**：DAG 轻量化兜底 + LangGraph 复杂场景兜底，覆盖 100% 企业 AI 需求

### 6.3 用例三要素

| 角色 | 情境 | 痛点 |
| --- | --- | --- |
| AI 运营小张 | 周一下午被业务方紧急要一个客服 Bot | 开发排期 3 周，业务方等不及 |
| 业务中间人小李 | 跨财务/法务/CEO 的 50 万贷款审批 | 现有工具 24h 后任务自杀，没法跨天 |
| 合规官 | 监管季度检查 | 必须 1 小时内调出任意一笔过去 90 天审批每一步证据 |

### 6.4 MVP 两阶段设计

**阶段 0 → 0.5（验证价值）**：
- 核心：DAG 轻量编排 + RAG 知识库 + 基础权限 + 单 Agent
- 目标：跑通 3 个真实业务场景（客服 / 内部知识问答 / 简单流程自动化）
- 退出标准：3 个场景日活合计 ≥ 200，业务方愿意付费内部结算

**阶段 0.5 → 1（真实可用）**：
- 核心：LangGraph 复杂编排 + CrewAI 多角色 + 全链路审计 + 人工介入节点
- 目标：金融风控审批 / 故障诊断 / 代码迭代 三个标杆案例落地
- 退出标准：标杆案例 ROI > 3、合规审计通过、平台支撑团队 ≥ 20

### 6.5 一定不优先（≥3 条明确不做）

1. ❌ **不做对外商业化 SaaS**：能力先在内部跑透，避免分散资源
2. ❌ **不自研基础大模型**：模型中台只做路由和管控，模型能力外采
3. ❌ **不重构 Dify 前端**：直接在 Dify 开源版上扩展，节省 80% 工作量
4. ❌ **不支持非 LangGraph/CrewAI 的第三方编排框架**：只两条腿走路，避免维护负担
5. ❌ **不做 C 端通用对话助手**：定位企业内部，C 端有更专业的产品

## 7. 核心功能与架构

### 7.1 核心模块清单（七大模块）

| 模块 | 职责 | 关键能力 | 联调补充建议 |
| --- | --- | --- | --- |
| 模型中台 | 统一管控所有大模型，企业成本与风险可控 | 多模型接入、模型路由策略、参数统一管控、用量统计与成本管控、模型黑白名单 | 补建议：增加跨模型成本对比看板、模型 SLA 监控 |
| 智能体编排 | 平台核心，分基础与企业级两层 | 见 7.2 | 已有原资料详述 |
| 企业级 RAG 知识库 | 适配内部文档、制度、风控规则、医疗资料、技术手册 | 多模态多格式解析、自定义分段、重排序、问题改写、混合检索、权限隔离、版本管理、增量更新 | 补建议：补充检索质量评测集、Bad Case 闭环工具 |
| 工具与插件生态 | 对齐 Coze 丰富度、保留 Dify 开放性 | 官方内置（联网/沙箱/文件/表格/图片）、自定义插件、企业私有插件市场、工具调用风控 | 补建议：插件评分体系、企业内插件复用率指标 |
| 监控与评测 | 实时监控智能体运行状态 | 自动化评测、Bad Case 闭环 | 补建议：增加 A/B 测试编排能力、PMF 量化看板 |
| 合规与运维 | Dify/Coze 企业版核心补齐项 | 全链路审计日志、自动脱敏、RBAC 权限体系、运维监控、版本管理 | 补建议：监管报告一键导出、敏感数据热点图 |
| 智能体编排（企业级层） | 长周期/动态/人工介入 | LLM 动态分支、动态条件循环、断点续传、状态快照、人工介入节点、子智能体嵌套 | 补建议：可视化时间旅行调试器 |

### 7.2 关键技术架构（三层混合）

| 层级 | 框架 | 职责 | 触发场景 |
| --- | --- | --- | --- |
| 平台层 | **Dify** | 前端、用户管理、权限、知识库 RAG、API 发布、运维 | 所有场景（始终在线） |
| 编排层 | **LangGraph** | 动态流程、状态持久化、人工介入、子图嵌套、故障恢复 | 仅复杂场景（约 10%） |
| 执行层 | **CrewAI** | 角色分工、任务分解汇总、工具/代码执行、组件复用 | 仅多角色任务 |

**已验证集成事实**：Dify v0.10+ 内置 LangGraph 作为工作流执行引擎，CrewAI v1.14+ 原生支持 LangGraph 作为可选后端，三者分层互补不冲突。

### 7.3 业务驱动模型分析

- **驱动类型**：单边平台（企业内部）+ 部分双边特征（业务方提需求/AI 运营做交付）
- **关键因素**：
  - 业务方数量：决定平台需求多样性，目前 20+ 团队
  - AI 运营人均产能：模板复用率高则人效高
  - 模板/组件沉淀率：决定边际成本下降速度
- **集中资源点**：核心是"模板复用率"这一杠杆，单一模板被 5+ 团队复用即标杆

## 12. 落地实践与迭代经验

### 12.1 已踩过的坑与教训

**坑 1：业务人员上手门槛高（已踩）**

- 现象：平台为追求强大灵活把"功能丰富度"做满，业务用户反馈"太复杂、上手难"
- 根因：管理层关注功能丰富度，执行层认知和接受程度被低估
- 教训：先识别"必须先过"的非典型用户（业务执行层），其阻塞决定项目成败
- 解法：分层设计 + 完善引导 + AI 赋能搭建

**坑 2：平台价值被持续质疑（已踩）**

- 现象：平台孵化期约 1 年，长期被追问项目与平台价值
- 根因：立项只定功能、没定培育规则；管理层用成熟业务 ROI 标准考核孵化平台
- 教训：基础设施类项目立项时必须同步约定培育周期、阶段性目标、考核口径、容错范围
- 解法：立项同步约定培育规则 + 显性/隐性价值分层沟通

**坑 3：纯平台闭门造车风险（已识别但需警惕）**

- 现象：早期容易陷入"做平台但没场景"
- 教训：必须坚持"业务项目为载体"，载体项目优选中型项目
- 解法：项目+平台双向赋能飞轮，借现有业务节奏稳步推进

**坑 4：AI 冲击下定位摇摆**

- 现象：管理层和团队都在问"AI 会不会替代低代码/智能体平台"
- 教训：必须明确"融合而非对立"的定位
- 解法：在迭代中预留 AI 扩展能力（智能表单、智能流程、智能问答、数据智能分析）
