## 导语

B 端产品从市场需求文档（MRD）到产品需求文档（PRD）的转换，是一项高门槛的结构化写作任务。一份完整的 PRD 包含产品概述、功能规格、流程设计、数据建模、页面规格 5 大章节共 20 个子模块，中等复杂度的 B 端产品 PRD 正文约 6 万字。传统方案用单一 Agent 或 Workflow 串联节点完成转换，在实践中暴露出三个结构性问题：单 Agent 上下文逼近 token 临界值导致注意力衰减（Context Rot）、单一"灵魂"指令无法同时适配产品视角与工程视角导致 Soul 漂移、以及 7 倍的准确率差距源于缺少独立质检环节。

本报告阐述的多智能体架构采用 1 个主 Agent + 5 个子 Agent + 1 个独立质检 Agent 的拓扑，将 PRD 写作拆解为 5 道连续工序，每道工序由一个角色独立完成，通过共享文件系统协作，由独立质检 Agent 做 100 分制评分。这份报告回答两个问题：为什么这样设计，以及整体怎么运作。

# 第一部分：设计思路

## 1. 架构演化路径

v3 并非一步到位的设计，而是经历了 3 轮迭代，每一轮都由一个具体的失败模式驱动。

### v0 → v1：通用 Agent 的崩溃

最初的方案用一个通用 Agent 负责从 MRD 拆解到 PRD 全文撰写。这个 Agent 同时承担拆解需求、写产品概述、画流程图、设计数据模型、写页面规格 5 种截然不同的任务。实践中它很快崩溃了——原因不是能力不足，而是"灵魂冲突"：产品概述要求"对用户友好、价值清晰"的思维方式，数据建模要求"模型严谨、约束完整"的思维方式，两种思维方式在同一上下文中互相干扰。同时，单次上下文逼近模型 token 上限，注意力开始衰减。

解法是拆为 1 个主 Agent + 3 个子 Agent（拆解 / 撰写 / 质检），让每个角色拥有独立的 Soul 和 Memory。

### v1 → v2：撰写 Agent 的过载

v1 的 ② 撰写 Agent 要一口气写完 PRD 全部 5 个章节。5 个章节合计约 6 万 token，远超单 Agent 的舒适上下文区间。结果是前两章（产品概述 + 功能规格）质量尚可，后三章（流程 / 数据 / 页面）质量断崖式下降——Agent 的注意力被前两章消耗殆尽。

解法是把 ② 撰写 Agent 拆为产品组（负责 PRD1+2）和工程组（负责 PRD3+4+5）。

### v2 → v3：PRD5 的独立

v2 的工程组仍由一个 Agent 负责流程、数据、页面三个章节。但页面规格（PRD5）单独占据了工程组 54% 的输出量，且它的服务对象是前端工程师和设计师，与流程组（服务后端）和数据组（服务后端 + DBA）的服务对象完全不同。Soul 漂移再次出现。

解法是让 PRD5 独立成 ④ 页面规格 Agent。至此架构稳定为 1 主 + 5 子 + 1 质检，每个角色的上下文全部可控（最大 25K token），职责边界清晰。

### 演化的核心逻辑

3 轮迭代遵循同一个判断标准——三维隔离判断法。每当一个 Agent 出现质量下降，就用"记忆数据 / 技能体系 / 决策偏好"三个维度验证它是否应该独立。如果三维中有两维以上存在显著差异，就拆分。这个判断法来自极客时间《企业级多智能体设计实战》第 25 课。

## 2. 核心设计原则

6 条原则贯穿整个架构，每一条都有明确的工程动机。

**Orchestrator 范式**：所有任务经主 Agent 调度，禁止子 Agent 之间自由互调。自由互调会导致误差链式放大——课程 L25 的数据显示，3 个 Agent 自由协作的误差放大倍数是 17 倍。中心化调度把误差控制在单跳范围内。

**三维隔离判断法**：每个角色的独立性通过"记忆数据 / 技能体系 / 决策偏好"三维验证。这套标准避免了"为了拆而拆"——只有三维中两维以上存在显著差异时才拆分。v3 的 7 个角色全部通过了三维验证。

**上下文工程硬约束**：每个 Agent 单次上下文严格控制在 30K token 以内。这个数字来自课程 L23 的关键设计——当上下文超过临界值，注意力呈 n² 衰减，后置内容的处理质量急剧下降。v3 的最大单 Agent 上下文是 ③ 质检的 25K，所有角色都在安全区间内。

**GT（Ground Truth）驱动**：每个 Agent 配 20-50 条历史样本作为参考。GT 不是"模板"，而是"校准锚点"——Agent 在写作时参考同类历史 PRD 的结构和深度，避免输出偏离实际标准。GT 按 4 类分库沉淀（产品 30 条 / 流程 20 条 / 数据 20 条 / 页面 50 条），而非维护一个庞大的完整 PRD 库，因为 100 条完整 PRD 占 200 万字，维护成本远超分类沉淀。

**独立验收**：③ 质检 Agent 只报告问题不修改内容，修复权归主 Agent。这条原则杜绝了"自检盲区"——写作者审查自己的产物时，天然倾向于跳过自己刚写过的部分。独立的第三方视角能发现写作者看不到的结构性缺陷。

**单一人类接口**：人类只与主 Agent 对话，不直接接触任何子 Agent。这避免了多头沟通导致的混乱，也防止人类绕过主 Agent 的调度逻辑直接干预某个子 Agent，破坏整体流程的一致性。

## 3. 关键架构决策

从 v3 主文档 §9 的 12 条技术决策中，精选 8 条对架构形态影响最大的决策。

### 决策 1：1 主 + 5 子拓扑

备选方案有 1+7（更细粒度拆分）和 1+3（更保守的拆分）。1+7 被否决是因为超过了"2-3 个有效 Agent"的实际上限（课程 BP-2），过多的 Agent 会导致协调复杂度急剧上升。1+3 被否决是因为 ② 撰写 Agent 的上下文仍然过载。1+5 是 PRD 写作流程的最细粒度——5 个角色分别对应 PRD 的 5 个章节，每个角色的上下文、技能、决策偏好都通过了三维验证。

### 决策 2：质检 Agent 独立于写作链

备选方案是让写作 Agent 自检。这被否决是因为独立质检与自检之间存在 7 倍的准确率差距（课程 BP-1）。独立质检 Agent 能以第三方视角发现写作者的盲区，且质检 Agent 的 Soul（"挑剔质疑、找漏洞"）与写作 Agent 的 Soul 天然对立，形成制衡。

### 决策 3：主 Agent 不持有任何写工具

主 Agent 负责调度、验收、决策，但绝不亲自下场写任何业务文档。这条约束防止主 Agent 在验收环节产生"自己写的东西自己验"的利益冲突。如果主 Agent 发现某子 Agent 的产物不达标，它只能 reject 并重新派发任务，不能自行修改。

### 决策 4：单 Agent 上下文 < 30K

备选方案是让单个 Agent 写完全部 5 个章节。这被否决是因为 Context Rot——注意力随上下文长度呈 n² 衰减。5 章节合计约 6 万 token，后置章节的质量会断崖式下降。拆分后每个 Agent 的上下文都在 7K-25K 区间内，质量稳定。

### 决策 5：Owner 唯一的文件所有权

共享工作区中的每个文件只有一个 Owner Agent，其他 Agent 只有读权限。这解决了多 Agent 并发写入时的冲突问题——课程 L26 的数据显示，37% 的协作失败源于文件所有权歧义。Owner 唯一原则通过 SOP 约定 + 工具层权限双重保障。

### 决策 6：三态邮箱状态机

Agent 之间的通信不用函数调用，而用邮箱协议。每个任务是一封邮件，经过 unread → in_progress → done 三个状态。三态而非二态（read: bool）是为了支持崩溃恢复——如果 Agent 在 in_progress 状态崩溃，Watchdog 机制能在超时后自动重置为 unread，触发重试，不会丢失任务。

### 决策 7：PRD5 独立成 Agent

页面规格（PRD5）最初属于工程组的一部分，但它单独占据工程组 54% 的输出量，且服务对象（前端 + 设计师）与流程组、数据组（后端 + DBA）完全不同。Soul 漂移再次出现——工程组 Agent 在写流程图时表现良好，写到页面规格时质量明显下降。独立后，④ 页面规格 Agent 专注于"视觉可还原、组件可复用、状态完整"。

### 决策 8：章节级并发

PRD 的 5 个章节中，PRD3（流程）、PRD4（数据）、PRD5（页面）可以在 PRD2（功能规格）完成后并发执行，因为它们都依赖功能 ID 清单但彼此不依赖。并发的前提是 outline 锁——主 Agent 必须先验收大纲（outline.md），确定章节间的接口契约（功能 ID、数据实体、页面清单），然后才允许 3 路 Agent 并发。outline 锁避免了并发写入时的接口冲突。这一设计节省约 40% 的端到端耗时。

### 4.2 7 个角色的职责边界

每个角色由四层框架定义：Role Charter（职责边界）、Soul（一句话灵魂指令）、NEVER 清单（红线）、Memory + Skills（记忆与工具）。

| 角色 | 核心职责 | Soul | 上下文 | 服务对象 |
|------|---------|------|--------|---------|
| **Manager** | 读 MRD 初始化工作区 / 选 GT 样本 / 派子 Agent 任务 / 验收产物 / 决策修复策略 / 监控降级与熔断 | 全局视野、不下场、严验收 | 20K | Human + 全体子 Agent |
| **① MRD 结构化** | 拆 MRD 为 5 大模块 / 抽取 9 字段 + 47+ 需求条目（带 ID）/ 标注推断来源 / 列出开放问题 | 宁可多问，不要漏拆；遇到模糊词先列问题、不擅自补全 | 8K | ② 产品组（下游消费方） |
| **② 产品组** | 写 PRD1（产品概述 8 子模块）+ PRD2（功能规格含 ID 清单）/ 维护 feature_id_list.md | 对用户友好、价值清晰、对业务方负责；结构 > 文采 | 15K | 业务方 + 全体下游 Agent |
| **②'' 流程组** | 写 PRD3（用户旅程 + 业务流程图 + 操作步骤）/ 用 Mermaid 画流程图 / 必含审批、校验、数据更新环节 | 严谨穷举、异常分支、对后端负责 | 8K | 后端工程师 |
| **②''' 数据组** | 写 PRD4（数据模型 + 流转规则 + 存储安全）/ 设计 ER 图 / 标注存储选型与索引 | 模型严谨、约束完整、对后端+DBA 负责 | 7K | 后端工程师 + DBA |
| **④ 页面组** | 写 PRD5（页面结构 + 交互规范 + 组件清单）/ 维护页面模板库 / 标注页面 5 状态 | 视觉可还原、组件可复用、状态完整、权限清晰 | 15K | 前端工程师 + 设计师 |
| **③ 质检** | 多视角审查（开发/测试/运营）/ 100 分制评分 / 标注具体段落 + 修改建议 | 挑剔质疑、找漏洞、不替写者决策 | 25K | Manager（决策依据提供方） |

### 4.3 三维隔离验证

5 个子 Agent 的拆分依据是三维隔离判断法——每个角色在"记忆数据 / 技能体系 / 决策偏好"三个维度上都必须与相邻角色存在显著差异：

| 角色对 | 记忆差异 | 技能差异 | 决策偏好差异 |
|--------|---------|---------|------------|
| ① ↔ ② | MRD 拆解方法论 vs PRD 写作模板 | 需求抽取 vs 价值主张提炼 | 宁可多问 vs 对用户友好 |
| ② ↔ ②'' | 产品级 GT vs 流程级 GT | 4 维映射 vs Mermaid 流程图 | 价值清晰 vs 异常穷举 |
| ②'' ↔ ②''' | 流程模式 vs 数据模型 | 旅程地图 vs ER 图设计 | 后端负责 vs DBA 负责 |
| ②''' ↔ ④ | 数据契约 vs 页面模板 | 安全清单 vs 组件一致性 | DBA 负责 vs 设计师负责 |

所有角色对在三维上均存在 ≥ 2 维的显著差异，满足拆分条件。

每个角色的完整四层框架定义（Charter / Soul / NEVER / Memory 字段 / Skills 调用条件 / 提示词骨架 / 评估指标）见 [`2-Agent详情/`](2-Agent详情/) 目录的 2.1-2.7 各篇。Skills 工具的输入输出 schema、模型参数、trace_id 规则等字典级配置见 [`3-Skills与配置详情/`](3-Skills与配置详情/)。

## 5. 协作机制

### 5.1 共享工作区

7 个 Agent 通过共享文件系统协作，而非函数调用或消息队列。工作区按 Owner 唯一原则组织——每个文件只有一个 Agent 有写权限，其他 Agent 只能读。

```
workspace/shared/
├── input/                    # MRD 原始输入（Owner: Human）
├── breakdown/                # ① MRD 结构化的产物（Owner: ①）
│   ├── requirements_list.md  #   功能需求清单（ID/描述/优先级/验收点）
│   ├── open_questions.md     #   待澄清问题
│   └── glossary.md           #   业务术语表
├── prd/                      # 5 个写作 Agent 的产物（按 section 切分 Owner）
│   ├── outline.md            #   大纲（Manager 验收后才允许并发）
│   ├── section_1_2.md        #   PRD1+2（Owner: ② 产品组）
│   ├── section_3.md          #   PRD3（Owner: ②'' 流程组）
│   ├── section_4.md          #   PRD4（Owner: ②''' 数据组）
│   ├── section_5.md          #   PRD5（Owner: ④ 页面组）
│   ├── handoff_34.md         #   ②'' → ②''' 数据契约
│   ├── handoff_45.md         #   ②''' → ④ 页面契约
│   └── feature_id_list.md    #   ② 输出，下游 3 个 Agent 共享
├── qa/qa_report.md           # ③ 质检产物（Owner: ③）
├── delivery/prd_final.md     # 终稿归档（Owner: Manager）
├── gt_samples/               # GT 样本库（4 类分库）
└── mailboxes/                # 邮箱协议（8 个 JSON 文件）
```

文件系统协作的优势在于天然可读——任何时刻打开工作区目录，都能看到每个 Agent 当前进度和产物状态。调试时不需要翻日志，直接看文件。

### 5.2 三态邮箱状态机

Agent 之间的任务派发通过邮箱协议完成。每封邮件是一个 JSON 对象，包含发送方、接收方、任务类型、输入/输出路径和时间戳。邮件经过三个状态：

```
unread ──Agent 读取──> in_progress ──任务完成──> done
  ▲                        │
  │                        │ Watchdog 超时（10 min）
  └────────────────────────┘
       自动 reset + 重试
```

三态而非二态（read: bool）的设计关键在于崩溃恢复。如果 Agent 在 `in_progress` 状态崩溃，Watchdog 每 10 分钟扫描一次邮箱，发现超时的 `in_progress` 邮件会自动重置为 `unread`，触发重试。这保证了任务不会因为单次崩溃而丢失。

### 5.3 handoff 接力

5 个写作 Agent 之间通过 handoff 文件传递接口契约。handoff 只包含"接口信息"（功能 ID、数据实体、页面清单），不复制 PRD 全文。这保证了每个 Agent 的上下文干净——它只看到自己需要的信息。

```
② 产品组 ──feature_id_list.md──>  ②'' 流程组
                                      │
                                      ▼
                                 handoff_34.md
                                      │
②''' 数据组 <──读 handoff_34.md──────┘
      │
      ▼
  handoff_45.md
      │
      ▼
  ④ 页面组
```

关键约束是：主 Agent 必须验收前序 Agent 的产物后，才允许后序 Agent 启动。这避免了"错误传播"——如果 ② 的功能 ID 清单有问题，③ / ④ 都会基于错误数据工作，浪费整个并发的算力。

## 6. 端到端流程

### 6.1 9 阶段 SOP

从 MRD 输入到 PRD 归档，完整的端到端流程分为 9 个阶段：

```
阶段 0  Manager 初始化
        读 MRD → 初始化工作区 → 选 GT 样本 → 检查 MRD 完整性
                                    │
阶段 1  派 ① MRD 结构化 ◄──────────┘
        ① 拆 MRD → 产出 9 字段 + 47 需求 + 开放问题
                                    │
阶段 2  验收 ① 产物 ◄──────────────┘
        Manager 读 breakdown/* → 验收字段齐全
        不通过 → reject 重派 / 通过 → 继续
                                    │
阶段 3  派 ② 产品组 ◄──────────────┘
        ② 写 PRD1+PRD2 → 产出 8 子模块 + 功能 ID 清单
                                    │
阶段 4  验收 ② 产物 ◄──────────────┘
        Manager 读 section_1_2.md → 验收模块齐全 + ID 规范
        不通过 → reject / 通过 → 开 outline 锁
                                    │
阶段 5  并发派发（关键瓶颈段）◄─────┘
        ┌─ spawn ②'' 流程组 → 写 PRD3
        ├─ spawn ②''' 数据组 → 写 PRD4
        └─ spawn ④ 页面组 → 写 PRD5
        （三路并发，Manager 串行收集结果）
                                    │
阶段 6  收集 + 验收 ◄───────────────┘
        逐个验收 PRD3/4/5
        不通过 → reject 对应 Agent 重写
                                    │
阶段 7  派 ③ 质检 ◄────────────────┘
        ③ 多视角审查 → 产出 qa_report.md（100 分制）
                                    │
阶段 8  读质检报告 ◄────────────────┘
        总分 ≥ 80 → 进入归档
        总分 < 80 → 合并缺陷 → 派对应 Agent 修订
        连续 3 轮 < 80 → error_alert → Human
                                    │
阶段 9  归档 + Human 终审 ◄─────────┘
        拼装 prd_final.md → Human 确认 → 归档
```

### 6.2 并发设计

阶段 5 是整个流程的效率核心。PRD3（流程）、PRD4（数据）、PRD5（页面）三个章节可以并发执行，因为它们共享的输入只有 `feature_id_list.md`（功能 ID 清单），彼此之间不直接依赖。

并发的安全前提是 outline 锁。在阶段 4 验收通过后、阶段 5 并发启动前，主 Agent 必须先确认大纲（outline.md），锁定三个并发 Agent 之间的接口契约——功能 ID 命名规范、数据实体列表、页面清单。没有这道锁，三个 Agent 可能对同一个功能 ID 产生不同的理解，导致最终拼装时接口冲突。

### 6.3 耗时估算

中等复杂度 MRD 的端到端耗时约 5 小时：

| 段 | 阶段 | 耗时 | 说明 |
|----|------|------|------|
| 串行段 | 0-4 | ~2h | MRD 拆解 + 产品组写作 + 验收 |
| 并发段 | 5-6 | ~2h | 三路并发写作 + 验收（比串行节省 40%） |
| 质检段 | 7-8 | ~1h | 质检 + 决策 |
| 人类介入 | 9 | 异步 | Human 终审（不阻塞） |

## 7. 质量与可靠性

### 7.1 100 分制质检

③ 质检 Agent 对 PRD 全文做 100 分制评分，分 5 个维度：

| 维度 | 满分 | 及格线 | 核心检查项 |
|------|------|--------|-----------|
| 完整性 | 20 | 16 | 5 大章节齐全 + 20 子模块齐全 |
| 一致性 | 20 | 16 | 术语统一 + 跨章节引用对齐 + 流程闭环 + 数值/ID 一致 |
| 可执行性 | 30 | 24 | 每条功能需求可写测试用例 + 验收标准 SMART + 异常分支覆盖 + 边界条件明确 |
| 风险标注 | 15 | 12 | 模糊词识别 + TBD 标注 + 异常分支 + 范围蔓延信号 |
| 风格统一 | 15 | 12 | 术语一致 + 句式一致 + 排版统一 |

**通过线 80 分**，但即使总分达标，任一维度低于及格线也会强制 reject。这个"木桶效应"设计防止了"总分合格但某个维度严重缺陷"的情况——比如完整性 20 分但可执行性只有 10 分，说明 PRD 看着齐全但开发没法用。

### 7.2 多视角审查

除了 5 维度评分，③ 质检还会从 3 个专业视角分别审查，各自输出 issue 清单：

| 视角 | 关注点 | 典型 issue |
|------|--------|-----------|
| 开发视角 | 功能可行性 / 边界条件 / 技术实现路径 | "PRD4 的 ER 图缺少软删除字段" |
| 测试视角 | 可测性 / 异常处理 / 边界用例 | "PRD3 的审批流缺少驳回分支的测试场景" |
| 运营视角 | 业务流程闭环 / 用户场景契合 / 价值主张落地 | "PRD1 的价值主张与 PRD2 的功能清单不匹配" |

3 视角的 issue 清单合并后，附在 qa_report.md 中作为"具体段落 + 修改建议"部分。主 Agent 根据这些 issue 决策派哪个 Agent 修订。

### 7.3 3 级降级 + 熔断

系统设计了 3 级容错机制，从轻到重依次触发：

```
L1 软失败（自动恢复）
  触发：JSON 解析失败 / 字段缺失
  处理：自动重试 1 次（换种子）
       │ 失败
       ▼
L2 硬失败（切换模型）
  触发：L1 失败 / LLM 调用超时
  处理：切换备份模型（DeepSeek-V3.1）+ 重试
       │ 失败
       ▼
L3 熔断（人类介入）
  触发：L2 失败 / 3 轮 reject 不收敛
  处理：error_alert → Human
  Human 决定：rescue / abandon / 调向
```

L1 和 L2 是全自动的，Agent 不会感知到故障。L3 才触发人类介入——只有当连续 3 轮质检都不达标，或者 LLM 在 L1+L2 都失败时，才需要 Human 决策。

### 7.4 模型选型

| Agent | 主模型 | 备份模型 | maxTokens | timeout |
|-------|--------|---------|-----------|---------|
| Manager | DeepSeek-V3.2 | V3.1 | 8,192 | 60s |
| ① MRD 结构化 | DeepSeek-V3.2 | V3.1 | 32,768 | 600s |
| ② 产品组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s |
| ②'' 流程组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s |
| ②''' 数据组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s |
| ④ 页面组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s |
| ③ 质检 | DeepSeek-V3.2 | V3.1 | 32,768 | 600s |

5 个写作 Agent 启用 thinking 模式（质量优先），③ 质检禁用 thinking（速度优先）。备份模型统一用 V3.1（同系列，质量差异 < 5%），保证降级后输出风格不会突变。

## 8. 人类介入设计

### 8.1 3 个介入点

系统设计了 3 个人类介入点，分别覆盖流程的前端、末端和异常态：

| 介入点 | 触发时机 | Human 动作 | 设计意图 |
|--------|---------|-----------|---------|
| **needs_clarify** | 阶段 1-2，① 发现 MRD 信息不完整 | 在 open_questions.md 补全或回复邮件 | 前置拦截——避免基于错误输入跑完全流程 |
| **checkpoint_request** | 阶段 8-9，PRD 终稿前 [TBD] 或模糊词超阈值 | 读 PRD 终稿 → confirm / reject + feedback | 终审把关——防止"形式上通过但实质上有空洞"的 PRD 流出 |
| **error_alert** | 任意阶段，子 Agent 连续失败 ≥ 3 轮或 LLM 熔断 | 决定 rescue / abandon / 调向 | 异常兜底——把不可自动恢复的决策交给人类 |

### 8.2 自动触发规则

介入点不是靠人类主动监控，而是由系统自动检测信号并触发：

| 信号 | 阈值 | 触发 |
|------|------|------|
| ① breakdown 中推断标注出现次数 | ≥ 3 | needs_clarify |
| open_questions.md 条目数 | ≥ 5 | needs_clarify |
| PRD 中 [TBD] 标记 | > 3 | checkpoint_request |
| PRD 中模糊词（"可能/大概/也许"） | ≥ 5 处 | checkpoint_request |
| 同一 Agent 累计 reject | ≥ 3 轮 | error_alert |
| ③ 质检总分连续 | < 80 达 3 轮 | error_alert |
| LLM 调用 L1+L2 都失败 | — | error_alert |

### 8.3 不介入范围

人类只在上述 3 个介入点参与决策。以下事项完全由 Agent 自主完成，不需要人类介入：

- 工作区初始化与子 Agent 选择排序
- 章节内部结构调整与验收标准措辞优化
- 模板复用与状态机内部逻辑

"不介入范围"的设计是为了避免人类疲劳型确认——如果每个细节都要求人类点头，Human 会逐渐变成"无脑点 yes"的橡皮图章，介入机制就形同虚设。通过限制介入点数量，确保每次介入都是高价值的决策。

## 9. 落地路径

架构采用渐进式落地策略，分 4 个阶段、每阶段 3 周，先验证再扩展。

### 阶段 1：基础工程（Week 1-3）

搭建 v1 骨架（1 主 + 3 子：Manager / ① / ② / ③），把 Coze Chatflow 的 5 章节 SOP 吸收到 ② 的 Skills 中，搭建共享工作区和邮箱协议。

**里程碑**：能用 v1 跑通 1 个简单 MRD 产出 PRD（不保证质量）。

### 阶段 2：质量提升（Week 4-6）

引入 GT 样本（先 20 条起步），③ 质检接入 100 分制评分，实现 3 级降级 + 熔断机制。

**里程碑**：v1 跑 5 个不同 MRD，质量稳定达到 80 分。

### 阶段 3：拆分到 v2（Week 7-9）

拆 ② 为产品组（PRD1+2）+ 工程组（PRD3+4+5），沉淀 handoff 协议和流程型职责边界，实现章节级并发。

**里程碑**：v2 跑 3 个真实 MRD，耗时比 v1 节省 30%。

### 阶段 4：拆出 PRD5（Week 10-12）

拆工程组为 ②'' 流程 + ②''' 数据 + ④ 页面，沉淀页面模板库（5+ 套），整体回归测试。

**里程碑**：v3 跑 5 个真实 MRD，耗时比 v2 节省 40%，质量稳定 85+ 分。

### 渐进式拆分的核心逻辑

4 个阶段的拆分顺序就是 v3 架构的演化顺序——先跑通最简单的 1+3，验证收益后再逐步拆细。这种策略避免了"一次性到位"的风险：如果 1+3 的基础链路都跑不通，1+5 的复杂度只会让调试更困难。每一阶段的里程碑都是可量化的（跑 N 个 MRD / 达到 X 分 / 耗时节省 Y%），为是否进入下一阶段提供决策依据。

## 风险与缓解

| 风险 | 严重度 | 缓解策略 |
|------|--------|---------|
| Manager 规划失误导致全链放大 | 高 | Manager SOP 化所有决策（"qa_report 命中 X 模式 → 自动派修订 Y"） |
| 子 Agent 越界（如 ② 写流程图） | 中 | NEVER 清单 + 工具层权限（② 写工具只允许 section_1_2.md）+ ③ 质检二次检查 |
| 5 个 Agent 协调复杂度上升 | 中 | 严格中心调度 + 流程型职责 + Manager 验收 |
| 人类疲劳型确认（每个 TBD 都点 yes） | 中 | checkpoint 数量限制（每段 ≤ 2 个）+ 高风险 TBD 单独标红 |
| GT 库初期不足导致 PRD 模板僵化 | 中 | 先 20 条 MVP 验证 → 后续每完成 1 个 PRD 沉淀 1 条 |
| 章节级并发冲突（接口命名/数据格式） | 中 | 强制 outline 锁（Manager 验收 outline 后才允许并发） |
| PRD5 模板库未沉淀导致 ④ 质量不稳定 | 中 | ④ 启动前必须有 5+ 套页面模板（CRUD/表单/列表/详情/统计） |
| 模型降级导致质量波动 | 低 | L2 备份模型用 V3.1（同系列，质量差异 < 5%） |
