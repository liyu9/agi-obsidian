## 一、Manager（5 个 Skill）

Manager 持有 5 个 Skill，覆盖 GT 匹配 / 任务派发 / 验收 / 决策 / 降级的完整调度闭环。

### gt_matcher
- **所属 Agent**：Manager
- **作用**：根据 MRD 关键词在 GT 库中匹配 1-2 份历史 PRD 样本，作为下游写作 Agent 的校准锚点（v3 §3.1）
- **输入**：`workspace/shared/input/mrd.md` 全文 + GT 库 4 类索引（产品/流程/数据/页面）
- **输出**：1-2 份 GT 样本 ID + 匹配度评分 + 注入到下游 Agent 启动 prompt 的 gt_references 字段
- **调用条件**：阶段 0 初始化工作区时自动调用 1 次；阶段 5 并发前可重调用刷新
- **课程依据**：L21《搜索驱动记忆系统》+ 7.0 §4 共性 1
- **关联 Skills**：与 ②/②''/②''' 后续补充的"本角色 gt_matcher"分层——Manager 的 gt_matcher 检索全局索引并裁决子库范围

### sub_agent_router
- **所属 Agent**：Manager
- **作用**：派发任务到 5 个子 Agent 的 inbox（邮箱协议三态状态机，v3 §4.2）
- **输入**：任务类型（task_assign / task_done）+ 接收方 Agent ID + 输入/输出路径 + trace_id
- **输出**：写入对应 `mailboxes/{agent}.json` 的 unread 邮件 + 触发 Watchdog 监听
- **调用条件**：阶段 1/3/5/7 派发时自动调用；reject 重派时再次调用
- **课程依据**：L23《Orchestrator 范式》+ L26《三态状态机》+ M10/M11
- **关联 Skills**：与 `artifact_validator` 串联（路由 → 验收）；与 `level3_fallback` 串联（路由失败 → 降级）

### artifact_validator
- **所属 Agent**：Manager
- **作用**：验收每个子 Agent 产物（清单 / 字段 / 格式）——不通过则 reject 重派（v3 §3.1）
- **输入**：子 Agent 产物路径（如 `breakdown/requirements_list.md` / `prd/section_1_2.md`）+ 验收 checklist
- **输出**：`accept` 或 `reject` + 具体缺陷清单（哪一字段缺失 / 哪一格式不合规）
- **调用条件**：子 Agent 邮箱状态变 `done` 时自动触发；Manager 收到产物后**必读原文**再决策
- **课程依据**：L25《三维隔离》+ M18 + 7.1 §3 G1
- **关联 Skills**：与 `qa_decision_tree` 互补——artifact_validator 做"结构层验收"（字段齐全），qa_decision_tree 做"语义层决策"（接受/修订/熔断）

### qa_decision_tree
- **所属 Agent**：Manager
- **作用**：读 qa_report.md → 决策（通过 / 修订 / 熔断）（v3 §3.1）
- **输入**：`workspace/shared/qa/qa_report.md`（5 维度评分 + 缺陷清单）
- **输出**：3 类决策之一——`pass`（≥ 80 分且无维度低于及格线）/`revise`（< 80 分派对应 Agent 修订）/`circuit_break`（连续 3 轮 < 80 → Human）
- **调用条件**：③ 质检邮箱状态变 `done` 时自动调用 1 次
- **课程依据**：L23 BP-1《独立质检》+ L36《评测体系》+ M08/M16
- **关联 Skills**：与 `artifact_validator` 互补；与 `level3_fallback` 串联（3 轮 reject → L3 熔断）

### level3_fallback
- **所属 Agent**：Manager
- **作用**：L1 重试 → L2 换模型 → L3 熔断（v3 §6.2 三级降级机制）
- **输入**：子 Agent 失败信号（JSON 解析失败 / LLM 超时 / 连续 reject）
- **输出**：L1（同模型+新种子）→ L2（切换 DeepSeek-V3.1）→ L3（error_alert 邮件给 Human）
- **调用条件**：任何 LLM 调用失败时自动触发；L3 触发后必发 Human 邮件
- **课程依据**：L31《3 级降级》+ M14
- **关联 Skills**：与所有子 Agent 的 LLM 调用串联（统一降级基础设施）；与 `sub_agent_router` 串联（L3 熔断后停止派发）

## 二、① MRD 结构化（5 个 Skill）

① 持有 5 个 Skill，覆盖"拆解 / 抽取 / 模板 / 术语 / 开放问题"完整拆解链。

### mrd_decomposer
- **所属 Agent**：① MRD 结构化
- **作用**：按 5 大模块固定结构（市场 / 用户 / 竞品 / 产品规划 / 风险）拆解 MRD（v3 §3.2）
- **输入**：`workspace/shared/input/mrd.md` 全文 + `breakdown_methodology.md` 拆解方法论
- **输出**：`breakdown/requirements_list.md`（5 大模块结构 + 9 字段）+ 47+ 需求条目（带 ID）
- **调用条件**：阶段 1 Manager 派发后自动调用 1 次
- **课程依据**：L07《需求拆解》+ L08《结构化分析》+ 7.2 §1
- **关联 Skills**：与 `requirement_extractor` 串联（拆解 → 抽取）；与 `open_question_lister` 互补（拆解同时记录模糊点）

### requirement_extractor
- **所属 Agent**：① MRD 结构化
- **作用**：用 INVEST 检查法从拆解结果抽取 47+ 需求条目（带 ID）（v3 §3.2）
- **输入**：`mrd_decomposer` 的产物（5 大模块结构）+ `requirement_id_spec.md` 命名规范
- **输出**：47+ 条需求条目，每条含 ID（MRD-R-NNN）/ 描述 / 优先级 / 验收点
- **调用条件**：`mrd_decomposer` 完成后自动调用
- **课程依据**：L08《INVEST 检查法》+ 7.0 M03
- **关联 Skills**：与 `user_story_template` 串联（抽取 → 用户故事转写）

### user_story_template
- **所属 Agent**：① MRD 结构化
- **作用**：套用用户故事模板把需求条目转写为"作为... 我想... 以便..."（v3 §3.2）
- **输入**：需求条目（带 ID）+ 角色清单（从 MRD 用户画像抽取）
- **输出**：每条需求对应 1 条用户故事（保持 ID 一致）
- **调用条件**：`requirement_extractor` 完成后自动调用
- **课程依据**：L07《用户故事》+ L08
- **关联 Skills**：与 `glossary_extractor` 并联（同时产出术语表，避免转写时用词不一致）

### glossary_extractor
- **所属 Agent**：① MRD 结构化
- **作用**：抽取业务术语表（glossary.md），给下游统一术语口径（v3 §3.2）
- **输入**：`mrd.md` 全文（不限于拆解结果）
- **输出**：`breakdown/glossary.md`（术语 / 别名 / 定义 / 首次出现章节）
- **调用条件**：阶段 1 与 `mrd_decomposer` 并行调用，结果汇总到 Manager 验收
- **课程依据**：L07《术语管理》+ 7.0 M03
- **关联 Skills**：与下游所有写作 Agent 共享（glossary 是术语统一性锚点）

### open_question_lister
- **所属 Agent**：① MRD 结构化
- **作用**：列出 MRD 中所有模糊点 / 缺失信息到 open_questions.md（v3 §3.2）
- **输入**：MRD 全文 + 拆解结果
- **输出**：`breakdown/open_questions.md`（条目数 / 模糊点原文 / 推断依据 / 建议澄清方式）
- **调用条件**：`mrd_decomposer` 完成后自动调用；条目数 ≥ 5 时触发 needs_clarify 邮件给 Human
- **课程依据**：L27《Human as 甲方》+ M17 + 7.0 §4 共性 1
- **关联 Skills**：与 `mrd_decomposer` 互补；与 Manager 的 `sub_agent_router` 串联（needs_clarify 邮件触达 Human）

## 三、② 产品组（4 个 Skill）

② 持有 4 个 Skill，覆盖 PRD1 / PRD2 写作全流程。略低于 v3.1 收紧下界（≥ 5），7.x 完善方案中已规划补 1 个 `gt_matcher`（产品子库版）。

### prd1_writer_sop
- **所属 Agent**：② 产品组
- **作用**：套用 4 维映射规则（场景 → 价值 → 功能 → 衡量）写 PRD1 8 子模块（v3 §3.3）
- **输入**：`breakdown/requirements_list.md` + `gt_samples_product/` 30 条产品级 GT
- **输出**：`prd/section_1_2.md` 中的 PRD1 部分（产品概述 8 子模块：背景 / 目标 / 范围 / 用户画像 / 价值主张 / 用例总览 / 衡量指标 / 风险）
- **调用条件**：阶段 3 Manager 派发后自动调用 1 次
- **课程依据**：L07《产品视角》+ L08《结构化写作》+ M04
- **关联 Skills**：与 `prd2_function_spec` 串联（PRD1 价值 → PRD2 功能）；与 `cross_section_consistency` 串联（自检 + Manager 二次验收）

### prd2_function_spec
- **所属 Agent**：② 产品组
- **作用**：把价值动作转写为功能关键词 + P0~P3 优先级（v3 §3.3）
- **输入**：PRD1 价值主张 + 需求条目 + `prd2_template.md`
- **输出**：`prd/section_1_2.md` 中的 PRD2 部分（功能规格表：ID / 名称 / 描述 / 优先级 / 验收点）
- **调用条件**：`prd1_writer_sop` 完成后自动调用
- **课程依据**：L07 + L08 + M04
- **关联 Skills**：与 `feature_id_assigner` 强绑定（功能 ID 是 PRD2 输出的核心契约）

### feature_id_assigner
- **所属 Agent**：② 产品组
- **作用**：强制 F-DOMAIN_类型_序号 命名规范，输出 feature_id_list.md 给下游共享（v3 §3.3）
- **输入**：PRD2 功能规格表
- **输出**：`prd/feature_id_list.md`（所有功能 ID + 名称 + 所属模块 + 优先级）
- **调用条件**：`prd2_function_spec` 完成后自动调用；输出后 3 个并发 Agent（②''/②'''/④）共享此文件
- **课程依据**：L07《功能 ID 规范》+ L26《接力棒》+ M04/M11
- **关联 Skills**：与 ②''/②'''/④ 的 Skill 强绑定（下游所有工作以 feature_id_list.md 为输入契约）

### cross_section_consistency
- **所属 Agent**：② 产品组
- **作用**：检查 PRD1.6 价值主张 ↔ PRD2.1 功能清单的跨章节引用一致性（v3 §3.3）
- **输入**：`section_1_2.md` 全文
- **输出**：一致性报告（通过 / 列出冲突的功能 ID 或价值主张点）
- **调用条件**：`prd2_function_spec` 完成后自动调用 1 次；Manager 验收前可重调用
- **课程依据**：L26《跨章节一致性》+ M04 + 7.3 §3 G3
- **关联 Skills**：与 `prd1_writer_sop` + `prd2_function_spec` 串联（写完自检）；与 Manager 的 `artifact_validator` 互补

## 四、②'' 流程组（4 个 Skill）

②'' 持有 4 个 Skill，覆盖 PRD3 流程图 / 旅程 / 异常穷举。略低于 v3.1 下界，已规划补 `gt_matcher`（流程子库版）。

### prd3_writer_sop
- **所属 Agent**：②'' 流程组
- **作用**：套用"场景 → 阶段；功能 → 行为"映射写 PRD3 3 子模块（v3 §3.4）
- **输入**：`feature_id_list.md` + `gt_samples_flow/` 20 条流程级 GT
- **输出**：`prd/section_3.md`（用户旅程 + 业务流程图 + 操作步骤 3 子模块）
- **调用条件**：阶段 5 并发启动后自动调用 1 次
- **课程依据**：L03《流程建模》+ L09《业务流程》+ M05

### mermaid_flowchart
- **所属 Agent**：②'' 流程组
- **作用**：用 Mermaid flowchart 语法画业务流程图（强制审批/校验/数据更新 3 环节）（v3 §3.4）
- **输入**：业务流程文本描述（来自 `prd3_writer_sop`）
- **输出**：Mermaid flowchart 代码块（嵌入 section_3.md）+ 跳转链接到 `handoff_34.md`
- **调用条件**：`prd3_writer_sop` 写完"业务流程图"小节时自动调用
- **课程依据**：L09 + 6.1-3《顺序/并发》+ M05
- **关联 Skills**：与 `prd3_writer_sop` 串联；与 ②''' 共享输出（通过 handoff_34.md 传递数据实体）

### exception_branch_lister
- **所属 Agent**：②'' 流程组
- **作用**：穷举异常分支（网络失败 / 权限不足 / 数据冲突 / 审批驳回 / 状态非法）（v3 §3.4）
- **输入**：`prd3_writer_sop` 的主流程图
- **输出**：异常分支清单（每条含：触发条件 / 用户感知 / 系统响应 / 恢复路径）
- **调用条件**：`mermaid_flowchart` 完成后自动调用
- **课程依据**：L09《异常处理》+ L26《容错》+ M05
- **关联 Skills**：与 `mermaid_flowchart` 互补（图 + 异常表）；与 ③ 质检的 `executability_checker` 共享异常分支列表

### journey_map_designer
- **所属 Agent**：②'' 流程组
- **作用**：设计用户旅程地图（场景 → 触点 → 情绪曲线 → 机会点）（v3 §3.4）
- **输入**：用户画像（来自 breakdown）+ 主流程 + 异常分支
- **输出**：`prd/section_3.md` 中"用户旅程"子模块（Mermaid journey 语法 + 表格）
- **调用条件**：`prd3_writer_sop` 启动时与主流程图并行调用
- **课程依据**：L09 + 6.1-3
- **关联 Skills**：与 `prd3_writer_sop` 串联；与 ② 产品组的 `user_story_template` 互补（用户故事 → 旅程地图）

## 六、④ 页面组（5 个 Skill）

④ 持有 5 个 Skill，是 5 个写作 Agent 中 Skill 最齐全的之一（与 Manager 并列 5 个），覆盖 PRD5 全部工作。

### prd5_writer_sop
- **所属 Agent**：④ 页面组
- **作用**：套用"页面清单 → 字段表 → 状态机 → 交互 → 权限"五步法写 PRD5（v3 §3.6）

- **课程依据**：L07《页面规格》+ L30《可观测性 + UI 基线》+ M07
- **关联 Skills**：与 `page_template_loader` 串联；与 `component_consistency_check` 串联（写完自检组件一致性）

### page_template_loader
- **所属 Agent**：④ 页面组

## 七、③ 质检（6 个 Skill）

③ 持有 6 个 Skill，是 7 个 Agent 中 Skill 最多的角色。覆盖 5 维度评分 + 3 视角审查。

### completeness_checker
- **所属 Agent**：③ 质检
- **作用**：检查 PRD 5 大章节 + 20 子模块齐全性（缺失即扣分）（v3 §3.7）
- **输入**：5 个 section 文件（section_1_2/3/4/5.md）+ `qa_checklist.md` 章节清单
- **输出**：完整性评分（0-20 分）+ 缺失章节 / 子模块清单
- **调用条件**：阶段 7 Manager 派发后自动调用
- **课程依据**：L36《评测体系-完整性》+ 6.4-5
- **关联 Skills**：与 `scoring_engine` 串联（评分汇总）；与 `consistency_checker` 并联（同时检查）

### consistency_checker
- **所属 Agent**：③ 质检
- **作用**：检查跨章节引用 / 术语 / 流程闭环 / 数值 / ID 一致性（v3 §3.7）
- **输入**：5 个 section 文件 + glossary.md + feature_id_list.md
- **输出**：一致性评分（0-20 分）+ 不一致点清单（哪个 ID 在哪一节被错误引用）
- **调用条件**：`completeness_checker` 完成后自动调用
- **课程依据**：L26《跨章节一致性》+ L36 + 6.4-5
- **关联 Skills**：与 `completeness_checker` 串联；与 ② 产品组的 `cross_section_consistency` 互补（② 自检 + ③ 复检）

### executability_checker
- **所属 Agent**：③ 质检
- **作用**：检查每条功能需求可写测试用例 + 验收标准 SMART + 异常分支覆盖（v3 §3.7）
- **输入**：5 个 section 文件 + 测试用例模板
- **输出**：可执行性评分（0-30 分）+ 难写测试用例的功能清单 + 异常分支覆盖矩阵
- **调用条件**：`consistency_checker` 完成后自动调用
- **课程依据**：L36《可执行性》+ 6.4-5
- **关联 Skills**：与 `consistency_checker` 串联；与 ②'' 的 `exception_branch_lister` 共享异常分支

### risk_identifier
- **所属 Agent**：③ 质检
- **作用**：识别模糊词 / 缺失依赖 / 范围蔓延信号 → 标注 [TBD]（v3 §3.7）
- **输入**：5 个 section 文件 + 模糊词词典（"可能/大概/也许"等）
- **输出**：风险评分（0-15 分）+ 模糊词位置清单 + [TBD] 标注建议
- **调用条件**：`executability_checker` 完成后自动调用
- **课程依据**：L27《风险识别》+ L36 + 6.4-5 + M17
- **关联 Skills**：与 `completeness_checker` 互补（完整性是"有没有"，风险是"有没有漏洞"）；与 Manager 的 `qa_decision_tree` 串联（风险高 → 触发 revise）

### style_consistency_checker
- **所属 Agent**：③ 质检
- **作用**：检查术语 / 句式 / 排版风格统一性（v3 §3.7）
- **输入**：5 个 section 文件 + 风格模板（术语表 + 句式规范 + 排版规范）
- **输出**：风格评分（0-15 分）+ 不一致点（术语混用 / 句式不统一 / 排版错位）
- **调用条件**：`risk_identifier` 完成后自动调用
- **课程依据**：L36 + 6.4-5
- **关联 Skills**：与 ④ 页面组的 `component_consistency_check` 互补；与 `scoring_engine` 串联

### scoring_engine
- **所属 Agent**：③ 质检
- **作用**：5 维度汇总为 100 分制总分 + 雷达图 + Langfuse score 回调（v3 §3.7 + 7.0 §9.3）
- **输入**：5 个 check 的评分（完整性 20 + 一致性 20 + 可执行性 30 + 风险 15 + 风格 15）
- **输出**：`qa/qa_report.md`（总分 + 5 维度明细 + 雷达图 + trace_id）+ Langfuse score API 调用（5 维度 + 总分）
- **调用条件**：5 个 check 全部完成后自动调用 1 次；Langfuse 回调失败时本地兜底（写本地 log）
- **课程依据**：L30《Langfuse 回调》+ L36《评分汇总》+ M15/M16 + 7.7 §3 G4
- **关联 Skills**：聚合前 5 个 check 的输出；与 Manager 的 `qa_decision_tree` 串联（总分 → 决策）
