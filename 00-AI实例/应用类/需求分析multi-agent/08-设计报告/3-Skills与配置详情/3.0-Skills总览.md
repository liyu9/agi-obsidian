## 1. 设计背景

v3 架构采用 1 个 Manager + 5 个写作/拆解子 Agent + 1 个独立质检 Agent 的拓扑，共 7 个持久化角色。每个角色配 4-6 个 Skill 工具，工具集是角色"做事"的具体抓手——Soul 定义它"想什么"，NEVER 清单定义它"不做什么"，Skills 定义它"能做什么"。v3.1 校验后，7 个 Agent 合计 33 个 Skill，全部满足 L25《团队角色设计》中"每个角色 ≥ 3 个 Skill、且工具集覆盖完整职责"的下界（实际下界已收紧至 ≥ 5 个，参见 7.0 §2.1）。

矩阵总览的目的不是把 33 个 Skill 一一展开——那是 3.1 字典的事——而是提供"角色 × 工具"的鸟瞰视角。读者可以快速判断：某个能力（如"GT 匹配"）由谁提供？某个角色（如 ② 产品组）总共能做什么？哪些工具是多个角色共享的基础设施？

## 3. 按 Agent 分组的 Skill 列表

下表按 Agent 分组，列出每个 Skill 的核心作用概要（详细字段见 3.1 字典）。每个 Agent 末尾给出 Skill 数量与该 Agent 的核心职责一句话。

### 3.1 Manager（5 个）

Manager 是 1+5 架构的调度者与验收者，5 个 Skill 覆盖"GT 选择 / 任务派发 / 验收 / 决策 / 降级"完整闭环。

| Skill | 核心作用 |
|-------|---------|
| `gt_matcher` | 根据 MRD 关键词在 GT 库中匹配 1-2 份历史 PRD 样本，作为下游写作 Agent 的校准锚点 |
| `sub_agent_router` | 把任务派发到 5 个子 Agent 的 inbox（邮箱协议三态状态机） |
| `artifact_validator` | 验收每个子 Agent 产物（清单 / 字段 / 格式）——不通过则 reject 重派 |
| `qa_decision_tree` | 读 qa_report.md → 决策（通过 / 修订 / 熔断） |
| `level3_fallback` | L1 重试 → L2 换模型 → L3 熔断（与 ③ 质检共享降级基础设施）|

> **核心职责**：全局视野、不下场、严验收；唯一接口（与 Human 和子 Agent）。

### 3.2 ① MRD 结构化（5 个）

① 是 MRD → 5 大模块的拆解者，5 个 Skill 围绕"拆得细 / 问得全"展开。

| Skill | 核心作用 |
|-------|---------|
| `mrd_decomposer` | 按 5 大模块固定结构（市场 / 用户 / 竞品 / 产品规划 / 风险）拆解 MRD |
| `requirement_extractor` | 用 INVEST 检查法从拆解结果抽取 47+ 需求条目（带 ID） |
| `user_story_template` | 套用用户故事模板把需求条目转写为"作为... 我想... 以便..." |
| `glossary_extractor` | 抽取业务术语表（glossary.md），给下游统一术语口径 |
| `open_question_lister` | 列出 MRD 中所有模糊点 / 缺失信息到 open_questions.md（≥ 5 条触发 needs_clarify）|

> **核心职责**：宁可多问，不要漏拆；遇到模糊词先列问题、不擅自补全。

### 3.3 ② 产品组（4 个）

② 是 PRD1+2 的撰写者，4 个 Skill 围绕"价值清晰 / 功能 ID 规范"展开。

| Skill | 核心作用 |
|-------|---------|
| `prd1_writer_sop` | 套用 4 维映射规则（场景 → 价值 → 功能 → 衡量）写 PRD1 8 子模块 |
| `prd2_function_spec` | 把价值动作转写为功能关键词 + P0~P3 优先级 |
| `feature_id_assigner` | 强制 F-DOMAIN_类型_序号 命名规范，输出 feature_id_list.md 给下游共享 |
| `cross_section_consistency` | 检查 PRD1.6 价值主张 ↔ PRD2.1 功能清单的跨章节引用一致性 |

> **核心职责**：对用户友好、价值清晰、对业务方负责；结构 > 文采。

### 3.4 ②'' 流程组（4 个）

②'' 是 PRD3 的撰写者，4 个 Skill 围绕"流程图 / 异常穷举"展开。

| Skill | 核心作用 |
|-------|---------|
| `prd3_writer_sop` | 套用"场景 → 阶段；功能 → 行为"映射写 PRD3 3 子模块 |
| `mermaid_flowchart` | 用 Mermaid flowchart 语法画业务流程图（强制审批/校验/数据更新 3 环节）|
| `exception_branch_lister` | 穷举异常分支（网络失败 / 权限不足 / 数据冲突 / 审批驳回 / 状态非法）|
| `journey_map_designer` | 设计用户旅程地图（场景 → 触点 → 情绪曲线 → 机会点）|

> **核心职责**：严谨穷举、异常分支、对后端负责。

### 3.5 ②''' 数据组（4 个）

②''' 是 PRD4 的撰写者，4 个 Skill 围绕"ER 图 / 安全"展开。

| Skill | 核心作用 |
|-------|---------|
| `prd4_writer_sop` | 套用"实体识别 / 关系设计 / 字段定义"三步法写 PRD4 3 子模块 |
| `er_diagram_designer` | 用 Mermaid erDiagram 画实体关系图（标注基数 / 主外键）|
| `data_flow_lister` | 列出跨模块数据流（哪个功能 → 哪个表 → 哪个字段）|
| `security_checklist` | 检查加密 / 脱敏 / 审计 / 软删除 / 索引 5 项安全基线 |

> **核心职责**：模型严谨、约束完整、对后端+DBA 负责。

### 3.6 ④ 页面组（5 个）

④ 是 PRD5 的撰写者，5 个 Skill 围绕"页面模板 / 状态机 / 可访问性"展开。

| Skill | 核心作用 |
|-------|---------|
| `prd5_writer_sop` | 套用"页面清单 → 字段表 → 状态机 → 交互 → 权限"五步法写 PRD5 |
| `page_template_loader` | 按功能类型（CRUD 列表 / 表单 / 详情 / 仪表盘 / 向导）加载对应模板 |
| `component_consistency_check` | 检查页面间组件命名 / 样式一致性（按钮 / 表单 / 表格 3 类组件库）|
| `mermaid_wireframe` | 用 Mermaid 画页面跳转关系图（page A → page B 触发条件）|
| `accessibility_baseline` | 可访问性基线检查（颜色对比度 / 键盘可达 / 屏幕阅读器 / 焦点环）|

> **核心职责**：视觉可还原、组件可复用、状态完整、权限清晰；对前端+设计师负责。

### 3.7 ③ 质检（6 个）

③ 是 PRD 全文的独立审查者，6 个 Skill 围绕"5 维度评分 + 3 视角审查"展开。

| Skill | 核心作用 |
|-------|---------|
| `completeness_checker` | 检查 PRD 5 大章节 + 20 子模块齐全性（缺失即扣分）|
| `consistency_checker` | 检查跨章节引用 / 术语 / 流程闭环 / 数值 / ID 一致性 |
| `executability_checker` | 检查每条功能需求可写测试用例 + 验收标准 SMART + 异常分支覆盖 |
| `risk_identifier` | 识别模糊词 / 缺失依赖 / 范围蔓延信号 → 标注 [TBD] |
| `style_consistency_checker` | 检查术语 / 句式 / 排版风格统一性 |
| `scoring_engine` | 5 维度汇总为 100 分制总分 + 雷达图 + Langfuse score 回调 |

> **核心职责**：挑剔质疑、找漏洞、不替写者决策；只报告不修改。

## 5. 跨 Agent 共享 Skill 标记

v3 架构中 33 个 Skill 全部为"角色独占"——每个 Skill 只有一个 Agent 持有，避免多 Agent 共享同一工具导致的调用歧义与责任模糊。但有 3 类工具**底层基础设施**是共享的：

| 共享层 | 描述 | 影响 Skill | 引用 |
|--------|------|-----------|------|
| **GT 库** | 4 类分库（产品 30 / 流程 20 / 数据 20 / 页面 50） | Manager 的 `gt_matcher` 检索全局索引；3 个写作 Agent 后续补充的本角色 gt_matcher 检索子库 | 7.0 §4 共性 1 |
| **降级机制** | L1 重试 → L2 换模型 → L3 熔断 | Manager 的 `level3_fallback` 持有控制权；所有 Agent 的 LLM 调用都接入此机制 | v3 §6.2 |
| **trace_id 与 Langfuse** | 7 个 Agent 各有前缀但接入同一追踪系统 | 所有 Agent 的输出契约都必含 trace_id；③ 质检的 `scoring_engine` 是 Langfuse score 回调的核心实施者 | 7.0 §9.2 / §9.3 |

**Owner 唯一原则**（v3 关键决策 5）：每个 Skill 只有一个 Agent 持有调用权，即使底层共享同一份数据/基础设施。"gt_matcher" 计划中的两个实例（Manager 全局版 + 写作 Agent 子库版）将由 Manager 统一配置检索范围，写作 Agent 的子库版只读、不修改 GT 库。

## 6. Skill 演化的下一步

依据 7.x 校验，Skill 集合的近期完善方向有 4 个：

1. **写作 Agent 补 gt_matcher 子库版**（P1）：②/②''/②''' 各补 1 个角色内 GT 检索工具，将 Skill 数量从 33 提到 36。
2. **Manager 决策模式库接入 RAG**（P0）：`decision_patterns.md` 升级为 ≥ 30 条 YAML 化模式 + 向量索引（参见 7.1 §3 G1）。
3. **③ 质检 3 视角 checklist 完善**（P1）：开发 ≥ 10 项 + 测试 ≥ 10 项 + 运营 ≥ 5 项（参见 7.7 §3 G3）。
4. **所有 Agent 工具白名单**（P0）：7.0 §4 共性 6 要求的"允许写入 / 允许读取 / 禁止"三类清单将在 3.1 字典的每个 Skill 条目中标注。

具体每个 Skill 的输入/输出/调用条件/课程依据见 [`3.1-Skills字典.md`](3.1-Skills字典.md)。
