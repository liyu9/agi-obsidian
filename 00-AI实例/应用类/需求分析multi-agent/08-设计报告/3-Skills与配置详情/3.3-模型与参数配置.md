## 1. 设计原则

v3 的模型与参数配置遵循 3 条核心原则：

**原则 1：主备模型同系列**——主模型用 DeepSeek-V3.2，备份模型统一用 V3.1（同系列，质量差异 < 5%）。这条约束保证 L2 降级后输出风格不会突变，避免降级后引入额外的"模型风格切换"问题。

**原则 2：上下文与质量权衡**——5 个写作 Agent 启用 thinking 模式（质量优先），③ 质检禁用 thinking（速度优先）。质检追求"快速读完全文 + 找到缺陷"，不需要深度推理链；写作追求"逻辑链完整 + 表达精准"，需要 thinking 辅助。Manager 启用 thinking 是因为它需要做大量决策推理（GT 匹配、修复策略选择），对推理质量敏感。

**原则 3：硬上限 + 软引导**——每个 Agent 有 maxTokens 硬上限（防止输出超长），同时有 timeout 软引导（防止 LLM 调用卡死拖垮整个流程）。两者结合保证系统既能产出充足内容，又不会因为单点故障阻塞端到端流程。

## 2. 主配置表（7 Agent × 6 字段）

下表是 7 个 Agent 的模型与参数主表，源自 v3 §6.1。Agent 按 v3 §2.2 顺序排列。

| Agent | 主模型 | 备份模型 | maxTokens | timeout | thinking |
|-------|--------|---------|-----------|---------|----------|
| **Manager** | DeepSeek-V3.2 | V3.1 | 8,192 | 60s | 启用 |
| **① MRD 结构化** | DeepSeek-V3.2 | V3.1 | 32,768 | 600s | 启用 |
| **② 产品组** | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| **②'' 流程组** | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| **②''' 数据组** | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| **④ 页面组** | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| **③ 质检** | DeepSeek-V3.2 | V3.1 | 32,768 | 600s | **禁用（速度优先）** |

### 2.1 字段解读

**主模型 DeepSeek-V3.2**：v3 选型时（基于课程 L31《模型选型》）评估对比了 6 款主流 LLM。V3.2 在中文长文本结构化写作、代码/Mermaid 生成、多视角推理 3 个维度上综合得分最高。中等复杂度 B 端 MRD 的拆解/写作/质检任务，V3.2 单 Agent 完成质量稳定在 85+ 分（同 prompt 同 GT 样本重复 5 次的均分）。

**备份模型 V3.1**：与 V3.2 同系列（同团队、同训练范式），质量差异 < 5%。这条来自 v3 §10 风险缓解表的最末行——"L2 备份模型用 V3.1（同系列，质量差异 < 5%）"。选择同系列而非跨系列备份（如 Qwen / Claude）的核心理由是降级时不需要重新校准 prompt，输出风格稳定。

**maxTokens 8,192 / 32,768**：Manager 的 8K 是因为它本身不写长文——它的输出是 5-10 行的任务邮件、决策报告、验收反馈。32K 是其他 Agent 的统一上限，覆盖单 Agent 最长产出（PRD1+2 约 12K tokens、PRD3-5 各 4-8K tokens）。

**timeout 60s / 300s / 600s**：Manager 60s 因为它做的是"短决策"，超过 60s 没结果就触发降级。① MRD 和 ③ 质检给到 600s 因为它们读全文（MRD 可能 20K tokens / PRD 全文 25K tokens）+ 深度推理。5 个写作 Agent 统一 300s 是因为它们的产出有上限（32K tokens）但有中等推理量。

**thinking 启用 / 禁用**：5 个写作 Agent 启用 thinking 提升质量（牺牲约 20% 速度，换约 8 分质量提升）。③ 质检禁用 thinking 是 v3 的"速度优先"决策——质检追求"快速找缺陷"，启用 thinking 反而会让模型"想太多"而漏掉浅层问题，且质检环节耗时占比约 20%，提速对端到端流程的收益显著。

### 2.2 与上下文硬约束的关系

v3 §1.3 关键设计原则 3：每个 Agent 单次上下文 < 30K token。本表的 maxTokens 是"输出 token 上限"，不是"输入上下文上限"。实际输入上下文控制由各 Agent 的 §4 提示词骨架决定（启动索引 + GT 注入 + 任务输入）：

- Manager 输入上下文：约 20K（含 5 子 Agent 启动索引 + 决策上下文 + GT 引用），不超 25K。
- ① MRD 输入上下文：约 8K（MRD 全文 + 拆解方法论 + 行业 patterns），不超 15K。
- ② 产品组输入上下文：约 15K（breakdown 产物 + 30 条 GT + 模板 + 任务），不超 20K。
- ②'' 流程组 / ②''' 数据组：各约 8K（feature_id_list + handoff + 20 条 GT + 模板）。
- ④ 页面组输入上下文：约 15K（feature_id_list + handoff_45 + 5+ 套模板 + 组件库）。
- ③ 质检输入上下文：约 25K（5 个 section 全文 + checklist + 视角标准），不超 30K。

所有 Agent 的输入上下文都在 30K 安全线以内（v3 关键决策 4）。

## 3. 降级参数表（3 级容错）

v3 §6.2 定义了 3 级容错机制——L1 软失败 → L2 硬失败 → L3 熔断。本表展开每级的具体参数。

| 级别 | 触发条件 | 处理动作 | 重试次数 | 切换模型 | 是否通知 Human |
|------|---------|---------|---------|---------|--------------|
| **L1 软失败** | JSON 解析失败 / 字段缺失 / 格式不合规 | 自动重试（同模型 + 新种子） | 1 次 | 否 | 否 |
| **L2 硬失败** | L1 失败 / LLM 调用超时 / 5xx 错误 | 切换备份模型 V3.1 + 重试 | 1 次 | 是（V3.2 → V3.1） | 否 |
| **L3 熔断** | L2 失败 / 同一 Agent 连续 reject ≥ 3 轮 / 质检总分连续 3 轮 < 80 | 停止派发 + error_alert 邮件给 Human | — | — | **是（必发）** |

### 3.1 L1 重试参数详解

- **重试次数**：1 次（不重试多次，避免一次失败拖垮整个 Agent 上下文）
- **种子策略**：新随机种子（避免重复同样的失败模式）
- **耗时上限**：与该 Agent 的 timeout 相同
- **失败计数**：L1 重试失败计入"子 Agent 失败次数"（达到 3 次触发 L3）
- **典型场景**：JSON 解析失败（括号不匹配 / 字段缺失 / 字段类型错误）、Markdown 标题层级错误、Mermaid 代码块语法错误

### 3.2 L2 模型切换参数详解

- **切换时机**：L1 重试失败后立即触发
- **切换模型**：DeepSeek-V3.2 → DeepSeek-V3.1（同系列，质量差异 < 5%）
- **重试次数**：1 次（L2 失败不再自动重试，直接 L3）
- **风格保持**：V3.1 与 V3.2 同 prompt 同 GT 样本，输出风格基本一致
- **失败计数**：L2 失败计入"子 Agent 失败次数"（达到 3 次触发 L3）
- **典型场景**：LLM 服务 5xx 错误、API 限流、超时（timeout 耗尽）、输出截断（> maxTokens）

### 3.3 L3 熔断参数详解

- **触发条件**（满足任一即触发）：
  1. L2 失败（L1 + L2 都失败）
  2. 同一子 Agent 连续 reject ≥ 3 轮（Manager 验收累计 3 次不通过）
  3. ③ 质检总分连续 3 轮 < 80（无论 reject 来自哪个 Agent）
  4. 任意子 Agent 单次任务耗时 > 30 min（流程型超时）
- **处理动作**：
  1. 停止派发新任务给该 Agent
  2. 发 error_alert 邮件给 Human（含 session_id / trace_id / 失败原因 / 累计失败次数）
  3. Manager 等待 Human 决策：`rescue`（继续重试）/ `abandon`（放弃当前 session）/ `redirect`（转交其他 Agent 修复）
- **是否计入 L 课**：L31《3 级降级》+ M14

## 4. 上下文剪裁规则

依据 7.0 §4 共性 4（上下文剪裁策略），v3.1 在 3.3 配置层面定义剪裁规则，与 maxTokens 配合形成"输入+输出"双层保护。

| Agent | 输入剪裁触发 | 剪裁策略 | 压缩策略 |
|-------|------------|---------|---------|
| **Manager** | 输入 > 20K | 保留：当前任务上下文 + SOP + 决策模式（最近 5 条）；Prune：旧 GT 引用 + 历史邮件 | LLM 摘要压缩 50% |
| **① MRD** | 输入 > 8K | 保留：MRD 全文 + 拆解方法论；Prune：行业 patterns 子节 | 直接剪裁（非关键段）|
| **② 产品组** | 输入 > 15K | 保留：当前需求 + 3-5 条相关 GT；Prune：其他 GT | 关键词匹配压缩 |
| **②'' 流程组** | 输入 > 8K | 保留：feature_id_list + handoff_34 + 2-3 条相关 GT | 直接剪裁 |
| **②''' 数据组** | 输入 > 7K | 保留：feature_id_list + handoff_34/45 + 2-3 条相关 GT | 直接剪裁 |
| **④ 页面组** | 输入 > 15K | 保留：feature_id_list + handoff_45 + 3-5 套相关模板 | 关键词匹配压缩 |
| **③ 质检** | 输入 > 25K | 保留：5 个 section 全文 + checklist；Prune：详细 GT 引用 | LLM 摘要压缩 70% |

剪裁是 v3.1 新增机制（v3.0 仅规定硬约束 < 30K），具体实现见 7.1-7.7 §3 G3 完善方案。

## 5. 并发与速率限制

阶段 5 的章节级并发（②''/②'''/④ 三路并发）需要额外的速率控制：

| 资源 | 上限 | 说明 |
|------|------|------|
| 同时活跃 LLM 调用 | 4 路 | Manager 1 + 3 路并发写作 |
| 单 LLM 调用 QPS | 5 | 避免触发 DeepSeek 限流 |
| 单 session 总 token 消耗 | 1.5M | 包含输入+输出+重试，超限触发 L3 |
| 端到端耗时 | 5h | 中等复杂度 MRD，超时触发 checkpoint_request |

## 6. 模型配置的实施依赖

配置表中的所有参数在实施时依赖 3 个外部组件：

1. **DeepSeek API 网关**：负责 V3.2 / V3.1 路由 + QPS 限流 + 5xx 重试
2. **Watchdog 守护进程**：每 10 分钟扫描邮箱中的 in_progress 邮件，发现超时自动重置
3. **Langfuse 客户端**：所有 LLM 调用都经过 Langfuse SDK 上报（详见 3.4 可观测性配置）
