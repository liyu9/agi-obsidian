## 1. 协作协议

### 1.1 共享工作区

7 个 Agent 通过共享文件系统协作，目录按 Owner 唯一原则组织——每个文件只有一个 Agent 有写权限：

```
workspace/shared/
├── input/mrd.md                       # Owner: Human
├── breakdown/                         # Owner: ① MRD 结构化
│   ├── requirements_list.md           #   功能需求清单（ID/描述/优先级/验收点）
│   ├── non_functional.md              #   非功能需求
│   ├── open_questions.md              #   待澄清问题
│   ├── glossary.md                    #   业务术语表
│   └── section_3.md                   #   竞品分析完整段
├── prd/                               # 5 个写作 Agent 按 section 切分 Owner
│   ├── outline.md                     #   大纲（Manager 验收后才允许并发）
│   ├── section_1_2.md                 #   PRD1+PRD2（Owner: ② 产品组）
│   ├── section_3.md                   #   PRD3（Owner: ②'' 流程组）
│   ├── section_4.md                   #   PRD4（Owner: ②''' 数据组）
│   ├── section_5.md                   #   PRD5（Owner: ④ 页面组）
│   ├── handoff_34.md                  #   ②'' → ②''' 数据契约
│   ├── handoff_45.md                  #   ②''' → ④ 页面契约
│   ├── feature_id_list.md             #   ② 输出，下游 3 个 Agent 共享
│   └── prd_draft.md                   #   拼装后的 PRD 草稿
├── qa/qa_report.md                    # Owner: ③ 质检
├── delivery/prd_final.md              # Owner: Manager
├── gt_samples/                        # GT 样本库（4 类分库：产品 30/流程 20/数据 20/页面 50）
└── mailboxes/                         # 邮箱协议（8 个 JSON 文件）
```

### 1.2 三态邮箱状态机

```
unread ──Agent 读取──> in_progress ──任务完成──> done
  ▲                        │
  │                        │ Watchdog 超时（10 min）
  └────────────────────────┘
       自动 reset + 重试
```

邮件是 JSON 对象：发送方、接收方、任务类型、输入/输出路径、时间戳。

### 1.3 handoff 接力

5 个写作 Agent 通过 handoff 文件传递接口契约（只含接口信息，不复制 PRD 全文）：

```
② 产品组 ──feature_id_list.md──> ②'' 流程组 ──handoff_34.md──> ②''' 数据组 ──handoff_45.md──> ④ 页面组
```

关键约束：主 Agent 验收前序产物后，才允许后序 Agent 启动。

## 2. 端到端时序

### 2.1 9 阶段 SOP

```
阶段 0  Manager 初始化（读 MRD → 初始化工作区 → 选 GT → 检查完整性）
阶段 1  派 ① MRD 结构化
阶段 2  验收 ① 产物
阶段 3  派 ② 产品组
阶段 4  验收 ② 产物 + 开 outline 锁
阶段 5  并发派发（②'' / ②''' / ④ 三路并发）
阶段 6  收集 + 验收并发产物
阶段 7  派 ③ 质检
阶段 8  读质检报告决策（通过 / 修订 / 熔断）
阶段 9  归档 + Human 终审
```

### 2.2 章节级并发

阶段 5 是效率核心。PRD3/4/5 共享 feature_id_list.md 但彼此不依赖，3 路并发可节省约 40% 耗时。安全前提是 outline 锁——阶段 4 验收后锁定接口契约。

### 2.3 耗时估算（中等复杂度 MRD）

| 段 | 阶段 | 耗时 |
|----|------|------|
| 串行段 | 0-4 | ~2h |
| 并发段 | 5-6 | ~2h（比串行节省 40%） |
| 质检段 | 7-8 | ~1h |
| 人类介入 | 9 | 异步（不阻塞） |

| Agent | 主模型 | 备份模型 | maxTokens | timeout | thinking |

| ① MRD 结构化 | DeepSeek-V3.2 | V3.1 | 32,768 | 600s | 启用 |
| ② 产品组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| ②'' 流程组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| ②''' 数据组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |
| ④ 页面组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 启用 |

## 4. 3 级降级

```
L1 软失败（自动恢复）
  触发：JSON 解析失败 / 字段缺失
  处理：自动重试 1 次（换种子）
       │ 失败
       ▼
L2 硬失败（切换模型）
  触发：L1 失败 / LLM 调用超时
  处理：切换备份模型（DeepSeek-V3.1）+ 重试
       │ 失败
       ▼
L3 熔断（人类介入）
  触发：L2 失败 / 3 轮 reject 不收敛
  处理：error_alert → Human
  Human 决定：rescue / abandon / 调向
```

L1/L2 全自动，Agent 不感知故障。L3 才触发人类介入——只有连续 3 轮质检不达标或 L1+L2 都失败时才需 Human 决策。

## 6. 质检体系

### 6.1 100 分制 5 维度

通过线 **80 分**。但即使总分达标，任一维度低于及格线（完整性 16 / 一致性 16 / 可执行性 24 / 风险标注 12 / 风格统一 12）也会强制 reject。

| 维度 | 满分 | 及格线 | 核心检查项 |
|------|------|--------|-----------|
| 完整性 | 20 | 16 | 5 大章节齐全 + 20 子模块齐全 |
| 一致性 | 20 | 16 | 术语统一 + 跨章节引用对齐 + 流程闭环 + 数值/ID 一致 |
| 可执行性 | 30 | 24 | 每条功能需求可写测试用例 + 验收标准 SMART + 异常分支覆盖 + 边界条件明确 |
| 风险标注 | 15 | 12 | 模糊词识别 + TBD 标注 + 异常分支 + 范围蔓延信号 |
| 风格统一 | 15 | 12 | 术语一致 + 句式一致 + 排版统一 |

### 6.2 多视角审查

| 视角 | 关注点 | 典型 issue |
|------|--------|-----------|
| 开发视角 | 功能可行性 / 边界条件 / 技术实现路径 | "PRD4 的 ER 图缺少软删除字段" |
| 测试视角 | 可测性 / 异常处理 / 边界用例 | "PRD3 的审批流缺少驳回分支的测试场景" |
| 运营视角 | 业务流程闭环 / 用户场景契合 / 价值主张落地 | "PRD1 的价值主张与 PRD2 的功能清单不匹配" |

3 视角 issue 合并后附在 qa_report.md 的"具体段落 + 修改建议"部分，主 Agent 据此决策派哪个 Agent 修订。

## 7. 人类介入

### 7.1 3 个介入点

| 介入点 | 触发时机 | Human 动作 | 设计意图 |
|--------|---------|-----------|---------|
| **needs_clarify** | 阶段 1-2，① 发现 MRD 信息不完整 | 在 open_questions.md 补全或回复邮件 | 前置拦截——避免基于错误输入跑完全流程 |
| **checkpoint_request** | 阶段 8-9，PRD 终稿前 [TBD] 或模糊词超阈值 | 读 PRD 终稿 → confirm / reject + feedback | 终审把关——防止"形式上通过但实质上有空洞"的 PRD 流出 |
| **error_alert** | 任意阶段，子 Agent 连续失败 ≥ 3 轮或 LLM 熔断 | 决定 rescue / abandon / 调向 | 异常兜底——把不可自动恢复的决策交给人类 |

### 7.2 自动触发规则

| 信号 | 阈值 | 触发 |
|------|------|------|
| ① breakdown 中推断标注出现次数 | ≥ 3 | needs_clarify |
| open_questions.md 条目数 | ≥ 5 | needs_clarify |
| PRD 中 [TBD] 标记 | > 3 | checkpoint_request |
| PRD 中模糊词（"可能/大概/也许"） | ≥ 5 处 | checkpoint_request |
| 同一 Agent 累计 reject | ≥ 3 轮 | error_alert |
| ③ 质检总分连续 | < 80 达 3 轮 | error_alert |
| LLM 调用 L1+L2 都失败 | — | error_alert |

### 7.3 不介入范围

人类只在上述 3 个介入点参与决策。以下事项完全由 Agent 自主完成：工作区初始化与子 Agent 选择排序、章节内部结构调整与验收标准措辞优化、模板复用与状态机内部逻辑。

## 附录 A. MRD 模板（5 大模块）

```
1 市场分析
  1.1 行业概况（市场规模 / 发展阶段 / PEST）
  1.2 市场问题与机会（核心痛点 / 机会点）
2 用户分析
  2.1 用户画像（企业属性 / 角色属性 / 行为特征 / 目标与痛点）
  2.2 场景分析（典型场景 / 任务流程 / 痛点）
3 竞争分析（直接竞品 / 差异化优势）
4 产品规划
  4.1 产品定位（产品名 / 一句话定义 / 价值主张）
  4.2 功能规划（功能模块清单 / 优先级 / 关联关系）
  4.3 非功能需求（性能 / 安全 / 可扩展性 / 合规 / 部署）
  4.4 实施路线（里程碑 / 风险评估）
```
