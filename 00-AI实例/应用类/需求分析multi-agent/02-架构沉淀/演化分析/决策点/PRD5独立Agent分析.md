# PRD5 页面规格单独成 Agent 分析

> 立场：基于上一轮"v2 = 1 主 + 4 子"（② 产品组 + ②' 工程组），评估 PRD5 是否要从 ②' 中再拆出
> 结论先行：**是，建议拆为 1 主 + 5 子**，PRD5 独立成 ④ 页面规格 Agent

---

## 一、为什么 PRD5 特别"重"——3 个独立证据

### 证据 1：单章节 token 占比是平均值的 2.5 倍

| 章节 | 典型产出 token | 工程组内部占比 |
|------|------------|------------|
| PRD3 流程设计 | 6,000 | 25% |
| PRD4 数据流建模 | 5,000 | 21% |
| **PRD5 页面规格** | **13,000** | **54%** |

**关键观察**：PRD5 单独一章就占工程组 54% 的输出量，**比 PRD3 + PRD4 合计还多**。

**为什么 PRD5 这么大**（B 端产品真实场景）：
- 每个页面要有：布局、组件、字段、状态（空/加载/错误/成功）、权限、交互
- 一个中型 B 端产品 PRD 通常有 30-80 个页面
- 每页面 200-400 字描述 = 6,000-32,000 字
- 还要附页面流程图（页面间跳转）

### 证据 2：Soul 偏好与 PRD3/4 显著不同

| 维度 | PRD3 流程 | PRD4 数据 | **PRD5 页面** |
|------|---------|---------|---------------|
| 决策偏好 | "流程逻辑严密、异常分支穷举" | "数据模型严谨、流转规则完整" | **"对设计师友好、视觉可还原、组件可复用"** |
| 技能体系 | 流程图 / Mermaid / 异常分支设计 | ER 图 / 字典设计 / 存储选型 | **UI 规范 / 组件库 / 状态机 / 交互模式** |
| 记忆数据 | 流程模式库（审批流、状态机等） | 数据模型库（业务实体关系） | **页面模式库（CRUD 表单/列表/详情/统计）** |
| 输出形态 | Mermaid 流程图 + 文字 | 表格 + Schema | **ASCII 线框图 + 字段表 + 状态说明** |
| 服务对象 | 开发（后端） | 开发（后端 + DBA） | **开发（前端）+ 设计师** |

**三维都不同** → 符合课程三维隔离判断法 → 独立成 Agent 成立。

### 证据 3：服务对象不同导致验收方不同

```
PRD3 流程 → 验收方 = 后端开发（关心业务逻辑对不对）
PRD4 数据 → 验收方 = 后端 + DBA（关心表结构、索引、约束）
PRD5 页面 → 验收方 = 前端开发 + UI 设计师（关心布局、交互、视觉）
```

②'（工程组）目前的 Soul 是"对开发友好、可执行"——这 3 章节对"开发"的含义不同（后端 vs 前端），**单一 Soul 必然偏科**。

## 二、拆出 PRD5 的额外收益

### 收益 1：把"页面级 GT"独立沉淀

**现状**：v2 设计中 GT 样本是"完整 PRD 全文"，50 条就占 100 万字。

**改进**：
- **产品级 GT**（30 条）：价值主张 / 用户画像 / 功能拆解 → 给 ② 产品组
- **流程级 GT**（20 条）：流程图 / 异常分支 / 状态机 → 给 ②'' 流程组
- **数据级 GT**（20 条）：ER 图 / 表结构 / 字段定义 → 给 ②''' 数据组
- **页面级 GT**（50 条）：页面模板 / 组件库 / 交互模式 → 给 ④ 页面规格组

**关键**：页面级 GT 是 4 类中最容易积累的（前端组件库有大量现成规范可参考），单独建库 ROI 最高。

### 收益 2：解耦"前端 ↔ 后端"开发节奏

```
当前（②' 工程组串行写）：
  PRD3 → PRD4 → PRD5  =  12,000 字上下文
  写 PRD5 时，前端和后端必须等同一份产出

拆分后（②'' 流程/数据 + ④ 页面 并行）：
  Manager 派 ②''（写 PRD3+4）和 ④（写 PRD5）并发
  各自上下文 < 1.5 万字
  整体时间 -40%（节省 PRD5 的串行等待）
```

### 收益 3：让"页面级 SOP"独立演进

PRD5 写作的痛点（业界经验）：
- 早期项目：1 个产品 + 1 个设计师，PRD5 写 50 页都嫌不够细
- 成熟项目：组件库稳定，PRD5 可以模板化（"参考 design system v3，列出差异点"）

④ 独立后，可以：
- 沉淀"页面模板库"（CRUD 模板 / 表单模板 / 列表模板 / 统计模板）
- 每个模板写一次，后续项目复用
- 模板覆盖率从 0 → 80% 后，PRD5 写作时间可从 4 小时降到 1 小时

### 5 个子 Agent 的清晰分工

| 角色 | 负责章节 | 上下文可控 | Soul 偏好 | 服务对象 |
|------|---------|----------|---------|---------|
| ① MRD 结构化 | 拆解 | 8K | 拆得细、问得全 | 下游所有 |
| ② 产品组 | PRD1+2 | 15K | 用户友好、价值清晰 | 业务方 / PM |
| ②'' 流程组 | PRD3 | 8K | 严谨穷举、异常分支 | 后端开发 |
| ②''' 数据组 | PRD4 | 7K | 模型严谨、约束完整 | 后端 + DBA |
| ④ 页面组 | PRD5 | 15K | 视觉可还原、组件可复用 | 前端 + 设计师 |
| ③ 质检 | 全文 | 25K | 挑剔质疑、找漏洞 | 验收 |

### 关键时序（含并行）

```
T0: Manager 读 MRD
T1: 派 ① → breakdown
T2: 选 GT 样本
T3: 派 ② 产品组 → PRD1+2 + handoff
T4: Manager 验收 PRD1+2
T5: 并发派发：
    - ②'' 流程组 → PRD3
    - ②''' 数据组 → PRD4
    - ④ 页面组 → PRD5（接收 PRD1+2 的功能 ID 清单）
T6: Manager 收集 PRD3+4+5，验收
T7: 派 ③ 质检 → qa_report
T8: Manager 决策（达标/修订/熔断）
T9: Human 终审 → 归档
```

**时间收益**：相比 v2 串行 ②'（PRD3→4→5），v3 并发（②'' 流程 + ②''' 数据 + ④ 页面）→ 整体时间 -40%。

## 四、角色数"5 个"会不会违反课程 BP-2？

### 课程 BP-2 原文（v1 文档中）
> "BP-2：先跑单 Agent，有明确收益再扩"
> "工程数据显示，有效 Agent 数量的天花板大约是 2-3 个，超过之后协调开销会超过并行收益。"

### 拆解分析

| 顾虑 | 实际情况 | 判定 |
|------|---------|------|
| 协调成本上升 | 5 个子 Agent + 1 个 Manager = 6 节点 | ⚠️ 接近上限 |
| 角色膨胀 | 每个角色都有"token 临界 + Soul 漂移"双重证据 | ✅ 必要拆分 |
| 误差 17 倍放大 | 仅适用于"无层级 + 自由互调"（L25 AP-4），**不适用** v3（中心协调 + Manager 验收） | ✅ 已规避 |

### 课程真正的反对场景

> "AP-4：无层级的 Agent 堆，误差 17 倍放大"——这是反对"无中心协调的自由 Agent 群"

v3 不是"无层级 Agent 堆"，而是：
- **严格中心协调**：所有任务经 Manager
- **清晰职责边界**：5 个子 Agent 各管一段，永不交叉
- **强制验收机制**：每个子 Agent 都有 Manager 验收 + ③ 质检
- **单维度多角色**：不是"5 个不同领域"，而是"PRD 写作流程的 5 个连续工序"

### 结论

**v3（1 主 + 5 子）不违反 BP-2 精神**。课程反对的是"为了多而多"的角色膨胀，不是"基于证据的合理拆分"。

但需要：
- **守住"先 v2 再 v3"**：先跑通 v2（1+4）验证收益，再扩到 v3（1+5）
- **守住"GT 池就绪"**：④ 页面组启动前必须有 50 条页面级 GT，否则 ④ 写不出高质量 PRD5
- **守住"修复决策权归 Manager"**：5 个子 Agent 都不自修，修改权统一归 Manager 派

## 五、风险与缓解

| 风险 | 来源 | 缓解 |
|------|------|------|
| 5 个 Agent 协调变复杂 | 角色数 +1 | Manager SOP 化所有决策（"qa_report 命中 X 模式 → 自动派修订"） |
| ②'' 流程与 ②''' 数据衔接断裂 | 新拆 | 通过 `shared/prd/handoff_34.md` 强制 ②'' 写完后再派 ②'''（或允许 ②''' 在 ②'' outline 阶段就启动） |
| ④ 页面规格与 ② 产品组的功能 ID 对不齐 | 跨 Agent 引用 | ② 必须先产出 `shared/prd/feature_id_list.md` 作为 ④ 的输入契约 |
| PRD5 质量不稳定 | ④ 单独承担 | ④ 必须配 page_template_lib（5+ 套模板：CRUD/表单/列表/统计/详情） |
| 5 个 Agent 上下文隔离变难 | 物理隔离 | Manager 强制每个 Agent 启动时只加载 `shared/prd/handoff_xx.md`，不读其他 Agent 写过的中间过程 |

## 六、4 层框架概要：④ 页面规格 Agent

### Role Charter

| 职责 | 不负责 |
|------|--------|
| PRD5 页面规格（页面结构、组件、字段、状态、交互、权限） | PRD1+2（产品组）/ PRD3（流程组）/ PRD4（数据组） |
| 页面级 GT 模板沉淀 | 整体 PRD 验收（③） |
| 组件库适配建议 | 业务规则定义 |

### Soul

> "视觉可还原、组件可复用、状态完整、权限清晰"

**NEVER 清单**：
- 绝不写价值主张 / 用户画像（→ ②）
- 绝不写后端流程 / 数据模型（→ ②'' 流程 / ②''' 数据）
- 绝不省略页面异常状态（空/加载/错误/权限不足）
- 绝不用模糊词"大概/可能/也许"描述交互
- 绝不复用其他 Agent 的写过的中间过程作为输入

### Memory

```
workspace/page_spec/
├── page_templates/                # 页面模板库
│   ├── crud_list.md
│   ├── crud_form.md
│   ├── detail_view.md
│   ├── dashboard.md
│   ├── wizard.md
│   └── ...
├── component_patterns.md          # 组件使用模式
├── state_machine_patterns.md      # 状态机模式
└── history_feedback.md            # 历史 PRD5 反馈
```

### Skills

| Skill | 内容 |
|-------|------|
| `prd5_writer_sop` | PRD5 写作 5 步标准（页面清单 → 字段表 → 状态机 → 交互 → 权限） |
| `page_template_loader` | 根据功能类型加载对应模板 |
