# 单 PRD 撰写 Agent 是否够用？—— 上下文工程的硬约束分析

> 关键问题：一篇完整 PRD 几万字，环节多（5 大章节 + 20 子模块 + GT 样本 + 上游字段 + 修订历史），单 Agent 真能扛？

---

## 一、先看数据：单 Agent 写 1 篇完整 PRD 的上下文估算

| 来源 | token 数（估算） | 占比 |
|------|---------------|------|
| ① 上游结构化结果（9 个 MRD 字段 + 47 条需求清单 + 开放问题） | 8,000 | 12% |
| ② GT 样本（2 份历史优质 PRD 全文） | 20,000 | 30% |
| ③ 5 个章节写作 Skill（规则+模板） | 6,000 | 9% |
| ④ 修订历史（qa_report + 上一轮 PRD） | 15,000 | 22% |
| ⑤ 输出 buffer（5 章节 Markdown 全文 3 万字） | 18,000 | 27% |
| **合计** | **67,000** | **100%** |
| 模型上限（DeepSeek-V3.2 / Qwen 长上下文） | 128,000 | — |

**结论 1**：**单 Agent 写 1 篇完整 PRD 在 token 上能塞下，但已经用了 52% 的上下文窗口**——留给"思考 / 推理 / 修订"的空间已经很少。

**结论 2**：再写 1 篇（历史 PRD 进 GT 后，第 2 篇要保留第 1 篇作为对照）→ 直接爆。

---

## 二、问题不止 token：还有 3 个更深的硬伤

### 硬伤 1：长上下文的"注意力稀释"（Context Rot）

课程 L23 反复强调：
> "上下文越长，模型对早期细节的注意力就越稀释——Context Rot 是真实存在的，研究显示这是 n² 级别的衰减。"

**具体表现**：
- ② 写到 PRD4 时，已经"忘了"PRD1.5 核心价值主张里强调的关键卖点
- 跨章节引用（如 PRD3.2 引用 PRD2.1 的功能 ID）容易写错
- 修订阶段（看 qa_report 改 PRD），qa_report 里说"PRD2.1 第 3 段有问题"，② 读完 6 万字上下文后，**注意力已经分散到所有段落**，无法精准定位

**Chatflow 的应对**：把 5 章节拆成 5 个独立 LLM 节点 + 5 个 Code 拆分节点。每个 LLM 节点的输入只 1-4 个上游变量，**单节点上下文不超过 1.5 万字**。

### 硬伤 2：角色决策偏好漂移

② 的 Soul 写的是"结构清晰、可读性强、对下游友好"。这个 Soul 在写 PRD1（产品概述）时合适，但写到 PRD3（流程设计）需要的是"流程逻辑严密、异常分支穷举"，**Soul 偏好与章节要求不一致**。

**具体表现**：
- 写 PRD1 时偏好"概述性描述"（OK）
- 写 PRD3 时应该"穷举异常分支"（与 Soul 偏好冲突）
- 写 PRD5 时应该"严谨到像素级"（与 Soul 偏好再次冲突）

**结论**：单 Agent 的 Soul 是"平均偏好"，无法适应每个章节的"峰值偏好"。

### 硬伤 3：质量上限——单 Agent 缺乏"自我质疑"

L23 BP-1 数据：
> "同一任务，有独立验收的准确率是 70%，没有的只有 10%——相差 7 倍。"

这个 7 倍的差距，本质是**独立视角**。单 Agent 自评时，会被自己的"完成度幻觉"骗过去：
- "我写了 3 万字 → 我做了很多 → 质量应该 OK"
- 看不到自己省略的边界 case
- 看不到跨章节的术语不一致

## 三、那 1 主 + 3 子够不够？需要看"篇均 PRD 体量"

| 场景 | PRD 体量 | 单 ② 是否够 |
|------|---------|------------|
| 简单工具（内部 1 个功能） | 5,000 字 | ✅ 够 |
| 中型 SaaS 模块 | 20,000-30,000 字 | ⚠️ 临界，勉强 |
| 大型产品（一篇覆盖 8 个子产品） | 80,000-100,000 字 | ❌ 不够 |
| 多产品组合 | 200,000+ 字 | ❌ 严重不够 |

**当前 v1 框架设计的目标场景**：B 端产品需求文档，**通常在 20,000-50,000 字之间**（5 大章节 + 20 子模块 + 验收标准）→ **单 ② 写 1 篇临界够用，但**：

- **没有并发收益**（5 章节串行 1 个 Agent）
- **修订轮次会累积**（qa_report 命中后重写，token 翻倍）
- **未来扩展困难**（产品线多了，GT 库必然膨胀）

---

## 四、3 种解法对比

### 解法 1：保持单 ② 写完，但加重 Agent 自身能力

**思路**：② 用最强模型 + 显式分段 + 强制每章节先列大纲再展开。

```
② 启动
  ↓
读 outline 模板
  ↓
写 5 章节 outline（占 token 2,000）
  ↓
逐章节展开（每次只把"当前章节模板 + 上游变量"加载到上下文）
  ↓
每章节写完 → 立即压缩成 500 字摘要 → 写 shared/prd/section_X_summary.md
  ↓
下一章节时只读上游变量 + 当前章节模板 + 上一章节摘要
```

| 优点 | 缺点 |
|------|------|
| 不增加角色 | **本质是"自欺欺人"**——压缩就是丢信息 |
| 简单 | 跨章节一致性靠"摘要传递" → 摘要越短越丢细节 |
| 实施快 | Soul 偏好漂移无解 |
| | 修订时仍要读全量上下文 |

**判定**：⛔ **不推荐**。与课程 L23 关键设计 ①"精准传递"理念相悖。

### 解法 2：② 内部"子会话"机制（仍归 ② 灵魂管辖）

**思路**：② 不是单次 LLM 调用，而是**一个长会话 + 5 个子会话**。子会话独立上下文，写完后把产物 commit 到 ② 的"长期记忆"（文件系统）。

```
② 主会话（持久化）
  ├─ 子会话 2A：写 PRD1（独立 8000 token 上下文）
  ├─ 子会话 2B：写 PRD2（独立 10000 token）
  ├─ 子会话 2C：写 PRD3（独立 12000 token）
  ├─ 子会话 2D：写 PRD4（独立 10000 token）
  └─ 子会话 2E：写 PRD5（独立 8000 token）
  ↓
所有子会话 commit 到 shared/prd/section_X.md
  ↓
② 主会话负责"协调"（不是写），最后做一次"全章节串联检查"
```

| 优点 | 缺点 |
|------|------|
| 单子会话上下文可控（< 1.5 万） | **不是真 Agent 拆分**，本质是单 Agent 内部"分段处理" |
| 主 Soul 一致 | 跨子会话的"决策偏好"仍漂移 |
| 不增加角色 | 实施复杂（需要会话管理机制） |
| 保留 1+3 架构 | 子会话间的"信息传递"靠文件系统，**失去 LLM 原生注意力** |

**判定**：⛔ **不建议作为长期方案**。是"工程技巧"，但 Soul 漂移和跨会话注意力问题没根治。

### 解法 3（推荐）：把 ② 拆为 2 个真子 Agent——"PRD 概述 + 功能组" + "流程/数据/UI 组"

**思路**：从 v1 的"1 主 + 3 子"扩为"1 主 + 4 子"。**新增的不是 GT 角色，而是把 ② 拆为两个分工更明确的子 Agent**。

```
1 主 + 4 子（v1 升级版）：
  Manager
  ├─ ① MRD 结构化
  ├─ ② PRD 撰写 - 产品组（PRD1 产品概述 + PRD2 功能规格）
  ├─ ②' PRD 撰写 - 工程组（PRD3 流程 + PRD4 数据 + PRD5 页面）
  └─ ③ PRD 质检
```

**为什么这次可以拆**（与方向 A 不同）：

| 维度 | ② 产品组 | ②' 工程组 |
|------|---------|----------|
| 记忆数据 | 价值主张、市场分析、用户画像 | 流程建模、数据字典、UI 规范 |
| 技能体系 | 文档写作 / 价值提炼 / 功能拆解 | 流程图 / Mermaid / 数据建模 / 页面原型 |
| 决策偏好 | "对用户友好、价值清晰" | "对开发友好、可执行、严谨穷举" |
| 协作接口 | 交付：PRD1+2 + 功能 ID 清单 | 接收：上游 PRD1+2；交付：PRD3+4+5 |

**三维都显著差异** → **符合课程三维隔离判断法**，新增角色成立。

**关键设计**：
- ② 和 ②' 之间通过 `shared/prd/handoff.md` 交接（**不是邮件，是文件**）
- Manager 在派 ②' 之前，必须先验收 ② 的产物
- ②' 启动时只能读 PRD1+2，不能"看到"② 写 PRD1+2 时的过程

**为什么这次不违反 BP-2"2-3 个子 Agent"**：
- BP-2 是建议值，不是硬约束
- 4 个子 Agent 是经过"单 Agent 不够用"的实际证据后扩的，符合"先跑通再有理由加"原则
- 每个新角色都有"明确的拆分理由"（Soul 漂移 + token 临界）

| 优点 | 缺点 |
|------|------|
| 解决 ② 过载 | 角色数 +1（5 个） |
| 每个子 Agent 上下文可控（< 2 万） | ② 和 ②' 之间要约定 handoff 协议 |
| 决策偏好与章节要求对齐 | 风格统一靠 ③ 强制约束 |
| 真实并发（② 完成 PRD1+2 后 ②' 启动） | 实施复杂度 +1 |
| 未来扩展容易（再加 ②'' 写"运营/数据后台"） | — |

## 五、决策树：到底要不要拆？

```
Q1：单篇 PRD 写完后，② 的上下文是否 > 60% 模型上限？
  ├─ 否 → 单 ② 够用
  └─ 是 → Q2

Q2：跨章节引用是否频繁（> 10 处）？
  ├─ 否 → 解法 2（子会话机制）
  └─ 是 → Q3

Q3：Soul 漂移是否已经在产出中体现（如 PRD3 流程不严谨、PRD5 页面描述模糊）？
  ├─ 否 → 解法 2
  └─ 是 → 解法 3（拆为 2 个真子 Agent）
```

**当前 v1 目标场景的判定**：
- 单篇 PRD 25,000-50,000 字 → ② 上下文约占 50-60% → 临界
- 跨章节引用频繁（PRD3 引用 PRD2.1、PRD5 引用 PRD3.3）→ Q2 = 是
- Soul 漂移：PRD1 偏"用户友好"、PRD3 应"严谨穷举" → Q3 = 是
- **结论：解法 3 拆为 2 个子 Agent**

## 六、最终建议：v1 升级为 v2（1 主 + 4 子）

### v2 架构

```
                    ┌─────────────────────┐
                    │   Human（甲方）      │
                    │   3 个介入点         │
                    └──────────┬──────────┘
                               ▼
        ┌────────────────────────────────────────┐
        │   Manager（加重：GT 选择 + 修复决策）   │
        └──────────┬─────────────┬───────────────┘
                   │             │             │
       ┌───────────▼──────┐ ┌────▼──────────┐ ┌────────────────┐ ┌──────────────────────┐
       │ ① MRD 结构化     │ │ ② 产品组     │ │ ②' 工程组      │ │ ③ PRD 质检           │
       │   拆解 / 澄清     │ │  PRD1 + PRD2 │ │  PRD3+4+5      │ │  多视角出报告        │
       └──────────────────┘ └──────┬───────┘ └──────▲─────────┘ └──────────────────────┘
                                   │                │
                                   └──── handoff ──┘
```

### 关键时序

```
T0: Manager 读 MRD
T1: 派 ① → 产出 breakdown
T2: Manager 验收 + 选 GT 样本
T3: 派 ② 产品组 → 产出 PRD1+2 + handoff
T4: Manager 验收 PRD1+2
T5: 派 ②' 工程组（注入 handoff） → 产出 PRD3+4+5
T6: Manager 验收 PRD3+4+5
T7: 派 ③ 质检 → 产出 qa_report
T8: Manager 决策（达标 → 通知人 / 不达标 → 派修订）
T9: Human 终审 → 归档
```

### 5 角色定义（四层框架概要）

| 角色 | Soul 偏好 | 永不做的（NEVER） | 记忆沉淀 |
|------|---------|------------------|---------|
| **Manager** | 全局视野 / 严验收 | 不写 PRD / 不替人决策 | SOP 迭代 / 团队名册 |
| **① MRD 结构化** | 拆得细 / 问得全 | 不写 PRD / 不改 MRD 原意 | 拆解方法论 |
| **② 产品组** | 用户友好 / 价值清晰 | 不写流程图 / 不定页面规格 | PRD1+2 模板、案例 |
| **②' 工程组** | 严谨穷举 / 可执行 | 不写价值主张 / 不定用户画像 | 流程/数据/UI 模板、案例 |
| **③ PRD 质检** | 挑剔质疑 / 找漏洞 | 不改 PRD / 不替写者决策 | 缺陷模式库 |

## 七、给你的 3 个关键判断问题

1. **你的 PRD 实际场景体量**大概在哪个范围？
   - < 1 万字（轻量）→ 单 ② 够
   - 1-3 万字（中型 B 端）→ 临界
   - 3 万+（大型 B 端 / 复杂业务）→ 必须拆

2. **是否接受 v2 架构（1 主 + 4 子）**？还是坚持 v1 的 1+3 走"工程技巧路线"（子会话 / 显式分段）？

3. **如果拆，② 和 ②' 的协作协议**用什么？建议用 `shared/prd/handoff.md` 文件交接（不是邮件），但也可以用"PRD 写入即触发"的轻量机制。
