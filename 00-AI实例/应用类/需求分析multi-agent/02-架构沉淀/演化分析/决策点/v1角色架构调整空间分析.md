# v1 角色架构调整空间分析（基于 Chatflow 节点对位）

> 问题：v1 的"1 主 + 3 子（持久化）"是否有调整空间？
> 立场：不否定 v1 的 Orchestrator 范式，但用 Chatflow 的 13 个执行节点做"压力测试"，看 3 个子 Agent 的负载是否合理

---

## 一、v1 角色 vs Chatflow 节点对位

先把 Chatflow 15 个节点映射到 v1 的 4 个角色：

| v1 角色 | 承担 Chatflow 节点 | 数量 | 实际工作内容 |
|---------|------------------|------|------------|
| **Manager（主 Agent）** | 100001 开始 / 167999 校验 / 900001 结束（部分职责） | 1.5 | 调度 / 路由 / 终审 |
| **① MRD 结构化** | 156468 LLM + 144389 Code | 2 | MRD 拆 5 大模块 / 正则拆 9 字段 |
| **② PRD 撰写** | 192934 + 1896132 + 177580 + 1802591 + 1119694（5 个 LLM）+ 1609399 + 1328344 + 1518710 + 1106122 + 1400836（5 个 Code） | **10** | 写 5 大章节 + 5 次 XML 拆分 |
| **③ PRD 质检** | （无对应，被 167999 吸收了校验职责） | 0 | 被 Chatflow 的"校验 LLM"代替 |
| **未对位** | 167999 整体校验 LLM | 1 | 校验 + 修复 5 章节 |

**关键发现**：

| 问题 | 现状 | 严重度 |
|------|------|--------|
| ② 承担 10 个节点的工作量 | 严重过载 | 🔴 高 |
| ③ 完全没有对应节点 | 角色空转（被 Chatflow 合并到校验节点） | 🔴 高 |
| 校验节点既检又改 | 课程 L23 BP-1 违反 | 🔴 高 |
| MRD 预处理与 ① 的边界模糊 | 156468 LLM 输出 XML，144389 Code 拆字段——两件事都是 ① 该做的工作 | 🟡 中 |
| Code 节点是 LLM 输出的工程补丁 | 6 个 Code 节点，本质是弥补"LLM 输出格式不可控" | 🟡 中 |

## 二、3 种调整方向

### 方向 A：保持 1 主 + 3 子，但内部拆分

**思路**：③ 实质化（独立）、② 拆为 2 个子 Agent、Manager 加重调度职责。

```
1 主 + 5 子：
  Manager（加重：GT 选择 / 章节调度 / 异常决策）
  ├─ ① MRD 结构化（不变，吸收 156468 + 144389）
  ├─ ② PRD 撰写 - 产品/功能组（吸收 192934 + 1896132 + 1609399 + 1328344）
  ├─ ②' PRD 撰写 - 流程/数据/UI 组（吸收 177580 + 1802591 + 1119694 + 1518710 + 1106122 + 1400836）
  └─ ③ PRD 质检（独立：吸收 167999 中"校验"部分）
```

| 优点 | 缺点 |
|------|------|
| 解决 ② 过载 | 角色数 5 个，超过课程 BP-2 推荐"2-3 个"上限 |
| ③ 实质化 | ② 和 ②' 之间需要新协议（章节交接、风格统一） |
| Manager 调度颗粒度更细 | Manager 的 SOP 复杂度上升 |

**违反课程**："团队越大协调成本越高"（L25 反模式四，误差 17 倍放大）；课程 BP-2"先少后多"。

---

### 方向 B（推荐）：保持 1 主 + 3 子，但重新切分职责

**思路**：把 Chatflow 的 15 个节点"折叠"到 4 个角色，**让每个角色的工作性质保持单一决策偏好**。

```
1 主 + 3 子（重新切分）：
  Manager（①+ ④ 入口 + ⑤ 终审）
  ├─ ① MRD 结构化（吸收 156468 + 144389，把 XML 拆字段内化为 Skill）
  ├─ ② PRD 撰写（吸收 5 个 LLM 章节 + 5 个 Code 拆分，把"分章节写"作为内部分批任务）
  └─ ③ PRD 质检（独立：吸收 167999 中"多视角校验"部分，**修复决策权交回 Manager**）
```

#### 关键改造点

| 改造 | 做法 | 依据 |
|------|------|------|
| ② 内部"分章节写作" | ② 启动后由 Manager 派 5 个内部 task（PRD1-5），② 自己排队写（不再 spawn 多个子 Agent） | 章节共享"PRD 撰写"灵魂，强行拆角色会破坏 Soul 一致性 |
| Code 节点 | 改为 ② 内部 Skill（Python 解析 Markdown 标题） | 消除 XML 中间态 |
| ③ 角色实质化 | ③ 接收 PRD 终稿，输出 qa_report.md，**不修复** | 课程 L23 BP-1：执行者不能自我评审 |
| 修复回路 | Manager 读 qa_report → 决策 → 派 ② 修订（带缺陷清单） | 课程 L23 AP-2：避免全链放大 |
| 校验 LLM 167999 | 一分为二：③ 做多视角出报告，Manager 决策修复范围 | 解决"改坏其他内容" |

#### 三维隔离判断法复核

| 维度 | ① MRD 结构化 | ② PRD 撰写 | ③ PRD 质检 | 结论 |
|------|------------|-----------|-----------|------|
| 记忆数据 | MRD 拆解方法论、需求 ID 规范 | PRD 模板库、GT 样本、章节套路 | 质检 checklist、缺陷模式库 | ✅ 完全不同 |
| 技能体系 | 需求拆解 / 用例分析 / 业务建模 | 文档写作 / 用户故事 / 流程图 / 原型说明 | 多视角审查 / 风险评估 | ✅ 完全不同 |
| 决策偏好 | "拆得细、问得全、不放过模糊点" | "结构清晰、可读性强、对下游友好" | "挑剔、质疑、找漏洞" | ✅ 完全不同 |

**三维都通过** → 仍可保持 1+3，**不需要增加角色**。

| 优点 | 缺点 |
|------|------|
| 不增加协调成本 | ② 内部需要"分章节工作"机制 |
| ③ 真正发挥作用 | ② 单 Agent 同时处理 5 章节需要强 SOP 约束 |
| 修复回路清晰 | 章节级并发需要 ② 自己实现（而非 Manager 并行派 3 个子 Agent） |

**优势**：
- 角色数 4 个，符合课程 BP-2 上限
- ③ 真正"挑刺"，独立视角不被 ② 污染
- 修复决策权归 Manager，避免"自检自修"的盲区

---

### 方向 C：退一步，回到 1 主 + 1 子

**思路**：砍掉 ③，把质检合到 ② 内部，Manager 自己做最终验收。

| 优点 | 缺点 |
|------|------|
| 极简 | 违反课程 BP-1"独立验收 70% vs 无验收 10%，7 倍差距" |
| 协调成本最低 | Galielo 数据不支持 |
| Manager 直接看稿 | 失去"找茬视角"，PRD 质量不可控 |

**结论：不推荐**，与课程核心数据冲突。

---

### 方向 D（备选）：升一档，1 主 + 4 子（增加"GT 匹配"角色）

**思路**：把 Chatflow 没做但课程 L35 强推的"GT 选择"独立成角色。

```
1 主 + 4 子：
  Manager
  ├─ ① MRD 结构化
  ├─ ② PRD 撰写
  ├─ ③ PRD 质检
  └─ ④ GT 匹配（新）：根据 MRD 关键词选 1-2 份历史 PRD 样本
```

| 优点 | 缺点 |
|------|------|
| GT 选择有专属记忆（哪类 MRD 匹配哪类样本） | 多一个角色 |
| ② 启动时直接拿到样本，不用自己选 | 协调成本 +1 |

**判定**：GT 选择逻辑不复杂（关键词 + 行业分类），可以并入 Manager 的 Skill，**不独立成角色**。但如果未来 GT 库到 100+ 条、需要学习排序，再独立。

## 三、推荐方案：方向 B（重新切分职责）

### 3.1 角色调整总览

| 角色 | 调整前 | 调整后 |
|------|--------|--------|
| **Manager** | 调度 + 验收 | 调度 + **GT 选择决策** + **修复决策** + 验收（加重） |
| **① MRD 结构化** | 拆 MRD | 拆 MRD（含 5 模块 XML 输出 → 9 字段 Markdown 表格） |
| **② PRD 撰写** | 写 PRD | 写 PRD（含 5 章节分批任务，由 Manager 派任务、② 自己排队执行） |
| **③ PRD 质检** | 形式化 | **实质化**：出 qa_report.md（多视角 + 100 分制评分） |

### 3.2 Manager 的 SOP 关键变化

```
阶段 0：初始化
  - 读 MRD
  - 初始化 shared/ 工作区
  - **新增**：选 GT 样本（关键词匹配）
  - 检查 MRD 完整性，需要时发 needs_clarify

阶段 1：派 ① MRD 结构化
  - spawn ①
  - 验收：breakdown/* 是否齐全
  - **新增**：要求 ① 输出从 XML 改为 Markdown 表格

阶段 2：派 ② PRD 撰写（分批）
  - 派 task 1：写 outline（5 章节大纲）
  - Manager 验收 outline（是否覆盖所有 subsection_xx 字段）
  - **章节级并发**：
    - 派 task 2A：写 PRD1（产品概述）+ PRD2（功能规格）
    - 派 task 2B：写 PRD3（流程设计）
    - 派 task 2C：写 PRD4（数据建模）+ PRD5（页面规格）
  - 注：② 是同一个 Agent 实例，由 Manager 派 3 个 task，② 内部按顺序执行
  - 每章节完成后，② 写 prd/section_X.md（不是单一 prd_draft.md）
  - **新增**：② 收到 GT 样本作为参考输入

阶段 3：派 ③ PRD 质检
  - spawn ③
  - ③ 读取所有 prd/section_X.md
  - 输出 qa_report.md（含 100 分制评分 + 缺陷清单）
  - **关键约束**：③ 只报告，不修改 PRD

阶段 4：Manager 验收 + 决策
  - 读 qa_report.md
  - 若总分 ≥ 80：
    - 通知 Human 终审
  - 若总分 < 80：
    - 合并 qa_report 中的缺陷
    - 派 ② 修订（task 4：带缺陷清单修订）
    - 修订后再派 ③ 复检
    - 连续 3 轮不达标 → error_alert

异常兜底：
  - 子 Agent 失败 ≥ 3 轮 → error_alert
  - LLM 调用失败 → 3 级降级（重试 → 换 V3.1 → 熔断）
```

### 3.3 ② 内部"分章节"机制

**关键问题**：② 怎么管理 5 个章节的内部任务？

**方案 ②-内部工作清单**（在 ② 的 workspace 里）：

```
workspace/prd_writer/
├── soul.md          # 决策偏好（"结构清晰、可读性强"）
├── agent.md         # 任务清单 + 章节模板
├── memory.md        # 历史 PRD 经验
├── skills/          # 5 个章节写作 SOP
│   ├── section_1.md
│   ├── section_2.md
│   ├── section_3.md
│   ├── section_4.md
│   └── section_5.md
└── inbox/           # 内部待办（Manager 派的任务进这里）
    ├── task_001_outline.md
    ├── task_002_section_1_2.md
    ├── task_003_section_3.md
    ├── task_004_section_4_5.md
    └── task_005_xxx.md
```

**机制**：
- Manager 不直接 spawn ② 的 5 次，而是 spawn ② 一次
- ② 启动后读 `inbox/`，按顺序处理
- 完成后把产物写到 `shared/prd/section_X.md`
- Manager 通过读 `shared/prd/` 知道进度

**优势**：
- ② 保持单一 Soul（"结构清晰、可读性强"），5 章节都遵循同一灵魂
- 章节间共享上下文（② 写 PRD1 时知道 PRD2 要写什么，更一致）
- 不破坏 1+3 角色架构

**代价**：
- ② 单 Agent 串行处理 5 章节，时间略长（vs 真正的并发子 Agent）
- ② 上下文会膨胀（5 章节都在同一个 session）—— 通过 5 个 Skill 文档 + 分批写文件缓解

## 五、推荐方案的"风险-缓解"对照

| 风险 | 来源 | 缓解 |
|------|------|------|
| ② 内部串行 5 章节耗时长 | 章节级并发收益损失 | outline 锁后允许 ② 内部并发（开 3 个 thread 同时写不同 section） |
| ② 上下文膨胀 | 5 章节在同一 session | Skill 文档按需加载（不一次性注入） + 每章节写完即总结压缩 |
| ② 自我风格漂移 | 5 章节共享上下文但缺乏独立 review | ③ 多视角审查 + 100 分制风格统一维度强制约束 |
| ③ 输出对 ② 改进价值有限 | qa_report 太抽象 | qa_report 必须带"具体段落 + 修改建议 + GT 对照" |
| Manager 决策负担过重 | 同时管 GT 选择 + 修复决策 | 决策 SOP 化（"qa_report 命中 X 模式 → 自动派修订"，不需临时判断） |

## 六、给用户的 3 个待确认问题

1. **方向 B 接受吗？** 即保持 1+3 角色数，但调整职责切分（② 内部消化 5 章节、③ 实质化、Manager 加重决策）。
2. **② 内部"分章节"用 inbox 机制吗？** 还是用其他方式（如每个章节独立 session、靠文件系统切分）？
3. **GT 角色是否独立？** 短期不独立（Manager 内化），但预留 ④ GT 匹配角色的接口（数据结构和职责边界先定义）。
