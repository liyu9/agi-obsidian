# 课程 v1 框架 × Chatflow 综合优化清单

> 立场：保留课程 v1 的"主 Agent + 3 子 Agent"骨架，吸收 Chatflow 的工程化优点
> 目标：让 v1 框架既具备 Orchestrator 范式的稳健性，又能落地为可投产的 PRD 团队
> 优先级：高（必修）→ 中（应做）→ 低（选做）

---

## 0. 现状对照

| 维度 | 课程 v1 | Chatflow 现状 | 差距 |
|------|--------|------------|------|
| 范式 | Orchestrator 动态派发 | Pipeline 静态编排 | v1 范式更优，保留 |
| 角色 | 1 主 + 3 子（持久化） | 6 LLM + 6 Code（一次性） | v1 角色更优，保留 |
| 任务切分 | 5 阶段（拆 → 写 → 审） | 5 章节串行 LLM 节点 | Chatflow 切得更细，借鉴 |
| 跨章节引用 | 显式参数注入 | 显式 ref_node 注入 | 两者一致，保留 v1 写法 |
| 共享工作区 | `shared/` + Owner 唯一 | 节点变量直传 | v1 更优，保留 |
| 邮箱协议 | 三态状态机 + 同步/轮询 | 无 | v1 更优，保留 |

## 一、高优先级（必须补的硬伤）

### 1.1 把 Chatflow 的 5 章节 Prompt 全部吸收为子 Agent Skills

**现状**：v1 只定义了 3 个子 Agent 的 Role Charter / Soul / Memory 框架，没有具体的"PRD 怎么写"内容骨架。

**完善点**：把 Chatflow 已验证的 5 章节 prompt 体系，写进 ② PRD 撰写 Agent 的 Skills 中。

| 章节 | 来源（Chatflow 节点） | 核心规则 | 落入位置 |
|------|-------------------|---------|---------|
| PRD1 产品概述 | 192934 | 4 维映射规则（市场/用户/产品/竞品 → PRD 要素）+ 工具类/社交类/电商类适配 | `skills/prd_writer/section_1_product_overview.md` |
| PRD2 功能规格 | 1896132 | 价值动作→功能关键词；功能 ID 规范 `F-DOMAIN_类型_序号`；P0~P3 优先级 | `skills/prd_writer/section_2_function_spec.md` |
| PRD3 流程设计 | 177580 | 场景→阶段；功能→行为；Mermaid 语法；必含审批/校验/数据更新 | `skills/prd_writer/section_3_flow_design.md` |
| PRD4 数据流建模 | 1802591 | 数据模型 / 流转规则 / 存储安全 | `skills/prd_writer/section_4_data_model.md` |
| PRD5 页面规格 | 1119694 | 页面结构 / 交互规范 | `skills/prd_writer/section_5_ui_spec.md` |

**为什么高优**：Chatflow 已经把这套规则跑通过，吸收到 v1 框架里，子 Agent 一启动就有"PRD 怎么写"的完整 SOP，**避免"框架完美但 Agent 不会干活"**。

**执行**：在 v1 文档第 10 节"后续步骤"中，把"输出每个子 Agent 的 prompt 模板"具体化为"吸收 Chatflow 已验证的 5 章节 prompt"。

---

### 1.2 拆分"校验 + 修复"，避免"改坏其他内容"

**现状**：Chatflow 167999 节点把"逻辑校验 / 风格统一 / 多角色审查 / 修复"塞在同一个 LLM 调用里，且 prompt 中"避免改动其他内容"这种约束**对 LLM 来说几乎无效**（课程 L23 AP-2：全链放大）。

**完善点**：把 Chatflow 的"校验 LLM"在 v1 框架里**拆为两阶段**，对应课程 L23 BP-1 "独立验收 Agent"：

```
阶段 A：质检 Agent（③ PRD 质检）
  - 职责：出 qa_report.md
  - 输出：缺陷清单（完整性 / 一致性 / 可执行性 / 风险）
  - 不修改 PRD

阶段 B：管理 Agent 决策
  - 读 qa_report.md
  - 决策：派 ② 修订 / 通知人 / 归档
  - 决定改哪、不改哪
```

**执行**：在 ② PRD 撰写 Agent 收到 reject 后，由 Manager 而不是 ③ 直接驱动修复。

**为什么高优**：这是 Chatflow 当前最严重的设计债务，必须用课程框架的结构性约束来根治。

---

### 1.3 补上"3 个人类介入点"

**现状**：Chatflow 全程无 Human 介入，4 类问题无人兜底：

| 场景 | 现状 | 应有 |
|------|------|------|
| MRD 缺失关键信息 | 强行编造（"「注：推断依据」"） | needs_clarify 邮件 |
| 关键设计抉择 | 由 LLM 自主决定 | checkpoint_request |
| 高风险条款出现 | 无识别机制 | checkpoint_request |
| 子 Agent 异常 | 模型降级静默重试 | error_alert 邮件 |

**完善点**：v1 框架的 3 个介入点全部生效，并配上 Chatflow 已有的"模糊词识别规则"做自动触发。

**触发信号定义**（吸收 Chatflow 经验）：

| 介入点 | 触发信号 | 处理 |
|--------|---------|------|
| needs_clarify | MRD 含 `[推断依据]` 标注 ≥ 3 处；subsection_1_1/1_2/2_1/2_2 任一为空 | Manager 自动发邮件 |
| checkpoint_request | PRD 中 `[TBD]` > 阈值；存在"可能/大概/也许"模糊词 ≥ 5 处；非功能需求出现 0 容错场景 | Manager 自动发邮件 |
| error_alert | 子 Agent 3 轮 reject 不收敛；LLM 调用超时；JSON 解析失败 | Manager 自动发邮件 |

**为什么高优**：课程 L27 反复强调"3 个介入点是底线"，缺一个整套都跑不稳。

## 二、中优先级（架构完善的点）

### 2.1 引入 GT（Ground Truth）样本库

**现状**：Chatflow 通过"4 维映射规则"间接代替 GT，v1 框架在 9 节"待确认问题"中也提到 GT 但未细化。

**完善点**：建立 50 条历史优质 PRD 样本库，作为 ② PRD 撰写 Agent 的参考输入。

**GT 落地**：

```
workspace/shared/gt_samples/
├── README.md                # GT 使用规则
├── index.json               # 50 条样本的元信息（行业 / 复杂度 / 章节数）
├── saas/001_客户分级.md     # 一份完整 PRD 样本
├── saas/002_数据分析.md
├── ...
└── tool/001_内部工具.md
```

**注入方式**：Manager 派 ② 时把 `gt_samples/saas/` 路径传给 ②，② 在 systemPrompt 末尾追加：
```
## 参考样本（GT）
以下是 1-2 份与当前 MRD 行业相近的高质量 PRD：
{{gt_sample_001}}
{{gt_sample_002}}
```

**预期效果**：PRD 风格、章节完整度、术语规范性向样本靠拢（课程 L35 GT 价值）。

---

### 2.2 启用章节级并发（v1 留作"可选" → 落地为"默认开启"）

**现状**：Chatflow 5 章节全串行；v1 文档"章节级并发"标为可选。

**完善点**：v1 Manager 的 SOP 中明确并发条件：

```
阶段 2：派 ② PRD 撰写
  - ② 启动后先写 outline.md
  - outline 完成后，Manager 验收 outline
  - 验收通过 → 把 5 章节拆为 2-3 个子任务并发
    - 子任务 A：PRD1 + PRD2（产品概述 + 功能规格，强依赖）
    - 子任务 B：PRD3（流程设计，可独立）
    - 子任务 C：PRD4 + PRD5（数据 + 页面，可独立但需要 PRD2 功能清单）
  - 共享变量：PRD_1_6 / PRD_2_1 / PRD_3_3 通过工作区共享
```

**风险**（来自课程 L23 AP-3）：并发前必须先有 outline，否则会出现"接口命名 / 数据格式 / 风格"不一致。

---

### 2.3 模型降级 + 重试 + 熔断（吸收 Chatflow + 课程 L31 可靠性）

**现状**：
- Chatflow：校验节点配 V3.1 备份模型 + 1 次重试
- v1：只说"error_alert"，没具体策略

**完善点**：3 级降级策略写入 Manager SOP：

| 失败等级 | 触发条件 | 处理 |
|---------|---------|------|
| L1 软失败 | 1 次重试可成功 | 自动重试 1 次，换种子 |
| L2 硬失败 | 重试 1 次仍失败 | 切换备份模型（V3.1）再试 1 次 |
| L3 熔断 | L1+L2 都失败 或 累计 ≥ 3 轮 reject | error_alert → Human |

**配套**：每个子 Agent 配 `max_tokens: 32768 + timeout: 600s`（参考 Chatflow 但拉齐）；PRD2/3/4 这种 JSON 输出节点 timeout 提到 300s（Chatflow 180s 偏紧）。

---

### 2.4 Code 拆分节点的功能回收

**现状**：Chatflow 用 6 个 Code 节点做 XML 正则拆分（工程补丁，弥补 LLM 输出格式约束弱）。

**完善点**：v1 框架**不直接沿用 XML 中间态**，而是让 ② 直接输出 Markdown，并通过结构化字段约定（标题层级 = 章节编号）。

```
# 1 产品概述
## 1.1 产品名称与定位
...
## 1.8 浏览器兼容性要求
# 2 功能规格
...
```

**优势**：
- 天然兼容人类阅读
- 拆分用 Python 解析 Markdown 标题比正则拆 XML 更可靠
- 校验节点直接读 Markdown 不用再转换

**代价**：需要把 Chatflow 的 5 章节 prompt 中"输出 XML 标签"改为"输出 Markdown 标题"。

---

### 2.5 SOP 中增加"GT 验收 + 业务指标"

**现状**：Chatflow 校验节点用 prompt 列举"开发/测试/运营"三视角，但**没有量化标准**（什么分数算通过？）。

**完善点**：v1 框架的 ③ 质检 Agent 配套 GT 评分表（参考课程 L36 评测体系）：

| 维度 | 满分 | 评分规则 | 及格线 |
|------|------|---------|--------|
| 完整性 | 20 | 5 大章节齐全 + 20 子模块齐全 | 16 |
| 一致性 | 20 | 术语 / 引用 / 流程闭环 | 16 |
| 可执行性 | 30 | 每条功能需求可写测试用例 | 24 |
| 风险标注 | 15 | 模糊词 / TBD / 异常分支 | 12 |
| 风格统一 | 15 | 术语 / 句式 / 排版 | 12 |
| **总分** | **100** | — | **80 分通过** |

**触发规则**：总分 < 80 → reject 重派 ②；连续 3 轮 < 80 → error_alert → Human。

## 三、低优先级（选做的工程优化）

### 3.1 拆分 GT 样本匹配

- 按行业（ToB SaaS / 工具 / 电商 / 硬件）建子目录
- Manager 根据 MRD 关键词自动选最相近的 1-2 份样本

### 3.2 沉淀"v1 → Chatflow"双向同步机制

- v1 文档第 10 节"输出主-子 Agent 配置文档"时，**直接附 Chatflow 的 5 章节 prompt 全文**（已有现成的）
- 后续若 Chatflow 升级（如加 PRD6 性能规格），通过 GT 样本 + Skill 增量更新回 v1

### 3.3 错误注入测试

- Manager SOP 末尾增加"干运行"测试：故意把 MRD 改坏（缺关键信息 / 互相矛盾），验证 needs_clarify 是否真的触发
- Chatflow 没有这层验证，可作为 v1 框架交付时的"自检 checklist"

### 3.4 多端适配可配置化

- Chatflow 167999 校验节点的"运营视角"中要求"页面要含移动端/桌面端"
- v1 可在 ② PRD5 节点前加一个"产品形态"选择题（Web / App / 桌面 / 多端），由 Manager 根据 MRD 关键词判断

### 3.5 章节完成度可观测

- Manager 工作区加 `prd_completion.json`：每章节完成后写入 `{section: 1, status: done, score: 92, time: 180s}`
- 用于后续第 38 课"线上监控"的基础数据

## 六、给用户的 3 个待确认问题

1. **GT 样本库是否真要做？** 工作量不小（50 条高质量样本），建议先做 10 条 MVP 验证效果。
2. **章节级并发是否默认开启？** 启用后需要约定 outline lock 机制，复杂度 +1。
3. **3 级降级策略中，备份模型是否就用 DeepSeek-V3.1？** 还是按子 Agent 选不同备选（如 ② 用 V3.1，① 用 R1 做深度推理）？
