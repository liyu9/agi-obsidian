## 四、变量与数据流（核心）

### 4.1 节点 156468：MRD 预处理（XML 输出）

**输入**：`USER_INPUT`（MRD 原文）
**输出**：`MRD`（string，被下一节点用正则拆）

**系统 Prompt 核心规则**（从原文摘录）：
- **5 大模块**固定结构（无论是否有内容都保留模块标签，无则标"无"）：
  1. 市场分析（行业概况 / 市场问题与机会）
  2. 用户分析（用户画像 / 场景分析）
  3. 竞争分析（直接竞品 / 差异化优势）
  4. 产品规划（产品定位 / 功能规划 / 非功能需求 / 实施路线）
- **推断标注**：`「注：推断依据——XXX」`
- **数据优先级**：量化数据 > 定性描述
- **格式**：严格 `<模块编号 模块名称>` / `<子模块编号 子模块名称>` 标签

1. **逻辑校验**：模块间逻辑连贯性（功能 ↔ 需求目标、上线计划 ↔ 功能优先级）
2. **风格统一**：术语、句式、排版统一
3. **多角色审查**：
   - 开发视角：功能可行性 / 边界条件
   - 测试视角：可测性 / 异常处理
   - 运营视角：业务流程闭环 / 用户场景契合
4. 修复问题不改动其他内容
5. 输出 Markdown（一级=模块 / 二级=子模块）
6. 只输出修复内容
7. 不省略内容

**特殊配置**：
- 备份模型：**DeepSeek-V3.1**（用 V3.2 出问题时降级）
- 1 次重试
- 600s 超时

## 七、设计特征与潜在问题

### 7.1 优点

1. **章节解耦**：每个 LLM 节点职责单一、上下文清爽（3000 字 prompt 上限内可控）
2. **XML 中间态**：标签化输出便于 Code 节点正则拆分，比纯 Markdown 易解析
3. **跨章节引用显式**：通过 `ref_node` 精确指定数据来源，避免隐式依赖
4. **多视角校验**：最终节点覆盖开发/测试/运营三个角度
5. **降级机制**：校验节点配置备份模型 V3.1
6. **无 Manager 调度**：纯流水线编排，适合确定性场景

### 7.2 潜在问题

| # | 问题 | 严重度 | 对应课程反模式 |
|---|------|-------|--------------|
| 1 | 节点 192934 的 `subsection_1_1` ~ `subsection_4_1` 共 6 个输入塞给同一个 LLM 节点，潜在上下文污染 | 中 | L23 关键设计 ① 违反 |
| 2 | 全流程没有 Manager 角色（纯 Pipeline），不满足课程 L23 的 Orchestrator 范式 | 中 | L23 第一代反模式 |
| 3 | 校验节点修复了 5 章节的"风格 / 逻辑 / 视角"问题，但没有"独立验收 Agent"（仍由同一个 LLM 串行处理） | 中 | L23 BP-1 缺失 |
| 4 | 章节顺序不可调，无法在产品形态未定时跳过不必要章节（如纯后端无 UI 时 PRD5 浪费） | 中 | L35 三问缺失 |
| 5 | 校验节点 prompt 把"修改 + 输出"放一起，**修改边界不可控**（可能改坏前面内容） | 中-高 | L23 AP-2 全链放大 |
| 6 | 没有 Human 介入点：所有澄清、确认、异常兜底都缺失 | 高 | L27 单一接口原则全缺 |
| 7 | 异常兜底靠 backupLLmParam（换模型），但没有"超阈值熔断 + 通知人" | 高 | L27 反模式二 |
| 8 | 没有"GT 历史样本"输入（虽然 4 维映射规则本身是 GT 的代偿） | 低 | L35 GT 概念 |
| 9 | 子任务无并发（5 章节全串行），性能瓶颈 | 中 | L23 并发价值未利用 |
| 10 | 节点 1609399 等 Code 节点职责是"XML→字段拆分"，实际上是 LLM 输出格式强约束的补丁 | 中 | 工程债务 |

### 7.3 关键 Prompt 工程细节

- **MRD 预处理**：标注规则（"「注：推断依据——XXX」"）保证可追溯
- **PRD1-1**：产品类型适配（工具/社交/电商三类）覆盖典型 ToB/ToC
- **PRD2-1**：功能 ID 命名规范强制（F-MATERIAL_管理_001）便于后续追踪
- **PRD3-2**：业务流程图强制 Mermaid 语法 + 必须含审批/校验/数据更新
- **PRD5**：响应式适配要求（页面规格要含移动端/桌面端）
- **校验节点**：禁止省略内容（"完整文章所有内容，不要省略"）

## 八、与课程 v1 框架的对比

| 维度 | 课程 v1（我们设计的） | 这份 Chatflow |
|------|-------------------|---------------|
| 范式 | Orchestrator（主 Agent 动态派发） | Pipeline（固定顺序） |
| Agent 数 | 1 主 + 3 子 = 4 | 6 LLM + 6 Code + 1 校验 LLM = 13 个执行节点 |
| 任务编排 | 动态（主 Agent 决定） | 静态（DAG edges 写死） |
| 上下文传递 | Task 对象精准传参 | 显式 `ref_node` 引用 + prompt 模板变量 |
| 子 Agent 隔离 | 独立 Crew / 子进程 | 同一工作流串行节点 |
| 协作协议 | 共享工作区 + 邮箱 | 节点间变量直传（无持久化） |
| 角色 Charter | 四层框架 | 单一 systemPrompt（无 Memory / Skills 独立文件） |
| 验收 | 独立 Agent（BP-1） | 同一 LLM 串行校验 |
| 人类介入 | 3 个介入点 | 无 |
| 异常兜底 | error_alert + 熔断 | 模型降级 + 1 次重试 |
| 并发 | 可选章节级并发 | 全串行 |
| 复用性 | 角色替换工作区即可 | 改 prompt 才能换场景 |
| 可观测性 | 邮箱 / Langfuse | 节点执行日志 |

**本质差异**：课程 v1 是"通用 PRD 团队"（4 个持久化角色），这份 Chatflow 是"单次 PRD 流水线"（13 个串行节点）。前者可承接多份 MRD、跨 session 积累；后者是单 MRD → 单 PRD 的一次性转化。

## 九、关键发现与建议

### 9.1 这份 Chatflow 适合的场景

- ✅ MRD 文本结构相对规范、一次性的 PRD 生产
- ✅ 不需要人类多次介入确认
- ✅ PRD 模板固定，跨场景复用度高
- ✅ 工程团队对 Coze 平台熟悉

### 9.2 不适合升级为"持续 PRD 团队"的场景

- ❌ 同一产品线需要长期维护 PRD（多次迭代、版本管理）
- ❌ 业务复杂到需要多 PM 视角（产品 / 运营 / 业务）协作
- ❌ 需要沉淀"团队 PRD 经验"到知识库
- ❌ PRD 经常需要根据业务方反馈回炉

### 9.3 升级到 v1 课程框架的关键改造点

1. 把"MRD 预处理 LLM 节点"包装为**① MRD 结构化 Agent**（含独立 workspace）
2. 把"PRD1-5 五个 LLM 节点"合并为**② PRD 撰写 Agent**（Manager 派发时按模板拆分任务，但 ② 内部用 GT 样本自主写）
3. 把"整体校验节点"独立为**③ PRD 质检 Agent**（独立 Crew、独立视角）
4. 新增**Manager 调度**（处理人类介入 / 重试 / 异常兜底）
5. 新增**shared/ + mailboxes/**协作协议
6. 新增**human.json + human_cli**（人在回路）

### 9.4 立即可行的工程优化（不动主架构）

1. **章节级并发**：PRD1 完成后，PRD2 / PRD3 拆出独立 DAG 分支并发（依赖关系不变）
2. **Code 节点缓存**：MRD 拆分结果缓存，避免重试时重复正则
3. **校验节点降级**：把"修复 + 输出"拆为"先检测 → 再决定是否进入修复 LLM"，避免误改
4. **GT 注入**：在每个章节节点的 prompt 末尾追加"参考示例"块（1-2 个历史高质量片段）
5. **超时分级**：PRD2/3/4（JSON 输出）超时 180s 偏紧，提到 300s
6. **异常熔断**：每个 LLM 节点加 settingOnError.processType: 2（异步通知） + 失败邮件
