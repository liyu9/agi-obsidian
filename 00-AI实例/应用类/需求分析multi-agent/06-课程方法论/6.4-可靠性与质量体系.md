## 1. 可观测性：Hook 骨架 + Langfuse 全链路追踪（L30 核心）

### 1.1 为什么需要可观测性

**课程 L30 核心命题**：
- LLM 应用的失败模式与软件不同——不是 Exception，而是"沉默的退化"
- "看起来成功"但"实际质量下降"是最危险的
- 必须用 **Hook 骨架** + **全链路追踪** 来"看见"系统

### 1.2 Hook 骨架

**课程 L30 设计**：在 Agent 生命周期的关键节点埋 Hook。

| Hook 节点 | 触发时机 | 记录内容 | v3 体现 |
|----------|---------|---------|--------|
| `before_llm_call` | 调用 LLM 前 | prompt + 上下文 + trace_id | Manager `completion.json` |
| `after_llm_call` | 调用 LLM 后 | 响应 + token 用量 + 耗时 | Manager `completion.json` |
| `before_tool_call` | 工具调用前 | 工具名 + 参数 | 子 Agent 邮箱日志 |
| `after_tool_call` | 工具调用后 | 工具返回 + 错误码 | 子 Agent 邮箱日志 |
| `on_error` | 异常时 | 异常堆栈 + 上下文 | `manager/escalation_log.md` |
| `on_done` | 任务完成 | 产物路径 + 评分 | `qa_team/score_calibration.md` |

**v3 §6.3 可观测性实现**：
- 邮箱日志：所有任务派发 / 完成 / 重试
- `completion.json`：每章节完成后写入 `{section, status, score, time, retry_count}`
- `trace_id 贯穿`：每个任务有唯一 trace_id

### 1.3 Langfuse 全链路追踪

**课程 L30 工具**：
- Langfuse = 开源的 LLM 应用可观测平台
- 自动捕获 prompt / response / token / latency
- 支持 trace 树（一个请求下多个子调用）

**v3 集成规划**：
- v3.0（当前）：自建 `completion.json` + 邮箱日志
- v3.1（待）：接 Langfuse（v3 §11 后续迭代）
- v3.2（待）：接 Langfuse + 自定义评分回调

## 2. 可靠性：重试、循环控制与成本围栏（L31 核心）

### 2.1 三个核心机制

| 机制 | 课程定义 | v3 体现 |
|------|---------|--------|
| **重试（Retry）** | 失败后自动重试 1-N 次 | v3 §6.2 L1 重试（换种子） |
| **循环控制（Loop Control）** | 防止无限循环 | retry_count ≥ 3 → L3 熔断 |
| **成本围栏（Cost Fence）** | 控制单次 / 单日成本 | v3 §6.1 maxTokens + timeout 限制 |

### 2.2 v3 3 级降级（v3 §6.2）

```
        ┌────────────────────────────────────────┐
        │  L1 软失败                              │
        │  · 触发：JSON 解析失败 / 字段缺失       │
        │  · 处理：自动重试 1 次（换种子）        │
        │  · 恢复条件：重试成功 → 继续            │
        └────────┬───────────────────────────────┘
                 │ 失败
                 ▼
        ┌────────────────────────────────────────┐
        │  L2 硬失败                              │
        │  · 触发：L1 失败 / LLM 调用超时        │
        │  · 处理：切换备份模型（V3.1）+ 重试    │
        │  · 恢复条件：备份成功 → 继续            │
        └────────┬───────────────────────────────┘
                 │ 失败
                 ▼
        ┌────────────────────────────────────────┐
        │  L3 熔断                                │
        │  · 触发：L2 失败 / 3 轮 reject 不收敛  │
        │  · 处理：error_alert → Human           │
        │  · Human 决定：rescue / abandon / 调向  │
        └────────────────────────────────────────┘
```

### 2.3 成本围栏

**课程 L31 关键设计**：
- 每个 Agent 配置 `maxTokens` + `timeout` + `daily_cost_limit`
- 超阈值即熔断，不带"无限重试"幻想

**v3 §6.1 模型选型**：

| Agent | 主模型 | 备份模型 | maxTokens | timeout | retry |
|-------|--------|---------|-----------|---------|-------|
| Manager | DeepSeek-V3.2 | V3.1 | 8,192 | 60s | 0 |
| ① MRD 结构化 | DeepSeek-V3.2 | V3.1 | 32,768 | 600s | 1 |
| ② 产品组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 1 |
| ②'' 流程组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 1 |
| ②''' 数据组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 1 |
| ④ 页面组 | DeepSeek-V3.2 | V3.1 | 32,768 | 300s | 1 |
| ③ 质检 | DeepSeek-V3.2 | **V3.1** | 32,768 | 600s | 1 |

**关键设计**：
- ③ 质检节点禁用 thinking（速度优先）+ 备份 V3.1（可靠性优先）
- 5 个写作 Agent 启用 thinking（质量优先）
- ② 流程/数据/页面三类 JSON 输出节点 timeout 提到 300s

## 3. 企业安全性：沙箱、权限网关与身份认证（L32 核心）

### 3.1 三个核心机制

| 机制 | 课程定义 | v3 体现 |
|------|---------|--------|
| **沙箱（Sandbox）** | Agent 工具调用限制在指定路径 | v3 §4.1 Owner 唯一原则（每文件 1 Owner） |
| **权限网关（Permission Gateway）** | 每个工具调用前校验权限 | v3 §3.x NEVER 清单 + 工具层权限 |
| **身份认证（Authentication）** | 区分"是谁"调用 | Manager / 子 Agent / Human 各自 token |

### 3.2 v3 工具层权限

**v3 §10 风险 2 反制**：
> "② 写工具只允许 `prd/section_1_2.md`"

**v3 每个 Agent 的工具白名单**：

| Agent | 允许写入 | 允许读取 | 禁止 |
|-------|---------|---------|------|
| Manager | `mailboxes/*` / `manager/*` / `delivery/*` | 全部 | 任何 PRD 文件 |
| ① MRD 结构化 | `breakdown/*` | `input/mrd.md` | `prd/*` |
| ② 产品组 | `prd/section_1_2.md` / `prd/feature_id_list.md` / `prd/handoff_2to3.md` | `breakdown/*` / `gt_samples/product/*` | `prd/section_3.md` / `prd/section_4.md` / `prd/section_5.md` |
| ②'' 流程组 | `prd/section_3.md` / `prd/handoff_34.md` | `prd/section_1_2.md` / `prd/feature_id_list.md` | 其他 prd 文件 |
| ②''' 数据组 | `prd/section_4.md` / `prd/handoff_45.md` | `prd/section_3.md` / `prd/handoff_34.md` | 其他 prd 文件 |
| ④ 页面组 | `prd/section_5.md` | `prd/section_4.md` / `prd/handoff_45.md` | 其他 prd 文件 |
| ③ 质检 | `qa/qa_report.md` | 全部 prd 文件 | 任何 prd 文件（只读） |

### 3.3 沙箱边界

**v3 沙箱设计**：
- 文件系统层：每个 Agent 只能在自己的目录 + 读路径
- 工具层：每个工具调用前校验路径
- 网络层：v3.0 不联网（v3.1 考虑接 L21 搜索）

## 4. 需求边界：AI 适用性评估表（L34 核心）

### 4.1 课程核心命题

**课程 L34 警示**：
- 不是所有需求都适合用 AI
- "表演式 AI"——能跑但不创造价值的 AI 部署——是最常见的失败
- 必须用 **AI 适用性评估表** 提前识别高 ROI 场景

### 4.2 AI 适用性评估表（v3 适配版）

| 维度 | 高 ROI（适合） | 低 ROI（不适合） | v3 场景 |
|------|--------------|----------------|--------|
| **任务结构化程度** | 高（5 章节固定模板） | 低（开放式探索） | ✅ 适合 |
| **可验收性** | 强（100 分制可量化） | 弱（主观评价） | ✅ 适合 |
| **GT 样本可得性** | 高（历史 PRD 充足） | 低（无历史） | ✅ 适合 |
| **业务风险** | 中（PRD 是文档，非决策） | 高（直接决策） | ✅ 适合 |
| **人机协作性** | 中（3 介入点） | 高（需实时交互） | ✅ 适合 |
| **ROI** | 节省 60% 撰写时间 | 节省 < 20% | ✅ 适合 |

**v3 决策**：
- MRD → PRD 转换 = 高 ROI 场景（结构化 + 可验收 + 充足 GT）
- 6 类不适合 AI 的场景在 v3 §10 风险表中已列举

### 4.3 不适合 AI 的需求特征

**课程 L34 反向清单**：
- 开放式探索（如"帮我思考未来 5 年战略"）
- 强实时性（如客服实时对话）
- 强创造性（如艺术创作、文学创作）
- 强政治性（如薪酬决策）
- 强合规性（如医疗诊断）
- 强物理性（如机器人控制）

## 5. 评测体系：让 AI 质量可量化（L36 核心）

### 5.1 课程 L36 核心命题

- AI 应用的质量 **必须可量化**，否则无法迭代
- 量化 = 指标体系 + 评分校准 + A/B 实验

### 5.2 v3 100 分制评分（v3 §7.1）

| 维度 | 满分 | 评分规则 | 及格线 |
|------|------|---------|--------|
| **完整性** | 20 | 5 大章节齐全（各 4 分）+ 20 子模块齐全（每缺 1 扣 1 分） | 16 |
| **一致性** | 20 | 术语统一（5 分）+ 跨章节引用对齐（5 分）+ 流程闭环（5 分）+ 数值/ID 一致（5 分） | 16 |
| **可执行性** | 30 | 每条功能需求可写测试用例（10 分）+ 验收标准 SMART（10 分）+ 异常分支覆盖（5 分）+ 边界条件明确（5 分） | 24 |
| **风险标注** | 15 | 模糊词识别（5 分）+ TBD 标注（3 分）+ 异常分支（4 分）+ 范围蔓延信号（3 分） | 12 |
| **风格统一** | 15 | 术语一致（5 分）+ 句式一致（5 分）+ 排版统一（5 分） | 12 |
| **总分** | 100 | — | **80 分通过** |

### 5.3 多视角审查（v3 §7.2）

| 视角 | 关注点 | 输出物 |
|------|--------|--------|
| **开发视角** | 功能可行性 / 边界条件 / 技术实现路径 | "开发侧 issue 清单" |
| **测试视角** | 可测性 / 异常处理 / 边界用例 | "测试侧 issue 清单" |
| **运营视角** | 业务流程闭环 / 用户场景契合 / 价值主张落地 | "运营侧 issue 清单" |

**3 视角各自输出 issue 清单** → 合并为 qa_report.md 的"具体段落 + 修改建议"部分。

### 5.4 评分校准

**课程 L36 关键设计**：
- 不同时间点的评分必须可比
- 解决：评分校准表（`qa_team/score_calibration.md`）
- 每月回看 5 个历史 PRD 的分数，校准评分标准

**v3 体现**：
- `qa_team/score_calibration.md`（v3 §3.7 ③ Memory）
- 触发器：每完成 10 个 PRD 校准一次

## 6. 持续集成：让 AI 应用稳定演进（L37 核心）

### 6.1 CI/CD for AI

**课程 L37 核心命题**：
- 传统 CI：代码变更 → 自动化测试 → 部署
- AI CI：prompt 变更 / GT 变更 / 模板变更 → 自动化质检 → 部署

### 6.2 v3 CI 设计

| 触发 | 流水线 | 验证 | 部署 |
|------|--------|------|------|
| **Prompt 变更** | 5 维度质检 + 100 分制 | 总分 ≥ 80 | 灰度 1 个 PRD |
| **GT 新增** | 关键词匹配验证 | 匹配准确率 ≥ 70% | 进入 GT 库 |
| **模板变更** | 章节完整性 + 必含项 | 完整性 ≥ 95% | 进入模板库 |
| **质量阈值变更** | 历史 PRD 重评分 | 一致性 ≥ 90% | 校准记录 |

### 6.3 v3 §11 阶段 2 落地

- Week 6：搭建 CI 流水线
- 验证：5 维度质检自动化
- 部署：每次 PR 触发 5 维度评分

## 7. 线上监控：知道 AI 到底跑得怎么样（L38 核心）

### 7.1 监控的 4 类指标

| 类别 | 课程定义 | v3 体现 |
|------|---------|--------|
| **可用性** | uptime / 任务完成率 | Watchdog 成功率 |
| **质量** | 平均分 / 一次通过率 | qa_report 总分分布 |
| **效率** | 平均耗时 / token 用量 | completion.json 统计 |
| **业务** | Human 终审通过率 | checkpoint_request confirm 比例 |

### 7.2 v3 监控面板（v3.1 规划）

- **首页看板**：今日任务数 / 平均分 / 熔断次数
- **质量趋势**：30 天平均分 / 一次通过率
- **效率趋势**：单 PRD 平均耗时 / 章节并发度
- **熔断记录**：最近 10 次 error_alert

## 8. 数据飞轮：用线上数据持续迭代（L39 核心）

### 8.1 飞轮设计

```
完成 1 个 PRD
    ↓
③ 质检 + Human 终审通过
    ↓
拆解出"可复用片段"
    ↓
沉淀到 GT 库
    ↓
下次同类 MRD 关键词匹配
    ↓
减少 30-50% 写作时间
    ↓
更多 PRD 完成
    ↓
（飞轮加速）
```

### 8.2 v3 飞轮实施路径

| 阶段 | GT 数量 | 写作时间 | 一次通过率 |
|------|---------|---------|----------|
| v3.0 MVP | 20 条 | 5 小时 | 60% |
| v3.1（飞轮 1） | 50 条 | 4 小时 | 70% |
| v3.2（飞轮 2） | 100 条 | 3 小时 | 80% |
| v3.3（飞轮 3） | 200 条 | 2 小时 | 90% |

### 8.3 飞轮的反模式

**课程 L39 警示**：
- **数据偏移**：线上分布 ≠ 训练分布
- **负反馈循环**：GT 沉淀了低质量样本，下次更差
- **冷启动**：GT 库为空时，质量必然低

**v3 反制**：
- 飞轮 1：人工筛选前 20 条 GT（v3 §10 风险 5 缓解）
- 飞轮 2：自动筛选 + 人工抽检 10%
- 飞轮 3：完全自动 + ③ 质检把关

## 10. 关键方法论 takeaway

1. **可观测性 = Hook 骨架 + 全链路追踪**——v3.1 接 Langfuse
2. **3 级降级** = L1 重试 → L2 切模型 → L3 熔断，避免"无限重试"
3. **成本围栏** = maxTokens + timeout + daily_cost_limit
4. **沙箱/权限网关/身份认证** = 工具层白名单 + 路径校验 + token 区分
5. **AI 适用性评估表**——提前识别高 ROI 场景
6. **100 分制 + 3 视角 + 评分校准**——可量化的质量体系
7. **CI for AI**——prompt / GT / 模板变更触发自动化质检
8. **数据飞轮**——每完成 1 个 PRD 沉淀 1 条 GT，但要反制"负反馈循环"
