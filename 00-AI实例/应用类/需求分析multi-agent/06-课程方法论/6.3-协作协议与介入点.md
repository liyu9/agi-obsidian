## 1. 任务链与信息传递（L26 核心）

### 1.1 三个核心反模式（L26 1.1）

**课程 L26 警示**：多 Agent 协作 70% 失败源于以下三个反模式。

| 反模式 | 含义 | 失败率 | v3 反制 |
|--------|------|--------|--------|
| **1 信息丢失** | 上下文传递时关键信息被截断 | ~25% | v3 §4.1 共享工作区 + 文件即接口 |
| **2 所有权歧义** | 多 Agent 写同一文件冲突 | ~37% | v3 §4.1 Owner 唯一原则 |
| **3 状态不可见** | Agent 不知道别人在干什么 | ~20% | v3 §4.2 三态邮箱状态机 |

**关键数据**：
- 三类反模式合计 ~82% 失败
- v3 §9 决策 5（Owner 唯一文件所有权）的依据 = "37% 失败源于所有权歧义"
- v3 §9 决策 6（三态邮箱状态机）的依据 = 解决"状态不可见"

### 1.2 信息传递的两种模式

| 模式 | 课程定义 | v3 体现 | 优劣 |
|------|---------|--------|------|
| **A 上下文传递** | 主 Agent 把自己的上下文复制给子 Agent | ❌ v3 不采用 | 上下文膨胀 / 注意力稀释 |
| **B 文件路径传递** | 只传 input/output 路径，子 Agent 自主读 | ✅ v3 §4.2 邮箱协议 | 上下文可控 / 可验证 |

**课程原话（L23 关键设计 ①）**：
> "主 Agent 的全局历史——之前和用户的对话、之前其他子 Agent 的执行细节——全都不传。"

**v3 严格遵循**：每个子 Agent 只读自己需要的 `input_path` / `gt_sample_path` / `output_path`，从不读 Manager 的全局历史。

### 1.3 任务链的"接力棒"机制

**课程 L26 核心思想**：任务链 = "接力棒"传递，每个 Agent 只接上一棒 + 传下一棒。

**v3 体现**：
- ② 产品组 → ②'' 流程组：通过 `feature_id_list.md` + `handoff_2to3.md` 传递
- ②'' 流程组 → ②''' 数据组：通过 `handoff_34.md` 传递（功能 ID + 流程节点 + 数据实体）
- ②''' 数据组 → ④ 页面组：通过 `handoff_45.md` 传递（功能 ID + 数据实体 + 页面清单）

**关键约束**（v3 §4.3）：
- 每个 handoff 文件由前序 Agent 写、后序 Agent 读（Owner 唯一）
- handoff 内容只列"接口契约"，不复制 PRD 全文
- 强制 Manager 验收前序产物后再开后序 Agent

## 2. 三态邮箱状态机（L26 3.4）

### 2.1 为什么需要三态

**课程核心命题（L26 3.4）**：
- 简单 `read: bool` 二态无法支持"崩溃恢复"和"补单机制"
- 三态状态机 = `unread` → `in_progress` → `done`，加上 `processing_since` 时间戳

### 2.2 v3 邮箱协议实现

```json
{
  "id": "msg-20260624-001",
  "from": "manager",
  "to": "product_team",
  "type": "task_assign | task_done | needs_clarify | checkpoint_request | error_alert",
  "subject": "派发 task-20260624-002：写 PRD1+PRD2",
  "content": "路径引用 + 关键摘要，不复制文档全文",
  "task_payload": {
    "input_path": "shared/breakdown/requirements_list.md",
    "gt_sample_path": "shared/gt_samples/product/saas/001.md",
    "output_path": "shared/prd/section_1_2.md",
    "feature_id_list_path": "shared/prd/feature_id_list.md"
  },
  "timestamp": "2026-06-24T10:30:00+08:00",
  "status": "unread | in_progress | done",
  "processing_since": "2026-06-24T10:30:05+08:00",
  "retry_count": 0
}
```

### 2.3 Watchdog 机制

**课程 L26 3.4 设计**：
- Watchdog 每 10 分钟扫一次 `mailboxes/`
- 超时的 `in_progress`（超过 30 分钟）→ reset 为 `unread` → 触发重试
- `retry_count` ≥ 3 → 升级到 `error_alert` → Human 决定

**v3 体现**：
- 邮箱文件存于 `shared/mailboxes/{agent}.json`
- Watchdog 由 Manager 的 `level3_fallback` Skill 触发
- retry_count 触发 L3 熔断（v3 §6.2 3 级降级）

### 2.4 5 种邮件类型

| 类型 | 含义 | 触发方 | 接收方 |
|------|------|--------|--------|
| `task_assign` | 派发新任务 | Manager | 5 子 Agent |
| `task_done` | 任务完成 | 5 子 Agent | Manager |
| `needs_clarify` | 需要澄清 | ① MRD 结构化 | Manager → Human |
| `checkpoint_request` | 关键节点确认 | Manager | Human |
| `error_alert` | 异常熔断 | 任意 | Manager → Human |

## 3. Human as 甲方：人类介入点设计（L27 核心）

### 3.1 为什么 Human 是"甲方"

**课程 L27 核心命题**：
- Human 是"客户"，Agent 是"乙方团队"
- **不是每件事都问**——是"关键节点才问"
- 介入点设计 = 决定"哪些决策权归 Human，哪些归 Agent"

### 3.2 v3 三个介入点（v3 §8.1）

| # | 介入点 | 触发条件 | Human 动作 | Manager 响应 |
|---|--------|---------|-----------|------------|
| **1** | `needs_clarify` | ① 标注"「注：推断依据」" ≥ 3 处 / 字段缺失 / MRD 关键维度不全 | 在 `open_questions.md` 补全或回复邮件 | 收到后继续阶段 1 |
| **2** | `checkpoint_request` | PRD 中 `[TBD]` > 3 处 / 模糊词 ≥ 5 处 / 非功能需求 0 容错 / 多解需求 | 读 PRD 终稿 → confirm / reject + feedback | 确认 → 归档；拒绝 → 重派 |
| **3** | `error_alert` | 子 Agent 失败 ≥ 3 轮 / JSON 解析持续失败 / LLM 多次超时 / qa_report 连续 3 轮不达标 | 决定 rescue / abandon / 调向 | 收到指令继续 |

**关键设计**（v3 §1.3 关键设计原则 ⑥）：
- **单一人类接口**——Human 只与 Manager 对话，不直接对话子 Agent
- **介入点不超 3 个**——避免"人类疲劳型确认"（v3 §10 风险 4）
- **不介入的范围**——v3 §8.3 列了 6 类"Agent 完全自主"事项

### 3.3 自动触发规则（v3 §8.2）

| 信号 | 计数 | 触发 |
|------|------|------|
| ① 标注"「注：推断依据」" | ≥ 3 | `needs_clarify` |
| `open_questions.md` 条目数 | ≥ 5 | `needs_clarify` |
| PRD 中 `[TBD]` 标记 | > 3 | `checkpoint_request` |
| 模糊词（"可能/大概/也许"） | ≥ 5 处 | `checkpoint_request` |
| 同一 Agent 累计 reject | ≥ 3 轮 | `error_alert` |
| ③ qa_report 总分连续 | < 80 达 3 轮 | `error_alert` |
| LLM 调用失败 | L1+L2 都失败 | `error_alert` |

### 3.4 L27 课程关键 takeaway

| L27 原则 | v3 体现 |
|---------|--------|
| **甲方乙方化** | Human = 客户，Agent 团队 = 乙方 |
| **介入点分类** | 澄清 / 验收 / 异常三类（v3 §8.1） |
| **避免疲劳** | 介入点 ≤ 3 个 + 高风险单独标红（v3 §10 风险 4） |
| **不介入的范围** | 6 类 Agent 自主事项（v3 §8.3） |

## 4. 数字员工的自我进化（L28 核心）

### 4.1 自我进化的三层（L28 1.1）

| 层级 | 课程定义 | v3 体现 |
|------|---------|--------|
| **L1 个人进化** | 单 Agent 写自己的 Memory | 子 Agent 写 `history_clarifications.md` / `history_feedback.md` |
| **L2 团队进化** | 团队共享知识库 | Manager 的 `decision_patterns.md` + 子 Agent 的 `gt_samples_*` |
| **L3 跨团队进化** | 跨项目沉淀 | 飞轮：每完成 1 个 PRD 沉淀 1 条 GT（v3 §11 后续迭代） |

### 4.2 自我进化的触发条件

| 触发 | 进化层级 | v3 体现 |
|------|---------|--------|
| 同一类型问题出现 2 次 | L1 个人进化 | 子 Agent 写 `history_*.md` |
| 同类决策模式被复用 3 次 | L2 团队进化 | Manager 写 `decision_patterns.md` |
| 累计完成 10 个 PRD | L3 跨团队进化 | GT 库从 20 → 50 → 100 条 |

### 4.3 v3 飞轮设计（v3 §11 后续迭代）

```
完成 1 个 PRD
    ↓
③ 质检 + Human 终审通过
    ↓
拆解出"可复用片段"（章节 / 数据模型 / 流程图 / 页面）
    ↓
沉淀到 `gt_samples/` 对应子库
    ↓
下次同类 MRD 关键词匹配 → 直接加载
    ↓
减少 30-50% 写作时间
```

### 4.4 自我进化的反模式（L28 警示）

| 反模式 | 含义 | v3 反制 |
|--------|------|--------|
| **过度进化** | Agent 改坏自己的核心 Soul | v3 §3.1 Manager NEVER 清单第 1 条：绝不写 PRD |
| **盲目模仿** | 子 Agent 模仿 GT 样本但场景不匹配 | ③ 质检打分时检查"是否过度引用" |
| **遗忘过快** | 旧经验被覆盖 | Manager 的 `decision_patterns.md` 只追加不删 |

## 5. Process 任务调度与信息传递（L09 核心）

### 5.1 Process 的 4 个核心对象

| 对象 | 课程定义 | v3 体现 |
|------|---------|--------|
| **Input** | 上一棒产物的文件路径 | `task_payload.input_path` |
| **Output** | 本棒产物的文件路径 | `task_payload.output_path` |
| **Trigger** | 触发条件（哪条 email / 哪个文件就绪） | Watchdog 扫描 |
| **Side Effect** | 副作用（更新邮箱 / 写 handoff / 触发下游） | 子 Agent 写完自动 trigger 下游 |

### 5.2 Process 设计的反模式

| 反模式 | 含义 | v3 反制 |
|--------|------|--------|
| **1 循环依赖** | A 等 B / B 等 A | v3 §4.3 handoff 严格按 ② → ②'' → ②''' → ④ 顺序 |
| **2 状态机歧义** | 状态可同时属多态 | v3 §4.2 三态严格三选一 |
| **3 触发器遗漏** | 某些事件无人监听 | Watchdog 兜底 |
| **4 副作用爆炸** | 一次操作触发 10 个下游 | handoff 文件 1 对 1 契约 |

### 5.3 v3 端到端 Process 概览（v3 §5 9 阶段）

| 阶段 | Process 类型 | 触发 | 输出 |
|------|------------|------|------|
| 0 Manager 初始化 | 启动 | Human 投递 MRD | `shared/` 工作区 + 邮箱初始化 |
| 1 派 ① MRD 结构化 | 顺序 | Manager 主动 | `task_assign` 邮件 |
| 2 ① 产出 breakdown | 顺序 | ① 写完 `breakdown/*` | `task_done` 邮件 |
| 3 派 ② 产品组 | 顺序 | Manager 验收通过 | `task_assign` |
| 4 ② 产出 PRD1+2 | 顺序 | ② 写完 `section_1_2.md` | `task_done` |
| **5 并发派发** | **并发** | **Manager 验收通过** | **3 封 `task_assign` 同时** |
| 6 收集 PRD3+4+5 | 顺序 | 3 子 Agent 各自 `task_done` | Manager 收集 |
| 7 派 ③ 质检 | 顺序 | Manager 验收通过 | `task_assign` |
| 8 读 qa_report | 顺序 | ③ 写完 `qa_report.md` | Manager 决策（通过/修订/熔断） |
| 9 归档 + Human 终审 | 顺序 | Manager 决策通过 | `checkpoint_request` → `delivery/prd_final.md` |

**关键优化**：阶段 5 三路并发节省 40% 时间（v3 §11 阶段 3 里程碑）。

## 7. 关键方法论 takeaway

1. **70% 失败源于三类反模式**：信息丢失 / 所有权歧义 / 状态不可见——v3 §4 全部反制
2. **文件即接口**：不传上下文，只传路径（L23 关键设计 ①）
3. **三态状态机**：unread → in_progress → done + Watchdog（L26 3.4）
4. **单一人类接口**：Human 只与 Manager 对话，避免多头沟通
5. **介入点 ≤ 3 个**：避免"人类疲劳型确认"
6. **自我进化三层**：L1 个人 / L2 团队 / L3 跨团队，由触发条件驱动
7. **飞轮设计**：1 PRD 1 GT，跨项目沉淀
