## 1. 四种 AI 架构范式（L01）

### 1.1 范式对比表

| 范式 | 核心驱动力 | 适用场景 | 局限 | v3 架构位置 |
|------|----------|---------|------|------------|
| **1 Prompt Engineering** | 人 | 单次问答 / 文本改写 | 3-5 万字后指令遵循急剧下降 | — |
| **2 Workflow / Chain** | 程序员（Code-Driven） | 80% 工业落地（边界清晰） | 异常分支多时枚举成本不可接受 | — |
| **3 Single Agent** | 模型（Model-Driven） | 单一长链路任务 | 上下文膨胀 → 幻觉/崩溃 | — |
| **4 Multi-Agent System** | 组织（团队） | 复杂长链路 / 跨职能交付 | 协调成本 | **v3 整体定位** |

**关键认知（L01）**：
- 范式 1-4 的"自主性"和"复杂度"由低到高
- **不是替代关系，是叠加关系**——v3 是"Multi-Agent 范式 + 内部子节点用 Workflow"（如 ②'' 流程组的 Mermaid 流程图生成本身是 Workflow 节点）
- 选型口诀：**边界清晰用 Workflow，自主探索用 Single Agent，跨职能交付用 Multi-Agent**

### 1.2 v3 架构对应

- **总体范式**：Multi-Agent（1 主 + 5 子）
- **子节点**：②'' 流程组 / ②''' 数据组 / ④ 页面组 内部用 Workflow 节点（如 Mermaid 流程图生成是"输入实体 → 输出图表"的代码驱动节点）
- **Manager 决策**：用 Single Agent 范式（接 LLM 自主判断 GT 选择 / 修复策略 / 熔断）

## 2. Agent 解剖学与 ReAct 范式（L02）

### 2.1 Agent 五脏俱全的"数字生命"

```
┌────────────────────────────────────────┐
│  Agent = 大脑 + 工具箱 + 记忆 + 反馈环  │
├────────────────────────────────────────┤
│  · 大脑 = LLM（推理 / 规划）            │
│  · 工具箱 = Tools（执行 / I/O）         │
│  · 记忆 = Memory（跨 session 持久化）   │
│  · 反馈环 = Observe → Think → Act     │
└────────────────────────────────────────┘
```

### 2.2 ReAct 范式（Reasoning + Acting）

| 步骤 | 含义 | v3 体现 |
|------|------|--------|
| **Reasoning** | 模型读上下文 / 拆解任务 | Manager 收到 MRD → 拆解为 5 个写作子任务 |
| **Acting** | 调用工具 / 写文件 | 子 Agent 调用 `feature_id_assigner` 写 `section_1_2.md` |
| **Observing** | 读工具返回 / 自我评估 | 子 Agent 读自己写的产物，校验格式 |

**关键原则（L02）**：
- **Agent 的"自主性"来自反馈环**——观察 → 思考 → 行动 → 观察 ...，没有这一步就是 Workflow
- v3 ① MRD 结构化 Agent 在"拆解 47 需求"时**会多次重读 MRD 片段**（ReAct 范式）
- v3 ③ 质检 Agent 的"5 维度评分"是 Reasoning 输出，不是单次 LLM 调用

### 2.3 与 v3 主文档的映射

- v3 §3 每个 Agent 的"Soul"字段 = Agent 的"价值观"（Reasoning 的隐性偏好）
- v3 §3 每个 Agent 的"NEVER 清单" = Reasoning 的硬约束
- v3 §3 每个 Agent 的"Skills" = Agent 的工具箱
- v3 §3 每个 Agent 的"Memory" = 跨 session 持久化

## 3. Multi-Agent 协作的三个核心对象（L03 + L23）

### 3.1 Agent / Task / Process 三元组

| 对象 | 课程定义 | v3 映射 |
|------|---------|--------|
| **Agent** | 角色 + 工具 + 记忆 | Manager + 5 子 Agent（v3 §3 七层） |
| **Task** | 工作包（role + goal + task + tools + input/output 路径） | v3 邮箱协议中的 `task_payload`（v3 §4.2） |
| **Process** | 调度关系（顺序 / 并发 / 条件分支） | v3 §5 端到端 9 阶段 SOP |

### 3.2 Task 对象的 5 字段契约（L23 关键设计 ①）

```json
{
  "role": "后端 Developer",
  "goal": "实现员工假期管理系统的 CRUD 接口",
  "task": "根据接口规范实现 FastAPI + 内存存储后端",
  "input": "workspace/api_spec.md（接口规范文档路径）",
  "output": "将代码写入 workspace/backend/main.py",
  "tools": ["FileReadTool", "FileWriterTool"]
}
```

**关键原则**：
- **不传上下文，只传工作包**（v3 §4.2 邮箱协议完美对应）
- 主 Agent 的全局历史不传给子 Agent
- 子 Agent 只读自己需要的 input 路径

### 3.3 Process 的两种形态

| 形态 | 课程定义 | v3 体现 |
|------|---------|--------|
| **顺序 Process** | step1 → step2 → step3 | 阶段 1-4（Manager 验收 → 派 ② → ② 产出 → 验收） |
| **并发 Process** | 多个 step 同步执行 | 阶段 5（②'' / ②''' / ④ 三路并发） |

**v3 关键技术决策**：
- 阶段 5 之所以能并发，**前提是 Manager 验收 outline 锁**（v3 §10 风险 6 缓解）
- 并发节省 40% 时间（v3 §11 阶段 3 里程碑）

## 4. Orchestrator 范式（L23 核心）

### 4.1 三代多 Agent 演化

| 代 | 形态 | 问题 | 课程结论 |
|----|------|------|---------|
| **1 Pipeline** | 流程写死 | 中间状态与假设不符时卡住/错 | 已被淘汰 |
| **2 Swarm** | 去中心化自由互调 | 误差叠加 / 无验收 / 不收敛 | 已被验证失败 |
| **3 Orchestrator** | 主 Agent 调度 + 子 Agent 执行 | — | **当前工程主流** |

**v3 严格遵循 Orchestrator 范式**（v3 §1.3 关键设计原则 ①）。

### 4.2 Orchestrator 三个关键设计（L23 关键设计 ① ② ③）

| # | 关键设计 | 课程原话 | v3 体现 |
|---|---------|---------|--------|
| ① | **Task 对象传递工作，不传上下文** | "主 Agent 的全局历史——之前和用户的对话、之前其他子 Agent 的执行细节——全都不传" | v3 §4.2 邮箱协议的 `task_payload` 字段 |
| ② | **文件路径作为接口** | "子 Agent 只读 input 路径，不直接对话" | v3 §4.1 Owner 唯一原则（文件即接口） |
| ③ | **主 Agent 不下场** | "明确限制主 Agent 不许执行，只允许子 Agent 干活" | v3 §3.1 Manager NEVER 清单第 1 条 |

### 4.3 与 Claude Code 的同构性

**课程原话（L23）**：
> "你已经在用 Orchestrator 了。Claude Code 的五种工作模式本质上都是主 Agent + 子 Agent 的变体。"

**v3 借鉴点**：
- Claude Code 的"协调者模式" = v3 Manager
- Claude Code 的"fork 型子 Agent" = v3 5 个子 Agent
- Claude Code 的"Task 工具" = v3 §4.2 邮箱协议

## 5. 团队角色体系（L25 核心）

### 5.1 三维隔离判断法（BP-2 反模式排除）

**课程 L25 核心方法**：判断一个角色是否独立为 Agent，看"记忆数据 / 技能体系 / 决策偏好"三维是否独立。

| 维度 | 含义 | v3 体现 |
|------|------|--------|
| **记忆数据** | 跨 session 需要的持久化知识 | ② 读 GT/product，②'' 读 GT/flow，②''' 读 GT/data |
| **技能体系** | 调用的工具集 | ② `prd1_writer_sop`，②'' `mermaid_flowchart`，②''' `er_diagram_designer` |
| **决策偏好** | "Soul" / 价值观 | ② "用户友好"，②'' "严谨穷举"，②''' "模型严谨" |

**v3 1+5 架构的拆分依据**（v3 §9 决策 7）：
- ② → ②'' → ②''' → ④：每拆一次都过三维验证
- ④ 页面组单独成 Agent：占 54% 输出 / Soul 漂移 / 服务对象不同（v3 §9 决策 7）

### 5.2 团队 SOP（v3 Manager §3.1 Memory）

| 文件 | 课程对应 | v3 用途 |
|------|---------|--------|
| `sop_prd_team.md` | 团队协作流程规范 | 阶段 0-4 流转规则 |
| `team_roster.md` | 团队名册 | 5 子 Agent 角色 + 职责 |
| `decision_patterns.md` | 决策模式库 | "qa_report 命中 X → 自动派修订 Y" |
| `gt_index.md` | GT 索引 | 4 类 GT 关键词匹配 |
| `escalation_log.md` | 升级记录 | 历史熔断 + 修复案例 |

### 5.3 角色类型分类

| 类型 | 课程定义 | v3 体现 |
|------|---------|--------|
| **调度型** | 派任务、验收、决策 | Manager |
| **执行型** | 写文档、生成图 | ① / ② / ②'' / ②''' / ④ |
| **审查型** | 多视角检查、出报告 | ③ 质检（"只报告不修改"） |

**v3 关键约束**：审查型不可兼执行型（v3 §1.3 关键设计原则 ⑤）——避免"自检盲区"。

## 7. 关键方法论 takeaway

1. **范式选型**：边界清晰用 Workflow，自主探索用 Single Agent，跨职能交付用 Multi-Agent（v3 总体用 Multi-Agent，内部子节点用 Workflow 组合）
2. **ReAct 范式**：Agent 的"自主性"来自反馈环（Observe → Think → Act），没有反馈环 = Workflow
3. **Orchestrator 三大设计**：Task 对象 / 文件路径 / 主 Agent 不下场
4. **三维隔离判断法**：记忆 / 技能 / 决策偏好——任一维度独立即可拆 Agent
5. **角色类型三分类**：调度型 / 执行型 / 审查型——审查型不可兼执行型
