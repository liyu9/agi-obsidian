## 1. 记忆的本质（L18 核心认知）

### 1.1 一个核心反直觉

**课程原话（L18）**：
> "大模型没有记忆。每一次 API 调用都是独立的，模型不知道你上一句说了什么。"

**记忆的本质 = 一套构建 message list 的机制**：

```python
messages = [
    {"role": "system",    "content": "你是 XiaoPaw，一个飞书工作助手..."},
    {"role": "system",    "content": "用户偏好：周报格式先汇总再列计划..."},  # ← 这就是"记忆"
    {"role": "user",      "content": "帮我发周报"},
    {"role": "assistant", "content": "好的，我来按你喜欢的格式..."},
]
```

**关键洞察**：
- **没有魔法，只有信息流设计**——你往 messages 里塞什么，模型就"知道"什么
- 模型本身 = CPU（只计算，不存储）
- 上下文窗口 = RAM（容量有限，断电就没了）
- 外部存储 = 硬盘（持久化但需主动读取）

### 1.2 记忆系统的核心命题

**课程原话（L18）**：
> "记忆系统要做的事情，就是设计一套机制：什么时候从硬盘加载到内存，什么时候从内存写回硬盘，内存快满了怎么腾空间。"

**v3 架构映射**：
- "硬盘" = `workspace/各角色子目录`（v3 §3 每个 Agent 的 Memory 字段）
- "内存" = 单次 LLM 调用的上下文窗口（v3 §2.2 6 个 Agent + Manager 单次 7K-25K）
- "加载" = GT 样本匹配 + handoff 文件读取
- "写回" = 子 Agent 产物落盘到 `shared/prd/`

## 2. 三代记忆范式演进（L18）

### 2.1 三代对比表

| 代 | 时代 | 核心方法 | 上下文管理 | 角色 |
|----|------|---------|----------|------|
| **1 Prompt Engineering** | GPT-3 时代 | 人写全部 | 不需要管理（人写的就是全部） | 骑手（手把手拉缰绳） |
| **2 Context Engineering** | 2024-2025 | 工程逻辑构建 | 剪裁 / 压缩 / 截断 | 教练（规划赛道和路线） |
| **3 Harness Engineering** | 2026 OpenAI 提出 | 设计环境让模型探索 | 预加载关键索引 + 模型按需探索 | 牧场主（建围栏、让马自己跑） |

**关键演进逻辑**：
- 驱动力 1：模型能力变化（GPT-3 → GPT-4 → Claude）
- 驱动力 2：产品形态变化（聊天 → Workflow → Agent 自主探索）

### 2.2 控制权的转移

**课程原话（L18）**：
> "控制权从'写内容'转向'造环境'。"

**v3 体现**：
- Manager 的"GT 选择" = 给子 Agent "造环境"（哪个 GT 样本加载）
- 子 Agent 的"Memory 字段" = 子 Agent 的"工作环境"（团队 SOP + GT 库 + 历史反馈）
- v3 §3.1 Manager 的"decision_patterns.md" = "预加载关键索引"（Harness 范式）

### 2.3 Harness 范式常见误区

**课程纠正（L18）**：
> "Harness 时代不是'完全放手让模型自己搞'。现实中即使是最先进的 Claude Code，也依赖 CLAUDE.md 预加载项目结构、rules/ 预加载约束、MEMORY.md 前 200 行自动注入记忆索引。正确的理解是：**预加载关键索引 + 模型按需探索的混合模式**。"

**v3 反例避免**：
- v3 §3.1 Manager 5 个 Memory 文件不是"全部加载"，而是"按场景加载"
- v3 §3.4 ②'' 流程组的"GT 样本按子类加载"（approval_flows / state_machines / exception_patterns）= Harness 范式

## 3. 上下文治理：加法与减法（L18）

### 3.1 加法

**核心原则**：让模型知道它该知道的。

| 类别 | v3 体现 |
|------|--------|
| **静态知识** | 每个 Agent 的 Soul + NEVER + Skills 名册（v3 §3） |
| **动态上下文** | handoff 文件（v3 §4.3） / GT 样本（v3 §3.3 product_team/gt_samples_product/） |
| **历史反馈** | Manager 的 `decision_patterns.md`（"qa_report 命中 X → 派修订 Y"） |
| **运行时上下文** | 当前 MRD 文件路径 / 当前任务 ID / 当前 trace_id |

**加法原则**：
- 必要信息**不省略**（如 Soul + NEVER 必须在 system prompt 里）
- 加什么**先问"用不用得上"**（如 Manager 不需要产品级 GT 样本）

### 3.2 减法

**核心原则**：别让模型知道它不该知道的。

| 类别 | v3 体现 |
|------|--------|
| **过时上下文** | v3 §3.1 Manager `escalation_log.md` 只保留最近 30 条 |
| **冗余信息** | handoff 文件只列"接口契约"，不复制 PRD 全文（v3 §4.3 关键约束 ②） |
| **敏感信息** | v3 §6.2 L1/L2/L3 降级时不带敏感 token |
| **错误信息** | 子 Agent 失败时不暴露其他子 Agent 的中间产物 |

**减法原则**：
- **剪裁（prune）** 优先于 **压缩（compress）**——剪裁去掉整段，压缩用摘要替代
- **压缩有信息损失**——L19 强调"摘要意味着信息损失"
- **子 Agent 之间的产物不互相传递**——v3 §4.1 Owner 唯一原则

### 3.3 v3 上下文硬约束（v3 §1.3 关键设计原则 ③）

**v3 单 Agent 上下文 < 30K token**——避免 Context Rot（n² 注意力衰减）。

| Agent | 单次上下文 | 课程依据 |
|-------|----------|---------|
| Manager | 20K | L19 上下文生命周期 |
| ① MRD 结构化 | 8K | L19 剪裁：MRD 通常 5K，加 GT 样本 2K，加产物 1K |
| ② 产品组 | 15K | L19 PRD1+2 章节长，加 GT 5K |
| ②'' 流程组 | 8K | L19 流程图 + 旅程 8K |
| ②''' 数据组 | 7K | L19 数据模型 7K |
| ④ 页面组 | 15K | L19 PRD5 页面清单 + 状态 15K |
| ③ 质检 | 25K | L19 全文质检，但需剪裁 |

## 4. 上下文的生命周期（L19 核心）

### 4.1 三阶段

```
Bootstrap（启动）  →  Prune（剪枝）  →  Compress（压缩）
       ↓                  ↓                  ↓
   加载关键索引       去掉过时/冗余       用摘要替代原文
```

| 阶段 | v3 体现 |
|------|--------|
| **Bootstrap** | Manager 读 MRD（v3 §5 阶段 0） / 子 Agent 读 handoff 文件（v3 §4.3） |
| **Prune** | 子 Agent 写完产物后清空工具调用历史（v3 §6.2 L1 重试换种子） |
| **Compress** | Manager 收到子 Agent 产物后，提取关键字段存入 `decision_patterns.md` |

### 4.2 Bootstrap 的关键索引

**课程 L18 范例**：
- Claude Code 的 CLAUDE.md（项目结构）
- Claude Code 的 rules/（约束）
- Claude Code 的 MEMORY.md 前 200 行（记忆索引）

**v3 关键索引**：
- Manager 的 `sop_prd_team.md`（团队 SOP）
- Manager 的 `team_roster.md`（5 子 Agent 名册）
- 子 Agent 的 GT 索引（按子类加载）
- 子 Agent 的模板索引（`prd1_template.md` / `prd2_template.md` 等）

## 5. 文件系统记忆（L20 核心）

### 5.1 核心思想

**课程原话（L20）**：
> "让 Agent 自己写记忆、自己学技能。"

**机制**：
- Agent 完成一次任务后，把"决策 + 依据 + 结果"写入文件系统
- 下次同类任务时，先读历史记录再决策
- 形成"自我进化"闭环

### 5.2 v3 体现

| v3 字段 | 对应课程机制 |
|---------|------------|
| `manager/decision_patterns.md` | "qa_report 命中 X 模式 → 派修订 Y" 的历史决策库 |
| `manager/escalation_log.md` | 历史熔断记录（避免重蹈覆辙） |
| `product_team/history_clarifications.md` | ① 历史澄清记录（用户偏好） |
| `page_team/history_feedback.md` | ④ 历史 PRD5 反馈 |
| `qa_team/gt_bad_prds.md` | ③ 反面 GT（常见错误样本） |
| `qa_team/score_calibration.md` | ③ 评分校准记录 |

**v3 GT 沉淀机制**（v3 §10 风险 5 缓解）：
> "先 20 条 MVP 验证 → 后续每完成 1 个 PRD 沉淀 1 条"

### 5.3 文件即记忆 vs 数据库即记忆

| 形态 | 课程 L20 结论 | v3 选择 |
|------|------------|--------|
| **文件** | 可读 / 可版本控制 / 适合人协作 | ✅ v3 全部用文件（`workspace/`） |
| **数据库** | 高效检索 / 适合机器 | ❌ v3 未采用（初期成本不划算） |

## 6. 搜索驱动的记忆系统（L21 核心）

### 6.1 企业级海量记忆管理

**课程 L21 核心命题**：
- 记忆条目从 10 条到 1000+ 条时，**全量加载不可行**（超出上下文）
- 需要"按需检索"——RAG（检索增强生成）

### 6.2 v3 检索需求

| 检索对象 | 索引方式 | 更新频率 | 数据源 |
|---------|---------|---------|--------|
| **GT 样本** | 关键词匹配（行业 + 功能类型） | 每完成 1 PRD 沉淀 1 条 | `shared/gt_samples/` |
| **历史决策** | 全文检索（决策模式） | 每次 Manager 决策后 | `manager/decision_patterns.md` |
| **历史缺陷** | 关键词 + 类别 | 每次 ③ 出报告后 | `qa_team/defect_patterns.md` |
| **业务术语** | 字典查询 | ① 产出 glossary 后 | `breakdown/glossary.md` |

### 6.3 v3 检索工具规划

- **v3.0（当前）**：关键词匹配（GT 4 类独立库，v3 §9 决策 10）
- **v3.1（待）**：向量检索（接 L21 课程的"语义搜索"）
- **v3.2（待）**：图谱检索（实体关系 + 业务流程）

## 9. 关键方法论 takeaway

1. **记忆本质**：没有魔法，只有信息流设计——message list 里塞什么模型就"知道"什么
2. **三代演进**：Prompt（骑手）→ Context（教练）→ Harness（牧场主），控制权从"写内容"转向"造环境"
3. **Harness 范式本质**：预加载关键索引 + 模型按需探索（不是"完全放手"）
4. **加法原则**：必要信息不省略；加什么先问"用不用得上"
5. **减法原则**：剪裁优先于压缩；子 Agent 之间的产物不互相传递
6. **v3 硬约束**：单 Agent 上下文 < 30K token（避免 Context Rot）
7. **文件即记忆**：v3 用文件系统而非数据库（可读 / 可版本控制 / 适合人协作）
8. **检索策略**：v3.0 关键词匹配 → v3.1 向量检索 → v3.2 图谱检索
