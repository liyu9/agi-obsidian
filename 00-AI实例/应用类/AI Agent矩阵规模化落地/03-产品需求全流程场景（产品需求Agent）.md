# 产品需求全流程场景（产品需求Agent）— 详细设计

> **产品设计方法论映射**：本场景按照"需求验证三步法→成功指标4步法+反指标→数据驱动迭代"闭环设计
> 方法论来源：[[产品设计核心知识总结]]

---

## 1. 需求验证（三步法）

| 步骤 | 内容 |
|------|------|
| **确认用户** | 产品经理（PRD撰写者）、业务方需求提出者 |
| **痛点假设** | ①需求调研耗时长，从调研到MRD平均2-3天 ②PRD撰写重复性高，60%+为结构化重复劳动 ③方案质量参差不齐，缺乏统一标准 ④历史方案散落，无法复用 |
| **验证假设** | 单个需求从调研到PRD初稿平均3-5天；60%+内容为模板化重复撰写；企业方案库缺失导致知识无法传承 |

**用户问题说明**：作为产品经理，我想快速完成从需求调研到PRD输出的全流程，从而帮助我将更多时间投入需求深度思考而非重复撰写

---

## 2. 核心交付

- 实现需求调研到PRD输出全流程AI化，拆解为两阶段多Agent协作模式
- 建立企业方案库，实现方案自动更新与知识传承

---

## 3. 多Agent协作架构（Supervisor模式）

### 第一阶段：需求调研 → MRD生成

```
┌─────────────────────────────────────────┐
│  coordinator (kanban-orchestrator)       │
│  ├── analyst：需求收集+用户调研+拆解+排序  │
│  └── ai-pm：AI功能分析+技术路线判断       │
└─────────────────────────────────────────┘
```

| Agent | 角色 | 核心职责 |
|-------|------|---------|
| coordinator | kanban-orchestrator | 分解目标、分配任务、监控进度、整合结果 |
| analyst | kanban-worker | 需求收集、用户调研、需求拆解、优先级排序 |
| ai-pm | kanban-worker | 分析需求AI功能、判断技术路线、标记Agent适用性 |

### 第二阶段：PRD推导 → 方案输出

```
┌─────────────────────────────────────────┐
│  coordinator (kanban-orchestrator)       │
│  ├── agent-pm：智能体架构+工作流+Prompt   │
│  ├── planner：技术方案+实施计划+风险评估   │
│  └── advisor：编程指导+代码审查+最佳实践   │
└─────────────────────────────────────────┘
```

| Agent | 角色 | 核心职责 |
|-------|------|---------|
| coordinator | kanban-orchestrator | 分解目标、分配任务、监控进度、整合结果 |
| agent-pm | kanban-worker | 智能体架构设计、工作流编排、Prompt工程 |
| planner | kanban-worker | 技术方案、实施计划、架构设计、风险评估 |
| advisor | kanban-worker | 编程指导、代码审查、技术选型、最佳实践 |

### ai-pm 与 agent-pm 的接力逻辑

> 依据产品设计"侵蚀效应"原则：新Agent功能不应挤占原有产品成绩

```
ai-pm（AI产品经理）                    agent-pm（Agent产品经理）
  ├── 分析需求中AI部分                    ├── 设计Agent方案
  ├── 判断技术路线                        ├── 智能体架构+工作流
  └── RAG/Agent/微调选型                  └── Prompt+工具设计
           │                                      │
           └── "适合Agent实现"的判断 ──────────────┘
```

| Agent | 核心判断 | 输出 |
|-------|---------|------|
| ai-pm | 需求中哪些适合AI/Agent实现？技术路线选型 | AI需求分析报告 |
| agent-pm | Agent架构设计、工作流编排、Prompt工程 | Agent方案设计文档 |

## 4. PRD 5要素验证

> 参照成功指标4步法 + PRD 5要素框架

| PRD要素 | Agent场景映射 | 验证方法 |
|---------|-------------|---------|
| 痛点 | 需求调研效率低、文档质量不稳定 | 用户访谈+工时统计 |
| 论证痛点 | 当前调研→PRD初稿平均3-5天 | 历史数据对比 |
| 指标+反指标 | 初稿效率提升70%（正）/ PRD可用率≤60%需重写（反） | A/B测试 |
| 场景 | 需求调研→MRD→PRD→验收标准全链路 | 用例写法 |
| 功能方案 | 两阶段多Agent协作+企业方案库 | MVP验证 |

## 5. 企业方案库

**核心机制**：

| 能力 | 说明 | 价值 |
|------|------|------|
| 方案自动归档 | PRD完成后自动提取方案入库 | 减少知识散落 |
| 方案检索匹配 | 新需求自动匹配历史方案 | 提升复用率 |
| 方案自动更新 | 关联源文档变更时自动提醒更新 | 防止方案漂移 |
| 知识传承 | 新人可检索学习历史方案 | 降低上手成本 |

## 6. 成功指标体系（4步法 + 反指标）

**第一步：产品最高目标** → PRD初稿生成效率提升70%

**第二步：子指标分解**

| 类别 | 指标 | 当前值 | 目标值 |
|------|------|--------|--------|
| 效率 | PRD初稿生成效率 | 基线 | 提升70% |
| 效率 | 方案库复用率 | 0% | ≥40% |
| 质量 | 文档质量评分（人工抽检） | — | ≥4.0/5.0 |
| 质量 | 调研→MRD耗时 | 2-3天 | ≤4小时 |
| 质量 | MRD→PRD耗时 | 2-3天 | ≤1天 |

**第三步：功能与指标关系**

| 功能模块 | 影响指标 | 影响方向 |
|----------|---------|---------|
| 多Agent协作 | PRD初稿效率 | 正向，并行处理调研+撰写 |
| 企业方案库 | 复用率 | 正向，历史方案直接复用 |
| ai-pm→agent-pm接力 | 方案质量 | 正向，专业分工提升专业性 |
| 5步迭代机制 | 持续质量 | 正向，Bad Case驱动改进 |

**第四步：反指标（必须量化）**

| 反指标 | 安全阈值 | 降级策略 |
|--------|---------|---------|
| PRD可用率（无需重写） | ≥60% | <40%触发全面Review，检查Agent协作流程 |
| 方案库漂移率（过时方案占比） | ≤10% | >15%触发方案库全量校验 |
| 幻觉率（编造需求/数据） | ≤3% | >5%强制人工审核所有AI生成内容 |
| 侵蚀效应 | 监控 | 新Agent功能挤占原有产品成绩时触发评估 |

## 7. 京东商家智能助手Multi-Agent实践参考

**三层角色体系**：

```
领域专家（各种Agent）：具备决策能力+调度工具能力
  ↓
工具（服务能力接口API）：只执行不具备决策
  ↓
总管（Master Agent）：整体编排调度
```

**Master Agent ReAct循环**：

| 组件 | 说明 |
|------|------|
| Thought（思考） | 自然语言描述解题思路 |
| Action Code | 基于Thought解析的可执行指令 |
| Trust_Mode | 控制是否需要再推理 |
| Memory | 近远期特征存储 |

**架构优势**：
- 复杂生成任务拆解为多个层级化文本预测
- 模型规模不需要很大，减少训练部署资源
- 可灵活接入各种资源方
