# 企业 AI Copilot 成本估算与优化（GLM-4.7）

## 1. 背景与目标

主方案在 4.5 章节提到"运行半小时"的成本考量，但**未给出企业级 Copilot 形态下的完整成本估算与优化方案**。本专题用于：

- 给出 **2000 人企业 Copilot 形态** 的成本模型
- 对比 **不同模型档位与调用频次** 的成本区间
- 提供 **可落地的成本优化组合**（混合路由 + 缓存 + 熔断）
- 给出 **预算熔断与降级策略**

## 2. 适用场景与边界

- **适用**：企业内部 AI Copilot（飞书/钉钉/微信 嵌入办公）
- **不适用**：纯售前/售后客服（用主方案原数据）

## 3. 场景定义

| 维度 | 数值 | 说明 |
|---|---|---|
| **企业规模** | 2,000 人 | 题目给定 |
| **产品形态** | Copilot 模式 | 嵌入文档/问答/搜索 |
| **月活用户** | ≥ 1,600 人（80%） | Copilot 渗透率远高于客服机器人 |
| **人均日均调用** | 1-3 次 | 用户做文档、查资料时随时触发 |

| **月工作日** | 22 天 | 法定工作日 |

## 7. 成本优化策略

### 7.1 优化策略矩阵

| 策略 | 节省成本 | 实施难度 | 推荐度 |
|---|---|---|---|
| **上下文缓存** | 30-50% | 中 | ★★★★★ |
| **混合路由**（FlashX + Pro） | 30-50% | 中 | ★★★★★ |
| **关闭 thinking 默认值** | 30-50% | 低 | ★★★★ |
| **提示词精简** | 10-20% | 低 | ★★★★ |
| **RAG 检索片段压缩** | 10-15% | 中 | ★★★ |
| **重复问题合并** | 5-10% | 高 | ★★★ |
| **预算熔断 + 自动降级** | 防失控 | 低 | ★★★★★ |

### 7.2 推荐组合方案

```
基础成本（中位）= ¥90,288/月
├─ 启用缓存（命中率 50%）     → × 0.6 = ¥54,173
├─ 混合路由（80% FlashX）     → × 0.65 = ¥35,212
└─ 关闭 thinking 默认值        → 已包含在混合路由

最终成本 ≈ ¥30,000 - 50,000/月
```

> **优化后月成本可降低 50-67%**

## 8. 关键优化详解

### 8.1 上下文缓存

GLM-4.7 原生支持上下文缓存（[文档](https://docs.bigmodel.cn/cn/guide/capabilities/cache)），适用场景：

| 缓存场景 | 命中率 | 节省成本 |
|---|---|---|
| 系统提示缓存 | 100% | -10% |
| 知识库片段缓存 | 50-80% | -20-30% |
| 多轮对话历史缓存 | 30-50% | -5-10% |
| **合计** | **50-70%** | **-30-50%** |

**Copilot 形态特别适合缓存**：
- 同一用户多次提问引用相同产品资料
- 系统提示词相对固定
- 知识库片段重复使用率高

### 8.2 混合路由

```python
def route_to_model(question: str, complexity: int) -> str:
    """根据问题复杂度路由到不同模型"""
    if complexity < 3:
        return "glm-4.7-flashx"     # 80% 流量：¥0.03/次
    elif complexity < 7:
        return "glm-4.7"             # 15% 流量：¥0.086/次
    else:
        return "glm-4.7-thinking"    # 5% 流量：¥0.13/次
```

**复杂度评估维度**：
- 是否需多步推理
- 是否含代码生成
- 是否需联网搜索
- 用户是否标记"重要"或"复杂"

### 8.3 提示词精简

| 项 | 精简前 | 精简后 | 节省 |
|---|---|---|---|
| 系统提示 | 2,000 tokens | 800 tokens | -60% |
| RAG 检索 | 3,000 tokens | 1,500 tokens | -50% |
| 历史对话 | 2,000 tokens | 800 tokens | -60% |
| **合计** | **7,000 → 3,100** | — | **-56%** |

### 8.4 预算熔断与降级

```yaml
# 预算熔断规则
monthly_budget: 50000  # ¥50,000
warning_threshold: 0.8  # 80% 告警
downgrade_rules:
  - when: cost_ratio >= 0.8
    action: route_all_to_flashx  # 全部降级到 FlashX
  - when: cost_ratio >= 1.0
    action: disable_thinking + route_all_to_flashx  # 关闭 thinking
  - when: cost_ratio >= 1.2
    action: queue_non_priority + alert_admin  # 排队 + 告警
```

## 10. 落地步骤

1. **Week 1**：搭建 GLM-4.7 API 网关 + 启用上下文缓存
2. **Week 2**：实现混合路由（FlashX 默认 + Pro 升级）
3. **Week 3**：上线预算熔断 + 飞书/钉钉告警
4. **Week 4**：埋点 + 监控看板（参考 [04-指标体系](./04-指标体系与A-B实验.md)）
5. **Month 2**：优化提示词 + 知识库片段压缩
6. **Month 3**：评估是否私有化部署

## 11. 验证标准

- [ ] 月成本控制在 ¥50,000 以内
- [ ] 缓存命中率 ≥ 50%
- [ ] 80% 请求走 FlashX
- [ ] 预算熔断机制能 5 分钟内飞书告警

- [ ] 用户满意度 ≥ 4.0

## 12. 风险与对冲

| 风险 | 对冲 |
|---|---|
| 成本超预算 | 预算熔断 + 自动降级 + 飞书告警 |
| 缓存命中率不达标 | 监控 + 提示词/知识库结构优化 |
| FlashX 质量问题 | A/B 测试（命中率/满意度对比） |
| 启用 thinking 后成本爆炸 | 默认关闭，复杂任务按需开启 |
| API 限流 | 多区域部署 + 队列削峰 |
| 私有化部署成本失控 | 先 API 跑通，再评估是否私有化 |
