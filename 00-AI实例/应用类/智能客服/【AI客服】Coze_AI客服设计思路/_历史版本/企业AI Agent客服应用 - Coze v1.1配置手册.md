# 企业AI Agent客服应用 - Coze v1.1 配置手册

> **版本**：v1.1 | **平台**：Coze 扣子（对话流 Chatflow）
> **目标**：按本手册逐步操作，可在 Coze 中完整搭建 AI 客服系统

---

## v1.1 迭代内容

> 相比 v1.0 的主要改动：

| 迭代项 | v1.0 | v1.1 |
|-------|------|------|
| 低置信度处理 | 直接转人工 | 追问用户补充意图 |
| 分支路由 | 2 分支 + 否则 | 3 分支 + 否则 |
| 意图识别 Prompt | 低置信度改 intent 为 non_service | 置信度仅作参考，不改变分类结果 |
| 新增节点 | 无 | 意图澄清（输出节点） |
| 审核重试 | 无 | 审核不通过最多重试 1 次 |
| 节点总数 | 14 个 | 16 个 |

**核心优化**：

1. **低置信度追问机制**：意图识别置信度过低时，不再直接转人工，而是追问用户补充描述，提升自动解决率
2. **审核重试机制**：答案审核不通过时，自动重试 1 次重新生成答案，仍不通过才转人工
3. **意图分类扩展**：product_inquiry 范围扩大，覆盖订单物流、售后服务等

## 第一步：创建对话流

### 1.1 进入 Coze 平台

1. 打开 [coze.cn](https://www.coze.cn)，登录账号
2. 进入**工作空间**（左侧边栏选择你的团队/个人空间）

### 1.2 创建智能体

1. 点击左侧**「智能体」**菜单
2. 点击**「创建智能体」**按钮
3. 填写基本信息：
   - **名称**：`在线客服`（可自定义）
   - **描述**：`企业智能客服，自动回答产品咨询、订单物流、售后政策等常见问题`
4. 点击**「创建」**

### 1.3 创建对话流

1. 进入刚创建的智能体 → 点击**「对话流」**标签页
2. 点击**「创建对话流」**
3. 输入名称：`客服主流程`
4. 点击**「确认」**，进入对话流编辑器

> 进入编辑器后，画布中央会自动出现一个**「开始」**节点和一个**「结束」**节点。

## 第二步：创建知识库

> 在配置节点之前，先创建好知识库，后续知识库检索节点需要绑定。

### 2.1 创建产品知识库

1. 点击左侧**「知识库」**菜单（或进入「资源库」→「知识库」）
2. 点击**「创建知识库」**
3. 填写信息：
   - **名称**：`产品知识库`
   - **描述**：`商品信息、功能介绍、规格参数、使用方法等`
4. 点击**「创建」**
5. 进入知识库 → 点击**「添加文件」** → 上传产品相关文档（Markdown/TXT/Word）
6. 等待文件解析完成

### 2.2 创建 FAQ 知识库

1. 重复上述步骤，创建第二个知识库：
   - **名称**：`FAQ知识库`
   - **描述**：`常见问题与标准答案`
2. 上传 FAQ 问答文档

### 2.3 知识库内容格式要求

上传的文档建议使用以下格式（一问一答结构）：

```
Q: 这个产品支持什么支付方式？
A: 我们目前支持微信支付、支付宝、银行卡支付、花呗/京东白条分期。

Q: 退货流程是什么？
A: 退货流程：1. 进入「我的订单」→ 找到对应订单 2. 点击「申请退货」→ 选择退货原因 3. 等待审核通过 → 寄回商品 4. 确认收货后退款到原支付账户。
```

> **提示**：每个 Q&A 之间用空行分隔，便于 Coze 自动分段。

3. **添加输入参数**：
   - 点击**「添加输入参数」**
   - 参数名：`question`，类型：String
   - 变量引用：点击右侧 `{{}}` 按钮 → 选择 `USER_INPUT`

4. **粘贴代码**（在代码编辑区域）：

> ⚠️ **Coze Python 代码节点格式要求**：
> - 入口函数必须为 `async def main(args: Args) -> Output:`
> - 通过 `args.params` 获取输入参数
> - 输出变量必须命名为 `ret`，类型注解为 `Output`
> - `args` 由平台自动注入，不要 import 或重新定义

```python
async def main(args: Args) -> Output:
```

### 节点 3：意图识别（大模型节点）

**创建方式**：点击画布空白处 → 选择**「大模型」**节点 → 拖入画布

**步骤**：

1. **重命名节点**：改为 `意图识别`

2. **选择模型**：
   - 模型：选择 **豆包 Lite**（或任意 7B 级别小模型）

3. **模型参数设置**：
   - **温度（Temperature）**：设为 **0.1**（确保分类稳定）
   - **最大输出长度**：500 tokens

4. **输出格式**：
   - 选择 **JSON**

5. **JSON 样例配置**：
   - 在输出格式区域，点击**「添加字段」**或导入样例
   - 添加以下 3 个字段：

| 字段名 | 类型 | 说明 |
|-------|------|------|
| `intent` | String | 意图分类 |
| `confidence` | Number | 置信度 |
| `key_info` | Array | 关键信息 |

   - 或直接粘贴 JSON 样例：
   ```json
   {
     "intent": "product_inquiry",
     "confidence": 0.92,
     "key_info": ["iPhone 16 Pro", "颜色"]
   }
   ```

6. **添加输入参数**：
   - 参数名：`question`，类型：String
   - 变量引用：`{{USER_INPUT}}`

7. **系统提示词**（System Prompt）：

```
你是电商客服意图识别专家。你的任务是分析用户的问题，判断其意图分类，并提取关键信息。

## 意图分类体系

1. product_inquiry - 产品咨询（商品信息、功能介绍、规格参数、使用方法、订单物流、售后服务等）
2. chitchat - 闲聊寒暄（打招呼、感谢、再见、闲聊等非业务对话）
3. non_service - 非客服问题（与产品和服务完全无关的请求，如写代码、做PPT、翻译文档等）

## 分类规则

- "你好""谢谢""在吗""再见""辛苦了" → chitchat
- "今天天气怎么样""讲个笑话""你叫什么" → chitchat
- "帮我写代码""帮我做PPT""帮我翻译" → non_service
- 与产品、订单、售后、支付、物流相关 → product_inquiry
- 拿不准时，优先归为 product_inquiry

## 输出要求

请以 JSON 格式输出，包含以下字段：
- intent: 意图分类（使用上述英文标识）
- confidence: 置信度分数（0-1之间的小数）
- key_info: 提取的关键信息数组（如商品名称、订单号、错误描述等）

## 注意事项

- 如果用户消息包含指代词（如"那个"、"这个"），请结合对话历史理解其含义
- 置信度仅作为参考，不要因为置信度低就改变意图分类结果
- 即使不确定，也要给出最可能的意图分类
- key_info 中提取的信息应尽量具体，便于后续知识库检索
```

8. **用户提示词**（User Prompt）：

```
请分析以下用户问题：

用户问题：{{question}}

请输出 JSON 格式的意图识别结果。
```

9. **会话历史**：
   - 找到**「会话历史」**或**「智能体会话历史」**开关 → **开启**

10. **异常处理**：
    - 找到**「异常处理」**配置
    - 选择**「返回设定内容」**
    - 设定内容：
    ```json
    {
      "intent": "non_service",
      "confidence": 0,
      "key_info": []
    }
    ```

### 节点 4：分支路由（选择器节点）

**创建方式**：点击画布空白处 → 选择**「选择器」**（或叫**「条件分支」**）节点 → 拖入画布

**步骤**：

1. **重命名节点**：改为 `分支路由`

2. **配置分支条件**：

   **分支 1**（闲聊寒暄 → 通用回复）：
   - 点击**「添加条件」**创建第一个分支
   - 条件：
     - 左值：点击 `{{}}` → 选择 `意图识别.intent`
     - 运算符：**等于（==）**
     - 右值：输入 `chitchat`
   - 该分支含义：打招呼、感谢等 → 简短回复

   **分支 2**（置信度过低 → 追问用户）：
   - 点击**「添加条件」**创建第二个分支
   - 条件：
     - 左值：选择 `意图识别.confidence`
     - 运算符：**小于（<）**
     - 右值：输入 `0.5`
   - 该分支含义：意图不够明确 → 追问用户补充描述

   **分支 3**（超出能力范围 → 告知能力）：
   - 点击**「添加条件」**创建第三个分支
   - 条件：
     - 左值：选择 `意图识别.intent`
     - 运算符：**等于（==）**
     - 右值：输入 `non_service`
   - 该分支含义：写代码、做PPT等 → 告知能力范围

   **分支 4**（产品咨询 → 正常流程）：
   - 点击**「添加条件」**创建第四个分支
   - 条件：
     - 左值：选择 `意图识别.intent`
     - 运算符：**等于（==）**
     - 右值：输入 `product_inquiry`
   - 该分支含义：产品咨询 → 走知识库检索

   **否则分支**（兜底 → 转人工）：
   - 默认已存在，无需手动创建
   - 含义：以上条件都不满足 → 走人工引导

> **分支优先级说明**：Coze 选择器节点按分支创建顺序从上到下匹配，先匹配到的分支生效。分支顺序：闲聊 → 低置信度 → 超出能力 → 产品咨询 → 兜底。

### 节点 4.5：意图澄清（输出节点）

> **新增节点**：当意图识别置信度过低时，追问用户补充描述。

**创建方式**：点击画布空白处 → 选择**「输出」**（或叫**「消息」**）节点 → 拖入画布

**步骤**：

1. **重命名节点**：改为 `意图澄清`

2. **配置输出内容**：
   ```
   不好意思，没太理解您的意思，您是想问：
   - 产品相关（价格、尺码、材质等）
   - 订单物流（发货、退货、快递等）
   - 售后服务（发票、保修等）
   可以具体说一下吗？
   ```

3. **流式输出**：设为**关闭**

4. **会话历史写入**：设为**写入**

   > **重要**：必须设为「写入」，这样下一轮用户回复时，意图识别节点能看到追问的上下文，结合用户补充的描述进行更准确的意图识别。

5. **下游连接**：意图澄清 → 回复输出

   > **说明**：输出节点执行后，流程必须到达结束节点。意图澄清输出追问消息后，连接到回复输出（结束节点），本轮对话结束。用户补充描述后，下一轮消息会重新从「用户消息输入」开始走完整流程。

---

### 节点 4.6：通用回复（输出节点）

> 用于处理闲聊/寒暄类消息，给一个自然的简短回复。

1. **添加节点**：点击**「+」** → 选择**「消息节点」**（Message Node）

2. **重命名节点**：改为 `通用回复`

3. **配置输出内容**：
   ```
   有什么可以帮您的？
   ```

4. **流式输出**：设为**关闭**

5. **会话历史写入**：设为**不写入**（寒暄不需要记入历史）

---

### 节点 4.7：能力引导（输出节点）

> 用于处理超出能力范围的问题，告知用户 agent 能做什么，引导回业务。

1. **添加节点**：点击**「+」** → 选择**「消息节点」**（Message Node）

2. **重命名节点**：改为 `能力引导`

3. **配置输出内容**：
   ```
   这个我帮不了，我主要能帮您解答产品相关的问题，比如：
   - 产品信息（价格、尺码、材质等）
   - 订单物流（发货、退货、快递等）
   - 售后服务（发票、保修等）
   有需要的话可以问我。
   ```

4. **流式输出**：设为**关闭**

5. **会话历史写入**：设为**不写入**

---

### 节点 5：转接原因生成（代码节点）

**创建方式**：点击画布空白处 → 选择**「代码」**节点 → 拖入画布

**步骤**：

1. **重命名节点**：改为 `转接原因生成`

2. **选择语言**：Python

3. **添加输入参数**（共 3 个）：

| 参数名 | 类型 | 变量引用 |
|-------|------|---------|
| `n3_intent` | String | `{{意图识别.intent}}` |
| `n3_confidence` | Number | `{{意图识别.confidence}}` |
| `n7_reason` | String | `{{答案审核.reason}}` |

   > **注意**：`n7_reason` 引用了「答案审核」节点的输出。在首次配置时，答案审核节点可能尚未创建，变量引用可能显示为红色。这是正常的，后续创建答案审核节点后会自动关联。

4. **粘贴代码**：

```python
async def main(args: Args) -> Output:
    params = args.params
    n3_intent = params.get('n3_intent', '')
    n3_confidence = params.get('n3_confidence', 0)
    n7_reason = params.get('n7_reason', '')

    # 如果答案审核已执行（有审核原因），使用审核原因
    # 否则根据意图识别结果生成默认原因
    if n7_reason:
        reason = n7_reason
    elif n3_intent == 'non_service':
```

### 节点 10.5：重试判断（代码节点）

> **新增节点**：用于判断答案审核不通过时是否已经重试过，防止无限循环。

**创建方式**：点击画布空白处 → 选择**「代码」**节点 → 拖入画布

**步骤**：

1. **重命名节点**：改为 `重试判断`

2. **选择语言**：Python

3. **添加输入参数**（共 2 个）：

| 参数名 | 类型 | 变量引用 | 说明 |
|-------|------|---------|------|
| `approved` | Boolean | `{{答案审核.approved}}` | 审核是否通过 |
| `is_retry` | Boolean | `{{重试判断.is_retry}}` | 是否已重试（首次为空/False） |

   > **注意**：`is_retry` 引用了自身节点的输出。在 Coze 中，首次执行时该变量为空（False），重试时为上一次的输出值（True）。如果 Coze 不支持自引用，可改用答案生成节点的执行次数或其他方式判断。

4. **粘贴代码**：

```python
async def main(args: Args) -> Output:
    params = args.params
    approved = params.get('approved', False)
    is_retry = params.get('is_retry', False)

    # 如果审核通过，不需要重试
    if approved:
        ret: Output = {
            "is_retry": False,
            "need_retry": False
        }
        return ret

    # 如果审核不通过且尚未重试，标记需要重试
    if not is_retry:
        ret: Output = {
            "is_retry": True,
            "need_retry": True
        }
        return ret

    # 已经重试过仍然不通过，不再重试
    ret: Output = {
        "is_retry": True,
        "need_retry": False
    }
    return ret
```

5. **确认输出参数**：

| 参数名 | 类型 | 说明 |
|-------|------|------|
| `is_retry` | Boolean | 是否已经重试过 |
| `need_retry` | Boolean | 是否需要重新生成答案 |

### 节点 11：满意度判断（选择器节点）

**创建方式**：点击画布空白处 → 选择**「选择器」**节点 → 拖入画布

**步骤**：

1. **重命名节点**：改为 `满意度判断`

2. **配置分支条件**：

   **分支 1**（审核通过 + 有知识库支撑 → 直接回复）：
   - 条件组合模式选择 **AND**
   - 条件 A：
     - 左值：`{{答案审核.approved}}`
     - 运算符：**等于（==）**
     - 右值：`true`
   - 条件 B：
     - 左值：`{{命中判断.has_knowledge_hit}}`
     - 运算符：**等于（==）**
     - 右值：`true`

   **分支 2**（审核不通过 + 未重试 → 重新生成答案）：
   - 条件组合模式选择 **AND**
   - 条件 A：
     - 左值：`{{重试判断.need_retry}}`
     - 运算符：**等于（==）**
     - 右值：`true`
   - 条件 B：
     - 左值：`{{答案审核.approved}}`
     - 运算符：**等于（==）**
     - 右值：`false`

   **分支 3**（审核不通过 + 已重试 → 引导人工）：
   - 条件：
     - 左值：`{{重试判断.need_retry}}`
     - 运算符：**等于（==）**
     - 右值：`false`

   **否则分支**（兜底 → 引导人工）：
   - 默认已存在

> **重试机制说明**：审核不通过时，如果尚未重试过（`need_retry=true`），流程会回到「答案生成」节点重新生成答案，然后再走一遍答案审核。如果重试后仍然不通过（`need_retry=false`），才走转人工路径。**最多重试 1 次，防止无限循环。**

| 7 | 多轮对话 | 先问"羽绒服"，再问"那个多少钱" | 结合上下文理解"那个" |
| 8 | 意图澄清 | 输入模糊短句如"那个呢" | 追问用户补充描述 |
| 9 | 意图澄清后补充 | 追问后回复"羽绒服的价格" | 正常返回产品价格 |
| 10 | 审核重试（首次不通过） | 触发审核不通过的场景 | 自动重试1次生成新答案 |
| 11 | 审核重试（两次不通过） | 连续触发审核不通过 | 重试1次后仍不通过，引导人工 |

### 5.3 调试技巧

- **查看节点执行结果**：点击已执行的节点，可查看该节点的输入和输出
- **查看变量值**：将鼠标悬停在变量引用上，可看到当前值
- **单步调试**：在预览时，每个节点会按顺序高亮显示执行状态

## 常见问题解答

### Q1：为什么没有「查询会话历史」节点？

v1.0 相比完整版（v2.0）精简了独立的「会话上下文加载」节点。原因是：**对话流（Chatflow）的大模型节点原生支持读取对话历史**。

只需在「意图识别」和「答案生成」节点中**开启「智能体会话历史」开关**，历史对话就会自动作为上下文传递给模型，无需额外配置。这比 v2.0 用独立节点查询会话历史更简洁高效。

---

### Q2：缓存匹配后如何分流到不同路径？

代码节点本身不支持条件分支输出（不能根据结果走不同的出口）。因此需要在「高频缓存匹配」后面加一个**「缓存判断」选择器节点**：

```
高频缓存匹配 → 缓存判断（选择器）
                  ├── is_cached == true → 回复输出（直接返回缓存答案）
                  └── is_cached == false → 意图识别（继续走完整流程）
```

这个设计在手册第四步「连接节点」中有详细说明。

---

### Q3：什么是前缀缓存？

前缀缓存（Prefix Cache）是 Coze 大模型底层的一种**性能优化机制**（LLM KV Cache），用于加速重复前缀的推理速度。这是平台自动处理的，**不需要你配置任何东西**，与业务流程无关，可以忽略。

---

### Q4：置信度（confidence）是什么？阈值怎么设？

置信度是意图识别模型对分类结果的**把握程度**，范围 0-1：
- **0.8-1.0**：模型很确定分类正确
- **0.5-0.8**：模型基本确定，但有一定犹豫
- **< 0.5**：模型不太确定

当前设计：置信度 < 0.5 时，将意图设为 `non_service`，走转人工路径。这个阈值可以根据实际效果调整：
- 如果发现很多正常问题被误判为非客服 → **降低阈值**（如 0.3）
- 如果发现很多无关问题被误判为产品咨询 → **提高阈值**（如 0.6）

---

### Q5：异常处理有什么用？

异常处理是 Coze 大模型节点的**兜底机制**，当 LLM 调用失败时触发。常见触发场景：
- 模型服务超时
- 模型服务不可用（平台故障）
- 输出格式不符合要求（如要求 JSON 但输出了纯文本）

**意图识别的异常处理**：返回默认 JSON `{"intent": "non_service", "confidence": 0, "key_info": []}`，确保流程走到转人工路径，而不是卡住报错。

**答案生成的异常处理**：返回纯文本 `抱歉，系统繁忙，请稍后再试`，这段文本会自动作为 `answer` 输出给用户。

**答案审核的异常处理**：设为「中断流程」，审核失败不重试，直接走异常处理。

---

### Q6：答案生成异常处理为什么只填纯文本，不定义输出函数？

答案生成节点的输出格式是**文本（Text）**，不是 JSON。在文本输出模式下，异常处理返回的纯文本会**自动赋值给输出变量 `answer`**，不需要手动定义函数或指定输出格式。

简单理解：正常时模型生成文本 → 赋值给 `answer`；异常时平台把设定内容 → 赋值给 `answer`。两种情况下游节点拿到的都是 `answer` 变量，处理逻辑一致。

## 常见问题排查

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| 知识库检索无结果 | 知识库未绑定或内容为空 | 检查知识库检索节点，确认已勾选知识库并上传了文档 |
| 意图识别结果不准确 | 模型选择错误或温度过高 | 确认使用豆包 Lite 7B，温度设为 0.1 |
| 回复内容编造信息 | 知识库内容不足 | 补充知识库文档，检查答案生成 Prompt 中的约束 |
| 变量引用显示红色 | 引用的节点尚未创建 | 先完成所有节点创建，变量会自动关联 |
| 缓存匹配不生效 | 代码中关键词与用户输入不匹配 | 检查 cacheRules 中的关键词，确保覆盖常见表述 |
| 选择器分支未触发 | 条件值类型不匹配 | 确认条件值的类型（String/Boolean/Number）与变量类型一致 |
| 流式输出不生效 | 结束节点配置错误 | 确认结束节点为"返回文本"模式，流式输出已开启 |
| 进度反馈出现在对话历史中 | 会话历史写入未关闭 | 确认进度反馈和联系方式引导节点的"会话历史写入"设为"不写入" |
