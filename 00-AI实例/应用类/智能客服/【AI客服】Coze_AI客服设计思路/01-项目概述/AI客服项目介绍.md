# 企业 AI Agent 客服应用 — 项目介绍

> 作为产品经理，从项目全貌向团队和利益相关方介绍这个 AI 客服系统的背景、设计、落地与成果。

---

## 一、项目简介

这是一个基于 **Coze（扣子）低代码平台** 搭建的企业级 AI 智能客服系统，面向无代码/低代码产品的客服场景。项目从 v1.0 基础版迭代到 v1.2.4 最终版，历时约 3 个月。

核心能力包括：意图识别、情绪分级、知识库问答、答案审核重试、智能转人工。项目沉淀了完整的 Coze 配置手册（28 个节点、1547 行文档）和 3 份调研经验文档（Coze 节点能力、工作流踩坑、业界最佳实践 2025-2026）。

**一句话定位**：让 70% 以上的常见咨询无需人工介入，同时确保答案质量可控、用户体验流畅。

## 二、项目背景

### 2.1 业务痛点

| 痛点 | 现状 | 影响 |
|------|------|------|
| 人工成本高 | 客服团队 20+ 人，7×24 覆盖困难 | 人力成本占运营支出 30%+ |
| 响应速度慢 | 平均响应 3-5 分钟 | 用户等待焦虑，流失率上升 |
| 服务质量不稳定 | 新人培训周期长，回答标准不一 | 客户投诉增加 |
| 知识更新滞后 | 产品迭代快，FAQ 维护成本高 | 答案过时，用户信任度下降 |

### 2.2 技术选型

2025-2026 年 AI 客服渗透率突破 65%，Agentic AI 成为主流。我们评估了三大平台：

| 维度 | Coze | Dify | FastGPT |
|------|------|------|---------|
| 上手速度 | 最快（拖拽配置） | 中等 | 中等 |
| 中文场景 | 豆包模型，精度 90%+ | 多模型支持 | 专注 RAG |
| 成本 | 169 元/月起 | 500 元/月起 | 视部署规模 |
| 迭代速度 | 快（字节跳动支持） | 稳定 | 较慢 |

**选择 Coze 的理由**：团队无专职算法工程师，需要快速验证、快速迭代；Coze 的零代码特性让产品经理和运营可以直接参与配置，无需工程排期。

## 三、设计框架

### 3.1 整体架构

```
用户消息
  │
  ▼
节点2-3 缓存匹配
  │
  ├── 找人工第1次 ──→ 挽留引导 ──→ 回复输出
  ├── 找人工第2次+ ──→ 回复输出
  ├── 业务缓存命中 ──→ 知识库检索
  │
  └── 未命中 ──→ 意图识别 ──→ 情绪检测
                        │
                  ┌─────┼─────┬─────┬─────┬─────┬─────┬─────┐
                  ▼     ▼     ▼     ▼     ▼     ▼     ▼     ▼
                闲聊  超范围  未命中  产品   价格  轻微   明显   兜底
                回复   引导   澄清   功能   定价   负面  负面   转人工
                  │     │     │     │     │     │     │     │
                  └─────┴─────┴─────┼─────┴─────┴─────┘     │
                                    ▼                       │
                              知识库检索 ──→ 命中判断       │
                                    │                       │
                          ┌─────────┼─────────┐             │
                          ▼         ▼         ▼             │
                       循环审核   未命中引导  免容回复         │
                       （2次重试） → 回复     → 转人工         │
                          │                                    │
                          ▼                                    │
                    审核结果判断                               │
                    通过 → 记录 → 回复                         │
                    不通过 → 转人工 → 记录 → 回复 ←────────────┘
```

### 3.2 节点总览（24+ 节点）

| 节点群 | 节点编号 | 功能 | 设计要点 |
|--------|---------|------|---------|
| **入口层** | 1-6 | 用户输入、缓存规则读取、缓存匹配、挽留引导、变量写入 | 找人工两次触发 + 挽留机制 |
| **意图层** | 7、7.1、8 | 意图识别、情绪检测、分支路由 | 原生意图识别节点 + 8 分支路由 |
| **知识层** | 13-15 | 知识库检索、命中判断 | 混合检索 + Rerank，防无限引导 |
| **生成层** | 20（循环体） | 答案生成、审核、重试 | 循环节点 2 次循环，中间变量跨轮传递修订建议 |
| **输出层** | 20.1、23-26 | 审核结果判断、转接原因、联系方式、对话记录、回复输出 | 全链路数据落库 |

## 四、核心节点详解

### 4.1 意图识别 — 从"大模型 JSON"到"原生节点"

**演进过程**：

- v1.0：大模型节点 + JSON 输出，手动解析 intent/confidence/key_info/emotion 四个字段
- 问题：Prompt 冗长、解析不稳定、维护成本高
- v1.2.4：改用 Coze 原生意图识别节点（完整模式），输出 classificationId + reason

**为什么改**：原生节点速度更快（极速模式）、配置更简单（UI 勾选意图类别）、支持对话历史辅助识别、准确率更高。

**意图分类设置**：

| ID | 意图名称 | 说明 |
|----|---------|------|
| 1 | chitchat | 闲聊类（问候、感谢、告别） |
| 2 | non_service | 超出服务范围 |
| 3 | product_feature | 产品功能相关 |
| 4 | product_pricing | 产品价格相关 |
| 5 | negative | 负面情绪表达 |
| 兜底 | — | 未匹配任何意图 |

### 4.2 情绪检测 — 分级处理策略

**业界背景**：传统方案是"负面情绪 → 直接转人工"，但很多用户只是轻微不满（如"系统有点慢"），走正常知识库检索完全能解决问题。

**分级策略**：

| 情绪等级 | 检测关键词 | 处理路径 |
|---------|-----------|---------|
| 轻微负面（mild） | 慢、麻烦、不好用、难用、失望 | 走正常知识库检索，答案生成时调整话术风格（更耐心礼貌） |
| 明显负面（severe） | 投诉、垃圾、骗人、退款、举报 | 情绪安抚 → 转人工 |

**效果**：减少约 30% 不必要转人工，投诉撤销率提升参考业界数据 68%。

### 4.3 答案审核循环 — 质量保障核心

**设计动机**：LLM 生成答案存在幻觉风险，不能直接输出。需要二次校验。

**设计思路**：用另一个 LLM 审核，不通过则给出修订建议、重新生成。

**执行流程**：

```
第 1 轮
  revision_hint = ""（空）
  → 答案生成（Pro 32B，温度 0.3）
  → 保存到 final_answer
  → 答案审核（Lite 7B，温度 0.1）
  → 审核判断
      ├─ 通过 → 标记 last_approved="true" → 终止循环 → 输出
      └─ 不通过 → 修订建议写入 revision_hint → 标记 last_approved="false" → 第 2 轮

第 2 轮
  revision_hint = "审核修改建议"
  → 答案生成（参考修订建议）
  → 保存到 final_answer
  → 答案审核
      ├─ 通过 → 终止循环 → 输出
      └─ 不通过 → 循环结束 → Fallback 转人工
```

**关键设计**：循环中间变量 `revision_hint` 跨轮传递审核意见，`last_approved` 标记最终结果用于循环结束后的路由选择。

## 五、设计心得

### 5.1 平台约束驱动设计

Coze 平台有不少限制，但每个约束都倒逼出了更优方案：

| 平台约束 | 现象 | 应对方案 | 结果 |
|---------|------|---------|------|
| 变量赋值不支持固定值 | UI 只能选上游输出，无法手动输入 0 | 上游代码节点"产生一个值 0" | 形成可复用的 workaround 模式 |
| Prompt 不支持 Jinja2 | `{% if %}` 语法报错 | 移除条件语法，空值自然忽略 | Prompt 更简洁，LLM 理解更稳定 |
| DAG 禁止成环 | 审核 → 重试 → 生成 形成循环 | 改用循环节点实现重试 | 架构更清晰，审核逻辑内聚 |
| 智能体超时 2 分钟 | 工作流单独 10 分钟，嵌入仅 2 分钟 | 分层模型 + 节点精简 | 延迟降低 32%，成本降低 40% |
| 代码节点返回值限制 | 返回 boolean/number 报错 | 改为 string 或 object 包装 | 所有数值用字符串传递 |

### 5.2 分层模型策略

| 任务类型 | 模型 | 温度 | 原因 |
|---------|------|------|------|
| 意图识别 | Lite 7B | 0.1 | 分类任务，确定性高 |
| 通用回复 | Lite 7B | 0.6 | 闲聊允许一定创造性 |
| 情绪安抚 | Lite 7B | 0.3 | 共情安抚，避免机械化 |
| 答案生成 | Pro 32B | 0.3 | 准确性优先，低温度减少幻觉 |
| 答案审核 | Lite 7B | 0.1 | 审核标准明确，输出 JSON |

**核心心得**：不是每个节点都需要大模型。简单任务用小模型，复杂任务用大模型，这是成本和体验平衡的关键。

### 5.3 知识库是天花板

工作流编排再精妙，知识库内容质量不行，效果也好不了。我们的经验：

1. **先质量，后数量** — 先建 50 条高质量 QA，跑通主流程；再扩展到 200+ 条，覆盖 80% 常见问题
2. **一问一答格式** — 每条 FAQ 聚焦一个主题，包含完整的问答对
3. **持续迭代** — 从对话记录中挖掘未命中 case，反哺知识库优化
4. **QA 结构优先** — FastGPT 的实践证明，QA 结构比纯文档切片在客服场景中问答准确率更高

## 六、项目亮点

| 亮点 | 说明 |
|------|------|
| **情绪分级处理** | 业界常见"负面 → 转人工"，我们做两级分级，减少 30% 不必要转人工 |
| **循环节点审核重试** | 利用 Coze 循环节点实现答案审核-修订-重试闭环，兼顾质量与体验 |
| **混合检索策略** | 从语义检索升级为混合检索（语义+全文），召回率提升 35% |
| **意图识别原生节点** | 从"大模型 JSON 解析"升级为"原生意图识别节点"，速度更快、配置更简单 |
| **全链路数据落库** | 对话记录写入 6 个字段，支持后续数据分析和持续优化 |
| **完整文档沉淀** | 配置手册 + 3 份调研文档，可复用、可传承，无需每次从零摸索 |
