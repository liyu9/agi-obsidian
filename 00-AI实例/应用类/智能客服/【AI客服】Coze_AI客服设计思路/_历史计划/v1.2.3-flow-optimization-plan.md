# v1.2.3 流程优化计划

## 概述

对 v1.2.2 配置手册进行流程优化，目标：减少节点数量、修复逻辑漏洞、提升用户体验。当前 30 个节点优化为约 22 个。

## 当前状态

- 文件：`/workspace/企业AI Agent客服应用 - Coze v1.2.2配置手册（低代码平台）.md`
- 节点数：30 个
- 主要问题：节点过多、进度反馈多余、找人工计数无重置、命中判断+选择器可合并、答案审核 ROI 低

## 优化项清单（8 项）

### 优化 1：删除进度反馈节点（P0）

**问题**：节点 13（进度反馈）在知识库检索前输出"正在查询，请稍等"，增加一次回复延迟。知识库检索本身 0.2-0.5s，用户感知不到明显延迟。

**改动**：
- 删除节点 13（进度反馈）
- 分支路由分支 5/6（product_feature / product_pricing）直接连接到 FAQ 知识库检索
- 缓存判断分支 3（业务缓存命中）直接连接到 FAQ 知识库检索
- 更新所有引用（连接关系表、流程图、速查表、数据流向）
- 节点数：30 → 29

### 优化 2：找人工计数重置机制（P0）

**问题**：`transfer_cnt` 只增不减。用户被挽留后正常咨询了多轮业务问题，再次找人工时 `transfer_cnt` 已是 1，直接给联系方式，没有再挽留。

**改动**：
- 在答案生成节点的代码之后（或回复输出之前），增加重置逻辑
- 实现方式：在回复输出节点之前新增一个"重置找人工计数"代码节点，当 `is_hit` 不等于 "transfer" 时，将 `transfer_cnt` 重置为 "0"
- 或者更简单：在缓存匹配代码中，当匹配到非找人工规则时，输出 `transfer_cnt` 为 "0"（重置）
- 推荐第二种方式（在缓存匹配代码中处理），不增加节点

**具体实现**：修改缓存匹配代码，在匹配到业务缓存（is_hit="cached"）或未命中（is_hit="none"）时，`transfer_cnt` 输出为 "0"：

```python
# 未命中
ret: Output = {
    "is_hit": "none",
    "boost_query": "",
    "transfer_cnt": "0"  # 重置找人工计数
}
return ret
```

同理，业务缓存命中时也输出 `"0"`。只有找人工时才 +1。

### 优化 3：双知识库合并为单节点检索（P1）

**问题**：FAQ 检索 → FAQ 命中判断 → FAQ 命中判断选择器 → 产品知识库检索 → 产品命中判断 → 产品命中判断选择器，共 6 个节点。Coze 知识库检索节点支持同时勾选多个知识库。

**改动**：
- 合并节点 14（FAQ知识库检索）和节点 17（产品知识库检索）为 1 个"知识库检索"节点
- 该节点同时勾选 FAQ 知识库 + 产品知识库
- 删除节点 14、15、16、17、18、19（6 个节点）
- 新增 1 个"知识库检索"节点 + 1 个"命中判断"代码节点 + 1 个"命中判断选择器"选择器节点
- 命中判断代码：检查 outputList 是否有结果，有则 has_knowledge_hit=true
- 节点数：29 → 24

### 优化 4：命中判断+选择器合并（P1）

**问题**：命中判断（代码节点）和命中判断选择器（选择器节点）是 1:1 关系，可以合并。

**改动**：
- 将命中判断代码节点的输出直接用于选择器分支，这个已经是当前设计
- 但可以考虑把判断逻辑放到选择器的条件表达式中（如果 Coze 支持）
- **暂不合并**：Coze 选择器的条件表达式功能有限，复杂判断（如 outputList 长度 > 0）需要代码节点。保持代码节点 + 选择器的组合

### 优化 5：情绪安抚改为 LLM 节点（P2）

**问题**：节点 12（情绪安抚）是输出节点，固定文案。用户情绪程度不同，固定文案无法适配。

**改动**：
- 节点 12 从输出节点改为大模型节点
- 模型：豆包 Lite 7B
- 温度：0.4
- System Prompt：根据用户情绪和问题，动态生成安抚话术，2-3 句话，自然不生硬
- 异常处理：返回设定内容

### 优化 6：答案审核标记为可选（P2）

**问题**：答案审核增加 1-2s 延迟和成本，但审核不通过概率低。

**改动**：
- 在答案审核节点配置中添加"可选"标注
- 说明：v1.2.3 默认保留，但如果对延迟敏感可以跳过（直接连接答案生成 → 对话记录 → 回复输出）
- 不删除节点，但提供"跳过审核"的简化连接方案

### 优化 7：更新找人工计数合并到缓存匹配代码（P3）

**问题**：节点 6（更新找人工计数）是单独的变量赋值节点，仅用于更新 `transfer_cnt`。

**改动**：
- 删除节点 6
- 在缓存匹配代码中，找人工时直接输出 `transfer_cnt` 为 `str(transfer_cnt + 1)`
- 缓存判断分支 2（找人工第二次+）直接连接到回复输出，不再经过更新找人工计数
- 缓存判断分支 1（挽留引导）也直接连接到回复输出
- 但需要确保 `transfer_cnt` 被写入会话变量——Coze 中代码节点的输出变量不能直接写入会话变量，需要变量赋值节点
- **结论**：保留变量赋值节点，但可以改名为"写入会话变量"，同时处理 transfer_cnt 和 retry_cnt 的写入
- 节点数不变，但逻辑更清晰

### 优化 8（新增）：答案生成 Prompt 中的 intent 引用问题

**问题**：答案生成 Prompt 中有 `intent=product_pricing` 的促单判断，但答案生成节点的输入参数中没有 `intent`。需要从意图识别节点传递。

**改动**：
- 答案生成节点新增输入参数 `intent` / String / `{{意图识别.intent}}`
- 确保促单逻辑能正确工作
