## 1. 项目概览

### 1.1 一句话使命与边界

**使命**：在企业内部，让"任何懂业务的人都能用一句中文问数"，把 SQL 报表流水线从"只有数据分析师能跑"升级为"所有业务角色都能自助分析、自动归因、主动洞察"，让 BI 从被动出报表升级为主动推结论。

**边界**：
- 做：自然语言到 SQL（NL2SQL）、到结果（NL2Result）、到洞察（NL2Insight）端到端闭环；覆盖业务自助查数、复杂归因、异常预警、可视化推荐与多轮澄清。
- 不做：通用对话助手、外部数据爬取、基础大模型自训练（仅做模型路由与微调样本沉淀）、面向 C 端的 ChatBI SaaS 商业化。

### 1.2 当前阶段与规模

| 维度 | 当前值 | 说明 |
| --- | --- | --- |
| 业务演进阶段 | 第 4 阶段：智能 BI（主动分析、主动推） | 已从报表式 → 自助式 → 对话式走到主动 BI |
| 核心链路 | **8** 步：提问 → 解析 → 标准化 → 意图 → 规划 → SQL 生成 → 校验 → 执行 | 原资料即 P0 主链路 |
| 实体抽取要素 | **6** 类：指标 / 时间 / 对比时间 / 维度 / 人群 / 任务目标 | 决定 NL→需求结构化颗粒度 |
| 任务规划子任务 | **3** 项：基准差异 / 公式拆解贡献度 / 维度下钻 | 复杂归因分析模板 |
| 技术栈 | BI 平台 + Spark + PrestoSQL + 元数据中台 | 与游戏业务现有数据栈对齐 |
| 服务对象规模 | 数十款游戏项目 + 多业务团队 | 原资料：会 SQL 的人少，需 SQL 的项目多 |

### 1.3 关键成果速览

平台已具备口语化提问到自动出图、出洞察的全链路能力。把"取数响应时长"从分析师人工排队的天级压缩到对话式秒级；把"复杂归因分析"从分析师 1-2 天的人力工作压缩到智能体自动规划与并发执行；并通过双重校验、异常自修复机制守住 SQL 安全与稳定性这条底线。具体量化数据见第 11 章。

## 2. 背景与多角色痛点

### 2.1 企业层痛点

- **数据驱动决策被卡在"取数"环节**：游戏行业每天产出 TB 级日志（埋点、付费、运营事件），但分析师人手有限，业务方提一个临时需求往往等 3-7 天才能拿到一张表，决策速度被数据基础设施的"最后一公里"拖住。
- **取数成本与价值长期错配**：分析师 60% 的时间在写"昨天 XX 渠道收入是多少"这种重复 SQL，真正高价值的归因/洞察/建模工作被挤压到 20% 不到。
- **数据治理与口径割裂**：每个业务线对"新用户/付费用户/活跃天"的定义自己解释自己，跨项目对齐时反复返工，财报口径与运营口径长期不一致。

### 2.2 业务层痛点（运营 / 产品 / 市场）

- **不会写 SQL 的人写不出 SQL**：业务运营和产品同学懂业务、看得懂数据，但不会写 join、不会写窗口函数，遇到稍复杂的留存/漏斗就只能找分析师代写。
- **"为什么下降"问不出来**：业务方真正关心的是归因（为什么昨天首日付费金额这么低），但传统 BI 只能出"是多少"的表，归因要靠分析师人工拆解，往返耗时 1-2 天。
- **报表多到没人看**：BI 平台上历史沉淀报表上千张，业务方真正每天看的不到 5%，"被动出表"模式效率极低。

### 2.3 技术层痛点（数据工程师 / 分析师 / 数仓团队）

- **SQL 语法门槛与方言碎片**：PrestoSQL、Spark SQL、HiveQL、ClickHouse 各种方言细节差异多，新人 3 个月内写出 P0 级事故是常态。
- **元数据漂移**：表字段每周都有改动，文档与现实脱节，新人写 SQL 第一步就要靠老人"口述"。
- **测试集构建难**：原资料明确指出"强提示会提供多个选项干扰判断、多节流程增加测试覆盖复杂度"，导致 NL2SQL 评测集做不出来、回归不稳定。
- **多轮会话尚未跑通**：原资料"后续规划"中明确：多轮会话如何实现、落地难点尚待进一步梳理。

### 2.4 管理层与合规痛点

- **数据安全红线**：自然语言查询如果不做权限校验、不做敏感字段脱敏，可能让业务方一句话查到不该查的数据（手机号、实名信息、薪酬），出事就是合规事故。
- **业务侧"AI 写 SQL"的可信度焦虑**：业务方第一反应是"AI 给的数对不对，谁背锅"，决策权重摇摆。
- **代码执行能力的不确定性**：原资料经验"代码执行能力是关键提升方向"——意味着复杂分析需要 Python/Pandas 而不仅仅是 SQL，技术栈复杂度上一个台阶。

### 2.5 行业数据交叉验证（联网 + 训练知识）

## 3. 需求验证三步法

### 3.1 三步法概览

| 步骤 | 问题 | 本项目结论 |
| --- | --- | --- |
| 第 1 步：确认目标用户 | 谁在承受这个痛点？ | 游戏业务运营/产品、数据分析师、数据工程师、合规与安全团队 |
| 第 2 步：痛点假设 | 为什么存在？根因是什么？ | SQL 门槛高 + 分析师供给紧 + 业务问题口语化 + 归因复杂度高 |
| 第 3 步：验证假设 | 有什么数据/证据能证明？ | 原资料长期排队取数现状 + 行业基准 + 已上线 ChatBI 的真实使用 |

### 3.2 各痛点的三步法验证

| 痛点 | 目标用户 | 痛点假设 | 验证方式 |
| --- | --- | --- | --- |
| 业务方写不出 SQL | 运营/产品/市场 | 数据栈学习曲线陡，业务侧无 ROI 投入 | 历次需求 90% 由分析师代写、平台 SQL 编辑器使用率 <5% |
| 分析师被重复取数挤占 | 数据分析师 | 业务问题颗粒度小、个性化高、被反复打断 | 行业数据佐证 50-70% 工时在数据准备 |
| 复杂归因无人做 | 业务/管理层 | 分析师产能不足，归因模板未沉淀 | 一次"为什么 ARPU 下降"的归因平均耗时 1-2 天 |
| SQL 安全/权限风险 | IT/合规 | 自然语言绕过原有 BI 权限模型 | 监管要求"行级/列级权限可追溯"，原 BI 已具备但 NL 通道尚未接入 |
| 多轮会话不连续 | 业务/分析师 | 第一轮问完后第二轮只能从头说 | 原资料"多轮会话如何实现"列入后续规划 |
| 测试集与评估缺失 | 数据团队 | 强提示干扰、多节点流程难覆盖 | 原资料"已知问题"明确列出 |

### 3.3 验证结论

- ✅ "业务方写不出 SQL"为强真实痛点，已被多次需求暴露，且行业普遍存在；
- ✅ "复杂归因无人做"为高价值痛点，是把 ChatBI 从"查数工具"升级为"洞察工具"的关键；
- ⚠️ "多轮会话"是真痛点但未跑通，需在 P0 阶段就把上下文带槽位补齐机制定下来；
- ⚠️ "测试集与评估"是工程痛点，决定能否做到 PMF 验证，是反指标关键来源；
- ⏸️ "代码执行能力"是延展痛点，决定能否覆盖超出 SQL 的统计分析与机器学习类问题，列入 P1。

### 4.2 用户问题说明（"作为…我想做…从而帮助我…"）

- **作为** 业务运营，**我想做** 用一句话问出"昨天安卓新用户首日付费金额为什么低于上周同期"，**从而帮助我** 不必排期等分析师，3 分钟内拿到归因结论并向上汇报。
- **作为** 数据分析师，**我想做** 把已沉淀的归因模板和指标口径交给智能体复用，**从而帮助我** 把 60% 的时间从重复取数中释放出来，做更高价值的建模与洞察。
- **作为** 产品经理，**我想做** 在版本上线后第二天主动看到"哪些指标显著恶化、可能原因是什么"，**从而帮助我** 抢在用户流失之前回滚或调优。
- **作为** 数据工程师，**我想做** 把元数据、口径、表关系一次性维护进知识库，**从而帮助我** 不再每周重复回答业务"这个字段什么意思"。
- **作为** 合规官，**我想做** 让自然语言问数走完整审计路径并自动屏蔽敏感字段，**从而帮助我** 出事时能 1 小时内调出任意一条问数的全链路证据。

## 5. 底层需求洞察

### 5.1 表面需求 vs 底层需求

| 角色 | 表面需求 | 底层需求 |
| --- | --- | --- |
| 业务运营（小赵） | "我要 ChatBI" | 不必排队等分析师，自己就能回答业务问题 |
| 产品经理（小孙） | "版本后给我个智能日报" | 把"找异常+找原因"两件事变成一件 |
| 数据分析师（小钱） | "给我减负工具" | 把重复劳动转化为可复用的方法论资产 |
| 数据工程师（老周） | "元数据要好维护" | 让元数据"活起来"，被业务和模型同时消费 |
| 合规官（小李） | "审计日志要全" | 出事时能在监管时间窗内自证清白 |
| 管理层 | "数据要驱动决策" | 把"决策—执行—复盘"周期从周级压缩到天级甚至小时级 |

### 5.2 一句话统一所有 P0 角色诉求

> **每一类人都希望"问数据 - 拿数据 - 拿结论 - 拿行动建议"这条链路上自己负责的那一段，能像水电一样顺手、可控、可追溯，并把节省下来的时间投入到真正只有人能做的判断上。**

### 5.3 心理学维度（记忆碎片 / 爱现 / 安全感）

- **记忆碎片论（业务运营）**：每一次"等分析师"的痛是反复触发的"碎片"，平台一旦让他自助闭环一次，碎片消失，黏性极强；反过来，一次错答会立刻让他重建"AI 不可信"的碎片记忆，所以准确率与可解释性是黏性命脉。
- **爱现心理（运营/PM）**：在群里 @ 智能体一句话出图、当场回答老板的"为什么"，是社交资本；有强烈意愿主动安利，传播是免费的。
- **成就感（分析师）**：把自己的归因模板做成"被全公司复用 N 次"的资产，是可量化的"军功章"，比单纯的"我又写了一个 SQL"成就感强 10 倍。
- **掌控感（数据工程师）**：维护一份让模型读得懂、业务也读得懂的元数据，是数仓团队从"基建支持"升级为"知识中台"的最直接路径。
- **安全感（合规/IT）**：审计日志完整 = 出事不背锅，这是底线需求，权重高于一切——任何一次"为了体验好简化日志"的妥协，都会在某次监管检查中以 10 倍代价偿还。

### 5.4 业务驱动模型分析

- **驱动类型**：单边平台（企业内部）+ 部分双边特征（业务方提问 / 分析师沉淀模板与口径）
- **关键因素鱼骨图**：
  - 准确率（最关键）：实体抽取准确率 + 标准化口径覆盖率 + Schema Linking 准确率 + SQL 校验通过率
  - 响应时长：意图识别耗时 + SQL 生成耗时 + 并发查询耗时
  - 业务覆盖度：标准指标库覆盖率 + 模板沉淀数量 + 多轮会话稳定性
  - 安全可信：行级/列级权限、敏感字段脱敏、审计日志完整性
  - 业务方接受度：可解释性、错误重试体验、可视化推荐质量
- **当前阶段集中资源点**：先 all-in"准确率 + 标准化口径"，因为一旦业务方对答案产生不信任，再多功能都白搭；准确率到位后再投资源到"主动洞察 / 主动推送"。

## 6. 产品定义与方案

### 6.1 使命宣言

让企业的数据从"分析师专属语言"变为"业务通用语言"——一句话问数、一张图答问、一段话给洞察、一条链路可追溯。

### 6.2 产品原则

1. **准确优先于花哨**：宁可少给一个答案，不给一个错答案；可解释性 > 绝对覆盖率。
2. **口径来自知识库而非模型**：业务术语、指标口径、表字段映射全部走标准化知识库，不让大模型"自由发挥"。
3. **简单与复杂分流**：简单查数走快路径（直出 SQL），复杂归因走任务规划路径（拆解执行树），不强迫所有问题走最重的链路。
4. **安全是底线而非选项**：行级/列级权限、敏感字段脱敏、审计日志、SQL 沙箱执行——一条都不能少。
5. **闭环可学习**：错答、超时、空结果都要进异常自修复回路；每条 Bad Case 都要回流测试集。
6. **能不让用户输入就不让输入**：意图识别、要素抽取、对比时间默认补齐、维度智能推荐——把多轮澄清留给真正模糊的问题。

### 6.3 用例三要素

| 角色 | 情境 | 痛点 |
| --- | --- | --- |
| 业务运营小赵 | 周一早会前 10 分钟想看一眼"昨天安卓 ROI" | 报表找不到、SQL 不会写、分析师不在 |
| 产品经理小孙 | 卡牌新版本灰度后第二天 | 不知道哪些指标动了、动了多少、为什么动 |
| 数据分析师小钱 | 反复被业务追问"为什么 ARPU 跌了" | 归因要 1-2 天，期间被打断 5+ 次 |
| 合规官小李 | 季度合规检查 | 必须 1 小时内调出过去 90 天任意一条 NL 问数的全链路证据 |

### 6.4 MVP 两阶段设计

**阶段 0 → 0.5（验证价值）**

- 核心 MVP 能力：
  - 自然语言提问 + 6 类要素抽取（指标/时间/对比时间/维度/人群/任务目标）
  - 业务术语标准化（接入元数据中台 + 指标口径库）
  - 简单查数路径直出 PrestoSQL + 双重校验（语法 + 权限）
  - 异常自修复（语法错误 / 超时 / 空结果回 SQL 生成节点重试）
  - 基础可视化推荐（数值/趋势/分布/对比 4 种图表）
  - 完整审计日志 + 行级权限下推
- 退出标准：
  - 简单查数 Top 200 高频问题 SQL 准确率 ≥ 85%
  - 业务方平均自助查数响应时长 < 10 秒
  - 0 起合规事故、0 起越权访问
  - 月活业务用户 ≥ 100 人，跨 ≥ 5 个游戏项目

**阶段 0.5 → 1（真实可用）**

- 核心 MVP 能力：
  - 复杂归因：意图识别分流 + 智能体任务规划（基准差异 / 公式拆解 / 维度下钻）
  - 多轮会话与槽位补齐
  - 主动推送：异常预警、版本诊断、日报智能摘要
  - 图表推荐算法升级 + 交互式可视化
  - 评测集与回归流水线（含强提示干扰对照组）
  - 代码执行沙箱（Python/Pandas）覆盖 SQL 表达不了的统计/ML 类问题
- 退出标准：
  - 复杂归因端到端正确率 ≥ 70%（参照 BIRD 基准）
  - PMF 信号达成（详见第 9.5 节）
  - 模板复用：单个归因模板被 ≥ 5 个业务方复用
  - 业务方 NPS ≥ 40

### 6.5 一定不优先（≥3 条明确不做）

1. ❌ **一定不优先：**自训练基础大模型；只做模型路由 + 微调样本沉淀，模型外采。
2. ❌ **一定不优先：**对 C 端开放 ChatBI 服务；定位企业内部，不做对外商业化 SaaS。
3. ❌ **一定不优先：**支持非 PrestoSQL 方言的全量适配；先吃透自家数据栈主方言，其他方言走"翻译层"二期再说。
4. ❌ **一定不优先：**自然语言写入数据库（NL2DML/NL2DDL）；只做读路径，写路径永远走人工/审批。
5. ❌ **一定不优先：**爬取或接入未授权外部数据源；数据边界由数据中台统一管控。
6. ❌ **一定不优先：**把所有可视化都做"开放编辑"；MVP 阶段只给推荐 + 极简编辑，避免做成新一代 BI 编辑器。

### 8.6 我们的差异化与差距

**差异化**：
- 游戏行业垂直指标体系（ARPU/LTV/首日 ROI/留存/付费率）做深做透，比通用厂商更贴业务

**差距（需要追赶）**：
- ⚠️ 多轮会话稳定性落后于 ThoughtSpot Sage / Power BI Copilot
- ⚠️ 评测集与回归流水线尚未体系化，落后于字节 DataWind 内部
- ⚠️ 代码执行能力未覆盖统计/ML 场景，落后于 OpenAI ADA / Hex Magic
- ⚠️ 主动推送的"用户接受度调优"机制尚未建立，可能造成"骚扰"反指标

## 9. 指标体系

### 9.1 正向指标（成功指标 4 步法）

**Step 1 - 最高目标**：把"业务问题→数据答案→洞察→行动"的端到端周期压缩 10 倍以上，让数据真正驱动游戏业务的每日决策。

**Step 2 - 子指标分解**

| 子指标 | 当前值 | 目标值（12 个月） | 行业对标 |
| --- | --- | --- | --- |
| 简单查数 SQL 准确率 | 待补充（推断 ~75%） | ≥ 90% | Spider 1.0 SOTA 约 90% |
| 复杂归因端到端正确率 | 待补充（推断 50%） | ≥ 70% | BIRD SOTA 约 70% |
| 平均自助查数响应时长 | 5-30 秒（按链路） | < 10 秒（P95） | 行业承诺 5-30 秒 |
| 业务方月活用户 | 待补充 | ≥ 500 人 | 行业头部数千 |
| 业务覆盖项目数 | 部分游戏项目 | ≥ 20 个项目接入 | - |
| 模板复用率 | 待补充 | 单模板 ≥ 5 业务方复用 | - |
| 重复取数工时下降 | 待补充 | ≥ 40% 同比 | Gartner：50-70% 工时浪费可被 ChatBI 收回 |
| 主动推送阅读率 | 待补充 | ≥ 60% | Tableau Pulse 案例 50-80% |
| 月 NPS | 未测 | ≥ 40 | 行业头部 ChatBI 30-50 |

**Step 3 - 功能与指标因果链**

- 简单查数 SQL 准确率 ← Schema Linking 质量 + 标准化口径覆盖率 + 双重校验
- 复杂归因正确率 ← 任务规划模板沉淀数 + 多轮澄清稳定性 + 异常自修复成功率
- 响应时长 ← 简单/复杂分流准确率 + SQL 并发执行 + 缓存命中
- 月活与覆盖项目数 ← 模板库丰富度 + 业务侧推广运营 + IM 直入入口
- 月 NPS ← 准确率 + 可解释性 + 错答恢复体验

**Step 4 - 量化机制**：每周固定日全员对齐指标看板；每月一次 Bad Case 回顾会；季度一次模板库重构。

### 9.2 反指标（量化阈值 + 安全红线 + 降级策略）

| 反指标 | 量化阈值 | 触发动作 | 降级策略 |
| --- | --- | --- | --- |
| SQL 错答率（产出错误结果未自纠） | > 2% 持续 1 周 | 立即触发 Bad Case 回归 + 暂停新模型上线 | 切回上一稳定 NL2SQL 模型 + 关闭复杂归因路径 |
| 越权访问漏拦率 | > 0.01% 出现一次即红线 | 立即告警 + 全平台冻结 NL 通道 | 走人工审批通道 + 全量审计回放 |
| 敏感字段泄露 | 0 容忍（任何一次都触发） | 立即告警 + 通报合规 | 启用全量字段强脱敏 + 暂停新业务方接入 |
| 平均响应时长 P95 | > 30 秒持续 2 小时 | 触发性能告警 | 自动降级到"简单查数路径优先"+ 关闭主动归因 |
| 异常自修复死循环 | 同一查询重试 ≥ 3 次未成功 | 自动回退到人工提示 | 推荐分析师 + 进入 Bad Case 队列 |
| 主动推送骚扰率（用户关订阅率） | > 5% 月环比 | 触发推送策略复审 | 默认改为"用户主动订阅"模式 |
| 复杂归因 token 月超支 | > 预算 20% | 通知 IT + 限流 | 启用低成本模型路由 + 关闭非 P0 业务方的复杂分析 |
| 模型黑词漏拦率 | > 0.1% | 安全告警 | 启用更严格策略 + 强制人工复核 |

### 9.3 指标权衡机制

**权衡顺序**：安全 > 合规 > 准确 > 响应速度 > 业务覆盖 > 主动洞察

> 这意味着：业务方再着急、产品经理再想要"更智能的推送"，行级/列级权限下推、敏感字段脱敏、审计日志完整性这三条红线都不让步；其次保证答案准确，其次再压响应；最后才是覆盖和花哨能力。一旦反指标触发，宁可降级到"简单查数路径"也不放任错答继续扩散。

### 9.4 侵蚀效应评估

- **对原 BI 报表平台的侵蚀**：ChatBI 跑通后，业务方可能不再打开静态报表，导致存量报表"看起来活跃度暴跌"——这不是真侵蚀，而是替代。**对策**：以"业务问题闭环数"为统一上层指标，避免子指标内部互卷。
- **对分析师"成就感"的侵蚀**：模板被复用越多、分析师重复劳动越少，但也可能让初级分析师感到"被替代"。**对策**：把"贡献模板被复用次数"做成分析师 KPI，让 ChatBI 是分析师的扩音器而不是替代品。
- **对元数据治理质量的侵蚀**：业务方习惯"问就行"后，可能不再主动反馈字段错误，元数据腐烂会被放大。**对策**：所有 Bad Case 必回流到口径库与元数据中台，反向驱动治理。

### 9.5 PMF 判断标准

| 维度 | PMF 临界点 | 当前判断 |
| --- | --- | --- |
| 简单查数准确率 | ≥ 90% | ⏸️ 待量化 |
| 复杂归因正确率 | ≥ 70% | ⏸️ 待量化 |
| 业务方周活留存（4 周连续使用） | ≥ 60% | ⏸️ 待量化 |
| 月 NPS | ≥ 40 | ⏸️ 未测 |
| 模板复用：单模板被 ≥ 5 业务方复用 | ≥ 30% 模板达成 | ⏸️ 待量化 |
| 标杆案例：解决 1-2 天的归因问题 | 端到端 < 5 分钟 | ✅ 单点已实现，规模化未验证 |

**当前结论**：PMF 尚未达成，处于 MVP→PMF 的迭代循环中；最关键的 PMF 信号是"业务方周活留存 + 简单查数准确率"两条同时达标。

### 10.2 一定不优先（≥3 条）

1. **一定不优先**：自训练通用基础大模型；只做行业指令微调与样本沉淀。
2. **一定不优先**：自然语言写入数据库（NL2DML/NL2DDL）；只做读路径，写永远走人工/审批。
3. **一定不优先**：对 C 端开放 ChatBI 服务；定位企业内部，不做对外 SaaS 商业化。
4. **一定不优先**：支持非 PrestoSQL 主方言的全量适配；先吃透自家主方言。
5. **一定不优先**：把可视化做成"全功能 BI 编辑器"；保留极简编辑能力即可。
6. **一定不优先**：在准确率达标前上线主动推送；不能让"主动"变成"主动错"。

### 10.3 权衡取舍四步法

1. **识别冲突**：业务方要"覆盖更多场景"vs 安全/合规要"权限/脱敏不让步" vs 工程要"准确率优先"。
2. **回到目标**：最高目标是"端到端周期压缩 10×"，但前提是答案可信；安全/准确不可让步。
3. **拆解层级**：
   - 安全/合规：100% 必须，红线一条不让；
   - 准确率：先到 85% 再扩覆盖；
   - 业务覆盖：高频 Top 200 优先于长尾；
   - 主动洞察：准确率达标后再开。
4. **明确取舍**：先窄而准，再宽而智。先把"昨天 ROI 是多少"问对，再去回答"为什么 ROI 跌了"。

## 12. 落地实践与迭代经验

### 12.1 已踩过的坑与教训

**坑 1：测试集构建被强提示干扰（已踩）**

- 现象：评测时为了"帮"模型选对，常常把多个候选 SQL 一起塞进 prompt，结果模型在评测里表现优异，上线后真实业务问数立刻塌陷。
- 根因：评测口径与生产口径不一致——评测给了模型"提示选项"，生产没有。
- 教训：评测集必须严格"无提示"裸跑，强提示版本只作辅助调试；同一题保留"提示版/裸跑版"双口径对比。
- 解法：建立分层评测集（裸跑 / 单候选提示 / 多候选提示三档），每次回归同时跑三档并报告差距。

**坑 2：多节点流程的回归覆盖度缺口（已踩）**

- 现象：8 步链路任意一步出错都会让整体失败，但单元测试只覆盖了"SQL 生成"一步，导致一个看似无关的"标准化"调整把端到端准确率打崩。
- 根因：节点间契约未冻结、节点输出格式漂移、回归用例少。
- 教训：节点级契约必须显式化（输入/输出 schema + 边界条件），每个节点至少 50 条 Bad Case。
- 解法：建立 8 节点 × N 条用例的矩阵评测，所有改动必须过节点矩阵 + 端到端两套门禁。

**坑 3：业务术语黑话的"长尾陷阱"（已识别）**

- 现象：Top 200 高频指标做对了，但每个游戏项目仍有几十条独有黑话（"次留" vs "次日留存" vs "D1 留存"），命中率落到 60% 以下。
- 教训：术语标准化不是一次性工程，而是与业务方共建的长期治理。
- 解法：每周从 Bad Case 中自动挖掘新黑话候选，由数仓团队 review 后入库，给业务方"贡献术语"积分激励。

**坑 4：异常自修复死循环风险（已识别）**

- 现象：模型对同一报错反复"重写"，3 次后仍然失败但已经消耗大量 token。
- 教训：自修复必须有"最大重试次数"和"错误类型白名单"。
- 解法：3 次内修复不通则降级到人工提示并入 Bad Case 队列，避免无限循环。

**坑 5：主动推送 vs 骚扰的边界（待踩）**

- 现象：第 4 阶段智能 BI 一旦上线，主动推送密度过高会造成"被关闭订阅率"飙升，反而让平台变成"骚扰源"。
- 教训：主动推送必须先做用户接受度 A/B、默认走"弱推送（仅异常 + 仅 PM 关心指标）"。
- 解法：把"用户关订阅率"做成反指标，设阈值 5%。

**坑 6：合规漏洞的低概率高代价**

- 现象：自然语言通道一旦绕过原有 BI 权限模型，可能让运营一句话查到不该查的数据。
- 教训：行级/列级权限下推必须在校验层硬卡，不能依赖大模型"自觉"。
- 解法：所有 SQL 在执行前必须过权限校验函数，未通过即拒绝执行并记录审计。

### 12.2 关键决策的对错复盘

| 决策 | 评估 | 复盘 |
| --- | --- | --- |
| 用 8 步流程显式编排，而不是端到端"一锅 LLM" | 做对了 | 每一步可观测、可回滚、可单独优化，是工程化基础 |
| 把业务术语标准化做成独立中台，而不是塞进 prompt | 做对了 | 口径治理被显式化，模型只负责映射不负责定义 |
| 简单/复杂分流，而不是所有问题都走任务规划 | 做对了 | 简单查数延迟低、token 省，复杂归因走重链路 |
| 异常自修复回 SQL 生成节点 | 做对了 | 用最少改动覆盖最多失败模式 |
| 早期未冻结节点契约 | 做错了 | 局部改动打崩端到端，付出额外回归代价 |
| 早期未做"测试集裸跑/带提示"双口径 | 做错了 | 评测高分但生产失分，浪费一轮迭代周期 |
| 早期忽视合规权限下推 | 做错了 | 后期补做 RBAC 与审计，付出额外工程成本 |
| 早期未把 Bad Case 回流口径库 | 做错了 | 长尾术语命中率长期上不去，靠人肉补 |

### 12.4 项目方法论沉淀（写给后来者）

1. **不要把 NL2SQL 当成"一个模型问题"**：它是"知识库 + 元数据 + 校验 + 评测 + 治理"五件套合奏，模型只是其中一件。
2. **先窄而准，再宽而智**：把 Top 200 高频问题问对，比给 LLM 加三个新能力但准确率掉 5 个点更值得。
3. **节点契约即合同**：8 步任意一步的输入输出必须 schema 化，改动必须配对回归。
4. **Bad Case 是金矿不是废纸**：每条 Bad Case 都要进库、进 retest、回流到口径库与评测集。
5. **安全/合规优先级永远高于功能**：一次合规事故就能让项目停摆 6 个月。
6. **复杂归因模板是"军功章"**：一个被复用 N 次的归因模板，比 100 张静态报表更有沉淀价值。
