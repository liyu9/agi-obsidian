## 学习路径
学习两个由浅入深的实战案例（含可复制的提示词骨架、工具配置要点与核对清单）。

## 核心概念对比

| 组件 | 功能 |
|------|------|
| 对话机器人 | 基于大语言模型的智能助手。可理解自然语言并即时调用工具完成查询、统计等任务，让你以对话驱动业务 |
| AI Agent 节点 | 执行时可基于上下文自动分析与判断，并调用工具完成操作，使流程具备自主推理与行动能力 |

### 工具定义
**工具**：让 Agent 执行任务的接口；可查询/新增/更新/汇总工作表，或调用 PBP、外部 API、发送通知/邮件等。

### 结构化输出
将模型答案组织成 JSON 或固定格式，便于下游节点直接引用。

## 案例一：对话机器人基础用法

### 目标
销售可通过聊天完成"查客户、补录线索、更新跟进"。系统自动写回工作表，并受用户权限约束。

### 步骤
1. 创建对话机器人 → 填写描述 → 系统自动生成的「对话触发 + AI Agent」工作流
2. 配置工具：查询记录 / 新增记录 / 更新记录 / 汇总（手动设置工作表范围：客户、线索）
3. 对新增/更新工具勾选「调用前需要用户确认」
4. 勾选「按用户权限」：AI Agent只能访问对话人有权限的数据

### 安全建议
- 新增/更新 类工具建议勾选「调用前需要用户确认」，避免Agent误操作
- 开启"使用系统预设的回复风格"，获得稳定的回复质量

## 案例二：智能判断场景

### 场景
以"客户投诉分级"为场景，演示 AI Agent 节点的应用方式。该思路可用于需要智能判断、自动总结或决策的任意流程。

### 目标
自动识别投诉严重程度，判断责任人，执行不同的后续动作（通知、PBP 流程、归档等）

### 实现思路

#### 传统流程思维
1. AI提取投诉内容关键信息
2. 根据规则输出投诉严重程度与建议处理方式
3. 模型选择：DeepSeek-V3（该场景重在阅读理解与分类，无需复杂推理，性价比较高）
4. 建议明确角色（分析专员）与判断标准（文本、次数、金额），以提升输出稳定性
5. 输出：使用结构化输出（JSON 字段定义），以便后续节点直接引用字段，无需二次解析
6. 职责：根据投诉类型、责任部门或产品线，自动判断应由谁处理
7. 可将任务拆分到不同 AIGC 节点：复杂度较低的步骤使用高性价比模型（如 mini、nano 系列），在稳定性的同时降低成本

#### 条件分支
- 若 severity = 轻微 → 路径 A
- 若 severity = 一般 → 路径 B
- 若 severity = 严重 → 路径 C

#### 分支执行
- 分支 B（一般）：立即通知负责人并更新状态
- 分支 C（严重）：立即通知管理层并启动紧急流程（PBP）

### 传统vs Agent思维
投诉内容被识别、严重程度被判断、不同分支触发不同动作——逻辑清晰、执行可靠。

但聪明的你可能意识到了一个问题：我们仍然在使用传统的流程思维。每一个判断、每一个动作，都是我们在告诉系统"该怎么走"。

而真正的Agent，不是被告知怎么做，而是自己知道该做什么。

### Agent方式
一个 AI Agent 就能完成全部逻辑：
- AI Agent 不只是理解文本的节点，它拥有完整的判断能力和工具调用能力
- 在提示词中定义规则后，Agent 可以自动判断严重程度，并直接调用工具执行操作

**AI Agent 节点的意义**：不在于"替代"传统流程，而在于让流程从机械执行，进化为智能决策。

### 演进对比
| 传统方式 | Agent方式 |
|---------|-----------|
| 我们用条件分支去判断，用多个节点去执行。系统只是遵循预设路径行动 | 当 AI Agent 节点加入其中，一切都变得不同 |
| - | 它能理解业务语境、根据规则自主判断，并直接调用工具完成任务 |
| - | 流程的"思考"不再依赖人工设计，而是由 Agent 自行完成 |

## 模型选择指南

在为 AI Agent 节点选择模型时，需要平衡三个关键考虑因素：功能、速度和成本。

### 图片识别需求
- 如果任务包含截图、票据、表格图片等输入，请优先考虑支持图片识别的模型
- 若不确定是否会涉及图片上传，建议使用支持图片处理的模型，兼顾文本与图像处理

### 模型选择建议

| 场景 | 推荐模型 |
|------|---------|
| 对准确率或逻辑一致性要求极高 | GPT-5 |
| 成本敏感或原型阶段 | 先用 Qwen Turbo / GPT-5-nano 验证 |

## 提示词设计指南

提示词（Prompt）决定了 Agent 的理解方式与输出质量。无唯一标准，可参考：

| 要素 | 说明 | 示例 |
|------|------|------|
| 角色明确 | 说明 Agent 的身份和职责范围 | "你是客户线索助手，只处理与客户/线索相关的任务" |
| 任务具体 | 列出可执行的动作（查询、汇总、更新、生成报告等），用自然语言描述即可 | - |
| 边界清晰 | 告诉模型"不处理什么"，防止误解或越权 | - |
| 输出格式要求 | 告知希望返回的形式 | Markdown、表格或 JSON |
| 语气与风格 | 若面向终端用户（对话机器人），应保证语气自然友好；在流程中执行（AI 节点）时应简洁稳重 | - |

### 测试与微调
多次运行后，根据日志反馈逐步修改提示词，不必追求一次完美。

### 经验总结
- 越具体的提示词越稳定，越模糊的提示词越容易"跑题"
- 简洁清晰往往比冗长复杂更有效

## 配置最佳实践

### 工作表范围
强烈建议手动指定目标表，避免误触其它表。

### 查询范围
用筛选明确时间、部门、负责人等边界。

### 用户权限
按用户权限（对话流特有）：默认开启；若关闭将忽略对话者权限（一般不建议）。

### 操作确认
Agent 在执行重要操作前会征求你的同意。该功能仅在对话流中提供。

适用工具：新增记录、更新记录、发送站内通知、发送邮件、调用封装业务流程、调用已集成API。

## 性能优化

| 优化方向 | 方法 |
|---------|------|
| 任务拆分 | 将任务划分为多个子任务，在不同的AIGC节点中处理，以提高流程的稳定性，同时还能节省费用（简单任务选用高性价比模型，如mini、nano系列） |
| 仅传必要上下文 | 收紧记录工具的工作表范围。待选工具集越小，结果更稳，token 消耗更低 |
| 记忆轮次 | 按需配置，避免无效上下文累积 |
| 结构先行 | 要求输出 JSON，减少二次解析与重复调用 |
