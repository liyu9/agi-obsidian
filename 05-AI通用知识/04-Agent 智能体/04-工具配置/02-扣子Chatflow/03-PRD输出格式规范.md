# PRD 输出格式规范

本文档定义了 Chatflow 各 LLM 节点生成的 PRD 完整格式。所有章节在 LLM 节点中以 XML 标签输出，经 Code 节点转换为 Markdown 后，由校验节点统一格式输出最终 PRD。

---

## PRD 整体结构

```
# 1 产品概述
  ## 1.1 产品名称与定位
  ## 1.2 产品应用语言
  ## 1.3 产品愿景与目标
  ## 1.4 产品使用终端
  ## 1.5 核心价值主张
  ## 1.6 目标用户群体分析
  ## 1.7 市场需求与竞品简析
  ## 1.8 浏览器兼容性要求

# 2 功能规格
  ## 2.1 功能详述
  ## 2.2 功能模块间的关系图

# 3 用户流程
  ## 3.1 用户旅程地图
  ## 3.2 关键业务流程图
  ## 3.3 各场景下的用户操作步骤

# 4 数据流设计
  ## 4.1 数据结构与关系
  ## 4.2 关键数据流向图
  ## 4.3 数据存储与处理原则

# 5 页面规格
  ## 5.1 页面概览
    ### 5.1.1 整体布局架构
    ### 5.1.2 页面列表
  ## 5.2 页面详情
    ### 5.2.1 [页面名称] ([页面ID])
    ### 5.2.2 [页面名称] ([页面ID])
    ...
```

---

## 第1章 产品概述

生成节点：④ PRD1_产品概述 (192934)

### 1.1 产品名称与定位

内容要求：产品名称、一句话定位描述。

### 1.2 产品应用语言

内容要求：产品支持的语言列表（如中文、英文等）。

### 1.3 产品愿景与目标

内容要求：
- 产品愿景（行业价值定位）
- 产品目标（核心解决方向，需可衡量）

推导来源：市场分析维度输入（1.1行业概况 + 1.2市场问题与机会）

### 1.4 产品使用终端

内容要求：产品运行平台（PC Web / 移动端 App / 小程序等）。

### 1.5 核心价值主张

内容要求：以编号列表形式列出核心价值点，每条价值点需：
- 价值描述
- 与用户痛点的对应关系
- 与竞品的差异化（如适用）

推导来源：用户场景维度 + 产品定位维度 + 竞品差异化维度

### 1.6 目标用户群体分析

内容要求：
- 用户分层描述（决策者 / 使用者 / 其他角色）
- 每类用户的：特征、核心诉求、使用场景
- 场景清单

推导来源：2.1用户画像 + 2.2场景分析

### 1.7 市场需求与竞品简析

内容要求：
- 市场需求核心趋势
- 竞品核心优劣势归纳
- 本产品的差异化定位

推导来源：3竞争分析

### 1.8 浏览器兼容性要求

内容要求：需支持的浏览器及版本列表（如 Chrome 90+、Safari 15+、Edge 90+）。

## 第2章 功能规格

生成节点：⑥ PRD2_功能规格 (1896132)

### 2.1 功能详述

内容要求：以结构化方式列出所有功能，每条功能需包含：

| 字段 | 说明 |
|------|------|
| 功能ID | 按 `F-[模块前缀]_[序号]` 格式，如 F-MATERIAL_001、F-REPORT_003 |
| 功能名称 | 简洁明确，直接提炼核心功能点 |
| 功能描述 | 包含操作对象、操作行为、约束条件的完整描述 |
| 优先级 | P0（核心必做）/ P1（重要）/ P2（锦上添花）/ P3（远期规划） |

推导规则：
- 价值主张中的核心动作（管理/监控/分析/追溯/预警）→ 功能名称关键词
- 核心价值对应 P0/P1，延伸价值对应 P2/P3
- 功能关联关系（如"数据同步→报表生成"）→ 记入模块间关系

### 2.2 功能模块间的关系图

内容要求：以 Mermaid 语法绘制功能模块间依赖关系图，展示：
- 模块节点
- 模块间依赖连线（箭头方向表示数据/调用流向）
- 跨模块支撑关系（如权限管理→所有核心模块）

## 第3章 用户流程

生成节点：⑧ PRD3_流程设计 (177580)

### 3.1 用户旅程地图

内容要求：以表格形式输出，列定义如下：

| 列名 | 说明 |
|------|------|
| 阶段 | 每个核心使用场景对应一个阶段 |
| 用户目标 | 该阶段用户的终极目标 |
| 行为 | 用户为达成目标执行的具体操作 |
| 触点 | 对应的系统界面或模块，命名规则 `P-[功能模块名]_LIST` 或 `P-[功能模块名]_DETAIL` |
| 痛点 | 用户在该阶段可能遇到的困难 |
| 解决方案 | 对应功能如何解决该痛点 |
| 体验 | 便捷 / 高效 / 准确 / 流畅 等 |

### 3.2 关键业务流程图

内容要求：
- 选择最核心的业务流程，约 3 个
- 使用 Mermaid 语法绘制
- 以用户角色和系统作为核心节点
- 起于业务触发点，终于业务状态完成
- 包含判断分支（如审核通过/驳回）

### 3.3 各场景下的用户操作步骤

内容要求：
- 为用户旅程地图中的每个核心阶段，列出详细操作步骤
- 编号列表格式
- 明确区分不同用户角色的动作（如"用户"点击XX → "系统"返回XX → "审核人"审批XX）
- 体现与流程图的对应关系

## 第4章 数据流设计

生成节点：⑩ PRD4_数据流建模 (1802591)

### 4.1 数据结构与关系

内容要求：以表格形式输出，列定义如下：

| 列名 | 说明 |
|------|------|
| 表名 | 数据实体名称（如 t_material、t_user） |
| 字段名 | 字段名称（如 material_name、created_at） |
| 字段类型 | 数据类型（如 VARCHAR(255)、INT、DATETIME） |
| 约束 | PK / FK / NOT NULL / UNIQUE 等 |
| 说明 | 字段业务含义，需关联用户输入中的业务上下文 |

推导规则：
- 操作步骤中的数据对象 → 表定义
- 操作依赖关系 → 外键关系
- 输入字段 → 表字段 + 审计字段（created_at 等）

### 4.2 关键数据流向图

内容要求：
- 使用 Mermaid 语法绘制
- 包含三层交互结构：
  - 用户操作层
  - 应用逻辑层
  - 数据存储层
- 箭头标注数据流向名称（如"库存数据→预警模块"）

### 4.3 数据存储与处理原则

内容要求：以编号列表形式输出，每条原则包含：

| 字段 | 说明 |
|------|------|
| 原则名称 | 如：数据安全性、数据一致性、数据完整性、数据可追溯性、可扩展性、索引优化 |
| 具体描述 | 原则的具体要求和实施方式 |
| 推导依据 | 如"基于输入中的[XX操作]" |

至少覆盖 6 项原则：安全性、一致性、完整性、可追溯性、可扩展性、索引优化。

## 第5章 页面规格

生成节点：⑫ PRD5_页面规格设计 (1119694)

> 输出内容不超过 15000 文字

### 5.1 页面概览

#### 5.1.1 整体布局架构

内容要求：
- 布局模式（如 Web 端响应式布局、标准顶部导航+侧边栏）
- 空间分配策略（各区域尺寸与关系）
- 导航体系（多级导航定义）
- 主要交互模式（页面切换、弹窗、侧边抽屉等）

#### 5.1.2 页面列表

内容要求：以表格形式列出所有页面，列定义如下：

| 列名 | 说明 |
|------|------|
| 页面ID | 如 P-MATERIAL_LIST、P-REPORT_DETAIL |
| 页面名称 | 页面中文名 |
| 核心功能 | 页面支持的主要功能点 |
| 布局类型 | 单栏/双栏/三栏 等 |
| 右侧面板 | 是 / 否 / 慎用 |

### 5.2 页面详情

为页面列表中的每一个页面ID创建一个子章节，格式为：

```
### 5.2.[序号] [页面名称] ([页面ID])
```

每个页面详情包含以下 5 个子节：

#### 布局架构设计

内容要求：
- 具体布局描述（如"二栏布局"）
- 各区域包含的具体元素（顶部导航、左侧菜单、主内容区等）
- 元素与页面核心功能的对应关系

#### 响应式适配策略

内容要求：
- 大屏（≥1440px）布局
- 中屏（1200-1439px）布局调整
- 小屏（<1200px）布局调整
- 移动端布局调整
- 核心功能在各设备上的可用性保证

#### 组件尺寸规范

内容要求：
| 组件类型 | 推荐尺寸（高×宽） | 间距规范 |
|---------|------------------|---------|
| 按钮 | 如 32px × 80px | 内边距 8px，外边距 12px |
| 输入框 | 如 32px × 240px | — |
| 表格行高 | 如 48px | — |
| ... | ... | ... |

#### 核心功能

内容要求：列出该页面支持的主要功能点，与页面列表中的核心功能描述一致并可适当细化。

#### 数据结构

内容要求：如果该页面有关键的数据展示（如表格），以表格形式定义数据结构：

| 列名 | 数据类型 | 宽度建议 | 是否可排序 | 操作功能 |
|------|---------|---------|-----------|---------|
| [列名1] | String | 120px | 是 | — |
| [列名2] | Number | 80px | 是 | — |
| ... | ... | ... | ... | ... |

若无关键数据展示，可省略此节。

## 格式转换规则

LLM 节点以 XML 标签格式输出，Code 节点按以下规则转为 Markdown：

| XML 层级 | Markdown 层级 | 示例 |
|----------|-------------|------|
| `<1 产品概述>` | `# 1 产品概述` | level=1 |
| `<1.1 产品名称与定位>` | `## 1.1 产品名称与定位` | level=2 |
| `<5.1.1 整体布局架构>` | `### 5.1.1 整体布局架构` | level=3 |
| `<5.2.1 页面名 (P-XXX)>` | `#### 5.2.1 页面名 (P-XXX)` | level=4 |

转换函数：`convert_xml_to_markdown(xml_string, level=1)`，递归匹配 `<标签>内容</标签>` → `# 标签\n内容`，每嵌套一层 level+1。

## 校验后最终输出格式

校验节点 (167999) 统一输出为 Markdown 格式：
- 一级标题为模块名称
- 二级标题为子模块名称
- 术语统一（"用户"/"客户"不混用）
- 句式统一（正式书面语）
- 排版统一（标题层级、列表格式）
- 流式输出
