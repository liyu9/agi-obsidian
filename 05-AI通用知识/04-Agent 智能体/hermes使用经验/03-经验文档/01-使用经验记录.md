# Hermes 多 Agent 使用经验记录

## 经验 #1：确认 kanban 技能加载机制

**日期**：2026-05-14
**结论**：kanban-orchestrator 和 kanban-worker 是 bundled 技能，位于 `skills/devops/` 目录。dispatcher 在 spawn worker 时自动加载 `--skills kanban-worker`，无需手动 `skills install`。

**源码依据**：[kanban-orchestrator/SKILL.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/devops/kanban-orchestrator/SKILL.md) 和 [kanban-worker/SKILL.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/devops/kanban-worker/SKILL.md)

**错误认知**（已修正）：
- ~~"profile create 时自动同步"~~ → 实际是 dispatcher spawn 时自动加载
- ~~"需要手动 `hermes -p coordinator skills install kanban-orchestrator`"~~ → 不需要，bundled 技能自动注入

## 经验 #2：assignee 必须对应真实 Profile

**日期**：2026-05-14
**结论**：dispatcher 对不存在的 assignee 名静默跳过——任务永远停在 `ready`，不会报错。

**正确做法**：
1. coordinator 必须先 `hermes profile list` 确认可用 Profile
2. 缓存结果，后续对话复用
3. 不确定时直接问用户"你有哪些 Profile？"

## 经验 #3：基于 GitHub 源码验证的关键机制

**日期**：2026-05-14
**源码版本**：NousResearch/hermes-agent main 分支

| 机制 | 旧认知 | 源码验证结果 |
|------|--------|-------------|
| 依赖设置 | `kanban_link()` 或 `parent=` | `kanban_create(parents=[...])` 在创建时设置，parents 是列表 |
| `kanban_create` 返回值 | 无 | `{"task_id": "..."}` 返回任务ID |
| `kanban_comment` 参数 | 位置参数 `(task_id, body)` | `task_id=..., body=...` 具名参数 |
| `kanban_block` 参数 | 位置参数 | `reason="..."` 必须参数 |
| `kanban_complete` | `summary + metadata` | 增加 `created_cards=[...]` 幻觉门控 |
| Worker 生命周期 | 无 | 6步：orient → work → heartbeat → block/complete |
| Profile 名单 | 固定3-4个 | 没有默认名单，用户自定义 |
| review 后返工 | 重跑旧任务 | 创建新任务分配给原 implementer |
| claim TTL | 无 | ~15分钟，超时自动回收 |

## 经验 #4：故障恢复机制

**日期**：2026-05-14

| 命令 | 场景 |
|------|------|
| `hermes kanban reclaim <id>` | worker 卡住，手动回收 |
| `hermes kanban reassign <id> <profile> --reclaim` | 模型不适合，切换 Profile |
| `hermes -p <profile> model` | 修改 Profile 模型后 reclaim 重试 |

dashboard 会标记 ⚠ 并打开 Recovery 区域。

## 经验 #6：基于三大场景的架构评估

**日期**：2026-05-14

### 三大应用场景 vs 当前架构

| 场景 | 当前流水线 | 适用性 | 问题 |
|------|-----------|--------|------|
| **需求调研** | coordinator → analyst → ai-pm → planner → advisor | ✅ 完整覆盖 | analyst 一个人做调研+分析可能不够细 |
| **需求分析** | coordinator → analyst（拆解）→ planner（方案）→ advisor（审查） | ✅ 完整覆盖 | 无 |
| **方案输出** | coordinator → analyst（需求）→ ai-pm（AI选型）→ planner（方案）→ advisor（审查） | ✅ 完整覆盖 | ai-pm 仅在AI场景需要 |

### 优化建议

| 优化点 | 说明 | 优先级 |
|--------|------|--------|
| analyst 内部可拆为调研+分析两步 | 大型调研时，coordinator 可创建两个 analyst 任务并行（P1扇出模式），一个做背景调研，一个做用户调研 | 中 |
| 增加 researcher 角色（可选） | 如果调研任务重，可拆出专职 researcher 做 web-search + summarize，analyst 专注分析 | 低（当前 analyst 已够用） |
| ai-pm 的触发条件 | coordinator 需在 SOUL.md 中明确：涉及 RAG/Agent/微调/知识库/AI搜索 时插入 ai-pm，纯传统需求跳过 | 高（已写入） |

### 缺失的 Agent 类型分析

| 潜在角色 | 职责 | 是否需要 | 理由 |
|---------|------|---------|------|
| researcher | 专职搜索+摘要 | ❌ 不需要 | analyst + web-search 技能已覆盖 |
| writer | 报告撰写 | ❌ 不需要 | 各 Agent 自己写 summary 即可 |
| reviewer | 专职审查 | ❌ 不需要 | advisor 已覆盖审查职责 |
| tester | 测试验证 | ⚠️ 可选 | 如果场景扩展到开发实施阶段才需要 |
| data-analyst | 数据分析 | ⚠️ 可选 | 如果需要数据驱动的需求验证 |

**结论**：当前5 Agent 架构已覆盖三大场景，暂不需要新增 Agent。如果未来扩展到开发实施阶段，可考虑增加 tester。
