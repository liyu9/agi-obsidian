## 核心问题

**传统时代 vs AI时代的设计模式**

| 传统时代 | AI时代 |
|----------|--------|
| 架构设计模式 | AI应用开发的设计模式 |
| 领域驱动设计（DDD） | Prompt Engineering |
| MVC模式 | Workflow / Chain |
| 代码设计模式 | Single Agent |
| 特定场景的最佳实践 | Multi-Agent System |

---

## 四大架构范式

```
复杂度 ↑
         │
         │  Multi-Agent
         │  (组织的力量)
         │
         │  Single Agent
         │  (五脏俱全的数字生命)
         │
         │  Workflow / Chain
         │  (代码驱动的流水线)
         │
         │  Prompt Engineering
         │  (一切交给模型)
         │
         └──────────────────→ 自主性
```

---

## 范式一：Prompt Engineering（提示词工程）

**核心理念**：一切交给模型

**特点**：
- 最简单直接的方式
- 通过精心设计的提示词引导LLM输出
- 适合确定性高、任务简单的场景

**局限**：
- 复杂任务难以通过单一Prompt完成
- 缺乏可控性和稳定性

---

## 范式二：Workflow / Chain（工作流/链式）

**核心理念**：代码驱动的流水线

**特点**：
- 预先编排的执行步骤
- 每个节点定义明确的功能
- 稳定可预测的执行流程

**示例流程**：
```
爬虫抓取网页 → Python清洗 → LLM提取观点 → LLM总结 → LLM审核 → 写入PDF
```

**优势**：
- 执行稳定，不依赖模型的自主决策
- 易于调试和优化
- 适合流程固定的场景

**局限**：
- 缺乏灵活性
- 遇到未预见情况无法自主调整

---

## 范式三：Single Agent（单个Agent）

**核心理念**：五脏俱全的数字生命

**特点**：
- 具备完整的感知、决策、执行能力
- 模型决定下一步做什么（Model-Driven）
- 可以调用工具、访问外部资源

**执行流程**：
```
竞品分析任务
    ↓
拆解搜索任务
    ↓
工具调用 + 搜索
    ↓
判断信息是否充足
    ├─ 信息不足 → 补充搜索
    └─ 信息充足 → 生成报告
    ↓
审查报告
    ↓
写入文件系统
```

**优势**：
- 灵活性高，可应对复杂场景
- 具备一定的自主决策能力

**局限**：
- 单个Agent能力有限
- 复杂任务可能超出单个Agent的处理能力

---

## 范式四：Multi-Agent System（多Agent系统）

**核心理念**：组织的力量给模型减负

**特点**：
- 多个Agent协同工作
- 分工明确，各司其职
- 通过协作完成复杂任务

**关键机制**：
- **回退**：Agent可以回退到上一步
- **拒绝**：Agent可以拒绝不合理的任务
- **协作**：Agent之间可以相互通信

**阿什比定律**：
> 业务的不确定性决定系统的不确定能力

**优势**：
- 通过分工降低单个Agent的复杂度
- 系统整体具备更强的鲁棒性
- 更接近真实组织的运作方式

---

## 课程总结

### 四种范式的定位

| 范式 | 核心理念 | 适用场景 |
|------|----------|----------|
| Prompt Engineering | 一切交给模型 | 简单任务、快速验证 |
| Workflow / Chain | 预先编排，稳定执行 | 流程固定、质量要求高 |
| Single Agent | 模型决定下一步 | 复杂但边界清晰的任务 |
| Multi-Agent | 组织的力量给模型减负 | 超复杂任务、需要多角色协作 |

### 选择原则

1. **从简单开始**：先用Prompt Engineering验证可行性
2. **逐步复杂化**：根据需要引入Workflow、Agent
3. **按需选择**：业务不确定性与系统复杂度需要匹配

回顾一下之前的AI应用场景，思考业务的不确定性和系统实现的复杂度是否匹配？
