## 第一性原理｜理解 LLM 的本质

### LLM 是如何「思考」的

大语言模型的工作方式可以用一句话概括：**预测下一个 token**。

当你向 LLM 提问时，它并不是先在「脑中」构思好完整答案再输出。相反，它每次只做一件事：基于当前看到的所有文本（你的输入 + 它已经生成的内容），预测最可能的下一个词是什么。然后把这个词加入序列，再预测下一个，如此循环直到生成结束，这种方式被称为 **自回归生成（Autoregressive Generation）**。

### LLM 的三个本质特征

**1. 没有独立于输出的「思考」过程**

LLM 的推理就是生成本身。它不能先想好再说，只能边说边想。这就是为什么让模型「一步步思考」（Chain-of-Thought）会提升效果 — 你实际上是在给它更多的「思考空间」，让它通过生成中间步骤来辅助推理。

**2. 上下文就是全部记忆**

LLM 没有独立的记忆存储。它对当前对话的所有「理解」，完全来自于输入给它的上下文窗口。窗口之外的内容，对模型来说就是不存在的。

**3. 生成具有概率性**

每一步预测都是基于概率分布采样，这意味着同样的输入可能产生不同的输出。

### 自回归机制的局限

自回归（autoregressive）LLM 的核心工作方式是：一次只预测下一个 token，然后把自己刚生成的内容再喂回去继续生成。这个机制很强（通用、可扩展，能「写出」复杂结构），但也天然带来一些局限，在 Coding Agent 里这些局限会被放大，因为**软件开发是「长链路，强约束，强验证」的任务**。

## Coding Agent 的实现原理

### 基于消息的对话结构

Coding Agent 本质上是一种特殊的 LLM 对话，它的消息结构通常包含：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是一个编程助手..."
    },
    {
      "role": "user",
      "content": "帮我写一个快速排序函数"
    },
    {
      "role": "assistant",
      "content": "好的，这是一个 Python 实现的快速排序..."
    }
  ]
}
```

三种角色各有用途：
- **system**：设定 Agent 的行为准则、能力范围和工具定义
- **user**：用户的输入
- **assistant**：模型的回复

### Tool Calling 机制

Coding Agent 的核心能力来自**工具调用**。API 允许你定义工具的 schema，模型会在需要时生成结构化的工具调用请求：

```json
{
  "tools": [
    {
      "name": "read_file",
      "description": "读取指定路径的文件内容",
      "parameters": {
        "type": "object",
        "properties": {
          "path": {
            "type": "string",
            "description": "文件路径"
          }
        },
        "required": ["path"]
      }
    }
  ]
}
```

当模型决定调用工具时，它的响应会包含工具调用信息：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "name": "read_file",
      "arguments": "{\"path\": \"src/main.py\"}"
    }
  ]
}
```

工具执行结果作为新消息返回给模型：

```json
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "def main():\n    print('Hello, World!')\n..."
}
```

### Reasoning Content 的保留

对于具有显式推理能力的模型，API 响应中可能包含 reasoning 或 thinking 字段，记录模型的思考过程：

```json
{
  "role": "assistant",
  "reasoning_content": "用户需要读取文件来理解项目结构。我应该先查看 src 目录下的主要文件...",
  "content": "让我先看一下项目的主文件。",
  "tool_calls": [...]
}
```

在多轮对话中保留这些推理内容，可以帮助模型维持思维的连贯性。模型可以「回顾」自己之前的思考过程，从而做出更一致的决策。

### Prompt Caching：工程实践的关键

由于 LLM 的自回归特性，每次请求都需要重新处理整个上下文。对于动辄几万 token 的 Coding Agent 对话来说，这意味着大量的重复计算和延迟。

**Prompt Caching** 通过缓存上下文前缀的计算结果来解决这个问题。关键在于：缓存基于前缀匹配。只有当新请求的开头部分与之前的请求完全一致时，才能命中缓存。

这直接影响了 prompt 的组织方式：

```
┌─────────────────────────────┐
│  System Prompt              │  ← 稳定不变，可缓存
│  (角色定义、行为准则)         │
├─────────────────────────────┤
│  Tool Definitions           │  ← 稳定不变，可缓存
│  (工具的 schema 定义)        │
├─────────────────────────────┤
│  Project Context            │  ← 相对稳定，尽量少变
│  (项目说明、代码规范)         │
├─────────────────────────────┤
│  Conversation History       │  ← 动态增长
│  (对话历史)                  │
├─────────────────────────────┤
│  Current User Message       │  ← 每次都变
│  (当前用户输入)              │
└─────────────────────────────┘
```

### Agent Loop：核心循环

Coding Agent 通过 Agent Loop 实现多步骤任务：
1. 接收用户任务
2. 模型推理决定下一步行动
3. 调用工具执行
4. 获取执行结果
5. 循环直到任务完成

|---------|------|------|

| 命令执行 | execute_command | 运行Shell命令 |

## 常见问题与解决方案

### 会话间失忆

**问题**：每次对话都是全新开始，Agent 无法记住之前的上下文。

**解决方案**：
- 使用任务追踪系统记录进度
- 定期保存对话摘要
- 在新对话开始时提供背景信息

### 上下文窗口耗尽

**问题**：对话太长超过上下文窗口限制。

**解决方案**：
- 观察遮蔽（Observation Masking）：只保留关键上下文
- LLM 摘要：用模型自动生成对话摘要
- 分段处理：将大任务拆分为多个子任务

### 有效上下文远小于标称值

**问题**：上下文窗口很大，但有效信息密度低。

**解决方案**：
- 精简 prompt，避免冗余描述
- 优先提供关键代码片段
- 使用结构化格式提高信息密度

### 新发现的任务被丢弃

**问题**：Agent 在执行过程中发现新问题，但无法处理。

**解决方案**：
- 记录所有待处理任务
- 设置任务优先级
- 定期回顾检查

### 过早宣告完成

**问题**：Agent 声称完成任务但实际未完成。

**解决方案**：
- 强制验证步骤
- 添加测试用例验证
- 人工检查关键节点

### 工具选择不当

**问题**：Agent 选择了错误的工具或工具组合。

**解决方案**：
- 清晰定义工具描述
- 提供工具选择示例
- 限制可用工具范围

## 最佳实践建议

### 1. 短对话优于长对话

保持对话简短有以下优势：
- 上下文更集中
- Token 消耗更低
- 中途调整方向成本小
- 更容易保持专注

### 2. 以对话为单位组织工作

每个对话应该专注于一个具体任务或子任务。避免在一个对话中混合多个不相关的任务。

### 3. 编写有效的项目配置文件

项目配置文件应包含：
- 项目目录结构说明
- 代码规范和风格指南
- 常用命令和脚本
- 依赖和环境信息

### 4. 200K Token 足够了

不要迷信更大的上下文窗口。实践中，200K token 的上下文窗口对于大多数任务已经足够。关键是提高信息密度，而非简单堆积内容。

### 5. Compounding Engineering：让系统自我改进

将每次与 AI 协作的经验和最佳实践沉淀下来，形成项目专属的知识库和配置文件。这样 AI 在每次新对话中都能继承之前的经验，持续改进。

### 6. 对人难的事，对 AI 也难

如果某个任务对人类开发者来说很困难，那么对 AI 来说可能同样困难。不要期望 AI 能轻易完成人类都觉得复杂的事情。

### 7. 刻意练习：像学乐器一样学习 AI

与 AI 协作是一项需要练习的技能。通过刻意练习，你可以：
- 学会更好地表达需求
- 理解 AI 的能力和局限
- 掌握高效的协作模式
- 建立对 AI 输出质量的判断力

## 总结

从第一性原理理解 LLM 和 Coding Agent：

1. **LLM 本质是概率性的自回归生成器** — 它不能真正"思考"，只能根据上下文预测下一个 token

2. **上下文就是它的全部记忆** — 没有独立于对话的持久记忆

3. **Coding Agent = 对话结构 + 工具调用 + Agent Loop** — 通过这三个机制实现自动化执行

4. **Prompt Caching 是工程落地的关键** — 优化 prompt 结构可以显著提升效率

5. **最佳实践的核心是"精简"** — 短对话、精选上下文、结构化配置
