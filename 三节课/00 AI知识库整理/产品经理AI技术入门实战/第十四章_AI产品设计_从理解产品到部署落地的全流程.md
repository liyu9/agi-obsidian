# 第十四章 AI产品设计：从理解产品到部署落地的全流程

## 章节引入

好，接下来是我们这个概念先导片的最后一章。

学完这14章呢，你就会对AI怎么跑起来是有一个基础的印象。后面呢我们会进入一个算法的课程。

那今天我们现在正式开始这最后一章呢，我们的定位就是一个阶段性的整合加上实现的闭环。把前面学的Prompt、模型选型、知识库、向量库这些能力，我们整合成为一整套可以跑通项目的AI产品设计和交付流程。

## 核心问题

那么**面向的问题是怎么从一个模糊需求走到一个可以落地的AI产品方案**：
- 我应该先做什么
- 需要去做哪些模块
- 哪些地方需要和研发联动
- 不同的项目它的路径是怎么样的
- 有哪些典型的坑位和节奏节点需要特别的去关注

## AI产品项目从哪里开始

### 第一部分：从场景理解到问题建模

**在AI的项目里边，起点永远不是模型，不是代码，不是工具库，而是业务场景加上用户问题加上产品机会点**。

**明确入口**：就是说你面对的是一个场景，而不是一个技术命题。老板常常说一句话，"我们可不可以加一个智能推荐，我们能不能做一个自动写日报的"，"要不要做一个AI客服"。听起来呢像是在说技术，实际上他是在说业务痛点。

所以作为产品经理，你需要把这些含糊的诉求翻译成为一个可以落地的产品起点。

### 第一个问题

**你应该问自己的第一个问题是，这个AI功能是为了解决一个什么样的核心问题**？

- 是用户找不到信息效率太低
- 还是客户的体验太差
- 你是想去提效还是降本，还是让结果更优化

### AI的价值类型

**你可以用这四个关键词来判断AI目标的类型**：

| 价值类型 | 说明 | 典型场景 |
|---------|------|---------|
| **提效** | 提高效率，节约时间 | 自动写周报、自动摘取会议纪要、自动工单填写 |
| **替代** | 替代人工执行 | 智能客服、出差发票识别 |
| **增强** | 增强现有人的能力 | 销售话术建议、用户画像生成 |
| **创造** | 创造原本无法提供的服务 | 个性化推荐、AI陪伴对话、内容生成工具 |

### 判断任务类型

**那接下来要判断任务的类型，你是在做问答还是在做流程？**

这是很多的产品经理他在理解AI的场景的时候最容易犯错的部分。他会把AI当成搜索引擎，或者是当成万能的管家。

所以**你要学会识别你面前的任务是属于哪一种**：

| 任务类型 | 说明 |
|---------|------|
| **查询型任务** | 单轮的输入，类似于搜索加知识库 |
| **交互型任务** | 多轮对话，引导型的澄清 |
| **闭环型任务** | 需要带动作加执行加反馈，它是一个流程链 |

**这一步很关键，它是决定了你后面是用Prompt就够了，还是需要去用Chain和Action，是用对话引导还是流程的自动化**。

### 第一阶段核心任务

**那第一阶段的核心任务是从一句模糊的需求去推导出清晰的AI项目原型**：

你需要输出的三样东西：

1. **场景描述**：用一句话去说清楚"在什么场景下遇到什么问题"

2. **AI的任务目标**：明确这个AI模块它到底是要干嘛的，是去帮用户找信息，还是去自动地执行任务，还是根据数据去生成内容，具体做哪些步骤你要确定

3. **初步的能力规划**：你要学会用一句话或者是一个结构表去说明这个AI模块需要具备哪些能力，准备接入哪些模块

**所以你不要先急着去写Prompt的，你要先做结构图，通过换流程图或者是任务分解框架，再决定是只靠Prompt就能搞定，还是需要去串成Chain、搭建搭载Action去接入向量库结构先行，技术后置**。

## AI项目规划五步法

### 用AI视角重新拆解产品逻辑

那我们接下来就讲一下这个AI项目规划的五步法。

**传统的我们做产品很可能的习惯是页面结构是怎么设计的，用户流程是怎么走的，功能点有没有对上竞品**。

但是在AI的产品里边，这一套逻辑是不够用了。因为你不再是去创造一套规则，你是在调度一个智能体。

那AI产品它它不再等于我们之前的这种功能堆砌了，它是需要去做一个任务的编排，做能力的调度和数据的驱动。

### 第一步：任务拆解

**那我们用五步法来跑通这个流程了**：

首先是**需要进行一个任务的拆解**。AI产品经理的第一个责任是你需要把"我想要个智能助手"翻译成为"他要怎么去干活"。

比如说老板告诉你说做一个自动会议纪要，你不能上来就写，你需要去拆解结构。

什么结构呢？**会议纪要Agent它是包含了**：语音录音 → 语音转文字 → 要点提取 → 内容重写 → 格式排版 → 到自动发送的。

这一步拆的越清晰，你后面选模型、接工具、搭Chain，它才不会混乱。

这个时候我们可以给你推荐任务流程草图，或者是AI职责矩阵。

### 第二步：模型选型

**第二个就是模型选型**。模型选型的话不是说谁红你就用谁，你要去考虑哪些模型最适合你当前的任务。

比如说文本生成，那GPT-4的模型现在是OpenAI的嘛，它的语言能力是最强的，推理性是最稳定的。Claude-3呢它是上下文超强，安全性高。再就是DeepSeek它是一个多模态的能力强，你在看工具操作类和工具调度类模型的时候，就有OpenAI Function Calling，或者是ReAct模式，或者是LangChain Tool。

**选型的时候要去评估，评估的并不是说它能力强不强，你要评估它的延迟，评估它的成本，评估它的安全性，评估它是否支持本地化部署**。

我们选型的目标产物是一个模型的能力对比表，加上你选型的决策逻辑。

### 第三步：输入设计

**第三个就是一个输入设计，有了这个模型你还要去告诉他怎么去动手**。

这个就是Prompt设计。你需要设计的不是文案，而是一个任务指令系统。

你需要思考这个Prompt它是一次性的还是多轮的交互，是否是需要加入记忆模块上下文状态，是否是要用模块化设计来拼接，要不要引入Prompt DSL让AI来更精确。

### 第四步：RAG设计

**第四个就是你打算给AI多少参考资料，因为大语言模型它不是万能的**。

它不是在记忆里提供的资料，而是在根据训练加上上下文的进行创作。你要让AI回答的靠谱，通常你就需要用到RAG。

也就是你要把资料做成一个私有的知识库，在AI临史检索之后再生成。

你需要去判断：
- 要不要去查本地的文档政策和历史数据
- 要不要接入数据库
- 要不要去接外部的API
- 要不要去搭建向量库
- 怎么样做Embedding

这个时候你的目标产物是需要做知识结构图加上数据接入方式。

### 第五步：流程编排

**到第五步你就要去做一个流程编排，比如说Chain加Action加Memory加状态控制**。

最后呢你需要把这些能力模型呢去串成一个能够执行的流程链。

你要想清楚是一问一答还是闭环的执行，是对话的驱动还是一个系统的自动触发，是多步的是多步骤的任务还是一个嵌套任务。

到底需不需要去判断条件，如果失败了到底要不要兜底，谁来兜底。

你会需要的就是Chain的调度和Memory的状态控制，以及图的管理器。

## 交付节奏和协作方式

**还第三部分呢就是我们的交付节奏和协作方式**。

很多人在做AI项目的时候有个误区，他觉得自己写好Prompt，选好模型就可以上线了。但是真正能够让AI跑得动的，是一个从想法到POC到VP到正式产品的完整的推经验。

所以它的每一个阶段的目标交付物和协作方式都不一样的。

### 产品阶段拆解

| 阶段 | 说明 | 核心工作 |
|------|------|---------|
| **原型期** | 概念验证 | 快速验证思路，验证AI做这个事情能不能靠谱。用GPT或者Claude直接调用，验证能否解决用户痛点 |
| **MVP期** | 团队内部交付 | 从能用到能跑，包括明确输入来源、输出格式、上下游对接，建立基础知识库，Prompt模块化结构，加入最小可控的流程链路 |
| **小范围测试** | 暴露问题 | 加入异常处理、权限控制、接口，保证接口稳定性。增加监控，测试用户完成度，驱动迭代 |
| **正式交付** | 产品上线 | 加入用户权限、数据加密、操作日志审计 |

### 协作要点

**我们和研发算法数据的协作要点就是AI项目它其实不怕技术难，他没有太多的这种技术上面的问题。他怕的是你做一半他做一半，大家都不知道AI走到哪一步**。

所以一定要建一个任务责任分层的模型。你需要去理解任务的目标，去调用数据库，去对结果进行一个排序。然后控制任务的顺序。

我们用可视化的工具和接口文档建立一个共识。

**AI项目不是你一个人写就写Prompt就完了，而是你要带着模型，带着数据工具去组建一个AI小组**。

这个时候你就可以用Prompt模块表或者是建流程图这一个接口说明表。这些地方的话能让这些工具做好了之后，让技术团队，让工程师团队能够一眼就看懂你要调用的是什么。

## 复盘和迭代机制

**第四部分呢就是我们的复盘和迭代机制**。

这个就是很多产品人他在做AI项目的时候，他会把上线当做终点。但实际上对于AI来说的话，它的上限只是他开始自我演化的第一天。

因为AI它不是一个写死的逻辑，它是一个很容易出错，很容易被误解，会遇到很多新问题的一个可学习的系统。

**所以真正成熟的AI项目，它一定是有几个关键词的**：可监控、可定位、可调整、可复用。

不管结果准不准，你都需要去有一整套的反馈机制。**其实AI他最害怕的并不是答错，而是答错了你还不知道**。

### 反馈机制组件

那最好有几个组件呢：

- 用户评分的模型
- 异常情况的标签和自动记录
- 失败的Prompt

**我们这个目的它不是去追责AI而是收集哪一类的任务它的失败率更高，哪类的用法容易翻车**。

### 问题溯源

那翻车之后呢，你要理解哎，它并不像传统的系统那样，它是出错的就报错的。它可能是给你一个悄无声息的给一个似是而非的答案，是看起来好像是对的。但是你仔细研究又不太对。

**所以你要有能力去溯源，就这句回答到底是哪一步出了问题，就你需要列一个这种执行任务执行的日志结构**。

这个表能够让你很快速地定位，到底是Prompt它的逻辑设计的问题，还是用户输入的太模糊，还是模型上下文忘了前面一句。

**所以这个里建议你建立这个三张活的表**：

1. **Prompt的模块表**
2. **任务链的结构图**
3. **Prompt DSL的语法库**（这些语法呢都是需要有一个注释版本号和影响范围的）

### 问题定位思考路径

我们可以举个例子，就很多人一看AI的打错了，他就会说Prompt不够好。但是其实这个问题真的并不一定在本身，你是需要有一个结构化的思考路径。

比如说AI它反馈错误了，你要去找到用户在哪里：

1. 到底是Prompt的设计问题
2. 还是输入的信息不足
3. 还是任务链的顺序错了
4. 还是知识库的命中不准

**然后：**
- 调整Prompt的结构
- 加入多轮的追问去重排执行流程
- 重新去做Embedding

**AI它不是一个一次性交付的作品，它是一个需要你持续去调教、反馈、优化的一个可成长型的一个产品**。

所以有些人不懂AI的，他他总是希望AI能够马上达到百分之百的准确率。这就是非常荒谬的想法。

这个是一个可以调度模型，控制逻辑和定义行为的系统的一个设计者。

1. **你能够看懂问题背后的AI任务的结构**
