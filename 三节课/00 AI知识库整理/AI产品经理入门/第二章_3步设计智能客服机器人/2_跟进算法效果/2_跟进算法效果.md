# 第2步：跟进算法效果

## 一、AI产品经理应了解技术到什么程度

### 1. 核心问题

> 产品经理应不应该懂技术？应该懂到什么程度？

**结论**：对于AI产品经理来说，这个问题毋庸置疑，一定要懂一些算法技术。

### 2. 技术了解三阶段

#### （1）基础入门阶段

**适用人群**：非计算机专业、研发或算法工程师转岗的AI产品经理

**学习目标**：理解AI技术的一些基本概念和技术背景

**基础术语清单**：

| 术语类别 | 具体内容 |
|---------|---------|
| 学习类型 | 深度学习、机器学习、有监督学习、无监督学习、迁移学习、强化学习 |
| 核心能力 | 技术原理理解、能解决什么问题、不能解决什么问题 |

**不需要深入**：CNN等模型怎么用、怎么写、用多少层

**需要了解**：
- 深度学习 vs 机器学习的差异
- 它们各自能解决什么问题、不能解决什么问题

**学习途径**：
- 知乎技术论坛
- 开源AI讲座
- AI产品经理基础书籍

#### （2）进阶阶段

**核心要求**：对某个具体领域方向有认知

**领域方向**：
- **NLP（自然语言处理）**
- **CV（机器视觉）**
- **智能语音**

**进阶内容**：
- 该领域有哪些算法技术
- 目前技术能解决什么问题，解决到什么程度
- 业内已有场景的应用方式
- 什么场景是现有技术不能解决的
- 持续关注所在细分领域的技术发展和创新型应用

**面试洞察**：

> 之前面试过一些NLP细分领域的产品经理，他们简历上会将细分领域的技术基本上都提到一遍，但对于某个场景为什么要用这个技术，并不能很清楚地表达出来。

**思考深度要求**：

> 在人机对话的场景，为什么要使用知识图谱、语义网络，而不是用向量对话就可以了？作为做智能客服机器人的产品经理，你需要能够解释清楚。

#### （3）高级阶段

**适用方向**：算法中台、机器学习平台等

**要求**：
- 对算法技术有更深刻的理解
- 不需要自己写代码
- 但对算法原理需要有一定理解

**推荐读物**：
- 《深度学习》（花书）
- 《机器学习》（西瓜书）

**价值**：提升数学逻辑能力

### 3. 技术了解的重要性

**两大价值**：
1. 与业内人士沟通更顺畅
2. 评估业务场景时，知道能解决什么问题、不能解决什么问题，知道用什么技术可以解决

## 二、智能客服机器人算法技术全景

### 1. 整体架构

```
智能客服机器人
├── 文本机器人
│   ├── 语义理解
│   ├── 意图预测
│   ├── 情感识别
│   └── 其他NLP技术
└── 语音机器人
    ├── ASR（语音转文本）
    ├── TTS（文本转语音）
    └── 其他语音技术
```

### 2. 文本领域核心算法

| 技术 | 功能描述 |
|------|---------|
| **语义理解** | 理解用户问题语义，匹配答案 |
| **意图预测** | 预测用户下一步意图 |
| **情感识别** | 识别用户情绪（正向/中性/负向） |
| **实体识别** | 识别文本中的关键实体 |
| **文本聚类** | 对问题进行聚类分析 |
| **热词聚类** | 发现热点问题 |
| **知识查重** | 知识库去重优化 |

### 3. 语音领域核心算法

| 技术 | 全称 | 功能描述 |
|------|------|---------|
| **ASR** | Automatic Speech Recognition | 语音转文本 |
| **TTS** | Text To Speech | 文本转语音 |
| **智能打断** | - | 语音对话中的智能打断 |
| **音频降噪** | - | 去除背景噪声 |
| **说话人识别** | - | 识别说话人身份 |
| **语种识别** | - | 识别语言种类 |
| **语音推理** | - | 基于语音的推理 |

### 4. 关键技术详解

#### （1）语义理解技术选择

**两大常见技术**：

| 技术类型 | 优势 | 劣势 | 适用场景 |
|---------|------|------|---------|
| **分类模型** | 匹配准确率更高 | 训练时间长，实时性较差 | 企业内部定制系统，有独立知识库 |
| **相似度模型** | 实时性好 | 准确率可能略低 | SaaS应用 |

**选择依据**：根据企业实际业务场景需要决定

#### （2）ASR技术成本

**现实情况**：
- 自研ASR模型前期耗资在上千万人民币
- 目前做应用层的企业不太会自研

**解决方案**：
- 阿里巴巴、科大讯飞等AI大厂提供ASR接口
- 按转译工作量付费使用

#### （3）其他技术成熟度

**已形成共识的技术**：
- 实体识别
- 情感识别
- 智能打断

> 虽然这些技术也是当前业务场景的刚需，但随着近5-10年技术的普及和发展，各个技术的应用边界在业内已经有共识和最佳实践。

**起步建议**：
- 刚开始做智能客服机器人的厂商
- 参考前人对这些技术的最佳实践
- 基本可以快速搭建智能客服机器人应用

#### （4）尚未突破的技术

**案例：通过语音语调识别情绪**

**期望**：通过用户语音语调识别情绪

**现实**：
- 人类可以听出对方情绪差异
- 但目前业内对这件事技术上还没有很好突破
- 通过语音语调识别情感目前不太可行

**可行方案**：
- 通过ASR将音频转译成文本
- 然后进行情感识别技术匹配

```

**产品经理职责**：
- 明确需求要做什么

**交付物**：给到算法工程师明确的算法需求文档

#### （3）第三步：持续优化

**上线后工作**：
- 持续收集bad case

- 提升业务指标

## 四、实战案例：情感识别算法需求

### 1. 业务背景

**发现场景**：查看用户对话记录时发现的问题

**问题描述**：
- 用户有负面情绪时
- 机器人回复答案依旧就事论事
- 对话整体感觉比较生硬

**典型案例**：

**用户原话**：
> "要命了，我的衣服已经寄回去七天了，你还不给我退钱，我要投诉你了"

**机器人回答**：
> "您的订单我们客服已经收到货了，正在处理中"

**对比人工客服**：
> "亲，您不要生气，小二马上帮您查查看，当前订单已经收到货了，正在处理中，马上就会给您退钱的，请您放心。"

**优化目标**：当用户问题带有情绪时，机器人首先予以安抚，再给出答案

### 2. 算法需求定义

#### （1）输入输出

| 项目 | 内容 |
|------|------|
| **输入** | 用户问题 |
| **输出** | 情绪值（正面/负面/中性） |

> 目前市面上有些智能客服机器人在负面情绪里还会细分焦虑、生气等，但本次举例将所有负面情绪归到负面这一类。

#### （2）业务指标

**目标**：情绪识别总准确率达到90%以上

#### （3）技术调研结论

**实现方式**：使用分类算法

**原理**：将用户每个问题定位到情绪分类中

### 3. 分类算法入门

#### （1）二分类

**案例**：黑白羊分类

**训练过程**：
- 算法学习大量黑羊和白羊的照片
- 训练得到分类模型

**应用**：给你一只羊的照片，判断是黑羊还是白羊

**判断正确**：新来一只黑羊，模型判断为黑羊 → 正确

#### （2）多分类

**本次需求**：三分类（正面/负面/中性）

**训练过程**：
- 提供2万个问句
- 人为标注每个问句的情绪类别
- 算法学习这些标注数据
- 训练得到分类模型

**应用**：给你一个句子，模型告诉你它的情感类别

### 4. 理解技术选型的原因

**问题引入**：

**场景**：两个句子

- **A句子**："我抓狂了，我要去315投诉"
- **B句子**："到底行不行，我很着急"

**人为感知**：A句子比B句子负面得多（用户马上要投诉，已经很生气）

**算法结果**：模型给A和B的打分相差不多，甚至可能一样

**原因解释**：
- 使用的是分类模型
- A和B都被归到"负面"这一类
- 给出的置信度都相对较高
- 但分类模型不会给出情感强度细分

**产品经理职责**：
- 对技术有一定理解
- 能够给出可解释性说明
- 不能因为A负面值"更高"，就期望算法给更高分

### 5. 标注数据的重要性

#### （1）核心原则

> 标注数据的准确率就是算法模型能够实现效果的上限值。

**案例分析**：

标注了2万条问句：
- 95%标注正确
- 5%不正确或模棱两可

**算法上限**：最多能达到95%（可能还达不到）

**原因**：模型学习的就是人工给的标注结论

#### （2）标注质量保障

**建议做法**：
- 同一批语料至少由两个人分别标注
- 最后取交集
- 不一致的部分进行核对和校验

## 五、算法效果衡量指标

### 1. 数据集划分

**数据分配建议**：

| 数据集 | 比例 | 用途 |
|--------|------|------|
| **训练集** | 80% | 算法训练模型 |
| **验证集** | 20% | 测试模型效果 |

**案例**：2万条数据
- 16000条用于训练
- 4000条用于测试

### 2. 混淆矩阵

#### （1）二分类混淆矩阵

**以正向情绪预测为例**：

| 指标 | 含义 | 位置 |
|------|------|------|
| **TP** (True Positive) | 真实正向，预测也是正向 | 左上角 |
| **FN** (False Negative) | 真实正向，预测为负向或中性 | 左下角 |
| **FP** (False Positive) | 真实负向或中性，预测为正向 | 右上角 |
| **TN** (True Negative) | 真实负向或中性，预测也是负向或中性 | 右下角 |

**理解记忆**：
- **T** = True = 预测正确
- **F** = False = 预测错误
- **P** = Positive = 正向/预测为正向
- **N** = Negative = 负向或中性/预测为负向或中性

#### （2）三分类混淆矩阵（情感识别）

**数据示例**：

| 真实值/预测值 | 预测为正向 | 预测为中性 | 预测为负向 |
|--------------|-----------|-----------|-----------|
| **真实正向** | 1435 | 10 | 6 |
| **真实中性** | 30 | 3247 | 45 |
| **真实负向** | 12 | 56 | 5643 |

### 3. 核心指标计算

#### （1）准确率（Precision）

**定义**：算法认为对的样本里面，有多少确实是对的

**计算公式**：

```
准确率 = TP / (TP + FP)
```

**案例（正向情绪）**：
- TP = 1435（预测正向，真实也正向）
- FP = 30 + 12 = 42（预测正向，但实际不是）
- 准确率 = 1435 / (1435 + 42) = 1435 / 1477

#### （2）召回率（Recall）

**定义**：本来是对的样本里面，算法找出来了多少对的

**计算公式**：

```
召回率 = TP / (TP + FN)
```

**案例（正向情绪）**：
- TP = 1435
- FN = 10 + 6 = 16（真实正向，但预测错了）
- 召回率 = 1435 / (1435 + 16) = 1435 / 1451

#### （3）F1值

**目的**：平衡准确率和召回率

**计算公式**：

```
F1值 = 2 × 准确率 × 召回率 / (准确率 + 召回率)
```

**原则**：期望准确率和召回率都越来越高

### 4. 业务场景指标选择

#### （1）业务背景回顾

**原始需求**：
- 用户有负面情绪时 → 先给安抚，再回答问题
- 用户有正向情绪时 → 考虑给鼓励

#### （2）不可接受的场景

**场景1**：用户有负向情绪，识别成正面向

**影响**：
- 用户已经很生气，还给他一个很正向的响应
- 违和感严重，完全不能接受

**场景2**：用户有正向情绪，识别成负向

**影响**：
- 用户表达了感谢或开心状态
- 但被识别成负向情绪
- 给了一句安抚："亲，您不要着急，我们马上帮您看一下"
- 违和感很重

#### （3）指标选择建议

**单目标场景**（只要负面时安抚）：
- 当前结果可用

**双目标场景**（负面安抚 + 正向鼓励）：
- 需要考虑：
  - 能否接受正向预测成负向
  - 能否接受负向预测成正向
- 根据业务容忍度选择指标

## 六、多数据源验证

### 1. 验证目的

基于当前业务场景，预留不同场景下的测试语料，验证模型在不同场景下的效果。

### 2. 验证流程

```
收集不同场景测试语料
    ↓
输入模型进行验证
    ↓
人工核对结果
    ↓
检查各场景准确率是否符合预期
    ↓
不符合 → 补充语料重新训练
    ↓
符合 → 上线
```

### 3. 验证案例

**情感识别模型测试**：

| 场景 | 抽取数量 | 准确率 | 结果 |
|------|---------|--------|------|
| 售前问题 | 100个 | 98%+ | ✓ |
| 售后问题 | 100个 | 98%+ | ✓ |

**异常情况处理**：

- 不同业务场景问法不同
- 表达方式有差异
- 情感识别结果不符合预期

**解决方案**：
1. 补充该场景语料，重新训练模型
2. 针对不同业务场景训练专属模型（非通用模型）

## 七、持续优化迭代

### 1. 优化方向

#### （1）收集线上bad case

**关注内容**：
- 明明是负向，被识别成正向
- 明明没有情绪，被识别成有情绪

**处理流程**：
1. 收集这些问句
2. 进行标注
3. 提供给算法工程师
4. 更新模型并测试上线

#### （2）更新线上语料

**原因**：业务持续变化

**建议**：
- 定期收集线上新用户问句语料
- 进行标注
- 提供给算法工程师更新模型

### 2. 效果天花板

**现实认知**：

> 算法效果可能受限于当前标注语料质量，也可能因为当前场景本身存在技术壁垒，需要寻求更深技术突破。

**案例**：
- 算法从70分提升到80分，可能需要算法工程师和标注团队付出非常多的努力
- 但如果加上产品设计辅助，从70分提升到85分还是很有希望的

└── 第3步：持续优化
    ├── 收集bad case
    └── 更新线上语料
```

### 关键指标公式

| 指标 | 公式 | 含义 |
|------|------|------|
| **准确率** | TP / (TP + FP) | 预测正确的占预测正类的比例 |
| **召回率** | TP / (TP + FN) | 预测正确的占实际正类的比例 |
| **F1值** | 2×P×R / (P+R) | 平衡准确率和召回率 |
