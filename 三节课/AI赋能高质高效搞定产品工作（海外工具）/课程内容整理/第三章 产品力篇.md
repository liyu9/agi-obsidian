# 第三章 产品力篇

## 第一节 产品规划

### 一、什么是产品规划

#### 1.1 产品规划定义

**定义**：在产品开发过程中，通过系统化思维和方法对产品的目标、功能、市场、资源和时间进行整体规划和管理，以确保产品成功推出和持续发展。

**核心要素**：
- 目标：明确产品发展方向
- 功能：规划产品应具备的功能
- 市场：分析目标市场和用户
- 资源：合理配置资源
- 时间：制定合理的时间计划

#### 1.2 规划的关键特征

| 特征 | 说明 | 反面案例 |
|------|------|----------|
| 可落地 | 规划是行动方案，不是愿景画饼 | "我们要成为行业第一" |
| 有边界 | 聚焦于产品问题 | 面面俱到但无重点 |
| 产价值 | 规划要带来产品价值 | 为规划而规划 |

#### 1.3 为什么要做产品规划

| 维度 | 说明 |
|------|------|
| **资源协调** | 产品线众多时，需要协调人力、开发、运营资源 |
| **把握方向** | 紧密结合市场用户变化，把握产品方向和商业模式 |
| **团队对齐** | 明确不同阶段做什么，团队对目标和方向清晰认识 |

**核心观点**：
> 产品经理是团队的掌舵人。只有你足够专业，你的团队才够专业。

### 二、产品规划考虑维度

#### 2.1 三大考虑维度

```
┌────────────────────────────────────┐
│      产品规划三维框架               │
├────────────────────────────────────┤
│  1. 产品阶段                        │
│     新产品 vs 成熟产品               │
├────────────────────────────────────┤
│  2. 汇报对象                        │
│     老板/投资人 vs 部门 vs 开发团队  │
├────────────────────────────────────┤
│  3. 规划周期                        │
│     长期(1-3年) vs 短期(3-6个月)    │
└────────────────────────────────────┘
```

#### 2.2 不同产品阶段的规划重点

| 产品阶段 | 规划重点 | 说明 |
|----------|----------|------|
| **新产品** | 分析说明方向可行性 | 全面论证，避免战略错误 |
| **成长期** | 突出迭代演进路线 | 确定需求功能优先级 |
| **成熟期** | 发现优化点 | 细分数据分析 |

#### 2.3 不同汇报对象的规划重点

| 汇报对象 | 规划重点 | 关注内容 |
|----------|----------|----------|
| **老板/投资人** | 商业价值 | 商业模式、市场空间、价值 |
| **部门** | 运营价值 | 对公司和其他业务线的价值 |
| **开发团队** | 清晰明确 | 产品路线，让团队理解一致 |

#### 2.4 不同规划周期的时间颗粒度

| 周期 | 时间跨度 | 颗粒度 | 重点 |
|------|----------|--------|------|
| **长期规划** | 1-3年 | 粗粒度 | 产品计划大纲、把控大方向 |
| **短期规划** | 3-6个月 | 细粒度 | 明确阶段目标、交付物 |

### 三、产品规划四步法

#### 3.1 第一步：目标分析

**内容框架**：

| 分析维度 | 具体内容 | 信息来源 |
|----------|----------|----------|
| 用户需求及痛点 | 目标用户核心痛点与需求 | 用户研究、用户画像、满意度调查 |
| 市场空间 | 目标领域市场机会与价值 | 行业分析、市场调研 |
| 产品现状 | 自身产品SWOT分析 | 竞品分析 |
| 发展策略 | 确定方向和商业模式 | 综合分析 |

**注意事项**：
- 不是所有分析维度都需要
- 展示内容要结合业务和汇报层级

#### 3.2 第二步：做什么

| 模块 | 内容 |
|------|------|
| **产品定位** | 产品愿景、目标用户、核心价值 |
| **产品蓝图** | 功能架构图、业务流程图 |
| **目标用户** | 用户画像、用户场景 |
| **差异化价值** | 商业价值、产品价值 |
| **产品路线图** | 分阶段规划、上线时间节点 |

**产品定位要素**：
- 产品是什么？
- 解决什么问题？
- 目标用户是谁？
- 核心价值是什么？
- 在什么场景下满足什么需求？

**产品路线图**：
- 需求在时间轴上的总体视图
- 展示不同阶段的目标和交付物
- 制定关键节点的里程碑

#### 3.3 第三步：怎么做

| 要素 | 说明 |
|------|------|
| **呈现形式** | 原型图、框架图、UX/UI设计图 |
| **产品策略** | 兼顾功能实现的逻辑方案 |
| **产品计划** | 里程碑、时间点 |
| **资源需求** | 资金、团队、运营、市场 |

**MVP原则**：
> 用最小成本验证核心假设，快速迭代。

#### 3.4 第四步：结论

**核心问题**：
- 市场需要什么？
- 用户需要什么？
- 我们有什么？

**结论框架**：
```
外部市场情况 → 业务发力点 → 用户/市场需求 → 内部优势 → 角色梳理 → 变现逻辑 → 突破点 → 核心功能 → 运营方式
```

### 五、产品经理PPT要点

#### 5.1 为什么PPT重要

**核心观点**：
> 会做事的，不如会写PPT的。

**原因**：
- 好内容需要好形式呈现
- 不会表达 = 事倍功半
- 产品也需要包装

#### 5.2 PPT制作原则

| 原则 | 说明 | 示例 |
|------|------|------|
| 字不如表 | 能用表格就不用文字 | 数据对比用表格 |
| 表不如图 | 能用图表就不用表格 | 趋势用折线图 |
| 数据有出处 | 标注数据来源 | "来源：艾瑞咨询2024" |
| 每页有结论 | 每页要有论点 | 先论点再论据 |
| 总分总结构 | 先总结再展开 | 开头总结，中间展开，结尾总结 |

#### 5.3 PPT内容本质

**核心认知**：
> PPT本质上是一篇议论文，只有论据没有论点是不行的。

**输出内容的意义**：
> 别人看到你的PRD和PPT，要看到的是这个人逻辑清晰、思维缜密，是个好的合作伙伴。

### 六、本节要点总结

#### 核心框架

```
产品规划四步法
├── 1. 目标分析 → 用户需求、市场空间、SWOT
├── 2. 做什么 → 产品定位、蓝图、路线图
├── 3. 怎么做 → MVP、计划、资源
└── 4. 结论 → 市场/用户/我们有的
```

#### 关键工具

| 场景 | 工具推荐 |
|------|----------|
| 大纲生成 | 豆包、腾讯元宝 |
| PPT制作 | WPSAI |
| 效率提升 | AI辅助提升4-6倍 |

#### 关键认知

> **产品经理输出的内容无论是PRD还是PPT，都是你对外的表达方式。** 要让别人看到你逻辑清晰、思维缜密。

## 第二节 产品流程设计

### 一、产品设计层次

#### 1.1 五层分析法

```
┌────────────────────────────────────┐
│          产品设计五层模型            │
├────────────────────────────────────┤
│  5. 表现层                         │
│     UI设计、视觉效果、可用性          │
├────────────────────────────────────┤
│  4. 框架层                         │
│     高保真原型、交互设计              │
├────────────────────────────────────┤
│  3. 结构层                         │
│     功能结构图、信息结构图、流程图     │
├────────────────────────────────────┤
│  2. 范围层                         │
│     PRD、功能需求、业务规划           │
├────────────────────────────────────┤
│  1. 战略层                         │
│     市场定位、目标用户、商业价值(MRD/BRD)│
└────────────────────────────────────┘
```

#### 1.2 产品设计原则

**从大到小原则**：
1. 从大场景出发，梳理各模块
2. 把模块串联成完整流程
3. 逐步设计细化每个流程和细节
4. 考虑不同角色的信息需求

**案例**：电商平台设计
- 买家：购物流程
- 卖家：商品管理流程
- 管理员：后台管理流程

### 二、产品设计五阶段

| 阶段 | 产出 | 说明 |
|------|------|------|
| **1. 功能列表** | 功能清单、成本、技术选型 | 明确产品需要什么功能 |
| **2. 流程设计** | 流程图 | 组织功能成完整流程 |
| **3. 结构设计** | 功能结构图、信息结构图 | 明确模块层级和信息分类 |
| **4. 原型设计** | 高保真原型 | 可视化呈现 |
| **5. PRD撰写** | 产品需求文档 | 完整需求说明 |

**重要提醒**：
> 需求评审会前，原型和PRD完整度至少95%以上。需求想清楚再入会，别被开发问住。

### 五、AI辅助流程图

#### 5.1 流程图基础

**常用符号**：

| 符号 | 名称 | 用途 |
|------|------|------|
| ○ | 开始/结束 | 流程起点和终点 |
| □ | 处理环节 | 执行的操作（最常用） |
| ◇ | 判断 | 条件分支 |
| → | 箭头 | 流程方向 |

**三大基本结构**：
- 顺序结构
- 分支结构
- 循环结构

#### 5.2 流程图类型

| 类型 | 特点 | 适用场景 |
|------|------|----------|
| 功能流程图 | 展示操作步骤 | 单角色流程 |
| 泳道图 | 跨职能流程图 | 多角色/多部门流程 |

#### 5.3 绘制注意事项

1. 从左到右或从上到下排列
2. 开始符号只能出现一次
3. 判断符号必须有"是"和"否"两种结果
4. 同一流程内符号大小一致
5. 连接线不能交叉
6. 处理流程需要单一入口和单一出口

#### 5.4 工具推荐

**ProcessOn**
- 使用年限：6年
- AI功能：AI助手绘图
- 效果：当前领域最佳

**AI辅助流程图提示词**：
```
请帮我生成一张团长开团的流程图。

流程描述：
1. 团长选择某商品
2. 提交订单进行支付
3. 检查支付状态
4. 成功则等待好友拼团
5. 检查是否成团
6. 成团/失败都结束
```

### 六、AI辅助结构设计

#### 6.1 功能结构图

**定义**：以功能模块为类别，介绍模块下各功能组成

**特点**：
- 采用"动词+名词"语言描述
- 体现功能从属关系
- 辅助思路梳理，避免功能缺失

#### 6.2 信息结构图

**定义**：脱离实际页面，抽象产品数据

**特点**：
- 类似数据库表结构设计
- 考虑数据组成、流动、关联
- 节点要素为名词

#### 6.3 AI辅助实操

**功能结构图提示词**：
```
【任务】
根据功能结构图说明，帮我生成参与拼团的落地页功能结构图。

【落地页描述】
当购买商品的团长开团成功后，分享拼团信息给好友，
好友点击拼团信息进入后的落地页。
```

**信息结构图提示词**：
```
【任务】
根据功能结构图清单，帮我生成对应的信息结构图清单。

【信息结构图说明】
脱离页面功能，考虑数据组成。
```

### 七、本节要点总结

#### 核心框架

```
产品设计流程
├── 五层模型：战略→范围→结构→框架→表现
├── 设计五阶段：功能→流程→结构→原型→PRD
└── AI辅助：功能列表→脑图→流程图→结构图
```

#### 关键工具

| 场景 | 工具推荐 |
|------|----------|
| 功能列表 | ChatGPT、质谱轻言 |
| 思维脑图 | Mapify |
| 流程图 | ProcessOn |
| 结构图 | 大模型+Mapify |

#### 设计原则

1. **从大到小**：先场景模块，后流程细节
2. **先功能后信息**：功能驱动，信息支撑
3. **颗粒度适中**：越细需求越精准
4. **善用AI不依赖AI**：结合业务判断

#### 关键认知

> **产品经理的职业要求就是"细"。专业方法熟能生巧，没有太多技巧，都是深入实践长期积累来的。**

## 第三节 原型设计与PRD撰写

### 一、产品方案呈现方式

| 方式 | 特点 | 适用场景 |
|------|------|----------|
| **原型** | 快速试错，直观表达 | 设计初期、沟通需求 |
| **PRD文档** | 完整系统，沉淀知识 | 需求评审、合同依据 |
| **宣讲** | 现场沟通，即时答疑 | 需求评审会 |

### 二、原型设计

#### 2.1 原型类型

| 类型 | 特点 | 适用场景 |
|------|------|----------|
| **手绘草图** | 快速、低成本 | 早期想法验证 |
| **低保真原型** | 简单标注 | 快速表达 |
| **高保真原型** | 接近实物，可交互 | 详细评审、真机体验 |

**推荐**：真机可交互原型，让团队实际体验

#### 2.2 AI辅助原型设计

**现状评估**：
- AI画原型目前效果一般
- 只能提供大概思路和灵感
- 细节调整耗时，不如自己画

**勉强可用的工具**：
| 工具 | 开发商 | 特点 |
|------|--------|------|
| 即时AI | 即时设计 | 国内产品 |
| 墨刀AI | 墨刀 | 功能有限 |

**使用场景**：
- 快速生成大概页面
- 提供设计灵感
- 生成草图参考

**即时AI使用示例**：
```
【任务】
帮我生成一张电商产品的拼团详情页

【模型选择】
根据描述类型选择对应模型
- 概述型描述：JSON模型
- 明细型描述：JSOI模型
```

**生成效果评估**：
- UI视觉角度基本过关
- 具体功能交互设计仍需人工调整
- 目前商用还有距离

### 三、PRD撰写

#### 3.1 PRD格式类型

| 类型 | 特点 | 适用场景 |
|------|------|----------|
| **Word文档** | 传统、详细、系统 | 复杂项目、政府/大B定制 |
| **原型标注** | 直观、快速 | 敏捷开发、初创公司 |

**Word版适用场景**：
- 需要全面系统性描述产品需求
- 功能复杂涉及多模块
- 政府项目或定制采购项目（合同依据）

**原型标注适用场景**：
- 敏捷开发团队
- 产品需快速迭代
- 小优化单一功能

#### 3.2 完整PRD结构

```
┌────────────────────────────────────┐
│          PRD文档结构                │
├────────────────────────────────────┤
│  1. 头部                           │
│     版本号、修改时间、修订记录        │
├────────────────────────────────────┤
│  2. 引言                           │
│     目的、阅读对象、参考资料、名词解释 │
├────────────────────────────────────┤
│  3. 产品介绍                        │
│     产品背景、定位、目标              │
├────────────────────────────────────┤
│  4. 产品结构                        │
│     蓝图、架构图、流程图、功能结构图   │
├────────────────────────────────────┤
│  5. 全局说明                        │
│     全局规则、异常说明、通用交互、规则范式│
├────────────────────────────────────┤
│  6. 功能说明                        │
│     功能介绍、操作界面、流程、规则、交互│
├────────────────────────────────────┤
│  7. 非功能需求                      │
│     统计需求、性能需求、兼容性需求     │
├────────────────────────────────────┤
│  8. 附录                           │
│     相关文档、超链接                  │
└────────────────────────────────────┘
```

#### 3.3 各部分说明

**全局规则**：
| 类型 | 内容 |
|------|------|
| 全局规则 | 图片裁剪方式、加载样式 |
| 异常说明 | 异常情况处理策略 |
| 通用交互 | 全局页面交互、提示内容 |
| 规则范式 | 图片尺寸、时间格式等 |

**非功能需求**：
| 类型 | 内容 |
|------|------|
| 统计需求 | UV、跳出率、DAU、留存、转化等 |
| 性能需求 | 页面加载时间等 |
| 兼容性需求 | 机型、系统适配 |
| 接口需求 | 第三方接口调用 |

#### 3.4 PRD常见问题

| 问题 | 建议 |
|------|------|
| 可以不写文档只画原型吗？ | 除非原型就是PRD，能完整表达 |
| 先写文档还是先画原型？ | 先画原型后写文档 |
| PRD质量如何评估？ | 正确、无歧义、完整、可验证 |
| 敏捷开发时PRD怎么写？ | 敏捷PRD，原型标注，快速迭代 |

**重要提醒**：
> PRD太丰富不是好事，开发兄弟不愿看长篇大论。只要能完整准确清晰简洁描述需求即可。
