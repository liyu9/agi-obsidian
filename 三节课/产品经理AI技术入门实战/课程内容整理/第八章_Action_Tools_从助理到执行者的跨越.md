# 第八章 Action & Tools：从助理到执行者的跨越

## 章节引入

接下来呢我们今天需要讲的action和tools，它其实是AI从说到到做到的一个关键。从简单的这种聊天互动到我们他能够帮你做一些事情的一个关键。

那今天我们就通过这个订票的案例，让你理解怎么样设计让AI真正动起来的一个流程。

## 实际应用场景

首先我们来举个例子，就想象一下你是做OTA的嘛，老板他让你去做一个AI助手。能够自动的去帮用户订一张明天的机票。

不仅仅是能够帮助订机票，还能够同时查找到最佳航班价格计算。这个其实现在国外已经有很多公司做到了，你比如说booking，他这些都是能够支持智能匹配住宿，茶酒店。根据用户的行为偏好去做一些AI的航班，整合酒店和交通，并且做出建议。

这个都是现在说实话已经很成熟的东西。

## Action和Tools的定义

### 什么是Action？

那什么是action和action呢？

**Action它就是AI它会根据你的需求，通过你的命令去进行一个工作**。

### 什么是Tools？

**Tools它就是调用外部工具或者服务帮助他完成工作**。这些工具可以是API第三方的应用，也可以是他自己内建的功能。

## Action机制的工作原理

那action机制它是怎么样动起来的呢？

就简单的说我们前面说的这个大源模型，他在收到用户的请求之后。比如说"帮我预定明天的机票"，他就会通过理解分析出用户的需求。通过大语言模型的分析，系统会进入action层。

在action层然后AI它会根据大语言模型的理解去选择合适的执行步骤。它不仅仅是给出一个语言回答，而是触发实际的任务。

比如说要用外部的航班查询工具去进行一个支付和处理。

假如你告诉AI"你帮我发一封确认邮件，告诉对方我接受了会议的邀请"。那选择行动的话，哎，他在完成执行任务的时候，他会调用邮件工具，准备邮件内容，确认收件人，邮件发送完成之后，AI他会反馈"邮件已经发送"。

在这个过程中间，AI不仅仅是回答"好的"，而是通过实际行动完成了发送邮件的任务。

**同样类比一下我们昨天讲的output，它是大语言模型生成的一个原内容，他对用户的答复是，比如说"好的，我已经帮你预定了机票"或者是"预定成功航班是什么"**。

那**action它是根据大语言模型分析后的指令选择并且执行某个操作，这个并不是语言内容，而是一个执行层面的动作，他做的是做事的实际操作**。

## Tools机制

那我们的tools机制又是什么呢？

那我们的工具是AI可以调用的外部服务或者是API帮助我们的AI去执行更复杂的任务。通过工具呢AI它能够超越自己的内景功能，调用外部系统来解决更多的问题。

那我们有人就问了，**为什么要用tools**？因为它其实就是起到一个联动的作用。它是可以去访问网络，查询数据库和其他的系统对接。它让这个AI能够在执行任务的时候拥有更多的资源支持。

## Action和Tools的交互流程

那**action它和tools的交互流程我们来列一下**，就这两个机制是必须配合使用才能够让AI发挥最大的作用的。

是不是有点像我们前面说到的那个decoder和output，其实他们这两个也是紧密配合的。

就action呢，他是决定AI要做什么，tools它就帮助AI去执行任务。**没有action的话，AI就只能够说话，但是没有tools呢哎它的做事能力就会受到一定的限制**。

那么完整的交互流程，从产品经理的角度来看：

1. **用户提出请求**："帮我发一封邮件"
2. **AI选择行动**：就是发邮件这个动作
3. **调用工具**：调用邮件工具
4. **执行任务**：发送邮件
5. **反馈结果**：再反馈"邮件已经发送"

**他是这样一个tools流程就能够**。

## 产品经理如何设计Action和Tools机制？

那作为产品经理的话，你要怎么去设计AI的action和tools机制呢？

那你也知道AI不仅仅是能说话，还要能做事。

**那第一步就是需要我们去定义任务的目标**：我们需要去确定用户需要AI去执行哪些任务。

**那设计任务的流程就是AI执行任务的时候步骤是什么，每一步要采取哪些行动**。

然后**根据任务目标选择合适的外部工具来支持AI的行动**。比如调用外部的API第三方服务，或者是使用内建的一个工具。

**第三步就是我们的设计交互流程**：我们要确保AI执行任务的时候能够顺畅地切换到action和tools，达到自然的用户体验。

那设计怎么样将用户执行结果及时地反馈给用户，确保用户能够快速地了解任务进度或者完成情况。

## Action和Tools的真实行业场景

我们设计这个action和tools功能能够满足哪些真实的行业场景需求呢？

这个应该也是我们的很多产品经理感兴趣的。就为什么产品经理除了在前面的这些概念之外，你还要去理解action和tools？

### 医疗场景

比如说我们在医疗场景。AI用户他可以去让AI帮他预约下周三的心脏科的专家号。

那这个时候的话，AI其实是可以直接调用医院挂号系统去对接医院的系统接口。然后执行预约并且反馈结果的。

这个时候就不需要像我们现在一样，先去搜某一个医院，再去查某个医生有没有号，再去我们自己去预约。那现在AI可以帮我们做到这一步。

### 电商场景

那比如说电商场景的时候，用户想退货，我们就可以发起退货流程。那我们的tools就可以去调用订单系统的API加上物流的接口自动地去退货。

## Tools的技术选型

另外一个呢就是我们tools的技术选型。如果你不会代码也可以，因为你主要是去评估几个维度：

| 评估维度 | 说明 |
|---------|------|
| **工具的稳定性** | 确保我们可以正常去调用 |
| **延迟** | 延迟其实对用户来说影响还是挺大的 |
| **成本** | 我们要肯定产品经理是需要去考虑投入产出比的 |
| **合规性** | 如果是不符合法律法规，那肯定就是有问题的 |

## Action设计的安全机制

**Ok那action设计怎么样让AI不闯祸**，是因为你把它设计出来了，它就直接去执行了，对不对。那直接执行肯定会出现误操作，这个误操作就需要我们从**权限管控、结果可追溯、失败回退机制**这几个方面去进行一个全面的把控：

### 权限管控
- 我们在执行高风险动作前，必须要进行二次确认

### 结果可追溯
- 所有的执行必须有记录日志

### 失败回退机制
- 如果调用失败的时候，你需要去进行一个回退机制

## 用户体验的节点设计

**怎么样让用户能够感觉到从action到tools它能够让用户感觉到AI是靠谱的？**

这个时候就需要我们把执行路径去做一个节点切分：

| 阶段 | 用户感知 | 设计要点 |
|------|---------|---------|
| **执行前** | 明确的告知用户到底要做什么 |
| **执行中** | 显示进度状态 |
| **执行成功** | 结构化反馈相关的信息 |
| **执行失败** | 提供补救方案 |

每一个节点都需要有你对应的措施以及情感化的设计技巧。

## Action和Tools的产品思维底层逻辑

**那最后呢就是我们的action和tools的产品思维底层逻辑**。

它其实就是**AI的行动力 = 精准的意图识别 + 合理的动作编排 + 可靠的资源支持**，这缺一不可的。

我们不要去盲目地追求过多的动作，也不要去忽视工具的它的运维成本，更不要忘记去教育用户。
