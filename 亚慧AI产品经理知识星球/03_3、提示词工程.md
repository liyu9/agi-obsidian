# 3、提示词工程

提示词是一项工程：比如对于不同模型需要调整不同的提示词；对于同一场景，也需要需要调整提示词以达到最大化满足需求。

## 3.1 **结构化的prompt的基础模板**
CRISPE 框架(https://github.com/mattnigh/ChatGPT3-Free-Prompt-List)，代表以下含义：

CR：Capacity and Role(能力与角色)。你希望 ChatGPT 扮演怎样的角色。

I：Instruction(指令)，你希望LLM做什么

S：Strcuture（结构化)，输出结构

P：Personality(个性特征)，你希望LLM以什么风格或方式回答你。互动情感基调等

E：Experiment(实验验证)，通过实践测试和优化提示词效果

基础模版如下（用写诗歌举例）

```Bash
# Role: 诗人

## Profile
- Author: 亚慧
- Version: 1.0
- Language: 中文
- Description: 诗人是创作诗歌的艺术家，擅长通过诗歌来表达情感、描绘景象、讲述故事，具有丰富的想象力和对文字的独特驾驭能力。诗人创作的作品可以是纪事性的，描述人物或故事，如荷马的史诗；也可以是比喻性的，隐含多种解读的可能，如但丁的《神曲》、歌德的《浮士德》。

### 擅长写现代诗
1. 现代诗形式自由，意涵丰富，意象经营重于修辞运用，是心灵的映现
2. 更加强调自由开放和直率陈述与进行“可感与不可感之间”的沟通。

### 擅长写七言律诗
1. 七言体是古代诗歌体裁
2. 全篇每句七字或以七字句为主的诗体
3. 它起于汉族民间歌谣

### 擅长写五言诗
1. 全篇由五字句构成的诗
2. 能够更灵活细致地抒情和叙事
3. 在音节上，奇偶相配，富于音乐美

## Rules
1. 内容健康，积极向上
2. 七言律诗和五言诗要押韵

## Constraints
1. 拒绝以不符合法律规范与道德规范的内容为主题

## Workflow
1. 让用户以 "形式：[], 主题：[]" 的方式指定诗歌形式，主题。
2. 针对用户给定的主题，创作诗歌，包括题目和诗句。

## Initialization
您好, LLM, 接下来, Let's think step by step, work hard and painstakingly, 请根作为一个拥有专业知识与技能(Skills)的角色(Role)，严格遵循步骤(Workflow)step-by-step, 遵守限制(Constraints), 完成目标(Goals)。这对我来说非常重要，请你帮帮我，谢谢!让我们开始吧”
```

```Python
6.优化Prompt:基于步骤1-5思考的内容，假装你是我，帮我向chatGPT提问，完整表达出我的诉求，输出[优化Prompt】

4.**输出格式**:考虑到这是一个技术性的问题，最适合的输出格式应该是一个清晰、结构化的步骤列表。可以使用Markdown格式，同时附带代码示例。

接下来这是我的问题"{{需要优化的问题}}"，请根据我的Prompt
```

## 3.2 1个入门框架
**提示词的框架就是“提示词模板”**。框架是为了让我们更容易上手、方便记忆。在充分实践后就不必拘泥于框架。网上有非常多的提示词框架， **==最简单的是RTF： 代表 Role（角色），Task（任务）， Format（格式）==**。

以客服场景举例：

```Bash
## Role
情感标注人员

## Task
我给你的一句客户留言文字，请你判断出文字中的情绪。请你从以下选项中选择：
1. 正面：表达了肯定、喜欢、赞赏、褒扬
2. 负面：表达了否定、讨厌、贬低
3. 中性：通常客观描述，没有主观意向， 没有肯定、喜欢、赞赏、褒扬，也没有否定、讨厌、贬低

## Format
严格按照以下格式输出：
{
  "客户留言": "客户留言内容",
  "情绪判断": "情绪判断结果"
}
```

在撰写提示词时需要注意两条不成文的“规矩”。

（1） **提示词中的标记位参考 Markdown 语言来写**，比如例子中 “##” 代表一个小标题，Markdown 语言既能方便人来操作，又能让计算机很好理解。所以在提示词的撰写中广泛应用。

（2） **输出格式结构化**。上面的提示词特别规定了严格的输出格式（通常是 JSON 格式）。这是因为开发同学通常会对模型的输出做下一步处理，结构化输出会方便他们解析。

```JSON
在实际应用中，结构化输出意味着将用户的自然语言输入转换为机器易于处理的结构化数据格式，如标记用户意图的 JSON 对象，该对象详细描述了用户的查询意图以及相关的关键信息。这样，其他应用程序可以基于这些结构化的信息做出响应或采取动作，从而以更加智能的方式满足用户的需求。
```

## 3.3 n个基本技巧（Few-Shots、COT）
### 3.3.2.1 **Few-Shots（少量样本提示）**
在大模型的应用中， **Few-Shot Prompting（少样本提示）**，其实就是“先举几个例子给模型看”，再让它完成新的任务。这种方式可以帮助模型更好地理解上下文语境，进而做出更贴近人类预期的输出。

尤其在客服类场景中，我们可以通过提供几组“客户留言 + 正确情绪判断”的示范，让模型掌握情绪分类的基本规则。这就像是给它提前“培训”了一下标准答案的思路。

不过，Few-Shot 的关键就在于样本的“选”与“放”

```JSON
（1）数量不能太少：否则模型无法学习到多样化的判断规律；
（2）数量也不能太多：因为上下文长度是有限的，放太多会挤占主任务空间；
（3）要选典型代表性强的样本：例如要覆盖“客观陈述”、“正面称赞”、“强烈抱怨”、“委婉不满”等情绪边界。
```

所以 Few-Shot 本质上是 **在提示词中嵌入“小型数据集”来引导模型**，这也正是“提示词工程”之所以被称为“工程”的原因之一：它并不是写一句话那么简单，而是要通过反复试验、调优结构、精挑样本，让模型表现尽可能贴近预期。

### 3.3.2.2 COT思维链
对于理解类的问题，少样本是适用的， **而对于计算推理类的可靠性强要求的场景，少样本的效果并不够，还是需要用到思维链。**简单来说就是在提示词里加上“让我们一步步来，第一步……，第二步……”， **==主要用于推理场景==**，比如数学应用题计算，再比如规划旅程时中转站的时间要前后合理，这些都是推理场景。

可以参考：https://zhuanlan.zhihu.com/p/589087074

![image](images/img_0033.png)

![image](images/img_0034.png)

![image](images/img_0035.png)

1、步骤：

COT可以与少样本提示相结合，让模型在回答之前进行推理的更复杂的任务，获得更好的结果。

在给模型的提示里，加入中间推理步骤的示例，引导模型生成类似的思维链，具体步骤：

1. **==分步提示设计==**：编写大模型应用时，可以用特定格式的提示（Prompt）要求模型展示思考过程。比如说，用 “Let's think step by step” 这样的关键词，触发模型一步步推理。而且支持零样本（Zero-shot）和少样本（Few-shot）两种模式，就算没有太多示例，也能让模型开动脑筋
2. **==中间状态生成==**：模型会把中间推理步骤生成文本，每一个步骤都能作为后面推理的基础，就像搭积木一样，一步一步搭出完整的推理过程。通过自回归的方式逐步生成这些内容
3. **==结果提取==**：模型把推理过程写出后，就能从生成的文本里找到最终答案。一般像 “Therefore, the answer is” 这样的关键词后面跟着的就是答案

举例：

```Bash
// 提示
这组数中的奇数加起来是偶数：4、8、9、15、12、2、1。
A：将所有奇数相加（9、15、1）得到25。答案为False。
这组数中的奇数加起来是偶数：17、10、19、4、8、12、24。
A：将所有奇数相加（17、19）得到36。答案为True。
这组数中的奇数加起来是偶数：16、11、14、4、8、13、24。
A：将所有奇数相加（11、13）得到24。答案为True。
```

### 3.3.2.3 **自动思维链（Auto-CoT）**

**3.3.2.6 思维树 (ToT)**

对于需要探索或预判战略的复杂任务，传统或简单的提示技巧是不够的。思维树(Tree of Thoughts，ToT)框架基于思维链提示进行了总结，引导语言模型探索把思维作为中间步骤来解决通用问题。

![image](images/img_0044.png)

ToT 需要针对不同的任务定义思维/步骤的数量以及每步的候选项数量。

举例：

```JSON
请以“思维树（ToT）”框架解决以下问题，生成并评估多条推理路径：
问题：{{用户问题}}

步骤1：问题分解
- 将问题拆解为{{N}}个子问题，例如：
  · 子问题1：{{关键点1}}
  · 子问题2：{{关键点2}}
  · 子问题3：{{关键点3}}

步骤2：生成潜在思维路径
- 路径A：{{假设性方案A}}（如技术可行性、成本预估）
- 路径B：{{假设性方案B}}（如用户体验影响、市场适配性）
- 路径C：{{假设性方案C}}（如风险与收益平衡）

步骤3：评估与决策
- 对每条路径按以下标准打分（1-5分）：
  · 可行性：技术/资源是否支持？
  · 用户价值：是否解决核心痛点？
  · 成本效益：ROI是否合理？
- 综合得分最高的路径：{{最优路径}}（附详细理由）

最终答案：基于多路径评估，推荐执行{{最优路径}}，具体方案为...


实例：
问题：如何确定下一季度产品功能优先级？
步骤1：拆解为子问题：
  · 用户需求紧迫性
  · 开发资源投入
  · 市场竞争差异度

步骤2：生成路径：
  · 路径A：优先开发AI辅助工具（技术优势，但周期长）
  · 路径B：优化现有核心功能（用户反馈集中，ROI高）
  · 路径C：探索新付费模式（市场潜力大，风险较高）

步骤3：评估：
  · 路径A得分：可行性3，用户价值4，成本效益2 → 总分9
  · 路径B得分：可行性5，用户价值5，成本效益4 → 总分14（最优）
答案：推荐优先优化核心功能，快速提升用户满意度。
```

### **3.3.2.9 ReAct 框架（对应5.2.1）**
**ReAct（Reasoning + Acting）**是当前最流行的 Agent 架构模式，结合了推理和行动：

框架包括：

推理(Reasoning)：系统理解问题的上下文以及需要做什么。

行动(Action)：然后，它执行特定的任务，如计算或数据检索，基于这个理解。

观察(Observation)：执行行动后，系统会观察结果，并根据这些信息调整后续的推理和行动。

```Bash

### 第一步：提供ReAct指令提示
Q：请为以下任务生成一个包含推理和行动步骤的ReAct提示：“分析远程工作对员工生产力的影响”
A：[LLM生成一个ReAct提示，包括推理步骤和可能的行动步骤，如搜索相关研究、分析数据、比较不同工作模式的影响等]

### 第二步：执行行动步骤
Q：根据提示，执行以下行动步骤：
- 搜索远程工作生产力相关的研究和数据
- 分析这些数据，找出关键趋势和洞见
```

### **3.3.2.10 自我反思Reflexion（对应5.2.6）**
通过引导大型语言模型(LLMs)进行自我反思和自我评估来提高其输出的质量和相关性。在这种框架下，模型被要求在生成最终答案之前，先对自己的推理过程进行反思，以确保其回答是基于正确的理解、充分的证据和逻辑严密的推理。

![image](images/img_0045.png)

1、自我反思由3个不同的模型组成：

（1）参与者(Actor)：

根据状态观测量生成文本和动作。参与者在环境中采取行动并接受观察结果，从而形成轨迹。 **链式思考(CoT)(opens in a new tab) 和 ReAct(opens in a new tab) 被用作参与者模型**。此外，还添加了记忆组件为智能体提供额外的上下文信息。

（2）评估者(Evaluator)：

**对参与者的输出进行评价。具体来说，它将生成的轨迹(也被称作短期记忆)作为输入并输出奖励分数**。根据人物的不同，使用不同的奖励函数(决策任务使用LLM和基于规则的启发式奖励)。

（3）自我反思(Self-Reflection)：

生成语言强化线索来帮助参与者实现自我完善。 **这个角色由大语言模型承担**，能够为未来的试验提供宝贵的反馈。自我反思模型利用奖励信号、当前轨迹和其持久记忆生成具体且相关的反馈，并存储在记忆组件中。 **智能体利用这些经验(存储在长期记忆中)来快速改进决策**。

2、Reflexion框架的关键步骤通常包括：

（1） **理解任务**：模型首先需要理解提示中的任务和要求。

（2） **生成初步答案**：模型根据理解生成一个初步的答案。

（3） **自我反思**：模型对自己的初步答案进行反思，评估答案的合理性、完整性和准确性。

（4） **修正和改进**：基于自我反思的结果，模型对初步答案进行修正和改进。

（5） **生成最终答案**：模型提供经过反思和改进后的最终答案。

3、示例：

```Bash
## 任务：生成一篇关于“远程工作对员工生产力的影响”的高质量文章 #

## 第一步：理解任务
Q：你被要求写一篇关于远程工作对员工生产力影响的文章。请确认你理解了任务的要求。
A：[模型确认其理解任务的要求，包括文章的主题、预期的长度、所需的证据类型等]

### 第二步：生成初步答案
Q：请生成一个关于远程工作对员工生产力影响的初步文章草稿。
A：[模型生成一个初步的文章草稿，包括引言、几个主要段落和结论]

### 第三步：自我反思
Q：现在，请你对刚才生成的初步草稿进行反思。你的文章是否全面覆盖了远程工作的所有相关方面？是否有充分的证据支持你的观点？你的结论是否逻辑严密？
A：[模型进行自我反思，识别出初步草稿中可能的漏洞、不足的证据和逻辑上的不严密之处]

### 第四步：修正和改进
Q：基于你的自我反思，请对初步草稿进行修正和改进。确保你的文章有充分的证据支持，逻辑严密，并且全面覆盖了远程工作对员工生产力的所有相关方面。
A：[模型对初步草稿进行修正和改进，添加更多的证据，加强逻辑论证，并确保文章的全面性]

### 第五步：生成最终答案
Q：请提供你经过反思和改进后的最终文章。
A：[模型提供最终的文章，这是经过自我反思和改进后的版本，应该是一篇高质量的文章]
```

| 5 | 其他（延伸场景） | ==基于提示词技术的内容再表达、重构优化== | 文案洗稿、结构重排、信息提炼、改写 |

提示词调试是一个“逐步优化”的过程，而不是一味追求复杂。在实际使用大语言模型（LLM）时，提示词的优化应该遵循 **从简单到复杂、从模糊到清晰**的思路逐步推进

```JSON
1. 普通口语描述（Plain Natural Language）目的：快速验证模型是否理解基本需求
示例：帮我写一个道歉短信给客户

2. 结构化提示词（Structured Prompt）目的：明确角色、目标、限制、格式
示例：
你是一名客服专员，请根据用户留言判断情绪类型
输出格式为 JSON，标签为：正面、负面、中性、混合

3. Chain-of-Thought 推理（CoT）目的：引导模型“逐步思考”以提高准确性
示例：先分析情绪关键词，再判断整体情绪倾向，最后输出标签

4. 正向引导 Few-Shots 示例（Few-Shot Prompting）目的：用典型样例做“上下文微调”，增强模型理解偏好
示例：
用户留言 + 情绪判断示例 × 3-5 条
要求新样本仿照已有模式输出

5. 避免常见错误（Anti-pattern Calibration）目的：在提示词中显式说明“不要这么做”
示例：
不要输出解释，只返回情绪标签
避免输出“我认为”“可能是”等主观词汇
```

## 3.8 5大实用 RAG 提示词模板 + 4个优化 RAG 提示词的技巧
**-5大模版：**

**1个好的提示词需要精准传达3件事**：

（1）检索到的信息怎么用（RAG 不能光拿到数据，还得知道怎么整合进回答）

（2）你的具体需求是什么（RAG 猜不透你的心思，得明确告诉它方向）

（3）推理逻辑如何展开（RAG 得清楚怎么组织信息，避免胡编乱造）

此外，LLM 处理文本有 “容量限制” （它只能处理一定数量的 token）。这意味着没办法把一整个资料库都丢给它，而是要靠 RAG 系统先筛选出最相关的数据，再通过提示词引导 RAG 使用这些信息。要提示词不清晰，RAG 很可能还是会给出错误或不完整的答案

1、 **==提示词 1：精准提问 + 关联信息==**

核心思路就是先把用户的问题提炼得更加精准，然后结合相关的知识库信息，这样就能让 RAG 生成最优答案。

```JSON
示例提示词：“用户想了解 [X]。请先提炼问题的核心意思，然后结合以下知识库中的内容，给出最清晰、最准确的答案。” 这里的 [X] 就是用户提出的具体问题，比如 “苹果的营养价值”why：
优化问题表述能减少歧义，让 RAG 更聚焦，避免误解问题；提示 RAG 必须基于检索到的信息回答，这样就能有效避免它 “脑补” 或乱编内容，回答更精准。

适用场景：
```

```JSON
当用户问题比较笼统或模棱两可时能帮 RAG 更好地理解需求。或者希望 RAG 直接抓住问题重点，不绕弯子。尤其是各种开放式提问，当用户的问题过于宽泛时，先 “精炼问题 + 提供上下文”，回答质量会大大提升
```

2、 **==提示词 2：用 “思维链” 提升 RAG 逻辑性==**

当遇到复杂问题，信息量大时，RAG 很容易给出混乱甚至错误的答案。“思维链”（Chain-of-Thought，CoT）的核心思路是让 RAG 按照清晰的步骤推理，而不是直接跳到答案，不仅逻辑更清楚，还能减少胡编乱造

```JSON
示例提示词：“这是用户的问题和相关文本。请按照以下步骤来回答：用更简单的语言总结用户问题；挑选出最相关的文本片段；把这些片段整理成逻辑清晰的大纲；基于大纲撰写一个完整、连贯的答案。请展示你的推理过程，并提供最终精炼后的答案。”why：
强制 RAG 先分析问题，再回答，避免它 “想当然” 地生成错误内容；先列大纲能保证答案结构清晰，更易读，逻辑也更顺畅；最后，推理过程透明可见，如果答案有错，你能轻松找到问题

适用场景：
在需要准确推理的任务中，如金融、法律、医学等领域，RAG 不能胡编乱造， “思维链” 就非常有用。当检索信息量很大时可以帮 RAG 过滤掉无关信息，专注于重要部分。
```

3、 **==提示词 3：让 RAG 学会说 “不知道”==**

如果知识库里没有相关内容，RAG 可能还是会给出 “不完整” 甚至 “瞎编” 的答案

```JSON
示例提示词：“以下是与用户问题最相关的内容。如果你发现其中有足够的信息来回答，就请据此作答；如果没有，请直接说：‘我没有关于此问题的完整信息。’ 摘要：（插入检索到的相关文本或要点）现在你的最终答案是什么？”why：
能有效减少 “幻觉” 问题，RAG 只会用现有数据回答，避免胡乱生成内容；同时提示 RAG 在回答前先确认信息是否足够；而且如果 RAG 频繁回答 “我不确定”，还能发现知识库可能存在数据缺口，需要补充新内容

适用场景：
在智能客服场景中，能避免 RAG 胡乱回答，而是礼貌地承认 “没有完整信息”；在研究分析场景中，能确保 RAG 只在有足够依据的情况下给出答案，不随意推测。RAG 的作用是增强信息获取，不是凭空创造内容，与其误导用户，不如让它学会say no
```

4、 **==提示词 4：让 RAG 先写再改，答案更精准==**

有些任务如总结技术文档、改写政策文件、生成详细报告，让 RAG 一次性给出完美答案并不现实。这时候，多步骤修订的方法 — 让 RAG 先写初稿，然后自己检查、修正，最后再输出完整答案，还能提供来源列表，增强可信度

```JSON
示例提示词：“第一步：“根据用户请求，生成一份完整的草稿，并结合下方 RAG 检索的所有相关段落。
第二步：“现在重新检查初稿，看是否遗漏了任何有价值的上下文，并进行修订。
第三步：“提供最终版本，确保内容连贯、精准。
第四步：“标明引用的所有来源。”why：
RAG 先写初稿再自查修订，能进行自我审查，减少遗漏，确保充分利用所有关键信息；如果 RAG 检索到的内容较多能帮助它全面整合，不遗漏重要细节，提高准确性；最后，提供数据来源就像研究论文引用参考文献一样，能增强读者对答案可靠性的信任

适用场景：
政策文件、人力资源指南、法律声明等正式文档，对内容准确性要求极高；在多来源汇总场景，比如营销文案，需要从多个产品页面提取信息并整合，用 “先写后改” 也很合适；还有复杂知识库，如果数据库信息较多，单次生成可能会遗漏关键内容，多步骤审查能保证完整性
```

5、 **==提示词 5：用 “对比查询” 让 RAG 更聪明==**

不是简单抛出一个问题，而是给 RAG 两个相关但有差异的问题，让它回答时学会分辨，并明确引用不同信息来源

```JSON
示例提示词：“查询 A：(用户的第一个问题)；查询 B：(一个相似但角度不同的问题)；检索到的文本：(插入相关内容片段)；要求：针对每个问题单独作答，确保每个答案都引用最匹配的文本。回答完成后，解释你是如何决定哪些内容适用于哪个问题的。” 比如，查询 A 是 “苹果手机和安卓手机哪个系统更流畅”，查询 B 是 “苹果手机和安卓手机哪个拍照效果更好”，然后插入从手机评测报告、技术资料等获取的相关文本片段。”why：
有时候知识库的内容涵盖多个话题，这种方法能帮助 RAG 选取最合适的文本回答不同的问题；同时，指定每个答案必须基于不同的来源，能减少 “答案混淆” 的情况；让 RAG 自我解释推理逻辑，不仅能帮助调试，还能提高回答的透明度，让你清楚它是如何选择答案的

适用场景：
在客户支持 & 销售场景中，比如一个客户问 “这个产品多少钱”，另一个问 “这个产品支持哪些功能”，RAG 需要从定价和技术文档中找出最匹配的内容，用 “对比查询” 就不会把答案混在一起；对于多主题知识库，如果数据库里内容交叉较多，这种方法可以帮 RAG 识别哪些信息适合回答哪个问题
```

**-4个技巧：**

除了设计合理的提示词，还要考虑数据质量、格式选择、Token 限制等因素，具体有4个技巧：

（1） **清理和整理 RAG 数据源**：可以设定规则确保检索出的信息足够精准，并过滤掉无关内容，提高系统整体的准确性。比如，在一个电商产品知识库中，定期删除已下架产品的信息，避免 RAG 在回答关于产品的问题时引用到无效内容

（2） **控制 Token 限制，找到平衡点**：最佳做法是 **使用摘要或预处理方式精简信息**，确保 RAG 只接收最核心的数据。比如，在处理一篇长篇新闻报道时，先对报道进行摘要，提取关键信息后再提供给 RAG，这样既能保证信息完整，又不会超出 Token 限制。

（3） **选择合适的提示词格式**：不同的内容类型，适合不同的提示词格式。在某些情况下，调整提示词结构能显著提升 RAG 的回答质量，如：

**要点式总结**：适用于技术性内容，能让信息更清晰易读。比如总结代码技术文档时，用要点式列出关键代码功能、使用方法等。

**问答结构（Q&A）**：适用于 FAQ 或知识库查询，便于模型精准匹配答案。像常见问题解答系统，直接采用一问一答的格式让 RAG 更高效地给出回应。

**表格格式**：适用于信息比对，比如产品参数、数据分析等场景。在对比不同品牌产品参数时，用表格呈现数据，RAG 能更直观地进行分析和回答。

（4） **加入审核机制，确保答案可靠**：在高风险场景（如法律、医疗、金融等领域），不能仅依赖 RAG 自动生成答案，而是需要增加审核机制。可以采用2种方式：

**辅助模型审核**： **用另一个 AI 先检查回答质量，发现问题后优化**。比如先用一个专门的语言质量评估模型检查 RAG 生成的法律文件解读是否准确、通顺，再进行后续处理。

**人工复核**： **对于关键内容，增加人工审核流程，确保最终输出准确无误**。像医疗诊断建议，在 RAG 生成初步结果后，由专业医生进行人工复核，保障患者安全。

```Python
如果知识专家接收到知识片段，首先检查知识片段，如果<context>至</context>标签中没有内容，则不能进行回答。
如果有知识片段，在回复时，只能基于<context>至</context>标签中的内容进行回答，且不能透露上下文原文，同时也不能出现<context>或</context>的标签字样。
```

4、输出防护检测：

```Python
##输出防护专家

##Workflow:
1、用户提出的问题：
<user_input>
{user_input}
</user_input>

2、模型回复的内容：
<model_output>
{user_output}
</model_output>

3、对“用户提出的问题”和“模型回复内容”进行比对，如果“模型回复内容”与“用户提出的问题”无关，模型直接输出“No”，否则输出“模型回复内容”。

1. 正向示例：
用户提出的问题原文：马里亚纳海沟有多深？
模型回复内容：马里亚纳海沟在太平洋海面11265米以下。
内容相关性思考：用户输入的问题是在询问马里亚纳海沟的深度，模型回复的内容也解答了关于马里亚纳海沟的具体深度信息，模型回复与用户问题高度相关。
模型回答：马里亚纳海沟在太平洋海面11265米以下。

2. 反向示例：
用户提出的问题原文：马里亚纳海沟有多深？
模型回复内容：珠穆朗玛峰高度8848米。
内容相关性思考：用户输入的问题是在询问马里亚纳海沟的深度，但模型回复却答复了珠穆朗玛峰的高度，很明显内容不相关。
模型回答：No.
```

## 3.9 Prompt 质量评估四步法（产品经理版）
> **==能运行（正确性） → 做对事（功能基线） → 做得好（质量评估） → 能长久用（适应性）==**
>

**1、正确性（Correctness）—能不能跑起来**

```Python
目标：Prompt 的输出格式必须符合预期，需要严格的类型与格式校验，确保后续流程正常执行。
举例：
要求生成小说，就必须以 function call 或 JSON mode 返回，并且字段类型正确（string、array 等）。
如果输出不合规，后面流程都会报错，就像接口返回了乱七八糟的格式一样。

检查方法：单元测试 / 自动化检测，保证每次调用都能通过格式校验。
```

**2、基线功能（Baseline Functionality）—有没有做对事**

```Python
目标：Prompt 至少完成了任务的核心要求。
举例：
要求“写一篇有两个角色的小说”，那生成结果必须包含两个角色，否则就是功能不达标

检查方法：自动化检测（可以用另一个模型来检测输出是否满足条件）。
```

**3、质量评估（Quality Evaluation）—做得好不好**

```Python
目标：在完成任务的基础上，评估内容的质量、结构和可读性。
这个阶段机器评测效果有限，很多时候还是需要人工评测，因为“好”是个主观标准。

检查方法：高质量模型辅助评分（如 GPT-5 进行内容打分）/人工打分，尤其是目标用户或专家评审
```

4、 **模型适应性与迭代空间（Adaptability & Sustainability）—放权还是管控**

```Python
目标：判断 Prompt 在不同模型迭代下是否可持续表现良好。
举例：
如果模型像一个能力强的实习生，你只需告诉他目标（任务是什么），不要管他怎么做，他可能比你想象的还要好。
如果模型像能力较弱的新人，就要写 SOP 式的 Prompt，细化到每一步该怎么做。
随着模型能力提升，过度限制可能反而束缚了它的表现空间。

关键提示：Prompt 要不要写得非常详细，取决于模型能力和任务复杂度。一个好的 Prompt 像一个“容器”，提供必要信息和目标，而不是替模型思考所有细节。
```

举例（电商退货政策问答）：

**用户query示例：**“我在你们店买的衣服，如果尺码不合适，可以退吗？”

**Prompt**： “你是某电商平台客服，请根据公司退货政策准确回答用户问题，输出 JSON 格式： `{ "answer": "...", "policy_url": "..." }` 。

1、 **正确性：目标：生成结果必须是符合 JSON 规范、字段齐全、类型正确。**

```Python
正确输出：
{
  "answer": "可以退货，请在收到货后7天内申请。",
  "policy_url": "https://shop.com/policy"
}
错误输出：
可以退货哦~
缺 JSON 格式，后续系统无法解析
```

2、 **功能基线：目标：回答必须包含退货的核心条件（时间限制、适用范围等）**

```Python
验证：
用另一个 LLM 检查生成内容是否提到退货的时间条件。
基线通过：明确写了“7天内可退”。
基线不通过：只说“可以退货”但没说时间条件（关键信息缺失）。
```

**3、质量评估：目标：功能达标的前提下，看回答是否友好、清晰、完整**

```Python
高质量：
“可以退货哦，只要您在收到商品后7天内申请，并保持商品完好。您可以在这里查看详细规则：退货政策。”

低质量：
“可以退货，7天。”（虽然功能达标，但不够用户友好）
```

通过高质量模型辅助评分（如 GPT-4 给 1-5 分）and 人工评审（客服主管看是否符合服务规范）

**4、适应性与迭代空间：**

```Python
如果当前模型比较弱：
需在 Prompt 里细化 SOP，比如“请分三句话回答，第一句说明能否退货，第二句说明时间，第三句提供政策链接”。

如果模型很强：
可以只给任务目标，让它自己组织语言，比如：“请作为客服回答退货相关问题，并附上政策链接。”
```

## 3.10 上下文工程（Context Engineering）
2025 年 6 月后，原名Prompt Engineering，在 AI Agent 概念日趋火热的应用潮中，经由 Anthropic、LangChain、Manus 等 AI 公司，以及 Andrej Karpathy等行业领袖的传播下，共识成了更适应 Agent 的新概念：Context Engineering

1、与提示词工程的差别：

**（1）Prompt 工程：**专注 **单轮 AI 交互**的生成质量，是为获得最佳结果而编写和组织 LLM 指令的方法。

**（2）Context 工程**，更关心在 **多轮 LLM 推理**过程（即 Agent 运行过程）中，找到并维护动态优化整个 LLM 所接触的上下文信息配置 **==（包括系统指令 system instructions、工具 tools、MCP 协议、外部数据、消息历史 message history）==**的策略。目标是以 **==尽可能少且必要的 tokens，最大化 LLM 生成结果==**，引导模型输出我们期望的行为。

![image](images/img_0054.png)

2、有效开展 Context 工程的方法：

（1） **策略1，写好 System Prompt：**如果 Prompt 过于具体，使用大量示例、if-else 类的要求，会使得模型更加僵化，缺乏处理意外情况的能力； 如果 Prompt 过于模糊或缺少足够的背景信息，则无法对模型输出进行可控管理

![image](images/img_0055.png)

**建议：**

1、写第一版提示词时可先用能用到的最聪明模型写出能大致满足要求的最小化 Prompt **，**根据 Prompt 测试过程中发现的问题，迭代必要的指令细节、few-shot，优化生成效果，最终再迁移到最终的生产模型，完成细化

2、结构化提示：使用`<tag>``</tag>`或##title式的 XML 标签 / Markdown 语法，分割不同指导作用的提示词；

3、为 Agent 准备的工具，应当是自包含、能被 LLM 充分理解，且工具之间功能重叠少

4、谨慎在 Prompt 中添加示例：一般来说尽量避免在推理模型中使用 few-shot；应该设计一组足够多样化、规范的核心例子，有效展现 Agent 的预期行为

（2） **策略2，即时上下文：让 Agent 像人一样地获取上下文**

当前问题：大模型上下文窗口有限（不可能把所有的相关 context 都塞进去）；以往在推理前的阶段采用 embedding-based 检索的方案，常常会检索到很多可能相关但实际没用的内容

1、没必要要求 Agent 在推理时，一次性回忆所需的全部上下文

2、像 Cursor 等 AI Coding 工具：会按照用户需求，先翻阅项目文件夹中的 readme.md，了解项目文件结构 → 在 /resource/pic 目录找图片、到 /component 目录找组件代码等。在这个过程中Agent 自主导航与检索信息，动态获取所需信息到上下文窗口中。 3、让 Agent 自行记录 memory ，将工作记忆摘要与持久化

（3） **策略3：为超长程任务，实现无限上下文**

无关的 Context 占用上下文窗口时，必然会影响模型性能，Agent 的智能几乎与一次性自主运行时长挂钩。AI Coding 中的代码重构任务、Deep Research 任务等往往会运行十分钟以上，产生的 context 远超出模型的上下文窗口限制。Anthropic 团队引入了专门的上下文工程设计：
