# 9、AI产品经理如何评估算力成本？

## 9.1 模型层成本计算的基本认知（背景了解）
**==在满足业务需求的前提下，选择最“小而美”的模型组合，才是最优的经济解==**

### ① 模型成本与参数量、训练数据 Token 数直接相关
模型训练成本通常 **与模型参数量成正比**。参数量越大，所需的算力资源、训练周期、存储成本就越高。

**训练数据的 Token 总量**也是影响成本的重要因素。Token 越多，训练所需迭代次数越多，相应计算资源开销更高。

### ② 参数小 ≠ 能力弱，重点看适配性
并非参数量越大越好。小模型在 **特定垂直场景**（如客服问答、产品推荐）下经过优化，也能展现出与大模型相当甚至更优的效果。

如何判断一个小模型是否适合自己的场景？可以通过“三看一测”方法：

- **看评测**：参考如 SuperCLUE、C-Eval 等权威模型榜单的表现；
- **看垂直度**：是否有过针对你业务场景的微调或优化；

**亲测**：在你自己的任务数据集上进行验证。

### ③ 训练数据质量重于数量
虽然 Token 数多可以帮助模型泛化能力增强，但 **数据质量与领域相关性更关键**。

在训练阶段， **高噪声、无效重复的数据不仅浪费算力，还可能拉低模型性能**。相比之下， **精炼、高覆盖度的语料**更能提升模型在实际任务中的表现。

### ④ 降本建议：采用“联邦小模型”策略
面对大模型成本高昂的问题，可以尝试一种组合策略—— **联邦小模型架构**：

不同子模型在客户端或业务层根据任务分发请求；

模型之间可以按能力协同调用，形成“模型集群”式执行；

在无需通用模型覆盖全部场景的前提下，大幅 **降低调用成本与部署资源占用**。

### 9.1.1 模型运行成本的关键因素：算力消耗
对于 AI 产品经理而言， **==每一个产品决策都应伴随着 ROI（投入产出比）的评估==**。其中，“投入”的核心即是—— **模型的算力成本**。

1、 **模型算力成本的2大组成**

对于大模型厂商（如讯飞、通义千问、文心一言、豆包、混元、智谱等）来说，模型运行成本可拆分为两个主要部分：

```JSON
预训练成本：指模型在初始训练阶段所产生的算力费用；推理成本：指模型部署后每次调用（推理）所需的实时计算资源。

其中；预训练成本估算公式：
预训练成本 =（模型参数量 ✖️ 训练轮数/每秒计算能力）✖️ 显卡租用单价 ✖️ 训练数据 Token 总量
```

| **参数项** | **含义** | **示例值/来源** |
| --- | --- | --- |
| **模型参数量** | 指模型的规模（如70B参数） | 常见参数量：7B/13B/33B/70B等 |
| **训练轮数** | 每个参数平均要被遍历训练多少次，一般经验值为 6 轮 | 来源：业界经验（如OpenAI） |
| **A100 显卡计算能力** | Nvidia A100 GPU 每秒浮点运算能力 | 官方公布值：312 TFLOPS/s |
| **显卡租用价格** | 按秒计价的 GPU 成本 | 示例：Azure上A100按秒租价 ≈ $2.2659/3600 秒 |
| **训练数据 token 总量** | 训练语料库中所有文本的 Token 数 | 示例：1万亿 Tokens、300B Tokens 等 |

**1、预训练成本计算（示例）**

假设：

使用参数量 70B 的模型；

训练数据量为 1 万亿 Tokens；

每个参数训练 6 次（6轮）；

使用 A100 显卡（312 TFLOPS）；

显卡租用单价：$2.2659/小时 ≈ $0.00063/秒

预训练 FLOPs = 模型参数量 ✖️ 训练轮数 = 70B × 6 = 420B 次操作 训练耗时（秒）= 420B / 312T ≈ 1.35 秒（假设单个 Token） Token 总数 = 1,000B（1 万亿） 总时间 ≈ 1.35s ✖️ 1,000B = **1.35 万亿秒**
 成本 ≈ 1.35 万亿秒 ✖️ $0.00063 = **约 8.5 亿美元**

实际训练通常是并行运行多块显卡，因此真实成本 = 时间/并行GPU数 ✖️ GPU租金，结果会更低一些，但数量级相当。

**2、推理成本计算与模型选型原则**

在 AI 产品落地过程中，“推理成本”是最直接影响产品运行开销的算力指标，尤其对于面向 C 端或高频调用场景的产品更是核心变量。

### 什么是推理成本？
> 推理成本，指的是每次调用大模型（即每轮问答、生成）时所产生的算力消耗。 **==推理成本 = 按调用量计费，通常以“每千个 Token”的生成为单位进行核算。==**
>

**推理成本的估算公式（以 OpenAI A100 卡为参考）**

> **==每千个 Token 的推理成本 ≈ 1000 ✖️ (模型参数量 ✖️ 2 / A100 每秒计算能力) ✖️ 显卡单位租金==**
>

| **参数** | **含义** | **示例值** |
| --- | --- | --- |
| 模型参数量 | 模型的规模（如 13B/33B/70B） | 例如 LLaMA2-13B |
| 计算能力 | A100 显卡的计算能力 | 312 TFLOPS |
| 显卡租金 | 单位时间的 GPU 成本（以秒计） | $2.2659/小时 ≈ $0.00063/秒 |
| ✖️2 的原因 | 前向推理 + 反向传播计算 | 通常保守估计都考虑 ×2 |

#### **==产品视角：没有“最大的模型”，只有“最合适的模型”==**
**==并不是模型越大越好，很多产品场景并不需要超大规模参数模型来完成任务。例如客服问答、规则式文案生成等，使用中小参数模型即可达标，甚至更稳定、响应更快、成本更低。==**

**3、模型选型原则——如何评估小模型是否够用？采用“三看一测”方法**

```JSON
看权威评测榜单
例如 SuperCLUE、C-Eval、MMLU、MT-Bench 等；
注意观察模型在“推理能力”、“语言表达”、“指令遵循”等维度的得分。

看业务匹配场景
不同业务对模型能力侧重不同：
若重点是逻辑推理类任务（如智能推荐），应选择在推理评测中表现优异的模型；
若重点是语言生成类任务（如摘要、写作），应选择在表达能力上更平衡的模型。

看数据来源与训练策略
如果你对生成结果准确性要求高，建议选择领域微调模型；
对知识更新要求高，则优先考虑具备检索增强能力的模型。

亲测场景效果
使用你实际业务中的提示词、数据集、任务格式，分别在不同模型上测试生成结果的准确性、稳定性、速度与成本；
建议构建一个统一评测框架，对比不同模型下的输出质量与调用成本，选出最合适的一款。
```

### 9.1.2 联邦小模型
”联邦小模型“是在应用层的小模型，有的模型擅长表达，有的擅长推理，那么在应用层可以按照场景将问题分发给不同的模型，从而达到”花小模型的钱，享大模型的福”的效果。

### 9.1.3 基于 AI 产品的目标来做的算力需求评估
计算成本的前提是计算： **算力需求**（即需要多少次运算），可以依据以下公式算出需要使用GPU、多长时间做完训练，用GPUhours表示：

> **==GPUhours = 所需计算次数 / （GPU 芯片每秒计算次数 * 3600 秒* GPU 利用率）==**
>

1、 **算力**：模型训练（对模型参数产生改变）中，不管是预训练还是微调，所需的算力都是：

> **==被训练的模型参数量 * 训练数据量 * 6==**
>

6：在一次训练迭代中，包含前向传递和后向传递，前向传递对于每个 token 需要进行 2 次计算（一次加法，一次乘法），后向传递的计算量是前向传递的 2 倍，所以一次迭代总共是 6 次运算

2、 **算法（参数量）：**预训练和全参微调，被训练的模型参数量和模型架构固有的参数量一致(图中的前两种情况)，PEFT-参数高效微调（图中第三种情况）的参数量和训练方法有关

3、 **训练数据：**预训练、全参微调和 PEFT 依次有数量级上的下降。

拓展：

PEFT（Parameter-Efficient Fine-Tuning）是一种针对大语言模型预训练的微调技术， **核心目标是在保持模型大部分参数不变的情况下，通过仅调整少量额外参数来适应新任务，从而减少微调过程中需要调整的参数量，同时保持或提高模型的性能。**

PEFT的主要方法包括：

**Prefix Tuning**：通过在模型输入层之前添加可训练的前缀嵌入（prefix embeddings）来影响模型的输出。这些前缀嵌入与原始输入拼接后一起输入到模型中，而模型的其他部分保持不变。

**LoRA（Low-Rank Adaptation）**：一种用于微调大型预训练语言模型的方法。核心思想是在模型的关键层中添加小型、低秩的矩阵来调整模型的行为，而不是直接改变整个模型的结构。LoRA通过将权重矩阵分解为两个较低秩的矩阵来减少参数量，具体来说，对于模型中的某个权重矩阵W，LoRA将其表示为两个较小的矩阵A和B，使得W≈A×B。

**Adapter Tuning**：通过在预训练模型的基础上添加适配器层（adapters），来实现特定任务的微调。这种方法旨在保留预训练模型的原始权重，仅在需要适应新任务的地方进行小规模的参数调整。

PEFT技术的优势在于：

减少计算资源需求：PEFT方法仅微调少量模型参数，大大降低了计算和存储成本。

节省存储空间

提高模型多样性：PEFT可以对预训练LLM添加额外的含有少量训练参数的层，只对额外层的参数进行训练，无需改动整个模型。

## 9.2 具体评估维度
在构建企业级 AI 产品时， **大语言模型的选型与部署方式**直接决定了整体技术成本结构。为了实现 **高性价比且安全可控的 AI 解决方案**，产品经理需要从两个核心维度出发，对模型部署和使用方案进行系统评估。

1、维度1： **==部署方式对成本的影响（决定性）==**

有3种方式：

#### （1）SaaS 模式：调用公有云模型 API
**特点**：无需部署模型，开箱即用。

> **成本结构**：以 **==Token 消耗==**为计费单位（例如 OpenAI、文心一言等 SaaS 计费模式），付费即用。
>

**适用场景**：

快速验证原型；

对数据安全要求不高的外部产品；

小团队/初创团队低成本试水。

#### （2）私有化部署在云端（开源模型）
**特点**：模型运行在企业专属的云环境中。

**成本结构**：

不需支付模型授权费用；

> **==需承担 GPU 云资源成本；==**
>

若涉及模型微调，则需额外支付训练期间的 Token 消耗成本。

**优势**：

避免数据上传至第三方平台，提升数据安全；

易于与企业内部系统（数据库、接口）集成；

弹性部署，适合业务扩展。

**适用对象**：中大型企业、政府机构、对数据合规性有高要求的部门。

#### （3）私有化部署在本地硬件（离线部署）
**特点**：模型运行在企业本地的服务器或数据中心。

**成本结构**：

> **==需采购本地 GPU 服务器，前期硬件投入高；==**
>

> **==微调需求需配备大显存显卡（如 A100、H100）==**；
>

后续运维由企业自主承担。

**优势**：

完全数据可控、零外泄；

网络环境独立，稳定性高；

满足高度敏感行业（如金融、国央企、医疗）的合规要求。

**适用对象**：金融机构、大型央企、关键领域行业客户。

2、维度2：成本消耗方式（可控性）

（1） **推理**：模型调用生成响应内容的过程，即每次用户问答/文本生成所产生的计算消耗。

> **计费方式**： **==按生成文本 Token 数计算，常用单位为“每千 Token”。==**
>

**特点**：

是 AI 应用的日常运行成本；

涉及每一次用户调用模型的使用场景。

（2） **模型微调**：对预训练模型进行少量再训练，使其更符合企业业务数据和使用场景。

**计费方式**：

> **==SaaS 模型微调需按训练 Token 计费；==**
>

> **==私有化模型微调则需计算训练 GPU 时间成本。==**
>

**特点**：

是“非日常性”的一次性训练成本；

属于按需启用，不是所有项目必须进行

## 9.3 评估方式
| **类型** | **推理成本** | **训练成本（模型微调）** |
| --- | --- | --- |
| **直接调用模型厂商的接口** | = 模型推理接口调用的Token单价 × Token数。 Token换算不同， 区分语言和模型； Token单价有高低， 区分Input/Output 和Batch。 | = 模型微调接口Token单价 × 训练数据Token数 微调是否有必要， 关键要看量消耗； 一次投入价会高， 持续支出会降低。 |
| **私有化部署在云资源** | = 所需GPU卡型号xx的租赁价格 × 租赁时长 私有部署更安全， 无需再缴Token费； 模型参数加两成， 即得显存租显卡。 | FP16精度模型所需显存 = 模型训练参数量 × 20 微调显存要求高， 训练参数二十倍； 高效微调得性价， 全参数调价更高。 |
| **私有化部署在本地机器** | = 所需GPU卡型号个数 × 单价 保密要求需自买， 算好显存再采购； 显存仍是多两成， 市场价格要摸透。 | = 所需GPU卡型号个数 × 单价 微调硬件要求高， 多卡并行有损耗； 一次购入要谨慎， 合理利用勿闲置。 |

### 9.3.1 调用模型厂商的接口的成本计算
（1） **推理成本**= 模型推理接口调用的 Token 单价 * Token 数。

（2） **训练成本（微调成本）**= 模型微调接口 Token 单价 * 训练数据的 Token 数

模型推理、微调接口的单价都由各模型厂商在官网直接宣布，每个厂商都有不同的型号，价格越高，一般意味着模型参数量越大。 比如下图是 OpenAI GPT-4o 系列模型的 Token 价格。

（1） **输入（input），输出（output）的Token 单价不一样**。

如示例，输出 Token 单价高达输入 Token 单价的 4 倍，而 cached（缓存提示词）价格还会更低。

缓存提示词：指在与大语言模型进行多轮对话的过程中，发给大模型的上下文经常有大段重复内容。比如在一次对话中，有 10 轮对话，第9轮对话会把前8轮对话作为上下文发给大模型，而在第10轮对话中，需要把前9轮的对话作为上下文发给大模型。

那么这两次对话的上下文中，都有前八轮对话，那么大语言模型在处理时， **如果检查到前若干个提示词是一样的，会减少部分运算，达到既不影响效果，又能降低算力成本的效果。**

（2） **BatchAPI：批量调用接口的价格。即一次“批发”，对算力的占用会降低，价格会便宜**

**BatchAPI 是异步执行输入输出的，模型不能实时返回，大约 24 小时内能返回**。

i.e. BatchAPI **主要用在实时性不高，数据量又比较大的时候，比如对海量知识进行分类、总结**。它的价格是实时输入输出的 50%，所以，在必要的场景下你可以使用 BatchAPI 来降低成本。

因此计算成本，需要确定：

**（1）是否调用 BatchAPI**

**（2）对 input、output 区别对待**

**（3）计算token数**

注：token：是“词元”对应的向量，词元是语言的最小单位，可以直观地理解为具备一定语义的最小字母组合。比如英文中的 “pre” 可能不是一个单词，但它却是一个词元。因为“pre”作为前缀具有“提前”的语义

一般来说：

| 模型 | PlayGround | 单个中文汉字对应的token数（平均值） | 单个英文单词对应的token数（平均值） |
| --- | --- | --- | --- |
| OpenAI GPT3.5&GPT4 | https://platform.openai.com/tokenizer | 1.02 | 1.33 |

#### 9.3.1.1 推理成本
得到 token 与单词数量的换算比例（Ratio）后，可以将输入给模型的单词量或者模型输出的单词量转换为 Token 数再乘以 Token 单价，就可以计算推理成本了。

推理成本 = 模型推理接口调用的 Token 单价 ✖️ token 数

= 模型推理接口调用的 Token 单价 ✖️ 单词数 ✖️ 单个汉字（或单词）对应的 token 数

在计算输入单词量的时候，并非只是用户的输入，而是需要把 **上下文 + 用户输入共同加起来**

计算单价：要区分 BatchAPI，输入量、输出量

举例：上下文是什么：给大模型下达任务，不仅要告诉它用户的诉求，还要告诉它这是一个什么场景，有哪些参考资料可以使用。比如智能客服中，用户的问题只有四个字“如何开机”，但要发给大模型的输入项还包括【系统提示词】、【可参考示例】、【可参考资料】等等；其中发给大模型的提示词往往比用户本身的指令要高出几十倍

#### 9.3.1.2 微调成本
1、通过接口微调模型的成本方面意义：

**==希望用一次性的微调投入，换来日常的低成本支出。==**所以，只要日常 token 的消耗量到达了一定程度，那么微调模型就有必要。

2、举例：以 OpenAI 的价格为例，对比直接使用 “OpenAI 的 GPT-4o” 和“微调 OpenAI GPT-3” 的成本，再评估什么时候使用微调模型才比较划算

（1）直接使用 OpenAI 的 GPT-4o = **Price(GPT-4) ✖️ Token 消耗**

（2）使用微调 OpenAI GPT-3.5 = **微调 GPT-3.5 的成本 (一次性投入) + Price(GPT-3.5) ✖️ Token 消耗**

= **模型微调接口 Token 单价 ✖️ 训练数据 Token 数 + Price(GPT-3.5) ✖️ Token 消耗**

但考虑到微调并不是一次就能成功，需要适当地将 **微调成本翻 10-20 倍来评估**

### 9.3.2 私有化部署大语言模型的成本测算指南（云端部署）
在采用私有化方式部署大语言模型时，企业需全面考量两类成本：

> 推理阶段（即模型运行时）所需的 **==显存与GPU租用成本==**
>

> 微调阶段（模型调教时）所需的 **==计算资源与训练时间==**
>

（1）显存： **GPU 芯片能存储的数据量**，也是选择 GPU 芯片配置的首要因素

假设每个参数是 16 位精度的浮点数，占 2 个字节

（2）峰值计算次数，是指 **GPU 的计算速度**

单位是 FLOPS（FLoating point Operations Per Second）， 即每秒浮点计算次数。对于不同精度 64 位、32 位、16 位、8 位的要求，计算速度也不同。主流大模型大多采用 16 位精度

（3）GPU 带宽：是指 **卡与卡之间的数据传递速度**

#### 9.3.2.1 推理成本评估（持续成本）
模型部署后长期运行的算力成本主要取决于 **模型参数量与显存要求**，通常包含以下两步：

#### ① 显存需求估算
**==模型推理所需显存 ≈ 模型参数量 × 参数字节数（通常为 FP16，即2字节）× 冗余系数（约1.2）==**

例：若模型为 GLM-4-9B（即 90 亿参数），其推理所需显存：

```JSON
显存 = 9B × 2 Bytes × 1.2 = 21.6GB
21.6GB 代表着租用显存为 24G 的英伟达 4090 型号的 GPU 显卡刚刚够，保险起见，我们可以租用 2 张来使用。
```

为满足冗余与多线程并发处理，推荐配置为 **2张NVIDIA RTX 4090（24GB）**

#### ② GPU资源租赁成本
若采用云端租赁，设每张 RTX 4090 的费用为 ¥2.01/小时

则月度运行成本（以2张卡、24小时运行、30天计算）：

```JSON
推理成本 = 2张 × ¥2.01 × 24小时 × 30天 = ¥2,880 / 月
```

#### 9.3.2.2 微调成本评估（一次性成本）
微调阶段是一种模型能力的定制化强化，主要涉及三项要素：显存配置、计算时长、GPU租金。

#### ① 显存与GPU型号选型
微调推荐使用 FP16 精度

显存需求估算：模型参数 × 20（经验值）

例：GLM-4-9B 的训练显存需求：

```JSON
显存 = 9B × 20 Bytes = 180GB
```

对应部署方案：配置至少 **3张 NVIDIA A100 80GB 显卡**

#### ② 训练时长估算
训练时长公式： **==训练时长 = 模型参数量 × 训练数据量大小 × 6 / GPU FLOPS / GPU计算效率==**

FLOPS（A100 80G，FP16）：约 312 TFLOPS

假设数据集大小为 1GB，GPU计算效率为 0.4，则：

```JSON
训练时长 ≈ 9B × 1GB × 6 / 312T / 0.4 （秒）≈ 120 小时
```

#### ③ 微调GPU租赁成本
单张 A100 云租价假设为 ¥28/小时

微调期间共使用 3张 A100，训练时长 120 小时

则总成本为：

```JSON
微调成本 = 3张 × ¥28 × 120小时 = ¥10,080
```

可通过 LoRA、QLoRA 等参数高效微调方法降低成本达 80%-90%

### 9.3.3 自采硬件私有化部署的成本计算
自采 GPU 进行私有化部署，主要适用于 **安全等级极高、对数据本地管控有严格要求**的场景，如政府机构、金融核心系统、企业财务主系统等。

**1、推理场景成本评估（部署运行阶段）**

部署目标：长期稳定运行大语言模型，保障本地推理能力。

**显存需求计算**： 模型参数量 × 每个参数占用空间 × 冗余系数（1.2） 以 GLM-4-9B 为例（90亿参数，FP16精度，2字节）：

```JSON

```

**采购成本**： 单张 A100-40G 市场价格约为 **10万元人民币**。

**2、训练场景成本评估（全参微调阶段）**

若需进行模型微调（如全参或LoRA训练），硬件资源需求显著提升。

**显存需求**： 微调推荐 FP16 精度，经验估算公式为：

```JSON

→ 9B × 20 = 180GB
```

**硬件配置建议**： 推荐采用 **3 张 NVIDIA A100-80G 显卡**，可组成高性能训练集群。

## 9.4 如何压缩模型调用成本？
**==先问“能不能不调用大模型”，再问“能不能少调用”，最后再问“能不能便宜地调用”==**==。==

**应用层降低 LLM 调用成本方法：**

```JSON
1. 构建高质量问答对向量库（Q&A Cache）原理：用历史问题-答案对作为向量检索库，命中后直接返回答案，无需调用大模型。
效果：可覆盖 60%～80% 的高频问题场景，显著减少调用频率。

2. 利用强模型生成高质量问答对，供弱模型使用
用昂贵模型（如 GPT-4）生成标准答案，构建知识库；
运行时用更便宜的模型（如 Qwen、Baichuan）来处理问答；
实现 推理降本 + 保持答复质量。

3. Prompt 压缩，减少 token 消耗
采用提示词压缩技术（如 Microsoft LLMLingua）；
或基于规则/模板简化提示词；
可实现平均 token 减少 20%～40%。

4. 优化 RAG 分块策略，减少上下文冗余
减少 chunk size（如从500 token 优化为300 token）；
精准分块：避免重复信息、多轮重复召回；
仅保留高匹配度内容作为上下文，控制召回内容数量与质量。
```

**模型层降低调用成本的方法**

```JSON
1. 借用强模型微调弱模型（知识迁移）
用强模型生成训练数据（如 CoT 推理过程）；
用这些数据微调轻量模型（如 Mistral、Qwen 1.8B）；
结合 LoRA 低成本微调方式，大幅降低推理开销。

2. 模型选择与调用分发（模型调度）多等级模型接力调用策略：
第一步用轻模型尝试回答；
若不确定或信心不足，再升级调用更强模型；
最终才交由最强模型接手；
类似“智能客服首轮机器人 + 升级人工”的机制，实现算力资源合理分发。

3. 模型能力与成本权衡选型
通过“三看一测”评估选用更合适的模型：
看榜单、看训练数据、看核心客户案例；
用自己场景测试评估 token 性价比；
同等质量下优先选用参数量更小、token 价格更低的模型。
```

### 9.4.1 应用层降低 LLM 调用成本
1、通过 **==问答对向量库==**降低模型调用次数，从而实现降本：

在满足特定条件时，系统完全可以脱离大模型完整执行一次问答。

如 SAAS 产品网站的帮助文档，可能用户 50%的问题都是相似的，产品运营人员可以将这些 FAQ 总结存入向量数据库。用户提问时按照向量语义检索直接找答案皆可，无需调用大模型。

此时，LLM 的作用 **是大大加快 FAQ 的生成速度，而非问答本身。FAQ 的维护机制：被动与主动双轮驱动**

**被动式维护机制：用户反馈驱动**

用户点击“点踩👎”某条 FAQ 回答；

用户留言反馈“答案不准确 / 不相关”；

多次搜索未命中有效回答（长尾问题上升）。

**主动式维护机制：LLM 巡检驱动**

设定定期巡检任务（如每日、每周批量运行）；

针对 FAQ 逐条进行回答验证。

**2、借用优质问答对+RAG 的方式优化 Agent 能力：**

在论文 *https://arxiv.org/abs/2310.03046 *中，作者使用了一个多 Agent方案进行问答。这种场景：

把“API 接口是否返回成功”作为一个高效的反馈，相当于FAQ 的人工标注，达到了无人工介入即可达成目标的效果。

把问答库作为一个 RAG 知识库在使用

![image](images/img_0475.png)

**具体步骤如下：**

> 系统 ==将用户诉求和大模型分发系统进行交互==；
>

> 大模型分发时： ==系统先调用便宜模型 GPT 3.5 进行撰写==，写好之后执行代码，如果成功，则接口返回成功，如果不成功，接口返回错误；
>

> 如果 ==通过 GPT3.5 经过几轮还是不能返回成功，才开始调用 GPT4==；
>

> 一旦 ==有返回接口成功==的记录；
>

> 系统 ==会将这次接口调用代码以及对应的用户诉求自动存入向量数据库==；
>

> 当 ==下次其他用户有诉求时，首先从向量数据库中检索是否有类似问题==；
>

> 如果 ==有类似问题，则提取出所有正确答案==；
>

> 然后 ==将答案加上本次用户的 query，一并合成 prompt==；
>

> ==将该 prompt 再发给大模型分发系统，首先调用低成本 LLM 模型==，如果不能返回结果再调用高成本模型；
>

**3、压缩提示词：**

在 LLM 应用中， **提示词（Prompt）所消耗的 Token 数量**会显著影响调用成本与响应速度。而自然语言提示词中普遍存在 **大量冗余信息**，因此提示词压缩成为降本增效的重要手段。

1、分区压缩原则：区别对待不同提示词结构

| **模块** | **内容描述** | **信息密度** | **压缩率** | **处理方式** |
| --- | --- | --- | --- | --- |
| **任务指令部分** | 明确要求 LLM 要做什么（Task/Instruction） | 高 | 低 | 尽量保留原意，少压缩 |
| **问题本体部分** | 用户的实际问题 / 查询 | 高 | 低 | 精准保留，避免模糊 |
| **上下文信息** | 背景说明、额外限制条件等 | 中 | 中 | 可适度精简 |
| **Few-Shots 示例** | 举例的内容，往往较长且存在重复结构 | 低 | 高 | 可使用模板缩写、结构抽象等方式 |

2. **迭代式压缩原则：多轮压缩优于一次性压缩**

```JSON
第一轮：结构归纳
将冗长的 few-shot 案例结构抽象为统一模板
合并重复性说明内容

第二轮：语义压缩
用更简洁词语表达复杂句式
合并同义、模糊的描述

第三轮：模型辅助压缩（可选）
使用辅助 LLM 进行语义压缩（如 LLMLingua）

第四轮：压缩后验证
保留任务原意的前提下，通过输出对比验证准确性不变
```

压缩神器：微软LLM Lingua（https://huggingface.co/spaces/microsoft/LLMLingua）（需要魔法）

![image](images/img_0476.png)

**4、优化 RAG 分块以降低 token 量实现降本：**

RAG（Retrieval-Augmented Generation）机制的核心在于： **将外挂知识库中检索到的文本片段作为上下文追加给大语言模型（LLM）进行生成**。这一设计虽然极大增强了模型的知识覆盖能力，但也直接导致了 **上下文长度增长**，带来了显著的 **Token 消耗上升**问题。

1、Prompt 压缩与 Chunk 优化的协同策略

为应对 Token 成本问题，在 RAG 的上下文追加环节中可以引入 **Prompt 压缩**手段。具体包括：

压缩检索到的块内容， **保留核心信息**、精简冗余描述；

压缩提示词中的指令与 Few-Shot 示例，减少非关键性内容；

在分块阶段提前筛选或摘要低权重内容，减少无效上下文。

但需强调： ==Prompt 压缩应建立在保证语义完整和任务完成度的基础之上，不能因压缩而破坏信息链路，影响最终结果的准确性。==

2、建议做法（实际工程中）

```JSON
调试适配性分块长度（如 BGE、Cohere 推荐长度）；

对每个 Chunk 预先做信息密度评估（如关键词覆盖率）；

对追加 Prompt 做“结构分区压缩”处理（Fewshot/Context/Instruction 分别处理）；

引入长上下文模型（如 GPT-4-128K、Claude-2-200K）适配超长上下文应用；

对生成结果引入 Checker Agent 做后验评估：压缩前 vs 压缩后准确性是否一致。
```

### 9.4.2 模型层降低 LLM 调用成本
**1、借用昂贵大模型微调便宜小模型：**

适用场景：企业想要训练自己私有化模型但在短期内又无法准备足够数据时

> 在产品初期， **==使用昂贵模型生成的优质问答对==**；
>

> 当优质问答对积累到一定程度， **==用这些问答对来微调便宜模型==**。
>

> **==当便宜模型的生成质量和昂贵模型类似时，底层切换为便宜模型==**。
>

**2、做好模型分发：**

已经有商业化的产品来专门做模型分发，背后的原理是：对用户问题进行语义分析，进行归类，然后按照不同模型擅长的领域来使用对应模型。你可以使用以下工具进行实验，为选择模型提供一定参考

比如：

Martian : *https://withmartian.com ：根据问题难度从模型库中选择最合适的模型*

Neutrino AI : *https://www.neutrinoapp.com*

Aurelio AI : *https://www.aurelio.ai/semantic-router*

**3、优先调用便宜模型，逐步升级后调用不同等级的模型：**

![image](images/img_0477.png)

（1）调用便宜模型（weaker LLM）：对模型的答案进行评估，（论文中使用 answer consistency 指标）

（2）如果评估通过，则使用便宜模型的答案；如果不通过，则调用昂贵模型（Stronger LLM）来回答。

but，有风险：加入 weaker LLM 能力特别弱，或者问题比较复杂，那么每次都要一次调用便宜模型，昂贵模型(Stronger LLM)，那么成本可能反而升高

（2）业务规模评估：业务规模直接影响大模型部署的硬件配置和模型参数量级选择

a） **用户量级与并发请求供参考**

- **小型企业（日活 <1 万）**：

典型场景：内部知识库检索、基础问答。

选型建议：轻量级模型（十亿参数级别），配置 1-4 颗 GPU。

- **中型企业（日活 1 万 -10 万）**：

典型场景：智能客服、工单处理。

选型建议：中等模型（百亿级别参数）+ 配置 4-8 颗 GPU。

- **大型企业（日活 >10 万）**：

典型场景：实时风控、大规模个性化推荐。

选型建议：大模型（千亿级别参数）+ 算力集群（如 8 卡以上）。

b） **算力需求公式**

-单次请求推理算力需求：

> ==算力（TFLOPS）= 模型参数量 *Token 数 / 请求 *2 / 延迟（秒）==
>

• **模型参数量**（Parameters）：模型的总参数个数（如 13B=130 亿）。

• **Token 数 / 请求（Tokens）**：单次请求处理的输入 + 输出 Token 总数（如输入 500 Tokens，输出 300 Tokens，合计 800 Tokens）。

• **常数 2**：源自 Transformer 架构中每个参数的前向传播计算量（1 次乘法 +1 次加法 =2 FLOPs/ 参数）。

• **目标延迟（秒）**：业务允许的单次请求最大响应时间。

-案例：130B 参数模型处理单次请求（输出 500 Tokens），要求延迟 ≤1 秒，则需算力：

130*109 * 500 * 2 / 1 =1.3* 1014FLOPS=130TFLOPS

![image](images/img_0483.png)

参数量超过一定阈值后，精度提升显著放缓，但成本飙升。 示例：13B 模型在客服场景准确率达 92%，升级到 70B 仅提升至 94%，但算力成本增加 5 倍。

6、数据治理与知识工程

```JSON
很多产品经理在写RAG项目经历时写不出内容，所以可以依次对应看如下工作你到底参与了多少
```

（1）数据治理体系构建

A. **数据采集与清洗：**

a） **多源数据整合**

内部数据：抽取业务系统日志（如用户行为）、文档库（合同 / 报告）、结构化数据库（CRM/ERP）……

外部数据：引入公开知识库（如 Wikipedia）、行业报告、合作伙伴数据（需签订数据共享协议）……

b） **数据质量过滤**

噪声清洗：使用正则表达式匹配无效格式（如乱码），NLP 工具（LangChain）过滤低相关性文本。

冗余去重：基于 SimHash 或 MinHash 算法识别重复内容，保留唯一性数据

B. **敏感数据处理：**

**分类分级**：按敏感程度标记数据（如 PII、商业机密、公开数据），制定差异化策略。

**脱敏技术**：静态脱敏：对姓名、身份证号等字段进行掩码（如“张 * 三”）、泛化（如“北京”—“华北地区”），动态脱敏： 在训练 / 推理流水线中实时替换敏感实体（如 FPE 格式保留加密）。

**合规审计**：记录数据血缘（Data Lineage），确保可追溯至原始来源，满足等保要求

C. **数据存储与权限管理：**

热数据：高频访问数据存于分布式内存（Redis/Memcached）。

温数据：向量化结果存于 Milvus/Pinecone 向量数据库。

冷数据：原始文本存于对象存储（MinIO/Ceph）。

权限控制：基于 RBAC 模型（角色权限）和 ABAC 模型（属性权限）限制数据访问范围

（2）知识工程实施

A. 领域知识抽取

a） **结构化知识抽取**

实体识别（NER） ：使用 BiLSTM-CRF 或 BERT 模型提取领域实体（如“药品名称”“金融产品”）

关系抽取（RE） ：通过预训练模型（如 DeepSeek-RE）构建实体关联（如“药物 A — 治疗 — 疾病 B”）

b） **非结构化知识挖掘**

事件抽取：从新闻、报告中识别行业事件（如“政策发布”“并购交易”）。

规则库构建：提炼业务规则（如金融风控规则“单日交易额 >50 万 需人工审核”）。

B. 知识图谱构建

a） **图谱架构设计**

本体定义：设计领域本体（Ontology），如医疗领域包括“疾病 - 症状 - 治疗方案”三元组。

知识融合：对齐多源数据（如合并不同名称的同一实体“COVID-19”与“新型冠状病毒”）。

b） **存储与查询优化**

图数据库选型：复杂关系查询用 Neo4j，高并发场景用 TigerGraph。

分布式扩展：通过分片（Sharding）技术支撑亿级节点存储。

C. 知识增强与向量化

a） **向量化表示**

文本嵌入：使用 Sentence-BERT 或 Contriever 模型生成文本向量。

多模态嵌入：融合图像（CLIP）、文本（BERT）生成跨模态向量（如“产品图 + 描述”）。

b） **知识增强训练**

知识注入：将知识图谱三元组作为 Prompt 输入模型（如“已知：A 会导致 B，因此 ...”）。

检索增强（RAG） ：训练阶段结合向量检索结果，提升模型事实准确性。

D. 推理阶段增强

**实时检索增强**：用户提问时，从向量库检索相关文档 / 知识，拼接为上下文输入模型。

**知识校验模块**：对模型输出进行实体链接（Entity Linking）和事实核查（如对比知识图谱）。
