# 8、AI产品经理 工作流程相关

传统PRD关注： **页面、功能点、接口逻辑**

AI产品新增关注：

（1） **模型行为不可控**（概率性）

（2） **输入输出不确定**（Prompt、推理路径）

（3） **决策链条不同**（不是按按钮，而是执行任务）

（3） **需要长期优化**，而不是开发完就结束

说明：

**PRD模版没有用！**PRD的核心是表达清楚需求，不是写八股文。你的PRD有以上几个模块一般就够用了（有些会涉及到性能需求等），关键的是里面具体的内容细节，那项目之间差异很大，也不存在套用模版。

### 8.2.2 将用户旅程转为Agent 工作流
**1、在传统产品设计中：**

“用户旅程（User Journey）”是产品经理必备的设计思维，它像一张 **交互地图**，用于明确用户从哪一步进入产品、在哪些界面做出操作、最终如何完成目标。因为传统产品的操作流程是 **线性、前台可见、由用户驱动的**，所以我们必须逐步定义每一步的操作路径和界面跳转。

**2、而在 AI 驱动的新一代产品中（如 Agent 应用）**

> **==产品流程不再完全依赖用户手动操作完成，而是转变为人机协作的工作流（Workflow）==**。其中大量操作由 AI Agent 自动完成，只有关键节点才需要用户输入或决策。
>

| 对比项 | 用户旅程（传统产品） | Agent 工作流（AGI产品） |
| --- | --- | --- |
| 驱动主体 | 用户手动操作每一步 | Agent 自动执行为主，人类决策为辅 |
| 流程结构 | 线性路径、明确跳转 | DAG/树形结构、动态路径 |
| 节点可见性 | 所有步骤均对用户可见 | 多数步骤封装在 Agent 内部，仅关键节点可见 |
| 设计关注点 | 界面跳转与交互一致性 | 判断交互点是否必要 + 是否信任 Agent |

**1、输出【Agent工作流】**

传统prd：用户旅程图，描述用户一步步的操作

AI产品PRD：用户只在发起query和关键节点做决策，Agent需要理解需求，执行具体任务最终汇报结果

### 8.2.4 原型图正在从 GUI 向 LUI 中的 GUI 演化
在传统产品中，原型图主要聚焦于 GUI（Graphical User Interface），即以图形界面呈现功能结构与交互流程。用户通过点击、滑动、选择等方式完成任务。 **但在基于大语言模型（LLM）的 AGI 应用中，用户界面逐步转向LUI（Language User Interface）语言交互界面为主。**

```JSON
什么是“GUI in LUI”？

在 AGI 驱动的系统中，大多数任务通过自然语言完成。界面不再是一个页面跳转的集合，而是对话流程中的“局部插入”。

当用户需要做出决策或操作时，系统会：
在对话窗口中动态插入可操作的 GUI 组件
以表单、卡片、图表等图形形式呈现内容
保留语言交互的连续性和上下文理解能力
```

### 8.2.6 【增加】评估体系
以招聘ai助手为例：

| 功能点 | 测试方法 | 测试指标 |
| --- | --- | --- |
| 招聘需求识别 | 测试人员（可借助大模型）将AI从口语化需求文本中提取的结构化信息，与人工标注的“黄金标准”进行比对，对准确率进行打分。 | 核心实体（职位名称、工作地点）F1分数 > 90%关键实体（经验年限、学历要求、核心技能）F1分数 > 85% |
| 招聘需求补全 | 测试人员模拟完成从模糊需求到完整JD的全过程，结合对话质量与对话轮次进行主观打分。 | 任务完成率 > 95%平均对话轮次 < 6次 |
| 专业JD生成 | 将AI生成的JD与资深招聘顾问/HR编写的JD混合，由招聘HR盲评专业度、完整性和吸引力。 | 各项均分 > 4分不可分辨率 > 75% |
| 需求画像生成 | 测试人员（可借助大模型）对比AI生成的“需求画像”与手工定义的画像，检验其关键要素覆盖度和准确率。 | 平均关键要素覆盖度 > 95%平均准确率 > 95% |

## 8.3 不同类型公司在大模型时代的产品建设差异
![image](images/img_0449.png)

1、 **新晋大模型公司（如国内6小虎）：以模型为核心的样板型企业**

（1） **特征定位：**这类公司以“模型研发”为主业，产品更多是为了展示模型能力的“样板工程”。其核心战略是： **用产品服务模型**，而非用模型服务产品。

（2） **团队结构：**

**模型预训练团队**：负责模型的底层训练，包括语料准备、预训练、行业细分场景下的继续训练（续训）等。

**推理优化团队**：聚焦模型服务化、API性能、响应速度等工程能力，保障模型可用性。

**产品与工程开发团队**：功能开发与落地实现，扮演传统产研角色，但以对接模型能力为核心。

（3） **产品开发模式：**

```JSON
模型团队先定义“某一时间点模型将具备的能力”，产品团队据此提前搭建外围框架。
产品经理的话语权相对有限，更多角色是能力桥接者与使用示范者：
参考行业标杆（如OpenAI）提出能力建设需求；
精准识别模型强项，将其嵌入适合的产品场景中，构建示范项目（如AI对话助手、代码自动生成器等），借此吸引市场注意力。
```

**2、传统互联网大厂/AI公司：场景牵引型 AI 战略实践者**

这类公司拥有成熟的业务体系和资源优势。AI 被视为增强工具，服务于两类主要目标：

**“+AI”**：在现有业务中嵌入 AI 能力，如阿里国际站的 AI 生意助手；

**“AI+”**：利用大模型开拓新业务形态，如字节的智能体平台 Coze、Ola Friend 耳机。

**AI 产品建设以场景驱动为主**，有清晰的业务目标，一般都是 **产品诉求等着模型能力建设**

**团队构成**：

**模型团队**：独立于业务部门，支持公司内外部模型服务，是类“平台型能力中心”。

**产品研发团队**：

**AI+团队**：偏新产品线孵化，职责类似模型厂商中的产品经理；

**+AI团队**：负责为已有业务模块加装“AI引擎”，需深刻理解业务与AI结合点。

**产品开发模式**：

产品需求通常由业务场景直接牵引，AI 能力作为手段而非目的；

明确的业务目标与指标（如效率提升、转化提升、用户增长）驱动产品设计；

产品经理既要懂业务，也要理解模型 API 能力边界，做好模型选型与效果调优。

![image](images/img_0450.png)

**3、AI 应用类公司：从场景中长出的 AI 落地者**

这类公司可能起源于原有传统业务（如制造业、运营管理），也可能是原生 AI 产品创业公司（如秘塔搜索、GenSpark.ai），他们以“应用场景驱动”为核心，贴近真实业务需求，灵活使用多种模型能力。

**团队构成**：

产品、算法、工程高度协作，形成“端到端”团队；

组织扁平化，试错迭代速度快，关注实际效果优先于技术“先进性”。

**产品开发模式：**

产品经理与研发、算法配合最为密切，需掌握从 prompt 设计、API 调用到效果验证的全过程；

面对模型能力瓶颈，需要灵活切换方案（如 RAG 替代生成、外部搜索补充、Function Calling + Tool 调度等）；

场景尚未标准化，很多产品形态仍处于探索期，如“知识问答？任务执行？Agent工具？”，产品经理需承担更多决策与探索责任。

## 8.4 产品经理如何与算法工程师协作
| **环节** | **目标** | **产品经理** | **算法** |
| --- | --- | --- | --- |
| 1、概念验证 | （1） **测验模型能力是否达到业务诉求**。Demo 一般会采用业界最佳模型（如OpenAI 的 GPT-4o）通过实验来判断模型能力能否达到业务诉求。如果实验成功，说明具备可行性，可以推进下一步的开发。这就避免了研发过早投入，浪费人力资源的情况。（2）拿着 Demo 结果 **进行市场、需求验证**，并根据用户的反馈及时调整 Demo 的使用体验，大大缩短客户期待与实际产出的差距。 | 在没有专业程序员的帮助下，可以利用 Coze、Dify 等 Agent 工具进行简单的概念验证， **构建能展现产品核心特性的小 Demo**，概念验证之后，再把复杂的工作流留给开发人员来实现 |  |
| 2、数据集构建与训练 | 产品定义的手段 ***由规则定义转向数据定义*** | 产品经理有义务、有责任来构建出能体现业务特征的数据（1） **数据收集**：从客户、需求方那里收集相关语料。比如你要构建一个医生小助手，就需要收集医患交流的问答对；如果你要构建一个能够自主规划、执行的小助手，就要收集对应场景的工作流数据。（2） **数据筛选**：主要指 **去除无效、不合格的数据。这一步一般由业务专家来完成**。（3） **数据合成**：当语料的数据量、丰富度不足时，我们也可以让高级大模型根据已有语料生成更多的数据来补足数据。让大语言模型根据 few shots 构建出 many shots。（4） **数据格式化**：每种训练方法和框架对数据格式都有一定要求，因此最后需要形成同一个格式 |

## 8. 8 badcase分析专题
### **1、现状分析**
（1）现在有一个基础方案（Baseline）；

（2）这个方案跑出来一定的效果，用一份标准的【数据评测集】去测，就能得到一组指标（比如准确率、召回率）；

（3）这组指标无论好坏，代表了起点（现状）。

（1）第一步： **准备数据评测集——准备一个可靠的评测集，是任何AI项目落地、优化的起点**

新手容易犯的错：随便拿两三条样本，跑一跑模型，遇到一个Bad Case就说模型不行，这样做没意义。评测集必须满足3个条件：

```SQL
a）数量要够，支撑统计意义（数量要足够大，才能让结果稳定）一般来说初步验证：每个场景100~300条；做版本上线决策，通常需要上千条，甚至更大规模b) 场景要真实，覆盖真实分布（评测集不能“造假”）比如直接复制同一条数据几十遍或者只挑简单问题，复杂问题不管，那效果肯定是虚高的

正确做法：
用真实的线上Query抽样（随机抓取一部分真实用户问题），尽量还原真实业务场景；覆盖不同类型：高频、长尾、复杂问题都有
比如：做一个房地产问答助手，如果评测集只放“房价是多少”这种简单问题，模型分数可能很高；但用户更关心的是“这个小区学区好不好？能贷款几成？物业费多少？”，这些没覆盖，就无法判断模型上线后的真实表现。

c）标注要可靠，质量要高
如果评测集标注质量差，模型明明答对了，结果被评成错误，会出现严重的误导
简单的检测方法：随机抽100条人工复查；如果正确率 ≥ 95%，说明数据集很靠谱；90%只能算勉强能用；如果低于90%，这个评测集基本不适合做效果评估。即便是开源数据集，也经常有标错的情况
```

**（2）第二步：设立指标体系**

衡量现状？最常用的方式就是用一套 **指标体系。要注意3个点：**

```SQL
1、指标必须和目标挂钩
如果目标是帮助客服减少错误回答，那准确率就是核心指标；
如果目标是预测用户行为（比如是否流失），光有准确率不够，反而要看召回率（模型找到所有可能流失用户的比例）。

举例：
电商客服 AI 系统，目标是减少转人工率（减少人工介入）。
所以应该同时跟踪“准确率”和“转人工率”，因为回答再准确，如果用户最后还是找人工，目标就没达成。

2、不要只看最终结果，要拆解整个链路的每个环节，都有指标

举例：
客服场景中：用户提问 → 检索知识 → 大模型生成答案 → 用户反馈，每一步都可能出错：
检索阶段：召回率是多少？有没有找到正确知识块？
生成阶段：答案是否结构化、有没有跑题？
用户反馈：用户是否点击“采纳”？是否再次提问？
你能快速发现：是检索的问题还是生成的问题，从而更高效的定位badcase

3、多个指标要结合使用，避免单一视角误导。
准确率高，但召回率低：说明系统只回答了少数简单问题，没覆盖复杂问题。
召回率高，但准确率低：说明系统回答很多，但错得多，用户体验差。
```

**（3）第三步：得出结论：**

回答两个核心问题：

```SQL
当前的算法效果到底好不好
是否还需要进行优化？如果需要，下一步大方向
```

```SQL
1、对比预期目标，判断效果好坏

对系统性能一般会有一个预期值，比如：准确率需要达到 80% 以上。
如果现状是 78%，虽然接近但说明还有优化空间；如果 65%必须继续优化；如果是85%，可以暂时投入更多资源到其他指标（比如响应速度）。


2、结论能指导后续行动，后续优化工作的决策依据

结论帮助规划下一步的动作：
如果效果已经达到或超过预期，可以考虑只做轻量维护；如果没达到，就要明确是继续调优现有模型，还是考虑换策略？

3、明确一个大方向，为 Bad Case 分析做铺垫
我们不需要立即列出每个细节的优化动作，但至少要总结出一个宏观方向：
是 提升准确率 为主？还是 扩大召回率，让系统覆盖更多用户问题？还是 平衡效率和成本，比如加缓存或用更轻量的模型？

比如：客服AI系统测试后发现：
准确率70%，主要问题集中在长问题的识别；用户采纳率低，很多回答没引用到最新知识。
结论是当前主要优化方向是：提高长问题理解能力、保证知识库更新同步。这两点将作为 Bad Case 分析的重点。
```

### **2、Bad Case 分析怎么做（粗看-追溯-解决-统计）**
盯着“模型出错”的样本，找到导致准确率、召回率下降的关键点。

（1）哪些 Bad Case 值得分析？

```SQL
a）分类错误的样本（影响准确率）
b）漏召回的样本（影响召回率）
c）一次分析 50-200 条随机样本，数量太少不准，太多效率低。
```

（2）具体方法：

```SQL
step1：粗看法——快速扫一眼，找大问题，比如整体浏览样本，找明显规律（长度、句式、关键词）适用于项目初期，先找主要矛盾

示例：
客服 Agent：大部分错误出在长问题，如“为什么我退货还没到账？”
教育 AI：公式类题目识别频繁出错。
电商导购 Agent：地名 + 产品属性（如“上海的轻薄羽绒服”）匹配失败

5~30 分钟就能锁定主要问题，效率高
```

```SQL
step2：追溯法：复现处理链路，找根因：还原检索、生成、输出每一步，看哪里出错适用于：效果收敛后，精准定位问题环节

示例：
电商问答：检索库缺少“最新运费规则”，生成回答跑题。
客服 AI：训练集中疑问句样本分布失衡，导致大量误判。
ChatBI：ETL 数据延迟，指标异常不是模型错，而是源数据没更新
```

```SQL
step3：倒推问题到解决策略：先想能用哪些方式能解决，再看哪些case能归到这些方案。

示例：
短句（如“退款”“关闭”）信息不足 ：先过滤。
价格相关查询频繁跑偏：统一用规则过滤敏感字段再调用模型
教育 AI 短答题识别率低 ：增加少样本微调
```

```SQL
step4：标记 + 统计法：量化问题分布，抓重点（重要）

（1）给每条case打标签（如“疑问句”“知识过期”“短句”）；
（2）统计占比，先解决前1-2大类问题。解决一个占比 30% 的问题，整体准确率可提升 10%+

示例：
客服系统：100 条错判中，60% 是疑问句、20% 短句、20% 杂项 ：优先补充疑问句训练样本。
招聘 AI：80 条错判，40% 技能解析错误、30% 行业分类错、30% 其他：先优化技能解析。
```

### 3、解决问题
1、 **样本误导：数据导致的偏差**

```SQL
错误场景举例：
训练集中，“怎么”几乎只出现在投诉问题里（正类），
模型学会了“凡是带‘怎么’的句子，都预测为投诉”。
结果用户问“你怎么收费？”时，也被当成投诉，分类出错。

解决办法：补充 带有“怎么”的负类样本，告诉模型不是所有“怎么”都是投诉；
让模型学到更细的特征（结合上下文和意图，而不是只靠关键词）


电商导购 Agent举例：
数据中“上海”“北京”多出现在高端产品类（正类），
模型自动认为凡是带城市名的查询都对应高价推荐，导致推荐错位；
解决方式：补足城市名的多样化样本（低价产品场景），平衡特征。
```

**2、阈值调优：平衡准确率与召回率**

阈值是判断一个预测结果是否“采纳”的门槛。阈值高，准确率高但漏掉很多结果（召回低）；阈值低，覆盖多但出错率上升。

```SQL
分数高于阈值 → 接受预测，返回结果；
分数低于阈值 → 拒绝或交给备用策略（比如转人工）
```

举例：假设用预测分数（0~1）做阈值调节，实验结果如下：

| 阈值 | 准确率 | 召回率 |
| --- | --- | --- |

对于客服和搜索场景，通常要优先保准确， **因为错答比漏答更影响体验，所以最终选 0.8~0.85 的区间**。比如教育 AI 批改时，低阈值能多改作业，但误改太多家长投诉；可通过实验找到“准确率 85%、召回率 70%”的平衡点，既能帮老师减负，又不影响公信力。

**调节阈值，平衡 准确率（Precision）和召回率（Recall）具体做法：**

1、 **准备验证数据：**用一份有人工标注的样本集，包含各种真实场景（比如客服问答的用户问题），确保能反映系统真实表现

2、 **逐个测试不同阈值：**逐步调节阈值，比如从 0.95 降到 0.5，每隔 0.05 测试一次，每个阈值下，计算对应的 准确率和召回率。

3、选取平衡点：

根据 业务需求 选定平衡点：如：

客服和搜索场景：用户体验最重要，优先保准确，一般选在 0.8~0.85；

推荐、召回、监控场景：宁可多抓一些，优先高召回，可以降到 0.7 左右。

**3、预处理、前处理和后处理：非模型手段的加速和修正**

光靠模型并不能解决所有问题，规则和预处理能快速补位。

（1） **预处理：**在数据进入模型前，去掉对预测有干扰的信息

```SQL
举例：
客服场景：删除“你好”“谢谢”等无意义寒暄，避免打乱语义。
语音助手：去掉“小爱同学”“小布”等唤醒词，防止模型误判。
招聘 Agent：规范化简历字段（学历、年限），防止格式不一致影响预测。
```

（2） **前处理：**模型预测前的快速筛选：减轻模型负担，把一些“确定性”样本用规则快速处理

```SQL
常见做法：
黑白名单（关键词完全匹配的直接输出，不进模型）；
命中时，直接走预设逻辑，完全跳过模型预测，
比如：脏话、攻击性语言，“你们公司骗子”：直接触发警告或转人工，不让模型参与
     竞争品牌、敏感行业词，“某山寨品牌”：直接拒绝回答

超短句、超长句（容易误判）直接拒绝或另行处理比如：短句：二次澄清，主动反问，补全信息再处理；长句：可以直接提示用户简化问题或分句处理）
```

（3） **后处理：对模型结果做修正**

```SQL
（1）阈值过滤（常见）

（2）打分调整：通过对关键词位置（句首/句尾）做加权，可以调整最终排序，让结果更符合用户意图

（3）实体约束：过滤模型学不到的规则，让模型结果符合业务逻辑，避免因语义相似而合并不该合并的内容。本质是 规则+词典补充，弥补模型无法学习到或难以泛化的“硬性边界”。比如：“五一节的由来” vs “六一节的由来”，语义很近，但不能合并为同类问题；用节日实体词典过滤，避免错误合并。步骤：1、准备实体词典，如：节日名词（五一节、六一节…）、品牌名、地名、产品型号等2、在检索或排序阶段引入检查：当模型检索或生成候选结果后，对 Query 和候选结果中的实体进行匹配，如果发现核心实体不同（例如“六一节” vs “五一节”），则降低相似度得分或直接剔除3、结合模型分数进行调整，如final_score = model_score × entity_penalty（entity_penalty 对于不匹配的实体可设为 0 或较低的值（如 0.1），匹配的为 1）示例：客服问答 Agent
用户问：“iPhone 15 维修政策是什么？”
模型召回了“iPhone 14 维修政策”，因为语义相似度高。
实体约束：检查型号实体，发现不匹配，剔除或降低分数，避免答错。
```

### **4.、验证与迭代：循环优化**
每次做完以上调整，都要重新跑评测集，看看效果是否真正提升。如果仍未达标，继续做 Bad Case 分析，进入下一轮优化。这是一个 螺旋上升的过程： **（1）每一轮解决最主要问题；（2）随着旧问题解决，新问题会逐渐暴露，所以建议定期再用数据评测集去验证跑小姑o；（3）当 Bad Case 分析发现问题已经无法归类，每类只剩少量散点问题，当前模型已经吃不下；或者现有调优手段收益极低，这时才考虑新架构或更强的模型**

### **案例补充：如何分析 AI 产品线上问题——以【电商客服 Agent】为例**
假设：你正在负责一个 **电商客服 Agent**，核心任务包括：查订单、查物流、售后规则问答、价格、库存、活动查询、商品推荐与比价

用户通过自然语言提问，例如：“我上周买的跑鞋现在到哪了？”； “手机壳为什么还没发货？”； “七天无理由支持吗？”产品上线后发现大量用户认为：“AI 回答不对”，但“不对”可能来自不同根因。如何系统分析线上问题？

**==——看链路：多轮对话 + 工具调用的系统，问题可能发生在任何节点，所以必须有链路回放、工具日志、RAG 召回记录、Prompt 日志。==**以“查物流”为例，一次完整的请求实际上包含至少 7 个链路步骤，任意一个环节出错，都可能导致最终回答不对

```Python
用户 Query
 →
Rewrite 标准化
 →
意图识别（判断是不是查订单）
→
获取用户最近 N 笔订单（工具调用）
→
匹配具体订单（逻辑校验）
→
工具调用物流系统
→
大模型对工具数据进行解释后生成结果
```

![image](images/img_0468.png)

那么问题可能出在：

1、 **链路执行错误：**如：

工具调用失败；搜索/RAG 返回错误；Rewrite 改坏了用户意图；Memory 读取错上下文；校验器逻辑出错

2、 **Prompt 设计缺陷：**如：

没写清楚格式要求；风格要求误导；prompt 内部冲突；多轮对话系统提示被覆盖

3、 **知识不足（RAG 缺失或不专业）**

专业场景（法律、人力、工程、医学）；行业术语、格式、规范不熟；缺对应知识

4、 **模型能力短板：**

计算；多步骤推理；时间感知；结构化能力

5、 **训练数据问题（自研模型）：**

口头禅模式化；冗余反问；SFT 噪声数据；RM 偏好异常；价值观/语气不一致；比如：模型总爱说“我觉得” ，可能是 SFT 数据的问题

![image](images/img_0469.png)

4、【案例3】回答售后规则模糊，专业度不够—不是模型弱，是知识缺失

```Python
用户问：“我这个手机壳能七天无理由退吗？”
系统回答：“通常情况下，大多数商品支持七天无理由退换。”
但实际上：手机壳类商品有例外条件；电商平台内每个店铺可能都有独立售后规则；某些券后商品可能不支持退换
```

**排查思路：**

**（1）这个问题模型是否调用了 RAG？**

**（2）是否有“售后规则”知识库？**

**（3）是否召回了正确的 chunk？**

**（4）召回内容本身是否包含店铺 ID、类目、SKU？**

**结论：**缺提供售后规则文档（店铺政策、类目规则、商品层规则）

**解决方案：**构建电商售后规则知识库（类目层 / 店铺层 / SKU 层）；每次回答必须基于召回引用；增加“非引用不回答”策略
