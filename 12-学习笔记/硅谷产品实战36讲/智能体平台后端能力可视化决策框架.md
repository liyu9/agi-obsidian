# 智能体平台后端能力可视化决策框架

> 做智能体平台的过程中，如何确定编辑器中的哪些后端能力要提供可视化的配置项
> 关联项目 → [[智能体平台项目实战分析]]、[[AI Agent矩阵规模化落地项目实战分析]]

---

## 一、核心判断原则：三问法

对每个后端能力，问三个问题：

| 问题 | 是 → 可视化 | 否 → 代码/API |
|------|------------|--------------|
| **1. 用户会不会改？** 目标用户（业务人员/运营）是否需要频繁调整这个参数？ | 改得频繁→必须可视化 | 很少改/上线后固定→配置文件/SDK |
| **2. 改错了会不会炸？** 这个参数的错误配置是否会导致严重后果（数据泄露/系统崩溃）？ | 后果严重→可视化+校验+约束 | 后果可控→自由度更高的代码配置 |
| **3. 改的时候需不需要理解技术细节？** 用户设置这个参数时，是否需要理解协议/数据结构/底层原理？ | 不需要理解→可视化 | 需要深度理解→留给工程师用SDK |

## 二、实操判断矩阵

将后端能力按两个维度分到四个象限：

```
                    改错后果严重
                        │
         象限2          │          象限1
    可视化+强校验        │       可视化+引导
    · API鉴权方式        │       · LLM模型选择
    · 数据访问权限       │       · Prompt模板
    · Token配额         │       · 知识库绑定
    · 敏感信息过滤       │       · 意图识别阈值
                        │
  ── 改动频率低 ────────┼──────── 改动频率高 ──
                        │
         象限3          │          象限4
    代码/配置文件        │       可视化+预设模板
    · 超时重试策略       │       · 工作流节点参数
    · 日志级别          │       · 回复话术
    · 连接池配置        │       · 转人工条件
    · 序列化格式        │       · 触发条件
                        │
                    改错后果可控
```

**四个象限的处理策略：**

| 象限 | 策略 | 例子 |
|------|------|------|
| **象限1（高频+严重）** | 可视化 + 强校验 + 预设约束 | API鉴权方式只允许下拉选择，不允许自由输入；Token配额设上限 |
| **象限2（高频+可控）** | 可视化 + 引导向导 | LLM模型选择提供推荐标签；Prompt模板提供结构化编辑器 |
| **象限3（低频+严重）** | 代码/配置文件 + 审批流程 | 超时重试策略写在配置文件里，修改需走变更审批 |
| **象限4（低频+可控）** | 预设模板 + 高级模式折叠 | 工作流节点提供默认参数，高级参数折叠在"高级设置"里 |

## 三、智能体平台具体能力分类

### 必须可视化（业务人员P0要改的）

| 后端能力 | 为什么可视化 | 可视化形式 |
|----------|------------|-----------|
| LLM模型选择 | 不同场景对模型要求不同，运营需要按成本/效果切换 | 下拉选择 + 推荐标签（"推荐：性价比最高"/"最强：复杂推理"） |
| Prompt模板 | Agent效果的核心调优项，需要频繁迭代 | 结构化编辑器 + 分层标签（系统层/场景层/对话层） |
| 知识库绑定 | 每个Agent要绑不同的知识库 | 勾选列表 + 搜索 |
| 转人工条件 | 业务规则决定何时转人工 | 条件组合器（意图匹配/情绪检测/关键词触发） |
| 工单联动规则 | 哪些意图触发哪个工单类型 | 意图→工单类型映射表 |
| 回复话术/语气 | 运营需要调品牌调性 | 模板选择 + 变量插入 |
| 触发条件 | Agent何时启动 | 事件选择器 + 条件组合 |

### 可视化但折叠在"高级设置"（工程师改，业务人员不常改）

| 后端能力 | 为什么折叠 | 可视化形式 |
|----------|-----------|-----------|
| RAG检索参数（top-k/相似度阈值） | 调优时需要改，日常不动 | 滑块 + 默认值 + 说明文字 |
| 意图识别置信度阈值 | 影响准确率/召回率的平衡 | 滑块 + 实时预览影响 |
| 多模型路由策略 | 成本优化，但需要理解模型能力差异 | 规则编辑器 + 预设策略模板 |
| 重试/降级策略 | 稳定性配置 | 预设策略选择（保守/平衡/激进） |

### 不可视化，走SDK/配置文件（工程师专属）

| 后端能力 | 为什么不可视化 | 处理方式 |
|----------|--------------|---------|
| API超时/重试/限流 | 改错后果可控，但需理解网络原理 | SDK配置项 + 合理默认值 |
| 连接池/并发数 | 需要理解系统架构 | 配置文件 |
| 日志级别/链路追踪 | 运维侧配置，与业务逻辑无关 | 运维后台 |
| 序列化协议/数据格式 | 工程细节 | SDK默认处理 |

### 必须可视化+强校验（安全红线）

| 后端能力 | 为什么强校验 | 可视化形式 |
|----------|------------|-----------|
| 数据访问权限 | 越权=事故 | 只允许从权限树勾选，不允许自由输入 |
| API鉴权方式 | 凭据泄露=事故 | 只允许选择预配置的鉴权配置，凭据本身在凭据沙箱中管理 |
| 敏感信息过滤规则 | 数据泄露=事故 | 预设规则 + 正则表达式校验器 |
| Token配额 | 成本失控=事故 | 数字输入 + 上限约束 + 超额告警 |

## 四、决策流程图（可直接复用）

```
某个后端能力是否需要可视化？
│
├─ P0用户（业务人员）会改吗？
│   ├─ 会 → 改错后果严重吗？
│   │       ├─ 严重 → 可视化 + 强校验 + 约束
│   │       └─ 可控 → 可视化 + 引导向导
│   └─ 不会 → P1用户（工程师）会改吗？
│           ├─ 会 → 改错后果严重吗？
│           │       ├─ 严重 → 可视化（折叠在高级设置）+ 校验
│           │       └─ 可控 → SDK/配置文件 + 合理默认值
│           └─ 不会 → 硬编码默认值，不暴露
│
└─ 追问：这个能力改的时候，用户需不需要"看到效果"？
    ├─ 需要（如Prompt、阈值、路由策略）→ 可视化 + 实时预览/调试
    └─ 不需要（如超时、重试）→ 配置文件即可
```

## 五、实战经验总结

1. **"看用户是谁"比"看能力是什么"更重要** — 同一个RAG检索参数，对运营人员是"高级设置里的滑块"，对算法工程师是"必须精确调的数字"。先确定谁在改，再决定怎么暴露

2. **可视化≠自由输入** — 最好的可视化是"选择"而非"填写"。下拉选择 > 数字滑块 > 文本输入 > 代码编辑器。能用选择解决的，不要让用户填

3. **默认值是最被低估的产品能力** — 大部分后端能力不需要用户改，只需要一个合理的默认值。90%的用户用默认值就够了，9%改一下可视化参数，1%走SDK深度定制

4. **Bad Case驱动暴露** — 不要预先猜测所有需要可视化的能力。先上线最小集，看Bad Case中哪些参数被频繁要求修改，再逐步暴露。这和MVP思路一致
