# 需求文档与项目验证

> 来源：《硅谷产品实战36讲》第11讲、第13讲、第30讲

## 核心原则

- 需求文档不要求面面俱到，但必须写出团队真正需要的内容
- 产品经理每天做得最多的事 = 砍功能
- 权衡取舍要无情

---

## 方法论：产品需求文档（PRD）五大内容

### 1. 要解决什么问题

让团队对痛点保持一致。如果成员对问题的理解不在一个频道，做出来的产品必然不成功。

### 2. 论证痛点确实存在

用数据验证，不能想当然。这是最容易踩的坑——很多产品经理随随便便写出痛点，却没有验证。

### 3. 成功指标和反指标

明确衡量标准，包括功能成功的指标和可能带来的负面影响（反指标/侵蚀效应）。

### 4. 用户场景

不同场景差别很大，需分别描述。

> 示例：豆瓣图书推荐三种场景
> - 用户已选一本书 → 推荐相似书（信息明确）
> - 用户选感兴趣主题 → 推荐书单（信息有限）
> - 用户刚进入页面 → 根据历史推荐（信息最少）

### 5. 产品功能方案

包含六个方面：

| 方面 | 说明 | 示例 |
|------|------|------|
| 如何开启功能 | 入口点 | 点击"推荐"菜单 |
| 流程图 | **最重要的部分** | 每种场景的步骤流程 |
| 复用已有架构 | 大大节约开发时间 | 豆瓣已有电影/音乐推荐的产品流可直接复用 |
| 跨组协作 | 提前沟通 | UI冲突需其他组修改菜单 |
| 异常情况方案 | 功能无法达到预期时的兜底 | 用户无浏览记录 → 推荐畅销书单；英文新书数据不足 → 提示不适用 |
| 可能的坑 | 事先没想清楚的地方会出问题 | 推荐系统重复推荐（同书不同版本）；数据分散导致畅销排名失真 |

## 方法论：产品发布前的权衡取舍

### 四步法

1. **明确功能问题的风险和受影响的人群**
2. **列出所有可行选项及对每个群体的影响**
3. **分析各选项的风险**
4. **有大局观，选择代价最小的方案**

### 判断标准

> "这个是不是 launch blocking？" — 没有这个功能会不会影响产品发布？

---

## 方法论：产品优先级

### 优先级等级

| 等级 | 含义 |
|------|------|
| P0 | 现在要做 |
| P1 | 有空就做 |
| P2 | 一定来不及做 |

10个功能中最多3个最优先，一定有3个不优先。

### 四大误区

1. **认为所有功能都优先** = 所有都不优先
2. **优先的功能是最简单的功能** — 应该是最有价值的功能
3. **只考虑工程难度和效果，忽略潜在风险** — 尤其是跨组合作的风险
4. **没有明确"最优先"的定义** — 是否重要到推迟发布也要等？

### 产品经理三原则

- **无知**：不马上下结论，保持好奇心，提出假设再验证
- **无畏**：制定有难度的成功指标，激发团队潜力
- **无情**：不管想法多好，都分出主次，明确一定不做什么

## 案例

### 豆瓣图书推荐 — PRD完整推演

1. **问题**：用户渴望通过个性化方式找到感兴趣且评分高的书
2. **验证**：35%豆瓣用户已习惯通过豆瓣找书，特别是探索新书 → 痛点真实存在
3. **成功指标**：通过推荐功能下载/购买图书的次数
4. **反指标**：豆瓣其他产品（电影、电视剧）的使用频率是否降低
5. **场景**：已选书推荐 / 选主题推荐 / 首页个性化推荐
6. **坑**：重复推荐（同书不同版本《爱的教育》有无数版本，评论分散导致畅销排名失真）

### 明星用户功能发布危机 — 权衡取舍

**背景**：新功能帮明星用户宣传，iOS发现Bug导致95%用户看不到。iOS修复需2周，安卓已测试完毕且明星好评如潮，其他产品也计划同时发布。

**三个初始方案都不理想**，换角度思考：iOS用户点击量对整体影响多大？

**用户调研发现**：有的明星80%访问来自iOS，有的来自安卓。

**最终方案**：其他产品照常发布，iOS普通用户部分推迟2周，2周后再向明星用户显示完整增长数据。先让明星形成使用习惯，再用完整数据激励。

### Instagram "一定不优先"板块

老板在路线图中加一个"一定不优先"板块，专门写明确不做的事情。目的：当有人提出"要不要试试这个功能"或领导随口问一句时，可以迅速回归正轨，减少干扰。
