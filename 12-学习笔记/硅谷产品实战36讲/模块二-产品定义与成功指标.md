## 一、最小化可行产品 MVP（第10讲）

### 核心理念

最小化可行产品，源于"精益创业"（Lean Startup），由埃里克·莱斯（Eric Ries）提出：

> 精益创业提倡企业进行"验证性学习"，先向市场推出极简的原型产品，然后在不断地试验和学习中，以最小的成本和有效的方式验证产品是否符合用户需求，灵活调整方向。如果产品不符合市场需求，最好能"快速地失败、廉价地失败"，而不要"昂贵地失败"。

### MVP = "凤凰男"比喻

当你刚和"凤凰男"相恋的时候，他只是对你好，除此之外真的一无所有，但是之后他奋发图强，赚了钱买了房子买了车，后来提升了时尚品味，开始健身了，开始品红酒了，带你去世界各地游玩，最终成为了一个"教科书"般迷人的老公。

但是你最需要的是对你好，如果他连最基本的对你好都达不到，你肯定不会跟他继续交往。

**MVP就好比一个奋斗阶段的"凤凰男"：**
- 它至少要满足你的一个需求，并且可以比较好地满足
- 否则你没有任何理由去选择它
- **"最小化"** = 没有任何一个功能是"加上去也挺好的"，但少了任何一个功能都无法解决用户最基本的需求

### 最小化 = 降低试错成本，速度 > 完美

很多时候把产品做到完美再推向市场所花费的成本太高了，可能付出几年时间做出的产品却未能解决真正的用户需求，浪费大量时间和金钱。

不如在一开始只做出一个能够解决用户需求的、最最基本的产品，然后一步一步通过用户和产品的互动，不断优化、不断创新，最终形成优秀的产品。

#### 成功案例1：2004年的Facebook

只有填写用户的个人介绍、联系方式、政治观点、个人兴趣，显示用户的朋友、加入的小组和发消息功能。

这个阶段的Facebook还没有大名鼎鼎的朋友圈（News Feed），但具备了为用户提供最基本的和朋友交流、看朋友群的功能，满足了用户的窥探欲以及和他人交流的基本需求，所以大受欢迎。

#### 成功案例2：1997年的Google

只有简单的文本搜索功能，域名还在Stanford下面。输入关键词，选择希望显示多少条搜索结果，点击搜索后看到最相关的特定数量的结果。

#### 成功案例3：1994年的Amazon

内容就是一个书单，看中了哪本书就下单，然后Amazon帮你找到这本书寄给你，这时连自己的物流管理系统都没有。网页中显示有100万本书，提供了一个目录，可以查看书的作者、简介、书名、关键词等。虽然网站非常简陋，但可以帮助你找到书店找不到的书，所以非常受欢迎。

**共同特点：** 初级阶段的功能非常简单，但都能以最好的方式满足用户一个未曾被满足的需求，所以用户会持续使用，形成粘性。

### 可行性 = 确保产品能够基本解决用户需求

加快进入市场的速度，并不是说产品什么也没解决就可以进入市场。如果MVP连最基本的唯一需求都解决不好，首先需要提升产品体验，看看能不能用更好的方式解决这个需求，而不是着急增加新功能。

> 如果"凤凰男"在你说病了的时候，只是说"多喝热水"，而没有拿着玫瑰花和凉毛巾直奔你家，那他可能就要提升恋爱情商了，不然就算月薪从两千涨到三千也没什么价值。

只有把最基本的需求解决好之后，MVP才有价值，这之后才是考虑新功能和新体验的好时机。

#### 成功案例：Instagram —— 滤镜让MVP真正"可行"

Instagram刚刚创立的时候，只有发图片的功能，用户体验并不好。

有一次，CEO凯文·斯特罗姆（Kevin Systrom）和女朋友介绍自己的这款APP，他女朋友看到图片后说了一句：**"能不能把这些照片弄得好看一点呢？"** 他茅塞顿开，便和创业小伙伴们联合开发了几款滤镜，于是才有了后面的故事。

**分析：** 没有滤镜功能的Instagram不能算是最小化可行产品，因为用户的需求并不只是分享照片，而是要能够轻松分享拿得出手的照片。所以虽然改进后的Instagram没有发消息、探索板块等功能，但用户增长速度还是突飞猛进。

#### 反面案例1：Jelly —— 需求只解决了一方

Twitter联合创始人比兹·斯通（Biz Stone）创立的APP，一开始发布时有众多媒体站台、头版头条呼声很大。

定位是做朋友互动的搜索引擎：你在APP上提问，朋友登录后可以看到并回答你的问题。

**两个主要问题：**
1. 只解决了提问者的需求，但对回答问题的人来说毫无意义，回答问题的人并没有养成使用这个APP的习惯，最终回答量逐渐减少
2. 等到朋友的回答需要时间，而你往往没有耐心和时间等待朋友给你的推荐

#### 反面案例2：Chorus —— 社交压力适得其反

迪克·卡斯特罗（Dick Costolo）离开Twitter后做的APP，目的是帮助一群朋友互相监督定期健身、吃健康的食物。一开始有不少用户，但一个月后就不行了。

**原因：** 有人懒惰或太忙没有健身，其他朋友会提醒你，但后来也就觉得没有意义了；而被提醒的人也因为感觉羞愧不再继续使用。产品并没有从根本上解决用户需求，试图通过社交压力让大家坚持健身，但过大的社交压力却适得其反。上线8个月后就下架了。

> **两个失败产品的共同教训：** 归根结底是忽视了"可行性"，并没有真正解决用户最基本的需求，或者说没有以很好的方式解决这个需求。

### 要点速查

| 概念 | 一句话定义 |
|------|-----------|
| MVP | 最小化可行产品 = 降低试错成本 + 确保解决核心需求 |
| 最小化 | 没有任何一个功能是"加上去也挺好的"，少了任何一个都无法解决基本需求 |
| 可行性 | 必须能比较好地满足至少一个核心需求 |
| 凤凰男比喻 | 先满足最基本需求，再逐步进化 |
| 速度 > 完美 | 先发布最基本版本，通过互动不断优化 |

## 二、制定产品成功指标（第12讲）

### 核心理念

硅谷最牛的风险投资人约翰·道尔（John Doerr），1999年投资谷歌时教给了创始人OKR的概念，帮助谷歌达到了今天的高度。他在《Measure What Matters》中指出：

> 指标是为了定义你想要完成的目标，需要表达清楚在什么期限之内、要达到什么具体的、可衡量的结果。

**好的指标 vs 坏的指标：**
- 好指标："2018年底之前实现100万日活"
- 坏指标："让用户多花时间在APP上"（缺少期限和具体衡量标准）、"争取用户规模达到100万"（缺少期限）

> 作为一个产品经理，当你确定了正确的成功指标，你就成功了一半。

### 错误指标的代价

#### 案例1：电商的成功指标

如果是电商，成功指标应该是**下单用户数**，而不是总的用户数量。因为可以让大家下载APP抽奖赢取福利，但大家下载后并没有下单，即使积攒了千万用户公司也依旧无法做下去。

#### 案例2：微信朋友圈的成功指标

假设微信朋友圈的成功指标是用户在微信朋友圈花的时间。为了达成这个目标，微信向你推送了更多花时间的内容（文章、视频），却减少了你所关注的朋友发的文字状态或图片内容。

这样看似增加了在朋友圈花的时间，却忽略了你使用朋友圈的目的是和朋友互动。当需求得不到满足时，就会减少在朋友圈花费的时间，甚至放弃朋友圈。单纯采用用户花费时间作为成功指标最终起到了反作用。

**结论：** 产品的成功指标要和实现的用户需求相契合。

### 方法论：成功指标4步法

以微信朋友圈添加表情包评论功能为例：

#### 第1步：弄清楚整个产品的最高目标

如果我是微信朋友圈的产品经理，从微信的核心指标开始，毕竟朋友圈是微信的一个功能。假设微信的核心指标就是用户的活跃程度，包括用户评论、分享、发消息、发图片等用户行为。

这是一个非常复杂的指标，需要考虑每项用户行为的权重。假设已通过用户数据、调研等方式确定了衡量指标：

**用户的总活跃分 = 评论×1 + 分享×0.5 + 发消息×1**

朋友圈的设计初衷是希望用户通过这个平台分享自己的生活、增加朋友间的互动，以此来增加用户的活跃程度，从而提升整个微信的总活跃分。

#### 第2步：思考产品功能还有哪些指标需要注意

朋友圈的核心目的是提升微信用户活跃度、增加微信总活跃分。

另外，微信朋友圈正计划增加在用户发的状态间穿插广告的功能，即每隔几个状态就穿插一条广告，所以希望用户可以多刷几条朋友状态，以提高穿插广告的曝光量。

**所以，用户浏览朋友状态的数量也是一个指标。**

#### 第3步：思考新功能可以解决的问题和上面列出的指标有什么关系

在朋友圈加一个可以用表情包评论的功能，目的是降低朋友间互动的门槛，帮助用户更方便地发表评论。

- 发表评论的用户：可以通过一个有意思的表情，表达用文字无法传达的情感，对他们来说意义非凡
- 发表状态的用户：以前一条状态可能只有两条文字评论，但现在因为表情包降低了回复门槛，评论数增加到10条甚至更多，会感觉到朋友们都很关注他，激发再次发状态的激情
- **最终结果：增加了微信的总活跃分**

#### 第4步：思考反指标是什么

**反指标（counter metrics）是指产品带来的负面影响。**

假设微信还会对朋友圈的内容质量打分，那么使用表情包评论功能的反指标就是降低了朋友圈内容质量分数。

因为以前大家使用纯文字交流时都比较"走心"，交流内容也很有深度；而现在几个简简单单的暴走漫画、卖萌表情就可以代替语言，反而让交流流于表面，丧失了原本的厚重感，所以会降低整个朋友圈的内容质量分数。

**明确了新功能的成功指标和反指标：**
- 成功指标：提升微信的总活跃分 + 用户每天浏览朋友状态的数量
- 反指标：降低了朋友圈内容质量分

### A/B测试验证新功能

设置了实验组和对照组，实验组增加了这个功能，对照组没有，其他条件一样，观察两组成功指标和反指标的变化。

**如果实验组的成功指标增加显著，且反指标被控制住了，说明功能起到了想要的效果。**

**注意事项1：设定量化提升目标**

一般会设定一个指标提升的具体目标，比如5%，这个量化标准非常重要。如果新增加的功能对成功指标的提升低于这个目标，那新功能不能算作成功的，没有必要添加。

比如，花了两个月的时间只提升了0.1%，就应该认真考虑有没有必要继续花1个月优化这个功能。通过数据分析和估算发现，继续优化并不能达到提升5%的目标，那后续的优化就根本不值得了，需要当机立断砍掉这个功能。

**注意事项2：多指标之间的权衡取舍**

如果产品有多个指标想要提升，需要将这些指标按照重要性进行排序，方便出现问题时权衡取舍。

案例中的权衡场景：成功指标中微信总活跃分下降了、用户每天浏览朋友圈状态的数量增加了。一般会确保新添加的功能不会影响整个产品的总指标，选择放弃新功能。

但这个案例并没有这么简单：广告穿插在朋友圈的状态之间，用户浏览朋友状态的数量增加 = 浏览的广告数量增加 = 更多广告收入。所以产品经理需要权衡是整个产品的成功指标重要，还是通过广告获取更多利润重要。

**这样的决定往往超出了产品经理所能处理的范围，需要公司最高级别的领导来决策。** 公司高层可能说收入上不去、股票大跌，必须赶快扭亏为盈，那广告收入更重要；也可能说要以用户为第一原则，不能为了短期利益损害用户信任，那整个产品的总指标更重要。

**注意事项3：A/B测试的时间**

过短的测试时间得到的指标不具有稳定性，需要等数据稳定后再做决定。

比如表情包评论的功能，可能大家一开始因为新鲜使用频率比较高，各项指标都非常好看；但过几天用户发现朋友圈的评论全都是各种表情包，并没有实质内容和有价值的讨论，所以逐渐丧失了兴趣，导致指标大跌。那就需要延长A/B测试的时间，等指标稳定后再做决定。

### 要点速查

| 概念 | 一句话定义 |
|------|-----------|
| 好指标 | 有期限 + 有具体可衡量结果 |
| 成功指标4步法 | 产品最高目标 → 子指标 → 功能与指标关系 → 反指标 |
| 反指标 | 产品带来的负面影响，必须和成功指标一起考量 |
| 量化目标 | 设定具体提升目标（如5%），低于目标则不值得继续 |
| 多指标权衡 | 按重要性排序，涉及公司战略需高层决策 |
| 测试时间 | 等数据稳定后再做决定，警惕新鲜感效应 |

## 三、如何撰写产品需求文档 PRD（第13讲）

### 核心理念

硅谷很多产品经理不喜欢把大量时间花在写PRD上，认为应该直接和工程师、设计师面对面沟通，当面把东西讲清楚，而不是写一摞文档最后根本没人看。

**好处：** 做决定的速度非常快，开完会马上开始干活。

**缺点：** 如果团队成员还不具备自己做小决定的能力，或者公司对基本UI部件没有固定标准，可能出现功能和功能之间不协调的问题。尤其是当成员辞职后，整个产品组需要花很长时间来填补空缺。

**结论：** 还是要写PRD，只不过只写清楚最最重要的内容就可以了。

### PRD的目的

撰写PRD是为了和工程师、设计师、数据科学家等团队成员清晰的沟通产品蓝图，讲清楚产品要解决的问题、实现的场景、成功的标准等等，并有据可查。

PRD需要具备三种功能：
1. 和团队成员高效沟通，用他们能够看懂的方式清晰表达想法，让他们清楚什么该做什么不该做
2. 记录之前的问题是如何解决的
3. 明确列出产品功能的短期目标、长期目标，绘制一个从短期到长期的产品蓝图

> PRD并不需要面面俱到，重要的是写出团队成员真正感兴趣的、对他们有帮助的内容。

### PRD五大要素

#### 要素一：要解决什么问题

工程师、设计师等对产品解决的问题都有自己的理解，而且根本不在一个频道，这个情况在产品经理的工作中非常常见。

**案例：直播唱歌打分功能**

- 工程师们认为是为了让主播提高唱歌水平
- 设计师们认为是让粉丝们在主播换歌的空当不会感到无聊
- 按照不同思路设计的产品必然不会成功

**问题出在了产品经理身上：** 没在PRD中讲清楚到底要解决的问题是什么。

**正确做法（以豆瓣读书添加图书推荐功能为例）：** 先讲清楚这个功能要解决的问题是什么 — 用户现在已经可以通过豆瓣浏览评价高的图书、通过豆列找到感兴趣的书，新增的图书推荐功能是进一步解决用户渴望通过个性化的方式找到自己感兴趣且评分比较高的书。

> 让大家对产品要解决的用户痛点保持一致，可以避免以后无数个日日夜夜里的争论不休。

#### 要素二：论证这个痛点到底是不是存在

**重要提醒：这个坑我踩过，大家一定要注意！**

很多工程师觉得产品经理只会吹牛、瞎扯，确实有不少产品经理随随便便就写出了用户痛点，而并没有验证过这些痛点到底存不存在。

**案例：直播打分功能**

到底粉丝们在主播换歌空档期有没有闷、闷到什么程度？到底主播有没有必要提升唱歌质量、粉丝们在不在乎主播的唱歌质量？应该先验证这些问题是不是真的存在，然后再去谈论具体怎么设计功能。

**正确做法（豆瓣读书的例子）：** 如何验证用户是真的有寻找读书建议的需求？如果发现35%的豆瓣用户已经习惯通过豆瓣找书阅读，特别是通过豆瓣来探索刚刚推出的新书，那这个问题就是真实存在的。

#### 要素三：写清楚成功指标和反指标

**成功指标：** 通过图书推荐功能，用户在豆瓣下载或者购买图书的次数。

- 如果使用图书推荐功能的用户数量多、频率高 → 说明功能有人用
- 如果用户通过推荐找到书后，下载或购买图书的次数也增加了 → 说明功能对豆瓣有好处

**反指标和侵蚀效应（Cannibalization）：**

反指标是指增加这个功能后用户使用其他豆瓣产品的频率。如果因为图书推荐功能，豆瓣的其他产品（豆瓣电影、电视剧等）的用户数量和使用频率降低了，那这个功能对整个豆瓣产品来说到底是不是好功能就有待研究了。

> **侵蚀效应：** 如果一项新功能的成绩会挤占原有产品的成绩，这就叫做侵蚀效应，来源于生物界的自相残杀（cannibalization）这个词。

#### 要素四：讲清楚要解决的用户场景

图书推荐功能的使用场景：

**场景1：用户已经选择了一本书**
- 自动推荐和他这本书类似的其他图书
- 用户给了非常明确的信息，表明了此时此刻找书的意向
- 例如："我刚看了《钢铁是怎么炼成的》，给我推荐一本相似的书"

**场景2：用户选择了感兴趣的主题**
- 推荐书单
- 用户只给了一点点暗示，"犹抱琵琶半遮面"
- 例如："我喜欢科幻小说，给我推荐几本" — 可推荐的很多，用户没有具体想要哪本的想法，更多是在探索

**场景3：用户刚进入豆瓣读书页面**
- 根据他以前读的书以及喜欢的作家推荐书单
- 我们不了解用户使用图书推荐的目的，只能根据以前习惯推荐
- 涉猎广泛的话可推荐的书就太多了，并且不知道用户此时此刻想看什么

**从产品角度看：** 这三种场景的信息丰富度差异很大，设计思路也应该不同。

#### 要素五：解释清楚产品功能方案

一般包含以下六个方面：

**1. 如何开启这个功能**

**2. 功能的流程图（最重要的部分）**
- 针对每一种场景画出流程图
- 不一定是经过精心雕琢的精美图表，也可以用第1步、第2步、第3步等方式来表达

**3. 复用已有架构或产品流**
- 可以在已有基础上稍作修改而不用重新开发，大大节约开发时间
- 例如：豆瓣已经存在电影推荐和音乐推荐功能，图书推荐列表可以参照以前的产品流
- 已经推出了让用户选择音乐类型的功能和测试流程，可以直接应用在图书推荐上

**4. 跨组沟通协调**
- 涉及和其他组合作时，需要先和其他部门沟通好
- 例如：功能会和其他组的产品功能在UI上有冲突，可能要修改"推荐"这个总菜单，需要在PRD里记录

**5. 异常情况解决方案**
- 用户没有任何图书浏览记录 → 无法提供个性化推荐 → 要么随便推荐一堆书，要么直接导入畅销书单
- 英文新书资料不足无法生成推荐 → 告诉用户这本书不适用于推荐功能

**6. 事先没想清楚的坑（重要！）**

> 往往事先没有想清楚的地方都可能会出现问题，导致整个产品设计和开发都得从头来。

**案例：推荐系统重复推荐问题**

造成重复推荐的原因可能包括：
- 不同出版社的同一本书
- 同一个出版社、同一个作家的2014年版、2015年修订版、2016年再版

如果一个书单里10本书有3本是重复的，体验就太差了。需要找到去掉重复书名的方式。

如果数据提取时就考虑到了，机器学习模型的结果就会比较准确。但如果事先没考虑到，就需要从头开始。

**更严重的影响：** 《爱的教育》这本书有无数个版本（宝宝版、小学必读版、人生成长版、精编版、简化版），所有版本加起来有1万条评论，但系统默认是不同的书，每个版本的几百个评论在畅销排名都很低，这本书压根不会出现在书单上。发现这个问题后，要重新处理数据、重新运行训练环境、更新畅销排名等，非常容易推迟产品发布。

### 要点速查

| 概念 | 一句话定义 |
|------|-----------|
| PRD目的 | 清晰沟通产品蓝图，有据可查 |
| PRD 5要素 | 痛点 → 论证痛点 → 指标+反指标 → 场景 → 功能方案 |
| 侵蚀效应 | 新功能挤占原有产品成绩（cannibalization） |
| 场景信息丰富度 | 不同场景给产品提供的信息量不同，设计思路也应不同 |
| 事先想清楚 | 没想清楚的地方最容易出现问题，可能导致从头来 |

## 模块知识卡片

| 概念 | 一句话定义 |
|------|-----------|
| MVP | 最小化可行产品 = 降低试错成本（最小化）+ 确保解决核心需求（可行性） |
| 凤凰男比喻 | 先满足最基本需求，再逐步进化，但基本需求必须满足好 |
| 最小化 | 没有任何一个功能是"加上去也挺好的"，少了任何一个都无法解决基本需求 |
| 可行性 | 必须能比较好地满足至少一个核心需求，否则不应增加新功能 |
| 好指标标准 | 有期限 + 有具体可衡量的结果 |
| 成功指标4步法 | 产品最高目标 → 子指标 → 功能与指标关系 → 反指标 |
| 反指标 | 产品带来的负面影响，必须和成功指标一起考量 |
| 权衡量化 | 设定具体提升目标（如5%），低于目标则不值得继续 |
| PRD 5要素 | 痛点 → 论证痛点存在 → 指标+反指标 → 场景 → 功能方案 |
| 侵蚀效应 | 新功能挤占原有产品成绩（cannibalization） |
| 异常预案 | 事先没想清楚的地方最容易出问题，必须提前考虑 |
