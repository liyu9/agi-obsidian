# 用产品设计知识框架补充项目内容 — 可复用SOP

> **目标**：后续有新项目时，按照本SOP的步骤和自检清单，即可产出结构完整、逻辑自洽的项目实战分析
> **方法论来源**：《硅谷产品实战36讲》产品设计核心知识框架 → 详见 [[产品设计核心知识总结]]
> **示范项目**：2000人互联网企业 — 智能体与多智能体协作平台 → 详见 [[智能体平台项目实战分析]]

---

## 一、核心思路

**输入**：一个项目（已有基本事实和成果数据）+ 一套产品设计知识框架
**输出**：用框架的每个模块去"追问"项目，补充完整的产品分析文档

**关键原则**：不是套模板填空，而是用框架的每个问题去"逼问"项目的真实逻辑。框架是"问什么"，项目是"答什么"，SOP确保每个问题都被问到、每个答案都有数据支撑、不同角色的答案之间不矛盾。

---

## 二、前置准备：收集项目原始信息

在开始分析前，先把项目的"硬事实"整理出来，作为后续分析的锚点：

| 信息类型 | 示范项目内容 |
|----------|-------------|
| 项目名称 | 智能体与多智能体协作平台 |
| 企业规模 | 2000人互联网企业，20+业务团队，技术团队约600人 |
| 项目核心描述 | 搭建企业级智能体与多智能体协作平台，支持零/低代码可视化Agent搭建、工作流节点编排、RAG知识库调用、多Agent协作及跨系统集成 |
| 关键技术方案 | "主Agent+角色化子Agent"协作体系；可视化工作流编排引擎（LLM调用/条件分支/循环/代码执行/API调用）；工作流节点内置RAG检索+多模型路由；基于企业组织架构的团队空间与权限体系 |
| 核心成果 | Agent落地周期从3个月缩短至2周；累计支撑20+业务团队；复杂任务处理质量提升60% |

> **操作要点**：这一步只整理事实，不做分析。成果数据先列出来，后面分析时会逐个"追问"它对应什么方法论。

---

## 三、10步分析流程

### 步骤1：多角色痛点梳理

**做什么**：不要只从"用户"角度想痛点，要分层扫描——企业/业务团队/工程师/管理者，每一层都可能独立产生需求。

**关键追问**：
- 每一层：现状是什么？行业数据能否佐证？深层原因是什么？
- 痛点梳理完之后，问自己"还有谁在这个系统里但是没被分析到？"

**示范产出**：

| 痛点层级 | 痛点 | 现状 | 行业数据支撑 |
|----------|------|------|-------------|
| 企业层面 | AI资产无法沉淀，重复造轮子 | 20+团队各自搭建Agent，Prompt/工作流/知识库互不共享 | 重复开发率70%（IDC 2026）；87%企业反映"成本和安全管不住"（McKinsey） |
| 业务团队 | AI落地周期长，试错成本极高 | 单个Agent从需求到上线平均3个月 | 60%企业仍处试点阶段（IDC 2026） |
| 后端工程师 | AI与业务技术栈割裂，工程化断层 | AI生态Python为主，企业后端Java/Spring Boot，中间全靠API拼接 | 90%企业卡在底层基建（CSDN 2026） |
| 组织层面 | 多Agent协作缺乏治理 | 各团队自建Agent各自为政，通信黑盒 | 40%项目因治理失败将被取消（Gartner 2025） |
| 权限层面 | 组织架构与权限体系缺失 | Agent无法融入企业OA权限体系 | 73%企业将数据主权列为首要考量 |

**本次实战经验**：最初只梳理了"业务团队"和"组织"两层痛点，遗漏了企业层面（资产不沉淀）和工程师层面（技术栈割裂）。后者的遗漏尤其致命——工程师是平台的"集成者"，如果他们觉得不好用会绕过平台，企业资产依然无法沉淀。

---

### 步骤2：需求验证（三步法）

**做什么**：对每个核心痛点，用需求验证三步法确认它是真实存在的。

**三步法**：
1. 确认目标用户 → 谁在承受这个痛点？
2. 痛点假设 → 为什么存在？根因是什么？
3. 验证假设 → 有什么数据能证明？

**示范产出**：

| 痛点 | 目标用户 | 痛点假设 | 验证方式 |
|------|----------|----------|----------|
| AI落地周期长 | 20+业务团队的产品/运营 | 缺乏统一低代码搭建平台，每团队从零开始 | 统计各团队AI项目开发周期，发现80%时间花在基础设施而非业务逻辑 |
| 工程师技术栈割裂 | 后端开发工程师 | AI生态Python主导与企业Java技术栈不兼容 | 内部调研：Java团队接入LLM平均需2周手写适配层 |
| 资产无法沉淀 | 企业IT管理层 | 无统一平台，各团队独立建设无复用机制 | 盘点发现同类Agent被3+团队独立开发 |

---

### 步骤3：用户问题说明

**做什么**：每个角色写一条"作为…我想做…从而帮助我…"的用户问题说明。

**关键追问**：不同角色的"从而"是否指向同一个底层需求？

**示范产出**：

> **作为** 业务团队的产品/运营人员，**我想做** 零代码搭建符合业务需求的AI Agent并接入工作流，**从而帮助我** 将AI落地周期从3个月缩短至2周，快速验证业务假设

> **作为** 后端开发工程师，**我想做** 通过标准化SDK和可视化编排接入企业AI能力，**从而帮助我** 摆脱重复编写模型调用适配层的困境，将精力集中在业务逻辑而非底层胶水代码

> **作为** 企业IT管理者，**我想做** 统一管控所有Agent的权限、成本和安全策略，**从而帮助我** 实现AI资产沉淀与复用，避免重复造轮子，确保数据主权和合规性

---

### 步骤4：先拓展再专注

**做什么**：列出所有潜在用户和角色，然后按优先级聚焦。

**关键追问**：
- 谁最痛？谁数据基础最好？
- 谁是被忽视但"必须先过"的角色？（如后端工程师——平台必须先过工程师这一关，否则他们会绕过平台）

**示范产出**：

| 阶段 | 目标用户 | 角色 | 优先级 |
|------|----------|------|--------|
| 拓展 | 所有20+业务团队 + 技术团队 + 企业管理层 | 产品/运营、后端工程师、IT管理者 | — |
| **专注** | 客服团队 + 内容运营团队 | 产品经理、运营人员 | P0 |
| **专注** | 后端开发团队 | 后端工程师 | P0 |
| 次专注 | 广告投放 + 风控团队 / IT管理层 | 产品/运营 / IT管理者 | P1 |
| 后期 | 全业务团队（自助搭建阶段） | 业务人员（非一期重点） | P2 |

**本次实战经验**：后端工程师最初未被列为P0，但分析后发现——如果工程师觉得平台不好用，他们会绕过平台自己搭，企业资产依然无法沉淀。这和腾讯内部"赛马机制"导致的资源内耗同理。

---

### 步骤5：用户画像

**做什么**：每个P0角色写一个具象人物——年龄、职责、痛点、需要，越具体越好。

**关键追问**：画像中的"需要"是否与步骤3的用户问题说明一致？

**示范产出**：

- **张伟（客服团队负责人/产品经理角色）**：35岁，管理30人客服团队，日均处理5000+工单。痛点：重复问题占60%人力。需要：快速搭建能理解知识库、自动处理常见工单的Agent
- **李敏（内容运营经理）**：28岁，负责3个内容频道。痛点：每天花2小时从多个系统拉数据做日报。需要：零代码编排"数据拉取→分析→报告→排期发布"工作流Agent
- **陈磊（后端开发工程师）**：29岁，Java技术栈。痛点：手写HTTP调用层处理鉴权/限流/重试，Prompt硬编码，改一次重部署一次。需要：标准化SDK + Prompt版本管理 + 运行时调试
- **王芳（IT管理部总监）**：42岁，负责IT治理与安全合规。痛点：不知道哪些Agent在访问敏感数据、Token花了多少钱。需要：统一管控面板，看到所有Agent运行状态和成本归因

---

### 步骤6：底层需求洞察

**做什么**：对比不同角色的表面需求，提炼跨角色的共性底层需求。

**关键追问**：底层需求的结论，能否用一句话解释所有P0角色的核心诉求？

**示范产出**：

| 角色 | 表面需求 | 底层需求 |
|------|----------|----------|
| 业务人员 | 零代码搭建AI Agent | 将AI能力转化为可执行的业务流程 |
| 后端工程师 | 标准化SDK接入AI能力 | 把AI从"黑盒实验"变成"工程化组件" |
| 企业管理者 | 统一管控所有Agent | AI资产可沉淀、可复用、可衡量 |

**统一底层需求**：让AI从"个人工具"升级为"组织能力"——不仅个人能用好，组织也能管控、沉淀和规模化复用。

---

### 步骤7：产品定义

**做什么**：使命宣言 → 产品原则 → MVP定义 → 完整架构，每一步都要回扣底层需求。

**关键追问**：
- MVP是否同时满足了所有P0角色的核心需求？有无遗漏？
- 产品原则是否覆盖了所有P0角色？
- "一定不优先"板块是否列出了明确不做的事项？

**示范产出**：

**使命宣言**：让每个业务团队都能在2周内拥有可用的AI Agent

**产品原则**：
1. 零代码优先（服务业务人员）
2. 工程化兼容（服务后端工程师）
3. 安全可控（服务企业治理）
4. 协作原生（服务多Agent场景）
5. 资产沉淀（服务企业长期价值）

**MVP = 最小化（3+1个核心能力）+ 可行性（同时满足业务人员和工程师）**：

| MVP核心能力 | 服务角色 | 不做什么 |
|-------------|----------|----------|
| 零代码Agent搭建 | 业务人员 | 不做自然语言生成Agent |
| 工作流编排 | 业务人员+工程师 | 不做循环/代码执行节点 |
| RAG知识库调用 | 业务人员+工程师 | 不做知识库管理后台 |
| 标准化SDK与调试 | 后端工程师 | 不做IDE插件 |

---

### 步骤8：成功指标 + 反指标

**做什么**：用成功指标4步法定义正向指标；每个正向指标配一个反指标；设定指标权衡机制。

**关键追问**：
- 每个反指标是否有明确的量化阈值？
- 安全红线的触发动作是什么？
- 是否有"增长代价"的考量？

**示范产出**：

| 正向指标 | 目标值 | 对应反指标 | 阈值 |
|----------|--------|-----------|------|
| Agent落地周期 | 3个月→2周 | Agent幻觉率 | ≤5% |
| 业务团队覆盖数 | ≥15个团队 | 数据越权访问率 | 0（零容忍） |
| Agent搭建完成率 | ≥60% | Token成本失控率 | ≤10%团队超预算 |
| SDK集成采纳率 | ≥50%技术团队3个月内 | 业务系统稳定性影响 | 月均≤2次 |
| AI资产复用率 | ≥30% | 人工介入率 | ≤20% |

**指标权衡机制**：安全 > 质量 > 增长。越权访问率>0立即暂停；幻觉率>8%自动降级；成本超150%自动限流。

---

### 步骤9：优先级与"一定不优先"

**做什么**：P0/P1/P2分级 + 明确不做的事项。

**关键追问**：
- P0是否覆盖了所有P0角色的核心需求？
- 是否有"一定不优先"板块？

**示范产出**：

| 级别 | 功能 | 理由 |
|------|------|------|
| P0 | 零代码搭建 + 工作流编排 + RAG调用 + SDK与调试 | 覆盖业务人员和工程师两个P0角色 |
| P1 | 多Agent协作 + 权限体系 + Token追踪 + 资产模板 | 重要但可后补 |
| P2 | Agent市场 + 自然语言生成Agent + 多模型路由 + IDE插件 | 生态/体验增强 |

**一定不优先**：通用聊天机器人、Agent自主进化、对外SaaS化

---

### 步骤10：行业对标与数据验证

**做什么**：检索行业数据和大厂实践，交叉验证项目假设。

**关键追问**：
- 大厂踩过的坑我们是否也会踩？
- 行业数据能否佐证至少一半以上的痛点假设？
- 每个大厂实践，能否对应到我们项目的一个具体决策？

**示范产出**：

| 行业数据 | 佐证的痛点 |
|----------|-----------|
| 87%企业反映"成本和安全管不住"（McKinsey） | 企业层面：资产无法沉淀、治理缺失 |
| 90%企业卡在底层基建（CSDN 2026） | 工程师层面：技术栈割裂 |
| 40%项目因治理失败将被取消（Gartner） | 组织层面：协作缺乏治理 |
| 重复开发率70%（IDC 2026） | 企业层面：重复造轮子 |

| 大厂实践 | 对本项目的决策 |
|----------|---------------|
| 腾讯：赛马内耗→统一治理中枢 | 治理先于增长，权限体系不能是后期补丁 |
| 阿里：存量系统→零改造接入（MCP+Higress网关） | Java SDK/Spring Boot Starter是工程师采纳前提 |
| 字节：技术栈分散→ByteLLM统一模型网关 | MVP即内置模型路由能力 |

## 四、自检清单

完成分析后，逐项检查：

- [ ] 痛点是否覆盖了企业/业务/技术/管理至少3个层面？
- [ ] 每个痛点是否有行业数据交叉验证？
- [ ] 用户画像是否包含"非典型用户"（如后端工程师、IT管理者）？
- [ ] 底层需求是否用一句话统一了所有P0角色的诉求？
- [ ] MVP是否同时满足了所有P0角色的核心需求？
- [ ] 反指标是否有明确的量化阈值和触发动作？
- [ ] 优先级表是否覆盖了所有P0角色必需的功能？
- [ ] "一定不优先"板块是否列出了3条以上明确不做的事项？
- [ ] 行业数据能否佐证至少一半以上的痛点假设？
- [ ] 大厂实践的每个启示是否对应到项目的一个具体决策？
