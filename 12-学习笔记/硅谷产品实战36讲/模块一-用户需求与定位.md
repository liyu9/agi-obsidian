## 一、如何寻找用户需求（第07讲）

### 核心理念

产品存在的意义是帮助用户解决一个之前无法解决的问题，或者提供一个比之前的解决方法强10倍、100倍的解决方案。如果产品无法解决用户需求，这个产品根本没有存在的意义。

**最重要的原则：先从痛点出发，确认用户是否真正存在这样的问题，而不是一上来就得出产品应该长什么样子、有什么功能的结论。**

最终发布的产品和一开始的版本差得非常多，所以一开始就指望得出正确的产品结论显然是不现实的，在设计产品时应该先立足用户的问题，后续再通过不同版本的修正，从而更好地解决用户问题。

### 案例详解

#### 案例1：平衡车（Segway）—— 痛点不真实

平衡车靠电力驱动、具有自我平衡能力，刚出现时惊为天人，各种投资人、发明家都为绝妙设计感到震撼，但被寄予厚望的发明并没有顺利落地。

原因分析：
- 平衡车需要经常充电，售价非常昂贵
- 长途出行开车最方便，几公里路程用更便宜更方便的自行车就好
- 平衡车解决的问题并不是广大用户真正存在的痛点
- 发明十几年后仍只能在高档宾馆、花园景点见到踪影

**教训：** 技术再惊艳，如果痛点不真实，产品就没有意义。

#### 案例2：区块链/人工智能项目 —— 新技术硬套场景

娱乐界的人工智能、网红圈的区块链层出不穷，很多这样的项目都强行用新技术来套用某个领域或者某个应用场景，而没有去验证：
- 用户是不是真正有这样的痛点
- 用户的痛点是否足够大到让他们丢弃已有习惯、使用新产品
- 产品加上新技术后是否真正解决了一个以前解决不了的痛点

### 方法论：需求验证三步法

#### 第一步：确认目标用户是谁

不同的用户群体痛点差异巨大。例如：
- 给老年人设计的听音乐产品 vs 给00后设计的听音乐产品 → 完全不一样
- Facebook刚创立时：首先定位在扎克伯格所在的哈佛大学 → 后来拓展到所有大学生 → 然后拓展到所有人

**要点：** 在产品刚开始时，专注于特定某一类的用户群体，才能让产品设计更有针对性。

#### 第二步：通过数据分析和用户调查，作出关于用户痛点的假设

当要解决的问题已经有了一些解决方案，或者用户基数足够大可以找到量化数据时，可以先从数据出发：
- 看行业年报数据
- 搜索相关的调查研究以及市场研究
- 如果产品已有用户数据，先从自己本身的用户出发

**案例：快时尚销售额下滑的假设**

当发现快时尚公司的销售额最近连年下滑，假设可能有：
- 快时尚公司的设计没有跟上形势
- 用户的消费标准越来越高，越来越看不上低质量的产品
- 用户花在时尚上的钱越来越少

根据数据或用户行为提出假设，为下一步做更精准的数据分析和用户调查奠定基础，大致知道下一步调研活动应该怎么开展。

#### 第三步：进一步挖掘数据和用户反馈，验证用户痛点的存在

有了假设之后，怎么知道哪个才是真正的问题？或者这些都不是？

针对快时尚的3个假设进行验证：
- "快时尚公司的设计真的没有跟上形势吗？" → 看快时尚公司完成模仿知名时尚品牌所花时间是否比以前更多
- "用户在时尚的总投入增长了还是下降了？" → 如果没下降，单品消费价格有没有变化

也可以通过用户调查来验证：采访客户问他们上一次购物在什么地方、花了多少钱、对快时尚品牌的印象有没有变化。

**目的：以最快的速度明确用户的痛点到底是什么，是什么原因导致的。**

### 用户调查两种方式

#### 方式一：一对一面谈

**适用场景：** 有大概假设，知道用户痛点大致在什么领域，但并不清楚具体有哪些选择，需要非常系统地深入了解具体的痛点。

**案例：** 已知微信公众号的模板不够灵活，是很大的痛点。通过面谈了解：
- 到底是哪一部分需要更加灵活？需要更多模板？还是允许每天多发几篇文章？还是允许发更长的视频？

通过提出问题，根据回答进一步提问，可以更清晰地知道痛点在哪里，了解在什么情况下痛点存在、什么情况下不存在。

**两个注意事项：**
1. **用户样本选择要具有代表性** — 比如想知道女性群体使用抖音的痛点，只采访20岁以下的群体，样本不具备代表性
2. **一对一面谈的局限性** — 采访人数不会特别多，不要认为某个用户说的某句话就是真理，需要多找几个例子，看这个点是否广泛存在

#### 方式二：问卷调查

**适用场景：** 已有比较成熟的假设，有几个选项，想知道用户怎么想。

**案例：** 已知微信公众号不灵活，估计有模板的问题、有视频长度的问题，但不知道哪个更重要。通过问卷调查和统计技巧，广泛采样，了解在目标群体中哪个选项的痛点更大。

也可以在问卷中增加空白区域让用户自由填写，但这种方式用户可能非常发散，结论往往不够系统和专注，需要引导用户在某个固定领域发挥，或在恰当时候加以限制。

### 要点速查

| 概念 | 一句话定义 |
|------|-----------|
| 用户需求 | 产品必须解决真实存在的痛点，而非拍脑袋想出来 |
| 需求验证三步法 | 确认用户群体 → 作出痛点假设 → 验证假设 |
| 一对一面谈 | 适合深挖具体痛点，注意样本代表性和面谈局限性 |
| 问卷调查 | 适合量化比较已成熟的假设选项 |

## 二、目标客户和用户画像（第08讲）

### 核心理念

确定目标客户，就是要弄清楚到底怎么划分用户群体，然后截取哪部分用户作为目标客户。简单地说，弄清楚目标客户，就是一个**先拓展再专注**的过程。

### 确定目标客户："先拓展再专注"策略

**先拓展：** 列出会对产品有需求的所有人，并尽可能地细分。

**再专注：** 专注于最需要这个产品的人群，即使这个人群规模很小。

> 能100%解决一小部分人的需求，远胜于只能解决一大群人50%的需求。

**专注于小群体不会丧失发展潜力。** 相反地，当你非常好地解决了这一小部分人的需求后，他们会成为产品的粉丝，自然而然地自发宣传这个产品，从而让其他用户也跃跃欲试。

#### 案例1：Facebook —— 先专注再拓展

- 一开始专注于大学生群体
- 后来拓展到所有人

#### 案例2：Airbnb —— 从沙发客到全域

- 一开始专注于沙发客
- 后来拓展到时代旅馆、度假社区
- 现在还推出了Airbnb Experiences，专注于组织活动和体验

**核心结论：** 只有先解决好了某一类人的需求，让产品成为解决这类人需求的最好方式，然后才能再拓展到更多人。初版产品一定不是一开始就定位在"所有人"上，先专注于某一类人，才会更有成效。

### 两大误区

#### 误区1：目标客户群体定位不够有针对性

**案例：视频版权管理系统**

从整体数据来看，用户活跃度很高，但仔细研究就会发现：
- 媒体公司的活跃度提升了整个数据
- 媒体公司的侵权视频很多，但有专人负责处理，处理效率非常高
- 名人和小艺术家没有那么多时间处理侵权视频，处理效率比较低
- 大部分视频侵犯的是媒体公司的版权，整体数据很漂亮，误以为产品很给力

**结果：** 产品之前的功能只适用于媒体公司，不适用于小艺术家。但之前定位的目标客户是"所有发视频的人"，设计了一堆对媒体公司来说太低级、小艺术家又没时间用的功能，产品发布后效果不好。

#### 误区2：没有研究清楚目标群体最底层的需求

**案例：SoulCycle —— 发现底层需求**

美国健身品牌SoulCycle成立于2006年，一开始只是在曼哈顿上西区有一家规模很小的工作室、有几十辆单车，但很快就拥有了一群女粉丝，她们每周都要来好几次。

表面理解：目标群体就是喜爱单车、要锻炼身体的人士。

**深层洞察：**
- SoulCycle提供的是单车课，却有夜店般的音乐、激励人心的教练，和团结互助的同好群体
- 单车课成了很多人解压、展示自己积极心态、打鸡血的地方
- 这才是真正要满足的用户需求

**结论：** SoulCycle的目标群体不仅仅是爱锻炼的人，也包含了希望表达自我、战胜自己、激励自己的人。很多从来不健身、不玩单车的人也深深爱上了SoulCycle。

在SoulCycle上市的公开募股书中，不乏"你的灵魂至关重要"和"我们渴望去激励人群"这样的表述，来源于对目标群体的精准把控和精准的产品定位。

> 推荐阅读：《定位》（杰克·特劳特 & 艾·里斯）

### 用户画像（User Persona）

**定义：** 生动描绘用户的特点，把这类用户抽象成一个人，然后用介绍这个人的方式来描绘这一类人。也就是说，要找到一些符合目标特点的潜在用户进行调研，然后生动描述调研用户的特点。

**案例：运动兴趣社交APP的用户画像**

假设初版产品的目的是帮助有运动爱好的朋友们找到同好、更好地社交：

- **约翰**：25岁，酷爱跑步，经常参加马拉松，每周跑步三四次。经常和朋友一起跑步，喜欢买跑鞋、透气性较好的衣服，关注Instagram的马拉松运动达人。最希望得到跑步的训练课程、贴士以及准备马拉松比赛的营养和饮食建议。
- **卡罗琳**：38岁，三个孩子，喜欢自行车运动。每天上下班都骑自行车锻炼，周末偶尔和朋友参加30公里左右的山地骑行活动，喜欢买适合山地骑行的紧身裤。希望关注专业骑行达人，看看他们有什么关于训练和装备的建议。

**用户画像两大优点：**
1. 帮助更生动地描绘用户特点，有利于和团队成员交流，解释产品功能以及如何解决这些人的需求
2. 帮助更深入地了解用户，考虑用户的生活方式、爱好、性格特点等，从而从更高视角观察用户、了解用户，而不是在这个阶段过度纠结于某个小细节

### 用户问题说明

**定义：** 一句话，精炼、简单地描述到底要为什么用户解决什么问题。

**公式：**
> 作为 XX（什么样的用户），我想做 XX（什么事情），从而帮助我 XXXX（达到什么目的）

- **"作为 XX"** = 目标用户
- **"我想做 XX"** = 用户需求（非常重要：要以用户为第一人称表达，而不是以产品能够解决的问题为主语表达）
- **"帮助我 XXXX"** = 对产品功能的预期（在"我想做XX"之后，说明产品功能一定要解决用户真实存在的问题。如果"我想做XX"不一样，"帮助我XXXX"肯定也不一样）

**Facebook的实践：** 经常要求新加入的产品经理能够用"用户问题说明"这句话简明扼要地表达清楚产品功能。如果总结不出来，那就说明这个产品经理对用户需求和目标用户定位不够清晰。

### 要点速查

| 概念 | 一句话定义 |
|------|-----------|
| 目标客户 | 先拓展（列出所有可能客户）再专注（聚焦最需要的人） |
| 100% vs 50% | 100%解决小群体需求 > 50%解决大群体需求 |
| 底层需求 | 不要被表面需求迷惑，深挖用户真正的心理动机 |
| 用户画像 | 把目标用户抽象成一个人，用介绍这个人的方式描绘这类人 |
| 用户问题说明 | "作为XX，我想做XX，从而帮助我XXXX" — 一句话说清为谁解决什么问题 |

## 三、用例（Use Case）写法（第09讲）

### 核心理念

用例就是描述在什么场景下用户用产品来做什么事。用例的具体格式需要根据具体的产品场景和公司文化来确定，但**用例的目的是清晰沟通这个产品到底需要解决哪几个问题，具体是怎么解决的，以及用户为了解决这个问题需要做哪些操作。**

用例可以用文字、图表或流程图来表示，能让设计师和工程师以及产品团队其他人员清楚、准确地理解，才是最重要的，而不是要一定遵循某个固定的格式。

### 案例详解：微信加好友功能的用例

#### 第一步：列出所有用例

添加好友是双向的，彼此都成为了对方的好友。添加好友有不同的途径：

**一个用户想添加另一个用户：**
1. 通过用户名添加
2. 通过其他朋友分享的名片添加
3. 通过扫描二维码添加
4. 在群成员中找到该用户，点击进入主页，添加好友

**一个用户想同时添加一群人（如同学聚会）：**
5. 找到距离很近的其他用户，同时添加所有在这个距离之内的朋友
6. 同时输入相同的密码自动加入同一个群，从而在群中一个个地添加好友

#### 第二步：写清楚用例的条件、操作步骤和产品框架

**1. 什么情况下能开启这个功能？**

- 前4种方式：只要用户登录了微信，任何情况下都可以开启。但第1种和第3种更适用于面对面添加好友的情况
- 第5种和第6种：虽然任何情况下都可以开启，但如果没有一群人在身边就小题大做了，适用场景是一群人在一起面对面地添加好友

**2. 执行完这个操作以后，用户得到了什么？**

用户添加对方作为好友是一个双向的过程，从此以后可以：
- 查看对方的朋友圈
- 给对方发消息
- 把对方加到某一个群里

**3. 考虑如何清晰地表述用例怎么利用已经存在的产品架构**

哪些部分是用户已经熟悉的、哪些部分是新的，这个问题一般适用于在已有产品上添加新功能的情况。

假设前4个用例在上一版产品中已经发布了，现在需要增加第5个和第6个用例：

**可以共用的部分：**
- 进入添加好友功能的"入口点"是一样的：点击"+" → 点击"添加好友" → 选择具体添加方式
- 找到要添加的用户名后，点击进入介绍页面（头像、用户名、一句话介绍、"添加到通讯录"选项），和前四种方式一模一样

**需要新增加的部分：**
- 在菜单里新增两个选项
- 前四种用例更多是搜索和匹配，第5、6种需要能让用户快速添加
- 第5种利用了地理位置，假设相同地理位置的用户多半是在一起聚会的

**关键提醒：** 不要过于追求复杂的图表，把大量时间花在做图上，而应该思考表述用例的方式是不是最准确、最清晰的。

### 用例具体化

#### 情况一：有成熟框架的产品

可以逐步骤详细描述工作流：

> 用户点击"+" → "添加好友" → 会有个文本框让用户输入用户名 → 开启搜索 → 必须在用户名完全吻合的情况下才能显示目标用户名 → 点击进入想要添加的用户页面 → 点击"添加到通讯录"

这种方式和产品需求文档上的内容非常相似，适用于产品已经有了很多成熟框架的情况（已有进入"添加好友"的工作流、显示好友搜索的逻辑、"添加到通讯录"选项）。

#### 情况二：还没有框架的新产品

流程图可能更粗略：

> 用户进入添加好友的页面 → 页面有一个可以搜索用户名的地方 → 显示搜索结果，但需要预防加错人的机制 → 添加目标用户

先把产品功能实现所需要的组成部分说清楚，然后详细思考一个个组成部分应该怎么设计：
- 用户如何进入添加好友的页面
- 如何避免用户加错人

只有把这些问题思考清楚了，才能把产品需求写清楚，工程师和设计团队才可以真正开始实施。

**Facebook实战经验：** 搜索、添加好友的功能涉及用户信息显示、隐私设置等问题。看似简单的添加好友功能，会影响几十个不同的产品、上百个工程师，以及非常多的场景，因此把用例写得足够清楚非常重要。

### 要点速查

| 概念 | 一句话定义 |
|------|-----------|
| 用例 | 描述在什么场景下用户用产品来做什么事 |
| 用例三要素 | 触发条件 + 用户结果 + 复用已有架构 |
| 具体化（成熟产品） | 逐步骤描述工作流，细节到每一步操作 |
| 具体化（新产品） | 先列功能模块，再逐个思考设计 |
| 核心提醒 | 不要追求复杂图表，准确清晰最重要 |
