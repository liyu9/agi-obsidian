# Part 1：方法论总纲

## 一、认知奠基

### 0. AI 应用的四种基础形态

PM 在设计前必须先明确要做的到底是什么——它属于"基础形态"中的哪一类，再谈后续的 Agent 设计。业界通用的四种形态（按自主度由低到高）：

| 形态 | 本质 | 典型场景 | 一句话判断标准 |
|---|---|---|---|
| **单 Prompt（Single Prompt / Zero-Shot）** | 一次 LLM 调用，输入→输出，无外部状态、无工具调用 | 翻译、润色、简单问答、生成式改写 | 只用一次模型调用就能完成 |
| **Workflow（工作流）** | 把多个步骤（LLM 调用 / 工具调用 / 条件分支 / 循环）按**预定义路径**编排，路径是开发者写死的 | 客服 FAQ 路由、多步骤审批、固定流水线（生成 → 检查 → 发布） | 步骤和分支在写代码时已确定 |
| **Single-Agent（单智能体）** | 一个 LLM 作为控制器，**运行时**自主决定调用哪些工具、走什么步骤，直到完成任务 | 数据分析助手、运维诊断 Agent、调研型 Agent | 路径由 LLM 动态决定，但只有一个主 Agent |
| **Multi-Agent（多智能体）** | 多个 Agent 协作，通常有 Orchestrator 主 Agent + 多个 Worker 子 Agent，按角色分工、协议通信 | 数字员工团队、虚拟研发团队、多角色协作（coder+reviewer+tester） | 多个 Agent 节点，任务可在它们之间流转 |

> **关键澄清**：很多人把"接了 LLM 就能聊天"的产品叫 Agent，但严格来说那只是单 Prompt；只有当 LLM 能在运行时**自主规划、调用工具、迭代多步**时，才算真正的 Agent（Single 或 Multi）。

### 1. Agent 经典公式（Lilian Weng）
> **AI Agent = LLM（大脑/控制器）+ Planning（规划）+ Memory（记忆）+ Tool Use（工具调用）**

- LLM 是核心控制器，不是"调用一次模型"。Agent 本质是"感知 → 规划 → 行动 → 观察反馈"的自主闭环（Agentic Loop），区别于单轮问答。
- 注意：单 Prompt 不算 Agent（无 Planning、无 Tool Use、无 Memory），Workflow 也不算 Agent（路径是预定义的）。只有 **Single-Agent 和 Multi-Agent** 才符合上述公式。

### 2. Agent 与 Workflow 的关系：不是对立，而是相互嵌套

在 Coze、Dify、LangGraph 等主流平台中，**Agent 和 Workflow 经常是嵌套组合**的，而不是二选一：

```
┌─────────────────────────────────────────────────────┐
│  【外层】一个 Agent（Multi-Agent 或 Single-Agent）    │
│   - 顶层规划：把用户请求拆成若干子任务                 │
│   - 调度：把每个子任务分派给合适的执行者               │
│                                                      │
│   【内层】每个子任务可以是一个：                       │
│   ├─ 单 Prompt：直接让 LLM 回答                       │
│   ├─ Workflow：执行一段预定义流程                      │
│   │     └─ Workflow 的某个节点又可以嵌入一个          │
│   │         ├─ Agent（让 LLM 自主判断下一步）         │
│   │         └─ 另一个更小的 Workflow                  │
│   └─ 工具调用：HTTP/数据库/代码执行等                  │
└─────────────────────────────────────────────────────┘
```

**三种典型组合模式**（Coze / Dify 中最常见）：

1. **Agent 套 Workflow（Agent ⊃ Workflow）**
   - 场景：主 Agent 负责"理解意图 + 拆任务"，每个子任务用一段 Workflow 执行（步骤明确、可控）。
   - 例：智能客服 Agent → 识别意图后调"工单创建 Workflow" → Workflow 内部又嵌入"敏感词检查 Agent"。

2. **Workflow 套 Agent（Workflow ⊃ Agent）**
   - 场景：主流程步骤明确，但在某个节点需要 LLM 自主判断（例如"内容审核节点"要理解语义后再决定是否放行）。
   - 例：内容发布 Workflow → 进入"AI 审核 Agent"节点 → Agent 自检 + 调工具查重 → 返回 pass/fail。

3. **Multi-Agent 套 Workflow 和 Agent（Multi-Agent 编排）**
   - 场景：复杂任务按角色拆分，每个 Agent 内部又有自己的 Workflow 或子 Agent。
   - 例：虚拟研发团队 → Planner Agent（拆需求）→ Coder Agent（生成代码，内部走代码生成 Workflow）→ Reviewer Agent（审查，可调工具查 lint）→ Tester Agent（测试，调测试执行 Workflow）。

**PM 关键原则**：
- **不要先选形态，先看场景**：步骤明确的优先 Workflow（可控、可调试），需要灵活判断的用 Agent。
- **嵌套是常态**：实战中纯 Single-Agent 或纯 Workflow 都少见，**多层嵌套**才是工程化 Agent 的真实形态。
- **平台视角**：Coze 的"智能体"可以包含"工作流"作为工具；Dify 的"Chatflow / Workflow"中可以嵌入"Agent 节点"；LangGraph 中节点本身就可以是 Agent 或子图（subgraph）。

### 3. Workflow vs Agent 分界（Anthropic 第一原则）
| 维度 | Workflow 工作流 | Agent 智能体 |
|---|---|---|
| 路径编排 | 预定义代码路径编排（开发者写死） | LLM 运行时动态自主决定路径与工具 |
| 可控性 | 高、可预测、可调试 | 低、需护栏、可观测性要求高 |
| 适用 | 步骤明确、可预先拆解 | 开放性、需灵活判断 |
| 调试难度 | 低（按节点排查） | 高（需 trace 整个推理轨迹） |
| 典型平台节点 | Coze 工作流、Dify Workflow、n8n | Coze 智能体、Dify Agent 节点、LangGraph Agent |

**核心忠告**：先找最简单方案；能用单 Prompt / Workflow 解决的，就不要过度"Agent 化"。Agent 是最后的手段，不是默认选项。

### 4. 演进路径
Chatbot（一问一答）→ Copilot（人机协作）→ Single-Agent（自主闭环）→ Multi-Agent（多智能体协作）→ Agentic AI（智能体化企业）。PM 要判断产品处于哪个阶段，不要跳级。

## 二、企业 Agent 落地场景地图

### 2.1 企业内部高价值场景清单（按部门）

| 部门 | 典型场景 | 适合的 Agent 类型 | 落地优先级 |
|---|---|---|---|
| **研发** | 代码生成、Code Review、测试、DevOps | Copilot / 执行型 | ★★★ 高（容错性高） |
| **客服** | 工单分派、智能问答、售后 | 对话型 / 检索型 | ★★★ 高 |
| **数据分析** | 报表生成、归因分析、洞察 | 执行型 / 决策型 | ★★★ 高 |
| **运维** | 故障诊断、工单处理、自动化修复 | 自主型 | ★★☆ 中高 |
| **销售** | 线索筛选、话术辅助、CRM 录入 | Copilot | ★★☆ 中 |
| **HR** | 简历筛选、政策问答、培训助手 | 检索型 / 对话型 | ★★☆ 中 |
| **财务** | 报销审核、对账、合规检查 | 工作流型 | ★★☆ 中（需合规） |
| **法务** | 合同审查、风险提示 | 检索型 + 人工兜底 | ★☆☆ 谨慎（高风险） |

### 2.2 落地优先级判断标准（四维评估）

1. **价值 × 容错性矩阵**：高价值+高容错 = 优先做；高价值+低容错 = 谨慎做+人工兜底；低价值 = 暂不做。
2. **数据成熟度**：是否有结构化数据 / 知识库 / 历史语料可用（这是 RAG 型 Agent 的前提）。
3. **集成可行性**：能否对接现有系统 API（决定执行型 Agent 可行性）。
4. **ROI**：节省的人力成本 vs 开发 + 算力 + 维护成本（私有化部署算力成本见第五部分阶段 10）。

### 2.3 场景筛选原则（国内厂商 + Anthropic 共识）
- 优先选**高价值、可容忍延迟、容错性较好**的场景（内部知识助手、数据分析、客服初筛、工单分派）。
- 避免一开始就做**高风险、强实时、零容错**场景（医疗诊断定论、自动转账执行），需先人工兜底。

## 三、Agent 分类与选型

### 3.1 按自主性分级
| 类型 | 自主度 | 人类介入 | 典型适用 |
|---|---|---|---|
| **Copilot 助手型** | 低 | 每步确认 | 写作、编码辅助 |
| **Assist 协作型** | 中 | 关键节点介入 | 数据分析、调研 |
| **Automated 自主型** | 高 | 仅异常时介入 | 监控、工单处理 |

### 3.2 按形态分类
- **对话型（Chatbot）**：以多轮问答为主，检索 + 生成。
- **工作流型（Workflow）**：步骤明确，LLM 在节点间编排（Anthropic 五大工作流模式：Prompt Chaining / Routing / Parallelization / Orchestrator-Workers / Evaluator-Optimizer）。
- **自主型（Autonomous Agent）**：动态规划执行，ReAct 循环。
- **多智能体型（Multi-Agent）**：多角色协作（详见第六部分）。

### 3.3 按能力分类
- **检索型（RAG-heavy）**：知识问答，核心是 RAG。
- **执行型（Tool-heavy）**：操作外部系统，核心是工具调用。
- **决策型（Planning-heavy）**：复杂判断，核心是规划与反思。

### 3.4 场景 → Agent 类型 选型矩阵

| 场景特征 | 推荐形态 | 推荐能力型 | 自主性 |
|---|---|---|---|
| 知识问答（FAQ/政策） | 对话型 | 检索型 | Copilot |
| 多步流程（审批/报销） | 工作流型 | 执行型 | Assist |
| 开放探索（数据分析/调研） | 自主型 | 决策型 | Assist→Automated |
| 复杂协作（研发/项目交付） | 多智能体 | 混合 | Automated |
| 实时监控（运维/风控） | 自主型 | 执行型 | Automated |

## 四、企业级 Agent 设计思路

### 4.1 企业级 vs 消费级的 7 大差异

| 维度 | 消费级 Agent | 企业级 Agent |
|---|---|---|
| **权限管控** | 弱 | 强：RBAC、操作审批、最小权限 |
| **数据安全与隔离** | 单用户 | 多租户隔离、数据不出域、脱敏 |
| **合规审计** | 弱 | 全链路审计日志、操作可回溯 |
| **可观测性** | 基础 | 全链路 trace、Langfuse、监控告警 |
| **系统集成** | 独立 | 对接 OA/ERP/CRM/飞书/钉钉等 |
| **高可用与性能** | 容忍波动 | SLA、并发、限流、降级 |
| **多租户** | 无 | 租户隔离、配置隔离 |

### 4.2 企业 Agent 架构分层（五层）

```
┌─────────────────────────────────────┐
│  接入层：前端 / IM / API / 语音多渠道   │
├─────────────────────────────────────┤
│  编排层：Agent 编排引擎、工作流、       │
│         Multi-Agent 协调（Orchestrator）│
├─────────────────────────────────────┤
│  能力层：提示词、Skills、Tools、子Agent │
├─────────────────────────────────────┤
│  数据层：RAG、知识库、记忆、向量库       │
├─────────────────────────────────────┤
│  基础设施层：模型网关、算力、监控、安全   │
└─────────────────────────────────────┘
```

### 4.3 Gartner 企业 Agent 能力框架（Competency Framework）
以"企业上下文为核心"，用**能力（Competency）**来定义、规划和管理 Agent 的能力边界，而非笼统的"做一个 Agent"。强调企业需建立一套能力目录来治理 Agent 资产。

## 五、Agent 通用设计全流程（十阶段）

### 阶段 1：需求定义与必要性判断
- **Agent 必要性三条件**（OpenAI）：多步骤任务 + 有工具可用 + 自主价值 > 复杂性代价。
- **问题建模五要素**：角色 + 任务 + 输入 + 输出 + 成功标准（可量化）。
- **自动化边界**：哪些步骤 Agent 自主、哪些需人确认、哪些必须人工执行。

### 阶段 2：能力边界与护栏设计
- **边界三问**：能力范围边界（能/不能做什么）、行为约束边界（工具/数据权限）、兜底边界（失败/低置信度回退）。
- **护栏三类**：输入护栏（拦截越界 prompt）、输出护栏（校验安全/格式/合规）、行为边界（只读不写、金额上限）。
- **HITL**：高风险动作（发送/支付/删除）前必须人工确认；介入点清晰可见、可中断。

### 阶段 3：上下文 / 提示词工程
- **范式跃迁**：Prompt Engineering → **Context Engineering**（上下文是有限关键资源）→ **Harness Engineering**（管理运行外壳）。
- **System Prompt 设计**：清晰 > 花哨；给"规矩"而非"人设"；结构化分区（角色/工具/流程/约束/示例）；复杂流程用 few-shot + CoT。
- **上下文三支柱**（Anthropic）：**Compaction**（压缩历史）、**Note-taking**（结构化笔记/scratchpad）、**Sub-agents**（子智能体隔离上下文）。

### 阶段 4：规划机制设计
- **任务分解方法**：CoT（逐步推理）、ToT（探索多条路径）、ReAct（推理+行动+观察交替）、子任务分解。
- **四大 Agentic Design Patterns**（Andrew Ng）：Reflection 反思、Tool Use 工具、Planning 规划、Multi-agent 多智能体。
- **权衡**：规划越复杂 → 自主性越强，但延迟/成本/不可控性越高。多数场景用简单 workflow 即可。

### 阶段 5：工具设计
- **工具定义三要素**：名称 + 描述 + 参数 schema（JSON Schema）。描述写给 LLM 看。
- **三大协议**：Function Calling（OpenAI）、Tool Use（Anthropic）、**MCP**（Model Context Protocol，开放标准，类似 USB-C，优先考虑以提升复用性）。
- **设计原则**：原子化（一工具一事）、错误信息对模型友好、能查不背（减少幻觉）、最小工具集起步。

### 阶段 6：记忆机制设计
- **双层模型**：短期记忆（会话上下文/scratchpad）+ 长期记忆（跨会话，RAG/向量库/知识图谱）。
- **四步模式**：推理前加载 → 推理中使用 → 记忆更新 → 信息处理（提取/压缩/检索）。
- **写入/检索策略**：什么值得记（关键事实/偏好/决策），什么该丢弃；检索按相关性+时效性+重要性打分。

### 阶段 7：评估体系（Evals）
- **离线评估**：构建 50–100 题的 Golden Dataset（含正例/边界/反例），每次变更前回归测试。
- **在线评估**：LLM-as-Judge（强模型打分）、用户反馈（点赞/修正率）、Trace 可观测。
- **指标层级**：任务级（成功率）→ 步骤级（工具调用对错）→ 过程级（轨迹合理性）。
- **原则**：无 Evals 不迭代，用数据而非感觉。

### 阶段 8：迭代飞轮
收集 badcase → 补充 Golden Set → 改 prompt/工具/护栏 → 回归测试 → 上线 → 观测 → 循环。

### 阶段 9：部署与可观测
- **可观测优先**：trace、日志、监控是上线基础设施（OpenAI Agents SDK 强调 handoffs/tracing）。
- **成本/延迟/准确率三角**：PM 必须持续权衡，这是 Agent 产品的核心约束。

### 阶段 10：商业化
- **算力成本**：AI 时代的"电费"怎么算。
- **私有化部署成本**：大模型私有化到底有多贵。
- **商业模式**：AI 技术如何改变产品赚钱方式。

## 六、多智能体（Multi-Agent）企业落地

### 6.1 何时用多 Agent（而非单 Agent）
- 任务复杂度超过单 Agent 能力边界。
- 需要多种角色/专业技能（如 coder + reviewer + tester）。
- 需要并行提效（多子任务同时执行）。
- 需要信息隔离（不同 Agent 处理不同敏感度数据）。

### 6.2 典型协作模式
| 模式 | 机制 | 适用 |
|---|---|---|
| **Orchestrator-Worker** | 主 Agent 拆任务、分派子 Agent、汇总 | 通用、最常见 |
| **Hierarchical 层级** | 树状层级分工 | 大型复杂项目 |
| **Peer 对等** | 平等协作、共享黑板 | 头脑风暴、探索 |
| **Debate 辩论** | 多 Agent 辩论达成共识 | 高质量决策 |

### 6.3 企业数字员工团队
按职能分工设计 Agent 编队（如：需求分析 Agent + 设计 Agent + 编码 Agent + 测试 Agent + 审查 Agent），定义角色体系、分工设计与行为规范、任务链与信息传递协议。

### 6.4 单 vs 多 Agent 决策指引
- 先用单 Agent + 工具跑通闭环。
- 只有当单 Agent 出现"上下文污染、角色混乱、工具过多"时，才升级为多 Agent。

## 七、PM 十大核心原则

1. **简单优先**（Anthropic 第一原则）：能用简单方案解决，绝不过度 Agent 化。
2. **边界清晰**：能力边界、行为约束、兜底机制三位一体。
3. **上下文是稀缺资源**：管理好"进模型的每一条信息"。
4. **工具 > 记忆**：能查的不要让模型硬背。
5. **护栏是必需品**：没有护栏的 Agent 不能上线。
6. **评估驱动迭代**：无 Evals 不迭代，用数据而非感觉。
7. **人机协同**：高风险点必须保留人工介入。
8. **可观测**：trace 全过程，才能定位问题。
9. **从最小可用起步**：单 Agent、窄场景、闭环跑通再扩展。
10. **权衡三角**：在自主性、成本、延迟、准确率之间持续取舍。
