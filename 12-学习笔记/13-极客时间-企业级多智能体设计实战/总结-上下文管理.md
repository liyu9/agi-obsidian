## 一、认知框架：记忆的本质

### 1.1 记忆的本质是构建 message list

**大模型本身没有记忆**。每一次 API 调用都是独立的，模型不知道你上一句说了什么。ChatGPT 之所以"记住"你之前说的话，是因为应用层把你之前的对话历史悄悄塞进了这次请求的 message list 里。

message list 由若干条带 role 标签的消息组成——system（系统背景）、user（用户发言）、assistant（助手回答）、tool（工具返回结果）。当模型处理一条新请求时，它"看到"的不是一句孤立的用户问话，而是应用层组装好的完整对话历史。

**你往 messages 里塞了什么，模型就"知道"什么；你没塞的，它就不知道。没有魔法，只有信息流设计。**

### 1.2 电脑类比：贯穿整个模块

| 类比               | 对应      | 特性         |
| ---------------- | ------- | ---------- |
| **模型本身**         | CPU     | 只负责计算，不存储  |
| **上下文窗口**        | 内存（RAM） | 容量有限，断电就没了 |
| **外部存储**（文件、数据库） | 硬盘      | 持久化但需要主动读取 |

**记忆系统的核心就是设计一套机制：什么时候从"硬盘"加载到"内存"，什么时候从"内存"写回"硬盘"，"内存"快满了怎么腾空间。**

### 1.3 三代演进

| 时代                      | 核心动作                | 角色类比          | 上下文特征          | 课程       |
| ----------------------- | ------------------- | ------------- | -------------- | -------- |
| **Prompt Engineering**  | 人写全部内容              | 骑手拉缰绳手把手控制    | 用户提问就是全部上下文    | —        |
| **Context Engineering** | 工程逻辑构建 message list | 教练规划赛道和路线     | 工具返回值、中间步骤进上下文 | L19      |
| **Harness Engineering** | 预加载索引 + 模型按需探索      | 牧场主建围栏、水源、草料站 | 模型自己决定下一步      | L18 引入概念 |

**控制权从"写内容"转向"造环境"。** 即使 Claude Code 这种最先进产品，也依赖 CLAUDE.md 预加载项目结构、rules/ 预加载约束、MEMORY.md 前 200 行自动注入记忆索引——**预加载关键索引 + 模型按需探索的混合模式**，不是完全放手。

### 1.4 三层记忆架构

| 层级       | 课程  | 存储介质                      | 职责                               | 触发方式                               |
| -------- | --- | ------------------------- | -------------------------------- | ---------------------------------- |
| **上下文层** | L19 | ctx.json + raw\.jsonl     | Bootstrap 预加载、剪枝、压缩、跨 session 恢复 | 启动时 + 每次 LLM 调用前                   |
| **文件层**  | L20 | soul/user/agent/memory.md | Agent 主动写入偏好、SOP、主题索引            | 对话中触发（memory-save / skill-creator） |
| **搜索层**  | L21 | pgvector + BM25           | 海量历史语义检索、混合召回                    | 隐式触发（按 description 路由）             |

**完整闭环**：Bootstrap 加载文件 → 对话产生记忆 → 写通道持久化 → 下次 Bootstrap 自动生效 → 大量历史走搜索层按需召回。

## 二、核心问题：要解决什么

### 2.1 Agent 的四大记忆缺陷（L18 提出）

| 缺陷               | 表现                     | 解决课程                     |
| ---------------- | ---------------------- | ------------------------ |
| **跨 session 失忆** | 重启后昨天说的全忘，每次从陌生人开始     | L19 Bootstrap + ctx.json |
| **长对话崩溃**        | 聊久了 token 超限报错，工具越强越刺眼 | L19 剪枝 + 压缩              |
| **偏好学习为零**       | 说一百遍"别用表格"下次还犯，没有写通道   | L20 memory-save          |
| **历史回忆空白**       | 问"上次那个分析结论"一问三不知       | L21 pgvector 搜索          |

### 2.2 Context Rot（上下文腐化）的物理根因

这不是经验之谈，而是 Transformer 架构的物理规律：

- **注意力是有限预算**：1000 token 每个分到 1/1000，100000 token 每个只分到 1/100000。上下文越长，每条信息被"认真看"的程度越低
- **40% 拐点**：上下文使用量超过约 40%，模型能力显著下降（不是线性，是明显拐点）。**研究数据显示性能下降 15-47%**
- **U 型注意力分布**：开头和结尾关注最多，中间最易被忽略（Liu et al., TACL 2024）
- **架构层无法规避**：错误信息一旦进入上下文，会持续影响后续输出（Context Poisoning）

**Context Engineering 不只是能力问题，更是经济问题**——Transformer 计算复杂度是 n²，上下文翻倍成本翻四倍。

### 2.3 文件索引的三大崩溃时刻

1. **规模爆炸**：`memory.md` 200 行硬上限撑破
2. **语义模糊查询**："上次那个航班"类查询无精确分类
3. **维护成本爆炸**：写入、去重、时间戳本身消耗注意力预算

**解法只有一个：把记忆从"全量加载"变成"按需检索"。** 这就是搜索驱动的记忆系统要做的事。

### 2.4 记忆腐化的三形态（L20 提出）

| 形态         | 表现                                       | 危害                |
| ---------- | ---------------------------------------- | ----------------- |
| **过期事实**   | 六个月前的项目状态、已被推翻的技术决策与今天的内容并排存放            | Agent 用错误历史做今天的决策 |
| **相互矛盾**   | user.md 说偏好简短回复，agent.md 说详细解释每个步骤       | Agent 行为不一致       |
| **死链/野文档** | memory.md 指向已删除文件；workspace/ 里有未被索引的孤立文件 | Bootstrap 静默失败    |

**反直觉结论：过时的事实比缺失的信息危害更大。** 缺失时 Agent 会说不确定；有错误记忆时 Agent 会自信地给出错误答案。

### 2.5 不干预的三种生产级崩溃

1. **Context Overflow（上下文爆炸）**：100 款商品对比，30 轮后 token 超限
2. **Context Rot（上下文腐烂）**：50 个文件后重复提意见、相互矛盾，模型真的变笨
3. **Context Poisoning（上下文污染）**：错误信息被 Agent 当事实持续影响后续输出

## 三、上下文生命周期：六个干预节点

**Agent 的上下文是"生长"出来的，不是"写"出来的。** Workflow 里上下文是你直接写的（Step1→Step2→Step3 完全可控），但 Agent 运行在 ReAct 循环里，模型自己决定下一步，工具返回自动塞进 message list。

**上下文生命周期的本质，就是你在 ReAct 循环中能够干预上下文的时机窗口。**

### CrewAI 提供的六个节点

| 节点               | 触发时机        | CrewAI 支持               | 典型用途              |
| ---------------- | ----------- | ----------------------- | ----------------- |
| **① Bootstrap**  | Agent 启动前   | backstory 参数            | 注入身份、规则、记忆索引      |
| **② Pre-Model**  | 每次 LLM 调用前  | @before\_llm\_call Hook | 剪枝、压缩、session 恢复  |
| **③ Post-Model** | 每次 LLM 调用后  | @after\_llm\_call（有副作用） | 脱敏、格式化（实践中不用）     |
| **④ Pre-Tool**   | 工具调用前       | 需手搓                     | 权限校验、参数修正         |
| **⑤ Post-Tool**  | 工具调用后       | 需手搓                     | 结果清洗、敏感信息过滤       |
| **⑥ AfterTurn**  | 整个 turn 结束后 | 需手搓（在 kickoff 后做）       | session 持久化、异步建索引 |

**CrewAI 官方提供 Bootstrap（backstory）和 Pre-Model Hook（@before\_llm\_call）两把手术刀**，其余节点理解原理即可，有需要时可手搓。

## 四、加法体系：让模型知道该知道的

### 4.1 加法的四种主要手段

| 手段                | 机制                  | 类比           | 实现位置                 |
| ----------------- | ------------------- | ------------ | -------------------- |
| **Bootstrap 预加载** | 启动时固定加载（人设、规则、记忆索引） | 员工手册         | backstory 注入         |
| **工具返回注入**        | Agent 调工具后结果自动进上下文  | 员工查完资料多了一条信息 | ReAct 循环自动           |
| **记忆检索注入**        | 从持久化存储中检索相关记忆注入     | 翻看工作笔记       | search\_memory Skill |
| **Skill 按需加载**    | 渐进式披露，模型判断需要时加载完整内容 | 翻操作手册的具体章节   | SkillLoaderTool      |

### 4.2 Bootstrap 四件套（缺一不可）

每次 Agent 启动时，需要把以下四个核心信息结构化注入到 system prompt 中：

- **soul（身份）**：我是谁——名字、人设、性格
- **user\_profile（用户画像）**：用户是谁——偏好、背景、习惯
- **agent\_rules（行为规范）**：我怎么干活——SOP、约束、规则
- **memory\_index（记忆索引）**：我还记得什么——主题指针，不超过 200 行

注入时使用 XML 风格的标签分块（如 `<soul>...</soul>`、`<user_profile>...</user_profile>`），让模型定位更准确。每个块都有字数/行数硬上限保护，防止膨胀。

**关键设计原则**：只注入"导航骨架"不注入"全部内容"，**索引 > 全文**——文件是目录不是书。

**agent.md 是自我进化日志**：用户说"以后发消息前先确认"，Agent 用 memory-save 增量追加到 agent.md，下次 Bootstrap 时自动注入，行为约束永久生效。这与 soul.md（固定身份）的本质区别就在这里。

### 4.3 写通道：memory-save（语义记忆）

**memory 文件的典型结构**（workspace/ 目录下）：

- `soul.md`：人设：固定，工程师写，不被 memory-save 修改
- `user.md`：用户偏好：结构化条目，memory-save 的主要写入目标
- `agent.md`：行为规范：Agent 的增量自我进化记录
- `memory.md`：记忆索引：只存指针，≤200 行，Bootstrap 全量加载
- `memory_{topic}.md`：主题文件：只在需要时按需加载（一个主题一个文件）

**memory.md 的核心设计：只存指针不存内容**。Bootstrap 每次都全量加载 memory.md，200 行是硬上限。如果把内容也塞进去，三个月后 memory.md 就会撑破上限，Bootstrap 每次都要带入所有历史内容，真正工作所需的注意力被压缩。

**类比**：目录永远很薄，书可以很厚。Bootstrap 每次全量加载 memory.md，200 行是硬上限。

**memory-save 四步规范**：

| 步骤           | 内容                                                                           |
| ------------ | ---------------------------------------------------------------------------- |
| **① 准入控制**   | 四信号：Utility（三个月后还有价值吗）/ Confidence（有直接证据吗）/ Novelty（是否已存在）/ Type（稳定信息 vs 瞬态） |
| **② 分类路由**   | target ∈ {soul, user, agent, memory\_index, topic}                           |
| **③ 写入前检查**  | memory.md 行数三级阈值（<150 正常 / 150-179 预警 / ≥180 停止）                             |
| **④ 更新优于追加** | 找到旧记忆用精准替换；完全找不到才追加                                                          |

**两种触发方式**：

- **显式触发**：用户主动说"把刚才聊的记下来"——信号明确，误判率低
- **主动触发**：description 里描述场景——但 Agent 的主动记忆意识没有你期待的那么强，要写得足够具体

**为什么用 Skill 不用 Tool**：

1. **容量限制**：BaseTool description 装不下几百行的规范
2. **安全隔离**：主 Agent 不持有 FileWriterTool，写操作全部通过 Sub-Crew + 沙盒完成，**提示可以被忽略，挂载不能**

### 4.4 写通道：skill-creator（程序记忆）

**一句话规则**：

- 记**是什么/有什么** → memory-save
- 记**怎么做 + 需要标准化执行** → skill-creator

**为什么 SOP 不能直接写进 memory 文件**：

1. **执行可靠性**：自然语言 SOP 模型每次执行只是参考，会漏步骤、顺序错、跳过 CRITICAL
2. **路由精准性**：SKILL.md 有 frontmatter，SkillLoaderTool 精准路由；memory 文件只能全文读
3. **可迁移性**：Skill 可以分享给团队其他 Agent，memory 只属于这个实例

**七阶流水线**（教学场景用简化三步）：

```
完整版：Capture Intent → Draft → Eval → Review → Iterate → Optimize → Register
简化版：Capture Intent → Draft → Register
```

**SKILL.md 写作规范**：

- **frontmatter 三大字段**：
  - `name`：{动词}-{名词}，kebab-case 全小写
  - `description`：≤1024 字符，"a little bit pushy"（写得过被动会 undertriggering）
  - `allowed-tools`：最小化原则，只列真正需要的
- **正文规范**：explain the why——每步操作必须说明原因，而不是堆叠 MUST/NEVER。**没有原因的 NEVER，模型在 edge case 会自行决定要不要遵守；说了原因，模型才能在没见过的情况下举一反三。**

**注册步骤**：

1. 检查 load\_skills.yaml 是否同名（避免静默覆盖导致旧 SOP 丢失）
2. 写入 SKILL.md 到对应目录
3. 追加条目到 load\_skills.yaml
4. Read-back 验证落盘
5. 返回 JSON

下次 session 启动时，SkillLoaderTool 重新解析 yaml，新 Skill 自动出现在主 Agent 的 XML 描述里，**无需改任何代码**。

## 五、减法体系：让上下文没有不该有的

### 5.1 减法的三种主要手段

| 手段               | 机制                      | 关键点                     |
| ---------------- | ----------------------- | ----------------------- |
| **压缩/截断**        | 旧对话压成摘要或截断超出窗口部分        | **30-45% 主动触发**，不要等 80% |
| **选择性遗忘**        | 主动丢弃低价值信息               | 不是所有信息都值得留              |
| **Sub-agent 隔离** | 任务委派给子 Agent 用干净上下文独立工作 | 主 Agent 上下文始终精简         |

### 5.2 剪枝（Pruning）：控制 Tool Result 膨胀

**最大的上下文膨胀体不是对话，是 Tool Result**。一次搜索工具调用可能返回 10,000 tokens 的网页全文。

**剪枝黄金规则**：

- 对话消息尽量不动（有语义连贯性要求）
- Tool Result 可以大刀阔斧（它只是"原材料"，模型用完就不需要了）
- 关键 ID/数字剪枝前先提取出来单独保存

**保留占位不删除**：剪枝时把 tool 消息内容替换为 `[已剪枝]` 占位符，保留消息结构。**为什么不用删除**：删除 tool 消息会导致 `tool_call_id` 引用断裂，Qwen/OpenAI 格式校验报错。保留消息结构但清空内容是安全做法。

### 5.3 压缩（Compaction）：把历史变成摘要

**触发阈值**：**30-45% 主动触发**（不是 80%）。Context Rot 表明上下文变长本身就导致性能下降，主动保持干净比被动救火更有效。

**任务类型影响阈值**：

- 问答/助手类（30-50%）：上下文独立性强，可以激进压缩
- 长任务/调试类（70-85%）：状态依赖强，压缩要保守

**Lossless 策略**：压缩必然丢失信息，关键策略是**压缩前先持久化**——把重要信息写到磁盘，磁盘上有完整记录。raw\.jsonl 是 append-only 原始完整历史，ctx.json 是压缩快照。**ctx 快照是压缩视图，raw 是完整审计日志**。

**压缩实现关键点**：

- **分块摘要**（chunk\_by\_tokens + 轻量模型）：比整体摘要更精准，也能控制单次摘要输入规模
- **摘要用小模型**（qwen3-turbo），对话用大模型（qwen3-max）：摘要是低创造性高准确性任务，成本降低 60-70%
- **以 user 消息边界切割**：以"倒数第 N 个 user 消息"为界，保证 tool\_call + tool\_result 成对保留。**绝不能按消息数量切，否则 tool\_call\_id 引用断裂会崩溃**
- **摘要用** **`role: "system"`**：语义上是"背景信息"而不是"用户发言"，让模型正确理解摘要性质

**结构化压缩 Prompt**：必须明确"保留什么、丢弃什么"，至少包含三个保留项——用户目标、关键事实、未完成事项。明确禁止：中间过程、失败尝试、重复内容。**一个烂的压缩 Prompt 生成的摘要等于丢掉 90% 的有用信息**。

## 六、三层记忆架构的实现细节

### 6.1 上下文层（L19）：Bootstrap + 剪枝 + 压缩

**Session 持久化两份存储，各有职责**：

- **ctx.json**：覆盖写，跨 session 快速恢复用的压缩快照
- **raw\.jsonl**：追加写，完整审计日志，调试用

**Session 恢复机制**：

Agent 启动时检查 ctx.json，读取上次保存的快照，加载到 context.messages 中，然后追加本轮新 user 消息。**恢复时必须先提取当前 user 消息**（在 clear() 之前），避免替换后丢失。

**Session 内多轮**：append-only 模式——不是重新建 Crew kickoff，而是往已有的 message list 追加一条 user 消息。Agent 在第 N 轮时，能看到从第 1 轮开始的所有中间过程，包括用户没看到的工具调用结果、中间推理。

**Session 持久化要在 kickoff 后由 main() 统一完成**。@after\_llm\_call 因 CrewAI 框架 bug 不能用于持久化——只要注册了 after hook，框架会对 LLM answer 强制 str()，导致 executor 的 `isinstance(answer, list)` 判断失败，工具调用无法执行。

### 6.2 文件层（L20）：memory-save + skill-creator + memory-governance

**memory-save 五种写入目标**：

| target         | 写到哪里                         | 存什么                 |
| -------------- | ---------------------------- | ------------------- |
| `soul`         | /workspace/soul.md           | XiaoPaw 自身设置（名字、人设） |
| `user`         | /workspace/user.md           | 用户偏好、习惯、个人信息        |
| `agent`        | /workspace/agent.md          | Agent 行为规范的增量更新     |
| `memory_index` | /workspace/memory.md         | 新增主题索引条目（只写指针）      |
| `topic`        | /workspace/memory\_{name}.md | 某主题的详细内容            |

**每条记忆条目的标准结构**：

每条记忆条目包含两个时间戳：`created`（信息产生时间）+ `updated`（最近一次确认/修改时间）。没有时间戳，治理就只能凭感觉；有了时间戳，治理有据可查。

**类比维基百科词条**：被编辑了 1000 次，读者永远看到最新版，不是 1000 条追加记录并排放着。记忆文件要的是这个效果——有历史（git log 可追溯），但呈现给 Agent 的永远是最新、最准确的状态。

**Garbage Collection（记忆治理）**：

- **触发方式**：阈值触发（memory-save 写入时检测行数）+ 定期触发（每月一次）+ 用户主动
- **8 类检查**：①行数+死链 / ②野文档 / ③路由错配 / ④表述冲突 / ⑤表述冗余 / ⑥Skills 健康度 / ⑦安全扫描 / ⑧过期条目
- **CRITICAL 约束**：扫描 → 分析 → 报告 → **等待用户确认** → 清理。不得在用户确认前执行任何删除或修改操作。**误判可能删掉有效的长期参考资料，代价不可逆。**
- **清理优先用归档**（移动到 archive/）而不是直接删除

**无 GC 的记忆系统生命周期**：

```
0-3 月：记忆有价值，Agent 越来越好用 ✓
3-6 月：噪音积累，偶尔表现变差
6 月+：记忆成为负担，重置比维护更省事 ✗
```

**真实案例**：记忆文件超过 6000 token 后，模型承认看了这些规范，然后随心所欲地行动——失控的记忆增长让某团队 API 开销从 $127/周飙升到 $47,000/月。

### 6.3 搜索层（L21）：RAG + 混合检索

**RAG 的本质**：检索增强生成是通用范式，**不等于向量搜索**。搜索方式可以是 grep、SQL 全文索引、向量语义搜索、知识图谱——任意的。

**四种搜索方式**：

| 方式              | 适用场景                          | 典型工具                                     |
| --------------- | ----------------------------- | ---------------------------------------- |
| **grep/全文扫描**   | 小规模、精确 token 匹配（错误码、变量名、文件路径） | grep, ripgrep                            |
| **BM25 + 字段搜索** | 工业标准，考虑词频+逆文档频率+文档长度归一化       | Elasticsearch, PostgreSQL tsvector + GIN |
| **向量语义搜索**      | 模糊查询（"上次那个航班"），让 AI 理解语义      | pgvector, Milvus, Pinecone               |
| **知识图谱**        | 关系推理（"A 的所有依赖"）               | Neo4j, Amazon Neptune                    |

**生产级方案是混合检索，不是纯向量**。纯向量搜索在生产中几乎不够用——"上周"是时间约束纯向量无法过滤，"代码"是标签约束纯向量精度下降。

**混合检索核心公式**：`score = 向量得分 × 0.7 + 全文得分 × 0.3`，按得分降序取 topK。权重 0.7/0.3 是经验值，语义相似度权重更高，关键字匹配作为补充。

**关键设计原则：向量是普通列，不是独立的向量数据库**。标量+向量在同一张表，一条 SQL 搞定，架构简单、运维成本低。pgvector 把向量作为普通列，专门向量数据库需要先向量搜索再回查关系数据库，两次 I/O、还要维护数据一致性。

**Schema 设计要点**：

- **两个向量列**：`summary_vec`（摘要语义搜索）和 `message_vec`（原始对话语义搜索），分别用于不同搜索场景
- **search\_tsv 用 GENERATED ALWAYS AS 自动维护**：写入 search\_text，PostgreSQL 自动计算并更新全文索引列，不需要手动维护，也不会出现索引和数据不一致的问题
- **标量索引**：tags（GIN 数组索引）、created\_at DESC（时间排序）、routing\_key（用户隔离）

**幂等写入**：`id` 用 `session_id + turn_ts + user_message 前32字符` 的 SHA256 生成，`ON CONFLICT DO NOTHING`。网络抖动、重启恢复、手动重跑都不会产生重复记录。

**降级重试策略写进 Skill 文档**（不写代码）：

1. 搜索结果为空 → 先去掉时间限制（时间范围可能太窄）
2. 还是空 → 再去掉标签限制（标签可能不匹配）
3. 还是空 → 切换纯语义搜索模式

**chunk 设计是效果的关键**，比模型选型更重要。召回效果 80% 取决于 chunk 质量，20% 取决于 embedding 模型。本课用"一问一答为一个 chunk"——用户的问题和助手的回答合在一起才能完整表达语义。

**chunk 策略**：

- chunk 太大：语义稀释，召回不准
- chunk 太小：上下文丢失，生成质量差
- 最佳实践：语义完整的最小单元（一个观点、一段对话、一个事件）

## 七、工程落地的关键设计

### 7.1 CrewAI Hook 系统的设计原理

**核心约束**：`@before_llm_call` 必须绑定在 `@CrewBase` 装饰的类上，手动构造的 Crew 实例无法注册钩子。这是 L19 的关键结论。

**Hook 底层运行机制**（@CrewBase 自动处理）：

1. **标记检测**：`@before_llm_call` 在方法上打 `is_before_llm_call_hook` 标记
2. **自动注册**：`_register_crew_hooks()` 扫描类方法，把 bound method 注册到全局 Hook 列表
3. **作用域绑定**：注册的是 `bound_hook = hook_method.__get__(instance, cls)`——绑定到当前 Crew 实例，天然隔离
4. **每次 LLM 调用前触发**：executor 遍历 Hook 列表，依次执行，传入 LLMCallHookContext

**关键约束：in-place 修改**——context.messages 是 executor 内部的直接引用，必须用 `clear()` + `extend()` 做 in-place 替换。**重新赋值会让变量名指向新列表，executor 内部引用没变，修改对框架完全不可见。**

**Hook 上下文能拿到的信息**：

- context.messages：List\[dict]，mutable，in-place 修改
- context.agent：当前 Agent 对象（可读 role、backstory 等）
- context.task：当前 Task
- context.crew：Crew 实例
- context.llm：LLM 实例（可读 context\_window\_size，动态计算压缩阈值）
- context.iterations：当前迭代次数（可用来做迭代上限控制）

### 7.2 异步建索引（不阻塞主流程）

每轮对话结束后，触发后台建索引任务，不阻塞主流程返回用户。必须持有 asyncio.create\_task 的引用，**防止 Python GC 取消任务**。

**核心流程**：

1. kickoff 返回后，先做同步持久化（ctx.json + raw\.jsonl）——必须完成
2. 然后用 `asyncio.create_task()` 异步触发建索引，不阻塞返回
3. 同步 DB 操作放线程池（`run_in_executor`），不阻塞 event loop

**为什么同步持久化 + 异步建索引**：持久化是 mission critical 的（影响下次启动），建索引是 nice to have 的（影响搜索召回）。让用户感知的延迟最小化是工程目标。

### 7.3 索引 pipeline 的四步流程

每轮对话建索引分四步：

1. **解析 session JSONL → 轮次列表**：把对话历史解析成结构化轮次
2. **LLM 提取摘要 + 标签**：调轻量模型从对话中提取一句话摘要和领域标签
3. **embedding 向量化**：摘要和原始对话分别向量化（两个向量列）
4. **幂等写入 pgvector**：用内容哈希做主键，`ON CONFLICT DO NOTHING`

### 7.4 完整集成架构（L22 实战）

**原骨架一行代码没动**，改动集中在四个地方：

| 改动            | 文件                    | 内容                                                               |
| ------------- | --------------------- | ---------------------------------------------------------------- |
| **核心改造**      | `agents/main_crew.py` | @CrewBase 类 + @before\_llm\_call 钩子 + run\_and\_index()          |
| **新增记忆模块**    | `xiaopaw/memory/`     | bootstrap.py / context\_mgmt.py / indexer.py                     |
| **新增 Skills** | `skills/`             | memory-save / skill-creator / memory-governance / search\_memory |
| **基础设施**      | `docker-compose.yml`  | 新增 pgvector 容器                                                   |

**"骨架零改动、记忆长出来"**：好的工程设计留了扩展空间，后来加的东西只需要挂上去，不需要动骨架。飞书消息路由（runner.py）、多用户 session 隔离（session/manager.py）、Skills 路由（tools/skill\_loader.py）三个核心模块全部锁着不动。

### 7.5 初始引导机制设计

把引导程序写进 `agent.md` 本身（不是代码里），内置"初始引导 SOP"——六步走完就完整配置好一个 Agent：

1. **起名** — 介绍自己，问是否改名
2. **主要用途** — 让用户用自己的话描述
3. **回复风格** — 根据用途推理 3 个候选，用户选择
4. **用户信息** — 聚焦问 1-2 个最关键背景
5. **禁忌** — 问有没有特别不想看到的
6. **SOP 调教** — 提出 1 个核心 SOP 草案，确认后调用 skill-creator 沉淀

**触发时机完全由对话决定**——不是程序判断"第一次启动"，而是 Agent 自己在对话中发现引导节存在自然开始。**引导可以跨 session 分多次完成，不会重复**。

**自我清除机制**：六步全部完成后，XiaoPaw 调用 memory-save，用 Python regex 脚本把整个引导节从 agent.md 里删掉。**引导完成，不留痕迹，也不再消耗后续每次 session 的 token 预算**。

**为什么写在 agent.md 里而不是代码里**：

- 引导逻辑是 Agent 的行为规范，不是程序流程
- 写在 agent.md 里，用户可以随时调整引导的步骤和问法
- 写在代码里，逻辑就固化了

## 八、最佳实践（生产级经验）

### 8.1 Bootstrap 相关

| 实践                       | 落地心法                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------ |
| **Bootstrap 四件套缺一不可**    | soul（身份）+ user（用户画像）+ agent（行为规范）+ memory index（记忆索引），缺一不可                           |
| **agent.md 是自我进化日志**     | 行为约束用 memory-save 增量追加到 agent.md，下次 Bootstrap 时自动注入，永久生效                             |
| **MEMORY.md 设 200 行硬上限** | Claude Code 工程团队经过生产验证的数字，超过 200 行的索引反而让模型难以定位关键信息                                   |
| **结构化标签分块**              | XML 风格的标签（`<soul>` / `<user_profile>` / `<agent_rules>` / `<memory_index>`），让模型定位更准确 |

### 8.2 压缩与剪枝相关

| 实践                      | 落地心法                                                    |
| ----------------------- | ------------------------------------------------------- |
| **激进的触发阈值（30-50%）**     | 把压缩阈值设为 0.45，不要等到 80%。Context Rot 数据表明上下文变长本身就导致性能下降    |
| **Raw log 保证 lossless** | append-only 写入必须每次 kickoff 后都执行，ctx 快照是压缩视图，raw 是完整审计日志 |
| **摘要用小模型，对话用大模型**       | 小模型做摘要、大模型做对话，成本降低 60-70%                               |
| **分块摘要**                | 比整体摘要更精准，也能控制单次摘要输入规模                                   |
| **结构化压缩 Prompt**        | 必须明确"保留什么、丢弃什么"，至少包含用户目标/关键事实/未完成事项                     |
| **后台静默压缩**              | 异步放到后台线程执行，压缩在对话间隙悄悄完成，用户感知瞬时响应                         |

### 8.3 写通道相关

| 实践                        | 落地心法                                                              |
| ------------------------- | ----------------------------------------------------------------- |
| **准入四门控：在调用前过滤**          | Utility → Confidence → Novelty → Type，写入成本极低，治理成本极高，在源头控制省 10 倍力气 |
| **双时间戳**                  | `created`（信息产生时间）+ `updated`（最近一次确认/修改时间），治理有据可查                  |
| **更新优于追加**                | 找到相关旧记忆用精准替换，完全找不到才追加。维基百科词条效果                                    |
| **闭环治理**                  | memory-save 写入超 150 行时返回信号，主 Agent 主动触发 memory-governance         |
| **禁止写来源不明的内容**            | 外部工具原始输出必须先人工提炼再写——防范 Prompt Injection 写入持久化记忆的第一道防线              |
| **Skill vs Memory 一句话规则** | 记是什么 → memory-save；记怎么做 + 标准化执行 → skill-creator                   |

### 8.4 搜索层相关

| 实践                  | 落地心法                                                   |
| ------------------- | ------------------------------------------------------ |
| **chunk 设计优先于模型选型** | 召回效果 80% 取决于 chunk 质量，20% 取决于 embedding 模型。问答配对为最小语义单元 |
| **幂等写入，增量更新**       | id 用内容哈希（SHA256 前 16 位），`ON CONFLICT DO NOTHING`       |
| **降级重试写进 Skill 文档** | 不写代码实现，写在 SKILL.md 里 Agent 自主执行                        |
| **向量是普通列**          | 标量+向量在同一张表，混合检索一条 SQL 搞定                               |

### 8.5 工程结构相关

| 实践                               | 落地心法                                                      |
| -------------------------------- | --------------------------------------------------------- |
| **骨架零改动、记忆长出来**                  | 飞书路由/session 隔离/Skills 路由三个核心模块不动，记忆系统只挂上去不侵入             |
| **引导写在 agent.md 而非代码**           | 引导逻辑是 Agent 行为规范不是程序流程，用户可调整，逻辑不固化                        |
| **同步持久化 + 异步建索引**                | ctx.json 同步（启动恢复）+ raw\.jsonl 同步（审计）+ pgvector 异步（不阻塞）    |
| **必须持有 asyncio.create\_task 引用** | 防止 Python GC 取消任务                                         |
| **渐进式披露**                        | memory.md 是索引（很薄），topic 文件是内容（按需读），与 SkillLoaderTool 同一哲学 |

### 8.6 Session 管理相关

| 实践                              | 落地心法                                               |
| ------------------------------- | -------------------------------------------------- |
| **持久化在 kickoff 后由 main() 统一完成** | @after\_llm\_call 因框架 bug 不可用（强制 str() 破坏 tool 调用） |
| **ctx 快照 + raw 日志双写**           | ctx 用于快速恢复，raw 用于 lossless 审计/调试                   |

| **Bootstrap 文件定期治理**            | 每周让 Agent 自我复盘，合并可合并条目，主题文件化                       |

## 九、反模式与避坑指南

### 9.1 上下文管理类反模式

| 反模式                           | 致命后果                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| **`memory=True`** **就算上下文管理** | CrewAI 的 `memory=True` 是 Task 级 RAG 检索，不是对话历史压缩/Bootstrap 加载    |
| **等 token 超限再处理**             | Context Rot 在超限之前就已经让模型变笨了，API 返回 `context_length_exceeded` 时已晚 |
| **重新赋值 context.messages**     | 重新赋值让变量名指向新列表，executor 内部引用没变，修改对框架完全不可见                        |
| **压缩时不保护 tool message pair**  | 框架处理 tool result 时找不到对应 tool\_call\_id 会报错，必须以 user 边界切割        |
| **压缩粒度过细**                    | 单条消息为单位压缩会完全丢失语义，chunk 必须包含上下文关联的若干条消息                          |
| **压缩写磁盘不加并发保护**               | 多进程并发写入会损坏文件，应用原子替换或文件锁串行化写入                                    |

### 9.2 文件记忆类反模式

| 反模式              | 致命后果                                                                              |
| ---------------- | --------------------------------------------------------------------------------- |
| **记忆污染链**        | Prompt Injection 写入持久化记忆，每次 Bootstrap 都作为事实重新注入，复利式放大。Palo Alto Unit42 试验成功率 >95% |
| **记忆贪婪症（无差别写入）** | 2025 年 MemSkill 论文量化：无差别写入记忆的 Agent 基准测试得分比空记忆还低                                  |
| **记忆腐化（只写不治理）**  | 真实案例：记忆文件超 6000 token 后模型随心所欲，API 开销从 $127/周飙到 $47,000/月                          |
| **跨用户记忆泄露**      | Echoleak 事件：GDPR/HIPAA 场景直接合规风险，扩展多用户时 workspace/{user\_id}/ 命名空间隔离               |

### 9.3 搜索层类反模式

| 反模式               | 致命后果                                             |
| ----------------- | ------------------------------------------------ |
| **把 RAG 等同于向量搜索** | 函数名/错误码/文件路径等精确 token 匹配，向量搜索召回率不如 BM25          |
| **冷启动就上 RAG**     | 记忆量几十条用 grep，几百条用文件系统，上千条才需要搜索。过早引入是过度工程         |
| **向量和标量数据分离存储**   | 两套系统数据一致性是噩梦，分布式事务复杂度远超收益。pgvector 把向量当普通列才是正确架构 |

### 9.4 工程实现类反模式

| 反模式                                   | 致命后果                                              |
| ------------------------------------- | ------------------------------------------------- |
| **直接给主 Agent 挂 FileWriterTool**       | 主 Agent 能写到任何路径，提示可被忽略，挂载不能。正确做法是 Sub-Crew + 沙盒隔离 |
| **用 @after\_llm\_call 做 session 持久化** | CrewAI 强制 str() 导致 executor isinstance 判断失败，工具不执行 |
| **不区分"是什么"和"怎么做"**                    | SOP 写进 memory 文件得到的是语义记忆不是程序记忆，执行不可靠              |

### 9.5 通用避坑提醒

- **sub-agent 也要遵循 file 隔离**：多用户场景必须用 `workspace/{user_id}/` 命名空间
- **description 写得太被动会 undertriggering**：Claude 有不触发 Skill 的倾向，description 要 "a little bit pushy"
- **CRITICAL 规则必须 explain the why**：没有原因的 NEVER，模型在 edge case 会自行决定要不要遵守
- **Bootstrap 不是越多越好**：四件套够用，agent.md 写得越多启动越慢
- **memory.md 超过 150 行就开始预警**：等到 180 行才停才有 20 行缓冲，非常危险

## 十、关键经验总结

### 10.1 核心公式

> **记忆系统 = 三层架构 + 双向闭环 + 主动治理**
>
> - 三层架构 = 上下文层（实时）+ 文件层（持久化）+ 搜索层（按需）
> - 双向闭环 = Bootstrap 读通道 ↔ memory-save 写通道
> - 主动治理 = 30-45% 触发压缩 + 150 行触发 GC + 180 天过期候选

### 10.2 设计哲学

1. **没有魔法，只有信息流设计**——记忆的本质是构建 message list
2. **控制权从"写内容"转向"造环境"**——Harness 时代，预加载索引 + 模型按需探索
3. **目录永远很薄，书可以很厚**——索引 > 全文，200 行硬上限
4. **三种加法 + 三种减法**——Bootstrap/工具返回/记忆检索/Skill 按需 + 压缩/选择性遗忘/Sub-agent 隔离
5. **异步不阻塞、同步要保证**——建索引异步、持久化同步

### 10.3 关键工程决策

| 决策点          | 推荐选择                    | 理由                                |
| ------------ | ----------------------- | --------------------------------- |
| 记忆存储         | pgvector（向量当普通列）        | 标量+向量同表，混合检索一条 SQL                |
| Bootstrap 触发 | backstory 注入            | CrewAI 官方支持，无需 monkey-patch       |
| 剪枝/压缩触发      | @before\_llm\_call Hook | 唯一可在 LLM 调用前干预的位置                 |
| Session 持久化  | kickoff 后由 main() 统一    | @after\_llm\_call 不可用（框架 bug）     |
| 写入通道         | Sub-Crew + 沙盒           | 主 Agent 不持有 FileWriterTool，挂载保证隔离 |
| 摘要模型         | 小模型（qwen3-turbo）        | 低创造性高准确性任务，省 60-70% 成本            |
| 压缩阈值         | 30-45% 主动触发             | Context Rot 物理规律，不要等 80%          |
| memory.md 上限 | 200 行硬上限 + 150 行预警      | Claude Code 工程团队生产验证              |
| 混合检索权重       | 向量 0.7 + 全文 0.3         | 经验值，语义相似度权重更高                     |
| chunk 单元     | 问答配对为最小语义单元             | 用户问题+助手回答合在一起才能完整表达               |

### 10.5 三句话总结

1. **记忆的本质是构建 message list**——你往里塞什么，模型就知道什么；context 不只是能力问题，更是经济问题
2. **三层记忆分工协作**——上下文层管实时（剪枝+压缩）、文件层管持久化（写+治理）、搜索层管海量（混合检索）
3. **写入成本极低，治理成本极高**——准入四门控+定期 GC+确认前不删除，把治理做在源头
