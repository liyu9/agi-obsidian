# 30｜不止于“一问一答”：实现多轮对话与上下文管理

你好，我是陈旭。

在上一讲中，我们共同完成了一次激动人心的跨越。我们的 AI 助手不再仅仅是一个能“听懂”话的聊天机器人，它已经学会了“行动”。我们通过定义“页面蓝图”和“AI 能力清单”，并借助 JSON Patch 这一利器，成功地将用户的自然语言指令，转化为了低代码画布上真实不虚的 UI 变更。

现在，当用户说出“帮我创建一个蓝色的登录按钮”时，我们的 AI 助手能够精准地识别意图、提取实体，然后生成一道指令，让前端忠实地在画布上呈现出一个蓝色的、写着“登录”二字的按钮。整个过程一气呵成，这无疑是一个巨大的进步。

但是，我们很快就会遇到新的瓶颈。这种“一问一答”的模式，看似高效，实则对用户提出了一个隐藏的要求：你必须像一个专业的“指令员”，在单句话中提供一个动作所需的全部信息。

可现实世界中的沟通，并非如此。

试想一下，你作为用户，更自然的表达方式可能就是简单的一句：“嘿，帮我建个按钮”。此时，我们的 AI 助手会如何反应？按照现有的逻辑，它会因为无法从这句话里提取到 `text`（按钮文字）、`parentId`（按钮放在哪）等必要信息而陷入困惑，最终可能只能无奈地回复：“抱歉，我没听懂您的意思”。

这样的交互体验，显然是脆弱且反人性的。一个优秀的助理，不应该在信息不足时直接放弃，而应该主动追问、引导和澄清。他应该会接着问：“好的，按钮上要显示什么文字呢？”、“您想把这个按钮放在哪个容器里呢？”。

这就是我们这一讲要攻克的核心目标：让我们的 AI 助手，从一个只会执行完整指令的“指令员”，进化成一个懂得沟通、具备上下文记忆能力的“沟通者”。我们要让它在面对模糊或不完整的指令时，能够主动发起一轮对话，引导用户共同完成任务。这，就是多轮对话的魅力所在。

## 多轮对话的核心：用“意图模板”和“对话状态”管理上下文

要实现多轮对话，关键在于解决两个核心问题：第一，AI 如何知道为了完成某个任务，到底需要哪些信息？第二，AI 如何记住在连续的对话中，已经聊了什么，还缺什么？

在探讨解决方案时，我们很自然地会联想到行业中一些更宏大、更具前瞻性的理念，比如近期由 Anthropic、OpenAI 等公司共同推动的“模型上下文协议”（Model Context Protocol, MCP）。

MCP 的目标是创建一个像 USB-C 一样标准化的通用接口，让 AI 模型可以和外部工具（比如我们的 Awade 低代码平台、各类 API、数据库等）轻松地实现“即插即用”。这是一个非常激动人心的愿景，它着眼于解决 **AI** **模型与外部世界如何标准化通信**的宏大问题。

然而，MCP 并非解决我们当下这个问题的合适选择，我们现在的核心矛盾，并低代码平台与第三方系统之间如何通信和调用，而是**在平台内部，如何管理一个具体任务的对话流程**。因此，直接引入 MCP 的复杂性，不如先从一个更轻量、更聚焦的内部方案入手。

所以，在这一讲中，我们不直接实现 MCP，而是采用一种更务实、更贴合现有架构的方式来解决眼前的多轮对话问题。这个方案，建立在两个核心概念之上：**意图模板（Intent Schema）****和****对话状态（Conversation State）**。

### **意图模板：AI** **的任务说明书**

首先，我们来思考第一个问题：AI 如何知道完成一个任务需要哪些信息？答案是，我们直接“告诉”它。

我们可以为后端支持的每一个 `Intent`（意图），都定义一份“模板”或者叫“说明书”。这份说明书用结构化的方式，清晰地列出了执行此意图所需要的全部参数（也就是实体），并标明了哪些是必须的（required），哪些是可选的（optional）。

我们以在 Awade 平台中创建一个组件的 `createComponent` 意图为例，它的“意图模板”可以设计成这样：

```
{
  "intent": "createComponent",
  "params": {
    "componentType": { 
      "required": true, 
      "prompt": "好的，您想创建什么类型的组件呢？（例如：按钮、输入框、表单）" 
    },
    "parentId": {
      "required": true,
      "prompt": "了解。请问您想把这个新组件添加到哪个容器里呢？（您可以告诉我容器的名称或ID）"
    },
    "text": { 
      "required": false, 
      "prompt": "需不需要给它加上一些文字？" 
    }
  }
}
```

你看，这份 JSON 格式的模板，就像一份给 AI 看的“任务说明书”。它一目了然地告诉 AI：

要执行 `createComponent` 这个任务，`componentType`（组件类型）和 `parentId`（父容器 ID）是绝对不能少的。`text`（组件文字）是可选的，用户不说也行。更妙的是，我们还为每个必须的参数都预设了一句友好、自然的“追问”话术（`prompt`）。当 AI 发现某个必须参数缺失时，它就知道该如何向用户提问了。

这种方式远比我们自己去实现一套复杂的对话管理机制要来得清晰、可控且易于扩展。当我们的 Awade 平台未来增加了新的组件或功能时，我们只需要定义或修改对应的“意图模板”即可，而无需改动核心的对话逻辑。

### **对话状态：AI** **的临时记事本**

有了“任务说明书”，我们接着解决第二个问题：AI 如何记住对话的上下文？这就需要为它配备一个“临时记事本”，我们称之为“对话状态（Conversation State）”。

当用户开启一个可能需要多轮沟通的任务时，我们就在后端为这次会话创建一个独立的“对话状态”对象。这个对象会实时追踪当前对话的进展。

继续上面的例子，当用户说出第一句话“帮我建个按钮”后，后端经过 DSPy 分析，识别出 `intent` 是 `createComponent`，并提取出 `componentType` 是 `Button`。此时，后端就会在内存中（对于生产环境，更可靠的方式是使用 Redis 这样的外部缓存）创建一个如下的“对话状态”：

```
{
  "sessionId": "user_abc_123",
  "activeIntent": "createComponent",
  "collectedEntities": {
    "componentType": "Button"
  },
  "missingEntities": ["parentId"],
  "nextPrompt": "了解。请问您想把这个新组件添加到哪个容器里呢？（您可以告诉我容器的名称或ID）"
}
```

这个“记事本”清晰地记录了：

- `sessionId`：标识这是属于哪个用户的对话。
- `activeIntent`：当前我们正在聊的核心任务是 `createComponent`。
- `collectedEntities`：我们已经收集到的信息是 `componentType: 'Button'`。
- `missingEntities`：我们还缺哪些**必须**的信息，这里是 `parentId`。
- `nextPrompt`：根据“意 uto 模板”，我们下一步应该问用户什么。

在整个多轮对话的过程中，这个“对话状态”对象会不断被更新。每当用户提供新的信息，`collectedEntities` 就会增加，`missingEntities` 就会减少。直到 `missingEntities` 数组变为空，就意味着任务所需的所有信息都已集齐，对话就可以圆满结束了。

## 后端实现：让我们的“指令官”学会思考和提问

理论框架已经清晰，现在我们来看看如何在 Python 后端实现这套逻辑。我们需要对上一讲中的 `/chat` 接口进行一次升级改造。

改造后的核心处理流程，大致如下：

### **第一步：检查是否存在激活的“对话状态”**

当后端收到一条来自前端的消息时，它要做的第一件事，不再是立刻调用 DSPy 进行意图识别，而是先根据 `sessionId` 检查当前用户是否存在一个尚未完成的“对话状态”。

### **第二步：如果存在，则处理“追问的回答”**

如果系统发现存在一个激活的“对话状态”，比如，系统正在等待用户提供 `parentId`。那么，新收到的消息（例如用户回复：“就放在那个‘用户注册’卡片里”）就会被认为是针对上一个问题的回答。

此时，后端的处理逻辑会变得非常聚焦。它会再次调用 DSPy，但给出的指令不再是泛泛的意图识别，而是更具体的：“请从‘就放在那个‘用户注册’卡片里’这句话中，提取出组件的 ID 或名称”。这样可以极大地提高实体提取的准确率。

提取成功后（比如得到了 `parentId: 'card_register'`），后端就会立刻更新那位用户的“对话状态”对象。

### **第三步：如果不存在，则开启一次新的对话**

如果系统检查后发现，当前用户没有任何激活的“对话状态”，那么就和我们上一讲的逻辑一样，正常调用 DSPy，识别用户的初始意图。

在识别出意图后（比如是 `createComponent`），系统不会立即去尝试执行动作，而是会先加载该意图对应的“意图模板”，然后根据用户第一句话提供的信息，初始化一个全新的“对话状态”，并存入内存。

### **第四步：核心判断循环**

无论是更新了“对话状态”，还是创建了一个新的“对话状态”，系统都会立刻进入一个核心的判断循环：

> **检查当前意图的所有“必须实体”是否都已在** `collectedEntities` **中？**

- **如果答案是“是”**：太棒了，信息收集完毕！这标志着本次多轮对话的结束。后端会立刻集齐所有实体，执行最终的动作（也就是生成我们在第 29 讲中熟悉的 JSON Patch），并将其作为响应返回给前端。最后，也是非常重要的一步，系统会从内存中删除这个“对话状态”对象，释放资源，功成身退。
- **如果答案是“否”**：说明对话仍需继续。系统会从“意图模板”中，找到下一个缺失的必须实体所对应的 `prompt`（追问话术）。然后，它会将这句追问话术作为一次普通的文本消息，直接返回给前端。

通过这样一套“检查 -> 更新 -> 判断”的闭环逻辑，我们的后端就具备了引导对话、管理上下文的思考能力。

## 前端配合：让 Chatbot 忠实地传递“问题”与“答案”

听到这里，你可能会想，后端变得这么“聪明”，那我们的 React 前端是不是要做一番天翻地覆的改造才能配合？

答案是：几乎不需要！

这正是我们这套新架构设计的优雅之处。前端的职责被最大程度地简化了。我们的 `App.js` 或者说 ProChat 组件，完全不需要知道任何关于“对话状态”、“意图模板”的复杂逻辑。它需要做的，仅仅是忠实地处理好两种来自后端的响应。

回顾一下，我们的 Chatbot 向后端 `/chat` 接口发送请求，现在可能会收到两种截然不同的响应：

**一个** **JSON Patch** **对象数组**：这代表着一个或多个 UI 变更指令。当前端收到这种格式的响应时，它就知道任务已经最终完成了。它会像第 29 讲中那样，调用 `applyPatch` 库，将变更应用到 `pageSchema` 上，UI 随之更新。这对于前端来说，是“最终答案”。**一段普通的文本字符串**：这代表着 AI 助手发来的一个“追问”。当前端收到这种格式的响应时，它要做的就更简单了：就像显示任何一条普通的聊天消息一样，把这段文字渲染到对话窗口中，作为 AI 助手的回复。这对于前端来说，只是“过程中的问题”。

看到吗？前端的逻辑被简化为只用判断响应的数据类型：是对象数组（JSON Patch）？还是字符串（追问）？根据不同类型执行不同的渲染逻辑即可。

这种清晰的职责划分，使得前后端的耦合度变得非常低。后端可以持续优化它的对话策略和意图模板，而前端则可以专注于 UI 表现和用户体验，互不干扰。

## 小结

今天这一讲，我们再次完成了一次意义重大的进化。我们的低代码助手，终于摆脱了“一问一答”的机械模式，学会了在信息不足时主动追问和引导。

我们没有引入任何复杂的外部工具或框架，而是通过在现有架构上，创造性地提出了“意图模板”和“对话状态”这两个核心概念，就优雅地实现了多轮对话与上下文管理的能力。

这套系统的核心思想在于：

- **契约化：**通过“意图模板”，将 AI 完成任务所需的信息需求，以结构化的“契约”形式固定下来，使其变得清晰、可管理。
- **状态化：**通过“对话状态”，为短暂的、无状态的 HTTP 请求，赋予了跨越多次交互的“记忆”，这是实现一切复杂人机对话的基础。
- **职责分离：**后端专注于复杂的对话逻辑和状态管理，前端则只负责简单的响应判断和 UI 渲染，使得整个系统清晰、健壮且易于维护。

现在，我们的 AI 助手离一个真正意义上的 “Copilot” 又近了一大步。它不再是一个被动的指令执行者，而开始扮演一个主动的、能够与用户协作的“沟通者”角色。这个能力的构建，为我们未来去挑战更复杂的、需要规划和推理的 Agent 功能，铺平了道路。
