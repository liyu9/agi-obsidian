# 29｜当自然语言遇上可视化：打造新一代低代码开发体验

你好，我是陈旭。

在前面两讲中，我们已经为低代码平台的智能化转型打下了坚实的基础。

第 27 讲，我们从 0 到 1 搭建了一个功能完备的 Chatbot，解决了人机交互的入口问题。紧接着在第 28 讲，我们引入了强大的 DSPy 框架，让我们的 AI 助手具备了意图分类和实体提取的能力。现在，我们的 AI 助手已经能“听懂”用户的指令了，比如当用户说“帮我创建一个登录按钮”时，AI 能够准确地识别出用户的意图是 `createComponent`，并提取出关键实体信息，如 `componentType: 'Button'` 和 `text: '登录'`。

我们已经成功地解决了“理解”的问题。但是，这仅仅是智能化改造的第一步。一个只能“听懂”却不能“行动”的助手，价值是非常有限的。我们真正的目标，是让 AI 成为一个能干活、能分忧的 Copilot。

这就引出了我们这一讲要攻克的难题：如何跨越从“理解”到“行动”的鸿沟？如何将 AI 脑海中抽象的“意图”，转化为低代码编辑器画布上实实在在的 UI 变化？

在开始解决这个问题之前，我们先来一起思考几个问题。

你是否也曾有过这样的经历：面对一个像我们的 Awade 这样功能强大的低代码平台，在数不胜数的配置项清单中，突然怎么也找不到某个配置项的界面了？

另一个可能的问题，当你需要实现一个略带复杂度的交互逻辑，比如“点击 A，校验 B，然后更新 C”时，你是否发现，用鼠标拖拽和连线的方式，很快就会让你的画布变得像一团乱麻，难以理解和维护？

这些是传统可视化操作的“痛点”，单靠可视化的手段是无法解决的。那难道这些问题就没有办法解决吗？显然不是，自然语言就是一种有效的解决方法。如果我们可以直接“告诉”平台我们的需求，它就能自动完成那些繁琐的配置，这显然是是一种更高效、更符合人类思维的交互方式！

但反过来想，自然语言就真的完美无缺吗？它会不会带来新的问题，比如语义的模糊性？我们又该如何界定它与可视化操作的边界？是彻底的替代，还是某种形式的共存？

在动手编码之前，我们有必要先想清楚这些关乎产品理念和用户体验的顶层设计问题。因为答案，将直接决定我们接下来代码的架构和方向。

## 新范式：自然语言与可视化的协同与互补

很多团队在引入 AI 时，容易陷入一个误区，认为 AI 是万能的，自然语言将彻底颠覆并取代旧有的交互模式。这种想法，我认为是危险且不切实际的。

任何脱离场景和用户价值的技术选型，都无异于空中楼阁。在低代码这个具体的领域里，可视化操作与自然语言驱动，并非“有你没我”的对立关系，而是一对优势互补、相辅相成的“黄金搭档”。

我们先来分析一下这两种模式各自的优劣。

### **可视化操作的“所见即所得”**

可视化操作，也就是我们熟悉的拖拽、点选、在属性面板里配置参数，是低代码平台的立身之本。

- **优点：****它的核心优势在于****直观**和**确定性**。用户可以直接在画布上操作 UI 元素，实时看到结果，真正做到“所见即所得”。对于调整组件布局、修改颜色、字体大小等视觉样式相关的任务，可视化操作的效率是无与伦比的。你很难用语言精确描述“把这个按钮向右移动 13 个像素，再调成饱和度低一点的蓝色”，但用鼠标拖拽和在取色器上点一下，却是几秒钟的事情。
- **缺点：****可视化操作的“阿喀琉斯之踵”在于****复杂性**。当平台功能越来越强大，组件的配置项越来越多时，属性面板就会变得异常臃肿，我们常常称之为“配置地狱”。用户为了实现一个简单的目标，可能需要在好几个不同的面板之间来回跳转，寻找那个深埋的配置开关。

更致命的是，可视化界面**难以描述和配置复杂的业务逻辑与交互行为**。比如，想象一下要如何通过点选来配置这样一个需求：“当用户点击‘提交’按钮后，首先校验‘手机号’输入框的内容是否符合格式，若不符合，则在输入框下方显示红色的错误提示‘请输入正确的手机号’；若符合，则进一步判断‘验证码’输入框是否为空，若为空，则禁用‘提交’按钮并开启一个 3 秒的倒计时，倒计时结束后再恢复按钮可用状态……”

这种带有条件、分支、状态变更的强逻辑流，用可视化界面来表达，其复杂程度可想而知，对用户的心智负担也极大。

### **自然语言驱动的“意随心动”**

现在，我们来看看新伙伴——自然语言驱动。

- **优点：****它的魅力在于****低门槛**和**对复杂意图的高效表达**。用户不需要学习复杂的界面，只需要像和人对话一样，说出自己的想法。它天然地绕开了“配置地狱”，你可以一句话完成跨越多个配置面板的操作，比如“创建一个带有‘确认’和‘取消’两个按钮的模态框，标题是‘警告’，点击‘取消’时关闭模态框”。更重要的是，它非常**善于描述我们前面提到的那种复杂的业务逻辑**。前面那个令人头疼的交互需求，用自然语言描述出来，是不是就清晰直观多了？
- **缺点：****自然语言也并非完美。它的主要问题在于****模糊性**和**非精确性**。AI 对语言的理解可能存在偏差，导致执行结果不符合预期。此外，对于需要精确视觉反馈的微调任务，比如我们前面说的移动 13 个像素，用自然语言反而显得笨拙和低效。

### **为何要“相辅相成”**

通过上面的分析，结论已经呼之欲出：我们不应该强迫用户在两者之间做“单选题”，而应该提供一个“组合拳”，让用户在不同场景下选择最高效的工具。

一个理想的智能化低代码平台，应该是这样的工作流：

**用自然语言完成“从** **0** **到** **1”的快速搭建和复杂逻辑定义。**用户可以说：“帮我创建一个用户注册表单，需要有用户名、邮箱、密码和确认密码四个输入框，都要有非空校验，密码和确认密码的值必须一致，最后再来一个‘注册’按钮。” AI 助手听令，唰唰几秒钟，一个带有基础布局和校验逻辑的表单就出现在画布上了。**用可视化完成“从** **1** **到** **1.1”的精细化调整和最终确认。**表单生成后，用户发现输入框之间的间距有点大，按钮的颜色和整体风格不搭。这时，他可以无缝切换到可视化模式，用鼠标轻松地拖拽调整间距，在属性面板里换一个更和谐的按钮颜色。

看，在这个流程里，两种模式各司其职，将各自的长处发挥到极致，同时又完美规避了自身的短板。这才是我们追求的、真正能有效降低使用门槛、提升开发效率的下一代低代码开发体验。

明确了这个顶层设计后，我们接下来要做的所有技术实现，都将围绕这个核心目标来展开。

## 从“理解”到“行动”的最后一公里

好了，让我们回到技术层面。

第 28 讲的成果是，我们的 Python 后端在接收到用户输入后，可以通过 DSPy 得到一个结构化的数据，通常是一个包含 `Intent` 和 `Entities` 的字典。例如，用户输入：“帮我创建一个蓝色的登录按钮”。

DSPy 处理后，我们得到：

```
{
  "intent": "createComponent",
  "entities": {
    "componentType": "Button",
    "text": "登录",
    "color": "blue"
  }
}
```

这是一个非常好的起点，但它还只是 AI 大脑里的一个“想法”。我们的前端，或者说浏览器，完全不认识 `createComponent` 是什么，也不知道 `componentType` 代表什么。它只认识 HTML、CSS 和 JavaScript，在我们的场景下，它只认识前端组件和传递给组件的 props。

所以，我们必须建立一座桥梁，一个翻译层。这个翻译层需要做一件事：**将这个抽象的、平台无关的“意图”数据，翻译成一个具体的、前端可以理解并执行的“行动”指令。**这就是我们从“理解”到“Action”的最后一公里。

## 制定契约：定义 AI 可理解的“动作”与“页面蓝图”

要建立翻译层，首先得有“法律”和“通用语”。我们需要和 AI 约定好两样东西：它能做的“动作”有哪些，以及我们描述页面的“语言”是什么。这个约定，就是前后端、乃至 AI 都需要共同遵守的“契约”。

**定义页面状态（Page Schema）：我们的“页面蓝图”**

首先，任何一个低代码画布上呈现的页面，无论多复杂，其本质都可以用一个结构化的数据对象来描述。这个数据对象就是页面的唯一真实来源。我们将它称为“页面蓝图”或“页面描述规范”（Page Schema）。最常见的选择就是 JSON 格式。

一个极简的页面蓝图可能长这样：

```
{
  "pageId": "page_001",
  "title": "首页",
  "components": [
    {
      "id": "comp_001",
      "type": "Heading",
      "props": {
        "level": 1,
        "text": "欢迎来到我的应用"
      }
    },
    {
      "id": "comp_002",
      "type": "Button",
      "props": {
        "text": "点我",
        "color": "primary"
      }
    }
  ]
}
```

这份 JSON 清晰地描述了页面上有什么组件（一个标题、一个按钮），以及每个组件的属性是什么。前端的任务就是读取这份 JSON，然后把它渲染成真实的 UI。反过来，AI 助手的核心任务，就是通过它的“行动”来修改这份 JSON。

**定义动作（Intents）：AI** **的“能力清单”**

接下来，我们要定义 AI 能执行哪些“动作”。这些动作必须是有限的、明确的，并且能覆盖低代码编辑器的核心操作。这些动作直接与我们上一讲定义的 `Intent` 相对应。

我们可以定义这样一组基础动作：

- `createComponent`：创建一个新组件。需要 `componentType` 等实体作为参数。
- `updateProperty`：更新一个已存在组件的属性。需要 `componentId` 和要更新的 `prop` 键值对作为参数。
- `deleteComponent`：删除一个组件。需要 `componentId` 作为参数。
- `moveComponent`：移动一个组件的位置。需要 `componentId` 和目标位置信息作为参数。
- `bindData`：将组件的某个属性与数据源绑定。
- `setInteraction`：为组件设置交互逻辑。

有了这份“能力清单”，AI 的任务就变得非常清晰：根据用户的自然语言，匹配到清单上的一个动作，并从语言中提取执行该动作所需的全部参数。

## 后端实现：将“意图”翻译为精确的“UI 变更指令”

契约制定好了，现在轮到后端工程师大展身手了。我们的 Python 后端需要扮演“翻译官”和“指令官”的角色。

**Action** **处理器**

当 DSPy 返回意图和实体后，我们的后端服务不能直接把它丢给前端，而是要先进行处理。一个优雅的实现方式是创建一个 Action 处理器分发器。

```
# 伪代码
def handle_action(intent_data):
    intent = intent_data.get("intent")
    entities = intent_data.get("entities")
    if intent == "createComponent":
        return handle_create_component(entities)
    elif intent == "updateProperty":
        return handle_update_property(entities)
    # ... 其他动作的处理器
    else:
        return {"error": "Unknown intent"}
# 具体的处理器
def handle_create_component(entities):
    # ... 核心逻辑在这里
    pass
```

**生成** **UI** **变更指令：为何选择** **JSON Patch** **？**

处理器内部的核心逻辑是什么？是生成一个新的组件对象，然后把**整个页面**的 JSON “蓝图”都发给前端吗？可以，但这样太粗暴了，效率也低。

想象一下，一个页面上已经有 100 个组件，用户只是想改其中一个按钮的文字。如果我们把包含所有 100 个组件的完整 JSON 都发回去，网络开销会非常大，前端处理起来也可能更慢。

我们需要一种更精确、更轻量的方式，只描述“发生了什么变化”。幸运的是，已经有了一个非常成熟的、专门为此设计的标准：**JSON Patch (RFC 6902)**。

JSON Patch 通过一个操作对象数组来描述对一个 JSON 文档的修改。每个操作对象都包含 `op`（操作类型，如 add, remove, replace）、`path`（要修改的位置）和 `value`（新的值）。

让我们以前面的例子来走一遍完整的流程：

用户输入：“添加一个蓝色的登录按钮”DSPy 输出：

```
{
    'intent': 'createComponent',
    'entities': {
        'componentType': 'Button',
        'text': '登录', 'color': 'blue'
    }
}
```

后端 `handle_action` 调用 `handle_create_component` 处理器`handle_create_component` 内部逻辑：

- 生成一个唯一的组件 ID，例如 `comp_xyz789`
- 根据实体构建新的组件 JSON 对象：

```
{
  "id": "comp_xyz789",
  "type": "Button",
  "props": {
    "text": "登录",
    "color": "blue"
  }
}
```

- 生成对应的 JSON Patch 指令。我们想把这个新组件添加到 `components` 数组的末尾。

处理器最终返回给前端的，不是整个页面，而是这个轻量级的 JSON Patch 指令：

```
[
  { 
    "op": "add", 
    "path": "/components/-", 
    "value": {
      "id": "comp_xyz789",
      "type": "Button",
      "props": {
        "text": "登录",
        "color": "blue"
      }
    }
  }
]
```

提示：这里的 `path` 里的 `-` 是一个小技巧，表示在数组的末尾添加一个元素。

这种方式优雅、高效且标准。前端拿到这个 Patch，就知道该做什么了，而不需要关心这个指令是怎么生成的。

## 前端实现：让画布响应“指令”，实时“活”起来

现在，皮球传到了前端这边。我们的前端应用需要能接收并执行这个 JSON Patch 指令。

**改造** **Chatbot API** **调用：**之前，我们的 Chatbot 向后端发送请求，可能只是期望返回一段文字。现在，它需要能处理后端返回的 JSON 数据，也就是我们精心设计的 JSON Patch。

页面状态管理：我们的前端应用需要有一个地方存储整个页面的“蓝图”JSON。最简单的方式就是使用 `useState` Hook。

```
const [pageSchema, setPageSchema] = useState(initialSchema);
```

应用 Patch，更新状态：当 API 调用成功返回 JSON Patch 后，我们需要一个工具来将这个 Patch 应用到当前的 `pageSchema` 上。我们可以自己写一个简单的函数，但更推荐使用成熟的库，比如 `fast-json-patch`。

```
import { applyPatch } from 'fast-json-patch';
// 在API成功回调中
const handleApiResponse = (patch) => {
  // 基于当前状态计算出新状态
  const newSchema = applyPatch(pageSchema, patch).newDocument;
  // 更新state
  setPageSchema(newSchema);
};
```

**响应式渲染：**一旦我们调用 `setPageSchema` 更新了 state，前端会自动检测到变化，并以最高效的方式重新渲染 UI。画布上的组件会“神奇地”根据我们的指令出现、消失或改变样式。用户看到的，就是一个“活”的、能听懂人话的画布。

## 将整个流程串起来

让我们在脑海中完整地过一遍这个流程。

**用户**（在 Chatbot 里输入）：“帮我把那个叫‘点我’的按钮的文字改成‘提交’”**前端**：将文字发送到后端 API `/chat`**后端**（Python/DSPy）：

- DSPy 分析得出：

```
{
    'intent': 'updateProperty',
    'entities': {
        'componentId': 'comp_002',
        'propertyName': 'text',
        'propertyValue': '提交'
    }
}
```

- `handle_update_property` 处理器被调用
- 处理器生成 JSON Patch (假设按钮在数组第 2 个位置)：

```
[{
    "op": "replace",
    "path": "/components/1/props/text",
    "value": "提交"
}]
```

- 后端将此 JSON Patch 作为响应返回

**前端：**

- API 调用成功，收到 JSON Patch
- 调用 `applyPatch`，将 Patch 应用到 `pageSchema` state 上
- `setPageSchema` 触发前端页面重新渲染

**用户**（在屏幕上看到）：那个按钮的文字瞬间从“点我”变成了“提交”

一次自然语言驱动 UI 变更就这样完成了！

## 小结

今天这一讲，我们完成了从“理想到现实”的关键一跃。我们没有局限于单纯的技术实现，而是首先从产品理念层面，确立了**自然语言与可视化协同互补**的核心战略。这为我们后续所有的工作指明了方向。

在技术上，我们设计了一套完整的、从理解到行动的端到端链路：

**制定契约：**通过定义“页面蓝图”（Page Schema）和“AI 能力清单”（Actions/Intents），我们建立了 AI 和编辑器沟通的通用语言。**后端翻译：**我们的 Python 后端成为了翻译官，利用 **JSON Patch** 这一利器，将 DSPy 输出的抽象意图，高效、精确地翻译为 UI 变更指令。**前端执行：**我们的前端页面成为了执行者，通过监听并应用 JSON Patch 来更新状态，利用框架的响应式能力，将 UI 变更实时地呈现在用户面前。

至此，我们的低代码助手终于不再只是一个能聊天的玩具，它已经具备了初步的、改变世界（至少是改变我们的画布世界）的能力。当然，现在的它还很简单，但麻雀虽小，五脏俱全。我们已经搭建好了最核心的骨架，后续要做的，就是在这个骨架上不断添砖加瓦，让它变得更强大、更智能。
