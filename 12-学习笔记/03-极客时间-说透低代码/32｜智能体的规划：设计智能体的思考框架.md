# 32｜智能体的规划：设计智能体的思考框架

你好，我是陈旭。

在上一讲中，我们共同完成了一次激动人心的跨越。我们的 AI 助手不再是一个“闭着眼睛开车”的盲人司机，我们为它成功安装了一双“眼睛”，一个强大的观察工具集。现在，它能够感知画布的现状，能够在行动前进行事实核查，甚至能回答你关于“页面上有什么”这类问题。这无疑是它从一个 Copilot（助手）向 Agent（智能体）进化过程中，里程碑式的一步。

我们的 AI 助手现在耳聪目明，既能听懂指令，也能观察环境。但是，它依然只是一个“一步棋选手”。你让它把按钮变红，它能精准完成；你问它页眉里有什么，它能清晰回答。它的所有行动，都还停留在“战术执行”的层面，一次交互，完成一个动作。

然而，现实世界的需求远比这复杂。

试想一下，当你不再满足于修修补补，而是想让它帮你完成一个更端到端的任务时，会发生什么？比如，你对它说：“嘿，帮我创建一个完整的用户登录页面，需要有标题、用户名和密码输入框，还要有一个登录按钮。”

面对这样一个指令，我们现有的 Agent 会瞬间“宕机”。因为它所掌握的，无论是 `createComponent` 还是 `find_components`，都是单一原子的能力。它缺乏将一个大目标，分解为一连串有序战术动作的“战略规划”能力。它就像一个虽然装备精良，但却不知道如何排兵布阵的士兵，无法应对一场真正的战役。

这，就是我们这一讲要攻克的山头。我们要让我们的 Agent，从一个“战术执行者”，彻底进化为一个“战略规划师”。

不过，今天我们不着急写代码。在建造一座宏伟的大厦之前，我们首先需要一份逻辑严密、细节完备的设计蓝图。所以，今天，让我们都化身为“智能体设计师”，一起专注于“纸上谈兵”，完整地、系统地设计出指导我们 Agent 进行任务规划的“思考框架”。这，将是它未来智慧的源泉。

## 顶层设计：引入“指令 / 目标”分流器（Router）

在我们一头扎进如何“规划”的细节之前，我们得先解决一个更前置的问题：我们的 Agent，在什么时候才需要启动它那套复杂的“规划”能力呢？

显然，不是所有的用户请求，都需要杀鸡用牛刀。

我们需要明确地区分两种性质截然不同的用户输入：“简单指令”（Simple Instruction）和“复杂目标”（Complex Goal）。

“简单指令”，就像我们上一讲处理的那些，通常指向一个单一、明确的动作。比如“把那个按钮的颜色改成红色”、“删除页脚的 Logo 图片”。这些指令，用我们上一讲构建的“观察 - 响应”循环，就已经能处理得非常好了，完全没必要启动一个多步骤的规划器。

而“复杂目标”，则指向一个需要通过多个步骤组合才能达成的最终状态。就像我们前面举的例子，“构建一个登录表单”，或者“设计一个包含顶部导航、侧边栏和内容区的页面布局”。这些目标，才是我们规划器需要大显身身手的地方。

因此，在我们的系统架构中，必须在所有请求的入口处，设置一个“交通警察”，我称之为“指令 / 目标分流器”（Router）。它将成为用户流量的第一站，它的核心职责只有一个：判断用户的输入，究竟是一个“简单指令”，还是一个“复杂目标”，然后决定请求的走向。

这个分流器的逻辑该如何设计呢？其实非常简单，我们完全可以再次利用大语言模型（LLM）的能力。当接收到用户的请求后，我们并不直接去思考如何执行，而是先在内部，向 LLM 提出一个“元问题”（Meta-Question）：

> “请判断以下用户请求：‘[用户的原始指令]’。这个请求更像是一个可以通过单一步骤完成的‘简单指令’，还是一个需要多个步骤才能完成的‘复杂目标’？请只回答 ‘single’ 或 ‘multi’。”

根据 LLM 返回的 single 或 multi，我们的系统就可以清晰地将流量导向两个不同的处理管道：

- 如果是 `single`：那就进入我们第 31 讲已经实现的、轻量级的“观察 - 执行”流程。
- 如果是 `multi`：那么，就将这个请求，正式移交给我们将要设计的、强大的“任务规划器”（Planner）。

通过这样一个轻巧的分流设计，我们确保了系统的效率，也让我们的规划器能够专注于它真正应该解决的那些复杂问题。

## 核心：解构规划器的“灵魂”——元提示的五大要素

好了，现在假设我们的“分流器”已经识别出了一个“复杂目标”，并将其交给了“规划器”。规划器的核心，就是要与 LLM 进行一次高质量的对话，让 LLM 为我们生成一份完美的行动计划。

而我们与 LLM 沟通的唯一媒介，就是“提示”（Prompt）。这份用于指导 LLM 进行规划的提示，我称之为“终极元提示”（The Ultimate Meta-Prompt）。它的设计质量，将直接决定我们 Agent 的“智商”上限。

这份元提示，必须像一份给人类专家的、逻辑严谨的“项目需求文档”，它需要包含五个至关重要的核心要素。

### **要素一：角色扮演（Role-Playing）**

这看似是一个小技巧，但实际上至关重要。在与 LLM 沟通的开始，我们必须明确地为它设定一个专家身份。这就像是给演员一个剧本，能够极大地帮助它进入状态，并以更专业、更结构化的方式进行思考。

我们可以这样对它说：

> “你是一位资深的低代码应用架构师。你的任务是分析用户的需求，并将其分解为一系列清晰、有序、可执行的步骤。”

通过这样的角色设定，我们把 LLM 从一个泛泛而谈的聊天机器人，瞬间“提拔”成了我们 Awade 低代码领域的专业顾问。

### **要素二：最终目标（The Goal）**

这一点非常直白，但也绝对不能遗漏。我们必须清晰地、无歧义地将用户的原始需求，告知这位“架构师”。

例如：

> The Goal: “创建一个包含用户名、密码输入框和登录按钮的表单。”

### **要素三：环境感知（Environmental Awareness）**

这是我们上一讲成果的直接应用，也是体现 Agent 智能的关键。在要求 LLM 做规划之前，我们必须让它“看清楚”当前的战场环境。

但是，我们能直接把整个页面的 JSON“蓝图”丢给它吗？绝对不能！

对于 LLM 来说，一个充满了层层嵌套、各种属性、括号和引号的原始 JSON 对象，是极其不友好的“噪音”。阅读它，会消耗掉 LLM 大量的计算资源（Token），而且很难让它抓住重点。这就像是让一位建筑师通过阅读一整本建筑材料采购清单，来理解一栋大楼的设计，完全是缘木求鱼。

所以，我们必须提供一份对 LLM 友好的“状态摘要”（State Summary）。这份摘要，应该用更自然、更结构化的语言，来描述页面的核心结构。经过多次实践，我发现，使用 Markdown 的列表格式，是效果最好、也最清晰的选择。

让我们来看一个对比，你就明白了。

**原始** **JSON（对** **LLM** **不友好）：**

```
{
  "id": "root",
  "type": "Page",
  "children": [
    {
      "id": "header_123",
      "type": "Header",
      "props": {
        "style": {
          "backgroundColor": "#FFF"
        }
      },
      "children": [
        {
          "id": "logo_456",
          "type": "Image",
          "props": {
            "src": "/logo.png"
          }
        }
      ]
    }
  ]
}
```

**状态摘要（对** **LLM** **友好）：**

```
- Page (id: root)
  - Header (id: header_123)
    - Image (id: logo_456)
```

你看，这份 Markdown 格式的摘要，是不是瞬间就清晰了？它剔除了所有不必要的细节（比如样式属性），只保留了最重要的组件类型、ID 和层级关系。这，才是我们的“架构师”LLM 真正需要看到的、干净清爽的“设计草图”。

### **要素四：可用工具（Available Tools）**

我们的“架构师”LLM 空有智慧，但手上没有工具也不行。我们必须向它清晰地“亮出家底”，告诉它到底能使用哪些工具来对我们的 Awade 平台进行操作。

这份工具清单，也需要有严格的格式，通常包含工具名称、功能描述和参数说明。

```
- `find_components(filters: array)`: 根据一个或多个属性条件，查找页面上所有符合条件的组件列表。
- `createComponent(parentId: string, componentType: string, properties: object)`: 在指定的父容器内，创建一个新的组件。
- `updateProperty(componentId:string, propertyName: string, propertyValue: any)`: 更新一个指定组件的某个属性。
- `deleteComponent(componentId: string)`: 删除一个指定的组件。
```

这份清单，就是 Agent 的“能力说明书”。LLM 会像一个工匠选择工具一样，从这份清单中挑选最合适的工具来完成每一步规划。

### **要素五：输出契约与行动纲领（Output Contract & Principles）**

最后，也是最关键的一环，我们必须和 LLM“约法三章”。我们得用非常严格的规则，来约束它的输出格式和思考方式。

首先是“输出契约”。我们不能让 LLM 随意地用自然语言给我们写一份计划，那无法被程序解析。我们要求它必须，且只能，输出一个特定结构的 JSON 对象。

这份 JSON Plan 的结构可以设计成这样：

```
{
  "plan": [
    {
      "step": 0,
      "reasoning": "这里是LLM对这一步的思考过程...",
      "tool_name": "createComponent",
      "parameters": { ... }
    },
    {
      "step": 1,
      "reasoning": "...",
      "tool_name": "updateProperty",
      "parameters": { ... }
    }
  ]
}
```

然后是“行动纲领”。这是一系列指导 LLM 如何思考的原则，是我们为它注入“灵魂”的地方。这些原则可能包括：

- **ReAct** **原则**：思考（Reason）和行动（Act）相结合。在决定使用某个工具前，先用 `reasoning` 字段写下你的思考过程。
- **观察优先原则**：在执行任何“修改”类工具（如 `createComponent`、`updateProperty`）之前，必须先使用“观察”类工具（如 `find_components`）来核实当前状态，确保操作的有效性。
- **经济原则**：尽量用最少的步骤完成目标。

通过这五大要素的组合，我们的“终极元提示”就构建起了一个完整、严谨的沟通框架，确保 LLM 能够像一个真正的专家那样，为我们提供高质量的行动计划。

## 升级：让计划支持“上下文”——设计步骤间引用语法

我们的设计已经非常接近完美了，但还差最后一块关键的拼图。

让我们再回到那个“创建登录表单”的例子。一个合乎逻辑的计划，应该是：

第一步：创建一个 Form 组件。第二步：在刚刚创建的那个 Form 组件内部，创建一个 Input 组件。

问题来了：在 LLM 生成整个计划的那一刻，第一步创建的 Form 组件还不存在于这个世界上，它自然也就没有 ID。那么，在第二步的 createComponent 调用中，parentId 这个参数该如何填写呢？

这就是步骤之间的“依赖”或“上下文”问题。如果不能解决这个问题，我们的计划就只是一系列独立的、无法协作的动作，无法形成真正的流程。

为了解决它，我们需要设计一套“步骤间引用语法”。这套语法允许计划中的后续步骤，引用前面步骤的执行结果。

经过反复推敲，我为你设计了这样一套简洁而强大的语法：`$steps.N.result.path`

让我们来拆解一下它的含义：

- `$`：这是一个特殊的标记，告诉我们的执行引擎，这部分内容不是一个普通的字符串，而是一个需要解析的引用。
- `steps`：代表整个计划的步骤数组。
- `N`：代表你想要引用的步骤的索引（从 0 开始）。
- `result`：代表第 N 步成功执行后，工具返回的结果对象。
- `path`：你想从结果对象中提取的具体值的路径（使用点表示法）。

现在，让我们用这个新语法，来解决刚才的问题。假设 `createComponent` 工具成功后，会返回一个包含新组件信息的 JSON 对象，如 `{"id": "form_1a2b3c", "type": "Form", ...}`。

那么，我们的计划就可以这样写：

**Step 0:**

- `tool_name`：`createComponent`
- `parameters`：`{ "parentId": "root", "componentType": "Form" }`

**Step 1:**

- `tool_name`：`createComponent`
- `parameters`：`{ "parentId": "$steps.0.result.id", "componentType": "Input" }`

看到这个 `$steps.0.result.id` 了吗？它就像一个神奇的“占位符”。我们的执行引擎在运行到第二步时，看到这个占位符，就会自动去获取第一步（索引为 0）的执行结果，并从中取出 `id` 字段的值，填充到这里。

问题迎刃而解！通过这套引用语法，我们的计划真正地拥有了“上下文”，步骤之间可以传递信息，形成了一个有机的整体。当然，这条规则，也必须被明确地写入我们元提示的“行动纲领”中，让 LLM 学会如何使用它。

## 蓝图演练：一次“干跑”（Dry Run）

设计图纸已经全部完成。在投入真金白银开始施工之前，任何一个严谨的架构师，都会在沙盘上进行一次模拟推演。我们也来做一次这样的“干跑”（Dry Run），不写一行代码，纯手动地模拟一次完整的规划过程，以此来检验我们设计的这套“思考框架”是否完备、自洽。

**任务目标**：创建一个包含标题（文本为“用户登录”）和提交按钮的表单。

**第一步：手动编写“状态摘要”**

假设我们的 Awade 画布当前是空的，只有一个根页面。那么，我们的状态摘要就是：

```
- Page (id: root)
```

**第二步：手动拼装“终极元提示”**

我们现在在脑海中，将所有要素拼装起来。这份发送给 LLM 的完整提示，将会包含：

**角色**：“你是一位资深的低代码应用架构师…”**目标**：“创建一个包含标题（文本为‘用户登录’）和提交按钮的表单。”**状态摘要**：就是上面那份 Markdown。**工具列表**：包含 `createComponent` 等工具的说明。**输出契约与行动纲领**：要求输出 JSON Plan，并遵守我们设计的各项原则，特别是要使用 `$steps.N.result.id` 语法来处理步骤依赖。

**第三步：人脑模拟** **LLM，手动编写最终的** **JSON Plan**

现在，最激动人心的时刻到了。我们戴上“LLM”的帽子，根据我们收到的这份详尽的“需求文档”，开始思考并编写计划。我们期望得到的、完美的输出，应该是这样的：

```
{
  "plan": [
    {
      "step": 0,
      "reasoning": "用户的目标是创建一个表单。首先，我需要创建一个Form组件作为所有登录元素的容器。它应该被放置在页面的根节点(root)下。",
      "tool_name": "createComponent",
      "parameters": {
        "parentId": "root",
        "componentType": "Form"
      }
    },
    {
      "step": 1,
      "reasoning": "接下来，根据需求，我需要在刚刚创建的表单内部添加一个标题。我会使用上一步(step 0)创建的表单的ID作为父容器ID，并设置其文本属性为'用户登录'。",
      "tool_name": "createComponent",
      "parameters": {
        "parentId": "$steps.0.result.id",
        "componentType": "Text",
        "properties": { "text": "用户登录" }
      }
    },
    {
      "step": 2,
      "reasoning": "最后，我需要在同一个表单中添加一个提交按钮。同样，我会使用步骤0的结果作为父容器ID。",
      "tool_name": "createComponent",
      "parameters": {
        "parentId": "$steps.0.result.id",
        "componentType": "Button",
        "properties": { "text": "提交" }
      }
    }
  ]
}
```

请仔细品味这份 JSON Plan。它逻辑清晰，步骤有序。`reasoning` 字段展示了“思考”的过程。更重要的是，它完美地使用了 `$steps.0.result.id` 来解决了步骤间的依赖问题。

这次“干跑”成功了！它雄辩地证明，我们设计的这套“思考框架”是完备、自洽且逻辑无误的。我们拥有了一份可以指导后续编码的、高质量的“设计蓝图”。

## 小结与展望

今天这一讲，我们没有编写一行核心的规划器代码，但我们可能完成了比写代码更重要的事情。我们作为“智能体设计师”，为我们 Agent 的“大脑”——任务规划器，绘制了一份完整而详尽的“设计图纸”。

我们确立了通过“分流器”来区分简单指令与复杂目标的顶层架构。我们系统地解构了指导 LLM 进行规划的“终极元提示”，明确了其必须包含的五大要素：角色扮演、最终目标、环境感知、可用工具，以及最重要的“输出契约与行动纲领”。最后，我们还创造性地设计了 `$steps` 引用语法，让我们的计划拥有了处理上下文依赖的能力。

设计图纸已经圆满完成，下一步，自然就是将它变为现实。在下一讲，我们将重新戴上“工程师”的帽子，用 Python 代码，将我们今天设计的这个强大的规划器模块，真正在我们的 Awade 项目中实现出来。我们将亲眼见证，我们的 Agent 是如何根据这份蓝图，自主地思考和规划，将复杂目标分解为智慧的行动序列。

## 思考题

我们今天设计的计划，是一个线性的、一步接一步的序列。但现实世界的任务，可能更复杂。

**错误处理**：如果计划中的某一步，比如 `step 1`，执行失败了，整个计划应该如何应对？是直接终止，还是尝试“自我修复”？我们该如何设计一套错误处理机制？**循环与条件**：如果用户的需求是“根据一个商品列表，为每个商品都创建一个卡片”，这显然需要一个“循环”结构。如果需求是“如果用户是管理员，则显示‘管理’按钮，否则不显示”，这就需要一个“条件”判断。我们又该如何扩展我们的 JSON Plan 结构，来支持循环和条件这两种更高级的编程逻辑呢？
