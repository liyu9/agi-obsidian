# 04｜演进策略：先发展通用能力还是先满足业务需求？

> **核心结论**：低代码平台演进分三个阶段（MVP → 成熟期 → 超越期），**成熟期必须坚持优先发展通用能力**。通用底座建成后，场景化完善是水到渠成。

---

## 一、三阶段演进模型

| 阶段 | 周期 | 目标 | 特征 |
|------|------|------|------|
| **MVP** | 3~6 个月 | 快速试错、快速闭环 | 备忘录留下待改进条目（欠债），性能问题单独关注（慢性毒药） |
| **成熟期** | 12~18 个月 | 发展通用能力 | 最艰难阶段：偿还 MVP 欠债 + 解决性能问题 + 面临"先通用还是先业务"抉择 |
| **超越期** | — | 场景化优化，全面超越 Pro Code | 具体化 + 自动化；通用底座上的场景化成本极低 |

### 性能与功能的关系

功能追加到一定程度 → 必须停下来专门处理性能 → **螺旋式上升关系**

---

## 二、两条发展路径对比

### 2.1 优先满足业务需求

短期见效快 → 但扩展性不足 → 业务场景变化时难以适应 → 针对新业务重新来一次 → 多次重复后出现"一堆工具无共同基因"

**后果**：
- 不同人/不同时间/不同方法（Shell、Native App、Web）做出的工具 → 无法整合
- 能力上限固定，**没有想象空间**
- 最终被通用性更强的平台替代

### 2.2 优先发展通用能力（**推荐**）

"通用能力" = 不与具体业务绑定的开发能力，适用于各种形式业务。

**通用性的边界 = 你对业务的想象空间 = 平台未来的能力上限**

**因果链**：
越通用 → 想象空间越大 → 能做的事情越多 → 潜力越大 → 能获得的资源和回报越大

**代价**：不能聚焦具体业务 → 特定业务表现可能不如 Pro Code → 容易成为毒瘤论的例证

---

## 三、成熟期的关键策略

### 3.1 核心原则

> 每面对一个新需求 → **灵魂拷问：如何在确保平台通用能力得到扩展的前提下顺便满足当前需求？**

### 3.2 四步方法

| 步骤 | 方法 |
|------|------|
| **① 最通用来考虑** | 即使对方只要一棵树，仍按一座森林来考虑，不见得实际交付森林，但要预留位置 |
| **② 抓共同特征** | 充分考虑已知场景的共同特征，暂时把个性化特征丢角落里。过多考虑个性化只会限制想象力 |
| **③ 复用优先** | 能用已有功能实现 → 决不新增；稍微扩展已有功能就能实现 → 也决不新增。资源集中投放到新的通用能力 |
| **④ 经营用户关系** | 放低姿态，倾听痛点，主动协助解决问题（编码/出方案）。用户友好度高 → 可以更多聚焦通用能力 |

### 3.3 关键决策因素（按顺序评估）

1. **可用资源**（根本）：资源充裕时基本可忽略其他因素；关注备用资源（技术骨干加班）
2. **用户友好程度**：友好度低 → 适当聚焦痛点，不一味追求通用；友好度高 → 更多聚焦通用能力
3. **老板/自身强势程度**：有人站台 → 更专注通用能力；需要学会讲故事（画饼），描绘想象空间

### 3.4 实战案例

**案例一：大场景需求**
- 需求：表单可视化开发 + Dashboard 可视化开发
- 深挖问题：表单之间如何串联？Dashboard 中的查询条件也是表单
- 解决方案：打造**不以任何具体场景为假设前提的通用场景编辑功能**

**案例二：图形需求**
- 需求：柱状图、折线图、饼图、仪表盘等 10+ 种图形可视化编辑
- 解决方案：先提供**支持任意图形的开发能力**（直接填写 echarts options），不提供可视化方式 → 短时间满足所有图形需求 → 资源投入其他功能

## 四、超越期：收获季

### 4.1 核心手段

**具体化 + 自动化**：场景越具体 → 配置内容越具体 → 越容易自动化 → 自动生成代码比例越高

### 4.2 场景化完善示例

| 通用期能力 | 超越期优化 |
|-----------|-----------|
| 通用场景下表单开发繁琐（需自己捕捉事件、编写校验逻辑） | 针对表单特性设计新配置流程，校验逻辑**全部自动化**，只需填写规则和提示文本 |
| 通用场景下 Dashboard 布局和交互麻烦 | 基于卡片的布局器，交互简化为单传参和获取数据，图表无需关注其他图表即可联动 |
| 通用图形实现门槛高（需学习 echarts 大量配置 API） | 针对常见图形设计可视化配置方式，屏蔽绝大部分配置细节，**会填表单就能开发复杂图形** |

### 4.3 为何一开始不这么做？

**资源！** 实现一个通用能力可同时解决许多业务需求 → 相同时间投入某个场景只能解决那一小部分需求

### 4.4 Low Code vs Pro Code 能力交叉

```
Low Code 能力超过 Pro Code 后 → 趋势不再回头
```

**原因**：Low Code 依托通用能力逐个纳入场景 → 每个场景凝聚专家经验 → 持续为各技能水平使用者赋能提效（Pro Code 做不到）

**Pro Code 的困境**：内秉性知识传递弊端 + 语言自身能力限制 → 能力上升极其缓慢 → 靠个人经验提升的边际收益越来越低

### 4.5 通用能力的二次价值

超越期后，通用场景**华丽转职为兜底策略的一部分**：
- 再完美的平台也总有能力边界 → 通用功能发挥兜底作用
- 让应用按期交付 + 给平台团队喘息时间
- 兜底策略给的底气：甚至可以无视某些"奇葩"需求

---

## 五、关键认知

1. **成熟期决定平台整体质量**：通用能力越扎实，超越期场景化越容易
2. **通用是长期投资**：类比中国先发展重工业后发展轻工业 → 重工业建设齐全后，轻工业发展就容易了
3. **场景化是收获**：通用底座上做场景化 → 即使做错也只是该场景推倒重来，不影响整体
4. **坚持 12~18 个月可熬过成熟期**：之后平台基本能实现任何业务需求（虽然实现方式未必酷炫），意味着平台已活下来
