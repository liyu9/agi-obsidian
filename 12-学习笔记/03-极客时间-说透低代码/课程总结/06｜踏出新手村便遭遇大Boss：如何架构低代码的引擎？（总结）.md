# 06｜踏出新手村便遭遇大Boss：如何架构低代码的引擎？

> **核心结论**：代码生成器与编辑器的关系是低代码架构中最重要的一环，根据抽象程度分为 4 个层级。层级选择直接决定平台的长期演进能力。编译器实现有直接法和间接法两条路径，需根据技术选型决定。

---

## 一、代码生成器的四个层级

### Level 1：没有代码生成器概念（玩具级）

| 特征 | 问题 |
|------|------|
| 无代码生成器，或仅由散落各处的三两个函数构成 | 无法区分编辑态和运行态 |
| 用 if else + 只读状态模拟运行态 | **一个 if 一个坑**：if = 对事物状态枚举，多数事物状态不可枚举 → 每少考虑一个状态就是一个 bug → flag 越加越多 → 代码改不动 |

**结论**：适合用作试验品/快速试错，确定要做工具级产品则**强烈建议推倒重来**

### Level 2：相对独立的代码生成模块（工具级）

**关键改进**：
- 将散落的代码生成函数挪到一起（至少同一个文件）
- 编辑态和运行态的公共部分抽取出来 → OOP 多态替代 if else
- 代码生成能力归入公共层

**此时必须引入 TypeScript 的理由**：
1. TypeScript 提供完整的 OOP 实现（基于 JS 原型链自行实现的 OOP 不完善）
2. 编辑器至少 **5~10 万行代码** → 无静态类型支持的开发效率仅为有类型支持的 **1/2~1/3**

**局限**：
- APP 只能在编辑器上运行，无法独立运行
- 平台与应用**耦合**（要么你包住应用，要么应用包住你）
- 扩展性和定制性很弱 → 只能在小范围内使用，无法规模推广

**重要提醒**：务必确认老板知晓平台与应用**可以解耦** → 因为耦合一旦开弓就没有回头箭 → 解耦状态下可以融合部署，反之走不通

### Level 3：编译器与编辑器对等独立（平台级）

**核心变化**：

```
Level 2:  编辑器 ←(紧耦合)→ 代码生成器（公共模块/库）

Level 3:  编辑器 ←(协议层)→ 编译器（同等地位的独立功能）
```

#### 协议层的作用

1. **对生成代码的各种功能 API 做抽象和约束**（一堆 interface）
2. **更深层目的：方便应用扩展和定制**
   - 默认实现 = 编译器的通用方式（与应用无耦合）
   - 应用需要定制时 → 编写自身实现 → 覆盖默认实现
   - 部分实现机制：应用只覆盖少数不适合的实现，复用大部分已有实现

**实际架构**：编译器提供默认实现 + 协议层部分实现 → 形成**应用定制 SDK** → 应用基于 SDK 做少量覆盖即可完成定制

**Level 3 的能力**：
- 架构清晰、层次分明
- 非常好的长期演进能力
- 良好的扩展性和定制能力
- 能优雅处理能力之外的需求
- 适合大规模推广

→ 此时可将代码生成器改称为**编译器**

### Level 4：插件系统与生态

在 Level 3 基础上：
- 对扩展/定制点做系统性设计
- 抽象出**编译生命周期**的各个时机
- 规范各时机的可扩展点
- 形成完备的插件开发能力 → **打造生态圈的基础**

### 作者实践参考

直接按 Level 3 目标编码 → MVP 阶段偷巧先将编译器当库实现 → MVP 完成后专门独立出来完成 Level 3 转型 → 目前处于 **Level 3.5**（拥有相对完善的插件系统）

## 二、编译器实现的两条路径

**编译器输入**：一组结构化数据（SVD），编译器唯一任务 = **将 SVD 转成代码**

### 2.1 直接法 vs 间接法

| | 直接法 | 间接法 |
|---|--------|--------|
| **过程** | SVD → 直接生成浏览器可识别的代码 | SVD → 生成 MVVM 框架代码 → 利用框架编译器进一步编译 |
| **架构复杂度** | 简单，无需协调另一个编译器 | 复杂，需额外协调 AVR 编译器 |
| **JiT 编译性能** | 间接法的约 **20%~30%**，几乎全程百毫秒以内 | 较差 |
| **实现工作量** | 少 | 多（需协调框架编译器，社区资料不覆盖"不正常"用法） |
| **先决条件** | **苛刻**（见下文） | 无特殊条件 |

### 2.2 只能选间接法的两个条件

**满足任一即必须选间接法**：

| 条件 | 说明 |
|------|------|
| **前端技术栈选型** | 机构使用 AVR（Angular/VUE/React）之一 → 到 Level 4 需要融入生态 → 必须选相同技术栈 → 只能间接法。除非机构强势到所有团队必须用你的平台 |
| **组件集实现技术** | 组件集用 AVR 之一实现 → 只能间接法。jQuery 实现的组件集可直接法（但大概率已被嫌弃并重写）。**例外**：Web Component 技术（如华为云低代码平台的实践）可屏蔽 AVR 差异 |

### 2.3 间接法的独特优势

**支持 Low Code 和 Pro Code 混合开发**（直接法做不到）

→ 可以相对妥善处理**存量代码**（低代码平台出现之前的页面代码）

### 2.4 技术栈选 Angular 的额外工作

需要额外协调 **TypeScript 编译器**，打通整个编译流水线。

## 三、关键认知

1. **代码生成器是"伪装成小怪的 Boss"**：看似简单的小功能，背后牵动长期演进的诸多考虑
2. **层级是目标而非过程**：实现时可根据实际情况灵活调整，但架构目标必须清晰
3. **协议层是 Level 3 的精髓**：它不仅是 API 约束，更是扩展/定制的渠道
4. **技术选型决定实现路径**：前端技术栈 + 组件集技术栈 → 决定直接法还是间接法
5. **间接法的核心价值**：混合开发能力 → 处理存量代码的桥梁
