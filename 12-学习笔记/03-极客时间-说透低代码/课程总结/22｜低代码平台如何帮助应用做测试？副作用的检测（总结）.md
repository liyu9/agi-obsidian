# 22｜低代码平台如何帮助应用做测试？副作用的检测

> **核心问题**：如何分析事件处理逻辑以追踪事件链，以及如何检测副作用以生成测试断言？
> - 上一讲遗留问题：如何分析事件处理逻辑（从事件链的上一级找到下一级）。

---

## 一、分析事件处理逻辑

低代码平台上事件处理有**两类方式**，需分别分析：

| 方式 | 分析方法 | 难度 |
|------|----------|------|
| 自定义代码块 | **AST 分析**（唯一可靠手段） | 高 |
| 一键绑定/自动更新等非代码方式 | 直接读取结构化配置 | 低，但定位属性难 |

### 1.1 AST（抽象语法树）分析代码块

**AST 定义**：表示程序代码语法结构的树形数据结构，每个节点代表一个语法结构，节点间通过父子关系相连。

**分析过程**：
1. 将代码块解析为 AST
2. 遍历 AST 树 → 找到 `CallExpression` 节点（调用 API 节点）
3. 读取子级节点 → 获得发送自定义事件的事件名
4. **只需寻找发送自定义事件的 API 节点** → 判断逻辑大幅简化

### 1.2 装饰器标记结构化配置

**问题**：低代码平台配置项过千，分布在深度 10~20 层的 JSON 树上 → 如何找到哪些属性存储了事件处理逻辑？

**方案：TypeScript 装饰器**

```typescript
export class ExecutiveData {
  @Interactive('eventEmitter', InteractiveConfig)
  config: InteractiveConfig;

  @Interactive('code-block')
  code: string;
}
```

**原理**：
- 装饰器给属性加上标记 → 信息记录在类的**原型链**上
- 遍历配置时从原型链读取标记 → 有标记 = 包含事件处理逻辑 + 知道结构类型
- **全程无 if else**，标记与属性紧挨 → 迭代时不易出错

## 二、副作用的检测

### 2.1 副作用的定义

**副作用 = 组件在功能触发前后的状态变化**

寻找副作用 = 寻找被测功能所波及到的**组件实例**。

### 2.2 副作用的产生途径

| 途径 | 示例 |
|------|------|
| 组件数据属性变化 | `table.data = new TableData(...)` |
| 调用组件 API | `table.refresh()` |
| 属性绑定的自定义事件触发 | `eventBus.emit('this.jigsawButton261.click')` |

### 2.3 检测方法

与分析事件处理逻辑的方法**基本相同**：
1. 用装饰器标记需要分析的属性（新装饰器，避免与 @Interactive 搞混）
2. 遍历配置 → 发现被装饰的属性 → 区分是代码块还是 JSON 对象
3. 代码块 → AST 分析获取组件 ID
4. JSON 对象 → 直接读取属性值获取组件 ID

## 三、断言的生成

### 3.1 断言的本质

断言 = 检查副作用是否符合预期 → 没有断言的测试用例**毫无意义**。

### 3.2 关键假设：组件不会出错

**推理链**：
- 低代码平台有专门特性团队为组件集质量负责 → 组件出错由他们修复
- → **只要喂给组件的数据是对的，组件渲染的界面肯定是对的**
- → 无需关注 DOM 细节，只需**校验组件当前数据**是否符合预期
- → **比对两个 JSON 对象**比比对两棵 DOM 树简单无数倍

### 3.3 比对策略

不采用严格相等，而是**包含关系**（`assertJsonEquality`）：

原因：预期数据需人工配置 → 开发人员倾向于只填核心数据（如表格只配一行关键数据）。
