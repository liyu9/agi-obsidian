# 35｜学会"反思"：实现Agent的错误处理与自我修正

> **核心主题**：为 Agent 注入"韧性"，构建"捕获 - 反思 - 重规划"闭环，使其在失败后能自我修正。

---

## 一、问题：脆弱的执行引擎

**失败场景**：用户说"把 ID 为 non-existent-btn 的按钮变红" → 规划器生成合理计划 → 执行引擎调用工具 → 组件不存在 → 抛异常 → **程序崩溃**。

**核心观念转变**：**失败是信息，不是终点** → 异常 = 包含丰富上下文的情报包 → 用于诊断和修正。

---

## 二、第一步：改造执行引擎——从崩溃到捕获

### 2.1 自定义异常体系

工具函数失败时抛出**描述性异常**而非返回 `None`/`False`：

| 异常类 | 触发场景 | 示例信息 |
|--------|---------|---------|
| `MCPToolError` | 所有工具错误的基类 | — |
| `ComponentNotFoundError` | 按 ID/条件找不到组件 | "未能在画布上找到ID为 'xxx' 的组件" |
| `InvalidParameterError` | 参数无效或缺失 | "调用工具 'xxx' 时缺少必要参数 'yyy'" |

**作用**：错误信息结构化、可识别 → 对后续"反思"至关重要。

### 2.2 改造 `execute_plan()` —— 加入 try-except 安全网

```
for 每个步骤:
    try:
        解析参数 → 调度工具 → 执行 → 保存结果
    except (ComponentNotFoundError, InvalidParameterError) as e:
        收集 failure_context → 调用 replan() → 用新计划继续执行
```

### 2.3 失败上下文 `failure_context` 的五个字段

| 字段 | 内容 | 作用 |
|------|------|------|
| `original_goal` | 用户原始目标 | Agent 需牢记最终方向 |
| `original_plan` | 完整原始计划 | 失败的"第一版草稿" |
| `succeeded_steps` | 已成功的步骤历史 | 它们可能已改变画布状态 |
| `failed_step_index` + `failed_step` | 失败步骤的详情 | 哪步、哪个工具、什么参数 |
| `error_message` | 人类可读的错误描述 | 从异常对象提取 |

## 三、第二步：重规划元提示（Re-Planning Meta-Prompt）

专门用于"修正模式"的元提示，比初始规划提示**更复杂**（包含更多动态上下文）。

### 结构拆解

| 部分 | 内容 | 设计要点 |
|------|------|---------|
| **① 角色扮演** | "经验丰富的调试专家" | 切换心智模式为"解决问题" |
| **② 事故报告** | 原始目标 + 原始计划 + 成功步骤 + 失败步骤 + 错误信息 | 结构化嵌入（标题 + JSON代码块），信息一目了然 |
| **③ 当前快照** | 重新获取的最新画布状态 | **最易被忽略但至关重要** → 失败前可能有步骤已成功 → 画布状态已变 → 必须基于最新状态决策 |
| **④ 新的任务指令** | 分析 + 规划 + 策略建议 | 甚至给出示例策略（如"组件未找到 → 先用 find_components 搜索"） |
| **⑤ 输出契约** | 严格 JSON 格式 | 确保程序可解析 |

### 关键：为什么需要"当前快照"

**因果链**：部分步骤已成功执行 → 画布状态已改变 → 若用过时状态做规划 → 决策错误 → **必须重新调用观察工具获取最新状态**。

---

## 四、第三步：重规划循环（Re-Planning Loop）

### 架构闭环

```
execute_plan()
  → try: 执行步骤
  → except: 收集 failure_context
    → replan(failure_context)
      → get_page_outline() 获取最新状态
      → 填充 REPLANNING_PROMPT_TEMPLATE
      → planner.generate_plan_from_prompt(prompt) → 新计划
    → 用新计划替换旧计划，重新执行
```

### `replan()` 方法核心流程

```
1. 获取最新画布状态（观察工具 + 状态摘要）
2. 将 failure_context 各字段填充到元提示模板
3. 调用规划器生成新计划
4. 返回新计划（或 None 表示重规划也失败）
```

### 新计划的使用策略

| 策略 | 说明 | 推荐度 |
|------|------|--------|
| **简单策略（推荐）** | 新计划完全替换旧计划，从头执行；加**重试次数上限**（如最多3次）防无限循环 | ✅ |
| 复杂策略 | 将新计划与旧计划中已成功的步骤合并 | ❌ 边界情况复杂 |

## 五、端到端演练：失败后恢复

### 场景："把 ID 为 non-existent-btn 的按钮变红"

**第一阶段：执行与失败**

| 环节 | 结果 |
|------|------|
| 规划 | 生成 `update_property` 计划 |
| 执行 | 工具抛出 `ComponentNotFoundError` |
| 捕获 | except 块触发，收集 failure_context |

**第二阶段：反思与重规划**

| 环节 | 结果 |
|------|------|
| LLM 分析 | "组件未找到 → 应先搜索所有按钮，再向用户确认" |
| 新计划 Step 0 | `find_components(filters=[{type: Button}])` |
| 新计划 Step 1 | `ask_user_for_clarification` → 向用户展示找到的按钮列表，请其选择 |

**第三阶段：恢复执行**

新计划被执行 → `find_components` 找到按钮 → 向用户发起智能交互。

**结果**：硬性错误 → 被转化为**与用户的智能交互**。
