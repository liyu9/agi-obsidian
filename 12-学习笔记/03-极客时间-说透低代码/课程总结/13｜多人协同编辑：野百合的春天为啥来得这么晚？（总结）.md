# 13｜多人协同编辑：野百合的春天为啥来得这么晚？

> **核心观点**：多人协同编辑是低代码平台成熟后的"甜蜜烦恼"——意味着平台已具备较强开发能力，但此时底层数据结构往往已固化，再引入最优解代价极大。**必须在平台建设之初就考虑多人协作**。

---

## 一、多人协作的三大难点

### 难点1：冲突解决

通信传输不是难点（WebSocket / WebRTC 均可，**推荐 WebSocket**——更成熟、服务端方案丰富、适合一对多广播）。

**真正难点是如何解决多人同时编辑同一组件/同一属性的冲突。**

→ **釜底抽薪方案：不让冲突出现** → 引入 CRDT 算法。

**CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）**：

- 核心原理：对所有操作打时间戳 → 网络分发历史记录 → 本地合并 → 冲突点用 **LWW（Last Writer Wins）** 策略处理
- LWW 策略：冲突发生时谁对谁错不重要 → 各方协商一致 → 各方稳妥拿到协商结果
- JavaScript 生态主流实现：**Yjs**、automerge、ref-crdts

| 实现 | 性能 | 备注 |
|------|------|------|
| **Yjs** | **极高**（效率曲线几乎贴横轴） | 推荐：性能优 + 内置 UndoManager |
| automerge | 较高 | 无 UndoManager |
| ref-crdts | 一般 | 无 UndoManager |

### 难点2：历史记录管理

多人同时编辑 → 历史记录交织 → 不能撤销别人的修改 → 自行设计极其复杂。

→ Yjs 提供 **UndoManager**，可正确记录各人历史、执行撤销/重做。

### 难点3：CRDT 可能用不了（最关键）

**CRDT 的根基是历史记录格式**，但低代码平台成型后：

1. **历史记录格式已固化** → 调整伤筋动骨
2. **应用数据归属已固定** → 用户数据按账号物理隔离 → 后期改逻辑隔离成本巨大

> **教训**：平台建设之初就要考虑多人协作，否则木已成舟，CRDT 再好也只能望洋兴叹。

---

## 二、CRDT 在低代码平台上的三个"水土不服"

虽然 CRDT 在多人协作文档中成熟，但在低代码平台上存在三个问题：

### 问题1：对话框导致"不及时记录"→ 冲突

低代码可视化开发中，复杂配置通过对话框承载 → 用户点"确定"后才一次性保存 → 期间修改未被及时记录 → CRDT 无法生效。

- **LWW 策略不友好**：对话框承载大量配置项，简单粗暴二选一会浪费他人工作；且不同属性本可直接合并，不应一律 LWW
- **解决方案**：使用**临时影子历史记录**及时保存所有修改 → 确定时合入主记录序列 → 取消则丢弃。影子记录保持及时记录特征 → LWW 覆盖范围小到可忍受

### 问题2：渲染性能

- 在线文档：修改同步后毫秒级生效
- 低代码：需要编译 + 渲染，复杂 App 需 **3~5 秒**一次反馈 → 多人同时编辑 → 无休止等待
- **解决方案**：引入**懒渲染**——只在需要时启动渲染，其他情况只记录并提示未渲染修改数量

### 问题3：多行属性值合并

- 在线文档插入位置：行+列两个整数
- 低代码插入位置：需要 **xpath（类似 DOM 树路径）**，属性值可能是简单值或多行文本（如代码段）
- 多行文本直接 LWW 覆盖 → 前一个人数十行改动被后一个人1个字符的修改覆盖
- **解决方案**：xpath + 行号，只有**同一 xpath 属性的同一行**编辑才用 LWW，其他直接合并（类似 git 合并代码）

## 三、补救方案（无法使用 CRDT 时）

作者实际采用的补救方案，适用于平台已定型的情况：

### 步骤1：解决数据归属问题

设计**分享动作**：将工程数据冗余到其他开发人员名下 → 各人各干各的、互不影响 → 完全复用原有流程。

### 步骤2：冗余数据归一

**约束**：冗余数据能且只能合并回原始版本 → 控制每次合并只在两份数据间进行 → 方向确定（始终合入原始所有者版本）。

### 步骤3：检测冲突

两份数据 = 3 个状态（分叉点 + 两个分支）：

1. 拿分支 A 与分叉点比较 → 修改集1（xpath + 行号 的二元组）
2. 拿分支 B 与分叉点比较 → 修改集2
3. 两组修改集取交集 → 每个相同修改点 = 一个冲突点

无冲突 → 直接合并（类似 git squash + rebase）。
有冲突 → **只能手工解决**（无 LWW 可用）：
- 单行属性值：二选一
- 多行属性值：类似 git 合并代码，推荐 Monaco 编辑器内置 diff 功能

### 步骤4：冲突缓解策略

- 后台实时检测冲突 → **第一个冲突出现时立即提醒**
- 对未合并修改计数 → 超阈值时非侵入性提示（侧边气泡）

### 关键注意：不能用通用 JSON 比对工具

低代码平台的"源码"是结构化数据 → 容器子级数组中的对象**顺序不一定敏感** → 通用 JSON 按数组顺序比对会得到大量错误修改集。

**正确做法**：根据组件 id 找到两份数据中的同一组件 → 按 schema 遍历所有属性 → 获取准确修改集。

## 四、关键教训

| 教训 | 说明 |
|------|------|
| **数据归属** | 不能让应用数据与开发人员账号形成物理隔离（一一对应），应集中存储 + 逻辑关联 |
| **持久化方式** | 不要偷懒发送全量数据，应采用增量保存（与 CRDT 实现一致） |
| **提前引入 CRDT** | 即使暂时不需要多人协作，也可先引入 Yjs → 获得成熟数据结构 + 历史记录管理 + 为未来演进留路 |

> **建议**：如果还有得选，优先引入 Yjs 作为底层数据保存和历史记录管理的基础。
