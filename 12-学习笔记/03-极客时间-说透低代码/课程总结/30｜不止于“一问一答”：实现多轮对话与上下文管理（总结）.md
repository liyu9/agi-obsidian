# 30｜不止于"一问一答"：实现多轮对话与上下文管理

> **核心内容**：通过**意图模板**和**对话状态**两个核心概念，在现有架构上优雅实现多轮对话。AI 助手从被动的"指令执行者"进化为主动的"沟通者"——信息不足时主动追问引导用户完成任务。

---

## 一、问题：一问一答的局限

**现状**：用户必须在单句话中提供动作所需的**全部信息** → 现实中人类表达往往不完整。

**示例**："帮我建个按钮" → 缺少 `text`（按钮文字）、`parentId`（放在哪）→ AI 困惑 → "抱歉，我没听懂"

**目标**：AI 应在信息不足时**主动追问、引导、澄清**，而非放弃。

---

## 二、为何不用 MCP

| | MCP（模型上下文协议） | 本讲方案 |
|---|---------------------|---------|
| 目标 | AI 与外部工具的**标准化通信**（USB-C 式通用接口） | 平台内部**具体任务的对话流程管理** |
| 复杂度 | 宏大，解决 AI 与第三方系统通信 | 轻量，聚焦内部多轮对话 |
| 适用性 | 解决的核心矛盾不同（非当前痛点） | 务实，贴合现有架构 |

---

## 三、两个核心概念

### 3.1 意图模板（Intent Schema）：AI 的"任务说明书"

为每个 Intent 定义一份模板，结构化列出执行所需全部参数，标明 required/optional，并为每个必选参数预设**追问话术**。

```json
{
  "intent": "createComponent",
  "params": {
    "componentType": {
      "required": true,
      "prompt": "好的，您想创建什么类型的组件呢？"
    },
    "parentId": {
      "required": true,
      "prompt": "请问您想把这个新组件添加到哪个容器里呢？"
    },
    "text": {
      "required": false,
      "prompt": "需不需要给它加上一些文字？"
    }
  }
}
```

**价值**：
- 一目了然告诉 AI：哪些参数绝对不能少，哪些可有可无
- 预设追问话术 → AI 知道如何向用户提问
- **易扩展**：新增功能只需定义/修改模板，无需改核心对话逻辑

### 3.2 对话状态（Conversation State）：AI 的"临时记事本"

用户开启多轮任务时，后端创建独立的对话状态对象，实时追踪进展。

```json
{
  "sessionId": "user_abc_123",
  "activeIntent": "createComponent",
  "collectedEntities": { "componentType": "Button" },
  "missingEntities": ["parentId"],
  "nextPrompt": "请问您想把这个新组件添加到哪个容器里呢？"
}
```

**字段说明**：
- `sessionId`：标识用户对话
- `activeIntent`：当前核心任务
- `collectedEntities`：已收集的信息
- `missingEntities`：还缺的**必须**信息
- `nextPrompt`：下一步应问什么

**生命周期**：用户提供新信息 → `collectedEntities` 增加 → `missingEntities` 减少 → 直到 `missingEntities` 为空 → 任务完成 → 删除状态释放资源。

生产环境建议使用 **Redis** 等外部缓存存储。

---

## 四、后端实现：四步处理流程

### 第一步：检查激活的对话状态

收到消息 → 先按 `sessionId` 检查是否存在**尚未完成的对话状态**（而非立即调 DSPy）。

### 第二步：存在对话状态 → 处理"追问的回答"

新消息被视为对上一问题的回答 → 调用 DSPy 做更**聚焦**的提取（"请从这句话中提取组件 ID"） → 提取准确率↑ → 更新对话状态。

### 第三步：不存在对话状态 → 开启新对话

正常调 DSPy 识别初始意图 → 加载对应意图模板 → 初始化全新对话状态 → 存入内存。

### 第四步：核心判断循环

```
检查所有必须实体是否已在 collectedEntities 中？
  ├─ 是 → 信息收集完毕 → 执行动作（生成 JSON Patch）→ 返回前端 → 删除对话状态
  └─ 否 → 从意图模板找到下一个缺失参数的 prompt → 作为文本消息返回前端
```

---

## 五、前端配合：几乎无需改造

前端只需处理**两种响应类型**：

| 响应类型 | 含义 | 前端行为 |
|---------|------|---------|
| **JSON Patch 对象数组** | 任务完成的"最终答案" | `applyPatch` 更新 `pageSchema`，UI 更新 |
| **普通文本字符串** | AI 的"追问" | 直接渲染到对话窗口，作为聊天消息 |

**职责分离**：后端负责复杂对话逻辑和状态管理，前端只负责响应判断和 UI 渲染 → 耦合度极低，互不干扰。

---

## 六、关键认知

1. **契约化**：意图模板将 AI 完成任务所需信息以结构化"契约"固定 → 清晰、可管理
2. **状态化**：对话状态为无状态 HTTP 请求赋予跨次交互的"记忆" → 一切复杂人机对话的基础
3. **职责分离**：后端复杂逻辑 + 前端简单渲染 → 系统清晰、健壮、易维护
4. **为 Agent 铺路**：多轮对话能力是未来挑战更复杂 Agent 功能（规划、推理）的基础
5. **不引入外部复杂框架**：仅通过两个核心概念在现有架构上优雅扩展
