# 12 | 业务数据：再好的App，没有数据也是白搭

> **核心内容**：App 开发三部曲（布局、交互、数据）的第三个环节——数据获取。从通用数据获取（参数配置、结构修正、数据模型）到个性化数据（插件机制），以及数据打桩（模拟与转发）。

---

## 一、HTTP 请求参数配置

### 1.1 三个传参位置

| 位置 | 注意事项 |
|------|---------|
| URL 传参 | 支持模板字符串语法 `${variable}`；需自动添加 `encodeURIComponent()` 编码；注意不要对已编码的值重复编码 |
| 请求头传参 | 参数值需注意编码 |
| 请求 body 传参 | HTTP 传输层自动编码，无需额外处理 |

### 1.2 URL 传参的常见陷阱

```
陷阱1：URL 输入框作为静态文本 → 无法传入变量
解决：支持模板字符串语法 → /some/data/url?p1=${v1}&p2=${v2}

陷阱2：变量值含敏感字符（如 &）或汉字 → URL 出错
解决：自动添加 encodeURIComponent() 编码

陷阱3：开发者已自行编码 → 重复编码出错
解决：检测已有编码调用，避免重复处理
```

## 二、数据结构修正

### 2.1 问题

通用型低代码平台对接的服务端无法预知 → 返回数据结构无法预知 → 前端组件对输入数据结构有预设要求。

### 2.2 常见输入数据结构

| 结构类型 | 数据形式 | 来源 |
|---------|---------|------|
| 二维表结构 | `[['v11','v12',...], ['v21','v22',...], ...]` | RMDB 直接读取 |
| 准二维表结构 | `[{f1:'v11', f2:'v12',...}, {f1:'v21',...}, ...]` | Node.js 等后端常见 |

### 2.3 处理策略

```
尽可能收集各种可能的输入结构 → 根据特定结构设定参数 → 自动生成转换代码
→ 减少开发者配置工作量和难度
```

**兜底方法**（预设类型之外的情况）：

```typescript
origin => {
    // 开发者编写处理逻辑
    const result = ...;
    return result;
}
```

可通过可视化编程编排转换逻辑，或直接给编辑器填写转换逻辑。

## 三、数据模型

### 3.1 概念

数据结构是对数据的**逻辑表达**，数据模型是对数据的**抽象化描述**。

### 3.2 维度-指标模型

来源于电信领域（运营商大数据），可推广到所有采用 RMDB 持久化的关系数据：

| 分类 | 说明 | 示例 |
|------|------|------|
| **维度** | 描述事物的各个实体 | 省市区（行政区）、手机厂商/型号 |
| **指标** | 数值型或可枚举值 | 温度、字数、确诊人数、考核等级 S/A/C |

> **时间**作为维度处理（虽看似数值型）。

### 3.3 数据模型的价值

```
配置数据模型 → 降低可视化配置界面的复杂度
→ 配置过程更具业务含义 → 提高配置效率 → 减少试错次数
```

### 3.4 中台加持

```
企业完成中台化改造 → 数据中台治理数据 → 给出结构统一的数据 + 数据模型 API
→ 低代码平台直接使用 → 省去数据结构修正和数据模型配置的麻烦
```

> 这是低代码与中台演进线路重合的一个实例。

## 四、数据打桩

### 4.1 问题

App 开发时数据未准备好或不在当前环境 → **没有数据可用** → 开发无法继续。

### 4.2 实现方式

| 方式 | 实现方法 | 适用阶段 |
|------|---------|---------|
| 模拟数据（假数据） | XHR 拦截器拦截请求，返回假数据；甚至不实际发出请求 | 开发早期 |
| 规则模拟 | 配置参数条件 → 不同参数值返回不同数据 | 需要更真实的模拟 |
| 代码模拟 | 开发者填写模拟代码，理论上可 **100%** 模拟服务端 | 复杂场景 |
| 请求重定向 | 将请求转发到真实服务端（后端开发人员电脑或私服实例） | 开发中后期 |

### 4.3 XHR 拦截器方案

| 框架 | 拦截方式 |
|------|---------|
| Vue / React | axios 的 `interceptors` |
| Angular | HttpClient 拦截功能 |
| jQuery | `ajaxSetup` 函数 |
| 无框架 | 对 `XMLHttpRequest.prototype.send` 打补丁 |

**Awade 的方案**：将桩代码生成到服务端 → 前端无需处理 → URL 重定向到桩代码 → 更真实。

### 4.4 请求重定向的跨域问题

```
通用型低代码平台 → 数据来源无法预知 → 不知道有哪些服务端
→ 无法配置 CORS 策略 → 跨域问题似乎无解
→ 作者找到了绕过跨域限制的方法（动态更新部分展开）
```

> 无视跨域约束地请求任何服务器数据，是通用型低代码平台的重要能力。

## 五、个性化数据（插件机制）

### 5.1 问题

通用数据获取方式适用于大多数场景，但个性化数据：通用性低、形式多、数量大 → **插件机制是最佳选择**。

### 5.2 插件架构

```
基础动作（抽象类）
├── 信息采集（抽象）→ 子类通过 MVVM 动态渲染器实现 UI
├── 信息保存（基类实现）→ 提供读写 API 给子类
└── 代码生成（抽象）→ 基类定义过程，子类实现具体逻辑
```

| 层次 | 职责 |
|------|------|
| 基础动作 | 两种动作（通用/个性化）的共同部分 |
| 通用获取数据动作 | 基础动作的默认实现，平台官方提供 |
| 个性化获取数据动作 | 新插件，由业务团队实现 |

### 5.3 编译器协议整合

```
基础动作代码 → 合并到编译器协议 SDK → 成为 SDK 的一部分
```

渲染器与基础动作的关系：TypeScript 为渲染器组件提供父类 → 减少子类开发难度和编码量。

### 5.4 插件的价值

```
通用方式获取同一笔数据 → 参数配置复杂，不易正确填写
个性化插件获取同一笔数据 → 定制化 UI，操作简洁直观
→ 插件自动生成通用方式的参数
```

### 5.5 插件的推广作用

```
平台推广初期 → 平台团队主动为业务团队开发常用数据获取插件
→ 解决与存量系统的对接问题 → 减少推广阻力
→ 插件起到"胶水"作用，将低代码平台与存量系统粘在一起
```

### 5.6 更复杂的场景

- **DAG（有向无环图）**：用于可视化数据编排
- **多数据源合并**：如趋势图同时展示历史数据 + 实时数据 → 大数据系统中两种数据分开处理 → 需要可视化数据编排分别读取后拼接

---

## 六、关键认知

1. **通用数据获取**必须处理好参数配置、数据结构修正、数据模型映射三个环节
2. **数据打桩**是 App 开发中不可或缺的能力，从模拟到重定向，覆盖开发全周期
3. **插件机制**是处理个性化数据的最佳方式——一个插件只专注一种个性化数据，实现难度低、效率高
4. **数据中台**可大幅简化低代码平台的数据工作（统一结构 + 模型 API）
5. 跨域问题在通用型低代码平台中有特殊解法（动态更新部分展开）
