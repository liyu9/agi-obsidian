# 15｜低代码平台应该优先覆盖应用研发生命周期中的哪些功能？

> **核心观点**：**开发能力决定低代码平台的能力上限，其他能力决定能力下限**。平台有一定成熟度后，需要从 App 开发生命命周期角度补充需求端、交付端、生产环境管理、资产管理等能力。

---

## 一、能力全景图

以开发能力为中心，四个维度展开：

| 维度 | 方向 | 包含能力 |
|------|------|---------|
| **需求端** | 左侧 | D2C、模板/业务组件 |
| **交付端** | 右侧 | 自动化测试、埋点与数据分析 |
| **生产环境管理** | 上方 | 自动部署、灰度发布 |
| **资产管理** | 下方 | 代码托管、版本管理 |

**优先级**：水平线（需求→开发→交付）优先发展 → 垂直线（管理）优先级较低（面向内部使用甚至可不发展，面向客户现场则必须）。

---

## 二、需求端

### 模板能力（优先级更高）

模板 = App 的半成品 / 常见有代表性的部分。

**三大价值**：

1. **快速"抄作业"** → 不从零开始 → 积累后分门别类 → 挑选接近的模板 → 演进为完整 App
2. **可视化脚手架** → 比纯编码脚手架更优秀（所见即所得）
3. **天然学习教材** → 依葫芦画瓢摸索学习 → 比看手册更有效（经验：大家不爱看手册，喜欢直接上手）

### D2C（Design to Code）

将 UX 设计稿转为可用代码。

**传统 D2C 的门槛**：自成一体 → 需要识别设计稿 + 生成对人类友好的代码 → 需要计算机视觉甚至 AI → 门槛高。

**低代码平台实现 D2C 的优势**：只需从设计稿识别出信息 → "喂"给低代码编译器 → 自动生成代码 → 无需高精尖技术。

**必须从设计稿获取的信息**：

| 信息类型 | 必要性 | 说明 |
|---------|--------|------|
| **组件类型** | **最关键** | 有类型即可根据 UX 设计规范推断大量预设数据 |
| 位置 + 尺寸 | 必须 | 决定生成 UI 是否可用，UX 规范给不了 |
| 文本/颜色/图标 | 可选 | 不影响成败，能识别越多 → 自动化率越高 |

---

## 三、交付端

### UI 自动化测试

**UI 自动化测试的现实困境**：

1. 用例代码调试成本高（特别是鼠标相关操作）
2. **维护成本更高**（页面 class 名/DOM 结构变更 → selector 失效 → 用例跑不过）
3. 需求紧张时测试用例代码第一个被砍

**低代码平台能做什么**：

低代码平台对 App 的 UI 结构和交互过程了如指掌 → 可以**自动生成测试用例** → 也可以**自动维护用例**。

**思路**：跟踪 UI 事件整理功能点 + 利用低代码对交互过程的了解 → 生成模拟人工操作的代码 → 自动生成自动化测试代码。

### 埋点与数据分析

App 上线后需采集使用情况、运行状况、异常信息 → 植入埋点 → 获取数据 → 提供分析功能。

低代码平台不需要重新发明方法 → **提供自动化程度更高的植入埋点能力 + 自动分析功能** → 帮助无经验的人获取所需数据。

---

## 四、生产环境管理

### 两种运行时模式

| 模式 | 说明 |
|------|------|
| 开发与运行合一 | "一键"推送 → 自动生成 URL 对外提供服务 |
| **开发与运行隔离** | 可分可合、按需处理（Awade 采用此方式） |

### 自动部署

**低代码平台应提供自动部署能力**：

- **容器化运行时**：自动生成应用镜像 → 内置蓝图、Dockerfile、配置信息 → 拿到即可部署
- **物理机环境**：打包依赖 → 生成脚本 → 解压后一个 `run.sh` 搞定

### 灰度发布

可视化灰度发布策略选择 + 可视化一键紧急版本回退。

**可支持的策略配置**：

| 配置类型 | 内容 |
|---------|------|
| 基本策略 | 用户规模、覆盖功能、回滚策略、新旧系统部署策略 |
| 用户画像 | 用户特征、年龄、数量、地理、终端、常用功能、友好度、净值度 |
| 分流规则 | 多以手工修改 nginx.conf 等配置文件为主 → 可视化集成后收益较高 |

埋点数据可与灰度策略配合 → 收集用户信息/运行时信息 → 作为灰度策略支撑数据。

---

## 五、资产管理

### 代码托管

Git 对非技术线用户太专业（MML 接口、冲突处理） → 低代码平台提供**可视化代码托管**，与 App 工程管理融合：

- 打开工程 → 自动 `git pull`
- 退出工程 → 自动 `git commit`
- 依托 GitLab（开源社区版免费）/ Gerrit（商业） → 自动发起代码走查 → 触发 DevOps 流水线 → 自动构建/测试 → 人工走查
- **大多数操作由 DevOps 流水线执行，低代码平台只需正确配置和触发**

### 版本管理

App 版本作为一种资产 → 低代码平台打通企业已有版本管理系统 → 一站式版本发布和更新。

---

## 六、总结：能力优先级

```
优先级高：需求端(D2C/模板) → 开发 → 交付端(自动化测试/埋点分析)
优先级低：生产环境管理(部署/灰度) → 资产管理(代码托管/版本)
```

- 面向内部使用：管理线能力可不发展
- 面向客户现场部署：管理线能力必须
