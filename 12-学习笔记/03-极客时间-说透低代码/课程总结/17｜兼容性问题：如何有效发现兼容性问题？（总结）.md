# 17｜兼容性问题：如何有效发现兼容性问题？

> **核心观点**：**兼容性是基础平台最难的技术问题**——其他问题是一时的，兼容性问题带时间维度、滚雪球递增，终将压垮团队。**能否妥善解决兼容性问题，决定了低代码平台是否能走得长远。**兼容性是劝退应用团队的重要因素之一。

---

## 一、代码走查（主动发现）

代码走查的核心要素 = **评审员**（没有之一）。

### 合格评审员的素质

- 深刻掌握被评审子系统的语言、工具、第三方库的长短处
- 深刻理解被评审子系统的全貌（架构→关键流程→各功能实现），**最好是原创作者，次好是长期维护者**
- **最好是专职**，临时参与则 Leader 需预留充分时间并计入业绩

### 关键原则：**避免自我走查**

- 代码作者修改时陷入细节（一叶障目，不见森林）→ 无法预见修改波及
- 资深人员：无意的考虑不足
- 资浅人员：限于对系统肤浅理解，根本无法预知不良影响
- 专业评审员：将修改放到系统全貌上下文来看 → 自然发现作者看不到的波及

---

## 二、DevOps 流水线（被动发现）

代码走查依赖人的经验 → 不可靠。DevOps 流水线用自动化脚本 → **在代码走查前先把大多数低级/已知的兼容性问题找出来**。

**持续改进闭环**：评审员发现兼容问题 → 思考是否可脚本化 → 脚本化后杜绝同类问题再次发生 → 点滴提升流水线可靠性。

### 可植入流水线的三种检测方法

#### 1. UT/FT

理论：每个函数/功能的输入输出修改前后一致 → 完全兼容。实操中覆盖率做不到 100% → **至少确保有覆盖的部分向后兼容**。

**成本控制策略**：
- 新模块初创时：评审员要求各功能点有一定比例测试用例
- 后续迭代：在某个函数踩坑 → 针对性补充用例 → 避免再次踩坑

#### 2. 代码扫描工具

弥补 UT/FT 覆盖率不足的空白 → 规则命中代码不一定有问题但概率大增 → 尽可能改掉报告中的潜在问题。

**注意**：工具往往收费、安装费事、扫描耗时耗 CPU、首次报告可能数以千计乃至上万条。

#### 3. 静态检查

lint 工具虽好但被其能力框住 + 全员学习成本 → **不推荐使用现成 lint 工具**。

兼容性问题的特点：**永远无法预知在哪儿、以哪种方式出现** → 检测脚本必须形式多样：

| 检查形式 | 适用场景 |
|---------|---------|
| 配置文件一致性检查 | — |
| 正则暴力检查源码 | 大多数场景 |
| AST 解析深度检查 | 正则搞不定时 |
| shell 脚本 | 能用 shell 就不用语言 |
| node.js 脚本 | shell 搞不定或太慢时 |

> **核心原则：尽量将已知的兼容性问题脚本化 → 避免在同一个坑里掉两次。** 协作意义：同一问题反复出现会让应用团队极不耐烦。

## 三、利用实际用户数据

**核心思路**：用实际 App 工程配置数据做测试 → 比 UT/FT/ST 中构造的数据更真实。

### 筛选高质量被测数据

构造数据太简单测不出问题 → 需从实际用户数据中筛选。

**两步筛选**：

1. **基础指标筛选**：编辑次数 > 300 次 AND 模块数量 ≥ 2（排除实验性工程）
2. **编译器校验**：只有通过低代码编译器编译的 App 工程数据才进入下一环节

### 两种检测方式

#### 方式A：编译器输出比对（适用于不修改生成代码的变更）

修改前编译器输出 vs 修改后编译器输出 → 有差异 → 可能有问题 → **专家评估**是否为破坏性变更。

#### 方式B：UI 自动化测试（适用于会修改生成代码的变更）

App 直接跑起来 → 自动操作 UI 到某个状态 → 截图比较修改前后差异 → 相似度阈值 **90%** → 低于阈值报错。

**前提**：Awade 可自动生成 App 的 UI 自动化测试代码（只需配置待测功能点 + 预期数据）。

> 即使不具备 UI 自动化测试条件，仅做编译器测试 + 实际用户数据 → 就能发现许多其他方式发现不了的兼容性问题。

## 四、为什么需要多角度发现

**熔喷布原理**：普通纺织布（经纬线交织）→ 线间有缝隙 → 病毒可穿过；熔喷布（乱七八糟喷在基材上）→ 满足厚度就无缝隙。

同理：**必须从差异很大的角度、采用差异很大的方法 → 尽可能多地发现兼容性问题。**

### 兼容性问题的特殊性

1. **最劝退的问题**：给应用团队带来计划外、被动式的额外对齐工作 → 次数多了萌生退意
2. **"怎么改都是错的"**：未及时发现的兼容性问题 → 导致平台团队陷入两难境地

案例：UI 安全边距 bug → 两个月前修改导致安全边距消失 → 恢复边距则新增 App 边距过大 → 不恢复则旧 App 没有边距 → **无论改不改都得罪人**。
