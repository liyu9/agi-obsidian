# 05｜基础设施：启动低代码平台研发之前，你需要有什么家底？

> **核心结论**：**Web 组件集是低代码平台最重要的基础设施，没有之一**。挑选组件集按重要程度排序：自主可控 > 封装程度 > 功能强大。组件集研发必须先于低代码平台至少 6~12 个月启动。

---

## 一、架构选型：B/S 架构

低代码平台选择 **B/S 架构**的理由：
- Web 技术长足发展，浏览器功能/性能足以承载高度复杂的 Web 页面
- 几乎所有 PC 端业务、越来越多移动端业务倾向 B/S 架构
- 即使需输出 Android/iOS Native App，Web 技术也可在浏览器中模拟 Native 效果

---

## 二、Web 组件集的三大职能

组件集贯穿低代码平台 **60%~80%** 的功能：

| 职能 | 说明 |
|------|------|
| 构筑低代码编辑器**自身** | 编辑器本身是复杂 Web 应用（状态多、交互密集、性能要求高） |
| 构筑编辑器的**开发能力** | 编辑过程 = 收集配置信息 → 为组件 API 生成正确值。**组件集的能力直接决定了编辑器的开发能力** |
| 构筑**业务应用** | 生成的 App 依赖组件集渲染 |

**因果链**：组件集能力 → 渗透三大职能 → 决定编辑器质量 → 决定低代码平台成败

---

## 三、挑选组件集的三个维度

### 3.1 自主可控（最重要）

**为何自主可控比功能更重要？**

编辑器委托组件集管控开发细节 → 编辑器本身没有开发能力，能力来自组件集 → **对组件集的定制需求巨大**

使用第三方组件集的问题：

| 问题 | 说明 |
|------|------|
| 定制需求不可理喻 | 有的需求专为编辑器定制，从 Pro Code 角度看不可理喻 |
| 开源社区不会为你定制 | 守护者从未考虑组件集给编辑器使用 |
| 交付周期不可控 | 小修改需等数周，PR 的 review/讨论/评估也需要时间 |
| **研发进度不能与不可控社区挂钩** | 最终要么 fork 单干，要么二次封装 → 实质上已向自主可控屈服 |

**UX 规范层面**：
- 第三方组件集 = 全盘接受其 UX 规范
- UX 规范如"国家宪法"，微小改动波及所有组件外观
- 用 CSS 覆盖原始样式 → 开发难度高 + 难以维护 + 侵入私有实现 + 版本升级可能导致失效

**结论**：**选一套自主可控的组件集，即使它看起来没有那么强大**。最好是自研或下级团队开发，至少也要兄弟单位开发且有足够源码修改权限。

### 3.2 封装程度高（第二重要）

**核心原则**：组件集是给**编辑器**使用的，不是给人类使用的。

#### 三种封装方式对比

| 封装方式 | 典型特征 | 适用场景 |
|---------|---------|---------|
| **数据驱动** | 所有 API 以数据方式驱动，HTML/CSS 彻底封装在内部 | **适合低代码编辑器** |
| 模板驱动 | HTML 部分复杂，数据/样式/状态在 HTML 模板里实现 | 适合 Pro Code（灵活定制） |
| CSS 样式模板 | 只给 CSS 样式，无动作 | 不适合低代码和大规模 Pro Code |

#### 封装程度差的危害（示例）

低封装度的 radio 组件：选中状态用变量、disabled 用 CSS 样式、文本用 HTML 节点 → 三种配置方式混用 → **代码生成器"东一榔头西一棒"，造成不必要麻烦**

高封装度的数据驱动方式：一个 `options` 变量 + 一个 `value` 变量 → HTML 极其简洁 → **编辑器只需正确生成变量代码**

**结论**：优先挑选数据驱动封装方式的组件集，自行实现时也必须采用此方式。

### 3.3 功能强大（第三重要）

#### 量化指标

| 指标 | 要求 |
|------|------|
| 原子组件 + 容器类组件 | 至少 **50 个以上** |
| 视图悬浮（气泡化） | 良好的封装 + 多层视图叠加管理（编辑器密集配置入口需要） |
| 数据采集组件 | 文本框/数字框/下拉选择等必须对表单友好 |
| 统一功能封装 | Angular 的 Directive：任意视图下拉、上传、多功能徽标、下拉多级菜单、拖拽等 |
| 图标库 | 不一定自研，可用开源（font-awesome、material design 的 SVG 图标库） |

#### 性能要求

**编辑器画布场景**：
- 活动视口同时 **100~200 个活动组件**（家常便饭）
- 若所见即所得非 iframe 实现（画布动态模块直接渲染）→ 性能要求**翻倍**
- 复杂 App 本身高复杂度 → 画布上可能同时 **200~300 个活动组件实例**
- 原子组件性能不佳 → 整个画布操作卡顿 → 影响开发效率和心情

## 四、皮肤深度定制能力（可选）

| 层级 | 说明 | 难度 |
|------|------|------|
| 同色系不同颜色 | 难度不大，多数可热切换 | 低 |
| 跨色系（明亮/黑暗） | 需要机制支持应用定制视图也实现跨色系；CSS3 变量特性可实现（IE11 支持不好） | 中 |
| **黑白同屏** | 同一页面两种相反色系共存（如明亮整体 + 深色 header/侧边导航） | 高 |

**实用性**：深色皮肤自带高端感，相同 UI 设计深色系比浅色系更显高端。黑白色系自由切换可大大提升业务应用展示张力。

## 五、启动时序与 UX 规范

### 5.1 组件集与低代码平台的启动关系

```
UX 规范建立 → 组件集启动研发（提前 6~12 个月）→ 低代码平台启动研发
                                          ↘ 组件集有一定积累后，两者可并行演进 ↗
```

- 组件集无法支撑低代码研发需要时 → 往往只能暂停低代码研发 → 先补充组件集能力
- 启动间隔不宜过近也不宜过长

### 5.2 UX 规范

- 对组件集、编辑器、业务应用产生全系列影响，不可忽视
- 不一定完全自研：Ant Design、Material Design、ISUX、ArcoDesign 都是可参考的优秀规范
- **一两位有深厚技术积累的领军人物是更重要的家底**
