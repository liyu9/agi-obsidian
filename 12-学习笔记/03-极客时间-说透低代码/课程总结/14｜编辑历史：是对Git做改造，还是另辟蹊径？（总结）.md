# 14｜编辑历史：是对Git做改造，还是另辟蹊径？

> **核心观点**：编辑历史是低代码编辑器的"后悔药"，主要目的是**鼓励试错、降低试错成本**。基本功能（撤销/重做）之外，低代码编辑器还应支持**多分支编辑历史**，这是代码托管能力的体现。

---

## 一、基本编辑历史的两种实现方案

### 方案A：Yjs（CRDT）

- 提供完善的**增量式编辑历史持久化机制**
- 内置 **UndoManager** 支持撤销/重做
- 即使不做多人协作也值得引入

### 方案B：Git

**优势**：

- 轻量小巧、性能优越（Linux 内核仓库已超 100 万 commit，活跃 App 历史记录未过万）
- 自带文件数据库（git commit / git log）
- 强大的分支管理和自动合并能力
- 全球数千万开发者使用，问题都能找到解决方案

**使用方式**：

| 方式 | 说明 | 推荐 |
|------|------|------|
| 单仓库 | 所有 App 放一个仓库 | ❌ 仓库大、历史多 |
| **多仓库** | 每个 App 独立仓库 | ✅ 物理隔离、安全性高 |

**Git 的三个问题**：

| 问题 | 说明 | 解决方案 |
|------|------|---------|
| **长单行文本** | 结构化数据 JSON.stringify 后为长单行 → git diff 几乎无效 | 多行文本按换行符拆分为字符串数组再存储 |
| **二进制数据** | 图片、字体、Excel 等 git 无法 diff | — |
| **GPLv2 协议** | GPL 有"感染性"→ 商业软件使用必须开源 | 预装 Git / 独立安装流程，解除平台与 GPL 软件捆绑 |

> ⚠️ **合规无小事！** 使用 GPL 协议软件时，商业平台必须确保发布版本不包含 GPL 文件。

### 方案C：Awade 自研方案

原因：Yjs 不适用（历史数据格式已固化）+ Git 使用 GPL 协议（中兴内部默认不用 GPL 软件）。

**实现原理**：

- 基于**全量数据存储**（每个历史记录 = 一份完整数据）→ 实现简单粗暴，代价是历史记录数据量大（单个 App 动辄数 GB）
- 数据结构：**双向链表** — 每个历史记录有 id、next 指针、previous 指针
- 游标（cursor）指向当前使用的历史记录
- 撤销/重做 = 移动游标；新增修改 = 新建节点 + 移动游标

## 二、编辑历史多分支的实现

### 为什么需要多分支？

低代码平台作为开发工具 → 必须有代码托管能力 → **多分支是代码托管的必备功能**。

同时，有了多分支 → 不需要为了保持单一分支而删除被撤销的历史记录 → 避免用户投诉。

### Awade 方案（基于双向链表）

核心操作极其简单：**无论游标在哪，直接新建记录节点，配置好相邻节点的 next/previous，移动游标即可**。

不需要真的创建独立链表 → 物理上只是平铺的记录序列 → 逻辑上通过遍历 next/previous 还原出分支树。

### Git 方案

Git 天生支持多分支管理 → 只需开发适当的可视化界面即可。

## 三、可视化分支管理

### Awade 的分支树还原算法

1. 从编号最小的记录开始 → 遍历 next 属性 → 得到第一个分支 → 标记所有节点
2. 将未标记节点归为新组 → 从编号最小的记录开始 → 根据 previous 值"挂到"对应节点下 → 遍历 next → 得到下一个分支
3. 递归直到没有未标记节点

**时间复杂度 O(n)**，配合最大记录数限制（Awade 限制 **600 条**）→ 常数级。

### Git 的分支可视化

```bash
git branch                    # 列出所有分支
git merge-base branch1 branch2  # 找出两个分支的共同 commit（分叉点）
```

通过分叉点即可画出与 Awade 相同的逻辑分支图。

> ⚠️ **误区警告**：市面上的 Git 命令行可视化工具都是"为了 Git 而 Git"——解决的是命令行难用的问题，不是编辑器历史管理的问题。**切勿直接套用**。

### 前端呈现

无论后台用哪种方案，前端呈现一致：**历史记录树 + 节点选择/删除等操作** → 对用户屏蔽链表、分支等术语。

## 四、编辑历史分支的合并

| 场景 | 合并目标 |
|------|---------|
| 多人协作 | 同一应用数据在**两个人**手里的两个版本 |
| 编辑历史分支 | 同一应用数据在**一个人**名下的两个版本 |

本质相同：**同一应用数据的两个不同版本的合并** → 直接复用第13讲的合并方法。

Git 方案则直接使用 `git rebase`。

---

## 五、多分支编辑历史的价值

| 价值 | 说明 |
|------|------|
| **降低试错成本** | 大胆探索性修改 → 成果合并到主分支 → 失败则直接丢弃 |
| **版本管理** | 发版分支 / 系统测试分支 / Dev 分支，一站式管理 |
