# 19｜如何使用平民技术实现UX设计稿转代码？

> **核心问题**：低代码平台如何以低成本、无需深度学习的方式实现 D2C（Design to Code），消除可视化布局中仍存在的重复劳动。
> - D2C 输入 UX 设计稿 → 输出可编辑的页面布局配置

---

## 一、D2C 背景与现状

### 1.1 行业发展时间线

| 时间 | 事件 |
|------|------|
| 2017 | pix2code 论文：深度学习接收 UI 截图 → 识别 UI 结构 → 生成 HTML 代码 |
| 2018 | 微软 AI Lab 开源 Sketch2Code：手绘草图识别 → 生成代码 |
| 2019 | 阿里上线 imgcook；58 推出 Picasso；美团推出 ui2code |
| 2022 | copilot、ChatGPT 等 AI 编码辅助出现，"研发智能化"内涵扩展 |

### 1.2 现有方案的问题

- **自研门槛高**：基本都依赖深度学习，无技术积累的团队成本极高，训练出满意准确率难度大
- **拿来主义问题多**：
  - 识别准确率脱离训练场景后**大幅下降**
  - 生成的代码 UX 规范不一定匹配
  - 输出的是代码，与低代码平台的对接**基本无解**

### 1.3 本文方案的核心思路

**借助 UX 规范的辅助，用平民技术实现 D2C**，无需深度学习。

---

## 二、预置条件

| 类型 | 条件 | 说明 |
|------|------|------|
| 必要条件 | UX 团队或至少一名 UX 设计师 | 没有设计稿就无从谈 D2C |
| 充分条件1 | **UX 规范** | 设计师与研发的衔接桥梁；可复用 antd、arco、Jigsaw 等开源规范 |
| 充分条件2 | **配套 Web 组件集** | Web 界面研发最重要的基础设施；antd、arco、Jigsaw 均有配套开源组件集 |

**关键发现**：大厂 D2C 方案都**忽略了 UX 规范在识别过程中的作用**，采用纯技术碾压。借助 UX 规范可大幅降低实现难度。

## 三、UX 设计方法调整

**目标**：将组件类型信息植入设计稿，降低算法识别难度。

### 3.1 组件化 + 规范命名

前提：UX 团队已采用组件化方式组装设计稿（与前端组件基本一致）。

**方法**：规范命名 UX 组件 → 对设计师工作几乎无侵入 → 组件类型自动植入设计稿数据。

**三段式命名规则示例**：`plx:button:error`
- 第一段：UX 规范大版本
- 第二段：组件种类
- 第三段：组件主要状态

### 3.2 有计算机视觉能力时的替代方案

人是最不可靠的 → 设计师可能不守规矩 → 可用计算机视觉替代：根据颜色、边缘、直线、圆角等特征"按图索骥"识别组件类型。

## 四、设计稿识别算法

### 4.1 组件属性识别

**关键原则**：别忘了 UX 规范！

UX 规范对组件属性的描述精确到像素级 → **在规范指定的位置读取的值，就是对应属性的值**。

推理过程：
1. 已知组件类型（由规范命名提供）
2. UX 规范规定了该组件每个属性的精确位置（如标题在距边框 16px 高、靠左 24px）
3. → 在指定位置读取文本/颜色等值
4. → 通过值推断更多属性（如红色背景 → 危险主动按钮 → 自动获取该按钮的全部生成信息）

### 4.2 层级结构推断

**问题**：设计师眼中的设计稿是**扁平的上下结构**，而前端需要**层次结构**（嵌套关系）。

**为何必须还原层级**：扁平结构生成的代码毫无逻辑，看不懂、改不动（如 Axure 输出的 HTML 代码）。

**抽象模型**：
- 界面抽象为一个个**盒子**
- 能装下其他盒子的 = **容器**
- 容器之外的 = **普通组件**

**推断规则**：
- 一个盒子**完全被**另一个盒子覆盖 → **父子关系**
- 未完全覆盖的盒子 → **兄弟关系**

### 4.3 UI 弹性推断

**问题**：静态设计稿无法表达动态弹性布局。例如"两翼有弹性中间固定"vs"两翼固定中间有弹性"，静态稿无法区分。

**解决方案：辅助 + 约定**

1. **人工辅助**：在需要弹性的部位放置**透明容器**（只有算法能"看"到）→ 被覆盖部分生成弹性代码，其他固定尺寸
2. **事先约定**：在 UX 规范中约定组件的弹性偏好
   - 按钮：垂直和水平都不弹性
   - 输入框：垂直固定、水平弹性
3. **特例处理**：辅助 + 约定无法覆盖的场景 → UX 设计师按需使用嵌套弹性容器，或交由开发人员在生成代码上调整

## 五、D2C 的延伸价值

### 5.1 设计即开发模式

D2C 实现 → **UX 设计稿 = 代码** → UX 设计师 = 开发人员 → 设计师可在 D2C 支持下完成业务素材（模板、业务组件）的开发和维护。

### 5.2 D2P（Design to Production）

UX 设计稿转代码后 → 进一步植入业务代码 → **一步到位转为可用 App**

适用场景：程式化、业务逻辑相似度高的场合；短平快、短周期、快速试错的场景。

**效果**：UX 出图后数秒内 App 即可上线。
