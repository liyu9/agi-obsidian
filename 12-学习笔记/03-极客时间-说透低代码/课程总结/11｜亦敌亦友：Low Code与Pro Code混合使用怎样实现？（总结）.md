# 11｜亦敌亦友：Low Code与Pro Code混合使用怎样实现？

> **核心观点**：高低代码混合开发是低代码平台的必要能力，无论平台处于起步还是成熟阶段。"代码含量"从低到高分为三层：**表达式 → 代码块 → 模块级纯编码**。

---

## 一、为什么低代码平台还需要编码？

### 1.1 天花板级平台

```
天花板级低代码平台 → 必须支持各种技能水平的人同时使用
→ 高技能开发者期望直接编码（职业获得感 + 自由发挥需求）
→ 可视化模式强制规定了开发套路 → 高技能者感到受限
```

### 1.2 发展中平台

```
发展中平台 → 可视化能力不完善 → 难免有搞不定的情况
→ 纯编码模式是**刚需**，甚至是雪中送炭
```

### 1.3 成熟平台（二八原则）

```
成熟平台 → 可视化模式覆盖 80% 场景
→ 剩余 20% 边边角角场景硬上可视化反而吃力不讨好
→ 纯代码兜底是明智选择
```

### 1.4 Awade 的黑料（MVP 初期策略）

MVP 初期对可视化端到端交付能力心存疑虑 → 结构化代码生成法刻意生成**人可读的代码** → 万一搞不定可导出代码手工继续。后来证明担心多余，但此特性意外实现了**高低代码模式无缝切换**。

---

## 二、高低代码混合开发的三层实现

### 2.1 第一层：表达式

| 特征 | 说明 |
|------|------|
| 定位 | 可视化模式的主要盲区，高低代码混合**最常见**的方式 |
| 作用 | 作为小功能点，连接大块可视化逻辑之间的缝隙 |
| 常见类型 | 真假表达式、三目运算、正则表达式、求值表达式、逻辑运算、数值计算 |

**示例**：可视化逻辑判断中，直接让开发者填写表达式计算真假 → 自然且高效。

**纯可视化方式的代价**：判断 `array.length == 0` 需要一整个表单配置 → 性价比极低。

### 2.2 第二层：代码块

| 特征 | 说明 |
|------|------|
| 定义 | 若干行完整代码组成、有特定功能的程序块 |
| 定位 | **可视化编程中实现高低代码混合的最好方式** |
| 使用方式 | 在逻辑流程中，可视化逻辑块和代码块**按需交织混合** |

混合编排场景：

```
开发者选择使用哪种方式的原因可能是：
- 某功能用可视化块效率更高
- 不知道如何写出预期代码，不得不用可视化块
- 没有合适的可视化块，不得不使用代码块
- 甚至随机选择
→ 编排器必须支持任意混合
```

### 2.3 第三层：模块级纯编码

**模块**：App 工程的唯一粒度。

| 规则 | 说明 |
|------|------|
| 启动模块 | 有且只有一个，由框架直接引用 |
| 模块类型 | 多种不同类型，按需创建 |
| 模块引用 | 可相互引用，一个模块可引用/被引用多个模块 |
| SPA 入口 | 模块是实现单页面应用、自定义组件等的入口 |

**操作方式**：将某个模块从可视化模式**切换为纯编码模式** → 开发者按照框架规范（如 Angular）纯编码开发。

**关键特性**：

- 切换只影响**当前模块**，其他模块保持原模式
- 纯编码模块可继续引用/被引用其他模块 → App 整体出现高低代码混合

## 三、高低代码混合编译

### 3.1 核心前提

低代码平台开发过程**有代码参与**（代码是副产品）→ 混合编译的前提天然存在。

### 3.2 编译流程（间接法）

```
SVD（配置数据）→ awadec → TypeScript → tsc → JavaScript → MVVM JiT → 组件描述符 → 渲染器 → DOM → 浏览器视图
```

| 步骤 | 工具 | 说明 |
|------|------|------|
| SVD → TypeScript | awadec（低代码编译器） | 纯编码模式跳过此步，手写就是 TypeScript |
| TypeScript → JavaScript | tsc | Angular 需要；React 需 JSX 转换；Vue2 不需要 |
| JavaScript → 组件描述符 | MVVM 框架 JiT 编译器 | 如 Angular JiT |
| 组件描述符 → 视图 | MVVM 渲染器 | 生成 DOM，驱动浏览器渲染 |

**间接法 vs 直接法**：

| 方法 | 所见即所得实现难度 |
|------|------------------|
| 间接法（先→MVVM框架代码→再→浏览器代码） | **简单**，高低代码混合编译流程几乎一致 |
| 直接法（直接生成浏览器代码） | 非常麻烦 |

**性能建议**：整个编译过程**全部前置到浏览器中完成**，以满足所见即所得的实时性要求。

### 3.3 纯编码模块能否回退？

```
模块转为纯编码模式 → 放飞思维 → 代码复杂度不可控
→ 不可能自动回退到可视化模式

强约束下理论上可以，但人的行为不可控 → 需要对人类友好的简洁规则
→ 目前无此需求（可视化模式 + 代码块已覆盖绝大多数场景）
```

## 四、编码体验

### 4.1 不同层级的编码体验需求

| 混合层级 | 编码体验需求 |
|---------|------------|
| 表达式 | 智能提醒、补齐、出错提示 |
| 代码块 | 需求较强烈 |
| 模块级纯编码 | 基本与 Web IDE / Native IDE 同级 |

### 4.2 解决方案

| 场景 | 方案 | 说明 |
|------|------|------|
| 表达式 + 代码块 | **Monaco 编辑器**（VSCode 的底层编辑器） | 功能强大、扩展性极强，完全足够 |
| 模块级纯编码 | **方案A**：继续扩展 Monaco | 集成度好，但扩展工作量大，资源投入偏离低代码核心 |
| 模块级纯编码 | **方案B**：VSCode 插件 | 成本低、可行性高，利用已有 IDE 能力，但集成度差 |

**建议**：表达式和代码块用 Monaco；模块级纯编码做 VSCode 插件。

---

## 五、关键认知

1. **高低代码混合是必要能力**：无论平台发展阶段，表达式和代码块的混合支持都是**必须的**
2. **代码含量三层递进**：表达式（最常见）→ 代码块（可视化编程最佳混合方式）→ 模块级（纯编码，24K纯度）
3. **生成对人友好的代码**是混合开发的基础——Awade 的结构化代码生成法意外成为关键能力
4. **间接法编译**是实现高低代码混合所见即所得的正确架构选择
5. **编码体验不可忽视**：Monaco 解决轻量场景，VSCode 插件解决重量场景
