# 18｜兼容性问题：如何有效解决兼容性问题？

> **核心观点**：解决兼容性问题的核心思想是**化整为零**——每个破坏性变更配套一个处理器，将变更前的数据升级为变更后的格式。一个处理器只关注一个破坏性 → 实现简单、健壮、好维护。

---

## 一、破坏性变更的类型与占比

| 类型 | 占比 | 说明 |
|------|------|------|
| **Schema 数据结构变更** | **~50%** | 字段从简单值→复杂对象、单值↔数组、字段拆分/合并等。初期占比更高，随平台成熟度增加而下降 |
| **模板文件更新** | **~20%** | 模板更新后，已实例化的文件内容不会更新 → 需要强制对齐 |
| **外部破坏性变更** | **~20%** | 第三方库升级（如 Vue2→Vue3、Angular8→10）、服务端 API 演进 |
| 其他 | ~10% | — |

**总体**：低代码平台内部演进产生的破坏性变更占绝大多数。

---

## 二、if else 方案为何不可行

### 复杂度爆炸

引入第1个破坏性 A → 1个 if else（2种情况）
引入第2个破坏性 B → 2个条件（4种情况）
引入第3个破坏性 C → 3个条件（8种情况）

→ **负担随破坏性个数为幂爆炸式增长** → if else 无法解决问题。

### 关键洞察

虽然蓝色分支（A之前）和橙色分支（A之后）下的破坏性 B 和 B'是独立的、时机不同 → 但**处理方法是等效的**。

→ 这就是解决问题的突破口：**需要一个统一的、不依赖分支上下文的处理方式**。

---

## 三、标记破坏性变更

必须先标记 → 拿到任意用户数据时能快速识别已包含哪些破坏性变更 → 否则必须写大量 if else 检测 → 不可行。

| 标记方式 | 优点 | 缺点 |
|---------|------|------|
| 时间戳 | 随时间递增 | 代码未改但不同时刻构建时间戳不同 → 矛盾 |
| **内部版本号** | 代码不改则版本号不变 | 须为每个破坏性发布新版本（可与对外版本号分开） |
| 正式版本号 | 简单直接 | 对在线软件无副作用（用户随时刷新拿新版本） |

**Awade 采用**：正式版本号标记（在线软件版本号不重要）。

---

## 四、化整为零方案

### 核心机制

**每出现一个破坏性变更 → 配套编写一个处理器（Processor）**：

```
处理器输入 = V1 格式（破坏性变更前）的用户数据
处理器输出 = V2 格式（破坏性变更后）的用户数据
```

- **一个处理器只处理一个破坏性** → 不关注其他破坏性 → 逻辑确定 → 易做健壮
- V2 及以后的代码"忘记"V1 的存在 → 无需 if else

### 数据升级流程

不同用户数据可能在不同时间创建（不同版本号）→ 升级时按版本号顺序**依次执行**对应的处理器：

```
用户数据(V1) → 处理器A → V2 → 处理器B → V3 → 处理器C → V4（最新）
```

→ **任何多年前的 App 工程都可随时打开再次编辑**。

## 五、三类破坏性变更的具体处理

### 5.1 Schema 数据结构变更

**案例1：简单值 → 复杂对象**

```json
// V1
{ "property": "simple string" }
// V2
{ "property": { "type": "default", "value": "..." } }
```

处理器：将字符串包装为对象 → 给 type 设默认值。

**案例2：数组简化为单值**

```json
// V1
{ "property": [{ "type": "type1" }, { "type": "type2" }] }
// V2（裁剪后只留 type1）
{ "property": { "type": "type1" } }
```

处理器：简化结构 → V2 代码无需知道 property 曾是数组。

### 5.2 模板文件变更

处理更简单：**将新模板拷贝到对应位置即可**。

常伴随 Schema 变更 → 一个处理器可同时处理多种类型。

### 5.3 外部破坏性变更

**纯代码模式下只能手工解决，低代码平台多数情况可悄无声息自动处理。**

#### 前端第三方库破坏性

案例：按钮组件 API 变更 `text` → `label`

处理器：找到 App Schema 中所有带 text 属性的按钮 → 自动将属性名改为 label。

> **注意**：实际修改的是 App 的 Schema 数据（低代码的"源码"），不是组件本身。

复杂案例：Angular 4.x → 8.x → 9.x（Webpack、TypeScript、RXJS 等一起调整）→ 同样思路：先了解需手工做哪些调整 → 在 Schema 对应位置做调整 → **两次大版本升级都表现良好**。

#### 服务端 API 破坏性

与前端第三方库处理方式如出一辙。

案例：返回数据从二维数组变为 `{ header, data }` → 处理器在 Schema 中筛选出使用该服务的位置 → 调整处理逻辑。

### 5.4 无法解决的破坏性

实际碰到过 **3~4 次**无法完全自动处理的情况：

- 编辑器底层逻辑重写 → 老 Schema 缺少大量属性 → 补经验值效果不达预期
- UX 设计规范大幅调整 → CSS 破坏性细节太多 → **约 30% CSS 细节泄露出**

**处理方式：升级大版本** → 对外宣布无解 → 提供详细处理方法 + 配专人协助升级。

> 需非常谨慎、尽量避免、与各应用团队达成共识。

## 六、关键数据

| 指标 | 数值 |
|------|------|
| 平均多少个修改引入一个破坏性 | **40~60 个** |
| 一年累计破坏性变更 | **20~30 个** |
| Schema 变更占破坏性比例 | ~50% |
| 模板变更占比 | ~20% |
| 外部变更占比 | ~20% |
| CSS 大改版泄露率 | ~30% |

> 没有有效方法 → 任何团队迟早被兼容性压垮 → 最直观表现：**代码没人敢改，没人知道为啥正确，也没人知道为啥出错**。
