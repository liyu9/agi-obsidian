# 08｜布局编辑器：如何做到鱼和熊掌兼得？

> **核心观点**：效率和通用性是布局器的两个相互制约维度。单一布局器无法同时兼顾 → 采用**组合策略**：多种布局器通过**编译器协议**实现松耦合，再包装为**容器**支持自由嵌套。

---

## 一、App 开发三部曲

| 步骤 | 说明 | 时间分布 |
|------|------|---------|
| 布局 | 按 UX 设计稿/需求草图放置组件并排列 | App 生命周期早中期 |
| 交互 | 配置组件行为和逻辑 | 中晚期 |
| 数据 | 配置数据获取和渲染 | 中晚期 |

> 三者非顺序执行，而是交织进行。D2C（Design to Code）可辅助自动化布局，但不能替代手工布局——自动识别后仍需微调，需求更新后需手工维护。

## 二、效率 vs 通用性

### 2.1 不同场景需要不同布局器

| 场景 | 高效布局方式 | 说明 |
|------|------------|------|
| 表单 | 基于行的布局 | 以行为单位，自上而下排列，一行含标签/编辑器/说明/错误提示 |
| Dashboard | 基于卡片的布局 | 快速切分大区域获得合适尺寸的卡片，小区域可融合成大卡片 |
| 通用 | 网格布局（绝对坐标） | 可以胜任表单和 Dashboard，但效率不如专用布局器 |

**绝对坐标布局器 ≠ 运行时无弹性**：编辑态用绝对坐标，运行时可通过分组算法 + Flex 布局实现弹性尺寸。

### 2.2 效率与通用性的制约关系

**不同场景下的制约**：

```
越通用的布局器 → 特定场景效率越低
越专用的布局器 → 适用范围越窄
```

**同一场景不同阶段的制约**（以 Dashboard 为例）：

| 阶段 | 高效方式 | 原因 |
|------|---------|------|
| 布局初始（大片空白） | 卡片布局 | 快速切分，8次操作完成整页 |
| 精细布局（卡片内部） | 网格布局 | 卡片切分性价比极低，小区域需9次操作（超整页的8次） |

## 三、组合策略：鱼和熊掌兼得

### 3.1 核心思路

```
靠单一布局器无法同时获得效率和通用能力 → 采用组合方式
```

关键架构支撑：**编译器协议**（来自第6讲 Level 3 架构）

```
编辑器/布局器 ←→ 编译器协议 ←→ 代码生成器
```

- 各布局器**遵守同一套编译器协议** → 代码生成器可识别任意布局器的输出
- 布局器之间无直接耦合 → 可自由组合
- **反面做法**：在代码生成器中用 if-else 处理不同布局器差异 → 判断条件指数增长，3-5种布局器后无法维护

### 3.2 实现方式：布局器包装为容器

- **容器** = 一种特殊组件，具有组件的所有特性 + 能装下其他组件或容器
- 容器支持相互嵌套 → 与布局器的组合需求天生匹配
- 开发时按页面特征挑选合适布局器，各种布局器发挥优势、规避短板

### 3.3 组合使用流程（垃圾分类页面示例）

```
卡片布局器（快速切分页面为多个卡片）
    ├─ 卡片A → 继续卡片切分
    ├─ 卡片B → 拖入网格布局器（精细化布局）
    └─ 卡片C → 拖入表单容器（表单方式布局）
```

## 四、四种布局器详解

### 4.1 网格布局器

| 特征 | 说明 |
|------|------|
| 核心特点 | **最通用**，推荐第一个实现 |
| 编辑态 | 绝对坐标定位，支持点选/框选/拖动位置/拖动尺寸 |
| 对齐方案 | **固定拖动步长（8px）**，而非磁力线自动吸附 |
| 8px 的来源 | 分析已有设计稿得出，UX 团队认可，作为所有 UI 的基本单位 |
| 运行态弹性 | 通过分组算法将平铺组件分组 → 生成有层级关系的树 → Flex 布局实现弹性 |

> 磁力线方案被否决的原因：(1) 实现工作量大；(2) UX 规范要求精确留白（如 8px 不能是 7px 或 9px），磁力线难以做到精确。

### 4.2 卡片布局器

基于 CSS 盒子模型的扩充：

| 盒子类型 | 排列规则 |
|---------|---------|
| 水平盒子 | 直接子级按水平排列 |
| 垂直盒子 | 直接子级按垂直排列 |

**关键特性**：水平和垂直盒子支持任意层级自由组合 → 两个极简单的盒子通过自由组合可描述整个二维 UI。

开源实现：Jigsaw 组件集中的 box 组件（运行时轻量化 box + 编辑时 box，二者实现差异很大）。

### 4.3 表单布局器

| 封装方式 | 适合低代码？ | 说明 |
|---------|------------|------|
| 数据驱动型 | ✅ 适合 | 低代码编辑器只需生成数据对象，喂给表单组件即可渲染 |
| 模板驱动型 | ❌ 不适合 | 表单 UI 定制需求巨大 |

推荐方案：

| 方案 | 技术栈 | 说明 |
|------|-------|------|
| ngx-formly | Angular | 满足 **99%** 需求（扣1分：复杂异步校验不完美） |
| Formily（阿里） | React / Vue | 优秀的数据驱动表单实现，还提供可视化设计器 |

### 4.4 流程编排器

| 用途 | 说明 |
|------|------|
| 流程审批类 App | 作为顶层布局器，各环节配合表单等布局器 |
| 数据编排 | 对服务端数据做编排组合和结构转换后给前端使用 |

实现方式：集成开源软件 X6。

## 五、演进规律

```
低代码编辑器早期 → 优先发展通用能力（先实现网格布局器）→ 成熟后 → 效率作为唯一追求 → 通过组合多种布局器发挥最大效率
```
