# 16｜扩展与定制：如何实现插件系统并形成生态圈？

> **核心观点**：插件系统是通用型低代码平台解决"通用性代价"的关键能力。插件廉价 → 开发成本低 → 数量庞大 → 填满各功能覆盖盲区。核心功能与扩展功能的**松耦合架构**是实现插件的基础。

---

## 一、通用型低代码平台的五大弊端

| 弊端 | 原因 |
|------|------|
| **使用门槛居高不下** | 通用到具体场景需大量定制化工作，难度不低 |
| **效率无法最大化** | 高不成低不就，如网格布局器做精细化 UI 效率高、做表单效率低 |
| 平台"高冷挑剔" | 需考虑各种场景 → 小需求也要漫长评估 → 甚至被拒绝 |
| **与业务耦合、逐渐腐化** | 扩展性不够 + 不够强势 → 用 if else 应急 → 第一个 if 出现 = 架构腐化开始 |
| 需求积压、团队不满 | 应用团队无法直接参与定制 → 需求全部积压到平台团队 |

**插件为什么能解决**：

- **廉价** → 开发成本低 → 试错成本低（搞错了推倒重来）→ 可先以插件验证 → 再融入平台
- 数量庞大 → 像细沙填满覆盖盲区
- 应用团队可参与 → 鞋子好不好脚知道 → 自行定制效率更高 → 挡住提交给平台团队的需求

## 二、插件系统的设计与实现

### 2.1 SDK 提取方法

SDK = Software Development Kit，提供实现插件的框架和必要辅助功能。

| SDK 组成 | 说明 | 优先级 |
|----------|------|--------|
| **接口和类型定义** | 代码量占比不到 1/10，但最重要 → 勾勒插件系统轮廓 | 最高 |
| **基类定义** | 通用部分尽可能完整实现 → 只留少量抽象方法 → 二次开发者补全即可 | 高 |
| **调试工具 + 构建/部署脚本** | 无则二次开发无法继续 | 高 |
| 辅助性工具类 | 降低开发难度、提升效率 | 低（按需提供） |

### 2.2 可扩展的功能点

#### 扩展点一：数据与数据模型（最重要）

**存量系统对接是刚需**。两种场景：

1. **新老系统并行** → 老系统流量逐渐切到新系统 → 但数据无法移植 → 给老系统做插件对接 → 老系统下线后移除插件，无残留
2. **低代码与众多存量系统共存** → 每个存量系统有自己的数据获取机制和数据模型 → 唯有针对各系统打造专用插件

#### 扩展点二：自定义组件

- 内置组件集通用常见 → 业务组件通用性差但价值高
- 内置组件有功能盲区 → 应用团队利用扩展点添加新组件
- **兜底策略**：低代码平台应支持在无须封装插件的前提下直接调用原生 API、快速使用第三方库

#### 扩展点三：自定义交互动作

- 封装程式化交互逻辑 → 只暴露若干输入框作为参数 → 使用体验好
- 对存量复杂系统的用法进行**场景化归纳** → 封装为自定义动作
- 案例：WebGIS 系统有上百个 API → 业务团队归纳出栅格展示、小区展示、热力图等用法 → 封装为动作 → 不熟悉 GIS 的人也能快速渲染图层

#### 其他扩展点

- **导出**：一键导出多平台应用包（物理机/Docker）/ 导出离线报告（Word/PDF）/ 离线 Web 应用包
- **登录**：多系统纳管场景 → 针对每个系统制作单点登录插件

### 2.3 Manifest 设计

Manifest 文件（固定位置和名称，如根目录 `manifest.json`）描述插件信息：

| 信息类型 | 内容 |
|---------|------|
| 静态描述 | 插件名、版本、所用 SDK 主版本、功能描述 |
| **Schema（关键）** | 实现了哪些扩展点、扩展点路径、个性化配置（如组件图标） |

### 2.4 二次开发建议

- **提供可安装可运行的 Demo 插件**（依葫芦画瓢 > 看文档）
- 常见问题解决方案通过**注释**写在 Demo 代码中
- 必要时在注释中放超链接导航到详细文档

### 2.5 插件生命周期管理

```
上传 → 安装 → 激活 → 使用 → 去激活 → 迭代更新 → 卸载
```

| 阶段 | 关键操作 |
|------|---------|
| 上传 | 开放插件上传通道 |
| 安装 | 静态校验 manifest.json → 检查配置项合法性 → 文件拷贝（JSBundle、NPM 包、静态文件） |
| **激活** | **安全风险最高**：前端下载 JSBundle 并 eval → 后端执行初始化脚本 → 将功能植入平台各环节（组件列表/动作列表/数据通道等） |
| 去激活/卸载 | 反向操作：删除植入的能力、删除插件文件 |

> ⚠️ 面向不确定公众开放时，安全性是重要议题（XSS 攻击 / 恶意代码执行）。内网场景可降低安全优先级（实名 + 日志追溯）。

**插件分发平台**（可选）：集中管理插件 → 新增/删除/在线发现/版本升级。资源有限时可复用制品库、内部 NPM 镜像、内部网盘甚至 FTP 服务器。

## 三、生态圈是副产品

插件系统务实目的 → 连通存量系统 → **生态圈是自然形成的结果**：

```
存量系统 ←插件→ 低代码平台 ←插件→ 应用团队
    ↓                    ↓                    ↓
  数据                  贯通               业务组件/模板
```

- 数据与数据、人与数据、人与人打通 → 形成圈子 → 正向增强回路
- 连通的系统越多 → 低代码平台对企业价值越大 → **低代码平台起到中台作用**
- 与其他系统打成一片同时独善其身 → **只有插件系统才可能达到**

---

## 四、插件系统架构

```
编译器内核 → 协议层（对外抽象，定义/约束所有扩展点）→ SDK（协议默认实现 + 扩展点基类）
                                                              ↑
                                                         插件 / 内置功能
                                            （两者平起平坐，都遵守编译器协议）
```

**关键设计**：内置功能与插件架构上平起平坐 → 确保插件有充分扩展能力。实际实现层面可通过 SDK 控制内置功能优势。
