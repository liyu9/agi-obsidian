# 25｜遭遇程咬金，低代码技术会被AI大模型替代吗？

> **核心结论**：大模型不是低代码的竞争对手，而是帮手。大模型带来**自然语言**这一新工具，恰好弥补可视化手段的内秉性缺陷，两者组合让低代码技术"带着智能化翅膀再次起飞"。

---

## 一、低代码技术的优弱势分析

### 1.1 杀手锏：可视化编辑 + 所见即所得

可视化编辑常用形式：
- 代码编辑改为**表单**形式
- 枚举配置项采用**下拉选择**
- 参数联动、自动填写、自动筛选
- 配置过程**及时校验**，提前报错

### 1.2 任务二分法：描述性 vs 逻辑性

| | 描述性任务 | 逻辑性任务 |
|---|---------|---------|
| 内容 | 数据展示、用户界面、样式和布局 | 数据处理/计算、业务流程管理、条件和规则、集成和连接 |
| 可视化表现 | **非常擅长** | **不适合** |
| 原因 | 信息展示和界面设计天然适合可视化配置 | 灵活性极高，业务抽象不够时问题不可预测 |

**一句话总结**：**传统低代码技术非常擅长处理描述性任务，但不适合处理逻辑性任务**。

### 1.3 低代码的不可能三角

**开发效率、易用性、可定制化**三者最多只能拥有其二，必须放弃第三个。

**易用性随复杂度的变化趋势**：
- 编辑器功能↑ → 复杂度↑ → 学习曲线陡峭 → 易用性螺旋下降
- 定性关系：功能丰富程度与易用性呈**反比**

---

## 二、大模型给低代码带来的价值

### 2.1 核心价值：自然语言作为输入手段

传统低代码工具箱只有**可视化**一个工具 → 逻辑性任务表现差 → 大模型带来**自然语言** → 弥补可视化手段不足。

### 2.2 自然语言的优劣势

| 优势 | 劣势 |
|------|------|
| **几乎人人生而具备**，与低代码"降低门槛"目标完美契合 | 逻辑不严谨，不能自洽，前后矛盾，表述歧义 |
| 可处理逻辑性任务 | 效率低，需长篇描述才能严谨表达逻辑 |
| 可替代部分可视化编辑方式 | 非结构化非标准化，过于随意自由 |
| 无可比拟的灵活性 | **效率比可视化方式低**（特定场合低得多） |
| | 有学习成本（面对空白输入框不知说啥） |

### 2.3 量化收益（Awade 平台经验）

- **60%~70%** 的工作量投入在可视化配置界面开发上
- NLU 替代一半界面 → 节约 **12~15 人/年** 工作量

### 2.4 对易用性的影响

围绕自然语言做交互设计 → 减少可视化配置界面数量 → 界面变简洁 → **整体易用性提升**。

定性关系变化：
- **改造前**：功能丰富度↑ → 易用性急剧下降
- **改造后**：功能丰富度↑ → 易用性**几乎保持不变**

---

## 三、可视化方式的定位

| 情况 | 可视化定位 | 自然语言定位 |
|------|----------|------------|
| 从零构建低代码平台 | 牛夫人（辅助） | **主角**，可视化仅在自然语言低效处打辅助 |
| 已有成熟低代码平台 | 小甜甜（主角） | 辅助手段，但1~2年后可能成为主要方式 |

**核心策略**：不是替代，而是**融合**——可视化高效+所见即所得，自然语言灵活+零门槛，充分发挥各自优势。

---

## 四、关键认知

1. **低代码仍是银弹**：大模型之前，可视化单一武器已让低代码风生水起；大模型带来自然语言新工具，恰好解决可视化内秉缺陷
2. **AIGC 中的 C 在低代码领域 = Code**：大模型和低代码的输出都是 Code，表面竞对实则互补
3. **自然语言三大价值**：①处理逻辑性任务的合适手段 ②替代部分可视化编辑，显著降低开发工作量 ③提升编辑器整体易用性
