# 24｜践行组装式架构设计，低代码平台的三个时态

> **核心问题**：低代码平台功能日益丰富后不可避免地臃肿，如何通过架构治理实现模块化拆分，使其适合云原生组装？
> - 拆分依据：**应用开发生命周期**（开发 → 测试 → 运行）。

---

## 一、为何要拆分？

### 1.1 可组装技术原则

| 原则 | 说明 |
|------|------|
| 模块化 | 系统由独立模块组成，每个模块有明确职责和边界 |
| 互操作性 | 模块通过标准化接口通信，不同环境无缝集成 |
| 复用性 | 模块可在不同项目和场景中重复使用 |
| 灵活性 | 组合不同模块，快速响应变化的业务需求 |

### 1.2 云原生与可组装的关系

- 云原生 → 提供**技术基础**（构建和运行现代应用）
- 可组装 → 提供**设计原则**（模块化和灵活性）
- 两者结合 → 构建、部署和管理复杂系统更高效灵活

云原生关键里程碑：2013 Docker 发布 → 2019 Service Mesh 成熟 → 2022 云原生技术逐渐成熟。

---

## 二、三个时态

以**应用开发生命周期**为业务流拆分依据：

### 2.1 开发时（Design Time）

- 可视化开发工具创建/迭代应用
- 拖拽组件、配置业务逻辑和数据模型
- **低代码平台的核心功能**（专栏前20讲的内容）
- ⚠️ 设计时与运行时**必须在架构设计之初就分开**，后期拆分几乎不可能

### 2.2 测试时（Test Time）

- 新功能测试 + 已有功能回归测试
- 自动化测试 + 手动测试结合
- 专栏21~23讲详细讨论的实现方法

### 2.3 运行时（Runtime）

- 部署到生产环境，监控运行状态
- 持续优化，改进功能和用户体验
- **最轻量部署**：极限情况只需 0.1 CPU、50M 内存

### 2.4 五种部署套餐

| 套餐 | 组成 | 适用场景 |
|------|------|----------|
| 全家桶 | 设计时 + 测试时 + 运行时 | 重度低代码应用；公司内效率工具部署 |
| 商用标准 | 设计时 + 运行时 | 对外商用；零代码开发简单场景，不需测试 |
| 仅运行时 | 运行时 | 外场部署；应用在内网全家桶开发，外场只需运行 |
| 仅测试时 | 测试时 | DevOps 流水线；代码仓库取出应用代码自动化测试 |
| 测试+运行 | 测试时 + 运行时 | 类似套餐四，但自动化测试依赖外部业务系统或数据 |

> 设计时一般无法独立部署（开发时的试错需要运行时辅助）。

## 三、如何拆分？

### 3.1 前提：抽象层级

回顾第06讲的代码生成器与编辑器关系层级：

| 层级 | 说明 | 能否拆分 |
|------|------|----------|
| Level 1 | 没有代码生成器或极其粗糙 | ❌ |
| Level 2 | 有相对独立模块但与编辑器耦合严重 | ❌ |
| **Level 3** | **代码生成器与编辑器基本独立** | ✅ |
| Level 4 | 插件系统与生态 | ✅ |

**至少达到 Level 3 才能拆分**。Level 1/2 下设计器与运行时严重耦合 → 解耦合是拔出萝卜带出泥 → 难度大且不直接产生业务价值 → 往往不了了之。

### 3.2 拆分步骤

**第一步**：将各时态的硬耦合重叠部分**抽出为共享库** → 时态之间无直接依赖，只依赖库。

```
拆分前：三个圈有重叠（硬耦合）
拆分后：三个独立圈 + 共享库层
```

**第二步**：修改编译脚本，将编译制品从一个单体拆为**3 个独立制品**。

**第三步**：解除单体模式下的**直接代码调用** → 改为**软依赖**。

### 3.3 软依赖的实现

| 方式 | 说明 |
|------|------|
| HTTP API 调用 | 推荐；几乎所有基础软件都支持 HTTP，对浏览器友好 |
| 事件驱动（Kafka/MQ） | 有基础设施时可选 |

**软依赖的优势**：编译时无感，仅在运行时产生作用 → 编译顺序无关 → 容易打桩和模拟 → **即认为是松耦合**。

---

## 四、拆分收益

1. 各时态内部依赖关系得到治理，逻辑关系更清晰
2. 各时态各司其职，边界清晰，范围明确
3. 符合**组装式设计原则** → 5 种套餐按需部署 → 节约 CPU 和内存 → 降低运营成本
4. 具备向**云原生架构**演进的基础 → 获得云原生技术栈支持
