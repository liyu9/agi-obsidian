## 一、Agent创建与配置

### 流程环节说明
Agent是Hify的核心业务模块，比Provider复杂得多。课程展示了复杂业务模块的拆解策略和增量交付方法。

### 课程原文内容

#### 1.1 复杂业务拆解

课程中展示的拆解思路：

> "Provider 模块是标准的 CRUD，接口清晰，数据模型简单。Agent 模块不一样——它和 Provider、Model、Knowledge、MCP 都有关系，还有 Prompt 模板和 LLM 参数配置，表面上是 CRUD，实际上是多模块关联 + 业务规则。

先搞清楚 Agent 和其他模块的关系：

> "Claude Code 给了一张依赖关系图：Agent 引用 ModelConfig（一个 Agent 绑一个模型），ModelConfig 引用 Provider（模型来自哪个提供商），Agent 可以关联多个 Knowledge Base（RAG 用），Agent 可以关联多个 Tool（MCP 工具调用用）。"

#### 1.2 策略模式实现

课程中展示的重构过程：

**原始代码（if-else）**：
```java
if (type.equals("openai")) {
    // 调用 OpenAI API
} else if (type.equals("anthropic")) {
    // 调用 Anthropic API
} else if (type.equals("ollama")) {
    // 调用 Ollama API
}
```

**重构后（策略模式）**：
```java
// 每个供应商一个 Adapter
public interface LlmProviderAdapter {
    ChatResponse chat(ChatRequest request);
    SseEmitter streamChat(ChatRequest request, SseEmitter emitter);
    ConnectionTestResult testConnection(String baseUrl, Map<String, String> authConfig);
    List<Model> listModels(String baseUrl, String apiKey);
}

// 自动注册，按 type 分发
@Component
public class LlmProviderAdapterFactory {
    private final Map<String, LlmProviderAdapter> adapters;
    
    public LlmProviderAdapter getAdapter(String type) {
        LlmProviderAdapter adapter = adapters.get(type);
        if (adapter == null) {
            throw new BizException(ErrorCode.PROVIDER_TYPE_NOT_SUPPORTED);
        }
        return adapter;
    }
}
```

#### 1.3 三层配置结构

课程中定义的三档配置：

**基础配置层**
```json
{
  "name": "智能客服",
  "description": "通用客服场景",
  "modelConfigId": 1,
  "temperature": 0.7,
  "maxTokens": 2000
}
```

**LLM参数层**
```json
{
  "temperature": 0.7,  // 创意程度 0-2
  "topP": 0.9,
  "maxTokens": 2000,
  "presencePenalty": 0,
  "frequencyPenalty": 0,
  "stopSequences": [" челове", "Done"]
}
```

**高级配置层**
```json
{
  "systemPrompt": "你是Hify的智能客服...",
  "maxContextTurns": 10,
  "enableRag": true,
  "ragTopK": 3,
  "enableTools": true
}
```

#### 1.4 增量交付策略

课程中的交付顺序：
```
1. Agent CRUD（最简单，先跑通）
2. 关联 Provider（下拉选，级联拉模型列表）
3. Prompt 模板（textarea）
4. LLM 参数（Slider + NumberInput）
5. 关联 Knowledge Base（多选）
6. 关联 MCP Tools（多选）
7. 前端 Chat 页集成（选 Agent）
```

## 二、对话引擎认知

### 流程环节说明
在动手之前先建立认知。课程通过咨询模式帮助理解对话引擎是什么、和普通HTTP接口的区别。

### 课程原文内容

#### 2.1 对话引擎的四大职责

> "会话管理。用户和智能客服聊了十轮，这十轮属于同一次对话。对话引擎要维护'会话'的概念。"

> "上下文拼装。LLM 本身没有记忆。你问完'Hify 怎么创建 Agent'，再问'那怎么配置模型'，LLM 不知道'那'指的是什么。对话引擎要把 System Prompt + 历史消息 + 当前消息拼成一个完整的 messages 数组。"

> "流式响应。LLM 生成一个完整回复可能要十几秒。如果等全部生成完再返回，用户要盯着空白页面干等。对话引擎要做流式推送，LLM 生成一个字就推一个字给前端。"

> "消息存储。对话结束后，用户消息和 AI 回复要持久化到数据库。"

#### 2.2 普通接口 vs 对话引擎

> "普通接口是请求-响应模式，一来一回就结束。对话引擎是长连接+流式，请求发出后，响应不是一次性返回的，而是一个字一个字持续推送，可能持续几十秒甚至一两分钟。"

#### 2.3 为什么不让前端直接调LLM API

课程中Claude Code的分析：

> "API Key 暴露在前端不安全。每个 LLM 供应商的 API 格式不同，前端要适配多套格式。没有上下文管理，前端每次要自己拼历史消息传给 LLM。"

## 三、流式技术选型

### 流程环节说明
流式响应是对话引擎的技术核心。课程详细对比了SSE和WebSocket，并讲解了SseEmitter的原理和坑。

### 课程原文内容

#### 3.1 SSE vs WebSocket

| 对比项 | SSE | WebSocket |
|--------|-----|-----------|
| 通信方向 | 单向（服务端推） | 双向 |
| 适用场景 | AI对话（发消息POST，收回复流） | 聊天（双方都要发消息） |
| 复杂度 | 低 | 高 |
| 业界选择 | OpenAI、Anthropic、Dify | - |

> "AI 对话就是'客户端发一条消息，服务端流式回复'，典型的单向推送。用户发消息走普通 POST 请求就行，不需要双向通信。WebSocket 的双向能力在这里完全用不上。"

#### 3.2 SseEmitter工作原理

课程中展示的线程切换模型：

```
Tomcat 线程:
  创建 SseEmitter(120s) → 提交任务给 llmExecutor → return emitter
  （线程释放，可以处理其他请求）

llmExecutor 线程:
  调用 LLM stream API → 收到 delta → emitter.send(delta)
                       → 收到 delta → emitter.send(delta)
                       → 收到 [DONE] → 存消息 → emitter.complete()
```

课程强调：
> "这就是为什么 10 讲要配独立的 llmExecutor 线程池。LLM 调用在自己的池子里跑，不占 Tomcat 线程，管理页面不受影响。"

#### 3.3 SseEmitter三个坑

课程中Claude Code特别提醒：

**坑1：超时**
> "SseEmitter 默认超时 30 秒。LLM 生成一个长回复可能要一两分钟，30 秒一到连接直接断了。必须设长，`new SseEmitter(120_000L)`。"

**坑2：客户端断开**
> "用户对话到一半关了浏览器标签页，HTTP 连接断了。但 llmExecutor 线程不知道，它还在调 LLM，每收到一个 delta 就 `emitter.send()`，直到 IOException。必须在 send 的 catch 里停止 LLM 调用并释放线程。"

**坑3：Nginx缓冲**
> "Nginx 默认会缓冲上游响应，收集一批数据后才一次性发给客户端。结果用户看到的是'等了十几秒突然全部内容一起出现'，流式效果完全失效。必须关掉缓冲："

```nginx
location /api/ {
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 120s;
}
```

#### 3.4 事务不跨SseEmitter

> "@Transactional 方法里不要直接返回 SseEmitter，事务提交时机和流结束时机不同，会导致事务提前提交或连接超时。要把写消息的操作拆成独立方法调用。"

## 四、上下文管理

### 流程环节说明
上下文管理是对话引擎的核心挑战。课程讲解了上下文的本质和各种管理策略。

### 课程原文内容

#### 4.1 上下文的本质

> "LLM 本身没有记忆。每次调用都是无状态的，你上一轮告诉它'我的订单号是 12345'，下一轮它完全不知道。"

> "'记忆'是对话引擎通过拼装历史消息实现的。每次调用都把历史消息重新塞进请求里，让模型在同一次推理中'看到'历史，造成记得的假象。"

#### 4.2 上下文窗口问题

> "上下文窗口有限。模型能处理的 messages 总长度有上限，叫 context window，单位是 token。超出窗口直接报错或截断。而且 token 是要花钱的，历史越长，每次调用越贵。"

#### 4.3 管理策略对比

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 全量保留 | 所有历史都塞进去 | 不丢信息 | 超窗口/贵 |
| 滑动窗口 | 只保留最近N轮 | 简单/可控 | 早期信息丢失 |
| Token预算 | 按token数裁剪 | 精确控制 | 实现复杂 |
| 摘要压缩 | LLM总结历史 | 信息密度高 | 延迟/成本 |

课程选择滑动窗口，理由：
> "20-50 人内部使用，对话不会特别长。maxContextTurns 已经在 Agent 表上配置了，每个 Agent 可以独立调整。Redis List 天然支持 RPUSH 新消息，超出时 LPOP 旧的，实现十行以内。"

## 五、对话存储三层分工

### 流程环节说明
对话历史存在哪？课程清晰地区分了Redis、MySQL、pgvector三者的分工。

### 课程原文内容

#### 5.1 三层分工

**MySQL：持久化存储**
> "数据的 source of truth。存全量对话记录，用户查看历史聊天、管理员做数据分析、Redis 缓存失效后的数据来源，都从 MySQL 查。"

**Redis：工作内存**
> "专门用于组装 LLM 请求。存最近 maxContextTurns 轮消息，ChatService 每次收到消息，直接从 Redis 取最近 N 轮拼入 messages 数组发给 LLM。读写 O(1) 毫秒级，TTL 2 小时到期自动清理。"

**pgvector：不存对话历史**
> "pgvector 在 Hify 里的角色是 RAG 知识库，不是用来存对话历史的。很多初学者容易混淆'对话记忆'和'知识检索'。"

#### 5.2 Cache-Aside模式

```
// 读上下文
List<ChatMessage> history = redis.get(sessionKey);
if (history == null) {
    // 冷启动：从 MySQL 加载最近 N 条，回写 Redis
    history = chatMessageMapper.selectRecent(sessionId, maxContextTurns * 2);
    redis.set(sessionKey, history, Duration.ofHours(2));
}
```

## 六、复杂前端交互

### 流程环节说明
对话页面的前端比管理页面复杂得多。课程提出了"复杂度分层"的方法论。

### 课程原文内容

#### 6.1 复杂度分层

> "复杂页面需要拆解，拆解的顺序有三层，有顺序依赖：
> - **结构层**：页面长什么样，组件怎么排列
> - **行为层**：用户做了什么，页面发生什么
> - **细节层**：动画速度、样式微调、边界处理"

> "乱了顺序就会返工——结构没对齐就去写行为，行为写完了布局改了，整个组件重来。"

#### 6.2 草稿图对齐结构

课程中展示的两种做法：

**做法一：截参考图**
> "打开 ChatGPT 或 Claude 的对话页面，截一张图，上传给 Claude Code：参考这张图的整体布局。左侧会话列表，右侧聊天窗口，底部固定输入框。"

**做法二：手绘草稿**
> "如果你想要的布局和现有产品不一样，画一张低保真草稿，矩形框标注区域名称就够了，不需要精确尺寸。"

关键步骤：
> "先让 Claude Code 描述它的理解。如果它说的和你想的一致，直接说'正确，开始实现'。如果有偏差，在这里纠正，比写完代码再改成本低得多。"

#### 6.3 两类交互描述方式

**静态交互：四维度描述**
```
布局：顶部操作栏（标题 + 新增按钮），主体是列表表格
数据：展示 name、type、status，status 用标签区分
交互：点新增弹出表单弹窗，字段包括...
接口：GET /api/v1/providers 查列表...
```

**动态交互：时间线描述**
```
发送消息的完整时间线：
1. 用户点发送，输入框立刻清空，发送按钮变为不可点击
2. 消息区域底部出现用户气泡（靠右，深色背景）
3. 紧接着出现 AI 气泡（靠左，浅色背景），内容为空，显示加载动画
4. 前端用 fetch 手动处理 SSE 流（不要用 EventSource，接口是 POST）
5. 每收到一个 delta chunk，追加到 AI 气泡，滚动到底部
6. 收到 done 事件，加载动画消失，发送按钮恢复
```

课程强调：
> "SSE over POST 是做 AI 对话产品几乎必踩的坑，在时间线描述里显式说明，一句话避开。"

#### 6.4 增量调整

课程中的调整格式：

差的调整：
> "帮我改一下，这个不太对"

好的调整：
> "当前打字机效果每字符间隔 50ms，感觉太快，改成 30ms，其他不变。"

> "AI 消息气泡没有渲染 Markdown，引入 marked.js 把 content 渲染成 HTML，代码块用等宽字体，其他样式保持。"

课程总结：
> "每个提示词描述一件事，明确原来是什么、现在改成什么。几轮下来，细节就到位了。"
