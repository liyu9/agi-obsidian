### 2.2 CLAUDE.md 臃肿的根因与解法

**症状**：
- 文件超过 200 行
- 大量"步骤 1/2/3"的流程
- Claude Code 开始忽略靠后内容

**根因**：把两类内容混在一起
- ❌ **任务流程**（放 Skills）：单测流程、集成测试步骤
- ✅ **全局规范**（放 CLAUDE.md）：代码风格、禁止事项

**解法**：先问这个问题
```
"这句话是全局规范，还是任务流程？"
  ↓
  全局规范 → CLAUDE.md
  任务流程 → Skills
```

**正确的目录结构**：
```
.claude/
├── CLAUDE.md              # 精简的全局规则
└── skills/
    ├── unit-test.md       # 单测流程
    ├── integration-test.md # 集成测试流程
    └── api-doc.md         # API文档流程
```

## 三、Spec-Kit 详解

### 3.1 Spec-Kit 核心概念

把"规范"从 Markdown 自由文本升级为有结构的规范文件：
- Claude Code 能更精确地解读
- 支持版本管理
- 与 Skills 体系无缝对接

### 3.2 目录结构

```
spec/
├── project.spec.md           # 项目级规范
├── modules/
│   ├── chat.spec.md         # 对话模块规范
│   └── provider.spec.md     # Provider模块规范
└── tasks/
    ├── unit-test.task.md    # 单测任务规范
    └── api-doc.task.md      # 文档任务规范
```

### 3.3 规范文件示例

```markdown
# 对话模块规范

## 职责边界
- 负责：对话会话管理、消息收发、上下文管理、SSE流式输出
- 不负责：LLM调用细节（Provider模块）、知识库检索（Knowledge模块）

## 接口规范
- 所有接口返回 Result<T>，HTTP状态码统一200
- 流式接口使用SSE，Content-Type: text/event-stream
- 事件格式：{"type":"delta"|"done"|"error","content":"..."}

## 数据约束
- sessionId：Long类型，不对外暴露自增规律
- 消息内容：最大4096字符，超出截断

## 禁止事项
- 禁止在ChatServiceImpl直接调用OpenAI SDK
- 禁止在Service层直接写SQL
- 禁止吞掉LLM调用异常

## 测试要求
- 核心链路必须有集成测试覆盖
- LLM调用使用MockProviderAdapter
```

### 3.4 与 Claude Code 结合使用

```markdown
读取 spec/modules/chat.spec.md，
基于这份规范，帮我实现ChatService的createSession方法。
输出前先确认：你理解的职责边界和禁止事项是什么？
```

Claude Code 会先复述规范，确认后再写代码 → 规范先行的输出质量更高。

## 四、Spec Coding 工作流

### 4.1 Spec Coding 本质

> 不是工具，是工作方式：**先写规范，再让 AI 执行**

```
规范（输入） ──→ AI执行 ──→ 代码（输出）

规范写得好 → 代码少改
```

### 4.2 完整流程示例：对话导出PDF功能

#### 方式一：直接执行（不推荐）

```
帮我给Hify加一个对话导出为PDF的功能。
```

问题：Claude Code 做了假设，但你不确定这些假设对不对
- 导出哪些字段？
- PDF样式是什么？
- 同步还是异步？
- 接口在哪个Controller？

#### 方式二：Spec Coding（推荐）

**第一步：写规范**

```
我要给Hify加"对话导出为PDF"功能，在写代码之前，
帮我把这个功能的规范写清楚。
需要包含：
1. 功能边界：导出什么，不导出什么
2. 接口设计：请求/响应格式，同步还是异步
3. 数据约束：对话长度限制，文件大小限制
4. 错误处理：哪些情况返回错误，错误码是什么
5. 对现有模块的影响
输出spec格式，不要写代码。
```

**第二步：Review规范**

Claude Code 输出的规范包含：
- 同步接口（理由：目标规模20-50人，并发不大）
- 错误码直接对应HTTP状态码
- 建议用 `flying-saucer-pdf-openpdf`（无iText授权问题）
- PDF生成用 `asyncExecutor` 线程池

**第三步：确认后执行**

```
规范已确认（见上方）。现在按这份规范实现导出功能。
技术约束：
- 使用flying-saucer-pdf-openpdf生成PDF
- 异步任务用Spring @Async
- 任务状态存Redis，key: export:task:{taskId}，TTL 1小时
```

### 4.3 适用场景

| 场景 | 建议方式 |
|------|----------|
| 复杂功能（>3个文件改动） | Spec Coding |
| 有不确定性的需求 | Spec Coding |
| 涉及外部系统集成 | Spec Coding |
| 简单CRUD | 直接执行 |

## 五、老项目改造

### 5.1 改造的本质

> **改造的本质是降低风险，不是追求完美**

不需要把整个代码库改造成教科书级别
只需要：**每次改动时，这个文件比改之前稍微好一点**

### 5.2 三种错误方式

```
❌ 错误1：推倒重来
   - 几乎从来不是对的答案
   - 代价太高，风险太大

❌ 错误2：大重构项目
   - 暂停新功能3个月
   - 企业里几乎不可能成功
   - 中途被叫停 / 引入大量新bug / 团队士气崩溃

❌ 错误3：先改代码，再补测试
   - 不知道现有代码的"正确行为"是什么
   - 可能修掉了下游依赖的"bug行为"
```

### 5.3 三大核心原则

```
┌─────────────────────────────────────────────────────────────┐
│                   老项目改造三原则                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  原则1：摸底先于动手                                         │
│  ├── 不要凭经验猜现状                                        │
│  ├── 让Claude Code读完代码给出客观报告                        │
│  └── 具体到文件名和行号                                      │
│                                                             │
│  原则2：先补安全网，再做改造（顺序不能反）                     │
│  ├── 先写集成测试锁住现有行为                                 │
│  ├── 测试通过 = 现状已记录                                   │
│  ├── 然后再重构                                              │
│  └── 全绿表示外部行为没有变化                                │
│                                                             │
│  原则3：童子军规则，渐进改造                                  │
│  ├── 每次动到哪个文件，顺便对齐规范                           │
│  ├── 不需要专门的大重构项目                                  │
│  └── 可持续的方式                                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.4 关键提示词

**摸底报告**：
```
读完这个项目的所有代码，给我一份现状报告。
包含：
1. 模块职责是否清晰，哪些地方存在职责混乱
2. 命名风格是否统一，有哪些不一致的模式
3. 高风险代码：圈复杂度高的方法、没有超时处理的外部调用、可能的SQL注入点
4. 测试覆盖情况：哪些核心链路没有测试保护
每个问题给出具体的类名/方法名，不要泛泛而谈。
```

**集成测试规划**：
```
基于现状报告，帮我规划[模块名]的集成测试清单。
目标是锁住现有行为，不是验证"正确行为"。
如果代码有明显的bug，先把现有行为记录下来。
每条测试给出：测试场景、输入数据、期望输出（基于现有代码的实际行为）。
先给清单，不要写代码。
```

**童子军修复**：
```
在实现这个功能的同时，对我们正在修改的文件做以下对齐：
1. 命名风格统一为CLAUDE.md里的规范
2. 把Service层里的SQL拼接移到Mapper的XML里
3. 裸露的catch(Exception e) {}改成打WARN日志
4. 方法超过50行的，如果逻辑清晰可拆分，顺手拆一下
不要改这个文件之外的代码，不要引入新依赖。
```

### 5.5 改造节奏

| 预期 | 说明 |
|------|------|
| 周期 | 3-6个月（有5年历史的中型项目 → 规范覆盖率80%） |
| 节奏 | 每周固定一个改造session + 日常顺手修复 |
| 成本 | 期间团队正常交付新功能 |

```
│  第2层：规范/流程层                                         │
```

### 6.2 编码助手对比

| 工具 | 优势 | 劣势 | 适合场景 |
|------|------|------|----------|
| **Claude Code** | 跨文件能力强、Agent能力最强 | 无IDE集成 | 复杂任务、搭骨架、重构 |
| **Cursor** | IDE集成、多模型切换、Tab补全好 | 复杂任务能力弱于CC | 日常迭代、单文件修改 |
| **Copilot** | GitHub生态成熟、企业管理完善 | 功能相对基础 | 已在GitHub Enterprise的团队 |
| **Windsurf** | 轻量、快速上手 | 功能有限 | 快速原型、个人项目 |

**推荐组合**：Claude Code + Cursor（一个月40美元）

### 6.3 工具选型判断框架

```
你现在最痛的问题是什么？

代码生成质量不够好？
  → 90%是规范问题，不是工具问题
  → 先检查CLAUDE.md写得够不够清晰

不知道选Claude Code还是Cursor？
  → 两个都用
  → 复杂任务用CC，日常迭代用Cursor

团队规范不一致？
  → Spec-Kit

企业有合规要求？
  → Kiro

CI/CD质量保障？
  → 先用GitHub Actions自己搭
  → 团队>20人、部署>5次/天再评估Harness

多个团队用LLM，成本失控？
  → AI Gateway

AI应用上线后出了问题不知道怎么排查？
  → LangSmith/Langfuse
```

## 七、课程终极复盘（文章32）

### 7.1 Vibe Coding 的本质

> **是驾驭，不是依赖**

```
┌─────────────────────────────────────────────────────────────┐
│                   Vibe Coding 两种模式                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ❌ 无积累的Vibe Coding：                                    │
│  ├── Claude Code给了5个方案，不知道选哪个                    │
│  ├── 生成了代码，看不出哪里有隐患                             │
│  ├── 问你"用Redis还是MySQL"，没有判断依据                    │
│  └── 结果：AI在驾驭你                                        │
│                                                             │
│  ✅ 有积累的Vibe Coding：                                     │
│  ├── 知道场景的约束条件，给出有意义的限定                     │
│  ├── 见过类似问题，知道方案哪里可能踩坑                       │
│  ├── 对领域有基本认知，能把Claude Code拉回方向               │
│  └── 结果：你在驾驭AI                                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**核心洞察**：
- AI工具是**放大器**，放大的是你已有的东西
- 你有判断力 → 好工具放大判断力
- 你没有积累 → 好工具放大错误

### 7.2 课程给了什么，没给什么

| **给了你的** | **没给你的** |
|-------------|-------------|
| 完整的项目经验（Hify全链路） | 计算机基础的厚度 |
| 可复用工作方式（咨询模式/SDD/Skills） | 垂直领域的深度 |
| 认知建立方法（领域四问法） | 大规模系统的经验 |

### 7.3 积累的方法：把Hify当作主干

```
主干的价值：让每个知识点"长在哪里"知道

├── 学数据库事务 → Hify里Redis read-modify-write的并发问题
├── 学HTTP协议 → SSE流式响应的原理
├── 学K8s健康检查 → readinessProbe/livenessProbe配置
├── 学向量数据库 → RAG管线里分块向量化
└── 学分布式系统 → 后续扩展方向

零散知识点有了锚点 → 学了能消化，不会读完就忘
```

**旁征博引，保持好奇心**：
- 遇到没想透的地方 → 往下看一层
- 今天多理解一个知识点 → 下次问Claude Code的问题质量更高
- 形成正向循环，而且会加速

### 7.4 复盘问题清单

```
停下来对照自己想一想：

1. 哪些决策你真的理解了，哪些只是看懂了？
   → 能说清"为什么这么做"的地方，是真正理解的地方

2. 哪些环节你最依赖Claude Code，几乎没有自己的判断？
   → 这些地方是知识盲区，是接下来值得投入的方向

3. 有没有哪个技术选型，当时完全跟着Claude Code走，
   现在也说不清楚为什么？
   → 把"接受了建议"变成"理解了为什么这是对的"

4. 做完Hify，你的知识盲区清单是什么？
   → 这个清单比课程任何内容都有价值
   → 它是专属你的学习路线图
```

### 7.5 好提示词的本质

> **提示词的质量，是你认知深度的外化**

```
你能问出"用Redis还是MySQL做上下文缓存"
  → 背后是你对两种存储特性的理解
```

## 九、关键要点总结

### 9.1 规范工具要点

1. **四层从轻到重**：CLAUDE.md → Skills → Spec-Kit → Kiro
2. **CLAUDE.md精简原则**：全局规范 vs 任务流程分清楚
3. **团队人数是关键变量**：1-3人用轻工具，20人+才用重工具
4. **Spec Coding是习惯**：先写规范再执行，规范写得好代码少改

### 9.2 老项目改造要点

1. **摸底先于动手**：让Claude Code给客观报告
2. **安全网优先**：先写集成测试锁住行为，再改代码
3. **童子军渐进**：每次顺手对齐，不要大重构
4. **改造是降低风险**：不需要完美，只需要每次好一点

### 9.3 工具选型要点

1. **不要追工具追问题**：你的问题是稳定的
2. **够用就好**：人少用重工具是浪费
3. **先确认现有工具是否没用到位**：大多数时候规范没建好
4. **工具是手段解决问题是目的**：最简单的工具最好用

### 9.4 认知成长要点

1. **Vibe Coding是驾驭不是依赖**：你的积累决定AI能帮你多少
2. **主干学习法**：让知识点有地方挂，学了能消化
3. **旁征博引保持好奇心**：往下看一层，形成正向循环
4. **复盘清单比内容更有价值**：那是专属你的学习路线图
