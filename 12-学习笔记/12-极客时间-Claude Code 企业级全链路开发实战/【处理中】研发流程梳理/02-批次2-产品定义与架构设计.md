## 一、产品定义

### 流程环节说明
产品定义是研发流程中最重要的环节之一。在开始编码之前，必须明确产品的边界、目标用户、技术选型和运维预期。这是架构决策的输入，也是后续所有工作的约束条件。

### 课程原文内容

#### 1.1 功能范围定义

课程中以Hify为例，展示产品定义的完整思考：

> "做 Dify 的简版，叫 Hify。目标用户是团队内部几十个人，暂时不面向外部市场。"

功能边界确定：
```
做什么：
- 模型提供商管理（多模型接入）
- Agent 配置与编排
- 对话引擎（RAG + 工具调用 + 工作流）
- 知识库（RAG）
- 简版工作流
- MCP 工具接入

不做什么：
- 多租户
- 计费系统
- 模型微调
- WebApp 发布平台
```

#### 1.2 技术栈选型

课程中展示了技术选型的决策过程：

> "技术选型上，我选的是 Spring Boot + Vue + MySQL + MyBatis-Plus + Redis + pgvector。前后端分离，单体优先，引入 pgvector 做向量存储。"

选型理由：
```
Spring Boot：Java 生态成熟，团队熟悉
Vue：前端团队现状
MySQL + pgvector：pgvector 0.5 版本后生产可用，一库两用
MyBatis-Plus：CRUD 开发效率高
Redis：缓存 + 会话存储
不选微服务：一个人维护太重，单体优先
```

#### 1.3 运维预期

课程中明确了一期的运维约束：

> "运维预期：50 人内部使用，单机部署。不需要 K8s，不需要高可用，不需要多副本。跑起来、能用、别出事。"

## 二、应用架构设计

### 流程环节说明
应用架构决定代码内部的组织方式。课程选择了"模块化单体"架构，在保持单体简单性的同时为未来扩展预留空间。

### 课程原文内容

#### 2.1 架构选型决策

课程中展示了与Claude Code的讨论过程：

Claude Code给出了三个方案对比：

> "**方案 A：按 package 分层。** 所有功能放在一个模块里，按 controller/service/mapper 分 package。最简单，但所有功能混在一起，后面代码量大了找文件费劲，想拆分也拆不动。"

> "**方案 B：Maven 多模块，按功能拆。** 一个 Spring Boot 应用，内部按 Maven 多模块组织，每个功能一个模块。模块之间通过接口调用，代码层面严格隔离。后续想拆分成微服务，只需要把接口调用改成远程调用，模块内部不用动。"

> "**方案 C：微服务。** 每个功能一个独立服务，通过网关路由，服务间 Feign 调用。"

追问环节：
> "一个人维护六七个微服务，每个要独立部署、独立配置、独立监控，精力消耗会不会太大？"

最终选择方案B（模块化单体）。

#### 2.2 模块划分

课程中确定的具体模块结构：

```
hify/
├── hify-app/               # 启动模块，Spring Boot Application
├── hify-provider/          # 模型提供商管理
├── hify-agent/             # Agent 管理与配置
├── hify-chat/              # 对话引擎
├── hify-mcp/               # MCP 工具管理与调用
├── hify-workflow/          # 工作流编排与执行
├── hify-knowledge/          # 知识库与 RAG
├── hify-common/            # 公共模块（工具类、常量、异常、DTO）
├── hify-web/               # Vue 前端
└── deploy/                 # Docker Compose 配置
```

#### 2.3 依赖关系管理

模块依赖关系的分析：

> "hify-chat 是依赖最多的模块——对话时要读 Agent 配置（依赖 hify-agent）、调模型（依赖 hify-provider）、可能走工作流（依赖 hify-workflow）、可能做 RAG 检索（依赖 hify-knowledge）、可能调工具（依赖 hify-mcp）。"

**关键原则：依赖是单向的，不能循环。**

## 三、代码组织规范

### 流程环节说明
代码组织规范是给AI看的规则。人不写代码时可以凭经验判断代码该放哪，但AI不知道，必须明确定义。

### 课程原文内容

#### 3.1 模块内部结构

每个业务模块统一的目录结构：

```
src/main/java/com/hify/{module}/
├── controller/        # REST 接口
├── service/          # 业务逻辑接口
├── service/impl/     # 业务逻辑实现
├── mapper/          # MyBatis-Plus Mapper
├── entity/          # 数据库实体
├── dto/             # 请求/响应对象
├── config/          # 配置类
├── exception/       # 模块级自定义异常
└── constant/        # 模块级常量
```

#### 3.2 分层职责边界

课程中明确定义的职责边界：

> "**Controller** 只做两件事：参数校验和调用 Service。不写业务逻辑、不做数据查询、不处理事务。"

> "**Service** 处理所有业务逻辑，包括事务管理、数据校验、业务规则。Service 之间可以互相调用，但只能调接口（interface），不能直接 new 实现类。"

> "**Mapper** 只做数据库操作。不要在 Mapper 的 XML 里写业务逻辑（比如复杂的条件判断），那是 Service 的事。"

#### 3.3 跨模块调用规则

这是模块化单体最关键的规范：

> "**跨模块调用规则：这条是模块化单体最关键的规范。** 模块之间只能通过 Service 接口调用，不能直接引用另一个模块的 Mapper、Entity 或内部类。"

原因：
> "因为我们选模块化单体的一个重要理由是'后续能拆分'。如果 hify-chat 直接引用了 hify-agent 的 Mapper，两个模块就焊死了——拆分时你要把所有这种引用找出来改成远程调用。但如果只通过 Service 接口调用，拆分时只需要把本地调用改成 HTTP/RPC 调用，接口签名都不用变。"

## 四、外部调用设计

### 流程环节说明
LLM调用是Hify最大的技术挑战。课程从线程管理、容错、超时、重试四个维度进行了系统设计。

### 课程原文内容

#### 4.1 线程池隔离

> "**线程池隔离——同意。** LLM 调用必须用独立线程池，不能和 Tomcat 的业务线程池共用。"

原因：
> "50 个并发 SSE 连接，每个持续 10-30 秒，如果共用线程池，管理页面的请求排在队列里等，用户看到的就是页面一直转圈。独立线程池解决这个问题——对话请求用自己的池子，管理请求用 Tomcat 默认的池子，互不影响。"

#### 4.2 熔断机制

> "**熔断机制——同意。** 某个 LLM 提供商连续失败时，快速熔断，后续请求直接返回错误，不浪费时间等超时。"

具体方案：
> "Claude Code 建议 Resilience4j，每个提供商独立熔断器——OpenAI 挂了不影响 Claude。"

#### 4.3 超时控制

> "**超时控制——同意，但我追问了细节。** 它建议对话接口 60 秒超时，连通性测试 10 秒。"

追问与调整：
> "流式响应场景下，一个 SSE 连接可能持续一两分钟，60 秒会不会把正常对话切断？"

最终方案：
> "SSE 连接超时设 120 秒，普通同步调用 60 秒。"

#### 4.4 重试策略

> "**重试策略——同意，细节有价值。** 不是所有失败都值得重试。网络抖动重试有意义，认证失败重试没用（重试一百次还是认证失败），限流需要退避重试（等一等再试）。"

按异常类型区分：
> "按异常类型区分重试策略，这个细节 Claude Code 给得很好。"

## 五、部署架构设计

### 流程环节说明
部署架构从第一天就在影响设计决策。课程确定了当前50人规模的部署方案，并规划了未来的演进路径。

### 课程原文内容

#### 5.1 当前部署架构

请求流转链路：

> "用户请求经 Nginx 分流，静态资源直接返回，API 请求转发给 Spring Boot，Spring Boot 按需读写 MySQL（业务数据）、Redis（缓存会话）、pgvector（向量检索）。"

#### 5.2 暂不做 vs 必须做

课程中Claude Code给出的分析：

| 必须做 | 暂时跳过 | 理由 |
|--------|----------|------|
| Docker Compose | K8s | 一期50人单机，K8s过度 |
| 限流 | 服务网格 | 单机不需要服务治理 |
| Nginx配置 | 多副本 | 单副本够用 |

## 六、性能瓶颈预判

### 流程环节说明
性能瓶颈需要提前预判，而不是等出了问题再救。课程让Claude Code基于架构图分析了可能的瓶颈点。

### 课程原文内容

#### 6.1 瓶颈分析

Claude Code按严重程度排序的瓶颈分析：

| 瓶颈 | 触发条件 | 一期处理 |
|------|----------|----------|
| LLM调用慢/超时 | 50人真实使用 | ✅ 必须处理 |
| SSE长连接占线程 | 50人真实使用 | ✅ 必须处理 |
| MySQL连接池耗尽 | 100+并发 | 暂时不管 |
| Redis内存压力 | 数据量10万+ | 暂时不管 |
| pgvector检索慢 | 数据量100万+ | 暂时不管 |

#### 6.2 一期处理策略

> "所以一期只做两件事：
> **LLM 调用设超时 + 线程隔离 + 熔断**。这是唯一能在 50 人规模下真实触发、影响所有用户的问题。
> **Nginx 开启 gzip**。成本极低（一行配置），首屏加载速度直接可感知。"

> "其他瓶颈全部标记'已知但暂不处理'。不是忽略，是时机未到。等触发条件到了（数据量上来、用户量上来），你第一时间知道该动哪里——因为这张表就是你的地图。"

## 七、扩展架构规划

### 流程环节说明
架构设计不在于现在做多复杂，在于每个决策都不堵未来的路。课程规划了三阶段的演进路径。

### 课程原文内容

#### 7.1 三个扩展阶段

**第一阶段：50 → 500人**
```
触发条件：响应变慢，CPU/内存持续告警
改什么：
- Spring Boot 从 1 副本扩到 2-3 副本
- MySQL 加读写分离（一主一从）
- 静态资源上 CDN
不改什么：整体单体架构不动，pgvector 不换
难点：SSE 连接粘连，需要 Redis 会话共享
```

**第二阶段：500 → 2000人**
```
触发条件：LLM 调用队列堆积，P99 > 2s
改什么：
- 引入消息队列（MQ）做 LLM 异步削峰
- pgvector 迁移到独立 Qdrant
- MySQL 按业务模块分库
不改什么：Spring Boot 仍是单体不做微服务拆分
难点：前端从 SSE 改成轮询或 WebSocket，是 breaking change
```

**第三阶段：2000 → 几千人**
```
触发条件：单模块发布频率互相干扰
改什么：
- 按模块拆微服务
- 引入 API Gateway
- Redis 换集群模式
不改什么：MySQL 主从不动，Qdrant 不动
难点：分布式事务，引入 Saga/TCC
```

#### 7.2 为未来留的口子

> "你应该注意到了，第 04 讲的每个设计决策都在为这条路径留口子：
> **模块化单体让第三阶段的微服务拆分成本可控，接口隔离让调用方式可以平滑切换，会话存 Redis 让第一阶段的多副本不需要改代码**。"

## 八、数据模型设计

### 流程环节说明
数据模型是系统的基础。课程梳理了约16张核心数据表，按功能域分组设计。

### 课程原文内容

#### 8.1 表结构概览

```
模型管理：
- model_provider（提供商）→ model（具体模型），一对多

知识库：
- knowledge_base → document → document_chunk，一对多链
- document_chunk 是向量化的最小单位，存在 pgvector 里

工具：
- tool，独立表，存 MCP 工具定义

Agent：
- agent 是关联最多的表
- agent → model（多对一）
- agent ↔ knowledge_base（多对多，通过 agent_knowledge_base）
- agent ↔ tool（多对多，通过 agent_tool）

工作流：
- workflow → workflow_node，一对多
- workflow_node 里的 LLM 节点关联 model

对话：
- conversation → message，一对多
- conversation 关联 agent 或 workflow
- message → document_chunk（多对多，通过 message_reference）

用户：
- user 和 api_key
```

#### 8.2 message_reference 表的设计价值

> "message_reference 这张表，它记录的是"这条 AI 回复引用了知识库的哪些片段"。很多人做 RAG 不存这个关系，回复完就丢掉了检索结果。但存下来有两个好处：一是用户可以看到"AI 的回答依据是什么"，增加可信度；二是后续优化 RAG 效果时，可以回溯分析检索质量。"

## 九、数据库性能规范

### 流程环节说明
数据库规范是给AI看的规则。AI不会自动遵守索引原则、分页规范等，需要明确定义。

### 课程原文内容

#### 9.1 通用字段约定

```
所有表必须包含四个公共字段：
id          BIGINT          NOT NULL AUTO_INCREMENT PRIMARY KEY,
created_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at  DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
deleted     TINYINT(1)      NOT NULL DEFAULT 0
```

硬规矩：
> "主键用自增 BIGINT，禁止 UUID（索引性能差）。禁止用 NULL，业务空值用空字符串或 0 代替。金额和 Token 用量用 BIGINT 存最小精度，不用 DECIMAL。枚举字段用 VARCHAR(32)，不用 MySQL ENUM 类型。"

#### 9.2 索引设计原则

**第一条：逻辑删除字段必须加进索引。**
```
-- ✅ 正确
INDEX idx_agent_user (user_id, deleted)
-- ❌ 不够
INDEX idx_agent_user (user_id)
```

**第二条：组合索引等值列在前，范围列在后。**
```
INDEX idx_message_conv_time (conversation_id, created_at)
```

**第三条：多对多关联表两个方向都要索引。**

#### 9.3 分页查询规范

```
-- ❌ 禁止 OFFSET 深分页，百万行时极慢
SELECT * FROM message ORDER BY id DESC LIMIT 20 OFFSET 100000;

-- ✅ 用游标分页
SELECT * FROM message
WHERE conversation_id = ?
  AND id < #{lastId}
  AND deleted = 0
ORDER BY id DESC
LIMIT 20;
```

#### 9.4 pgvector规范

```
-- 必须建 HNSW 索引，否则全表扫描
CREATE INDEX idx_embedding_hnsw
ON vector_chunk
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

硬规矩：
> "必须建 HNSW 索引（一期数据量小感知不到差异，但数据量上来后，没索引检索会从毫秒级变成秒级）。检索时必须加 LIMIT，禁止不加 LIMIT 的向量查询。"

## 十、CLAUDE.md规范体系

### 流程环节说明
CLAUDE.md是AI辅助开发的核心基础设施。它不是一次性写完的，而是在开发过程中渐进完善的。

### 课程原文内容

#### 10.1 五层结构

课程中定义的五层规范体系：

```
第一层：项目上下文（03讲）—— 项目概述、功能边界、目标用户
第二层：架构规范（04讲）—— 模块划分、依赖关系、外部调用处理
第三层：代码组织（04讲）—— 分层结构、Controller/Service/Mapper职责
第四层：部署与数据库（05讲）—— 部署架构、索引规则、分页规范
第五层：接口与行为（06讲）—— 接口规范、错误码、行为指令
```

#### 10.2 接口契约

模块级接口蓝图示例：

```
# Provider 模块接口契约
GET /api/v1/providers
  描述：分页查询提供商列表
  参数：page, pageSize, name(可选，模糊搜索)
  响应：Result<PageResult<ProviderListResp>>

POST /api/v1/providers
  描述：创建提供商
  请求体：ProviderCreateReq { name, type, apiKey, baseUrl }
  响应：Result<Long>

DELETE /api/v1/providers/{id}
  描述：删除提供商（需检查是否有 Agent 在使用）
  响应：Result<Void>

POST /api/v1/providers/{id}/test-connection
  描述：测试连通性
  响应：Result<ConnectionTestResp>
```

#### 10.3 行为指令

容易被忽略但最有价值的部分：

```
## 行为指令
### 写代码时
- 每个功能用最简单直接的方式实现
- 不引入不必要的设计模式，除非我明确要求
- 不做过度抽象
- 不引入技术栈以外的依赖，需要时先问我
- 所有外部调用必须有超时设置
- 配置项外化到 application.yml，不硬编码

### 改代码时
- 先理解相关模块的设计意图
- 不要为了新功能破坏已有接口契约
- 改完确保已有测试通过

### 不确定时
- 架构选择给我 2-3 个方案对比，我来拍板
- 规范没覆盖的情况，先问我，不要自己编规矩
```
