## 一、工作流执行引擎

### 流程环节说明
工作流执行引擎是让静态配置真正运转起来的核心组件。课程展示了完整的实现过程。

### 课程原文内容

#### 1.1 执行引擎概念

> "食谱放在那里什么都不会发生，厨师拿到食谱才能把菜做出来。工作流配置就是食谱，执行引擎就是厨师。"

执行引擎的职责：
> "从数据库加载22讲存的那份配置，构建nodeMap + edgeMap，然后从起始节点开始一个节点一个节点地执行，最终结果通过SseEmitter推给用户。"

#### 1.2 业界调研选方案

课程中展示的技术调研流程：

Claude Code调研了四个平台：

| 平台 | 线程模型 | 上下文传递 | 执行记录 |
|------|----------|------------|----------|
| Dify | 线程池+就绪队列 | VariablePool | 两层持久化 |
| n8n | 多Worker+Redis队列 | 消息队列 | 有 |
| Coze | Go goroutine | - | 有 |
| Temporal | 事件溯源状态机 | 检查点恢复 | 完整回放 |

课程选择理由：
> "n8n的Redis Queue是为多Worker水平扩展设计的，Hify面向小规模团队。Temporal是为小时/天级工作流设计的，Hify的工作流最长几十秒。Dify的代码沙箱是为用户自定义代码节点设计的，Hify的节点类型是固定的几种。"

#### 1.3 ExecutionContext变量池

课程中展示的Dify VariablePool模式：

```java
public class ExecutionContext {
    private final Map<String, Object> variables = new LinkedHashMap<>();
    
    // 变量池只增不改，历史输出不会被改掉
    public void set(String nodeKey, String varName, Object value) {
        variables.put(nodeKey + "." + varName, value);
    }
    
    // {{classify.intent}} 运行时替换
    public String resolve(String template) {
        String result = template;
        for (Map.Entry<String, Object> entry : variables.entrySet()) {
            result = result.replace("{{" + entry.getKey() + "}}",
                entry.getValue() != null ? entry.getValue().toString() : "");
        }
        return result;
    }
}
```

Context累积过程：
> "classify节点执行后，ctx里有classify.intent=售后；router节点执行后，ctx里有router.route=true；aftersale节点执行时，prompt里的{{router.route}}已经被替换成true。"

#### 1.4 NodeExecutor体系

课程中展示的统一接口+策略模式：

```java
public interface NodeExecutor {
    void execute(WorkflowNode node, NodeConfigDef config, ExecutionContext ctx);
    String nodeType();
}

// Spring自动注册，按type分发
@Component
public class NodeExecutorRegistry {
    private final Map<String, NodeExecutor> executors;
    
    public NodeExecutor get(String type) {
        NodeExecutor executor = executors.get(type);
        if (executor == null) {
            throw new BizException(ErrorCode.WORKFLOW_NODE_TYPE_UNKNOWN);
        }
        return executor;
    }
}
```

## 二、MCP协议认知

### 流程环节说明
MCP（Model Context Protocol）是让Agent能调用外部工具的标准化协议。课程从需求出发解释MCP的价值。

### 课程原文内容

#### 2.1 为什么需要MCP

> "更麻烦的是，LLM怎么知道有哪些工具可用？你得手动写进Prompt，'你可以查订单，API是这个，参数是那个'。每接一个新系统，就要改Prompt。"

> "MCP之前，M个AI平台 × N个工具 = M×N套适配代码。MCP之后，工具开发者只写一个Server，任何支持MCP的平台都能接 = M+N。这和USB解决的问题一样。"

#### 2.2 MCP三个核心概念

| 概念 | 说明 |
|------|------|
| MCP Server | 工具提供方，声明自己有哪些工具 |
| MCP Client | 工具调用方（Hify），统一方式发现和调用 |
| Tool Schema | 每个工具的标准描述，LLM通过schema知道有哪些工具可用 |

#### 2.3 Function Calling机制

课程中展示的两次LLM调用：

**第一次LLM调用**：判断要不要调工具
```json
{
  "finish_reason": "tool_calls",
  "message": {
    "tool_calls": [{
      "id": "call_abc123",
      "function": {
        "name": "query_order",
        "arguments": "{\"userId\": \"u001\", \"orderId\": \"12345\"}"
      }
    }]
  }
}
```

**第二次LLM调用**：基于工具结果生成回答
```json
{
  "finish_reason": "stop",
  "message": {
    "content": "您的订单12345已发货，预计明天送达。"
  }
}
```

课程强调：
> "description写得好不好，直接决定LLM选工具的准确率。这是MCP工具开发里最重要的地方。"

## 三、MCP Client选型

### 流程环节说明
课程展示了Java生态的MCP Client SDK对比和选型决策。

### 课程原文内容

#### 3.1 三个选项对比

| 选项 | 成熟度 | 文档 | Spring兼容性 |
|------|--------|------|--------------|
| 官方Java SDK | ⭐⭐⭐⭐ | 官方文档 | ⭐⭐⭐⭐⭐ |
| Spring AI MCP | ⭐⭐⭐ | 依赖Spring AI文档 | ⭐⭐⭐⭐⭐ |
| SSE Transport Only | ⭐⭐ | 社区 | ⭐⭐ |

#### 3.2 选型决策

课程选择官方Java SDK，理由：
> "Spring AI MCP的设计假设是你用Spring AI的整套抽象层。Hify已经有自己的一套：ProviderAdapter适配各LLM、LlmHttpClient做HTTP通信、ChatServiceImpl管对话流程。引入Spring AI MCP意味着两套抽象互相摩擦，不值得。"

课程中的技术决策：
> "官方SDK的HttpClientSseClientTransport有资源泄漏issue，每次build一个新的HttpClient实例，没有正确关闭。规避方式：按调用创建，用完关闭，不长期持有client对象。"

```java
// 每次调工具：建连 → 调用 → 关闭
try (McpSyncClient client = buildClient(server.getEndpoint())) {
    client.initialize();
    return client.callTool(new CallToolRequest(toolName, arguments));
}
```

## 四、自建MCP Server

### 流程环节说明
当没有现成的MCP Server可用时，需要自建。课程展示了从业务场景推导工具设计的完整过程。

### 课程原文内容

#### 4.1 什么时候自建

| 情况 | 方案 |
|------|------|
| 内部系统无公开Server | 自建 |
| 有公开Server但需定制业务逻辑 | 自建 |
| 有公开Server且满足需求 | 直接用 |

#### 4.2 从业务场景推导工具

课程中的推导过程：

**用户会说的话分类**：
- "我要退款" → 需要先查资格再提交
- "我的退款审批了没" → 查退款进度
- "不退了" → 撤销申请（PENDING状态才能撤）
- "为什么被拒了" → 查状态时一起返回拒绝原因

**推导出的四个工具**：

| 工具 | 入参 | 出参 |
|------|------|------|
| check_refund_eligibility | orderId | eligible、reason、deadline、amount |
| submit_refund | orderId、reason | refundId、status、estimatedDays |
| get_refund_status | orderId或refundId | status、statusLabel、rejectReason |
| cancel_refund | refundId | success、message |

课程强调：
> "statusLabel字段专门给LLM用，LLM直接把statusLabel说给用户，不需要自己翻译PROCESSING是什么意思。工具的返回值设计要考虑LLM的使用方式，不是只考虑数据完整性。"

#### 4.3 MCP Server代码结构

```
hify-mcp-refund/              ← 独立Maven项目
├── pom.xml
└── src/main/java/
    ├── RefundMcpApplication.java  ← Spring Boot启动类
    ├── config/
    │   └── McpConfig.java        ← 注册工具到MCP SDK
    └── service/
        └── RefundService.java    ← 真正的业务逻辑
```

课程总结：
> "MCP Server就是一个HTTP Server。MCP Server对Hify是黑盒，Hify只存了一个endpoint地址，发标准协议请求，不关心里面是Java还是Python，不关心查的是MySQL还是Oracle。这就是标准化协议的价值。"

#### 4.4 工具注册

```java
// description写法：说清楚什么情况下调这个工具
"check_refund_eligibility": 
  "查询订单退款资格。用户说'我要退款'时，先调此工具确认是否符合条件，
   再决定是否提交申请。不要跳过此步直接提交。"
```

课程强调：
> "调用失败时返回{\"error\": \"错误原因\"}，isError=true。不要让SDK抛出异常中断整个对话。"

## 五、MCP调试工具

### 流程环节说明
MCP Server接入前需要验证工具本身的行为。课程展示了调试工具的设计。

### 课程原文内容

#### 5.1 调试工具设计

```
功能：
1. 左侧：工具列表（从mcp_tool表读取），点击选中工具
2. 右侧调试面板：
   - 顶部显示工具description（让开发者确认描述是否合理）
   - 根据inputSchema动态渲染参数表单
   - 调用按钮 + 结果展示区（返回内容 + 耗时）
   - 保留最近5次调用记录

后端接口：
POST /api/v1/mcp-servers/{id}/debug
  入参：toolName、arguments（Map）
  逻辑：复用McpClientService.callTool()
  返回：result（String）、elapsedMs（Int）
```

#### 5.2 验收流程

课程中的验收步骤：
```
1. 工具自身跑通（用curl调MCP Server）
2. 调试工具验证（不经过对话引擎，直接测工具）
3. 接入Agent（绑定工具到Agent）
4. 端到端对话（从用户发消息到收到回答）
```

## 六、实操体验总结

### 流程环节说明
实操课总结了工作流开发中的真实体验。

### 课程原文内容

#### 6.1 快在哪里

> "元数据CRUD写得很快。三张表结构清晰，创建时拆分写入，查询时组装还原。"

> "NodeExecutor体系的代码也很顺。和14讲Provider适配层是同一个模式，统一接口+按type分发+Spring自动注册。Claude Code在这种'已有模式的复用'上表现很好。"

#### 6.2 慢在哪里

> "第一个是概念建立阶段。工作流是我没做过的子系统，一开始脑子里没有完整的图。"

> "第二个是执行引擎的异常分支。正常路径Claude Code基本能写对，但边界情况大概率遗漏。"

#### 6.3 最让人惊喜的

> "同一个智能客服Agent，问'耳机坏了怎么保修'走售后路径，问'最新蓝牙耳机有什么功能'走售前路径。三条路径，三种不同的回答风格，都是一个工作流配置驱动的。"

> "查workflow_node_run表，每个节点的输入输出、执行耗时，成功失败状态都清清楚楚。出了问题能精确定位到哪个节点。"
