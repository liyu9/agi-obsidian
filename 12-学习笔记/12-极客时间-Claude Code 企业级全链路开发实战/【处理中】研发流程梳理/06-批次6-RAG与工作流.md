## 一、核心功能基础实操课

### 流程环节说明
实操课展示了核心功能开发的真实节奏，包括快在哪里、慢在哪里，以及Skill沉淀的实际效果。

### 课程原文内容

#### 1.1 快在哪里

> "有了 08-12 讲的基础设施，每个业务模块的'脚手架'几乎不占时间。Entity 继承 BaseEntity、Mapper 继承 BaseMapper、Controller 套 Result + PageHelper，这些模板性的东西，一条指令生成，review 一遍，基本不用改。"

> "Skill 带来的节奏变化更明显。13 讲手动做 Provider，14 讲沉淀了模块交付 Skill，15 讲做 Agent 时一句'按模块交付 Skill 的流程，帮我做 Agent 模块'就启动了。Claude Code 自动按流程走，在数据模型确认环节停下来等我拍板，不多做也不漏做。"

> "前端对接也比以前快很多。11 讲封装的 HifyTable 和 HifyFormDialog，每个管理页面的改动量非常小。基础组件的回报，在用的时候才真正感受到。"

#### 1.2 慢在哪里

> "第一类是'想清楚'的时间。每个模块开始前，供应商分析、数据模型讨论、边界决策，这些和 Claude Code 来回讨论的时间不短。Provider 模块将近一个小时，对话引擎的设计讨论甚至超过了写代码的时间。但这个时间花得值，这些决策如果漏掉，后面返工的代价是几倍。"

> "第二类是跨层问题的排查。流式响应在 curl 里验证是对的，上了浏览器发现打字机效果失效，是 Nginx 缓冲的问题，curl 绕过了 Nginx 所以发现不了。"

#### 1.3 核心体验

> "最让我惊喜的是：Claude Code 按接口兼容性做了分类，指出 DeepSeek、Moonshot 这些国产模型接口和 OpenAI 完全兼容，只需要换 baseUrl。这个洞察直接影响了架构决策——不是每接一个供应商就写一套适配代码，而是设计一个'OpenAI 兼容'类型让用户自己配 baseUrl。"

## 二、RAG知识库：四步探路法

### 流程环节说明
当需要给系统加入一个完全陌生的技术能力时，课程提出了"四步探路法"。

### 课程原文内容

#### 2.1 第一步：从业务痛点出发

> "更好的方式是从业务痛点出发，用自己的场景问：我的智能客服 Agent 现在只能靠模型的通用知识回答问题，无法引用公司的产品手册和政策文档。我听说 RAG 可以解决这个问题。帮我解释：RAG 的核心思路是什么？"

课程强调：
> "你越能描述清楚自己的痛点，它的回答就越有针对性。"

#### 2.2 第二步：拆解技术组件，缩小陌生范围

> "为什么要专门问这个问题？因为 RAG 这个词作为整体看起来很复杂，但拆开来之后，你会发现大部分组件你已经会了，真正陌生的可能只有一两个点。"

Claude Code拆解的RAG六个组件：

**阶段一：文档入库管道**
- 文档解析器：TXT直接读，PDF用Apache POI
- 文本分块器：chunk_size 512 token，overlap 64 token
- Embedding模型：文本转向量
- 向量数据库：存向量，支持相似度检索

**阶段二：检索对话链路**
- 检索器：用户问题向量化，Top-K检索
- Prompt组装器：把检索结果拼进上下文

课程判断：
> "六个组件里，真正陌生的只有向量数据库。文档解析是调库，文本分块是纯代码逻辑，Embedding调API和调Chat Completion一样，检索器和Prompt组装器是改ChatService逻辑。把陌生范围从整个RAG缩小到向量数据库，心理压力少了很多。"

#### 2.3 第三步：给约束让Claude Code做选型对比

> "向量数据库有哪些主流选项？我的约束是：Java技术栈、已有PostgreSQL、一期数据量不大、基本的相似度检索够用。帮我对比pgvector、Milvus、Qdrant的优缺点。"

课程选择pgvector：
> "选pgvector。理由和12讲不引入LangChain4j是同一个逻辑：能不加新依赖就不加。Hify已经在用PostgreSQL，pgvector只是一个扩展，不引入新组件，不增加运维负担。"

技术决策原则：
> "用能解决当前问题的最简单方案，不为假想的未来过度设计。"

#### 2.4 第四步：最小Demo优先，跑通再说

> "选型定了，但光知道选哪个不够。在把pgvector集成进Hify之前，我需要先有手感——能插入向量、能查到相似结果，知道它到底怎么工作。"

课程展示的最小Demo：
```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE document_chunk (
    id        BIGSERIAL PRIMARY KEY,
    content   TEXT NOT NULL,
    embedding vector(1536)
);
-- 相似度查询：<=> 是余弦距离
SELECT content, 1 - (embedding <=> '[...]') AS similarity
FROM document_chunk
ORDER BY embedding <=> '[...]'
LIMIT 3;
```

课程总结：
> "这类坑：'这个类型需要特殊处理'是新技术里最容易在集成阶段踩到的。先跑最小Demo的价值之一就是把这些坑提前暴露出来，在一个干净的环境里解决，而不是混在业务代码里排查。"

## 三、RAG知识库：数据管线设计

### 流程环节说明
数据管线是独立的新模块，需要从零开始建。课程展示了完整的数据管线设计和实现方法。

### 课程原文内容

#### 3.1 数据管线三块

Claude Code拆解的RAG特性分三块：

**第一块：知识库与文档的CRUD**
> "管线不是凭空跑的，得先有知识库容器，得有文档上传入口。这是骨架。"

**第二块：管线处理逻辑**
> "文档上传后，异步触发五步处理：状态更新 → 解析文本 → 分块 → 向量化 → 存入pgvector。"

**第三块：前端页面**
> "管理员需要界面来操作，创建知识库、上传文档、看处理进度、查看分块结果。"

开发顺序：1 → 2 → 3 → 验收

#### 3.2 管线处理指令

```
知识库文档处理管线，在异步线程池中执行。
管线有五个环节，每个环节拆成独立的 private 方法：
1. 状态更新：document.status = PROCESSING
2. 解析：extractText(filePath, fileType) → String
3. 分块：splitChunks(text) → List<ChunkDTO>，chunk_size=512 token，overlap=64 token
4. 向量化：embedChunks(List<ChunkDTO>) → 补上 embedding 字段
5. 存储：JdbcTemplate.batchUpdate() 批量写入 pgvector
异常处理：
- 任何一个环节失败，都要 catch 住，更新 document.status=FAILED
- 不能因为一个文档处理失败影响线程池里其他文档的处理
```

代码组织原则：
> "每个环节独立方法，管线只负责串联。某个环节出了问题，能精确定位是哪一步，单独测试单独修复。"

#### 3.3 最小侵入点接入对话引擎

课程中的关键决策：

> "17讲的sendMessage有六步链路。RAG检索应该插在哪一步？"

Claude Code梳理的九步链路：
```
1. 加载Session → 拿到agentId
2. 加载Agent → 拿到配置
3. 加载ModelConfig → 拿到modelId
4. 加载Provider → 拿到baseUrl
5. 写入用户消息到MySQL
6. 从Redis加载上下文历史
7. 拼messages数组
8. 调LLM streamChat
9. 写入assistant消息，更新Redis
```

RAG插在第6步之后、第7步之前：
```
6.5 ★ RAG检索：用户问题 → Embedding → pgvector Top-K → 相关chunk
```

课程强调：
> "只有system变了，其余不动。检索结果注入system prompt，对历史消息和当前消息完全无侵入。这是最小侵入的接入方式。"

#### 3.4 增量开发三步走

> "圈定改动范围 → 验证旧功能没坏 → 验证新功能生效。三步的顺序不能乱，每一步都是对前一步的护栏。"

改动约束指令：
```
修改ChatService的buildMessages方法，在System Prompt后插入RAG检索结果。
改动范围：只改buildMessages这一个方法。
不要修改流式调用、SseEmitter转发、消息存储的逻辑。不要改Controller层。
```

## 四、RAG知识库：三维验收

### 流程环节说明
RAG的验收要覆盖三个维度：检索链路是否通、回答质量是否变、边界场景是否守住。

### 课程原文内容

#### 4.1 验收一：对比绑知识库前后的回答

测试文档内容：
```
退换货政策：
自签收之日起七天内，未拆封商品支持无理由退货。
已拆封但存在质量问题的商品，三十天内可申请换货。
```

绑知识库前回答：
> "根据一般的电商行业惯例，大多数平台支持七天无理由退货……"

绑知识库后回答：
> "根据退换货政策，自签收之日起七天内，未拆封商品支持无理由退货。如果商品已拆封但存在质量问题，三十天内可申请换货。"

#### 4.2 验收二：边界场景——文档里没有的问题

问：`"你们有没有学生优惠？"`

预期回答：
> "根据现有的产品手册，我没有找到关于学生优惠的相关信息。如需了解，建议联系人工客服确认。"

课程强调：
> "没有编造，诚实告知边界。这是Prompt里那句'如果资料中没有相关信息，直接说我没有找到相关资料'发挥的作用。"

#### 4.3 验收三：没有绑知识库的Agent不受影响

> "换一个没有绑知识库的Agent，正常对话，确认行为和之前完全一致。日志里没有任何RAG相关的输出。这一步确认的是：RAG的开关在Agent维度，没有绑知识库的Agent完全不受影响，最小侵入的承诺兑现了。"

## 五、工作流编排：概念建立

### 流程环节说明
工作流是Hify的另一个高级特性。课程先建立概念，再设计存储结构。

### 课程原文内容

#### 5.1 工作流是什么

> "单Prompt Agent的处理方式：把这句话扔给LLM，LLM凭训练知识编一个回答。问题是它根本没有查你的订单，不知道订单号、收货地址、快递状态。"

> "工作流的处理方式：把这件事拆成有序的步骤，每步做一件具体的事。问'退货政策是什么'，单Prompt够用；问'我的订单到哪了'，必须走工作流，因为答案在数据库里。"

#### 5.2 工作流在代码里长什么样

> "两张表，两个概念——节点 + 连线。"

**节点：做什么**
```java
WorkflowNode {
    workflowId = 1
    type = "LLM"       // 调LLM / 调API / 做判断
    name = "意图识别"
    config = {"prompt": "判断用户意图，返回 ORDER_QUERY 或 POLICY_QUERY"}
}
```

**连线：做完去哪**
```java
WorkflowEdge {
    sourceNodeKey = "classify"   // 从"意图识别"
    targetNodeKey = "router"     // 到"条件判断"
    condition = null              // 无条件，直接走
}
```

课程总结：
> "节点存'做什么'，连线存'做完去哪'，执行引擎按连线一步一步走完。存库是平铺的两张表，执行时加载进内存变成Map + while循环。"

## 六、工作流数据模型设计

### 流程环节说明
课程展示了工作流的完整数据模型设计，包括三张表和sealed interface类型安全方案。

### 课程原文内容

#### 6.1 三张表结构

```
MySQL:
  workflow          — 工作流基本信息（名称、描述、状态）
  workflow_node     — 节点（node_key、type、config JSON）
  workflow_edge     — 连线（source→target、condition）
```

课程强调的一个设计细节：
> "连线引用node_key字符串，不引用数据库主键id。原因是node_key由业务逻辑决定，前端拖拽时生成的临时标识可以直接存，不依赖数据库自增顺序。"

#### 6.2 JSON字段存配置

不同节点类型的配置格式差异大：
```json
// LLM节点
{"modelConfigId": 5, "prompt": "...", "outputVariable": "intent"}

// 条件分支节点
{"expression": "{{intent}} == 'ORDER_QUERY'", "outputVariable": "conditionResult"}

// HTTP节点
{"url": "...", "method": "GET", "outputVariable": "orderInfo"}

// 知识库检索节点
{"knowledgeBaseId": 3, "query": "{{userMessage}}", "topK": 5}
```

课程判断：
> "字段结构差异这么大，强行拆列会让表结构很难看。字段结构不确定、不同记录格式差异大的时候用JSON存；字段结构固定、需要按字段查询的时候才拆列。"

#### 6.3 sealed interface类型安全

```java
public sealed interface NodeConfig
    permits StartNodeConfig, LlmNodeConfig, ConditionNodeConfig,
            ApiCallNodeConfig, KnowledgeNodeConfig, EndNodeConfig {}

public record LlmNodeConfig(Long modelConfigId, String prompt, String outputVariable)
    implements NodeConfig {}

// 解析时按type分发
NodeConfig config = switch (type) {
    case "LLM"       -> objectMapper.readValue(configJson, LlmNodeConfig.class);
    case "CONDITION" -> objectMapper.readValue(configJson, ConditionNodeConfig.class);
    // ...
};
```

课程总结：
> "执行引擎里用switch模式匹配处理不同类型，编译器帮你检查穷举，漏写任何一个case就报错。新增节点类型只需要加一个record，不改其他代码。"

#### 6.4 CRUD实现约束

```
约束：
- 创建接口接收完整请求体（包含nodes和edges），拆分写入三张表
  三张表在同一个事务里，任何一张写失败全部回滚
- 查询详情接口从三张表组装回完整结构返回
- 更新工作流时，先逻辑删除原有的nodes和edges，再批量插入新的
  不要做diff更新，直接替换
- 删除工作流时，关联的nodes和edges一起逻辑删除
```
