## 一、顶层设计全流程实操

### 流程环节说明
顶层设计不是一次性完成的活动，而是分场景逐步推进的过程。课程以实操方式展示了四个场景的完整操作流程。

### 课程原文内容

#### 1.1 场景一：产品定义实操

**第一步：梳理竞品功能全景**

Claude Code的指令：
```
帮我梳理 Dify（https://dify.ai）这个产品的核心功能模块，
按类别分组，每个模块用一两句话说明它做什么。
```

实操要点：
> "Claude Code 几秒钟给出八大模块的结构化清单。我拿它的输出和 Dify 官方文档对了一遍，修正了过时描述，补了 MCP 协议支持。强调'AI 加速信息收集，但你要验证'。"

**第二步：功能取舍**

Claude Code的指令：
```
我要基于 Dify 做一个简化版的 AI Agent 平台，叫 Hify。
约束条件：一个人开发，面向团队内部 20-50 人使用，本地部署。
请从刚才梳理的功能列表中，帮我判断哪些是必须做的核心功能，
哪些可以砍掉，给出每个的理由。
```

实操要点：
> "Claude Code 给了三档分类（必须做 / 降级简化 / 砍掉），这个分档方式本身就有价值。重点展示 RAG 的判断，它建议保留，理由是'内部部署区别于 ChatGPT 的核心价值'。"

**第三步：技术选型**

Claude Code的指令：
```
Hify 是一个 AI Agent 开发平台，一个人开发，本地部署，目标 20-50 人使用。
帮我对比以下技术方案的优劣：
1) Spring Boot + Vue  2) Go + React  3) Python FastAPI + React
重点考虑开发效率、生态成熟度、AI 领域 SDK 支持、运维复杂度。
```

追问与决策：
> "Claude Code 推荐 FastAPI，还给了'Java + Python 混合'的折中方案。我否决了混合方案，一个人维护两套技术栈是灾难。最终选 Spring Boot：AI 生态劣势存在，但工程化和技术栈统一性优先。"

#### 1.2 场景二：应用架构设计实操

**第一步：应用架构选型**

Claude Code的指令：
```
Hify 是一个 Spring Boot 单体应用，功能包括模型提供商管理、Agent 配置、
对话引擎，知识库 RAG、简版工作流、MCP 工具接入。一个人开发，一期 50 人使用，
但后续可能要扩到几千人。代码内部怎么组织？给我方案对比。
```

追问指令：
```
一个人维护六七个微服务，每个要独立部署、独立配置、独立监控，
精力消耗会不会太大
```

实操要点：
> "Claude Code 给了 3 个方案，推荐微服务。我用'一个人维护太重'这个现实约束否决，选模块化单体。展示最终的 Maven 模块划分（七个业务模块 + common）。"

**第二步：代码组织规范**

Claude Code的指令：
```
Hify 是模块化单体，用 Spring Boot + MyBatis-Plus。帮我定义代码组织规范，
覆盖：每个模块内部的分层结构、每一层的职责边界、跨模块调用的规则。
要求具体到 AI 能直接执行，不要模糊的描述。
```

实操要点：
> "强调'这些规范是给 AI 写的，不是给人写的'。Controller 只做参数校验、跨模块走 Service 接口，人凭习惯知道，AI 不知道。展示规范写进 CLAUDE.md 的过程。"

**第三步：外部调用设计**

Claude Code的指令：
```
Hify 要调用多个外部 LLM API（OpenAI、Claude、Gemini、Ollama），
这些调用慢且不稳定。从线程管理、容错、超时、重试四个维度，给出完整的技术方案。
```

追问指令：
```
流式响应用 SSE，Spring MVC 怎么处理？需不需要引入 WebFlux？
```

实操要点：
> "Claude Code 建议 WebFlux，我否决，不增加技术栈复杂度。SseEmitter + 独立线程池 + 120 秒超时，50 人够用。展示线程池隔离、熔断、超时、重试的完整方案写进 CLAUDE.md。"

#### 1.3 场景三：部署架构与数据设计实操

**第一步：当前部署架构**

Claude Code的指令：
```
Hify 是模块化单体，技术栈 Spring Boot + Vue + MySQL + Redis + pgvector。
目标 50 人内部使用，生产环境用 Docker + K8s 部署。
帮我设计当前阶段的部署架构：有哪些组件、请求怎么流转、每个组件的职责是什么。
```

实操要点：
> "Claude Code 给了组件职责表 + '当前做 vs 暂时跳过'对比表。重点展示'暂时跳过'的判断——单副本够用、MQ 是过度设计、不需要链路追踪。"

**第二步：性能瓶颈预判**

Claude Code的指令：
```
基于 Hify 当前的部署架构，帮我分析：这个系统的性能瓶颈可能在哪？
按严重程度排序，每个瓶颈给出触发条件和一期是否需要处理。
```

实操要点：
> "Claude Code 给了 7 个瓶颈的排序表，结论是'一期只做两件事'。这张表就是你的系统软肋地图，现在不处理但心里有数。大部分工程师不会提前想这个，Claude Code 帮你几分钟画出来。"

**第三步：数据库规范**

Claude Code的指令：
```
Hify 用 MySQL 8.x + pgvector。帮我定义数据库层面的性能规范，
覆盖：索引设计原则、大表预判和应对策略、分页查询注意事项、通用字段约定。
要求具体到 AI 建表时能直接执行。
```

实操要点：
> "展示 Claude Code 给的五条索引规则（带正反例代码）。重点展示'逻辑删除字段必须加进索引'和'游标分页'，这些不写进规范 AI 就不会遵守。展示 pgvector HNSW 索引规范。"

## 二、工程初始化方法论

### 流程环节说明
工程初始化是AI辅助开发的重要场景。课程总结了三个核心方法论来确保初始化质量。

### 课程原文内容

#### 2.1 任务拆解标准

课程中提出的判断标准：

> "**标准一：生成的代码量是否超出你一次能 review 的范围。** 十几行代码，肉眼扫一遍就行，不用拆。几十个文件、几百行配置，一次看不过来，必须拆。"

> "**标准二：步骤之间是否有依赖关系。** 如果第二步依赖第一步的结果（比如业务模块的 pom 依赖公共模块的 pom），那就应该先完成第一步、验证正确，再做第二步。"

#### 2.2 初始化四步流程

课程中确定的四步顺序：

**第一步：Maven 多模块骨架**
- 父 pom + 子模块 pom + 目录结构
- 验收：`mvn clean install` 能通过

**第二步：hify-common 公共基础设施**
- Result、PageResult、ErrorCode、BizException
- GlobalExceptionHandler、全局异常处理
- MyBatis-Plus配置、Redis配置

**第三步：业务模块空壳**
- 每个模块的 package 结构
- Controller、Service、Mapper、Entity、DTO、Config

**第四步：验收**
- `mvn spring-boot:run` 能启动
- `/api/v1/health` 返回200

#### 2.3 影响范围review法

课程中总结的review优先级：

> "**第一优先级：结构性问题。** 模块依赖关系对不对？pom 里的依赖声明和 CLAUDE.md 里定义的架构一致吗？package 路径对不对？"

> "**第二优先级：公共模块的核心代码。** Result 类的字段和方法对不对？全局异常处理器的捕获优先级对不对？"

> "**第三优先级：配置文件。** application.yml 里的配置项对不对？有没有遗漏？有没有硬编码不该硬编码的东西？"

> "**最后才看：业务模块空壳。** 只是 package 结构和占位类，几乎没什么可出错的，扫一眼确认结构一致就行。"

## 三、后端骨架搭建

### 流程环节说明
后端骨架是整个工程的基础。课程采用"分步验收"的方式逐步推进。

### 课程原文内容

#### 3.1 Maven多模块骨架

Claude Code的指令：
```
按照 CLAUDE.md 中的项目结构和技术栈，创建 Hify 的 Maven 多模块工程骨架。
父 pom 声明所有子模块，统一管理 Spring Boot、MyBatis-Plus、Redis 等版本号。
子模块之间的依赖关系按 CLAUDE.md 中定义的架构来。
只创建 pom 和目录结构，不需要写 Java 代码。
```

重点检查三件事：
> "模块声明和目录结构是否一致；依赖关系是否正确；版本管理是否统一。"

#### 3.2 hify-common公共基础设施

任务拆分为五个小任务：

**任务一：统一响应 Result 和分页 PageResult**
> "在 hify-common 中创建统一响应类。按照 CLAUDE.md 接口规范：Result<T> 包含 code、message、data 三个字段。"

**任务二：错误码枚举和业务异常**
> "在 hify-common 中创建错误码枚举 ErrorCode 和业务异常类 BizException。"

**任务三：全局异常处理器**
> "在 hify-common 中创建全局异常处理器 GlobalExceptionHandler。捕获 BizException 返回对应错误码，捕获 MethodArgumentNotValidException 返回参数校验错误。"

**任务四：MyBatis-Plus 配置**
> "在 hify-common 中创建 MyBatis-Plus 配置类。包含：分页插件、自动填充（createTime、updateTime）、逻辑删除配置。"

**任务五：Redis 配置**
> "在 hify-common 中创建 Redis 配置类。包含：RedisTemplate 序列化配置、基础的 RedisUtil 工具类。"

#### 3.3 业务模块空壳

Claude Code的指令：
```
为 hify-provider、hify-agent、hify-chat、hify-mcp 等业务模块创建标准的 package 结构。
按照 CLAUDE.md 代码组织规范，每个模块包含 controller/service/service-impl/mapper/entity/dto/config 目录。
每个模块只创建 package 和一个空的占位类，不需要写业务代码。
```

## 四、前端工程搭建

### 流程环节说明
前端工程同样需要分步搭建，重点是前后端规范的对齐。

### 课程原文内容

#### 4.1 项目骨架

Claude Code的指令：
```
初始化 Hify 前端项目 hify-web。Vue 3 + TypeScript + Vite + Element Plus。
目录结构按 CLAUDE.md 中定义的前端结构来。
Vite 开发服务器配置代理：/api 请求转发到 localhost:8080。
```

#### 4.2 axios统一请求层

Claude Code的指令：
```
在 hify-web/src/utils/ 下创建 request.ts，封装 axios 实例。
baseURL 设为 /api。
响应拦截器里判断 code：200 直接返回 data 字段（自动解包），非 200 用 ElMessage.error 提示 message。
导出 get、post、put、del 四个方法。
```

课程中强调：
> "为什么要在拦截器里自动解包 data？因为后端定了统一响应格式 `Result<T>`，每个接口都返回 `{ code: 200, message: "success", data: {...} }`。前端的 axios 封装要和这套格式对接，让业务代码不需要每次都手动处理 code 判断和 data 解包。"

#### 4.3 路由和页面空壳

Claude Code的指令：
```
在 hify-web 中配置 Vue Router，创建以下路由和对应的空壳页面组件：
模型管理、Agent 管理、对话。
每个空壳页面只显示页面名称。
再创建一个 App.vue 布局：左侧 Element Plus 菜单栏，三个菜单项对应三个路由，右侧内容区用 router-view。
```

## 五、启动脚本与一键启动

### 流程环节说明
启动脚本是提升开发体验的关键。课程用Makefile封装了所有启动操作。

### 课程原文内容

#### 5.1 start.sh

Claude Code的指令：
```
写一个 start.sh 脚本，放在项目根目录。
功能：检查 MySQL 和 Redis 是否可用，构建后端并后台启动，
轮询等待后端健康检查通过，启动前端开发服务器。
加上错误处理：任何一步失败就停止并提示。
```

#### 5.2 stop.sh

Claude Code的指令：
```
写一个 stop.sh 脚本，优雅停止后端和前端进程。
按 PID 文件找进程，先 SIGTERM 再等待，超时 SIGKILL。
```

#### 5.3 Makefile

Claude Code的指令：
```
写一个 Makefile，包含以下 target：
make start（启动）、make stop（停止）、make restart（重启）、
make build（构建后端 + 前端）、make clean（清理构建产物）、
make package（打包成可分发的 tar.gz）。
```

课程中评价：
> "这 3 个文件加起来可能就一两百行脚本，但它们让整个项目的使用体验提升了一个档次。拉下代码，`make start` 就跑起来了，`make package` 就能打包分发。"

## 六、咨询模式与执行模式

### 流程环节说明
课程提出了两种AI协作模式，用于不同场景。

### 课程原文内容

#### 6.1 两种模式的定义

> "**执行模式：你想清楚了 → 给指令 → Claude Code 做 → 你验收。** 适合你对任务很清楚的时候。"

> "**咨询模式：你知道大方向但不确定细节 → 先问 Claude Code → 它帮你梳理 → 你判断取舍 → 再给指令执行。** 适合不确定性高的时候。"

#### 6.2 咨询模式的实际应用

课程中展示的咨询过程：

Claude Code的指令：
```
Hify 项目工程骨架已经搭好。现在要开始做业务功能了。
在写业务代码之前，还需要准备哪些基础组件？
从数据库层、接口层、外部调用、缓存、可观测性几个角度帮我梳理，
每个组件说明它解决什么问题。
```

Claude Code的发现：
> "Claude Code 帮我发现了两个我自己会漏掉的：schema.sql 和 @MapperScan。不是什么高深的东西，但你在列基础组件清单时很容易忽略。脑子里想的都是 BaseEntity、线程池这些有设计感的东西，反而忘了最基础的东西，比如表还没建、扫描路径不对。"

课程总结：
> "这就是咨询模式的核心价值，用它做遗漏检查。Claude Code 见过的项目比你多，它的建议不能直接照搬，但用来查漏补缺非常好。"

## 七、基础组件三档优先级

### 流程环节说明
基础组件按优先级分三档，确保关键路径优先打通。

### 课程原文内容

#### 7.1 第一档：必须先做，否则业务代码跑不起来

| 组件 | 问题 |
|------|------|
| 数据库初始化脚本 | Spring Boot启动时需要库和表已存在 |
| @MapperScan扫描路径 | 业务模块的Mapper包扫描不到，所有Mapper注入报错 |
| 线程池配置 | LLM调用的Bean必须存在，否则注入失败 |

#### 7.2 第二档：做业务时同步补，第一个列表接口之前搞定

| 组件 | 问题 |
|------|------|
| BaseEntity | 每个实体都有公共字段，不封装就重复写 |
| 统一分页封装 | 几乎每个列表接口都要分页 |
| 入参校验 | 每个创建/更新接口都需要参数校验 |
| 统一时间序列化 | 不配的话Jackson输出数组格式 |
| Spring Cache集成 | Provider/Agent配置需要Redis缓存 |

#### 7.3 第三档：可以后补，不影响功能开发

| 组件 | 问题 |
|------|------|
| HTTP客户端封装 | 调LLM API的基础 |
| Resilience4j熔断配置 | 每个提供商独立熔断器 |
| 结构化日志配置 | 区分开发/生产环境，请求日志过滤器 |

## 八、后端基础组件详解

### 流程环节说明
课程详细展示了每个基础组件的设计决策和实现要点。

### 课程原文内容

#### 8.1 数据库初始化脚本

Claude Code的指令：
```
按照 CLAUDE.md 的数据库规范和数据模型，生成所有业务表的建表 DDL。
放在 hify-app/src/main/resources/db/schema.sql。
表名小写下划线、主键 id bigint 自增、时间字段 created_at/updated_at datetime、
逻辑删除 deleted tinyint 默认 0、字符集 utf8mb4。
包含：provider、model_config、agent、agent_tool、mcp_server、chat_session、chat_message。
```

#### 8.2 线程池配置

课程中的设计决策：
> "场景：用户在对话（调 LLM，卡了 30 秒），同时另一个用户打开管理页面看 Agent 配置。如果共用线程池，对话请求占满了所有线程，管理页面一直转圈。"

Claude Code的指令：
```
在 hify-common 中创建 ThreadPoolConfig。
定义两个线程池：
- llmExecutor（核心 10，最大 50，队列 100，线程名前缀 llm-，拒绝策略 CallerRunsPolicy）用于 LLM 调用
- asyncExecutor（核心 5，最大 20，队列 200，线程名前缀 async-）用于日志异步写入等非关键任务
```

参数依据：
> "目标 20-50 人同时在线，一半的人同时对话就是 10-25 个并发 LLM 调用，核心线程 10 够用，最大 50 留余量。"

#### 8.3 HTTP客户端封装

课程中的技术选型：
> "帮我在 hify-common 中创建 LlmHttpClient 类。内部持有 RestTemplate（连接超时 5s，读超时 60s）和 OkHttpClient（连接超时 5s，读超时 120s）。"

超时时间的决策：
> "为什么超时设这么长？LLM API 不是普通 HTTP 调用，GPT-4 一次响应可能 10-20 秒，流式可能持续一两分钟。60 秒和 120 秒是实际经验的平衡。这也是我们作为程序员的价值所在，我们会去理解需求，从宏观去思考超时时间是多久。"

#### 8.4 熔断与重试

课程中的设计决策：
> "为什么每个 Provider 独立熔断器？OpenAI 挂了不代表 Claude 也挂了。共用的话一家失败会把其他正常的也拦住。"

重试策略：
> "重试按异常类型区分，认证失败重试一百次也不会成功，只有'暂时性'的失败才值得重试。"

#### 8.5 结构化日志

Claude Code的指令：
```
在 hify-common 中配置统一日志。
logback-spring.xml 区分环境：开发环境控制台彩色输出，生产环境 JSON 格式输出到文件（按天滚动，保留 30 天）。
创建 RequestLogInterceptor（HandlerInterceptor），记录每个请求的 method、path、status、耗时，慢请求（>1s）标 WARN。
请求进入时生成 traceId 放入 MDC，请求结束时清理。
```

traceId的价值：
> "一个对话请求从 Controller 进来，经过 Service、调 LLM，写数据库，可能产生十几条日志。一个 ID 串起整条链路，排查时不用大海捞针。"
